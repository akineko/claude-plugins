# Skill Respec

既存スキルを、別バージョン・別世代の Claude に「最新の知識と判断で再設計させる」ためのプロンプトを生成する。

## 1. このスキルが解こうとしている問題

新バージョンの Claude や別系統の Claude に同じ目的のスキルを書かせて比較したい、というニーズがある。
このとき次のジレンマが起きる。

- **原文を逐語的にトレースさせる**プロンプトを作ると、再生成先 Claude の知識や判断力が原文の選択に縛られ、世代間の差や能力の伸びが見えなくなる
- 逆に「同じ目的のスキルを作って」**だけ**だと、対象範囲やスキルが扱うべき入出力すらブレてしまい、もはや「同じスキル」と呼べなくなる

このスキルは中間の解として、次のように振る舞う。

- スキルの **骨組み**（§4 の 6 要素）は自動抽出してプロンプトに固定する
- それ以外の **実装選択肢** は抽出してユーザーに「含める / 除外」を選ばせる
- 「除外」と選んだ要素は、出力プロンプトに **言及しない**（明示的に「使うな」とは書かない）。再生成先 Claude が独自に別の選択をする余地を残すため

## 2. 入出力

**入力**: 対象スキルのディレクトリパス
（例: `ai-tuner/skills/prompt-engineer/`、`dev-toolkit/skills/codebase-investigator/`）

**出力**: 再生成プロンプトを `.claude/respec-prompts/<plugin>__<skill>.md` に保存

- ファイル名は `<plugin>__<skill>.md` 形式（§7.1）
- 出力ディレクトリが存在しなければ作成する
- 既存ファイルがある場合は §7.2 に従う

## 3. ワークフロー

1. **対象スキルを読み込む**
   - `SKILL.md`（frontmatter と本体すべて）
   - `references/*.md`（あれば全文）
   - `scripts/*`、`assets/*` は **ファイル名と1行説明のみ**（中身は読まない）
   - `evals/evals.json`（あれば、評価観点の抽出に使う）
   - 上記の存在パターン自体がスキルの構造を示すため、ファイル一覧は重要

2. **骨組みを抽出する（§4）**
   - 6 要素を確定する。ユーザー確認を挟まずプロンプトに組み込む

3. **実装選択肢を抽出してユーザーに提示する（§5）**
   - 10〜20 項目を上限の目安に、過不足ない粒度で挙げる
   - 各項目に「推奨: 含める / 除外」と理由を付ける
   - 1 メッセージにまとめて提示し、ユーザーから一括で選択を受け取る

4. **再生成プロンプトを組み立てる（§6 のテンプレート）**

5. **`.claude/respec-prompts/<plugin>__<skill>.md` に書き出し、ユーザーに完了報告する**
   - 「このプロンプトを別世代/別バージョンの Claude に渡してください」と伝える
   - ファイルパスを明示する

## 4. 骨組みの 6 要素（自動抽出・固定）

「骨組み」は、これが欠けるとスキルの同一性が失われる要素。逐語ではなく要約として抽出する。

### 4.1 目的（Purpose）

このスキルが解決する問題と、解決後の状態。2〜4 文で記述する。
原文に「動機」「なぜ」「背景」が書かれていればそこを起点にする。

### 4.2 トリガー条件 / 想定ユーザー（Triggers）

`description` から「いつ起動するか」と「誰のための処理か」を抽出。
トリガーフレーズは原文のニュアンスを残しつつ、**3〜5 個に絞って**列挙する。

### 4.3 入出力（I/O）

- 入力: ユーザーが渡すもの、参照するファイル種別
- 出力: 生成・編集する成果物、保存場所、形式

具体的な閾値（行数・個数）はここに入れない。それは §5 に分類する。

### 4.4 必須の処理段階（Required Stages）

スキルが踏む処理を「段階」として抽出する。書き方の指針：

- 各段階は「**何を達成するか**」だけを書き、「**どう達成するか**」は書かない
  - ❌「Anthropic 8 原則に従って書く」
  - ✅「中核原則を適用して書く（原則の選定は再設計時に判断）」
- 順序が本質的に重要な場合のみ番号付きにする
- 段階間の依存関係（A の出力が B の入力になる等）を 1 行で補足する

### 4.5 評価基準（Acceptance Criteria）

スキルの出力が「合格」と言える条件。原文に明示されていなければ、本文と `evals/` から推定する。
具体的なチェックリスト項目（"行数 200 行以下" 等）は §5 行き。ここでは「何をもって良しとするか」を抽象的に書く。

### 4.6 制約（Constraints）

破ると意味をなさない条件。例：

- 出力ファイルのパス・命名規則
- 触ってよい/触ってはいけないファイル領域
- 外部 API・ツールの必須使用、または禁止
- 機密情報・スコープに関するルール

これらは再生成先 Claude にも引き継ぐ。

## 5. 実装選択肢の判定と提示

### 5.1 判定基準

ある記述が「実装選択肢」かどうかは、次の問いで判定する。

> 「この記述を別の選び方に置き換えても、§4 の骨組みは保たれるか？」

Yes なら **実装選択肢**（ユーザー選択の対象）。No なら **骨組み**（固定）。

### 5.2 典型的な実装選択肢のパターン

経験的に以下が該当しやすい。スキル本文を読みながらこれらのパターンにマッチするものを拾い上げる。

| パターン | 例 |
|---|---|
| 具体的な数値・閾値 | 「3〜5 個」「200 行以下」「500 行以下」 |
| 特定の方法論・フレームワーク | 「Anthropic 8 原則」「TDD」「Plan/Act モード」 |
| 参考文献・URL | 公式ドキュメント、論文、外部記事 |
| 具体的なコード例・出力例 | inline 例、テンプレート、サンプル |
| 失敗パターン・ハマりがちな例 | 「ハマりがちな失敗パターン」セクション |
| 内部チェックリスト | self-review チェックリスト、出力前確認 |
| 哲学・原則・主張 | 「○○ より △△ を優先する」「× は避ける」 |
| ロール定義 | "You are a ..." の人物像 |
| 出力フォーマットの具体形 | 見出し構造、表のスキーマ、Markdown の骨組み |
| ツール選定 | 「`gh` を使う」「Read/Grep を使う」 |

同種の項目が複数ある場合は **1 項目にまとめる**（例: 失敗パターン全体を 1 項目）。粒度を細かく刻みすぎるとユーザーの判断負荷が増える。

### 5.3 ユーザー確認の提示形式

抽出した実装選択肢を、次の形式で **1 メッセージにまとめて**提示する。AskUserQuestion は上限 4 項目で足りないため、テキストでの一括提示・テキストでの一括回答を採用する。

```
## 実装選択肢の抽出結果（n 項目）

1. [推奨: 含める] <要約タイトル>
   原文: <該当箇所の短い引用 or 要約>
   推奨理由: <なぜ含めるべきと判断したか（1 文）>

2. [推奨: 除外] <要約タイトル>
   原文: <該当箇所の短い引用 or 要約>
   推奨理由: <なぜ除外を推奨するか＝再生成先 Claude の判断余地を残したい理由（1 文）>

...

回答形式：
- 推奨をそのまま採用する場合: `default`
- 推奨に対して反転したい項目がある場合: `default, except 3, 7`（3 と 7 を反転）
- 全項目を個別指定する場合: `include: 1,2,5 / exclude: 3,4,6,7,...`
```

### 5.4 推奨の付け方の方針

- **含める推奨**：その要素が「目的を実現する上で代替が乏しい」「外すと再設計時に方向が大きく変わる」「ユーザーが明示的に重視している（CLAUDE.md やコメントに書かれている）」と読み取れる場合
- **除外推奨**：「具体数値や具体例で、再生成先 Claude が別の値を選ぶ余地が大きい」「外部の知見に依存しており、再生成先 Claude が独自に最新版を引いた方が良さそう」「特定の流派・哲学で、別流派も成立する」場合

推奨の理由は **1 文で簡潔に**。長い説明はユーザーの判断を遅らせる。

## 6. 再生成プロンプトの出力テンプレート

ユーザーの選択を反映して、以下のテンプレートで `.claude/respec-prompts/<plugin>__<skill>.md` に書き出す。

````markdown
# <Original Skill Name> の再生成依頼

あなたは Claude Code のスキル作成者です。
以下の仕様に基づき、`<skill-name>` という SKILL.md を新規作成してください。
**実装上の判断は、あなた自身が最良と考える設計に委ねます。** 既存実装は提示しません。最新の知識と判断で書いてください。

## このスキルの目的

<§4.1 から>

## トリガー条件 / 想定ユーザー

<§4.2 から。トリガーフレーズは 3〜5 個>

## 入出力

- 入力: <§4.3 から>
- 出力: <§4.3 から>

## 必須の処理段階

<§4.4 から。各段階は「何を達成するか」のみを書く>

## 評価基準

<§4.5 から>

## 制約

<§4.6 から>

## 含めるべき要素（依頼者指定）

- <ユーザーが「含める」を選んだ実装選択肢のみを列挙>
- <選ばれなかった項目はここに書かない>

## 仕上げの指針

- SKILL.md 本体は適切なサイズに収める
- 詳細リファレンスが必要なら `references/<topic>.md` への分割を提案
- description にはトリガーフレーズと「何を/いつ」を含める
- 既存スキルの構造を意識せず、最新のベストプラクティスで設計してください
- 出力は SKILL.md 本体と、必要に応じた references/ の構成案
````

### 6.1 「除外」を選んだ要素の扱い

ユーザーが「除外」を選んだ実装選択肢は、テンプレートの「含めるべき要素」に**書かない**。
「これを使うな」と明示的に書かない理由は、それが再生成先 Claude にとってネガティブ制約になり、結局判断空間を狭めるため。**沈黙が最大の自由**。

### 6.2 出力プロンプトの長さ

再生成プロンプトは、骨組み + 含めると選ばれた要素 + 仕上げの指針の合算。
目安として **500〜1500 トークン程度**を想定する。これを大きく超える場合、骨組みに「方法論」が混入している可能性が高い（§9 のハマりがちな失敗パターン参照）。

## 7. ファイル命名規則と既存ファイル処理

### 7.1 ファイル名

形式: `<plugin>__<skill>.md`

- `<plugin>`: 対象スキルが含まれるプラグイン名。プラグインに属さない場合は `unscoped`
- `<skill>`: 対象スキルのディレクトリ名

例:
- `ai-tuner/skills/prompt-engineer/` → `ai-tuner__prompt-engineer.md`
- `dev-toolkit/skills/codebase-investigator/` → `dev-toolkit__codebase-investigator.md`
- `~/.claude/skills/my-skill/` → `unscoped__my-skill.md`

### 7.2 既存ファイルがある場合

`.claude/respec-prompts/<plugin>__<skill>.md` がすでに存在する場合：

- ユーザーに「上書きする / 別名で保存する / 中止する」を確認する
- 別名のデフォルトは `<plugin>__<skill>__<YYYYMMDD>.md`
- 日付は `date +%Y%m%d` で取得する

## 8. このスキルが対象としないもの

- **複数スキルを同時に再生成する**: 一度に 1 スキルを扱う。複数なら呼び出しを繰り返す
- **再生成プロンプトを実際に実行する**: プロンプトの生成までが責務。生成したプロンプトを別世代 Claude に渡すのはユーザーが手動で行う
- **他社 LLM 向けの抽象化**: 送り先は Claude 新バージョンを前提にする（SKILL.md 形式での再生成を期待する）
- **再生成された SKILL.md の評価・差分比較**: それは別スキルの責務

## 9. ハマりがちな失敗パターン

- **骨組みに「方法論」を入れる**：「Anthropic 8 原則を使う」は骨組みではなく実装選択肢。「中核原則を適用する」が骨組み
- **実装選択肢で「除外」を「禁止」に翻訳する**：「Anthropic 8 原則を**使わないでください**」は再生成先 Claude の判断空間を狭めるので NG。単に言及しない（§6.1）
- **すべての具体例を実装選択肢として挙げる**：粒度が細かすぎる。同種の例は 1 項目に丸める
- **トリガーフレーズを骨組みに入れすぎる**：3〜5 個に絞る。元 description が長くても要約する
- **scripts/ や assets/ の中身を読み込む**：構造（存在）だけを伝え、中身は再生成先 Claude に委ねる。読み込むと「具体実装をなぞらせる」誘惑が強くなる

## 10. プラグイン間参照スコープへの配慮

このリポジトリの CLAUDE.md には「プラグイン間で互いの成果物を直接参考にしない」というルールがある（同一プラグイン内は自由）。
このスキルは **対象スキルのファイルを「再生成プロンプトの素材」として読み取る** だけであり、別プラグインのスキルを参考にして自プラグインのスキルを書き換える操作ではない。したがってプラグイン間参照スコープのルールには抵触しない。

ただし、生成された再生成プロンプトを使って **他のプラグインに同じスキルを移植する** ような使い方は本スキルの想定外。そうしたい場合はユーザーが明示的に依頼する前提とする。
