# prompt-engineer 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

AI 向け指示文書（CLAUDE.md / SKILL.md / エージェント定義 / システムプロンプト等）の新規作成・レビューを、Anthropic 公式のプロンプトエンジニアリング原則の要約＋ファイルタイプ別ガイダンスで行うスキル。Opus 4.7 世代の公式ドキュメントを基に作成し、2026-08 に Opus 5 世代の公式ガイダンスへ追随改訂した。

兄弟スキル prompt-brief との棲み分け: 単発の依頼プロンプト（タスク依頼文）の対話設計は prompt-brief、永続的な指示文書ファイルの作成・レビューは本スキル。

## 中核的な設計判断

### 【load-bearing】セルフチェック指示の推奨はモデル世代の条件付き
- **決定**: Opus 4.x 以前・他社モデル向けには従来どおり推奨。Opus 5 向けには汎用の検証指示（double-check・最終検証ステップ・サブエージェント検証）を削除対象とし、残してよいのはモデルが自力で導出できない具体的な合格基準のみとする（§3.5）。
- **却下した代替案**: (a) 一律推奨の維持 — 公式が Opus 5 で「書き換えでなく削除」と明言したため却下。(b) 一律削除 — 旧モデル・他社モデル向けには依然有効なテクニックのため却下。
- **防いでいる失敗**: Opus 5 向け文書に検証指示を足して過剰検証・トークン浪費を招く／逆に旧モデル向け文書から有効なセルフチェックを剥がす。
- **出所**: 公式 Prompting Claude Opus 5「Task scope and over-verification」「Self-correction」、prompting best practices の self-check 項（2026-08-13 確認）。

### 【load-bearing】スコープ明示は両方向
- **決定**: 「広げたい範囲の明示」（Opus 4.7 のリテラル解釈由来）に加え、「広げてほしくない境界の明示」（Opus 5 のスコープ拡大傾向由来）を §2.6 に併記。レビュー系プロンプトの「重大のみ報告」「保守的に」がリテラル解釈で報告漏れになるアンチパターンも同所に置く。
- **防いでいる失敗**: リテラル解釈＝狭く解釈する話とだけ理解して、Opus 5 が勝手にスコープを広げる方向のズレを見逃す。レビューエージェント定義で報告を絞る指示を書いて検出漏れを起こす。
- **出所**: 公式 Prompting Claude Opus 5「Capability improvements（Code review）」「Task scope and over-verification」（2026-08-13 確認）。

### thinking の世代差は CoT 判断に必要な範囲だけ書く
- **決定**: §3.6 に「Opus 4.6〜4.8 / Sonnet 4.6 は省略時オフ、Opus 5 / Sonnet 5 は省略時オン、Fable 5 / Mythos 5 は常時オン、Opus 5 の無効化は effort high 以下のみ」と、無効時の 2 アーティファクト（tool call のテキスト漏れ・内部 XML タグ漏れ）＋緩和だけを書く。effort の段階や API パラメータ詳細は書かない。
- **却下した代替案**: API 仕様（effort ladder・max_tokens 等）の転記 — 指示文書の設計判断を変えない情報でサイズと同期コストだけ増えるため却下。
- **防いでいる失敗**: 「4.6/4.7 は adaptive thinking 内蔵」という旧記述のまま、thinking がデフォルトオンの世代に対して不要な CoT 指示や「考えるな」指示（タグ漏れを増やす）を残す。
- **出所**: 公式 What's new in Claude Opus 5「Behavior changes」、Prompting Claude Opus 5「Running with thinking disabled」（2026-08-13 確認）。

### モデル固有記述の陳腐化対策
- **決定**: モデル固有の挙動には対象モデル名を明記し、§8 に「モデル別ガイド URL（`prompting-claude-<model>` 形式）」と「新世代が出たらモデル固有記述（§2.6 / §2.7 / §3.5 / §3.6）を突き合わせて点検する」運用を書く。
- **防いでいる失敗**: どの記述がどのモデル世代の観測に依存しているか分からず、世代交代時に点検箇所を特定できない（2026-08 改訂で「Opus 4.7 基準の記述が古くなった」経験そのもの）。
- **出所**: 2026-08-13 の Opus 5 追随改訂の設計議論。

## 解釈・仮定（要確認）

- **過剰検証・応答長等の対象モデル**: 公式は Opus 5 を名指しで説明している（best practices でも「Claude Opus 5 is the exception」）。Sonnet 5 / Fable 5 に同じ挙動があるかは公式記述を確認していないため、本文は「Opus 5」に限定して書いた。⚠️ 5 世代全体に広げるのは各モデルのガイドで確認が取れてから。
- **セルフチェックの残し方**: 公式の「remove rather than rewrite」は汎用の検証・再チェック指示を指し、モデルが自力で導出できない具体的な合格基準（フォーマット要件・降格ルール）は別物と解釈して条件付きで残した。⚠️ より保守的な読み（Opus 5 向けは全部削除）もありうる。
- **公式文例の取り込み方**: 500 行制限内に収めるため、公式の長いプロンプト文例は逐語転載せず要約で取り込んだ。実際に使うときは §8 の原典を fetch して正確な文例を参照する前提。
