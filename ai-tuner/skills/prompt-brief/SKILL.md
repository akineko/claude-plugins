# Prompt Brief

AIへの依頼文を「ブリーフ」——目的・制約・判断基準を渡し、手段は受け手に委ねる依頼書——として設計する。

## 1. このスキルが解こうとしている問題

分岐や判断の多いタスク（スキルの設計、機能の設計・実装、調査など）をAIに依頼するとき、次のジレンマがある。

- 思いついたフローや手順をそのまま伝えると、AIがそれにアンカリングされ、本来より良い別アプローチを検討しなくなる
- 逆に目的だけを伝えると、ユーザーの頭の中にあった重要な考慮点（過去の失敗、品質基準、優先順位）が伝わらず抜け落ちる

このスキルは「案を伝えるか・伝えないか」の二択を取らず、**伝える情報の種類を変換する**。

- 手順・フロー案 → その手順で**防ごうとしていた失敗**（§4.1）
- 分岐・場合分け案 → その分岐を**駆動している判断基準・優先順位**（§4.2）

手順や分岐構造はAIが再構成できるが、ユーザーの失敗経験・ドメイン知識・価値判断はAIには導出できない。導出できない情報だけを渡せば、アンカーにならず、かつ抜けない。

## 2. 中核原理: 導出可能性のリトマス試験

集めた情報をブリーフに入れるかどうかは、**「この情報は、受け手のAIが目的から自力で導出できるか？」**で仕分ける。

| 導出できない → 全部渡す | 導出できる → 落とす（or 参考ラベル付き） |
|---|---|
| 目的・成功条件、ハード制約 | 処理フロー・ステップの順序 |
| 過去の失敗・ヒヤリハット | 分岐構造そのもの |
| 良い出力/悪い出力の具体例 | 中間成果物の形式 |
| トレードオフの優先順位 | 実現手段の選択 |

**重要な例外**: 手順に見えても、その理由が外部要因（ライセンス、社内規約、既存システムとの互換性、組織の合意事項）なら、それは導出できない情報。手順の形のまま「ハード制約」に残す。機械的に「手順だから削除」としない。

## 3. 進め方

### Step 1: 素材の棚卸し

会話履歴とユーザーの依頼文から、既に分かっていることを拾う。何をAIに依頼したいのか、目的、制約、ユーザーの頭の中にある案（手順・分岐）、過去の失敗への言及。**既に語られたことを二度聞かない**——聞き直しはユーザーの信頼と時間を削る。

### Step 2: 不足分のインタビュー

質問で止まるか、仮定を置いて先へ進むかは、**欠けている情報がブリーフの背骨か枝葉か**で決める。

- **背骨**（判断基準・優先順位・分岐の理由づけ・目的そのもの）が欠けている → 質問で埋める。ここを仮定で埋めて草案化すると、成功条件・判断基準・失敗モードの全体がその推測の上に建ち、外れたとき直すのは1項目でなく骨格全体になる。しかも確信ありげな仮定は今度はユーザーをアンカリングし、このスキルが防ぐ失敗が向きを変えて再発する。
- **枝葉**（出力形式・対象環境・スコープ境界）が欠けている → 止まらず ⚠️仮定 を置いて草案へ進み、確認は最後にまとめて行う。ここで質問を重ねるのは「聞きすぎ」（§6）。

質問するときは、開いた質問（「判断基準は何ですか？」）ではなく**考えられる答えを選択肢として並べて問う**（§4.2）。想起より認識で答えられて負荷が下がり、ユーザーが思いつかなかった解釈を横に並べて見せられる（＝抜け漏れ対策になる）。単一の推測をぶつけないのでアンカーにもならない。

質問は不足分だけを**まとめて一度に**出し（尋問のような逐次質問にしない）、背骨1〜2点に絞る。ラウンドは最大2回。**既に明示された制約・失敗（例: 「本番DB書き込み事故」）は仮定不要で確定扱いとし、質問対象にしない**。フロー案が語られていれば §4.1、分岐案が語られていれば §4.2 の技法で掘る。案が何もなければ失敗から直接聞く（「どうなったら失敗ですか？」「過去に困ったことは？」「絶対に守りたい条件は？」）。背骨が既に十分なら質問を省いて Step 3 へ進む。

### Step 3: 翻訳結果の確認

手順案・分岐案を預かった場合は、ブリーフを組む前に翻訳の対応表を見せる。

| ユーザーの案 | 翻訳結果 | 行き先 |
|---|---|---|
| 「まず全呼び出し箇所を列挙する」 | 呼び出し箇所の見落としによる修正漏れを防ぎたい | 防ぎたい失敗 |
| 「ライブラリXを使う手順で」 | ライブラリXはライセンス上の指定（外部制約） | ハード制約 |
| 「最後にMarkdownでレポート」 | （出力形式の希望として確認） | 成功条件 or 落とす |

ここが、誤訳——本当はハード制約だったものが「防ぎたい失敗」に弱められる、暗黙の要求ごと落とされる——をユーザーが検知できる唯一のポイント。対応表なしでいきなり完成形を出すと、ユーザーは何が削られたか分からない。

### Step 4: ブリーフの組み立てと出力

§5 のフォーマットで組み立て、コピーして使えるコードブロックで出力する。出力後、ファイルへの保存を提案する（後で編集・再利用する場合に便利なため。押し付けない）。

## 4. 翻訳の技法

### 4.1 手順 → 失敗モード

ユーザーの想定フローの各ステップについて問う。

- 「このステップが**無いと何が起きる**と思いますか？」
- 「そのやり方にしたのは、**過去に何かあった**からですか？」

回答によって行き先が変わる。

- 失敗経験・懸念が出てきた → **防ぎたい失敗**へ（失敗の内容を書く。手順は書かない）
- 外部要因でそうするしかない → **ハード制約**へ（手順のまま残してよい。§2の例外）
- 「なんとなく」「自然だと思った」 → **落とす**（AIが再構成できる情報）

**例**:
- ユーザー案: 「テスト生成を頼むとき、まず既存テストの命名規則を調べさせてから書かせたい」
- 質問: 「調べさせないと何が起きますか？」→「前に生成テストだけ命名が浮いて、レビューで全部直した」
- 翻訳: 防ぎたい失敗「生成物が既存コードの規約から浮き、手直しコストが発生する」

### 4.2 分岐 → 判断基準

ユーザーの想定する場合分けの裏にある判断を引き出す。開いた質問ではなく、**考えられる判断の候補を選択肢として並べて問う**（Step 2 の理由による）。

- 「AとBを分けているのは、(a) 時間・コスト (b) 技術的な適性 (c) リスクの大きさ のどれに近いですか？（複数可・他にあれば教えてください）」
- 「迷ったらどちらに倒しますか？」
- 分岐が浅い/自明で背骨と言えないなら、質問を省いてそのまま判断基準へ翻訳する

引き出した優先順位を**判断基準・優先順位**へ入れる。分岐構造（AならX、BならY）は書かない。基準が揃っていれば分岐はAIが設計でき、ユーザーが思いつかなかった分岐も出てくる。

**例**:
- ユーザー案: 「再現できるバグならデバッガで追わせて、再現できないならログ解析にしたい」
- 選択肢付き質問: 「この分岐を決めているのは (a) 再現試行に時間を溶かしたくない (b) デバッガで追えない障害型がある (c) その他、どれに近いですか？」→「(a)」
- 翻訳: 判断基準「バグ再現の試行は時間を区切り、見込みが立たなければ証拠ベースの調査に切り替える」

## 5. ブリーフのフォーマット

以下のテンプレートで出力する。該当する素材が無いセクションは削る（空欄で残さない）。

```markdown
# 依頼: <一言サマリ>

## 目的と背景
<何を解決したいか。なぜ今それが必要か>

## 成功条件
<何ができたら完了か。可能なら確認方法も>

## ハード制約
<違反したら失格になる条件。外部要因由来の手順指定もここ>

## 防ぎたい失敗
<過去の失敗・懸念。「〜が起きたことがある。これを防げる設計にしてほしい」の形>

## 判断基準・優先順位
<トレードオフの倒し方。迷ったときの既定の方向>

## 参考: 私が考えていた案（アンカーにしないこと）
<任意。翻訳しきれなかった案を残す場合は必ずこのラベルの下に置き、
「これに縛られず、より良いアプローチがあれば提案してほしい」と添える>

## 進め方への期待
<例: 着手前にアプローチを2〜3案、トレードオフ付きで提示してから進めてほしい>
```

## 6. 落とし穴

- **削りすぎ**: リトマス試験は機械的な手順削除ではない。理由が外部制約なら手順のまま残す（§2の例外）。迷ったら「参考」ラベル付きで残す方が、黙って落とすより安全。
- **背骨の当て推量**: 判断基準・優先順位・分岐の理由が不明なまま草案を出さない。推測した背骨はブリーフ全体に波及し、確信ありげな仮定はユーザーをアンカリングする。背骨の欠落は選択肢付き質問で埋める（Step 2）。枝葉（形式・環境・スコープ）は仮定で進んでよい。
- **聞きすぎ**: 枝葉を埋めるために質問を続けない。背骨1〜2点に絞り、2ラウンドで出なかった情報はブリーフを使ってみてから追記すればよい。
- **参考セクションの乱用**: 集めた情報を丸ごと「参考」に入れるのは翻訳の放棄で、アンカリングがそのまま再発する。参考に置いてよいのは、翻訳しきれなかった案そのものだけ。
- **「進め方への期待」への手順の書き戻し**: このセクションは受け手との協働の仕方（複数案の提示、着手前の確認など）を書く場所。処理フローを書いたら §4.1 からやり直し。

## 兄弟スキルとの棲み分け

- CLAUDE.md / SKILL.md / エージェント定義など**永続的な指示文書ファイル**の作成・レビュー → prompt-engineer
- **既存スキル**を別の Claude に再作成させるプロンプト生成 → skill-respec
- このスキルの守備範囲は「これからAIに投げる一回性の依頼文」。ブリーフの受け手がスキルを作る場合でも、出来上がった SKILL.md のレビューは prompt-engineer に任せる。
