# debug-investigate

症状から根本原因を特定する調査スキル。対立仮説を立て、hypothesis-investigator サブエージェントに並列で反証を試みさせ、生き残った仮説を確証して報告する。

## 原則

- **調査に徹する**。根本原因の特定と修正方針の提示までが責務。修正の実施・コミットは行わない。
- **単一仮説に飛びつかない**。原因が自明に見えても必ず対立仮説（最低2つ）を立てて検証する。裁定前に「原因はこれです」と断定しない。
- **証拠で語る**。すべての判定に `ファイル:行` または実行結果の根拠を付ける。

## フロー

### 1. 症状の構造化

引数と会話から次の3点を整理する。

- **期待動作** / **実際の動作** / **発生条件**（環境・データ・タイミング）

期待と実際の差分が言語化できないうちは調査を開始せず、ユーザーに質問して確定させる。

### 2. 再現性トリアージ

症状を3タイプに分類し、検証戦略を決める。

| タイプ | 判定基準 | 検証戦略 |
|-------|---------|---------|
| 再現可能 | テスト・コマンド・手順でローカル再現できる | 実験ベース。最初に最小再現を確立 |
| 痕跡のみ | ログ・スタックトレース等はあるが再現困難（本番障害等） | 読解ベース。痕跡とコードの突き合わせ |
| エラーなき誤動作 | エラーは出ないが期待と違う結果になる | 仕様確認＋実装トレース |

再現可能な場合、**仮説を立てる前に**最小再現手順（1コマンドで再現確認できる形）を確立する。これが以降の全検証の土台になる。

### 3. 痕跡収集

仮説の材料をメインが集める。

- エラーメッセージ・スタックトレースから関連コードパスを特定
- `git log` / `git diff` で該当箇所の直近の変更を確認（回帰の可能性）
- 発生条件に関わる設定・データ・環境差分

### 4. 対立仮説の生成

証拠に基づき対立仮説を2〜5個立てる。各仮説は次のセットで定義する。

- **主張**: 何が原因か（1文）
- **予測**: この仮説が正しければ観測されるはずの証拠
- **検証方法**: 予測を確認する具体的手段（読むファイル・実行するコマンド）

### 5. 並列検証

仮説ごとに hypothesis-investigator を1体ずつ、単一メッセージで並列起動する。各エージェントには次を渡す。

- 症状サマリ（ステップ1の3点）
- 担当仮説（主張・予測・検証方法）
- 最小再現手順（あれば）
- 調査スコープ（関連パス）

### 6. 裁定と確証

全エージェントの判定と証拠を突き合わせて裁定する。

- **supported が1つ** → 確証フェーズへ
- **複数生存** → 生存仮説を弁別する追加調査・実験を設計し、ステップ5をもう一巡
- **全滅** → 各エージェントの副次的手がかりから仮説を再生成してステップ4へ

ラウンドは**最大3回**。使い切ったら打ち切り、消去できた仮説と残る可能性を整理してユーザーに相談する。

**確証**（裁定で残った1仮説に対して）:

- 再現可能 → 「原因が正しければこの操作で症状がこう変わるはず」という予測を実験で当てる。コード変更を伴う実験（ログ仕込み・`git bisect` 等）はこの段階でメインが逐次実行し、**終了後に必ず作業ツリーを元へ戻す**。
- 再現不能 → 証拠の整合チェーン（トリガー → 欠陥 → 症状）を組み立て、矛盾がないことを確認する。

確度ラベル: **確定**（実験で確証済み）/ **有力**（複数の独立証拠が整合）/ **推定**（矛盾はないが直接証拠なし）

### 7. レポート

`docs/debug/YYYY-MM-DD-<slug>.md` に保存し（日付は `date` コマンドで確認）、会話では要約を報告する。

```markdown
# <症状の1行サマリ>

## 症状
期待動作 / 実際の動作 / 発生条件

## 根本原因（確度: 確定 | 有力 | 推定）
因果チェーン: トリガー → 欠陥（ファイル:行） → 症状

## 検証した仮説
| 仮説 | 判定 | 根拠 |
（棄却した仮説も残す。再調査時に同じ道を辿らないため）

## 修正方針
選択肢が複数あれば推奨と理由付き（実施はスコープ外）

## 未確定事項
確度が推定止まりの場合、確定に必要な追加情報（仕込むべきログ・監視項目）
```
