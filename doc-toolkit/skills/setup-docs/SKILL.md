# setup-docs

ドキュメントが整備されていないプロジェクト（新規・既存どちらも）に対して、**docs/ のディレクトリ構成と「ここに何を書くか」のガイド（各ディレクトリの README）を作る**スキル。

個別ドキュメントの中身は生成しない。書き手が迷わないための「置き場」と「書く・書かないの境界」を先に決めるのが目的。

## このスキルが解く問題

ドキュメントを書こうと思ったときに最初にぶつかるのは「**どこに何を置けばいいか分からない**」「**何を残して何を残さないか**の判断がつかない」という壁。結果としてドキュメントは README に雑多に書かれるか、書かれないまま放置される。

このスキルは、構成と書き方の境界を先に**ディレクトリ＋README**として固定することで、後続のドキュメント作成（ADR、機能設計、技術調査など）を素直に進められる土台を作る。

## 何を作るか

- `docs/` 配下（モノレポでは加えて `packages/*/docs/`）のディレクトリ
- 各ディレクトリの `README.md`（このディレクトリには何を書く／書かないか、ファイル名規則、関連スキル）
- ルート `docs/README.md`（全体のインデックス）

ドキュメントの**中身**（個別の ADR や設計書）は作らない。それは `create-adr` や `extract-design` の役目。

## 起動時に決めること

書き始める前に次の 3 点を確定させる。

### 1. リポジトリ形態（シングル/モノ）

自動で判定を試みる。次のいずれかが見つかればモノレポと判定する候補：

- `pnpm-workspace.yaml`
- `lerna.json`
- `turbo.json`
- `nx.json`
- `package.json` の `workspaces` フィールド
- ルート `Cargo.toml` の `[workspace]`
- `go.work`
- 慣習的なディレクトリ（`packages/`, `apps/`, `services/`）がトップに複数ある

不確実な場合はユーザーに確認する。シングル/モノでディレクトリの**置き場**が変わるため、ここを間違うと後で動かすのが面倒。

### 2. 既存 `docs/` の有無

既に `docs/` がある場合は中身を確認する。

- **空でないなら追記モード**: 既存ファイルは絶対に上書きしない。不足しているカテゴリのディレクトリ・README のみを追加する
- **空、または存在しないなら新規モード**: 全て新規生成
- 命名規則（例: `doc/` vs `docs/`、`adr/` vs `decisions/`）が既にあれば**それに合わせる**

### 3. 採用するカテゴリ

「コア」と「任意」を区別する。コアは原則全て採用、任意はプロジェクトの規模・性質に応じて取捨選択する。

**コア（既定で採用）**:

- `adr/` — 意思決定の記録
- `design/` — 機能単位の設計
- `research/` — 技術・ライブラリ調査
- `architecture/` — 横断的方針（ディレクトリ構造、エラーハンドリング、ログ、テスト戦略など）

**任意（ユーザーに確認）**:

- `glossary.md` — 用語集（ドメイン用語が多いプロジェクトで有効）
- `runbook/` — 運用・デプロイ手順（本番運用のあるサービスで有効）
- `postmortem/` — インシデントの振り返り記録（運用フェーズに入っているチームで有効）

任意の採用基準は [references/layouts.md](references/layouts.md) の「カテゴリ採用の判断指針」を参照。コアでも「このプロジェクトには不要」と明確に言われた場合は外してよい（例: 個人プロジェクトで ADR を作らない判断は妥当）。

## ワークフロー

1. **リポジトリ形態を判定**
   - 上記の検出ルールで自動判定 → 結果をユーザーに伝えて確認
   - 検出できない場合はユーザーに直接聞く

2. **既存 `docs/` を確認**
   - `docs/`（あるいは `doc/`）が存在するか、内容はどうか
   - モノレポの場合は `packages/*/docs/` も確認
   - 既存命名規則を読み取る（フォルダ名、ファイル名フォーマット）

3. **採用カテゴリをユーザーと決める**
   - コア 4 つ＋任意 3 つから選んでもらう（既定提案を出してから聞くと早い）
   - プロジェクトの状況（新規/既存、規模、運用フェーズか）を踏まえて推奨セットを提示する

4. **配置を決める**
   - シングルレポ: 全て `docs/` 配下に
   - モノレポ: [references/layouts.md](references/layouts.md) の判断ルールに従う
     - 全体に影響するもの（ADR、横断的方針、用語集）→ ルート `docs/`
     - パッケージ固有のもの（機能設計、パッケージ用の技術調査）→ `packages/<pkg>/docs/`
     - 迷ったらルートに置いて相互リンク

5. **ディレクトリと README を生成**
   - 各 README の内容は [references/readme-templates.md](references/readme-templates.md) のひな形を出発点にする
   - プロジェクト固有の事情（言語、フレームワーク、運用形態）がヒアリングや既存コードから読み取れる場合は、README の文面を少し調整してよい（例: TypeScript プロジェクトなら architecture/ の例として `tsconfig-strategy.md` を挙げる、など）
   - 既存ファイルは絶対に上書きしない。重複したら**スキップしてユーザーに報告**

6. **生成結果のサマリを報告**
   - 作ったディレクトリ・ファイル一覧
   - 既存と重複してスキップしたもの
   - 次にやることの導線（「ADR を 1 件作るなら `create-adr` を使う」「既存機能の設計を残したいなら `extract-design`」）

## モノレポ運用の判断ルール

モノレポはドキュメントを「全体に効くもの」と「パッケージに閉じるもの」に分けて配置する。境界が曖昧な場合の判断指針：

- **複数パッケージから参照される決定** → ルート `docs/adr/`
- **特定パッケージ内の選定（DBドライバ、内部ライブラリ等）** → `packages/<pkg>/docs/adr/`
- **エラーハンドリング・ログ規約のような全体規約** → ルート `docs/architecture/`
- **そのパッケージ固有の規約** → `packages/<pkg>/docs/architecture/` を作ってもよいが、まずはルート + パッケージ別 README で済むことが多い
- **用語集** → 原則ルートに 1 つ。パッケージ固有用語は同じファイル内のセクションで分ける

詳細は [references/layouts.md](references/layouts.md)。

## 既存 `docs/` がある場合の振る舞い

このスキルは**新規プロジェクト向けだけではない**。ドキュメント整備が中途半端なプロジェクトに後から土台を入れることもよくある。

- 既存ファイルは絶対に上書きしない（ユーザーの作業を消すリスクが大きい）
- 既存ディレクトリ名・ファイル名規則を読み取り、それに合わせて新規ディレクトリを命名する（`adr/` 既存なら `decisions/` を新設しない）
- 既存 README があるディレクトリには手を入れない。改善が必要そうな場合はユーザーに「現状の README を提示するので、必要なら整えてください」と促す
- 既存 `docs/README.md`（インデックス）がある場合、新しく追加したカテゴリへのリンクが入っていなければ、**ユーザーに編集案を提示する**（直接書き換えず）

## 守ること

- **個別ドキュメントの中身は作らない**。このスキルが作るのは構成と書き方ガイドのみ。`create-adr` や `extract-design` の役割を侵食しない
- **過剰なカテゴリを作らない**。「あったほうがいいかも」で `runbook/` や `postmortem/` を空のまま増やすと、未使用のディレクトリが心理的負債になる。実際に使う見込みがあるものだけ作る
- **既存ファイルを上書きしない**。これは最重要。重複が見つかればスキップして報告する
- **空ディレクトリは作らない**。各ディレクトリには必ず `README.md` を置く（`.gitkeep` ではなく、書き方ガイドとしての中身を持つ README）
- **README から関連スキルへの導線を入れる**。`adr/README.md` には `create-adr` を、`design/README.md` には `extract-design` を呼び出せることを書いておく
