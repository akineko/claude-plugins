# readme-templates — 各カテゴリの README ひな形

このファイルは各 `README.md` の出発点となるひな形を集めたもの。

スキル実行時は、該当セクションの本文を該当ディレクトリの `README.md` として書き出す。プロジェクト固有の事情（言語、フレームワーク、運用形態）が分かっている場合は、文中の例や用語をその文脈に寄せて調整してよい（例の差し替え程度。骨格は変えない）。

セクション間の見出しレベルは、書き出すファイル側では `#` から始まるよう調整する。

## モード別の書き出し対応

- **`docs/README.md`** はモードごとに 2 種類のひな形があり、選択したモードに応じて書き出す
- **累積系（adr / research / postmortem）と単発系（glossary）** はモード非依存。`<category>/README.md` または `docs/glossary.md` として書き出す
- **主題系（architecture / design / runbook）** はモードによって書き出し先が変わるが**中身は同一**:
  - standard モード: `docs/<category>/README.md`
  - minimum モード: `docs/_guide-<category>.md`
  - 同一の内容を保つことで、後から `mv docs/_guide-<category>.md docs/<category>/README.md` だけで分割できる
- モノレポでは、パッケージ配下に書き出すときも同じ規則。主題系のガイドは `packages/<pkg>/docs/_guide-<category>.md`（minimum）または `packages/<pkg>/docs/<category>/README.md`（standard）

---

## docs/README.md（standard モード版）

全カテゴリがサブディレクトリに分かれている構成のときの README ひな形。

```markdown
# ドキュメント

このディレクトリにはプロジェクト全体に関わる長期保管用のドキュメントを置く。
**1 年後、もしくは新しいメンバーが参加したときに役に立つこと**を基準に書く。

## カテゴリ

<!-- このプロジェクトで採用したカテゴリだけを残す -->

| ディレクトリ | 用途 |
|---|---|
| [adr/](./adr/) | 意思決定の記録（なぜその設計を選んだか） |
| [design/](./design/) | 機能単位の設計ドキュメント |
| [research/](./research/) | 技術調査・バージョンアップ影響・問題調査などの成果 |
| [architecture/](./architecture/) | エラー処理・ログ・命名などの横断的方針 |
| [glossary.md](./glossary.md) | 用語集 |
| [runbook/](./runbook/) | 運用・デプロイ手順 |
| [postmortem/](./postmortem/) | インシデントの振り返り |
| [plans/](./plans/) | 実装計画書（**完了時に削除する transient ドキュメント**） |

## 書くときの原則

- **コードを読めば分かることは書かない**。型・実装の細部はコードが一次情報
- **「なぜ」を書く**。「何を」だけだと将来読み返したときの価値が薄い
- **1 主題 1 ファイル**。複数の論点を 1 ファイルに詰めない
- **コードが変わると陳腐化する内容は最小限に**。長期保管できる情報に絞る

## 関連ツール

- `create-adr` スキル — 設計議論や設計書から ADR を抽出する
- `extract-design` スキル — 実装設計書や既存コードから設計ドキュメントを抽出する
```

## docs/README.md（minimum モード版）

累積系のみサブディレクトリ、主題系は `docs/` 直下フラット配置のときの README ひな形。`_guide-<category>.md` への索引と、将来サブディレクトリへ分割するための計画を含む。

```markdown
# ドキュメント

このディレクトリにはプロジェクト全体に関わる長期保管用のドキュメントを置く。
**1 年後、もしくは新しいメンバーが参加したときに役に立つこと**を基準に書く。

## 現在の構成

このプロジェクトは「最小スタート」構成。累積するカテゴリ（ADR、調査、ポストモーテム）のみサブディレクトリで分け、主題系（横断的方針、機能設計、運用手順）は `docs/` 直下にフラット配置している。書き方ガイドは `_guide-<category>.md` として並ぶ。

## カテゴリ

<!-- このプロジェクトで採用したカテゴリだけを残す -->

| 種類 | 場所 | 書き方ガイド |
|---|---|---|
| ADR（意思決定の記録） | [adr/](./adr/) | [adr/README.md](./adr/README.md) |
| 調査ドキュメント | [research/](./research/) | [research/README.md](./research/README.md) |
| ポストモーテム | [postmortem/](./postmortem/) | [postmortem/README.md](./postmortem/README.md) |
| 実装計画書（**完了時に削除**） | [plans/](./plans/) | [plans/README.md](./plans/README.md) |
| 横断的方針 | `docs/` 直下に `<topic>.md` として配置 | [_guide-architecture.md](./_guide-architecture.md) |
| 機能設計 | `docs/` 直下に `<feature>.md` として配置 | [_guide-design.md](./_guide-design.md) |
| 運用手順 | `docs/` 直下に `<operation>.md` として配置 | [_guide-runbook.md](./_guide-runbook.md) |
| 用語集 | [glossary.md](./glossary.md) | （単一ファイル運用） |

## 書くときの原則

- **コードを読めば分かることは書かない**。型・実装の細部はコードが一次情報
- **「なぜ」を書く**。「何を」だけだと将来読み返したときの価値が薄い
- **1 主題 1 ファイル**。複数の論点を 1 ファイルに詰めない
- **コードが変わると陳腐化する内容は最小限に**。長期保管できる情報に絞る

## 将来サブディレクトリへ分割する目安

主題系（architecture / design / runbook）のドキュメントが増えてきたら、サブディレクトリへの分離を検討する。

タイミングの目安:

- 同じ主題系カテゴリのファイルが 5 つ以上溜まった
- 別カテゴリのファイルと取り違えやすくなった
- カテゴリ内でさらに分類したくなった

分割手順（architecture を例に）:

\`\`\`bash
mkdir docs/architecture
mv docs/_guide-architecture.md docs/architecture/README.md
mv docs/error-handling.md docs/architecture/    # 該当する主題ファイルをすべて移動
mv docs/logging.md docs/architecture/
# このファイル（docs/README.md）の「カテゴリ」表と本セクションを更新
\`\`\`

`setup-docs` スキルを再実行すれば分割支援が起動する。

## 関連ツール

- `create-adr` スキル — 設計議論や設計書から ADR を抽出する
- `extract-design` スキル — 実装設計書や既存コードから設計ドキュメントを抽出する
```

## docs/adr/README.md

```markdown
# Architecture Decision Records (ADR)

「**なぜその設計を選んだか**」を残す場所。

## ADR とは

将来の自分・チームメンバーが「この設計はなぜこうなっているのか」を読み返すための短い記録。
個別の決定単位で 1 ファイルを作る。

## 何を残し、何を書かないか

| 残す | 書かない |
|---|---|
| Context: 制約・前提・解こうとした問題 | 実装手順・タスクリスト |
| Decision: 何を選んだか（採用案の概要） | 詳細なコード例・スキーマ定義 |
| Consequences: 採用による影響・トレードオフ | テスト戦略の詳細 |
| Alternatives: 検討した代替案と却下理由 | 試行錯誤の経緯・脱線 |
| Status: 提案中／採用済み／撤回 | スケジュール・期限 |

ADR は**時間が経っても陳腐化しないこと**を目指す。実装が変われば変わる情報は書かない。

## ファイル名

`NNNN-<短いケバブケースのタイトル>.md`（ゼロ埋め 4 桁の連番）

例: `0001-adopt-oidc-pkce.md`, `0042-introduce-rate-limit.md`

連番は採番順を表すだけで、必ずしも採用順や時系列ではない。**新しい ADR は `adr/` 内の最大番号 + 1 で採番**する。

日付プレフィックス（`YYYY-MM-DD-xxx.md`）を採用するプロジェクトもあるが、ADR は連番運用が広く使われている（Superseded by 0042 のような相互参照が短く書ける、決定の総数が見えやすい等）。**運用方法は途中で混在させない**。

## 書き方

`create-adr` スキルを使うと、実装設計書や AI との設計相談から ADR を作成できる。
ノイズ（フェーズ分割、コード例、試行錯誤）を落として決定の核だけを残す。

手書きする場合の最小テンプレート:

\`\`\`markdown
# <タイトル>

- Status: Proposed / Accepted / Deprecated / Superseded by [link]
- Date: YYYY-MM-DD

## Context
（何を解こうとしたか・前提・制約）

## Decision
（採用した方針。具体名で書く）

## Consequences
（採用による影響・トレードオフ・新たな制約）

## Alternatives
（検討した代替案と却下理由）
\`\`\`

## Status の運用

- **Proposed**: 提案中・議論中
- **Accepted**: 採用済み（実装着手後でも書ける）
- **Deprecated**: 廃止された
- **Superseded by [link]**: 別 ADR に上書きされた。新しい ADR へのリンクを残す
```

## docs/design/README.md

```markdown
# 機能設計ドキュメント

機能単位の「**長く読まれることを前提とした設計ドキュメント**」を置く場所。

## 何を残すか

機能の**設計意図・運用ルール・拡張手順・落とし穴**を中心に書く。

| 残す | 書かない |
|---|---|
| 設計意図と背景 | フェーズ・タスク分割 |
| メンタルモデル・全体像 | 詳細なコード例・行番号付き参照 |
| 運用ルール・規約 | 完了済みの TODO・移行ステップ |
| 拡張・変更手順 | API のリクエスト/レスポンス例 |
| 制約・落とし穴 | テスト戦略の詳細 |
| 代替案との比較 | 試行錯誤の経緯 |

判断基準は「**コードを読んでわかることは書かない**」「**コードが変わっても残る情報か**」。

## 1 ドキュメント 1 主題

`audit-log.md` のように主題を絞る。「監査ログと RBAC と通知を全部 1 ファイルで」のような書き方はしない。
スコープが広い場合は分割する（例: `rbac-overview.md` + `rbac-permission-model.md`）。

## ファイル名

ケバブケースの主題名: `audit-log.md`, `rbac.md`, `state-management.md`

## 書き方

`extract-design` スキルを使うと、実装設計書または既存コードから設計ドキュメントを抽出できる。
新規に設計を書く場合も、このスキルの「残す／落とす」の基準を参考にできる。

代表的なセクション（主題に応じて取捨）:

- 概要・目的
- メンタルモデル
- 主要コンポーネント / 配置
- 設計判断と背景
- 運用ルール・規約
- 拡張・変更手順
- 制約・落とし穴
- 関連リンク（関連 ADR など）
```

## docs/research/README.md

```markdown
# 調査ドキュメント

**調査・分析の成果のスナップショット**を残す場所。決定そのものではなく、決定や運用判断を支える資料、または後で参照したいノウハウを残す。

## ここに置くもの

代表的な調査タイプ:

- **技術選定のための比較調査** — 候補比較・PoC・評価軸の結果（決定そのものは ADR へ）
- **採用済み技術の詳細調査** — 採用が決まっている技術・ライブラリの内部挙動、ハマりどころ、運用ノウハウ
- **依存ライブラリのバージョンアップ影響調査** — `v3 → v4` の破壊的変更、影響箇所、推奨移行手順
- **問題・障害の原因調査** — 発生している不具合や非機能上の問題（性能・メモリ・再現性など）の解析レポート

共通するのは「**ある時点の調査の成果**」であり、コードや運用と共に継続的に育てるドキュメントではない点。

## 設計書からの分離

設計書に詳細な調査内容を全て書き込むと、本来の設計判断が読み取りづらくなる。
このディレクトリの主要な使い方の一つは**設計書を読みやすく保つための詳細の退避先**:

- 設計書には採用方針・対応方針だけ書く
- 詳細な検証結果・破壊的変更一覧・運用ノウハウなどはここに置き、設計書から「詳細は `docs/research/<file>.md` 参照」とリンクする

## 他カテゴリとの使い分け

| 残したい情報 | 置き場 |
|---|---|
| 採用した・採用しない**決定**そのもの | `adr/` |
| 守るべき**規約・方針** | `architecture/` |
| 機能の**継続的な設計** | `design/` |
| **本番インシデント**の対応記録と学び | `postmortem/` |
| 上記に当てはまらない**調査の成果** | ここ |

迷ったら「**今後コードや運用と共に育てるか、当時の調査として固定して残すか**」を問う。育てるなら他カテゴリ、固定なら `research/`。

## 何を書くか

調査タイプによって取捨するが、概ね次が中心:

- 調査の目的・背景
- 調査範囲とスコープ外
- 調査結果（事実・データ・引用）
- 結論・所見・推奨
- 未調査・確認できなかった点
- 参考リンク
- **調査時点の前提**（対象バージョン、環境、データ規模、調査日）

タイプ別の追加項目:

- 比較調査: 評価軸、各候補の評価、PoC 結果
- 採用済み技術調査: ハマりどころ、運用上の注意、関連ドキュメントへの索引
- バージョンアップ影響調査: 破壊的変更の一覧、影響を受けるファイル・モジュール、移行手順
- 問題原因調査: 再現手順、根本原因、暫定対応・恒久対応の案

## 古くなった調査の扱い

調査結果は**当時のスナップショット**。半年〜1 年経過すれば対象技術・コードベース・運用環境が変わっている可能性が高い。

- 再調査が必要なら**新しいファイル**として作る（古いものを書き換えない）
- 古い調査は削除せず、冒頭に「`YYYY-MM-DD` 時点の調査。現状と乖離している可能性がある」と注記して残す
- 既に検討の余地がなくなった調査（廃止技術・解決済み問題）は削除してもよい

## ファイル名

`YYYY-MM-DD-<主題のケバブケース>.md`（時系列で並び、陳腐化判断がしやすい）

タイプを示すプレフィックス（`comparison-`, `deep-dive-`, `upgrade-`, `investigation-` など）を付けると一覧性が上がる（強制はしない）:

- `2026-01-15-comparison-orm-prisma-vs-drizzle.md`
- `2026-01-15-deep-dive-pgbouncer.md`
- `2026-02-01-upgrade-react-18-to-19.md`
- `2026-02-10-investigation-checkout-timeout.md`
```

## docs/architecture/README.md

```markdown
# アーキテクチャ方針

**特定の機能に紐づかない横断的な設計・運用方針**を置く場所。

## 例

- `directory-structure.md` — ディレクトリ構成と各層の責務
- `error-handling.md` — エラーハンドリング方針
- `logging.md` — ログ出力の規約
- `testing-strategy.md` — テスト戦略
- `security.md` — セキュリティ方針
- `naming.md` — 命名規則

これらは「機能 X 用」ではなく「**コードベース全体で守るルール**」。実装するときに迷ったら立ち返る場所。

## 何を残すか

| 残す | 書かない |
|---|---|
| 規約の本文（こう書く、これは禁止） | 個別機能の実装例 |
| 規約を作った背景・理由 | 完了済みの移行手順 |
| 例外と例外を認める条件 | スケジュール |
| 守らせる仕組み（lint・CI など）への参照 | 試行錯誤の経緯 |

規約を作った**理由**を必ず書く。理由が書かれていない規約は形骸化しやすい。

## 1 ファイル 1 主題

「エラー処理とログ出力とディレクトリ構成」を 1 ファイルにまとめない。
主題ごとに別ファイルを作る。

## ファイル名

主題のケバブケース: `error-handling.md`, `directory-structure.md`, `logging.md`

## 規約と ADR の使い分け

- **規約（ここ）**: 守るべきルールそのもの。「どうやるか」が中心
- **ADR**: 規約を採用するに至った決定の記録。「なぜそれを選んだか」が中心

両者は補完関係。重要な規約には対応する ADR があるとよい。
```

## docs/glossary.md

```markdown
# 用語集

プロジェクト固有の語彙・略語・ドメイン用語を統一するための辞書。

## なぜ用語集が必要か

同じ概念に複数の呼び名がついていると、コードレビュー・設計議論・ドキュメントが噛み合わなくなる。
コードベースとドキュメントで使う用語を 1 箇所に集約する。

## エントリの書き方

各エントリは次の形式で書く:

### <用語>

- **読み**: （カナがあれば）
- **英語表記**: （コード上の表記）
- **定義**: 1〜2 行
- **使い分け**: 似た用語と何が違うか
- **使用箇所**: 主要なファイル・テーブル名

## どんな用語を載せるか

- ドメイン固有の概念（業界用語、業務ロジック上の概念）
- プロジェクト独自の略語
- 一般用語をプロジェクト固有の意味で使っている場合
- 似た意味の語を使い分けている場合（例: User / Customer / Member）

**一般用語をそのままの意味で使っている場合は載せない**（冗長になる）。

## アルファベット順 or カテゴリ別

エントリ数が少ない（〜30）うちはアルファベット順で十分。多くなったらドメイン領域でセクションを切る。
```

## docs/runbook/README.md

```markdown
# 運用手順 / ランブック

**本番運用で必要になる手順**を残す場所。

## ここに置くもの

- デプロイ手順
- ロールバック手順
- データ修正・マイグレーション手順
- 障害発生時の初動対応（深掘りは postmortem へ）
- 定期メンテナンス手順

## ここに置かないもの

- 機能の設計意図 → `docs/design/`
- 横断的な方針 → `docs/architecture/`
- 個別障害の振り返り → `docs/postmortem/`

## 書き方の原則

- **手順は実行可能であること**。手順通りに実行すれば結果が再現できる粒度で書く
- **前提条件を明示**。必要な権限、ツール、環境変数を冒頭に
- **危険な操作にはチェックポイントを**。「ここで止めて確認する」「失敗時は X に戻す」を含める
- **想定所要時間を書く**。長時間の作業は計画が立てやすくなる

## ファイル名

`<operation>.md`。例: `deploy.md`, `rollback.md`, `data-migration.md`
```

## docs/postmortem/README.md

```markdown
# ポストモーテム

**インシデント・障害の振り返り記録**を置く場所。

## 何を残すか

- 何が起きたか（事象）
- 影響範囲・影響時間
- 原因（直接原因・根本原因の両方）
- 対応の時系列（検知 → 着手 → 解決）
- 学び・再発防止策

## 書き方の原則

- **個人を責めない**。プロセスやシステムに対する学びとして書く
- **時系列を正確に**。検知時刻・対応開始時刻・解決時刻を残す
- **アクションアイテムを明確に**。担当者と期限を持たせる
- **再発防止策は実行可能なものを**。「気をつける」「注意する」は実行可能ではない

## ファイル名

`YYYY-MM-DD-<短い事象名>.md`

例: `2026-01-15-database-connection-leak.md`

## テンプレート

\`\`\`markdown

- 発生日時: YYYY-MM-DD HH:MM (TZ)
- 検知日時: YYYY-MM-DD HH:MM (TZ)
- 解決日時: YYYY-MM-DD HH:MM (TZ)
- 影響範囲: （ユーザー数・機能・地域など）
- 重大度: SEV-1 / SEV-2 / SEV-3
```

## docs/plans/README.md

```markdown
# 実装計画書

ある程度規模のある変更（機能追加・改修・バグ修正・リファクタリング・インフラ変更など）の **実装計画書を一時的に置く場所**。

⚠️ **このディレクトリのドキュメントは完了時に削除する前提**。永続的なドキュメントではない。

## このディレクトリの性質

他のカテゴリはすべて「残す」前提だが、`plans/` は **transient（消える）系**。
実装が完了したら、残す価値のある情報を各所に抽出して、計画書本体は削除する。
これにより設計書に「永続的な判断」と「陳腐化する手順・コード例」が混在する問題を避ける。

## いつ作るか

- 一定規模の機能追加・改修
- バグ修正でも複数ファイルや段階的対応が必要なもの
- リファクタリング
- インフラ・運用構成の変更

数ファイル程度の自明な変更では作らなくてよい。判断に迷ったら「実装中にレビューや参照したくなる粒度か」を問う。

## 計画書に最低限あるとよい情報

プロジェクト固有のテンプレートがあればそれに従う。なければ次を出発点に（**固定テンプレートではなく推奨項目**。変更種別に応じて取捨する）。

- **スコープ** — 何を変更するか（範囲を明確に）
- **目的・動機** — なぜこの変更が必要か
- **方針** — どう変更するか（主要な設計判断。詳細はコードで）
- **影響範囲** — 触るファイル群・影響する機能
- **リスク・落とし穴** — 想定される問題・回避策

「フェーズ分割」「コードサンプル」「テスト戦略」「タスクリスト」などは必要に応じて足す。
これらは陳腐化しやすい情報なので**最終的には削除する**前提で書く。

## ライフサイクル

1. 作成 — 設計・レビュー段階
2. 実装中の参照 — レビュー・実装の指針として使う
3. 完了時の抽出（下記チェックリスト）
4. 計画書を削除

## 完了時の抽出チェックリスト

実装完了時、計画書を削除する前に必ず確認する。

- [ ] 残す価値のある意思決定 → `docs/adr/` に抽出（`create-adr` スキル）
- [ ] コードと共に育つ機能設計 → `docs/design/` に追加・更新（`extract-design` スキル）
- [ ] 新しい横断規約 → `docs/architecture/` に追加・更新
- [ ] 用語の追加 → `docs/glossary.md` に追記
- [ ] 設計書から分離した詳細（バージョンアップ影響・問題調査・採用済み技術の運用ノウハウなど） → `docs/research/` に抽出
- [ ] 抽出漏れがないことを確認した上で本計画書を削除

## ADR / design 等から計画書への参照は禁止

計画書は完了時に消えるため、ADR や design ドキュメント側から計画書へリンクしない。
**抽出された情報は計画書を参照せずに完結している必要がある**。

## ファイル名

主題のケバブケース。日付・連番は不要（消える前提なので時系列重要でない）。

例:
- `refactor-auth-middleware.md`
- `feature-multi-tenant.md`
- `infra-migrate-rds-aurora.md`

## draft.md について

`plans/draft.md` には「今すぐ着手しないが忘れたくない」アイデアを箇条書きで残す。
書き方ガイドは [draft.md](./draft.md) 自身を参照。
```

## docs/README.md（パッケージ配下、モノレポ専用）

モノレポでパッケージごとに `docs/` を作る場合の README ひな形。
**ルート方針を基本とし、パッケージ固有の差分のみを記述する**方針。ルートの方針内容を再掲しない（DRY、ルート更新が自動的に反映される）。

```markdown
# <パッケージ名> ドキュメント

このディレクトリには `<パッケージ名>` 固有のドキュメントを置く。

リポジトリ全体のドキュメント方針は [`docs/README.md`](../../../docs/README.md) を参照。
本ファイルはこのパッケージ固有の方針のみを記述する（ルートの方針に準拠する部分は記載しない）。

## このパッケージ固有の方針

ルート方針からの逸脱・追加ルールがあれば記載する。代表的な対象:

- 命名規則・配置の例外
- このパッケージでのみ採用／不採用のカテゴリ
- パッケージ固有の用語の扱い（ルート用語集との関係）

固有方針がない場合は「現状なし。すべてルート方針に準拠する。」と明記する（空にしない）。
```
