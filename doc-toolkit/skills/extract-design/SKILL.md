# extract-design

実装設計書または実装コードを入力として受け取り、「長く読まれる前提のドキュメント」を作るためのスキル。

## このスキルが扱う問題

実装設計書は、設計と実装計画が混ざりやすい。フェーズ分割・具体的なデータ構造・コード例などは実装中は不可欠だが、実装が進むにつれてコードが正となり乖離していく。実装後も価値が残るのは「なぜこの設計か」「どう拡張するか」「何に気をつけるか」といった**設計意図と運用知**だけ。

また、ドキュメントが存在しない既存機能のコードからも、同じ種類の情報を抽出して残しておきたい状況がある。

このスキルは両方の入口に対応し、出力としては **1 つの主題に絞った設計ドキュメント**を作る。網羅的なリファレンスや API ドキュメントではない。

## 起動時に最初に確認すること

入力ソースとスコープが曖昧なまま書き始めると、的外れな抽出になる。次の 3 点をユーザーに確認するか、依頼文から読み取る。

1. **入力ソース** — 実装設計書か / コードか / 両方か
2. **対象主題** — 例: 監査ログ、RBAC、エラーハンドリング方針、ディレクトリ構成、特定機能の同期メカニズムなど。ドキュメントの粒度を決めるためのスコープ
3. **出力先** — どこに、どんなファイル名で保存するか（既存の `docs/` 配下に慣習がある場合はそれに従う）

スコープが広すぎる場合（例:「このリポジトリ全体の設計を抽出」）は、ユーザーに分割を提案する。1 ドキュメント 1 主題が読みやすさの原則。

## 何を残し、何を落とすか

これがこのスキルの核。判断基準は「**コードが変わったときに陳腐化するか**」。

### 残す（コードが変わっても価値が残る）

- **設計意図と背景** — なぜこの構造を選んだか、何を避けるためか
- **メンタルモデル** — 全体を理解するための概念図、登場人物の役割、データの流れ
- **運用ルール・規約** — 「常にこう書く」「これは絶対にしない」といった暗黙の前提
- **拡張・変更手順** — 新しい X を追加するときに踏むべきステップ（チェックリスト形式が読みやすい）
- **制約と落とし穴** — 一見冗長・不自然に見えるが意図的にそうなっている箇所、誤って壊しやすい箇所
- **トレードオフの記録** — なぜ別案 Y ではなく X を採用したか（採用案の優位性が将来失われたとき再検討の根拠になる）
- **参照ポイント** — 主要なファイル・モジュールへの**最小限の**ポインタ（深いコード引用は避ける）

### 落とす（実装中にしか価値がない、または陳腐化する）

- **フェーズ・タスク分割** — 実装計画は実装が終わった瞬間に役目を終える
- **TDD のテスト戦略やコミット粒度** — 実装ワークフローの一部
- **具体的なデータ構造の詳細** — 型定義はコードが一次情報。ドキュメントに転記すると乖離の原因になる
- **長いコードスニペット** — 動く保証がなくなる。設計を語るのに必要なら**最小限の擬似コードか型シグネチャ**まで
- **行番号付き参照** — リファクタで即陳腐化する
- **完了済みの TODO や移行ステップ** — 実装済みのものは履歴に過ぎない
- **APIのリクエスト/レスポンス例** — APIドキュメント側の責務

判断に迷ったら「1 年後にこのコードベースを引き継いだ人が読んで価値があるか」を問う。

## ワークフロー

どちらのモードでも、**実装コードが構造・挙動の一次情報**であることは変わらない。違うのは「設計意図・背景」を得るための入口があるか（設計書がある）、自分で読み取りに行く必要があるか（コードしかない）。

### モード A: 実装設計書がある場合

設計書は **設計意図・背景を得るための入口** として使い、構造の確認はコードで行う。

1. **設計書を読む** — 全文読み「設計判断・背景・運用ルール」のような長期価値のある部分と、「フェーズ分割・実装計画」のような捨てる部分を頭の中で分類する
2. **コードで構造を確認** — 設計書に書かれた構造が実装でどう実現されているか主要部分を読む。乖離がある場合は**コード側を正**として記載する（設計書をそのまま転記しない）。矛盾の度合いが大きい場合はユーザーに確認する
3. **構造化** — 後述の「出力構造」に従って章立てを決める。設計書の章立てをそのまま流用しない（実装計画寄りの章立てが残ってしまうため）
4. **執筆** — 設計意図・運用ルール・拡張手順を中心に書く。コード例は最小限
5. **削ぎ落とし** — ドラフトを書いた後、もう一度「コードが変わったら陳腐化するか」で各段落を見直して削る

### モード B: コードしかない場合

設計意図はコードから読み取る・ユーザーに聞くしかない。推測で埋めない。

1. **対象範囲の特定** — 主題に関わるファイル群を `Grep`/`Read` で洗い出す。エントリポイント、データの流れの起点・終点、関連する型定義
2. **メンタルモデルの構築** — 「このコードは何を実現しようとしているか」を自分の言葉で説明できるまで読む。表面的な処理の説明ではなく、抽象レベルでの役割
3. **設計判断の発見** — コードに表れている**意図された判断**を見つける。例: 共通化されている箇所、あえて分離されている箇所、コメントで触れられている制約、命名規則、エラー処理の一貫したパターン
4. **疑問点の整理** — コードからは読み取れない「なぜこうなっているか」をリスト化し、ユーザーに確認する（推測で書かない）
5. **執筆** — モード A と同じ章立てで書く。コードから読み取った事実と、ユーザーから得た意図を組み合わせる

## 出力構造

`references/output-template.md` を出発点として使う。テンプレートを機械的に埋めるのではなく、主題に応じて不要な節は削り、必要なら独自の節を足す。

代表的なセクションと使いどころ:

- **概要・目的** — 必須。この主題が何を担っているか、なぜ存在するか
- **メンタルモデル** — 全体像を一段抽象化した説明。図・表があると有効
- **主要コンポーネント / 配置** — どこに何があるかの地図。深い説明は避け、ポインタに留める
- **設計判断と背景** — なぜこの形か。代替案を退けた理由
- **運用ルール・規約** — 守るべき暗黙の約束
- **拡張・変更手順** — 「新しい X を追加するには」のような手順書。チェックリスト推奨
- **制約・落とし穴** — 触ると壊れる箇所、注意点
- **関連リンク** — 関連 ADR、関連ドキュメントへのリンク

不要な節を残すと薄まる。主題によっては「拡張手順」がメインで「メンタルモデル」が短くてよい、あるいはその逆になる。

## 出力先

出力先はプロジェクトの慣習に従う。判断の優先順位:

1. ユーザーが明示的に指定したパス
2. 既存の `docs/` 配下に類似ドキュメントがある場合、その配置と命名規則に合わせる
3. 慣習が見つからない場合、`docs/architecture/<topic>.md` または `docs/design/<topic>.md` を提案してユーザーに確認

ファイル名は主題を端的に表すケバブケース（例: `audit-log.md`, `rbac.md`, `state-management.md`）。

## 品質チェック

書き終わったら以下を確認する:

- **1 年後に読んでも価値が残るか** — 陳腐化しそうな記述が混ざっていないか
- **主題が 1 つに絞れているか** — 複数の主題が混在しているなら分割を検討
- **「なぜ」が書かれているか** — 「何を」だけだとコードを読めばわかる情報の重複になる
- **コードと矛盾していないか** — 設計書から起こした場合、コード側の現状と食い違っていないか
- **拡張手順が実行可能か** — 「新しい X を追加するには」の手順を実際に頭の中で辿れるか
- **コード引用が最小限か** — 長いスニペットや行番号参照が残っていないか
