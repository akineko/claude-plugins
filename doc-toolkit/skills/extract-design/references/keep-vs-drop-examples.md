# 残す情報・落とす情報の具体例集

このスキルの判断で最も難しいのが「何を残し、何を落とすか」。具体的な before/after を並べて感覚を共有する。

判断の中心軸: **「コードが変わったときに陳腐化するか」「1 年後に読んで価値が残るか」**。

---

## 例 1: ディレクトリ構成

### ❌ 落とすべき記述

```
src/
├── audit/
│   ├── logger.ts (123行) — ログ出力
│   ├── transports/
│   │   ├── stdout.ts (45行)
│   │   └── kafka.ts (87行)
│   ├── schema.ts (210行)
│   └── index.ts (12行)
└── ...
```

行数や個別ファイルの細かい列挙はリファクタで即陳腐化する。

### ✅ 残すべき記述

```
src/audit/ — 監査ログ機能の本体
├── logger.ts — ログ出力のエントリポイント。アプリ全体から呼ばれる単一の入口
├── transports/ — 送信先別の実装。ストレージや配信プロトコルが増えるたびにここに追加する
└── schema.ts — ログのスキーマ定義。新しいイベント型は必ずここに登録してから使う
```

「何を担うディレクトリか」「どこに何を足すか」が伝わる。

## 例 2: 監査ログのフォーマット

### ❌ 落とすべき記述（実装設計書からそのまま転記）

```ts
interface AuditLog {
  id: string;
  timestamp: ISO8601;
  actor: { userId: string; role: Role };
  action: ActionType;
  target: { type: string; id: string };
  metadata: Record<string, unknown>;
  // ... 30 行続く
}
```

型の詳細はコード側が一次情報。転記すると乖離する。

### ✅ 残すべき記述

監査ログのスキーマは以下の役割に対応するフィールドで構成される:
- **誰が** — actor (ユーザー ID とロール)
- **いつ** — timestamp
- **何を** — action と target
- **追加情報** — metadata (アクション種別ごとの拡張領域)

詳細な型定義は `src/audit/schema.ts` を参照。

スキーマ拡張の方針: 共通フィールドを増やさず、アクション種別固有の情報は `metadata` に入れる。これは固有情報がトップレベルに散らばると分析クエリが複雑化するため。

## 例 3: 新しい監査イベントの追加手順

### ❌ 落とすべき記述

```
## 実装フェーズ
### Phase 1: スキーマ追加 (PR #234 で実装済み)
### Phase 2: イベントクラス実装 (PR #235 で実装済み)
### Phase 3: 呼び出し元の更新 (PR #236 で実装済み)
```

完了したフェーズと PR 番号は履歴。ドキュメントに残す価値が薄い。

### ✅ 残すべき記述

```
## 新しい監査イベントを追加する

1. `src/audit/schema.ts` の `ActionType` にイベント種別を追加する
2. `src/audit/events/` に対応するイベント定義を実装する
3. 発火元ドメインから新イベントを呼び出す
4. metadata のスキーマが既存と異なる場合、分析クエリの利用者に共有する

最低限テストすべきこと:
- 新イベントが既存の transport を経由して正しく送信されること
- metadata の必須フィールドが欠落した場合に検出されること
```

手順そのものは陳腐化しにくく、追加作業時のチェックリストとして繰り返し参照される。

## 例 4: エラーハンドリング方針

### ❌ 落とすべき記述

```
## エラー処理実装計画
- Phase 1: try-catch ブロックを各ハンドラに追加（2 日）
- Phase 2: エラーログの出力先を統合（1 日）
- Phase 3: クライアントへのレスポンス整形（半日）

## 主要コード
\`\`\`ts
function handleApiError(err: Error) {
  if (err instanceof ValidationError) {
    return res.status(400).json({ ... });
  }
  // ...
}
\`\`\`
```

実装計画とコード例は実装中の話。

### ✅ 残すべき記述

```
## エラーハンドリング方針

エラーは **発生元に近い場所では握りつぶさず、API 境界の単一ポイントで集約処理する**。

レイヤー別の責務:
- ドメイン層: 不正な状態は専用エラー型を投げる（汎用 Error は使わない）
- アプリケーション層: ドメインエラーをユースケース文脈の例外に変換する。再スローするか、許容できる場合のみ握る
- API 境界 (`src/api/middleware/error-handler.ts`): ここで初めて HTTP レスポンスにマップする

### よくある落とし穴

- ドメイン層で try-catch して原因不明のメッセージを返してしまうケース。境界まで素直に投げ上げる
- 非同期処理の `unhandledRejection` を境界が拾えない場合がある。新しい非同期エントリポイント（cron, queue worker）を追加する際は専用のエラーハンドラを設定する
```

方針と落とし穴は長く価値が残る。

## 例 5: フロントエンドの状態管理方針

### ❌ 落とすべき記述

```
## 採用ライブラリ
- Zustand v4.5.0
- React Query v5.x
- React Hook Form v7.x

## ストア定義例
\`\`\`ts
export const useUserStore = create<UserState>((set) => ({
  user: null,
  setUser: (u) => set({ user: u }),
}));
\`\`\`
```

具体的なライブラリのバージョンと個別ストアの実装はコード側が正。

### ✅ 残すべき記述

```
## 状態管理の分類

状態を性質で分けてそれぞれ異なる仕組みで管理する:

- **サーバー状態** — API から取得したデータ。React Query が一次保持。コンポーネントから直接フェッチしない
- **クライアント状態（永続的）** — ユーザー設定、認証情報など。Zustand のグローバルストア
- **クライアント状態（一時的）** — モーダルの開閉、入力中のフォーム値など。コンポーネントローカルの useState または Hook Form

### 守るべきルール

- サーバーから取れる情報はクライアント状態に複製しない（同期破綻の原因）
- グローバルストアは過剰に作らない。コンポーネント間で共有が必要になった時点で初めて引き上げる
- 派生値はストアに持たず、selector か useMemo で算出する

### 状態スコープを変える手順

1. ローカル state を Hook 抽出して分離可能か確認する
2. 複数コンポーネントで必要ならまず Context、頻繁な更新を伴うなら Zustand に上げる
3. グローバル化したら旧 state を必ず除去する（重複状態を残さない）
```

選択基準と運用ルールが本質。

## 例 6: 自作 RBAC の設計

### ❌ 落とすべき記述

```
## ロール定義
| ロール | 権限 |
|---|---|
| admin | すべて |
| editor | 作成、編集 |
| viewer | 閲覧のみ |

## 実装ステップ
- Phase 1: ロールテーブル作成
- Phase 2: ミドルウェア実装
```

ロール一覧はコード側のシードか定数が正。実装ステップは消える情報。

### ✅ 残すべき記述

```
## 認可の判定モデル

権限判定は **(ユーザー, アクション, リソース) の 3 つ組** で行う。ロールは「アクション集合へのラベル」に過ぎず、判定本体は常にアクション単位で評価する。

### なぜロール直接判定を避けたか

`if (user.role === 'admin')` 形式の判定はビジネス側の権限変更（「editor も削除できるようにしたい」など）でコード全体に影響が広がる。アクション単位の判定にしておくと、ロール定義の差し替えだけで対応できる。

### 拡張手順

新しいアクションを追加するには:
1. `src/auth/actions.ts` にアクション定数を追加する
2. ロール × アクションのマトリクス（`src/auth/role-permissions.ts`）を更新する
3. 呼び出し元で `can(user, ACTION_X, resource)` を使う
4. リソース単位のチェックが必要な場合は ResourcePolicy（`src/auth/policies/`）を追加する

### 落とし穴

- ResourcePolicy は **ロール判定の後** に走る。ロールでブロックされたケースは Policy まで届かない
- 一括操作のときは「すべてのリソースに対して許可されているか」を都度判定する必要がある（途中で失敗すると整合性が崩れるため）
```

「なぜこの判定モデルか」「追加手順」「落とし穴」が長く読まれる情報。

## 例 7: Three.js と React フォームの双方向同期

### ❌ 落とすべき記述

```
## 実装コード
\`\`\`tsx
function CoordinateForm({ object }) {
  const [x, setX] = useState(object.position.x);
  useEffect(() => {
    object.position.x = x;
  }, [x]);
  // ... 50 行続く
}
\`\`\`
```

実装コードはコード側が正。

### ✅ 残すべき記述

```
## 座標同期の仕組み

Three.js のオブジェクト座標と React のフォーム入力値を双方向に同期させる。素朴に実装すると無限ループ・チラつき・桁落ちで破綻する領域。

### 同期の方向と権威

- **ユーザー操作の起点はどちらか一方** — フォーム入力時はフォームが権威、3D 上のドラッグ時は Three.js が権威
- 起点側が変更を検知し、もう一方に「外部由来の更新」として通知する。受け手はその通知では再通知を発火しない（ループ防止）

### 実装上の鍵

- 同期の単一窓口（`src/three/sync/coordinate-bridge.ts`）を経由する。直接 `object.position` を書き換える呼び出しはこの窓口を介さない限り禁止
- フォーム値はユーザーが編集中の状態（typing 中）と確定状態を区別する。確定までは Three.js 側を更新しない（途中値で再描画されるとパフォーマンス劣化）
- 値の比較は浮動小数の許容誤差を考慮する。完全一致では同期ループが止まらない

### よくある壊れ方

- 新しい座標項目を追加する際に bridge を経由せず直接更新してしまう → 一方通行になる
- 入力中の値を即座に Three.js に送る → ドラッグ操作とぶつかってカーソルが暴れる
```

仕組みと落とし穴は長期的に価値がある。

## まとめ: 判断のヒューリスティック

| 種類 | 残す目安 |
|---|---|
| 設計意図・採用理由 | 残す |
| 運用ルール・規約 | 残す |
| 拡張・変更手順 | 残す |
| 落とし穴・制約 | 残す |
| ディレクトリの役割（高レベル） | 残す |
| ファイルの行数・サイズ | 落とす |
| 完了済みフェーズ・PR 番号 | 落とす |
| 具体的な型定義の転記 | 落とす（コードを参照させる） |
| 長いコードスニペット | 落とす（最小限の擬似コード程度なら残す） |
| ライブラリの具体バージョン | 落とす（package.json が正） |
| 実装ステップ・スケジュール | 落とす |
