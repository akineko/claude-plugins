# 出力ドキュメントの章立てテンプレート

このテンプレートは出発点。主題に応じて節を取捨選択し、順序を入れ替えてよい。機械的に全部埋めようとせず、その主題で語る価値のある節だけを残す。

---

# [主題名]

## 概要

このセクションが扱うものを 2〜4 文で説明する。「これは何を担う仕組みか」「なぜ必要か」に答える。読者が「自分が今読むべきドキュメントか」を判断できる粒度にする。

## メンタルモデル

主題を理解するための抽象的な見取り図。図解や登場人物の一覧、データの流れなど。

例:
- 関与するコンポーネントとその責務
- データ・制御の流れ
- 概念的なレイヤー分け

具体的なコードレベルの詳細はここに書かない。

## 主要コンポーネント / 配置

どこに何があるかの地図。深い説明は避け、リンク（ファイルパス）に留める。

例:
- `src/audit/logger.ts` — ログ出力の中核
- `src/audit/transports/` — 送信先別の実装
- `src/audit/schema.ts` — ログのスキーマ定義

行番号は付けない（リファクタで陳腐化する）。

## 設計判断と背景

なぜこの形を選んだか。代替案を退けた理由があれば書く。後から「これは元の意図と合っているか」を判断する根拠になる。

例:
- なぜ単一のエントリポイントに集約しているか
- なぜ XX 形式ではなく YY 形式を採用したか
- 想定している制約（パフォーマンス、互換性、運用上の理由）

## 運用ルール・規約

守るべき暗黙の約束。コードを読んでも明示されていないが、コードレビューで指摘されるような事項。

例:
- 新しいログ項目は必ずスキーマに登録してから使う
- エラーは握りつぶさず、必ず特定のレイヤーで集約処理する
- この種のオブジェクトは直接 new せず、ファクトリを経由する

## 拡張・変更手順

「新しい X を追加するには」「Y を変更するときに踏むべきステップ」のような手順書。チェックリスト形式が読みやすい。

例:
新しい監査ログイベントを追加する手順:
1. `schema.ts` にイベント型を追加する
2. `events/` 配下に対応するイベントクラスを実装する
3. 送信元のドメインコードから新イベントを発火する
4. 必要に応じて Transport 側のフィルタを更新する
5. テストとして XX のケースを追加する

## 制約・落とし穴

「これに触ると壊れる」「一見不自然だが意図的」な箇所の記録。実装を読んでも気付きにくいため、明示的に残す価値が高い。

例:
- A のレースコンディションを避けるため、必ず B より先に呼ぶ必要がある
- このフラグは見かけ上重複しているが、それぞれ別の用途で使われている
- 削除フローでは外部キーの整合性のため処理順を逆にする必要がある

## トレードオフ

採用した設計の弱点と、それを許容した理由。後から「この弱点が顕在化したら見直す」という判断材料になる。

例:
- 同期書き込みのため大量ログ時にレイテンシ影響あり。許容量を超えたら非同期化を検討
- スキーマを厳格にした分、追加のたびにマイグレーションが必要
