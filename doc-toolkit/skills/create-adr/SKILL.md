# create-adr

実装設計書やAIとの設計相談のような「決定事項とノイズが混ざったソース」から、**意思決定の核**だけを抜き出してADRを作成する。

## このスキルが解く問題

ADRは「なぜその決定をしたか」を未来の自分やチームに伝える文書だが、ソースとなる素材は次のような問題を抱えている：

- **実装設計書**: 決定の根拠だけでなく、データ構造・コード・フェーズ分割・テスト計画など、実装が進むと現状と乖離する詳細を多く含む
- **AIとの設計相談**: 確定に至るまでの試行錯誤・却下された案・補足説明・脱線が含まれ、結論だけ取り出すのに労力が要る

両者に共通するのは「決定事項そのものよりノイズの方が多い」という点。このスキルの役割は、ソースの形式に依らず、**ADRとして時間の試練に耐える情報だけを残す**こと。

## ADRに残すもの・落とすもの

ADRが追跡したいのは「**何をなぜ選んだか、結果どうなるか**」。判断に迷ったら次の表に立ち返る。

| 残す | 落とす |
|---|---|
| Title: 何についての決定か | フェーズ・ステップ分割 |
| Context: 制約・前提・解こうとした問題 | 実装の手順・タスクリスト |
| Decision: 何を選んだか（採用案の概要） | 詳細なデータ構造・スキーマ定義 |
| Consequences: 採用による影響・トレードオフ | コード例・実装スニペット |
| Alternatives: 検討した代替案と却下理由 | テスト戦略・テストケース |
| Status: 提案中／採用済み／撤回 等 | スケジュール・期限 |
| Related: 関連する別のADR | 試行錯誤の経緯・脱線 |

落とす側のルールは「**実装が変わると陳腐化するもの**」と「**決定の動機を理解する上で不要な詳細**」。境界が曖昧なときは「6ヶ月後の自分がコードを読まずにこの判断の妥当性を再評価できるか」を基準にする。

## ソース別の抽出方針

### 1. 実装設計書からの抽出

設計書は構造化されているので、セクション単位で取捨を判断しやすい。典型的なマッピング：

- 「目的」「背景」「課題」セクション → **Context**
- 「採用案」「設計方針」「選定結果」セクション → **Decision**
- 「比較」「検討した案」「却下した案」セクション → **Alternatives**
- 「制約」「トレードオフ」「リスク」セクション → **Consequences**（影響範囲として）
- 「実装計画」「フェーズ」「タスク」「スケジュール」 → **落とす**
- 「データモデル」「API仕様」「コード例」 → 原則落とす。ただし**選択を一意に表現するために必要な最小限の固有名（採用したライブラリ名・パターン名）**は Decision に残す
- 「テスト戦略」 → 落とす

設計書が複数の独立した決定を含む場合は、決定ごとにADRを分ける（粒度は「Statusが独立して変わりうるか」で判断）。

詳しい判断境界は @references/extraction-rules.md を参照。

### 2. AIとの設計相談からの抽出

会話ログは時系列に揺らぐ。最終的な合意点を起点に逆引きする。

- 最後の合意・確定発言から **Decision** を取る
- 確定に至るまでに却下された案を **Alternatives** に集約（採用案と並ぶ「対案」として）
- 議論の出発点となった問題提起・制約条件を **Context** に整理
- 採用後に懸念として共有された事項を **Consequences** に
- 「あとで決める」「保留」となった事項は ADR には含めず、ユーザーに口頭で「未決事項あり」と伝える

会話の文脈に依存した曖昧な表現（「さっき言ったやつ」「あれ」「先ほどの案」）は、ADR本文では具体名に展開する。展開できない場合はユーザーに確認する。

## ワークフロー

1. **ソースを特定する**
   - ユーザーが設計書ファイルを指定 → そのファイルを読む
   - 「これまでの会話から」「さっきの議論を」等 → 直近の会話履歴を対象にする
   - 不明な場合は確認してから進める

2. **決定の単位を見極める**
   - ソースに複数の独立した意思決定がある場合は分割する
   - 関連はあるが Status が連動しないものは別ADRにし、Related で相互参照する

3. **抽出してテンプレートに埋める**
   - テンプレートは @references/adr-template.md
   - 抽出のbefore/after例は @references/examples.md
   - 空欄が出るセクション（例: Alternativesがソースに無い）はソースに無いことを明示するか、ユーザーに不足を確認する

4. **出力先を決めて書き出す**
   - 既存のADR置き場（`docs/adr/`, `doc/adr/`, `adr/` 等）があればそこに従う
   - 無い場合はユーザーに保存先を確認する
   - ファイル名は `YYYY-MM-DD-<短いケバブケースのタイトル>.md`。日付は `date '+%Y-%m-%d'` で取得した今日の日付を使う
   - 連番運用（`0001-xxx.md`）が既に使われているならそれに合わせる

5. **書き出し後にユーザーに確認を促す**
   - 抽出時に落とした情報のうち、ユーザーが残したいかもしれないもの（例: 重要な技術名、却下理由の補足）があれば一覧で報告する
   - 未決事項・確認漏れがあればここで明示する

## 守るべきこと

- **新しい情報を創作しない**。ソースに書かれていない理由を補完しない。Contextに書く制約や却下理由がソースから読み取れないなら、空欄にしてユーザーに確認する
- **採用案を抽象化しすぎない**。「適切な認証方式を採用する」のような無情報の記述ではなく、ソースから読み取れる範囲で具体名（「OIDC + PKCE」など）を入れる
- **Consequencesは正直に書く**。良い影響だけでなく、採用によって生じる新たな制約・移行コスト・将来の制限も書く。ソースで言及されていれば確実に拾う
- **Statusはデフォルト「Accepted」にしない**。ソースが「相談中で確定した」文脈なら Accepted、設計書が下書きフェーズなら Proposed。判断がつかなければユーザーに聞く
