# 抽出例（before / after）

実際にどの程度削ぎ落とすかを示す例。「これくらい削っていい」「これは残す」の感覚を掴むためのもの。

---

## 例1: 実装設計書からの抽出

### Before: 設計書の抜粋

```markdown
# ユーザー認証基盤の実装設計書

## 目的
SaaSのユーザー認証基盤を整備し、エンタープライズ顧客のSSO要件に対応する。

## 背景
- 現在は自前のメール+パスワード認証のみ
- エンタープライズ顧客3社からSAML SSO対応要望
- 自社開発チームの認証専門家は不在
- 半年以内のリリースが営業ロードマップでコミット済み

## 検討した選択肢

### A. 自前実装の拡張
既存実装に SAML / OIDC を追加実装。
- メリット: 外部依存なし
- デメリット: セキュリティ専門知識が必要、開発工数大、運用負荷

### B. Auth0
マネージドな IdaaS。
- メリット: 主要プロトコル対応済み、運用負荷低
- デメリット: コスト、ベンダーロックイン

### C. Keycloak セルフホスト
OSSのIdP。
- メリット: ライセンスコストなし、機能豊富
- デメリット: 運用負荷（K8s上での運用が必要）

## 採用案: B. Auth0

理由:
- 半年リリースのコミットに対し、専門家不在で自前は危険
- C.は運用負荷が3人チームでは過大
- B.のロックインリスクはOIDC準拠で抽象化可能と判断

## データモデル

ユーザーテーブルに以下を追加:
- `auth0_user_id`: VARCHAR(64), UNIQUE
- `auth_provider`: ENUM('legacy', 'auth0')
- `migrated_at`: TIMESTAMP NULL

## 実装フェーズ

### Phase 1: Auth0テナント構築 (1週間)
- テナント作成
- アプリケーション登録
- カスタムドメイン設定

### Phase 2: 新規ユーザー向け実装 (3週間)
- ログインフロー実装
- コールバックハンドラ
- セッション管理

### Phase 3: 既存ユーザー移行 (2週間)
- 自動移行ジョブ実装
- フォールバック認証
- 移行完了監視

## テスト戦略
E2Eテストは Playwright で実施。CIで毎晩実行。
```

### After: 抽出したADR

```markdown
# 2026-05-13-auth0-as-identity-provider

- Status: Accepted
- Date: 2026-05-13

## Context

エンタープライズ顧客3社から SAML SSO 対応要望があり、半年以内のリリースが営業ロードマップでコミット済み。一方で社内に認証専門家がおらず、自前実装にはセキュリティリスクと工数の双方で懸念がある。運用チームは3人体制で、追加の運用負荷を吸収する余力は乏しい。

## Decision

ユーザー認証基盤として Auth0 を IdP として採用する。SAML および OIDC を Auth0 経由で提供し、自社アプリケーションは OIDC で Auth0 と連携する。

## Consequences

- 認証プロトコルの実装・保守を自社で行う必要がなくなり、専門家不在のリスクが緩和される
- 月額利用料が発生し、ユーザー数に応じてコストが増える
- ベンダーロックインのリスクが生じる。これに対しては OIDC 準拠でアプリ側を実装することで、将来別IdPへの切り替え余地を残す
- 既存のメール+パスワードユーザーは段階的に移行する必要があり、移行期間中は新旧2系統の認証が共存する

## Alternatives Considered

### 自前実装の拡張
既存のメール+パスワード認証に SAML / OIDC 対応を追加実装する案。社内に認証専門家が不在で半年というスケジュールに対しリスクが高く、却下。

### Keycloak セルフホスト
OSS の IdP である Keycloak を自社運用する案。3人体制の運用チームでは K8s 上での Keycloak 運用負荷が過大と判断し、却下。
```

### 何を落としたか

- データモデルの具体的なカラム定義（`auth0_user_id` 等）
- Phase 1/2/3 の実装フェーズと工数
- テスト戦略（Playwright、CI実行）
- 「メリット・デメリット」の対称的な比較表（却下理由として再構成）

これらは全て、Auth0採用という決定の妥当性を後から再評価する上では不要な情報。実装が変われば陳腐化する。

## 例2: AIとの設計相談からの抽出

### Before: 会話ログの抜粋

```
ユーザー: 新機能で、長時間かかるレポート生成を非同期で処理したい。今のスタックは Rails + Postgres + Redis。

AI: いくつか選択肢があります。Sidekiq、ActiveJob with Async adapter、独立したワーカープロセス、AWS Step Functions などです。要件を教えてください: ジョブの平均実行時間、リトライ要件、可視性の重要度は？

ユーザー: レポートは5〜30分。失敗時は2回までリトライしたい。進捗を画面で見せる必要がある。

AI: それなら Sidekiq が筋がよさそうです。Redis がすでにあるので追加インフラ不要、リトライは設定で対応可能、進捗表示は Sidekiq Job の状態を取得して表示できます。

ユーザー: Step Functions はどう？

AI: AWS Step Functions は複雑なワークフローオーケストレーションに向いていますが、今回はワークフローというより単発の長時間処理なのでオーバースペックです。また Rails アプリから別サービスに処理を渡すコストがかかります。

ユーザー: なるほど。ActiveJob with Async は？

AI: Async アダプタはプロセス内スレッドで動くので、Rails プロセスが落ちるとジョブも失われます。長時間処理には不向きです。

ユーザー: じゃあ Sidekiq で。あ、それから将来的に Pro 版の機能（バッチ処理）を使う可能性があるけど、今は無料版で。

AI: 了解しました。
```

### After: 抽出したADR

```markdown
# 2026-05-13-sidekiq-for-async-report-generation

- Status: Accepted
- Date: 2026-05-13

## Context

新機能として長時間かかるレポート生成（5〜30分）を非同期で処理する必要がある。現行スタックは Rails + Postgres + Redis。失敗時は2回までのリトライ、および生成中の進捗をユーザーに画面表示する要件がある。

## Decision

非同期ジョブ実行基盤として Sidekiq（OSS版）を採用する。リトライは Sidekiq の設定で対応し、進捗表示は Job の状態を取得して画面に反映する。

## Consequences

- 既存の Redis を流用できるため追加インフラは不要
- 将来的に Sidekiq Pro のバッチ処理機能が必要になる可能性が認識されており、その時点でライセンス取得を再検討する余地を残す
- ジョブ実行用に Sidekiq ワーカープロセスの運用が新たに必要になる

## Alternatives Considered

### AWS Step Functions
複雑なワークフローオーケストレーション向けの機能であり、今回の単発長時間処理にはオーバースペック。また Rails アプリから別サービスに処理を委譲するコストが追加で発生するため却下。

### ActiveJob with Async adapter
プロセス内スレッドで動作するため、Rails プロセスが落ちるとジョブが失われる。長時間処理の信頼性要件を満たせないため却下。
```

### 何を落としたか

- 「Sidekiq、ActiveJob、独立ワーカープロセス、Step Functions のどれが良いか」という選択肢列挙の経緯
- AIが要件確認のために行った質問
- 採用に至る前の選択肢の絞り込みの順序（どの順番で却下されたか）
- 議論内で出ては消えた「独立したワーカープロセス」案（明示的に検討対象として議論されなかった）

会話ログには「議論の足跡」が残るが、ADRには「最終的な判断」だけを残す。

## ユーザーへの確認例

抽出後、ユーザーには次のような形で報告する：

> ADRを `docs/adr/2026-05-13-sidekiq-for-async-report-generation.md` に保存しました。
>
> 抽出にあたって以下は意図的に落としました。残したいものがあれば教えてください：
> - Sidekiq Pro の機能名（バッチ処理）の具体的な利用想定
> - リトライ間隔の具体値（議論で言及されず）
>
> また Status は Accepted にしましたが、まだ実装着手前であれば Proposed の方が適切です。
