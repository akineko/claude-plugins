# 抽出ルール詳細

SKILL.md の方針を補強する判断指針。ソースを読みながら迷ったときに参照する。

## 「残す／落とす」の判断境界

### ケース1: 採用したライブラリ・サービス名

**残す**。Decision に必ず含める。「OAuth2を採用」ではなく「Auth0 を IdP として OAuth2 認可コードフローを採用」のように、選択肢が一意に定まる粒度まで書く。

### ケース2: データ構造の詳細

**原則落とす**。ただし「データ構造の選択そのもの」が決定の核である場合（例: 「正規化第3形式ではなく単一テーブル設計を採用」）は、その選択方針だけを Decision に残す。フィールド名や型定義は落とす。

### ケース3: コード例・スニペット

**落とす**。例外として「APIの形（HTTP/gRPC/GraphQL）」「呼び出しパターン（同期/非同期/ストリーム）」のような**構造的選択**は Decision に文章で残す。コードそのものは残さない。

### ケース4: 実装フェーズ・タスク分割

**全て落とす**。フェーズ分割は実装の段取りであり意思決定ではない。ADRには含めない。

### ケース5: テスト戦略

**原則落とす**。例外として「テスト容易性が採用理由の主要因だった」場合は、Consequences または Alternatives の却下理由として一文で触れる。

### ケース6: スケジュール・期限

**落とす**。期限は ADR の関心事ではない。期限が決定理由（「Q4までに必要」など）に効いていた場合のみ、Context に「短期で構築可能であること」のような形で抽象化して残す。

### ケース7: 検討中・保留事項

**ADR本体には含めず**、ユーザーへの報告にまとめる。決まっていない事項は ADR の Status を Proposed にする方が誠実。

### ケース8: トレードオフの説明

**残す**。Consequences に書く。「導入により X が解決するが Y を失う」という形は ADR の中核なので削らない。

## セクション対応マップ（実装設計書 → ADR）

設計書のテンプレートは流派が多いが、典型的なマッピング：

| 設計書のセクション名（例） | ADRでの行き先 |
|---|---|
| 概要 / Overview | Title + Decision の一文目に集約 |
| 背景 / Background / 目的 / Motivation | Context |
| 課題 / Problem | Context |
| 制約 / Constraints | Context（箇条書きで） |
| 採用案 / 設計方針 / Design | Decision |
| 主要ロジック / 動作仕様 | 原則落とす。決定の核を表す表現だけ Decision に |
| データモデル / スキーマ | 原則落とす |
| API仕様 / インターフェース | 落とす。インターフェース設計の方針（REST採用等）のみ Decision に |
| 比較 / 検討した案 / 代替案 | Alternatives Considered |
| トレードオフ / 影響範囲 | Consequences |
| リスク | Consequences |
| 移行戦略 | Consequences（一時的な制約として） or 別ADR |
| 未決定事項 / 残課題 | ADR外（ユーザー報告） |
| 実装計画 / フェーズ / ロードマップ | 落とす |
| テスト戦略 | 落とす |
| スケジュール | 落とす |

## 会話ログからの抽出パターン

### パターン1: 段階的に絞り込まれた結論

「A案・B案・C案を検討」→「Bは却下」→「最終的にA」のような流れ。

- 最終発言を Decision の起点にする
- B, C は Alternatives に却下理由とともに記載
- 絞り込みの過程で出てきた制約は Context に集約

### パターン2: ユーザーの一言で確定

「じゃあ X で」のような短い確定。

- X が何を指すかを会話を遡って具体化する
- Context は議論の出発点となった問題提起から取る
- 代替案が明示されていない場合、Alternatives は省略可（ただしユーザーに「却下した案を残しますか」と確認）

### パターン3: 複数決定が混在

一回の議論で「認証方式」「DB選定」「デプロイ先」など複数決まった場合。

- それぞれ独立したADRに分ける
- 各ADRの Related で相互参照
- ファイル名の日付は同じでよい

## 粒度の判断

「複数のADRに分けるべきか、ひとつにまとめるべきか」は次で判断する：

- **Status が独立して変わりうるか**: Yes なら分ける
- **却下理由がそれぞれ異なるか**: Yes なら分ける
- **将来 Superseded されるとき、同時に置き換わるか**: 同時なら同じADRでよい

## ユーザーに確認すべきタイミング

以下のいずれかに該当したら、書き出す前にユーザーに確認する：

- Status を Proposed にするか Accepted にするか判断できない
- ソースから却下理由が読み取れない代替案がある
- 落とすか残すか迷う「実装詳細だが採用理由として効いている」情報がある
- 出力先（保存ディレクトリ・ファイル名規約）が分からない
- 複数決定が混在しており、分割可否の方針が決まらない
