# ADR テンプレート

MADR (Markdown Architectural Decision Records) を簡素化したテンプレート。実装設計書ではなく**意思決定の記録**であることを念頭に、各セクションは簡潔に書く。

```markdown
# <連番もしくは日付>-<短いタイトル>

- Status: <Proposed | Accepted | Deprecated | Superseded by [link]>
- Date: <YYYY-MM-DD>
- Deciders: <意思決定に関わった人／省略可>

## Context

<この決定が必要になった背景。解こうとしている問題と、検討時点で動かせなかった制約・前提を書く。「なぜ今これを決めるのか」が読み取れること。>

## Decision

<採用した案。読み手が「結局何を選んだか」を最初の数行で把握できるように書く。固有名（採用したライブラリ・パターン・方式）は省略しない。>

## Consequences

<採用したことで何が起こるか。良い影響と悪い影響の両方を書く。新たに生じる制約、将来的に発生しうる課題、運用上の注意点を含める。>

## Alternatives Considered

<検討した代替案を列挙し、それぞれなぜ採用しなかったかを短く書く。「比較表」よりも「却下理由」に重きを置く。>

### <代替案A>
<概要と却下理由>

### <代替案B>
<概要と却下理由>

## Related

<関連する別のADR、参考にした外部資料へのリンク。任意。>
```

## セクションごとの書き方の目安

### Status

- `Proposed`: 草案。まだ採用前
- `Accepted`: 採用済み
- `Deprecated`: かつて採用していたが現在は使っていない（代替もない）
- `Superseded by <link>`: 別のADRに置き換えられた

会話履歴からADRを起こすときは、ユーザーが明示的に「これで行く」と確定したかで判断する。判断がつかないなら Proposed で出してユーザーに確認する。

### Context

- 解こうとしている問題を 1〜3 文で
- 動かせない制約（例: 既存システムとの互換性、チームスキル、コスト枠）を箇条書きで
- 検討時点で前提として置いた事項

### Decision

- 採用した案を能動態で 1〜3 文で
- 固有名は省略しない（「認証基盤を採用する」ではなく「Auth0 を IdP として採用する」）
- 設計の中核となるパターンや構造があれば名前を出す（例: CQRS、Outbox パターン）

### Consequences

- 利点（採用によって解決される問題）
- 悪影響・新たな制約（運用負荷、コスト、技術的制約、ロックイン）
- 将来的な拡張・撤退の難易度

「Pros / Cons」のように形式化せず、起こることをそのまま書く方が後で読みやすい。

### Alternatives Considered

- 主要な代替案ごとに見出しを立て、却下理由を 1〜2 文で
- 「検討すらしなかった案」は書かない
- 表で比較するより、却下理由を文章で書いた方がADRとして価値が高い
