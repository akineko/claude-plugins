# impact-analysis

機能設計書を入力に、後続の実装設計フェーズが「どこに・何を・どの順で設計するか」を判断できる状態に整理する影響分析スキル。

## このスキルが置かれている設計フロー

```
[1] 要求仕様書 (request-spec)
       ↓
[2] 機能設計書 (feature-options)
       ↓
[3] 影響分析書 (このスキル: impact-analysis)
       ↓
[4] 実装設計書 (implementation-design)
```

このスキルが解く問題は **「実装設計に入る前に、何をどの順で設計すべきかを地ならしする」** こと。後続フェーズの存在は、このスキルの「やらないこと」を強く規定する:

- **[4] 実装設計** が技術選定・データ構造・API契約・アーキテクチャ・フェーズ分割を行う → このスキルでは詳細な How は決めない (「テーブルが必要」までは書くが「テーブルスキーマ」は書かない)
- **[2] 機能設計** がユーザー視点の振る舞いを確定している → このスキルでは振る舞いを再決定しない

つまりこのスキルが答えるべきは:

- **What/Where**: 何が変わるか、どこ(既存コード)に当たるか
- **What-to-design**: 詳細設計フェーズで「設計対象」になるべきトピックは何か
- **In-what-order**: それらを設計する推奨順序は何か

答えてはいけないのは:

- **How**: 具体的にどう設計するか (テーブル定義、API契約、関数シグネチャ、ライブラリ選定、コードレイアウト)

## 入力の前提

- **主入力**: feature-options が生成した機能設計書 (`docs/plans/<機能名>/feature-options.md`)
- **補助参照**: 必要に応じて要求仕様書 (`docs/plans/<機能名>/request-spec.md`) を参照してよい。ただし機能設計書に書かれている情報を再集約しない (成果物が肥大化するため)
- **対象コードベース**: 影響分析対象のリポジトリ。ローカルで調査可能であることを前提にする

機能設計書が見当たらない、または `4. 機能設計` セクションが欠けている場合は、まず feature-options を実施するようユーザーに案内する。

## 中核となる原則

### 原則1: How には踏み込まず、What/Where/設計順序の整理に徹する

このスキルの出力に書いてよい記述の例:

- 「商品カードコンポーネントにハートアイコンを追加する必要がある」(What)
- 「`src/components/ProductCard.tsx` を変更する必要がある」(Where)
- 「お気に入りデータの永続化方式を決める設計トピックがある」(What-to-design)

書いてはいけない記述の例:

- 「`Favorite` テーブルを `user_id, product_id, created_at` で作る」(How — テーブルスキーマ)
- 「`POST /api/favorites` で登録する」(How — API契約)
- 「`useFavorite` カスタムフックを作る」(How — 実装構造)

判定の助け: 書こうとしている記述を読んだ後続スキル(implementation-design)に、**設計の余地が残っているか**を自問する。残っていれば事実/論点の整理、決めきっていたら How への踏み込み。

例外: 機能設計書または要求仕様書に **制約条件** として明示されている技術選定 (例: 「Microsoft Entra ID を使う」「既存の通知基盤に乗せる」) は、影響分析の前提として参照してよい。独自に技術選定を新規追加してはいけない。

### 原則2: コードベース調査はサブエージェントに委譲し、本文は事実の整理に集中する

本スキルは、本体プロセス内で grep/Read を繰り返してコードを直接読み回ることをしない。代わりに **impact-investigator** サブエージェントに調査を依頼し、構造化された返答だけを受け取って本文に反映する。

サブエージェントを使う理由:

- 調査の中で見つかる無関係なコード片が本体スキルのコンテキストを圧迫するのを避ける
- 「調査しながら設計してしまう」ことを避ける (調査中に浮かぶ早すぎる設計判断を排除)
- 並列に複数の調査を投げて速度を稼ぐ

ただし次の場合はサブエージェント不要:

- 機能設計書だけで既に変更箇所と影響範囲が読み取れる小規模機能
- ユーザーから「コードベース調査は省略してよい」と明示された場合
- 機能設計書中で参照されているファイル名が既に十分具体的で、追加の調査価値が乏しい場合

### 原則3: 設計トピックは「独立して1パスで設計できる粒度」で切る

設計トピック = 詳細設計フェーズで「これを設計する」と1単位として扱える設計対象。粒度の目安:

- **大きすぎる例**: 「お気に入り機能全体」(機能丸ごと1トピックは分解の意味がない)
- **小さすぎる例**: 「お気に入り解除ボタンの押下処理」(関数1個レベルは詳細すぎ)
- **ちょうど良い例**: 「お気に入りデータの永続化方式」「お気に入りトグルUIの実装方式」「ナビゲーション動線への追加方式」

判定の助け: そのトピックを単独で詳細設計したとき、**他のトピックの設計を待たずに案を出せるか**? 待たずに出せれば独立したトピック、必ず他を見ないと進まないなら統合した方がよい。

なお **小規模な機能ではトピックが1〜2個に収まることもある**。「無理に分解する」のは本末転倒で、分解の目的は「全部を一度に考えると浅くなる」を避けることにある。**1〜2個で十分なら無理に分割しない**。

### 原則4: 設計バッチは「同時に決めた方が筋が通るもの」をまとめる

設計バッチ = 設計トピックを「一度の設計セッションで一緒に検討するまとまり」に集約したもの。グルーピング基準:

- **同じバッチに入れるべき**: 片方の設計が変わると、ほぼ確実にもう片方の設計も変わる関係 (例: API契約とそのリクエスト処理フロー)
- **別バッチでよい**: 片方の設計を後から見ても、もう片方を変える必要が小さい関係 (例: ロギング設計と画面UIの設計)

機能が大きい場合、全トピックを一度に設計すると次の問題が生じやすい:

- 把握する情報や考えることが多すぎて個々の設計が浅くなる
- 実装設計書の文章量が膨大になり、全容把握も部分参照も難しくなる

設計バッチ単位で分けることで、詳細設計フェーズが各バッチを「一度のまとまった設計の場」として扱えるようにする。

**機能が小規模で全トピックを1バッチで扱える場合は1バッチで止める**。バッチが1つしかない場合は、設計順序の議論が不要なので、その旨を出力で明記する。

### 原則5: 設計順序は「先に決まっている方が後段が楽になる方向」で並べる

設計バッチ間に依存関係がある場合、推奨設計順序を提示する。順序を決める基準:

- **基盤 → 個別**: データモデル、共通インタフェース、共通ライブラリ → それらを使う個別機能
- **契約 → 利用者**: バックエンドAPI契約 → それを使うフロントエンド
- **影響を与える方 → 受ける方**: 設計を後で変えた時の波及が大きい方を先に固める

「並列に進められるバッチ」も明示する。順序が必ず直列とは限らない。

順序の提示は **推奨** であり、絶対ではない。実装設計フェーズで合理的な事情があれば順序を入れ替える余地を残す。

### 原則6: 機能設計書の「6. 後続フェーズへの引き継ぎ」を起点に拾う

feature-options の機能設計書には、最後に `6. 後続フェーズへの引き継ぎ` セクションがあり、そこに **impact-analysis に持ち込みたい論点** が明示的に書かれている。これを起点に変更点・調査必要箇所・設計トピックの初期候補を立てる。

ただし「引き継ぎ」に書かれている論点だけで完結させない。機能設計書の `4. 機能設計` 本文を読み、引き継ぎセクションに明記されていなくても影響しそうな箇所を拾う。

## 進め方

このスキルは「機能設計書から変更点を読み取る → 調査をサブエージェントに並列依頼 → 設計トピック識別 → バッチ化と順序付け → ドラフト出力 → 論点深掘り対話」の流れで進める。

### Phase 1: 入力の受領と俯瞰

1. 入力(機能設計書のパス)を受け取る。指定が無ければユーザーに確認する
2. 機能設計書を読み込み、以下を把握する:
   - `1. 概要` の対象範囲 (どの要求 R を扱うか)、要求カバレッジ、1:1でない箇所 (前提機能や N:M の紐付けがどこか)
   - `4. 機能設計` の各機能(F1, F2, …)の選定案・画面要素・操作フローと、各機能の `関連要求`
   - `5. 横断的な機能設計上の決定` の方針
   - `6. 後続フェーズへの引き継ぎ` の impact-analysis 向け論点と「前提機能の欠落」(あれば)
3. 出力先パスを決定する: 機能設計書と同じディレクトリの `impact-analysis.md`
   - 例: 入力が `docs/plans/favorite-products/feature-options.md` → 出力は `docs/plans/favorite-products/impact-analysis.md`
4. 既に `impact-analysis.md` が存在する場合はユーザーに上書きしてよいか確認する
5. 必要に応じて要求仕様書を参照する。ただし要求仕様書の内容を本スキルの成果物に再掲しない

### Phase 2: 変更点の抽出と調査対象の特定

機能設計書の本文から、コードベース上で **何かしらの変更が必要になる箇所** を抽出する。機能(F)単位で次を整理する(各機能の `関連要求` で、どの要求に紐づくかを辿れる):

- **追加されるもの**: 新規画面、新規UI要素、新規データ、新規導線、新規動作
- **変更されるもの**: 既存画面/コンポーネント/動線のうち、要素追加・配置変更・状態追加が必要なもの
- **連動して影響を受けるもの**: 直接の追加/変更先ではないが、波及で確認が必要な箇所 (例: ナビゲーション全体の整合、既存通知パターンとの整合)

この段階では **「具体的にどのファイル」**を特定する必要はない。「商品カードコンポーネント」「マイページ」「グローバルナビゲーション」のような **論理的な対象** で書き出す。具体的なパスはサブエージェント調査の結果で埋まる。

次に、これらの中で **コードベース調査が必要なもの** を洗い出す。調査必要の判定基準:

- 既存の構造・配置・命名規則を把握しないと変更影響が読めない箇所 → 調査必要
- 機能設計書に「<既存画面X>に追加」と書かれているが、その既存画面の構造が不明 → 調査必要
- 全く新規で既存の影響を受けない部分 → 調査不要

調査対象は **論点ごとに分割する**。1つのサブエージェント呼び出しは1つの焦点を持つようにする (例: 「商品カードコンポーネントの構造」と「グローバルナビゲーションの構造」は別の調査として依頼する)。

### Phase 3: コードベース調査 (サブエージェント並列依頼)

Phase 2 で特定した調査対象について、`impact-investigator` サブエージェントを並列に呼び出す。

調査依頼の作り方:

- 1依頼につき1焦点。複数の調査を1依頼に詰め込まない (フォーカスを失う)
- 依頼文には次の3点を明示する:
  - **調査対象**: 何を調べてほしいか
  - **背景**: なぜそれを調べる必要があるか (この機能設計を踏まえてどう活かしたいか)
  - **重点観点**: 何を見てほしいか (関連箇所/既存パターン/依存関係 など)
- 機能設計書のうち、その調査に関係する抜粋を1〜2段落程度同梱する (サブエージェントは機能設計書全文を読まされる必要はない)

同時に複数のサブエージェントを起動できるツール環境であれば、独立した調査は並列に投げる。並列実行が難しい環境では順に投げてもよいが、調査同士が独立であることを意識し、ある調査の結果を待ってから次を決めるような直列依存は作らない。

サブエージェントから返ってきた結果は、本スキル本体ではそのまま読み込んだ上で、後続の Phase 4 以降で要約して本文に取り込む。**生の返答をそのまま貼ることはしない** (調査結果は本スキルの判断材料であり、影響分析書の読み手には整理済みのインデックスだけを見せる)。

### Phase 4: 設計トピックの識別と境界決定

機能設計書本文 + サブエージェント調査結果から、詳細設計フェーズで「設計対象」として扱うべきトピックを洗い出す。

進め方:

1. 機能設計書の各機能(F)について、設計判断が必要な側面を列挙する
   - 例: お気に入り機能 → データの持ち方、登録/解除のサーバー処理、UI実装、画面遷移、認証連携、エラーハンドリング
2. 列挙したものを「独立して1パスで設計できる粒度」(原則3) に揃える
   - 細かすぎるものは隣接トピックに統合する
   - 大きすぎるものは内側の判断点で分割する
3. 機能設計書の `5. 横断的な機能設計上の決定` で示された方針も、独自のトピックとして立ち上がる場合がある (例: 「フィードバック様式の統一」が複数機能に横断する設計トピックになる)

各トピックには次を記録する:

- **トピック名** (簡潔に。"<対象>の<側面>"のような命名が読みやすい)
- **概要**: そのトピックで決める対象を1〜2行
- **関連する要求(R)**: 機能設計書のどの要求と紐づくか (複数の場合もある)
- **関連箇所**: そのトピックの設計判断が影響を与える/影響を受ける既存コード箇所 (調査結果から)
- **設計時に決める必要があること**: 詳細設計フェーズで答えを出すべき問い (粗くてよい)

### Phase 5: 設計バッチへのグルーピングと順序付け

Phase 4 で識別した設計トピックを、設計バッチに集約する。

バッチ化の進め方:

1. トピック間の **結合の強さ** を見立てる (原則4)
   - 「片方の設計が変わると、もう片方の設計も変わる」 → 強結合 → 同じバッチ
   - 「片方の設計を後で見ても、もう片方を変える必要が小さい」 → 弱結合 → 別バッチ
2. 強結合トピックを集めてバッチを構成する
3. 各バッチに名前と「このバッチで一緒に決めること」の説明を付ける
4. **バッチが1つにしかならない場合は無理に分割しない**。その旨を明記する

順序付けの進め方:

1. バッチ間の依存関係を整理する (原則5)
2. 推奨設計順序を、矢印やリストで提示する
3. 並列に進められるバッチがあれば、その旨を明示する
4. 順序の根拠を1〜2行で添える (なぜ A バッチを先にすべきか)

### Phase 6: ドラフト出力と論点深掘り対話

成果物を後述の `成果物のフォーマット` に従って書き出し、ファイル保存する。

書き出し後、論点が大きい箇所だけピックアップしてユーザーと対話する。ピックアップ基準:

- 設計トピックの境界が悩ましかった箇所 (どこで切るかでバッチ構成が変わるもの)
- バッチ間依存の判定が微妙だった箇所
- 設計順序が複数案あり、根拠が決定的でなかった箇所
- 調査結果から「機能設計書の前提と現状コードに齟齬がある」と判明した箇所

ピックアップする件数は **最大3件目安**。ピックアップ対象が無ければ、無理に対話を起こさず、最終確認だけ求める。

対話の進め方:

- 対象論点について、複数案と選定理由を簡潔に提示する
- `AskUserQuestion` で確認する
- ユーザーの判断を受けて影響分析書を更新する

ユーザー確認の後、最終版として保存する。

## 成果物のフォーマット

影響分析書は次のセクションで構成する。**セクション順序とフィールド名は維持する**(後続の implementation-design がこの構造を前提に動く)。

```markdown
# 影響分析書: <機能名>

## 1. 概要

- **対象機能設計書**: <機能設計書のパス>
- **対象要求**: <扱う要求IDのリスト (例: R1, R2, R3)>
- **対象外**: <機能設計書にあるが本影響分析では扱わない要求があればその旨と理由>
- **調査範囲**: <impact-investigator による調査を実施した範囲の要旨>

## 2. 変更点と影響範囲

要求(R)ごとに、必要な変更点とそれが当たる既存コード上の箇所を整理する。

### 2.1 R<n> <要求の名前>

**追加されるもの**:
- <論理的な対象X>: <何が追加されるか>
- ...

**変更されるもの**:
- <既存対象Y>: <どんな変更が必要か>
- ...

**連動して影響を受ける箇所**:
- <影響対象Z>: <どう影響を受けるか>

**コードベース上の関連箇所**:

| パス | 役割 | 関連度 (主/関連) |
|------|------|-----------------|
| ... | ... | 主 |

(要求の数だけ繰り返す)

## 3. 設計トピック

詳細設計フェーズで設計対象となるトピックを列挙する。各トピックは「独立して1パスで設計できる粒度」を目安にする。トピック数は **多くても 5〜7 個程度** に収まることが多い。小規模な機能なら 1〜2 個でよい。8 個を超えるときは隣接トピックの統合余地を見直す。

### 3.1 T<n> <トピック名>

- **概要**: <このトピックで決める対象を1〜2行>
- **関連する要求**: <R1, R2 のように紐づく要求>
- **関連する既存箇所**: <影響を与える/受ける既存コード箇所>
- **設計時に決めるべきこと**:
  - <問い1>
  - <問い2>

(トピックの数だけ繰り返す)

## 4. 設計バッチと設計順序

### 4.1 設計バッチ

設計トピックを「一度の設計セッションで一緒に検討するまとまり」に集約する。

#### B<n> <バッチ名>

- **含まれるトピック**: T1, T3 (機能設計書のIDではなく、上記 3 のトピックID)
- **このバッチで一緒に決めること**: <なぜ一緒に決めるべきかを1〜2行>
```

## やりがちな失敗とその回避

### 失敗1: 詳細な How に踏み込む

症状: 「設計トピック」の中身に、テーブルスキーマ・API契約・関数名が書かれている。

回避の問い: その記述を読んだ implementation-design に、まだ設計の余地が残っているか? 残っていないなら踏み込みすぎ。トピックには **「何を決める必要があるか」(問い)** だけ残し、**「答え」**は残さない。

### 失敗2: サブエージェントを使わず本体で grep を繰り返す

症状: 本体スキルが直接 Grep/Read で大量にコードを読んでいて、調査中に出てきた断片に流されて設計判断を始めてしまう。

回避の問い: この調査は本当に本体スキルが直接やる必要があるか? サブエージェントに焦点を絞った依頼として投げれば、結果だけ受け取って判断できるのではないか?

### 失敗3: 設計トピックを過剰に細かく分解する

症状: 設計トピックが10個以上並んでおり、1つ1つが関数1つ分しかない。

回避の問い: そのトピックを単独で詳細設計したとき、本当に独立した設計判断として意味があるか? 隣のトピックと一緒に決めた方が早い・自然なら統合する。**目安: 設計トピックは多くても5〜7個程度に収まることが多い**。

### 失敗4: 設計バッチが結局1つで意味をなさない / 逆に細かく分割しすぎる

症状: 全トピックが1つのバッチに入っていてバッチの存在意義がない、または各トピック単独バッチで分割の意味がない。

回避の問い: バッチ化の判定基準(原則4)で見たとき、本当に同じ/別バッチが妥当か? 機能が小さいなら1バッチで明示するのが正解。逆に意味のあるグルーピングがあるなら、無理に統合しない。

### 失敗5: 設計順序の根拠が不明

症状: 「B1 → B2 → B3」とだけ書かれていて、なぜその順序なのかが書かれていない。

回避の問い: implementation-design がこの順序を読んだとき、順序を入れ替えていいかの判断ができるか? 根拠が無いと判断できないので、1〜2行でよいから理由を添える。

### 失敗6: 機能設計書の内容を再集約する

症状: 影響分析書に、機能設計書の操作フロー・画面要素・選定理由・採用案の利点が再記述されている。読み手は機能設計書も持っているのに、同じ説明が二箇所に並ぶ。

**悪い例**:

> ハートアイコンを商品カードに追加する。ユーザーがハートを押すと「お気に入りに追加しました」のトーストが出て、再度押すと解除される(機能設計書 F1 の選定案より)。エラー時は「お気に入りの更新に失敗しました」と表示し再試行できるようにする。

**良い例**:

> 商品カードに「お気に入りトグル UI」が追加される。挙動詳細は機能設計書 F1 に従う。本影響分析では、既存の商品カードコンポーネントと既存トースト基盤の有無に関する論点を T3 として扱う。

判定の助け: その記述から **影響範囲・設計対象に関係ない情報** (UIの見え方の説明・選定理由・採用案の利点・操作フローの詳細) を削ったとき、影響分析として読めるか? 読めなくなれば再掲、読めればOK。

回避のコツ: 機能設計書を引くときは「機能設計書 X による決定を前提に〜」「機能設計書 X で示された<論点名>は T<n> で扱う」のような **参照** の形に留め、本文中で挙動・選定理由を語り直さない。

### 失敗7: コードベース調査の結果を本文に生のまま貼り付ける

症状: サブエージェントの調査結果(テーブル形式・コード片を含む)が本文にそのまま貼られて、影響分析書の本来の構造が埋もれる。

回避の問い: サブエージェントの返答は「本体スキルが判断するための材料」。読み手にとって必要な情報は何か? 関連箇所のテーブルや既存パターンの要点だけを **2. 変更点と影響範囲** に組み込み、それ以外は本体スキルの判断材料として消費するだけでよい。

## 出力後にユーザーに確認すること

影響分析書を生成したら、次の点をユーザーに確認する(全部を一度に聞くのではなく、論点が大きい点に絞る):

- 設計トピックの分解粒度が妥当か (細かすぎる/大きすぎるものはないか)
- 設計バッチへのグルーピングが「一緒に決めるべきもの」を捉えているか
- 設計順序の推奨が妥当か (順序入れ替えの余地が必要な部分はないか)
- 機能設計書の前提と現状コードの齟齬が報告されている場合、その扱い方は妥当か
- 出力先パス `docs/plans/<機能名>/impact-analysis.md` で問題ないか
