# impact-analysis

機能設計書を入力に、後続の実装設計フェーズが「どこに・何を・どの順で設計するか」を判断できる状態に整理する影響分析スキル。

## このスキルが置かれている設計フロー

```
[1] 要求仕様書 (request-spec)
       ↓
[2] 機能設計書 (feature-options)
       ↓
[3] 影響分析書 (このスキル: impact-analysis)
       ↓
[4] 実装設計書 (implementation-design)
       ↓
[5] 実装 (phase-implementation)
```

このスキルが解く問題は **「実装設計に入る前に、何をどの順で設計すべきかを地ならしする」** こと。答えるべきは — **What/Where**(何が変わるか、どこの既存コードに当たるか)、**What-to-design**(詳細設計フェーズで設計対象になるトピックは何か)、**In-what-order**(それらを設計する推奨順序)。

後続フェーズの存在が「やらないこと」を強く規定する:

- **[4] 実装設計** が技術選定・データ構造・API契約・アーキテクチャ・フェーズ分割を行う → 詳細な **How** は決めない(「テーブルが必要」までは書くが「テーブルスキーマ」は書かない)
- **[2] 機能設計** がユーザー視点の振る舞いを確定している → 振る舞いを再決定しない

## 入力の前提

- **主入力**: feature-options が生成した機能設計書(`docs/plans/<機能名>/feature-options.md`)。`4. 機能設計` が欠けていれば、まず feature-options を実施するよう案内する。
- **補助参照**: 必要に応じて要求仕様書を参照してよいが、機能設計書に書かれている情報を**再集約しない**(成果物が肥大化する。原則6)。
- **対象コードベース**: 影響分析対象のリポジトリ。ローカルで調査可能であることを前提にする。ローカルに無い場合は調査を論理対象レベルに留め、その旨を `1. 概要` の調査範囲に明記する。

## 中核となる原則

進め方・フォーマット・自己点検はすべてこの6原則の適用。判断に迷ったらここへ戻る。

### 原則1: How には踏み込まず、What/Where/設計順序の整理に徹する

書いてよい — 「商品カードにハートアイコンを追加する必要がある」(What)、「`src/components/ProductCard.tsx` を変更する必要がある」(Where)、「お気に入りデータの永続化方式を決める設計トピックがある」(What-to-design)。
書いてはいけない — 「`Favorite` テーブルを `user_id, product_id` で作る」(テーブルスキーマ)、「`POST /api/favorites` で登録する」(API契約)、「`useFavorite` フックを作る」(実装構造)。

その場で効く判定: 書こうとする記述を読んだ implementation-design に、**設計の余地が残っているか**。残っていれば事実/論点の整理、決めきっていたら How への踏み込み。設計トピックには**「何を決める必要があるか」(問い)**だけ残し、**「答え」**は残さない。

例外: 機能設計書または要求仕様書に**制約条件**として明示されている技術選定(「Microsoft Entra ID を使う」等)は、影響分析の前提として参照してよい。独自に技術選定を新規追加してはいけない。

### 原則2: コードベース調査はサブエージェントに委譲し、本文は事実の整理に集中する

本体プロセスで grep/Read を繰り返してコードを直接読み回らない。**impact-investigator** サブエージェントに焦点を絞って調査を依頼し、構造化された返答だけを受け取って本文に反映する。理由: (1) 調査中に見つかる無関係なコード片で本体のコンテキストが圧迫されるのを避ける、(2)「調査しながら設計してしまう」早すぎる設計判断を排除する、(3) 独立した調査を並列に投げて速度を稼ぐ。

サブエージェントの**生の返答を本文にそのまま貼らない**。返答は本体スキルが判断するための材料であり、読み手に見せるのは整理済みの関連箇所(`2. 変更点と影響範囲` のテーブル等)だけ。

次の場合はサブエージェント不要: 機能設計書だけで変更箇所と影響範囲が読み取れる小規模機能、ユーザーが「調査省略でよい」と明示した場合、参照ファイル名が既に十分具体的で追加調査の価値が乏しい場合。

### 原則3: 設計トピックは「独立して1パスで設計できる粒度」で切る

設計トピック = 詳細設計フェーズで1単位として設計できる対象。粒度の目安 — ✗大きすぎ「お気に入り機能全体」(機能丸ごとは分解の意味がない) / ✗小さすぎ「解除ボタンの押下処理」(関数1個レベル) / ◯ちょうど良い「お気に入りデータの永続化方式」「トグルUIの実装方式」「ナビ動線への追加方式」。

判定: そのトピックを単独で詳細設計したとき、**他のトピックの設計を待たずに案を出せるか**。出せれば独立、必ず他を見ないと進まないなら統合する。**小規模な機能ではトピックが1〜2個でよい** — 分解の目的は「全部を一度に考えると浅くなる」回避なので、無理に分割しない(目安: 多くても5〜7個。8個を超えるなら統合余地を見直す)。

### 原則4: 設計バッチは「同時に決めた方が筋が通るもの」をまとめる

設計バッチ = 設計トピックを「一度の設計セッションで一緒に検討するまとまり」に集約したもの。基準 — 片方の設計が変わるとほぼ確実にもう片方も変わる関係(API契約とそのリクエスト処理フロー等)は同じバッチ、片方を後から見てももう片方を変える必要が小さい関係(ロギング設計と画面UI等)は別バッチ。

機能が大きいと全トピックを一度に設計するのは、個々が浅くなる・実装設計書が膨大になり全容把握も部分参照も難しくなる、という問題を生む。バッチ単位に分けて、詳細設計フェーズが各バッチを「一度のまとまった設計の場」として扱えるようにする。**小規模で全トピックを1バッチで扱えるなら1バッチで止め、その旨を明記する**(順序の議論が不要になる)。

### 原則5: 設計順序は「先に決まっている方が後段が楽になる方向」で並べる

バッチ間に依存があれば推奨設計順序を提示する。基準 — 基盤→個別(データモデル・共通IF・共通ライブラリ → それらを使う個別機能)、契約→利用者(API契約 → それを使うフロント)、影響を与える方→受ける方(後で変えた時の波及が大きい方を先に固める)。並列に進められるバッチも明示する(順序が必ず直列とは限らない)。順序は**推奨**であり絶対ではない — 実装設計フェーズで合理的事情があれば入れ替える余地を残し、根拠を1〜2行添える。

### 原則6: 機能設計書を起点に拾い、内容は再集約しない

機能設計書の `6. 後続フェーズへの引き継ぎ` に impact-analysis 向け論点が明示されている。これを起点に変更点・調査必要箇所・設計トピックの初期候補を立てる。ただし引き継ぎだけで完結させず、`4. 機能設計` 本文も読み、明記されていなくても影響しそうな箇所を拾う。

一方で、機能設計書の操作フロー・画面要素・選定理由を**本文に語り直さない**(読み手は機能設計書も持っている。二重記述は更新漏れと肥大化を招く)。引くときは「機能設計書 F1 による決定を前提に〜」「機能設計書で示された<論点>は T3 で扱う」のような**参照**に留める。判定: その記述から影響範囲・設計対象に関係ない情報(UIの見え方・選定理由・操作フロー詳細)を削って、影響分析として読めるか。読めれば OK。

## 進め方

「機能設計書から変更点を読み取る → 調査をサブエージェントに並列依頼 → 設計トピック識別 → バッチ化と順序付け → ドラフト出力 → 論点深掘り対話」で進める。

### Phase 1: 入力の受領と俯瞰

1. 入力(機能設計書のパス)を受け取る。指定が無ければ確認する。
2. 機能設計書を読み、`1. 概要`(対象範囲・要求カバレッジ・1:1でない箇所・制約条件)、`4. 機能設計` の各機能(F)の選定案と `関連要求`、`5. 横断的な決定`、`6. 引き継ぎ`(と「前提機能の欠落」)を把握する。
3. 出力先を決定する: 機能設計書と同じディレクトリの `impact-analysis.md`。既存ファイルがあれば上書き可否を確認する。

### Phase 2: 変更点の抽出・カバレッジ検算・調査対象の特定

機能設計書の本文から、コードベース上で変更が必要になる箇所を機能(F)単位で抽出する(各機能の `関連要求` でどの要求に紐づくか辿れる):

- **追加されるもの**: 新規画面/UI要素/データ/導線/動作
- **変更されるもの**: 既存画面/コンポーネント/動線で、要素追加・配置変更・状態追加が要るもの
- **波及確認が要るもの**: 直接の追加/変更先ではないが、波及で確認が必要な箇所(ナビ全体の整合、既存通知パターンとの整合 等)

この段階では具体的なファイルを特定する必要はない。「商品カードコンポーネント」「マイページ」のような**論理的な対象**で書き出す(具体パスは調査結果で埋まる)。

**カバレッジ検算(コード接地での欠落検出)**: 機能設計書が触れる各エンティティについて、コード上に**作成/管理側と参照/利用側の両方の変更先が立つか**を見る。片側しか立たないエンティティは、機能設計書の前提と現状コードの齟齬の候補 → `5. 後続フェーズへの引き継ぎ` の「機能設計書の前提と現状コードの齟齬」に流す。これは feature-options の前提機能洗い出し(ユーザー目線)が取りこぼした欠落を、コード接地という別レイヤーで拾う二重化であって、機能の振る舞いを再決定するものではない。

次に、上記のうち**コードベース調査が必要なもの**を洗い出す(既存の構造・配置・命名を把握しないと変更影響が読めない箇所は調査必要、全く新規で既存の影響を受けない部分は不要)。調査対象は**論点ごとに分割**する(1つのサブエージェント呼び出しは1焦点)。

### Phase 3: コードベース調査(サブエージェント並列依頼)

Phase 2 で特定した調査対象について `impact-investigator` を並列に呼び出す。依頼は1依頼1焦点で、**調査対象**(何を調べるか)・**背景**(なぜ/この機能設計でどう活かすか)・**重点観点**(関連箇所/既存パターン/依存関係)の3点を明示し、関係する機能設計書の抜粋を1〜2段落同梱する(全文は読ませない)。独立した調査は並列に投げ、ある調査の結果を待ってから次を決める直列依存は作らない。返ってきた結果は本体で読み込み、Phase 4 以降で要約して本文に取り込む(原則2: 生のまま貼らない)。

### Phase 4: 設計トピックの識別と境界決定

機能設計書本文＋調査結果から、詳細設計フェーズで設計対象となるトピックを洗い出す:

1. 各機能(F)について設計判断が必要な側面を列挙する(例: データの持ち方、登録/解除のサーバー処理、UI実装、画面遷移、認証連携)。
2. 「独立して1パスで設計できる粒度」(原則3)に揃える(細かすぎは統合、大きすぎは内側の判断点で分割)。
3. `5. 横断的な決定` の方針が独自トピックとして立つこともある(例:「フィードバック様式の統一」)。

各トピックに記録する: トピック名("<対象>の<側面>"形式)、概要(1〜2行)、関連する機能/要求、関連箇所(調査結果から)、設計時に決めるべきこと(**問いの形**で。答えは書かない)。

### Phase 5: 設計バッチへのグルーピングと順序付け

1. トピック間の結合の強さを見立てる(原則4)。強結合を集めてバッチを構成し、各バッチに名前と「一緒に決めること」を付ける。1バッチで十分なら無理に分割せず明記する。
2. バッチ間の依存を整理し(原則5)、推奨設計順序を矢印/リストで提示する。並列に進められるバッチを明示し、順序の根拠を1〜2行添える。

### Phase 6: ドラフト出力と論点深掘り対話

成果物を `成果物のフォーマット` に従って書き出し保存する。書き出し後、論点が大きい箇所だけピックアップして対話する(**最大3件目安**。対象が無ければ無理に対話せず最終確認だけ求める)。ピックアップ基準: トピック境界が悩ましかった箇所、バッチ間依存の判定が微妙だった箇所、設計順序が複数案で根拠が決定的でなかった箇所、調査で「機能設計書の前提と現状コードに齟齬」が判明した箇所。対象論点について複数案と選定理由を簡潔に提示し `AskUserQuestion` で確認、判断を受けて更新し最終版を保存する。

## 成果物のフォーマット

影響分析書は次のセクションで構成する。**セクション順序とフィールド名は維持する**(後続の implementation-design がこの構造を機械的に走査して前提にする。特に設計バッチ B<n> は implementation-design が「1実行=1バッチ」で参照する単位)。

```markdown
# 影響分析書: <機能名>

## 1. 概要
- **対象機能設計書**: <パス>
- **対象要求**: <扱う要求IDのリスト>
- **制約条件(上流から)**: <機能設計書/要求仕様書で制約として与えられた技術指定・既存基盤指定。どの要求(R)由来かを併記。なければ「該当なし」>
- **対象外**: <機能設計書にあるが本影響分析で扱わない要求。その旨・理由に加え差し戻し先を書く。なければ「該当なし」>
- **調査範囲**: <impact-investigator による調査範囲の要旨。未実施なら「コードベース調査は省略(理由)」>

## 2. 変更点と影響範囲
機能設計書の機能(F)ごとに、変更点と既存コード上の関連箇所を整理する(前提機能も対等に並べる)。

### 2.1 F<n> <機能名>
- **関連要求**: <R1, R2 (機能設計書 §4 の関連要求を転記)>
**追加されるもの**: - <論理的な対象X>: <何が追加されるか>
**変更されるもの**: - <既存対象Y>: <どんな変更が必要か>
**波及確認が要る箇所**: - <影響対象Z>: <どう影響を受けるか>
**コードベース上の関連箇所**:
| パス | 役割 | 関連度 (主/関連) |
|------|------|-----------------|
| ... | ... | 主 |
(機能の数だけ繰り返す)

## 3. 設計トピック
詳細設計フェーズで設計対象となるトピック。「独立して1パスで設計できる粒度」を目安に(多くても5〜7個。小規模なら1〜2個)。

### 3.1 T<n> <トピック名>
- **概要**: <決める対象を1〜2行>
- **関連する機能/要求**: <F1 (R1, R2) のように、機能とその関連要求を併記>
- **関連する既存箇所**: <影響を与える/受ける既存コード箇所>
- **設計時に決めるべきこと**(答えでなく**問いの形**で):
  - <問い1?>
  - <問い2?>
(トピックの数だけ繰り返す)

## 4. 設計バッチと設計順序
### 4.1 設計バッチ
#### B<n> <バッチ名>
- **含まれるトピック**: T1, T3 (上記3のトピックID)
- **このバッチで一緒に決めること**: <なぜ一緒に決めるべきか1〜2行>
(バッチが1つなら「設計バッチは1つに集約した」と理由を記す)

### 4.2 設計順序
(バッチが1つなら「設計バッチが1つのため順序の議論は不要」とだけ書く)
```
B1
  ├─→ B2 ─→ B3
  └─→ B4 (B2 と並列で進めてよい)
```
- **推奨設計順序**: B1 → B2 → B3
- **各バッチを先にする理由**: <1〜2行>
- **並列に進められるバッチ** / **設計順序が確定しない論点**: <あれば>

## 5. 後続フェーズへの引き継ぎ
- **設計バッチ単位での実装設計を推奨**: 上記4.1のバッチ単位で実装設計書を分割/章分けすることを推奨
- **<バッチX固有の引き継ぎ>**: <論点や注意点>
- **機能設計書の前提と現状コードの齟齬** (該当する場合): <Phase 2 のカバレッジ検算で見つかった片側欠落を含む不整合と扱い方>
- **未確定論点** (該当する場合): <確定しきれなかった点>
```

**全セクションを必ず置く**。該当内容がなければ見出し直下に「該当なし」と明記する(後続スキルはこの構造を前提に動くため、「セクションが無い」と「あって該当なし」は意味が違う)。必須なのは見出しレベルのセクションであり、「あれば」「省略可」「該当する場合」と明記された下位項目・サブセクションは省略してよい。

## 引き渡し前の自己点検

出力前に各原則を守れたかを点検する(詳細は対応する原則/Phaseへ):

- **How への踏み込み** — 設計トピックの中身がテーブルスキーマ・API契約・関数名になっていないか。読んだ implementation-design に設計の余地が残るか(原則1)
- **本体での grep 乱用** — コード調査を impact-investigator に委譲したか。調査中の断片に流されて設計判断を始めていないか(原則2)
- **生の調査結果の貼り付け** — 調査結果を整理せず本文に貼っていないか。読み手には整理済みの関連箇所だけを見せたか(原則2)
- **トピックの過剰分解** — 関数1個レベルに刻んでいないか。単独で設計判断として意味がある粒度か(原則3。多くても5〜7個)
- **バッチの形骸化** — 全トピック1バッチで存在意義がない/各トピック単独バッチで分割が無意味、になっていないか(原則4)
- **設計順序の根拠欠落** — implementation-design が順序を入れ替えてよいか判断できるよう、各順序に理由を添えたか(原則5)
- **機能設計書の再集約** — 操作フロー・画面要素・選定理由を語り直していないか。参照に留めたか(原則6)
- **カバレッジ検算** — 各エンティティの作成/参照両側にコード上の変更先が立つか検算し、片側欠落を齟齬として `5.` に流したか(Phase 2)

## 出力後にユーザーに確認すること

生成したら**論点が大きい点に絞って**確認する(全部を一度に聞かない):

- 設計トピックの分解粒度が妥当か(細かすぎる/大きすぎるものはないか)
- 設計バッチへのグルーピングが「一緒に決めるべきもの」を捉えているか
- 設計順序の推奨が妥当か(入れ替えの余地が必要な部分はないか)
- 機能設計書の前提と現状コードの齟齬が報告されている場合、その扱い方は妥当か
- 出力先パスで問題ないか
