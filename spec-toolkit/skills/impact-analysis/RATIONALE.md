# impact-analysis 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か」。実行時は非読込。更新時に改訂。SKILL.md は再掲せず参照に留める。

## 目的と背景

機能設計書を入力に、後続の実装設計が「どこに・何を・どの順で設計するか」を判断できる状態に地ならしする（パイプライン3段目）。What/Where/設計対象トピック/設計順序までを整理し、詳細な How（テーブルスキーマ・API契約・関数シグネチャ）は決めない。

## 中核的な設計判断

### コードベース調査は impact-investigator に委譲し、生の結果を貼らない
- **決定**: 本体は grep/Read を回さず、`impact-investigator` サブエージェントに焦点を絞って委譲し、構造化された返答だけを受け取って整理する。生の調査結果は本文に貼らない。
- **防いでいる失敗**: 調査中の無関係なコード片で本体コンテキストが圧迫される / 「調査しながら設計してしまう」早すぎる設計判断。
- **出所**: 元設計。委譲先の入出力契約は `agents/impact-investigator.md` 側に作り込み済み（生を貼らない/不確実は不確実/設計判断しない）。2026-05 の codebase 検証で実起動を確認（4焦点並列、実パス＋既存パターン＋不明点明記、設計判断なし）。

### カバレッジ検算（作成側/参照側の両変更先）【B2・2026-05追加】
- **決定**: Phase2 で機能設計書の各エンティティについて「コード上に作成/管理側と参照/利用側の両方の変更先が立つか」を検算し、片側欠落を `5. 齟齬` に流す。
- **位置づけ**: feature-options の前提機能洗い出し（ユーザー目線）が取りこぼした欠落を、**コード接地という別レイヤーで拾う二重化**。機能の振る舞いを再決定するものではない（責務競合にならない）。
- **出所**: 2026-05 境界チェックで「前提機能の検出が単一障害点（下流に二重化なし）」と判明。codebase 検証では favorites のお気に入りエンティティは両側に変更先が立つ（ギャップなし）と確認しつつ、調査で判明した実コードの足場不備（server エントリ欠落等）を齟齬として拾えた。

### 設計トピックの独立粒度 / 設計バッチ / 設計順序
- **決定**: トピックは「独立して1パスで設計できる粒度」（目安5-7、過剰分解しない）、バッチは「同時に決めた方が筋が通るもの」（1なら明示）、順序は推奨であり根拠を添える。
- **防いでいる失敗**: 全トピックを一度に設計すると個々が浅くなる/成果物が肥大化する。

### 機能設計書を再集約しない
- **防いでいる失敗**: 操作フロー・画面要素・選定理由を本文に語り直すと、読み手は機能設計書も持っているため二重記述になり更新漏れ・肥大化を招く。参照に留める。

### 固定スキーマ
- **維持**: 下流 implementation-design が「1スキル実行=1設計バッチ」としてバッチ構造に構文依存する。2026-05 再設計の柔軟化提案は退行と判断し維持。

### 調査範囲にインフラ層を含める条件【2026-07追加】
- **決定**: 対象機能がファイルアップロード・配信・非同期処理・スケジュール実行を含む場合、インフラ定義（Terraform 等の IaC・イベントトリガ・CDN・ストレージルール）を Phase 2 の調査対象洗い出しに含める。
- **防いでいる失敗**: 実運用（バックエンド機能の影響分析）で並列調査6件がすべてアプリケーションコードに閉じ、インフラ変更の要否が設計フェーズの brownfield 批評で初めて判明。影響分析書には最後までインフラの関連箇所が載らなかった。
- **出所**: 2026-07-15 実運用フィードバック提案7。

### 変更点整理は機能(F)単位【2026-07追加】
- **決定**: `2. 変更点と影響範囲` と設計トピックの紐づけを、要求(R)単位でなく機能設計書の機能(F)単位で組織し、関連要求を併記する。
- **防いでいる失敗**: feature-options が F 単位で捕捉した前提機能——特定の R に1:1で紐づかない——が、R 単位への再マッピングで行き場を失い追跡が切れる。上流の機能単位組織【load-bearing】の効果が影響分析の段で減衰する。
- **出所**: 2026-07 のプラグインレビューでの指摘。Phase 2 本文は既に F 単位で抽出と書かれており、成果物フォーマットだけが R 単位に残っていた不整合の解消。

### 成果物にプロセス痕跡を残さない【2026-07追加】
- **決定**: 対話を受けた更新では確定した内容だけを書き、検討経緯(「当初は〜だったが」)やスキル内部のプロセス名を本文に残さない。
- **防いでいる失敗**: 実運用で設計順序の説明に「当初はB3をB1と並列開始できる想定だったが、T6をB3に統合したことで依存が変わった」という編集履歴が残った。最終読者に必要なのは確定した依存関係と理由だけで、変遷の記述は誤読と肥大化を招く。implementation-design の原則3と同じ思想。
- **出所**: 2026-07-17 実運用成果物の横断レビュー。

### 3.x「関連する既存箇所」は 2.x の表を正とする（パス再掲の禁止）【2026-07追加】
- **決定**: 設計トピックの「関連する既存箇所」は、対応する F の「コードベース上の関連箇所」表への参照を基本とし、トピック固有の追加箇所だけを列挙する。
- **防いでいる失敗**: 実運用成果物で、2.x の表に役割付きで載せた同じパス群を 3.x がカンマ区切りで再掲していた（最多で7パス）。同じパスの二重管理は改訂時に片方だけ直る温床で、機能設計書の再集約禁止（原則6）と同じ「1情報1箇所」の文書内版。
- **出所**: 2026-07-19 実運用成果物の横断レビュー。

### 設計順序は矢印図に一元化＋単一トピックバッチのフィールド両対応【2026-07追加】
- **決定**: 4.2 の「推奨設計順序」「並列に進められるバッチ」フィールドを削除し、順序・並列関係の表現を矢印図に一元化（「各バッチを先にする理由」「設計順序が確定しない論点」は別情報なので維持）。4.1 の「このバッチで一緒に決めること」は複数トピック=なぜ一緒か / 単一トピック=なぜ独立させるか、の両対応に意味を定義。
- **防いでいる失敗**: 実運用成果物で同じ順序情報が「矢印図」「推奨設計順序リスト」「並列に進められるバッチ」の3形式で重複した（更新時の食い違いリスク＋肥大化）。また単一トピックバッチでは「一緒に決めること」が意味をなさず、書き手が「独立させる理由」に自発的に読み替えていた（その運用の公式化）。
- **考慮した影響**: implementation-design は 4.1 のバッチ構造にのみ構文依存しており、4.2 のフィールド削除は安全（確認済み）。
- **出所**: 2026-07-19 実運用成果物の横断レビュー。

### 記法規律（構造を潰した圧縮の禁止）【2026-07追加】
- **決定**: implementation-design で導入した記法規律（1項目1主張・段落内(1)(2)列挙の禁止・括弧内文の禁止・同格対象の見出し区切り）をテンプレート冒頭コメントと自己点検に展開。
- **防いでいる失敗**: 実運用成果物で、設計トピックの「関連する既存箇所」に7つのパスがカンマ区切りの1行で連結された。本スキルは本体が直接成果物を書くため、テンプレートが記法の唯一の注入点。
- **注**: 記法ブロックは4スキル（request-spec / feature-options / impact-analysis / quick-design）のテンプレートに同文で再掲（実行時独立性のための意図的重複。変更時は4テンプレート＋implementation-design 側を同期）。
- **出所**: 2026-07-19 実運用成果物の横断レビュー。
