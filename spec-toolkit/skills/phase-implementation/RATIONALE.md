# phase-implementation 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。
> このスキルは implementation-engineer / completion-verifier の2エージェントを協調させる。各エージェント固有の制約の理由は `../../agents/<name>.RATIONALE.md` 参照。本ファイルは**オーケストレーション全体の決定**を扱う。

## 目的と背景

spec-toolkit パイプライン(要求仕様 → 機能設計 → 影響分析 → 実装設計 → 実装)の最終段として、実装設計書の実装計画を実際のコードに変換する。ユーザーの運用は「フェーズ毎に実装 → レビュー → コミットのサイクルを回す」であり、その1サイクルの「実装」部分を本スキルが担う。implementation-design が 1実行=1バッチで繰り返されるのと相似に、本スキルは 1実行=1フェーズで繰り返される。

## 中核的な設計判断

### 【load-bearing】実装者と検証者の分離（2エージェント構成）
- **決定**: 実装は implementation-engineer、完了検証は completion-verifier に分離。本体はコードを書かないオーケストレーター。再検証も含め、実装した本人に完了判定をさせない。
- **却下した代替案**: (a) 実装エージェントにセルフチェックまで持たせる — 契約を読み違えた実装者はテストも同じ読み違いで書くため自己検出できない。(b) 本体が検証を行う — テスト出力・コード照合で本体のコンテキストが埋まり、差し戻し判断・報告統合の質が落ちる。
- **防いでいる失敗**: 実装エージェントの「できました」自己申告をそのまま完了として報告する幻覚的完了。
- **出所**: ユーザー要望(2026-07)「メインエージェントはオーケストレーターとしてサブエージェントが実作業を行うようにしたい」＋設計議論。

### 【load-bearing】ハーネスの範囲 = 完了検証まで（品質レビューに踏み込まない）
- **決定**: 検証は (a)完了条件テスト (b)リグレッション (c)設計書契約との整合、の3点で止める(SKILL.md 原則5)。
- **却下した代替案**: (a) セルフレビュー(品質観点)込み — 別プラグインのレビュー工程と観点が二重管理になり指摘の調停コストが生まれる。(b) 実装専念でチェックなし — 「実装が設計書の契約通りか」は汎用の品質・セキュリティレビューが持たない観点で、外部に委ねると空白になる。契約整合はレビューではなく設計書に書かれた完了定義の検証、と整理した。
- **出所**: ユーザーの主要な悩みとして提示され、AskUserQuestion で「完了検証＋設計書整合」を選択(2026-07-02)。

### TDD は本スキル側で規定し、エージェント定義に置く
- **決定**: 実装プロセスは TDD(Red→Green→Refactor)。規律の本文は implementation-engineer の定義に置き、SKILL.md は方針への言及に留める。
- **防いでいる失敗**: implementation-design は 2026-07 の改訂で実装プロセス非依存になった(設計書は読み手のプロセスを規定しない)。プロセスの決定をどこも持たないと実装の完了規律が場当たりになる。設計書=中立、実装スキル=TDD 規定、という分担で辻褄を合わせている。
- **出所**: ユーザーの運用(TDD で開発)＋AskUserQuestion で「TDD を規定する」を選択(2026-07-02)。

### 差し戻し上限は2回
- **決定**: completion-verifier の fail に対する修正往復は2回まで。上限到達でユーザーにエスカレーション。
- **防いでいる失敗**: 修正ループの暴走。2回の的確な指摘(期待・実際・該当箇所)で直らない問題は、契約自体の欠陥か環境問題である可能性が高く、エージェント往復では解決しない。
- **出所**: 設計議論(2026-07)。回数は経験則であり eval で見直してよい。

### 実装開始前の確認は「確認事項があるときだけ」の条件付きゲート
- **決定**: Phase 1 末尾の実装開始確認を無条件から条件付きに変更。入力の問題・フェーズ順序・作業ツリーの汚れ・設計書とコードの乖離・並列分割の意図を「確認事項」として収集し、1件以上あるときだけ全件まとめて1回で確認する。無ければ一言要約を伝えて確認なしで実装に進む。
- **却下した代替案**: (a) 無条件の実装開始確認(旧仕様) — 入力に問題がない時は設計書のフェーズ内容の転記を再確認させるだけの冗長なチェックになり、本当に判断が必要な確認が形式的な確認に紛れて識別できなくなる。(b) 確認事項ごとにその場で個別確認 — 1回の実行で複数回ブロックし、全体を見て開始可否を判断するゲートの意味が薄れる。
- **防いでいる失敗**: 形式的な確認の常態化でユーザーが確認を読み飛ばすようになり、実際に問題があるときの確認まで素通りされる。
- **出所**: ユーザーフィードバック(2026-07-23)「設計書とフェーズを明確に指定し状況にも問題がない時にまで確認があり、冗長なうえ実際に状況変化があった時と識別しづらい。本当に確認が必要な時だけにしたい」。

### 他プラグイン非参照のゼロベース設計
- **決定**: dev-toolkit の task-development(td-* エージェント群)は参照せずに設計した。完了報告でもレビュー・コミットのスキルを名指ししない(「ユーザーの運用に委ねる」と中立表現)。
- **理由**: プラグインの独立配布性。spec-toolkit 単体で完結し、他プラグインのインストールを前提にしない。
- **出所**: プラグイン間参照スコープ規約に基づく明示確認で「参照しない」を選択(2026-07-02)。

## 解釈・仮定（要確認）

- **フェーズ番号省略時の挙動**: ユーザーは「実装設計書＋どのフェーズかを指定して利用する」と述べたが省略時の挙動は未指定 → コードベースの実装状況から未実装の最初のフェーズを推定し AskUserQuestion で確認する、と解釈。⚠️「常に指定必須(省略はエラー)」の意図なら要修正
- **並列委譲は例外扱い**: 「サブエージェントが実作業」の要望に並列度の指定はなかった → 既定は1フェーズ=1委譲とし、実装範囲が明確に独立する場合のみ並列可、と保守的に解釈。⚠️積極的な並列化を期待しているなら分割基準の緩和が必要
- **作業ツリーの dirty チェック**: 明示要望ではないが、フェーズ毎コミット運用では差分の分離に価値があると判断して Phase 1 に入れた(2026-07-23 以降は確認事項の1観点)。⚠️過剰なら削る
- **確認なし時も一言要約は伝える**: 「本当に必要な時だけ確認」の要望から、確認(ブロック)は無くすが何の実装を開始したかの1〜2行の要約は伝える(完全サイレント開始はしない)と解釈。⚠️要約も不要なら削る
- **乖離チェックは軽量**: 設計書とコードの乖離検出は、契約抽出で読む範囲＋実装範囲の現状確認で判る程度に留め、専用の事前監査は新設しないと解釈(コストが常時発生する割に、深い乖離は実装・検証エージェントが契約照合で検出できる)。⚠️より厳密な事前検出を期待するなら要強化
- **並列分割は確認事項に含める**: タスク分割は設計書に書かれていない本スキル側の判断であり、旧仕様でも開始確認時に提示していたため、既定(1フェーズ=1委譲)から外れる場合は確認事項として扱うと解釈。⚠️分割も黙って進めてよいなら外す
- **コミットは行わない**: 「フェーズ毎に実装→レビュー→コミット」の運用から、レビュー以降はユーザーの領分と解釈し、スキルは完了報告で終わる。
