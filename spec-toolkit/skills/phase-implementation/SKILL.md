# phase-implementation

実装設計書(implementation-design の成果物)の **実装計画のフェーズ単位** で、実装を完了させるスキル。

## このスキルが置かれている設計フロー

```
[1] 要求仕様書 → [2] 機能設計書 → [3] 影響分析書 → [4] 実装設計書 → [5] 実装(このスキル)
```

前段(implementation-design)が「契約レベルの詳細設計」と「動くもの単位のフェーズ分割」を確定済みなので、本スキルは **設計判断をせず、確定した契約を実装に変換する** のが役割。implementation-design が設計バッチ数だけ実行されるのと同様に、本スキルはフェーズ数だけ複数回実行する(1スキル実行 = 1フェーズ)。

## 入口ガード

実装設計書が無い、または `4. 実装計画` が欠けている場合は、**自分で実装計画を代行して埋めず**、まず implementation-design を実施するようユーザーに案内して止まる。代行すると、前段が担う設計判断・契約確定・フェーズ分割を飛ばした場当たりな実装になる。前段成果物が揃っていることが本スキルの前提。

## 入力の前提

- **主入力**: implementation-design が生成した実装設計書(`docs/plans/<機能名>/implementation-design-<バッチスラッグ>.md`)
- **補助参照**: 実装設計書 `1. 概要` に列挙された参照ドキュメント(影響分析書・機能設計書・要求仕様書)
- **対象範囲**: 実装設計書の `4. 実装計画` のうち、**1スキル実行につき1フェーズ**だけを対象とする

## 中核となる設計

### オーケストレーター + 実装/検証エージェントの分離

本体はコード・テストを一切書かず、オーケストレーションに徹する:

- **implementation-engineer (実装担当)**: 対象フェーズの契約(設計書 3.x)に従い、TDD(Red → Green → Refactor)で実装する。TDD の規律はエージェント定義に規定済み
- **completion-verifier (検証担当)**: 実装がフェーズの完了条件を満たすか(テスト実行)、設計書の契約と一致するかを検証する。編集ツールを持たない

実装者と検証者を分離するのは、**実装エージェントの「完了しました」報告が自己申告にすぎない**ため。実装した本人は自分の解釈でテストと実装の両方を書いているので、契約の読み違いを自分では検出できない。独立した検証者が設計書と実装を突き合わせることで初めて完了が確定する。

## 中核となる原則

進め方・自己点検はすべてこの5原則の適用。判断に迷ったらここへ戻る。

### 原則1: 1スキル実行 = 1フェーズ

実装計画に複数フェーズがあれば、ユーザーに対象フェーズを確定させる。複数フェーズを一括実行すると、フェーズ毎に実装→レビュー→コミットのサイクルを回す運用が成立せず、レビュー・コミットの単位が肥大化する。完了報告には「全フェーズ中の位置」を明記し、利用者が「あと何フェーズ残っているか」を見失わないようにする。

フェーズは上から順に実行する前提。先行フェーズが未実装のまま後のフェーズが指定されたら、依存する契約が未実装であるリスクを伝えて続行可否を確認する。

### 原則2: 実装設計書は契約 — 実装中に設計へ立ち戻らない

設計判断は前段で完了している。実装中に契約(3.x)の曖昧さ・矛盾・不足が見つかっても、**契約を勝手に書き換えて実装しない**。実装を続けられる程度の曖昧さなら合理的に解釈して実装し、解釈内容を完了報告で明示する。契約と矛盾して実装を進められない場合は中断してユーザーに判断を仰ぐ(設計書の修正は implementation-design の責務)。黙って契約から逸脱すると、設計書が実態と乖離し、後続フェーズと後続レビューの基準が壊れる。

### 原則3: 本体はオーケストレーターに徹する

本体がコードを書き始めると、実装のコンテキストで本体が埋まり、検証判断・差し戻し判断・完了報告に使う「設計書の理解」が薄れる。実装は implementation-engineer へ、検証は completion-verifier へ委譲し、本体は契約の抽出・依頼の組み立て・報告の統合だけを行う。

### 原則4: 完了は独立検証で確定する

実装エージェントの報告だけでフェーズ完了を宣言しない。completion-verifier がテスト実行と契約照合を独立に行い、pass して初めて完了とする。検証が fail した場合は指摘を implementation-engineer に渡して修正させる。**差し戻しは2回まで**。2回で解決しない問題は大抵、契約自体の欠陥か環境の問題であり、エージェントの往復では解決しない。状況(何が合わないか・試したこと・選択肢)を整理してユーザーに判断を仰ぐ。

### 原則5: 検証は「完了検証」まで — 品質レビューに踏み込まない

検証範囲は (a) フェーズ完了条件のテスト pass、(b) 既存テストのリグレッションなし、(c) 設計書契約との整合、の3点で止める。コード品質・設計の綺麗さ・セキュリティ・パフォーマンスのレビューは実装後の別工程(ユーザーの運用)に委ねる。ここに観点を足すと別工程のレビューと二重管理になり、どちらの指摘が正かの調停コストが生まれる。

### ユーザー確認のタイミング

ユーザーが介在するのは **Phase 1 末尾(対象フェーズと実装方針の確定)と Phase 4(完了報告)の2回だけ**。それに加え、原則2(契約との矛盾)・原則4(差し戻し上限)のエスカレーション条件に該当した場合のみ随時確認する。実装中の逐一確認は、前段で契約を確定した意味を薄れさせる。

## 進め方

### Phase 1: 入力受領と対象フェーズの確定

1. 入力(実装設計書のパス・フェーズ番号)を受け取る。パス指定が無ければ確認する。
2. 実装設計書を読む。`4. 実装計画` が無ければ入口ガードに従い止まる。骨格(2.x)と詳細設計(3.x)も読み、本体が契約を把握する(Phase 2 の依頼組み立てと Phase 3 の報告統合の判断基準になる)。
3. 対象フェーズを確定する:
   - フェーズ番号の指定があればそれを対象にする。
   - 指定が無ければ、コードベースの実装状況(既存のモジュール・テストの有無)から未実装の最初のフェーズを推定し、`AskUserQuestion` で確認する。
   - 先行フェーズが未実装のまま後のフェーズが指定された場合は原則1に従いリスクを伝える。
4. 作業ツリーを確認する(`git status`)。未コミットの変更が既にあれば、本フェーズの差分と混ざる旨を伝えて続行可否を確認する(フェーズ毎にレビュー・コミットする運用では差分の分離が価値を持つ)。
5. 対象フェーズの契約を抽出する: 目的・テスト方針・実装範囲・完了条件(4.x)と、実装範囲に関係する詳細設計(3.1〜3.4)の項目。
6. 対象フェーズ・実装範囲の要約・(分割する場合は)タスク分割をユーザーに提示し、実装開始の確認を取る。

### Phase 2: 実装 (implementation-engineer)

1. **タスク分割**: 既定は 1フェーズ = 1委譲。実装範囲が「触るモジュール・ファイルが重ならず、それぞれ独立したテストで完結する」複数の部分に明確に分かれる場合のみ、並列に委譲してよい。迷ったら分割しない(同一ファイルの競合・テスト全体の整合コストが並列の速度メリットを上回る)。
2. **委譲**: implementation-engineer に次を渡す。TDD・契約遵守・完了判定をしない等の規律はエージェント定義に規定済みのため、依頼には対象の特定情報だけを書く:
   - 実装設計書のパスと対象フェーズ番号(分割時は担当範囲も)
   - プロジェクトルートと、把握していればテスト実行コマンド
3. **報告の受領**: 変更ファイル・テスト結果・契約の解釈/逸脱の報告を受け取る。「契約と矛盾して進められない」報告があれば原則2に従いユーザーへエスカレーションする。

### Phase 3: 完了検証 (completion-verifier)

1. completion-verifier に次を渡す: 実装設計書のパス・対象フェーズ番号・実装報告(変更ファイル一覧・実装者の契約解釈)。
2. 検証は原則5の3点。verdict(pass / fail)と不合格項目(期待・実際・該当箇所)を受け取る。
3. fail の場合、実装設計書のパス・対象フェーズ番号・不合格項目(期待・実際・該当箇所)を implementation-engineer に渡して修正させ、再検証する。差し戻しは2回まで(原則4)。上限到達でユーザーにエスカレーションする。
4. 再検証も completion-verifier に委譲する。実装した本人に検証させない(原則4の分離が崩れる)。

### Phase 4: 完了報告

以下のフォーマットで報告する。レビュー・コミットの実施はユーザーの運用に委ね、本スキルからは指示しない。

```markdown
## フェーズ実装完了: <フェーズ名>

- **対象**: <実装設計書のパス> のフェーズ <n>
- **全フェーズ中の位置**: <例: フェーズ1〜4のうち本実行はフェーズ2。残りは 3, 4>
- **変更ファイル**: <一覧(新規/変更の別)>
- **テスト結果**: <実行コマンドと結果要約>
- **完了検証**: <完了条件の充足・契約整合の結果。差し戻しがあった場合はその回数と内容の要約>
- **契約に関する報告**: <実装中の契約の解釈・曖昧さ・設計書側へ反映すべき事項。なければ「該当なし」>
- **残課題**: <あれば。なければ「該当なし」>
```

「契約に関する報告」は実装設計書へのフィードバックループの出口。ここに挙がった事項をユーザーが設計書に反映するかを判断できるよう、解釈の内容と根拠を具体的に書く。

## 引き渡し前の自己点検

完了報告の前に各原則を守れたかを点検する(詳細は対応する原則/Phaseへ):

- **複数フェーズの一括実行** — 1フェーズだけを対象にしたか(原則1)
- **本体の実装介入** — 本体がコード・テストを直接書いていないか。書きたくなった修正も implementation-engineer に委譲したか(原則3)
- **自己申告での完了** — completion-verifier の pass を経ずに完了を宣言していないか。再検証を実装者にさせていないか(原則4)
- **契約の無断変更** — 実装中の契約解釈・逸脱が完了報告に漏れなく記載されているか(原則2)
- **検証の逸脱** — 検証が品質・セキュリティレビューに踏み込んでいないか(原則5)
- **差し戻しの暴走** — 差し戻し2回の上限を守り、上限到達でエスカレーションしたか(原則4)
- **位置の明示** — 完了報告に「全フェーズ中の位置」があるか(原則1)
- **確認の過剰** — ユーザー確認を Phase 1 末・Phase 4(+エスカレーション時)に絞ったか
