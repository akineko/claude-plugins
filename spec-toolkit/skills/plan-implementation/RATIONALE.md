# plan-implementation 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。
> このスキルは phase-implementation と同じ2エージェント(implementation-engineer / completion-verifier)を協調させる。実装/検証の分離・差し戻しループ・ハーネス範囲の理由は `../phase-implementation/RATIONALE.md` が正準。本ファイルは**連続実行とコミットに固有の決定**を扱う。

## 目的と背景

spec-toolkit の実装段は phase-implementation(1実行=1フェーズ、レビュー・コミットはユーザー)のみで、複数フェーズの実装計画を放置で完走させる手段がなかった。実装設計書のパスを渡すだけで全フェーズを自律実行し、フェーズ毎に検証済みコミットを積む運用(人間レビューは完走後にまとめて)を可能にするのが本スキル。ユーザー要望(2026-07-27)。

## 中核的な設計判断

### 【load-bearing】phase-implementation へのモード統合ではなく別スキル
- **決定**: 連続実行+フェーズ毎コミットを独立スキルとして追加。phase-implementation は無変更。
- **却下した代替案**: phase-implementation に「連続モード」を追加する — 同スキルの中核原則「1実行=1フェーズ」「コミットはユーザーの領分」と真逆の動作をモード分岐で抱えることになり、原則が条件付きに崩れて SKILL.md 全体の遵守率が下がる。quick-design(バリアントは別スキル)の前例とも不整合。
- **防いでいる失敗**: モード分岐だらけの指示文書で、どちらのモードでも規律が中途半端に適用される。
- **出所**: ユーザーの主要な悩みとして提示され、AskUserQuestion で「別スキル」を選択(2026-07-27)。

### 【load-bearing】コミットは検証 pass の後にのみ・1フェーズ=1コミット(原則2)
- **決定**: completion-verifier の pass 確認 → コミット → 次フェーズ、の順序を固定。pass 前のコミットと、コミットせず次フェーズへ進むことの両方を禁止。
- **防いでいる失敗**: (a) 未検証コミットが混ざり、事後レビュー時に「どのコミットまで信頼できるか」が判別不能になる。(b) 複数フェーズの差分が1コミットに混ざり、フェーズ単位の追跡・revert・再開ができなくなる。
- **出所**: ユーザー要望の中核(「各フェーズの実装が完了する毎にコミットして次のフェーズに進む」)+設計議論(2026-07-27)。

### 【load-bearing】コミット操作は本体(オーケストレーター)が行う
- **決定**: implementation-engineer にはコミットさせない(エージェント定義でも担当外)。ステージ対象の突合・コミット実行は本体の仕事。
- **理由**: コミットは「検証 pass の刻印」であり、pass を確認した者が押すべき完了の確定行為。実装エージェントに持たせると、検証前コミットや自己申告コミットを構造的に防げない。
- **防いでいる失敗**: 実装者の自己申告による未検証コミット。

### phase-implementation と共通する原則は重複を許容して自己完結させる
- **決定**: 契約遵守・オーケストレーター専念・独立検証・検証3点の各原則は、phase-implementation とほぼ同文で本スキルの SKILL.md にも書く(連続実行の文脈を織り込んで)。
- **却下した代替案**: 「phase-implementation の SKILL.md 該当節に従う」と参照で済ませる — スキル指示は実行時に単体でロードされるため、参照先を読みに行く不確実性(読まれない・部分的に読まれる)を実行時規律に持ち込むことになる。
- **防いでいる失敗**: 参照が解決されず規律が抜け落ちた実行。
- **同期ポイント(重複の管理)**: 次を変更するときは両スキルを同時に見直すこと — (a) 入口ガードと入力の前提、(b) 契約遵守と逸脱時の扱い(原則3)、(c) 実装/検証の分離と差し戻し上限(原則5)、(d) 検証3点の範囲(原則6)、(e) 実行開始前チェックの観点と条件付きゲート思想。この同期義務が別スキル案の代償であり、モード統合案が持っていた唯一の利点を回収する装置。

### エージェントは新設せず再利用し、定義の呼び出し元を併記に更新
- **決定**: implementation-engineer / completion-verifier をそのまま使う。両定義の「呼び出し側(phase-implementation スキル)」記述を両スキル併記に改める。
- **却下した代替案**: 連続実行用の実装/検証エージェントを新設 — 実装・検証の規律は phase-implementation と完全に同一で、複製は乖離リスクだけを生む。
- **防いでいる失敗**: ほぼ同文のエージェント定義が2組でき、片方だけ改訂される。

### フェーズ内の並列分割をしない(phase-implementation より狭い)
- **決定**: 常に 1フェーズ = 1委譲。phase-implementation が条件付きで認める並列委譲を、本スキルは行わない。
- **理由**: phase-implementation では分割はユーザー確認事項(開始前ゲートで提示)だが、本スキルは走行中にユーザー確認を挟まない設計のため、フェーズ毎の分割判断を確認する場がない。開始前に全フェーズ分の分割を確定させる案は、ゲートを重くする割に得られるのはフェーズ内並列の速度だけで、連続実行全体の堅牢さを損なう。
- **出所**: 設計議論(2026-07-27)。並列化の需要が実測されたら再検討。

### コミット失敗(フック拒否)は差し戻し枠で処理する
- **決定**: pre-commit フック等の拒否は「修正委譲 → 再検証 → 再コミット」とし、原則5の差し戻し上限(2回)に数える。専用のリトライ枠は設けない。
- **理由**: フック指摘(lint 等)は検証 fail と同種の「機械が検出した不備」であり、同じループで扱うのが最も単純。別枠にすると上限管理が二重になる。修正後の再検証を挟むのは、フック対応の変更が契約整合を壊していないことを確認するため。
- **出所**: 設計議論(2026-07-27)。

## 解釈・仮定（要確認）

- **開始フェーズ省略時の挙動**: 依頼は「実装設計書のパスを受け取る」のみ → 省略時はコードベースの実装状況から未実装の最初のフェーズを推定し、推定した事実は確認事項としてゲートに載せる(中断後の再実行が「続きから」になる再開経路を兼ねる)と解釈。⚠️常に全フェーズをフェーズ1から、の意図なら要修正
- **コミットメッセージの規約**: 指定なし → プロジェクトの直近コミット履歴の慣行に従い、読み取れなければ Conventional Commits と解釈(spec-toolkit は独立配布のため特定プラグイン・ツールを前提にしない)。⚠️固定フォーマットを規定すべきなら要変更
- **人間レビューはフェーズ間に挟まない**: 「コミットして次のフェーズに進む」から、レビューは完走後にまとめて行う運用と解釈し、スキルはレビューに関知しない。⚠️フェーズ毎にレビュー待ちで止まる形が欲しいなら、それは phase-implementation の領分
- **フェーズ毎の進捗報告は出す**: 自律実行でも完全サイレントにはせず、1〜3行の非ブロッキング報告を出すと解釈(異常の早期発見と、ユーザーが途中で介入する余地のため)。⚠️報告も不要なら削る
- **中断時に巻き戻さない**: 中断しても完了済みフェーズのコミットは残し、停止フェーズの未コミット変更もそのまま残す(状態report付き)と解釈。stash・reset 等の後始末はユーザーの判断に委ねる。⚠️自動で作業ツリーを綺麗にする方が良ければ要変更
- **作業ツリーの未コミット変更は確認事項**: dirty でも即中止にはせず、ゲートで提示してユーザーに判断させると解釈(phase-implementation と同じ扱い。ただし本スキルではコミット混入リスクがあるため、進める場合も既存変更はステージしない)。
