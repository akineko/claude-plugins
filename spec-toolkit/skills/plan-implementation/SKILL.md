# plan-implementation

実装設計書(implementation-design の成果物)の **実装計画の全フェーズ** を、フェーズ毎に「実装 → 独立検証 → コミット」を刻みながら完走させるスキル。

## このスキルが置かれている設計フロー

```
[1] 要求仕様書 → [2] 機能設計書 → [3] 影響分析書 → [4] 実装設計書 → [5] 実装(このスキル)
```

[5] 実装段には2つのスキルがあり、運用で使い分ける:

- **phase-implementation**: 1実行 = 1フェーズ。フェーズ毎に人間のレビュー・コミットを挟むサイクルを回したいとき
- **plan-implementation(本スキル)**: 1実行 = 実装計画の完走。フェーズ毎の検証済みコミットを積みながら自律的に進め、人間のレビューは完走後にまとめて行うとき

「設計判断をせず、確定した契約を実装に変換する」役割はどちらも同じ。本スキルはそれを全フェーズ分、コミットの節目を刻みながら行う。

## 入口ガード

実装設計書が無い、または `4. 実装計画` が欠けている場合は、**自分で実装計画を代行して埋めず**、まず implementation-design を実施するようユーザーに案内して止まる。代行すると、前段が担う設計判断・契約確定・フェーズ分割を飛ばした場当たりな実装になる。前段成果物が揃っていることが本スキルの前提。

## 入力の前提

- **主入力**: implementation-design が生成した実装設計書(`docs/plans/<機能名>/implementation-design-<バッチスラッグ>.md`)、または quick-design が生成した設計メモ(`docs/plans/<機能名>.md`。`## 2`〜`## 5` が実装設計書と同一構造)
- **補助参照**: 実装設計書 `1. 概要` に列挙された参照ドキュメント(影響分析書・機能設計書・要求仕様書)。quick-design の設計メモは単体で完結しており補助参照は不要
- **対象範囲**: 実装計画の全フェーズ。開始フェーズ番号が指定された場合はそのフェーズから最終フェーズまで(先行フェーズは実装済みとして扱う)

## 中核となる設計

### オーケストレーター + 実装/検証エージェントの分離

本体はコード・テストを一切書かず、オーケストレーションに徹する。使うエージェントは phase-implementation と同じ2つ:

- **implementation-engineer (実装担当)**: 対象フェーズの契約(設計書 3.x)に従い、TDD(Red → Green → Refactor)で実装する。TDD の規律はエージェント定義に規定済み
- **completion-verifier (検証担当)**: 実装がフェーズの完了条件を満たすか(テスト実行)、設計書の契約と一致するかを検証する。編集ツールを持たない

実装者と検証者を分離するのは、実装エージェントの「完了しました」報告が自己申告にすぎないため。**コミット操作だけは本体が行う** — コミットは検証 pass を確認した者が押す完了の刻印であり、pass の確認と不可分だから。

## 中核となる原則

進め方・自己点検はすべてこの7原則の適用。判断に迷ったらここへ戻る。

### 原則1: 1スキル実行 = 実装計画の完走 — ただし進行は1フェーズずつ

本スキルは残フェーズすべてを連続実行するが、複数フェーズをまとめて実装・検証・コミットしてはならない。フェーズは実装計画が定めた「動くもの単位」であり、この単位で検証とコミットを刻むからこそ、中断時にどこまでが確定済みかが明確になる。フェーズは上から順に実行する。

### 原則2: コミットは検証 pass の刻印 — 1フェーズ = 1コミット

completion-verifier の pass を確認した後にのみコミットする。未検証のコードをコミットしない(検証前に積んだコミットは、事後レビューでどこまで信頼できるかの判別を壊す)。逆に、pass したフェーズは次フェーズに着手する前に必ずコミットする(次フェーズの差分と混ざると 1フェーズ = 1コミットの追跡性が壊れる)。

### 原則3: 実装設計書は契約 — 実装中に設計へ立ち戻らない

設計判断は前段で完了している。実装中に契約(3.x)の曖昧さ・矛盾・不足が見つかっても、**契約を勝手に書き換えて実装しない**。実装を続けられる程度の曖昧さなら合理的に解釈して実装し、解釈内容を完走報告で明示する。契約と矛盾して実装を進められない場合は中断してユーザーに判断を仰ぐ(設計書の修正は implementation-design の責務)。連続実行では特に、黙った逸脱は後続フェーズ全部の基準を壊す。

### 原則4: 本体はオーケストレーターに徹する

本体がコードを書き始めると、実装のコンテキストで本体が埋まり、検証判断・差し戻し判断・コミット判断に使う「設計書の理解」が薄れる。実装は implementation-engineer へ、検証は completion-verifier へ委譲し、本体は契約の抽出・依頼の組み立て・コミット・報告の統合だけを行う。

### 原則5: 完了は独立検証で確定する

実装エージェントの報告だけでフェーズ完了を宣言しない。completion-verifier がテスト実行と契約照合を独立に行い、pass して初めてコミットできる。検証が fail した場合は指摘を implementation-engineer に渡して修正させる。**差し戻しはフェーズ毎に2回まで**。コミットがフック等に拒否された場合も差し戻しと同様に扱い(修正委譲 → 再検証 → 再コミット)、この上限に数える。2回で解決しない問題は大抵、契約自体の欠陥か環境の問題であり、エージェントの往復では解決しない。

### 原則6: 検証は「完了検証」まで — 品質レビューに踏み込まない

検証範囲は (a) フェーズ完了条件のテスト pass、(b) 既存テストのリグレッションなし、(c) 設計書契約との整合、の3点で止める。本スキルの運用ではフェーズ間に人間レビューが挟まらないが、その分を検証観点の拡大で補おうとしない。コード品質・セキュリティ等のレビューは完走後の別工程(ユーザーの運用)に委ね、ここに観点を足すと別工程のレビューと二重管理になる。

### 原則7: 迷ったら止まる — 積んだコミットは残す

連続実行は「黙って進む」リスクと隣り合わせにある。中断条件(後述)に該当したら、そのフェーズで実行を止めてユーザーに判断を仰ぐ。中断しても完了済みフェーズのコミットは取り消さない — 各コミットは検証済みの「動くもの」であり、中断・再開の安全点として機能する。

### ユーザーとの接点

問題のない入力なら、ユーザーが介在するのは **開始時の一言要約と完走報告だけ**。開始前の確認は確認事項があるときに限り1回にまとめる(Phase 1)。フェーズ完了毎には1〜3行の進捗報告を出すが、確認は求めない(ブロックしない)。それに加え、中断条件に該当した場合のみ随時ユーザーに確認する。フェーズ毎に形式的な継続確認を挟むと、本スキルを phase-implementation と分けて自律実行させる意味がなくなる。

## 進め方

### Phase 1: 入力受領と実行計画の確定

1. 入力(実装設計書のパス・開始フェーズ番号(任意))を受け取る。パス指定が無ければ確認する。
2. 実装設計書を読む。`4. 実装計画` が無ければ入口ガードに従い止まる。設計方針(2.x)と確定仕様(3.x)、実装計画の全フェーズを読み、本体が契約の全体像を把握する。
3. 開始フェーズを確定する: 指定があればそれ。無ければコードベースの実装状況(既存のモジュール・テストの有無)から未実装の最初のフェーズを推定する(推定した場合は確認事項として扱う)。
4. コミット規約を把握する: 直近のコミット履歴からメッセージの形式・言語を読み取る。読み取れなければ Conventional Commits 形式とする。
5. 実行開始前チェック: 次の観点で「確認事項」を収集する。該当を見つけてもその場では確認せず、全観点を見終えてからステップ6でまとめて扱う。
   - **入力の問題**: 指定フェーズ番号が実装計画に存在しない等、入力と設計書が噛み合わない
   - **フェーズ順序**: 開始フェーズより前に未実装のフェーズがある形跡(依存する契約が未実装のまま進むリスク)
   - **作業ツリー**: `git status` で未コミットの変更がある(フェーズ毎コミットに無関係な差分が混入する、または分離できなくなる)
   - **設計書とコードの乖離**: 対象フェーズの実装範囲が既に実装されている形跡がある、契約(3章)が前提とする既存コードが見当たらない・形が変わっている等
   - **開始フェーズの推定**: ステップ3で推定により決めた場合、その推定内容
6. 実行開始の判断:
   - **確認事項が1件以上ある場合**: 全件を事象・影響・選択肢とともにまとめて提示し、実行開始の可否をユーザーに確認する。
   - **確認事項が無い場合**: 実行範囲の一言要約(例:「フェーズ2〜4の3フェーズを連続実装します。フェーズ毎に検証 pass 後コミットします」)を伝え、確認を取らずに Phase 2 へ進む。

### Phase 2: フェーズループ

開始フェーズから最終フェーズまで、フェーズ毎に次を繰り返す:

1. **契約の抽出**: 対象フェーズの目的・テスト方針・実装範囲・完了条件(4.x)と、実装範囲に関係する確定仕様(3章)の項目を特定する。
2. **実装 (implementation-engineer)**: 次を渡して委譲する。TDD・契約遵守・完了判定をしない等の規律はエージェント定義に規定済みのため、依頼には対象の特定情報だけを書く:
   - 実装設計書のパスと対象フェーズ番号
   - プロジェクトルートと、把握していればテスト実行コマンド
   - タスク分割はしない(常に 1フェーズ = 1委譲。フェーズ内並列は本スキルでは行わない — 走行中にユーザーへ分割確認を挟めないため、堅牢さを優先する)
   - 「契約と矛盾して進められない」報告があれば原則3に従い中断する
3. **検証 (completion-verifier)**: 実装設計書のパス・対象フェーズ番号・実装報告(変更ファイル一覧・実装者の契約解釈)を渡す。fail の場合、不合格項目(期待・実際・該当箇所)を implementation-engineer に渡して修正させ、**再検証も completion-verifier に委譲する**(実装した本人に検証させない)。差し戻しはフェーズ毎に2回まで(原則5)。上限到達で中断する。
4. **コミット**: 検証 pass を確認してから行う:
   - `git status` で作業ツリーの差分を確認し、実装報告の変更ファイル一覧と突合する。本フェーズの成果だけをステージする(開始時に許容した既存変更・無関係な変更は含めない)。
   - 実装報告に無い変更が現れ、テスト生成物・lockfile 等として説明もつかない場合は中断条件とする(帰属不明の変更をコミットに混ぜない)。
   - コミットメッセージ: Phase 1 で把握した規約に従い、1行目はフェーズの目的の要約、本文に実装設計書のパスと「フェーズ n/N」を記す。
   - フック等でコミットが拒否されたら、その出力を添えて implementation-engineer に修正を委譲し、再検証 → 再コミットする(原則5の差し戻し上限に数える)。
5. **進捗報告**: 1〜3行で「フェーズ名・検証結果(差し戻し回数)・コミットハッシュ・全体位置(n/N)」を報告する。確認は求めず、次フェーズへ進む。
6. **集約**: 実装報告の「契約の解釈」・検証の「所見」を完走報告用に記録してから、次フェーズへ。

### Phase 3: 完走報告

全フェーズ完了後、以下のフォーマットで報告する。レビューの実施はユーザーの運用に委ね、本スキルからは指示しない。

```markdown
## 実装計画 完走: <機能名/バッチ名>

- **対象**: <実装設計書のパス>(全<N>フェーズ中、フェーズ<開始>〜<N>を実行)
- **コミット**:
  - <short-hash> <メッセージ1行目>(フェーズ<n>。差し戻し<k>回)
  - ...(フェーズの数だけ)
- **テスト結果**: <最終フェーズ検証時の全体テストの結果要約>
- **契約に関する報告**: <各フェーズの契約解釈・設計書側へ反映すべき事項の集約。なければ「該当なし」>
- **残課題**: <あれば。なければ「該当なし」>
```

「契約に関する報告」は実装設計書へのフィードバックループの出口。ここに挙がった事項をユーザーが設計書に反映するかを判断できるよう、解釈の内容と根拠をフェーズ毎に具体的に書く。

## 中断と再開

次のいずれかに該当したら、そのフェーズで実行を止めて状況を報告する(原則7):

- 契約と矛盾して実装を進められない(原則3)
- 差し戻し上限(2回)に到達した(原則5)
- 本フェーズの成果と帰属不明の変更が作業ツリーに混在した(Phase 2 ステップ4)

中断時の報告に含めるもの:

1. **確定済みの範囲**: 完了・コミット済みのフェーズとそのコミット
2. **停止したフェーズと事象**: 何が合わないか・試したこと(差し戻しの経緯)
3. **作業ツリーの状態**: 停止フェーズの未コミット変更をどう残しているか
4. **選択肢**: 取りうる対応(2〜3個)と推奨

**再開**: 問題の解消後に本スキルを再実行すれば、Phase 1 の実装状況の推定が完了済みフェーズを検出し、続きのフェーズから始まる。フェーズ毎のコミットがこの再開の安全点になる。

## 引き渡し前の自己点検

完走報告の前に各原則を守れたかを点検する(詳細は対応する原則/Phaseへ):

- **未検証コミット** — 検証 pass の確認前にコミットしたフェーズがないか(原則2)
- **コミット漏れ** — pass したのにコミットせず次フェーズに着手していないか(原則2)
- **フェーズの一括処理** — 複数フェーズをまとめて実装・検証・コミットしていないか(原則1)
- **本体の実装介入** — 本体がコード・テストを直接書いていないか。書きたくなった修正も implementation-engineer に委譲したか(原則4)
- **自己申告での完了** — completion-verifier の pass を経ずにコミット・完了扱いしていないか。再検証を実装者にさせていないか(原則5)
- **契約の無断変更** — 各フェーズの契約解釈・逸脱が完走報告に漏れなく集約されているか(原則3)
- **検証の逸脱** — 検証が品質・セキュリティレビューに踏み込んでいないか(原則6)
- **中断条件の無視** — 差し戻し上限・帰属不明の変更・契約矛盾を抱えたまま進んでいないか(原則7)
- **差分の混入** — 各コミットに本フェーズ外の変更が混ざっていないか(Phase 2 ステップ4)
- **進捗の沈黙** — フェーズ完了毎の進捗報告を出したか。逆に進捗報告で確認を求めてブロックしていないか
