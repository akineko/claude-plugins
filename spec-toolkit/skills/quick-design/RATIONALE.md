> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

フルパイプライン（request-spec → feature-options → impact-analysis → implementation-design）はある程度の規模には満足されているが、小規模な機能追加・修正には重い（ユーザー要望 2026-07）。フル版の重さはほぼ規模対策の装置（4回の起動・複数成果物・サブエージェント協調・固定スキーマ×4・多段確認）に由来し、小規模ではその前提（コンテキスト逼迫・複数セッション・成果物の部分参照）が成立しない。そこで、小規模で品質を左右する2つの決定 —「ユーザーに見える振る舞い」「実装契約」— を軸に再構成した1実行・1ファイルの軽量版を新設した。設計議論では「案A: パイプライン縮約型（4段を1スキル内の4ステップに写像）」と「案B: 接地先行・決定駆動型」を比較し、案Bを採用。

## 中核的な設計判断

### 【load-bearing】接地先行（調査 → 選択肢の順序をフル版と逆にする）
- **決定**: コード接地（Step 2）を振る舞い選定（Step 3）の前に置き、推奨根拠に実装コストを解禁。ただし案の提示単位は「ユーザーに見える振る舞い」のまま維持し、実装都合は根拠欄に限定する。
- **却下した代替案**: フル版と同順（選択肢 → 接地）。長いパイプラインでは後段の設計自由度を守る価値があるが、同一セッションで実装設計まで行う本スキルではその利益が薄く、小規模改修（ほぼブラウンフィールド）では接地なしの選択肢が机上になる。
- **防いでいる失敗**: 既存構造と噛み合わない選択肢の提示、実装段階での選定のちゃぶ台返し。
- **リスクと歯止め**: 「調査しながら設計してしまう」早すぎる収束（impact-analysis 原則2が防ぐ失敗）を持ち込むが、選定前に必ず AskUserQuestion のゲートを通すことで抑える。
- **出所**: 設計議論（2026-07）。案A/案B比較の主争点。

### 【load-bearing】2層調査（探索は impact-investigator へ委譲、精読は本体）
- **決定**: 「どこに何があるか」の探索をサブエージェントに委譲し、本体は返答の関連箇所表から「主」だけを精読する（目安3〜5ファイル）。追加の探し物は本体で grep せず再委譲。
- **却下した代替案**: (a) 本体が探索から全部行う — 対象プロジェクトが大きいと探索過程（grep の空振り・無関係ファイルの読み込み）がコンテキストを消費する（ユーザー指摘 2026-07）。(b) フル版 impact-analysis と同様に本体は一切コードを読まない — 本スキルは本体自身が契約（シグネチャ・型）まで設計するため、要約頼みの契約は実在しないインタフェースを前提にする捏造リスクがある。
- **出所**: 当初案（本体が直接調査）へのユーザー指摘（2026-07）を受けて2層方式に確定。

### impact-investigator の共用（専用ロケーター新設の却下）
- **決定**: 既存の impact-investigator をそのまま使い、定義の呼び出し元表記だけ両スキルに更新した。
- **却下した代替案**: quick-design 専用の軽量ロケーターエージェント新設 — impact-investigator の出力契約（関連箇所表・既存パターン・不明点の明示）が探索役の要件をそのまま満たしており、ほぼ同一エージェントの重複になる。同一プラグイン内の資産共有はリポジトリ方針でも推奨。
- **保守上の注意**: 利用形が異なる — impact-analysis 本体は返答だけで判断しコードを読まない / quick-design 本体は関連箇所表を足がかりに精読する。investigator の出力契約は両者共通の土台なので、変更時は両スキルへの影響を確認する（agents/impact-investigator.RATIONALE.md にも記載）。

### 2値ラベル（[確定]/[未決]）への簡約
- **決定**: request-spec の3値（[決定]/[方向性]/[要検討]）を使わない。
- **理由**: [方向性]/[要検討] の区別は「後続スキルが選択肢提示で前進できるか / 合意形成が要るか」という**非同期の引き継ぎのためのルーティング情報**。対話型の1スキルでは「その場でユーザーに聞けるか（→選択肢確認へ）/ このセッションで決められないか（→仮置き+残課題へ）」を対話中に直接判定でき、事前ラベルの価値が下がる。
- **保持したもの**: 「未決を勝手に畳まない」という全段一貫の思想は原則1として維持（これを落とすと軽量版だけ未決の可視性が消える — implementation-design 原則5 と同型の失敗）。

### 成果物 `## 2`〜`## 5` の phase-implementation 互換
- **決定**: 見出し構造を実装設計書テンプレートに揃え、1ファイルをそのまま phase-implementation に渡せるようにした（入口ガードは `4. 実装計画` の有無を見て、骨格 2.x・詳細 3.x を読む）。phase-implementation 側の「入力の前提」にも quick-design 成果物を明記。
- **防いでいる失敗**: 軽量版の成果物だけ実装フェーズに乗らず、手動変換が必要になる分断。

### エスカレーションは入口判定＋途中停止（フル版への変換性は持たせない）
- **決定**: 規模判定を入口と接地調査後に行い、超過したら停止して request-spec からのフル版を案内。書きかけの設計メモは request-spec の入力として渡す。
- **却下した代替案**: 検討した案Aのように各セクションをフル成果物の縮約（同一語彙・同一構造）にして途中合流可能にする — 変換性のためにフル版の語彙・構造を全部背負うと軽量化の効果が半減する。
- **防いでいる失敗**: 小規模と誤判定したまま完走して浅い設計を出す。

### 3アーキテクト協調のセルフチェック化
- **決定**: brownfield / domain-first の観点（既存整合・移行 / 概念境界・用語）＋要件適合を、本体がチェックリストとして通す（Step 4）。
- **注意**: implementation-design の RATIONALE では「チェックリスト化（完全単独スキル化）」は却下案とされているが、それはフル規模での判断（批評の質が設計品質を左右する規模では、専用エージェント分離が思考の汚染を防ぐ）。小規模ではエージェント協調のコストが便益を上回るという**規模前提の違いによる再判断**であり、フル版の判断を覆すものではない。

## 解釈・仮定（要確認）

- **出力先**: 1ファイルなのでディレクトリを掘らず `docs/plans/<機能名>.md` とした。⚠️フル版の `docs/plans/<機能名>/` と並ぶ運用を想定（エスカレーション時はディレクトリが別途できる）。ディレクトリに揃えたい場合は要修正。
- **「小規模」の閾値**: 振る舞いのまとまり3つ以上 / 設計判断が独立した複数のまとまりに分かれる / 合意形成の未決が中心、を停止条件とした。⚠️目安は運用・eval で調整する想定。
- **精読の目安（3〜5ファイル）**: 上限規制ではなく「超過時は理由を完了確認で添える＋大幅超過は規模超過の兆候として入口ガード再判定」と明文化（eval iteration-1 で理由付き7ファイル精読を観測し、目安の解釈が採点でも割れたため）。⚠️数値自体は経験則。コンテキスト逼迫の実測に応じて調整。
