# quick-design

小規模な機能追加・修正を対象に、要求の整理からユーザー目線の振る舞い選定、実装契約の確定までを1回の実行で完結させ、1ファイルの設計メモにまとめるスキル。フルパイプライン(request-spec → feature-options → impact-analysis → implementation-design)の各段を順に縮約するのではなく、小規模で品質を左右する2つの決定 — **ユーザーに見える振る舞いをどうするか** / **実装契約をどうするか** — を軸に再構成した軽量版。

## フルパイプラインとの棲み分け

```
フル版: [1] request-spec → [2] feature-options → [3] impact-analysis → [4] implementation-design → [5] phase-implementation
軽量版: quick-design ([1]〜[4] 相当を1実行) ─────────────────────────────────→ [5] phase-implementation
```

- **フル版**: ある程度の規模の機能開発。4スキル・複数成果物・サブエージェント協調で、段ごとにユーザー確認を挟む。
- **本スキル**: 小規模な機能追加・修正。1実行で `docs/plans/<機能名>.md` の1ファイルを生成する。
- 成果物の `## 2`〜`## 5` は実装設計書と同一の見出し構造にしてあり、**そのまま phase-implementation に渡せる**(phase-implementation の入口ガードは `4. 実装計画` の有無を見る)。

## 入口ガード(規模判定)

入力を俯瞰した時点で次のいずれかに該当するなら、本スキルで進めず、フルパイプライン(request-spec から)を案内して止まる:

- 独立に選定が必要な「振る舞いのまとまり」が **3つ以上**に割れそう(フル版の機能 F 相当)
- 実装の設計判断が、互いに独立した**複数のまとまり**に分かれそう(フル版の設計バッチ相当 = 一度の設計セッションで一緒に検討するには多い)
- 関係者間の**合意形成を要する未決が議論の中心**(選択肢を出しても前進しない)

進行中に判明した場合(接地調査で変更先が多数モジュールに散る等)も同様に停止を提案する。その際、作成途中の設計メモは要望の整理済み入力として request-spec にそのまま渡せる。

判定に迷うグレーゾーンでは、規模感の認識をユーザーに確認してから進める(勝手にフル版へ切り替えない。軽量で済ませたいかどうかの判断は利用者のもの)。

## 中核となる原則

進め方・フォーマット・自己点検はすべてこの5原則の適用。判断に迷ったらここへ戻る。

### 原則1: 小規模でも「未決の可視化」は落とさない

入力の各事項を **[確定]**(内容が一意に定まっている) / **[未決]**(何かを決めないと進めない) に仕分ける。未決は次の2通りで扱い、**勝手に1案へ畳まない**:

- **このセッションでユーザーが決められる未決** → Step 3 の選択肢確認に載せて、その場で確定する
- **このセッションで決められない未決**(他の関係者との合意・ポリシー判断が要る) → 仮置き案を明示して設計を進め、`5. 残課題・後続検討事項` に未決のまま残す。ただし仮置き次第で設計骨格ごと変わりうる場合は進めずに停止し、入口ガード(規模判定)に戻る

未決が1案で埋まると採用理由が立ってしまい、「未決だったこと」自体が読み手から見えなくなる。フルパイプラインの全段が守るこの規律を、軽量版でも維持する。

(フル版の3値ラベル [決定]/[方向性]/[要検討] を使わないのは意図的。[方向性]/[要検討] の区別は「後続スキルが選択肢提示で前進できるか/合意形成が要るか」という非同期の引き継ぎのためにあり、対話型の本スキルではその場でユーザーに聞き分けられる。)

### 原則2: 接地してから選択肢を出す(探索は委譲、精読は本体)

振る舞いの選択肢を出す前に、変更予定地の既存コードに接地する。調査は2層に分ける:

1. **委譲探索**: 「どこに何があるか」の探索は **impact-investigator** サブエージェントに委譲する。対象プロジェクトが大きいと、探し出す過程(grep の空振り・無関係ファイルの読み込み)が本体のコンテキストを消費するため、探索コストをサブエージェント側に隔離する。
2. **本体精読**: 返答の関連箇所表から**「主」のファイルだけ**を本体が読む(目安 3〜5ファイル)。本スキルは本体自身が契約(シグネチャ・型)まで設計するため、要約だけを頼りに契約を書くと**実在しないインタフェースを前提にする捏造リスク**がある。精読した実物が契約設計の錨になる。目安は上限規制ではなく、契約設計の錨として不可欠なら超えてよい。ただし対象は「主」に限定し、超過した理由を完了確認の要約で一言添える。目安を大きく超えるようなら、それ自体を規模超過の兆候として入口ガードの再判定に使う。

規律: 精読中に新たな探し物が生じたら、本体で grep を回さず impact-investigator に再依頼する。副次効果として、関連箇所表は規模の再判定材料になる(「主」が多数モジュールに散る → 入口ガードに戻る)。

委譲探索のスキップ条件: 入力が対象ファイルまで特定している / プロジェクトが小さく変更予定地が自明 / ユーザーが調査不要と明示。この場合も精読の上限(目安 3〜5ファイル)は守る。

### 原則3: 選択肢は「ユーザーに見える振る舞い」で提示し、根拠には実装コストを含めてよい

フル版の feature-options が実装非依存の選択肢に徹するのは、後段スキルの設計自由度を守るため。本スキルは同一セッションで実装設計まで行うためその利益が薄く、逆に小規模改修(ほぼ既存コードへの追加・修正)では「案1は既存の◯◯パターンにそのまま乗るので変更が最小」のような**接地した推奨根拠**こそが判断材料になる。

ただし提示単位の規律は維持する: **案の名前と本文は「何が見え・何が起こるか」で書き、実装都合は採用根拠の欄でのみ語る**。ユーザーはコードではなく振る舞いを選ぶ。

- 各選択肢の提示では**推奨案を必ず明示し、根拠を添える**
- 入力で[確定]と指定された振る舞いにも、それを脅かす別案が成立するなら1つ添える(素通しは選択肢を出す意味を半減させる。別案が無ければ無理に作らない)
- 接地調査では、触るエンティティの**作成側/参照側の両方に変更先が立つか**を点検する(閲覧だけ設計して登録が抜ける取りこぼしの防止)

### 原則4: 契約レベルで止め、フェーズは「動くもの」単位

実装設計書と同じ境界を使う:

| 書く(契約) | 書かない(実装の中身) |
|---|---|
| 型・制約・インデックス | テーブル作成SQL本文 |
| シグネチャ・リクエスト/レスポンス形・主要エラー | 関数本体 |
| 主要動作フローの概略(5ステップ以内) | 全分岐の手続き・擬似コード・呼び出し例 |

実装計画は1〜3フェーズ目安。各フェーズは「終わったら何かが動いてテストで確認できる」単位にし、「型だけ定義」「ファイルだけ作る」のような中間状態をフェーズにしない。

### 原則5: ユーザー対話は「選択肢確認」と「完了確認」の2点に絞る

小規模では手戻りのコストが小さく、確認の往復コストの方が高くつきやすい。振る舞いの選択・実装方針の分かれ目・未決の扱いは **Step 3 の AskUserQuestion 1回に束ねる**(最大4問)。骨格の独立確認は設けず、実装契約まで進めて完了確認でまとめて見せる。AskUserQuestion では推奨案を先頭に置いて「(推奨)」を付け、選定根拠を説明に書く。

## 進め方

### Step 1: スコープ確定

1. 入力(要望のテキストまたはパス)を受け取る。無ければ確認する。
2. 要求を What/Why で数行に整理し、[確定]/[未決] に仕分ける(原則1)。
3. 入口ガード(規模判定)を通す。該当すればフル版を案内して止まる。
4. 出力先を決める: `docs/plans/<機能名>.md`(`<機能名>` はケバブケース)。既存ファイルがあれば上書き可否を確認する。

### Step 2: 接地調査

1. impact-investigator に委譲探索を依頼する(1〜2依頼、1依頼1焦点)。依頼には**調査対象**(何を調べるか)・**背景**(この要望のために何を知りたいか)・**重点観点**を書く。重点観点には、変更予定地の構造・似た既存機能のパターンに加え、**触るエンティティの作成側/参照側それぞれの変更先**を含める(原則3)。
2. 返答の関連箇所表から「主」を本体が精読する(原則2。目安 3〜5ファイル)。
3. 規模を再判定する。変更先が多数モジュールに散るなら入口ガードに戻る。
4. 精読で判明した「要望の前提と現状コードの齟齬」(前提の機能が実は無い等)は記録し、Step 3 の提示または `5. 残課題` に反映する。

### Step 3: 振る舞いの選定

1. 振る舞いのまとまりごとに、接地済みの選択肢を2〜3案発想する(原則3)。
2. AskUserQuestion 1回に束ねて確認する(原則5): 振る舞いの選択(推奨付き)、実装方針に分かれ目があればそれも、このセッションで決められる未決の扱いも。
3. ユーザーが決められない未決は仮置きを明示して `5. 残課題` へ(原則1)。
4. 選定結果と主要却下案(却下理由つき)を記録する。

### Step 4: 実装契約とフェーズ計画

1. 骨格の主要意思決定(2〜4個目安)を固め、契約(データ構造・インタフェース・主要フロー・エラー方針)を精読した実物に接地して書く(原則2・4)。
2. セルフチェックを通す — フル版が批評エージェント(brownfield / domain-first)に委ねる観点を、本体がチェックリストとして適用する:
   - **既存整合**: 既存パターン・命名と揃っているか。移行や共存で壊れるものはないか
   - **概念整合**: 概念の境界と用語が既存のドメイン語彙と一貫しているか
   - **要件適合**: [確定]事項と選定した振る舞いを漏れなく満たすか
3. 実装計画を1〜3フェーズで立てる(原則4)。

### Step 5: 保存と完了確認

1. 成果物を保存する。
2. 要約を提示して確認を求める: 選定した振る舞い(主要却下案を1つ添える)、主要意思決定、フェーズ数と各フェーズ見出し、残課題。修正指示があれば反映する。
3. 完了報告に次のステップを含める(例: 「次は `/spec-toolkit:phase-implementation docs/plans/<機能名>.md 1` でフェーズ1の実装に進めます」)。

## 成果物のフォーマット

`## 2`〜`## 5` は実装設計書と同一の見出し構造を保つ(phase-implementation が設計方針 2.x・確定仕様 3.x を読み、入口ガードで `4. 実装計画` を確認するため)。**章(##)の順序と見出しは維持し、全セクションを必ず置く**(3章の節は設計対象単位で可変)。該当内容がなければ見出し直下に「該当なし」と明記する。

```markdown
# 設計メモ: <機能名>

## 1. スコープ
- **要求**: <What/Why を数行。誰のためかが自明でなければ添える>
- **確定事項**: <[確定] の一覧。なければ「該当なし」>
- **未決事項**: <[未決] と各々の扱い(選択肢確認で確定 / 仮置き+残課題)。なければ「該当なし」>
- **対象外**: <扱わない範囲。なければ「該当なし」>

## 2. 設計方針
### 2.1 振る舞いの決定
(振る舞いのまとまりごとに)
- **選定案: <名前>**: <操作の流れと見え方の要点>
- **採用理由**: <推奨根拠。実装コストを含んでよい>
- **主要却下案**: <案: 概要 / 却下理由>(なければ「該当なし」)

### 2.2 主要な意思決定
- **<決定>**: <要点と理由>

### 2.3 変更箇所
| パス | 役割 | 変更内容 |
|------|------|---------|
| ... | ... | ... |
- **既存コードとの齟齬・前提**: <接地調査で判明した不整合。なければ「該当なし」>

## 3. 確定仕様
### 3.<n> <設計対象>
(設計対象の自然な単位 — エンティティ/エンドポイント/コンポーネント等 — で節を切り、各対象に契約・動作・エラーを一体で書く。実装設計書と同じ編成。理由は 2.x の決定を参照し、ここには書かない)

## 4. 実装計画
### フェーズ 1: <フェーズ名>
- **目的**: <このフェーズで何が動くようになるか>
- **テスト方針**: <完了を固定するテストのレベル: ユニット/統合/契約 など>
- **実装範囲**: <どの契約を実装するか>
- **完了条件**: <該当テストが pass + 動作確認>

## 5. 残課題・後続検討事項
```

## 引き渡し前の自己点検

出力前に各原則を守れたかを点検する(詳細は対応する原則/Stepへ):

- **未決の無断確定** — 未決を勝手に1案へ畳んでいないか。決められない未決は仮置きと明示して残課題に残したか(原則1)
- **探索の本体持ち込み** — 探索を委譲したか。精読が「主」を超えて広がっていないか。目安(3〜5ファイル)を超えた精読に理由を示せるか。新たな探し物を再委譲したか(原則2)
- **要約頼みの契約** — 契約に書いたシグネチャ・型は、精読した実物に接地しているか(原則2)
- **実装目線の露出** — 選択肢の名前と本文が振る舞いで書かれているか。実装都合が根拠欄に収まっているか(原則3)
- **推奨の欠落** — 各選択肢に推奨案と根拠を添えたか(原則3)
- **[確定]の素通し** — 確定指定にも別案を構想したか、構想して「無し」と判断したか(原則3)
- **ライフサイクル片側欠落** — 触るエンティティの作成側/参照側の両方に変更先が立つか(原則3)
- **契約レベル逸脱** — 3.x に関数本体・擬似コードが無いか(原則4)
- **フェーズの中間状態** — 各フェーズは「終わったら動いてテストで確認できる」か(原則4)
- **規模超過の看過** — 進行中に膨らんだ兆候(まとまり3つ以上・変更先の散在)を無視して完走していないか(入口ガード)
- **対話の分散** — 確認を選択肢確認1回+完了確認に集約したか(原則5)

## 出力後にユーザーに確認すること

完了確認(Step 5)では次に絞って提示する:

- 選定した振る舞いに最終形で違和感がないか(主要却下案を1つ添えて)
- 残課題の扱いが妥当か(仮置きのまま実装に進んでよいか)
- フェーズ分割が現実的か
- 出力先パスで問題ないか
