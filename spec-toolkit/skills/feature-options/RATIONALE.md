## 目的と背景

要求仕様書を入力に、ユーザー目線で機能の実現方法の選択肢を洗い出し・選定し、機能設計書にまとめる（パイプライン2段目）。「ユーザーから見て機能がどう振る舞うか」だけを確定し、技術選定・データ構造・実装手順には踏み込まず、下流（impact-analysis / implementation-design）が「より良い実装方法」を選ぶ余地を残す。

## 中核的な設計判断

### 【load-bearing】要求単位ではなく「機能」単位で組織する（Phase1.5 棚卸し＋Phase6 双方向検算）
- **決定**: `4. 機能設計` を機能(F)単位で組織し、機能洗い出しの前に Phase1.5 で要求横断にエンティティ/ライフサイクル（作成側/閲覧側）を棚卸し、後に Phase6 で順方向（取りこぼし）/逆方向（過剰）を双方向検算する。
- **却下した代替案**: 要求を1件ずつ機能化する。要求は機能ライフサイクルの一部しか語らない（「閲覧したい」は言うが「閲覧対象を誰が作るか」は言わない）ため、前提機能がまるごと抜ける。
- **防いでいる失敗**: 閲覧機能だけ設計して登録機能が抜ける等、要求一覧との照合では一見埋まって見える取りこぼし。
- **出所**: eval-lifecycle-gap で実証（旧版は施設スキャンの取り込み/マップ編集/ログインを取りこぼした）。commit 311e788 がこの再構成。2026-05 の codebase 検証でも F4 スキャン取り込み/F5 マップ配置/F6 ログインを前提機能として捕捉確認。**この棚卸し＋双方向検算の冗長性が抜け止めの本体**であり、減量時も「目標」だけに圧縮してはいけない。

### [決定] ラベルの要求にも別案を探る
- **防いでいる失敗**: 指定済みの案を素通しすると、このスキルを差し込む意味の半分（より良い選択肢の模索）が失われる。別案を構想して却下したか、構想すらしていないかには大きな差がある。

### [要検討] の扱い分け（合意形成を要する未決は選定保留）【B3・2026-05追加】
- **決定**: 原則1で、[要検討] のうち合意形成プロセス（部門調整・ポリシー・法務）を要するものは、選択肢を並べた上で**選定を保留**し確認ポイント/引き継ぎに返す。[方向性]（選択肢提示で前進）とは扱いを分ける。
- **出所**: 2026-05 境界チェック。request-spec が [要検討] に込めた「選択肢提示だけでは前進しない」区別が、原則1で[方向性]と同一処理に畳まれ消えていた契約ズレの是正。
- **防いでいる失敗**: 本来ユーザーに差し戻すべき意思決定をスキルが勝手に1案へ畳んで代行する。

### 案件固有軸の事前ユーザー確認（条件分岐つき）
- **決定**: 案件固有軸を立てた場合のみ Phase3 で確認を発火。共通軸だけなら確認スキップ。
- **防いでいる失敗**: 誤った固有軸は1要求でなく**全要求の選定を汚染**する。ドラフト後に気づくと全やり直し。
- **earned wisdom**: 共通軸は普遍的で解釈ブレが小さく、毎回確認すると対話が重い → 固有軸を立てた時だけ確認、という対話コスト最適化。

### 単独実行（機能をサブエージェントに fan-out しない）
- **理由**: 品質の核（評価軸・横断ポリシー・前提機能ハントの一貫性）は製品全体の振る舞いを1文脈に保持して初めて成立する。機能を個別エージェントに割ると各自が軸を再導出・前提機能を別々に探し、防ぎたい不整合（CONSISTENCY failure）をかえって製造する。
- **出所**: 2026-05 のゼロベース再設計が現行を見ずに独立に同じ論証へ到達。

### 固定スキーマ＋全セクション必須＋F-ID
- **決定/維持**: 機能(F)単位で組織し各機能に `関連要求` を必ず添える。後続 impact-analysis がこの構造を機械的に走査して全機能を拾い、要求との対応を辿る。2026-05 の再設計が「レイアウト柔軟化」を提案したが、下流契約への構文依存ゆえ退行と判断し**維持**。
