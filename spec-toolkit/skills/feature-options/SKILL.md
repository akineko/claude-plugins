# feature-options

要求仕様書(request-spec の成果物)を入力にとり、ユーザー目線で機能をどう実現するかの選択肢を洗い出し、評価して選定し、機能設計書としてまとめるスキル。

## このスキルが置かれている設計フロー

```
[1] 要求仕様書 (request-spec)
       ↓
[2] 機能選択肢の洗い出し・選定 (このスキル: feature-options)
       ↓
[3] 影響分析 (impact-analysis)
       ↓
[4] 実装設計 (implementation-design)
```

このスキルが解く問題は「ユーザーから見て機能がどう振る舞うか」を確定させること。後続フェーズの存在が「やらないこと」を強く規定する:

- **[3] 影響分析** がコードベース上の変更箇所・依存関係の事実を集める → 特定ファイル・モジュールの指定・命名はしない
- **[4] 実装設計** が技術選定・データ構造・アーキテクチャ・フェーズ分割を行う → ライブラリ・テーブル設計・実装手順に踏み込まない

つまり「**要求から、ユーザー目線で機能の振る舞いだけを確定する**」のが仕事。「どこをどう実装するか」は意図的に棚上げにし、後続スキルが「より良い実装方法」を選ぶ余地を残す。

## 入力の前提

- **入力**: request-spec が生成した要求仕様書(`docs/plans/<機能名>/request-spec.md` 等)。各要求に `[決定] | [方向性] | [要検討]` の具体度ラベルが付いている。
- **このスキルは全ての要求を対象とする**([決定] も対象から外さない。原則1)。
- 要求仕様書が見当たらない/要求一覧が欠けている場合は、まず request-spec を実施するようユーザーに案内する。

## 中核となる原則

進め方・フォーマット・自己点検はすべてこの6原則の適用。判断に迷ったらここへ戻る。

### 原則1: 具体度ラベルに応じて別案探索と選定の扱いを変える

- **[決定]**: ステークホルダーの指定を「ベースライン案」として扱い、それを脅かす別案が成立するなら主要却下案として記録する。別案が見当たらなければ「別案検討: 該当なし」と明記する(検討した痕跡を残すこと自体に意味がある)。[決定] を素通しすると、このスキルを差し込む意味の半分が失われる。
- **[方向性]**: 真っ白から複数案を出し、選定する。
- **[要検討]**: 選択肢は出すが、その未決が**合意形成プロセス(部門間調整・ポリシー・法務など)を要する**なら、選択肢を並べた上で**選定を保留**し、確認ポイント / `6. 後続フェーズへの引き継ぎ` に判断を返す。勝手に1案へ畳むと、本来ユーザーに差し戻すべき意思決定をスキルが代行してしまう。選択肢提示だけで前進できる[方向性]とは扱いを分ける(request-spec が[要検討]に込めた「選択肢提示だけでは前進しない」という区別を、ここで消さない)。

### 原則2: ユーザー目線に留まり、実装目線に踏み出さない

答えるべき問い — 何が見える/押せる/起こるか(画面要素)、何をどの順で操作するか(操作フロー)、どんな状態があり各々ユーザーに何が見えるか(状態の見え方)、既存のどの動線・画面と接続するか。
答えてはいけない問い — どんなテーブル/APIで実現するか、どのファイル/コンポーネントを作る・触るか、どのライブラリを使うか、どんな順序で実装するか。

その場で効く一文判定: 書こうとする記述から「ユーザーには見えない情報」(DB列名・API名・ファイルパス・実装言語)を取り除いて、それでも機能の振る舞いとして読めるか。読めなければ実装目線に踏み出している(例: ✗「ProductCard.tsx に handleFavorite を追加」/ ◯「商品カードの右上にお気に入りトグルを追加」)。

例外: 要求仕様書に制約として書かれている技術指定(「Microsoft Entra ID を使う」等)は、ユーザー視点の前提条件として参照してよい。独自に技術選定を新規追加してはいけない。

### 原則3: 出力は「選定案＋主要却下案」に絞る

機能ごとに残すのは、選定案(操作フロー+画面要素+採用理由)、主要却下案(最大3つ、どんな案でなぜ採用しなかったか)、確認ポイント(あれば)の3点だけ。検討途中の雑多な案・短命なバリエーション・明らかに弱い案は出力に残さない。後続スキルの読み手にとってノイズが多いと「結局この機能は何になったのか」が読めなくなるため、検討プロセスではなく結論+主要分岐点を残す。

「却下案ゼロ」は基本的に怪しい(別案探索の不足を疑う)。一方で弱い案・劣化版を惰性で並べるのもノイズ。主要な対立軸を代表する案に絞り、絞った結果ゼロになる場合だけ「該当なし」と明記する。

### 原則4: 評価軸は「テンプレ＋案件固有」で軸の質を担保する

比較は印象論でなく軸に基づく。共通テンプレ軸を常に意識する — **ユーザー価値**(要求のWhyをどれだけ満たすか) / **学習コスト** / **標準・類似サービスとの揃え** / **拡張性**(要求が増えても壊れにくいか) / **変更の不可逆性**(後戻りが難しくならないか)。

加えて案件特有に重要な軸があれば追加する。**案件固有軸には必ず「導出根拠」を添える**(要求仕様書のどの記述・背景・Why から、なぜこの案件でその軸が重要かを言語化)。

案件固有軸は、立てたら選定に入る前にユーザーへ提示して認識を合わせる(Phase 3)。理由: 誤った解釈の案件固有軸は1要求でなく**全要求の選定を汚染する**。ドラフトを作ってから軸の誤りに気づくと全選定をやり直すことになり、ドラフト前に正すよりコストが大きい。

軸は「考えるための足場」。評価マトリクスを必ず載せる必要はないが、選定案の採用理由・却下理由は**どの軸で勝ち負けがついたか**を読者が推察できる粒度で書く。

### 原則5: 既存実装の調査は「現状のUI/UX・機能仕様の把握」に限定する

調査するのは、新機能が既存機能と接続する箇所(ヘッダー・ナビ・商品詳細画面等)の現状レイアウト・動線、参考にすべき似た既存機能の UI/UX、変更案と対比する現状の振る舞い。
調査でやらないこと(後続の担当): ファイル名・関数名の取得(impact-analysis)、データ構造・API契約の調査(implementation-design)、実装上の制約の洗い出し(impact-analysis)。

調査結果は機能設計書の現状把握・前提条件にだけ反映し、選定案の本文では「画面の挙動」として書く(原則2)。

### 原則6: 要求ではなく「機能」を組織単位にする

要求と機能は1:1ではない。1つの機能が複数要求を満たすこともあれば、1要求が複数機能に分かれることもある。さらに**要求は機能ライフサイクルの一部しか語らない** — 「閲覧したい」とは言っても「閲覧対象を誰がどう作るか」までは言わない。要求を1件ずつ機能化すると、要求が語らなかった前提機能(閲覧対象を登録する機能、一覧に項目を追加する機能、一括登録した利用者がログインする認証)がまるごと抜け、全部実装しても使えないサービスになる。

そこで `4. 機能設計` を**要求ではなく機能の単位で組織**し、各機能に「関連要求」を添える。「これらの要求が満たされたサービスが成立するには、どんな機能が要るか」を起点に洗い出す(Phase 1.5・Phase 4)。これを機械的に担保するのが Phase 1.5(事前のライフサイクル棚卸し)と Phase 6(事後の双方向カバレッジ検算)。

ただし「成立に必要な機能を補う」ことと「あれば便利な機能を妄想で足す」ことは別 — これは**対の失敗**で、その場では楽な方(足す/足さない)へ引っ張られやすい。両者を分ける歯止めの問い: その機能を消したとき、関連要求が語った機能はユーザー操作として**成立するか**。成立しない(操作対象が存在しない・前提状態に到達できない)なら必要な機能。成立する(あれば便利なだけ)なら足さない。迷ったら足さない側へ。これは request-spec の「自然な補完か過剰な追加か」を「動作するか」に翻訳した基準。スコープ/ポリシー判断を要する前提(認証方式の選定など)は勝手に1案に決めず、確認ポイントか `6. 後続フェーズへの引き継ぎ` に回す。

## 進め方 (ハイブリッド対話モード)

「ドラフトを先に出して全体感を共有 → 論点が大きい機能だけ深掘り対話」で進める。機能が10件あっても全件を対話で詰めず、判断が分かれそうな箇所だけ立ち止まる。立ち止まりは2種類: **評価軸の確認**(案件固有軸を立てた場合のみ、選定の前 / Phase 3)と、**論点深掘り**(選定の後、判断が分かれそうな機能のみ / Phase 5)。前者は「物差しが正しいか」、後者は「物差しを当てた結果が妥当か」を見る。

このスキルはサブエージェントに分割せず単独で進める。品質の核である「評価軸・横断ポリシー・前提機能ハントの一貫性」は、製品全体の振る舞いを1つの文脈に保持して初めて成立する。機能を個別エージェントに fan-out すると各自が軸を再導出し横断方針を別々に決め前提機能を別々に探すため、防ぎたい不整合をかえって製造してしまう。

### Phase 1: 入力の受領と俯瞰

1. 入力(要求仕様書のパス)を受け取る。指定が無ければユーザーに確認する。
2. 要求仕様書を読み込み、要求一覧と各ラベルを把握する。
3. 出力先を決定する: 要求仕様書と同じディレクトリの `feature-options.md`(例: `docs/plans/favorite-products/feature-options.md`)。既存ファイルがあれば上書き可否を確認する。

### Phase 1.5: エンティティとライフサイクルの棚卸し

機能を要求から1件ずつ起こすと「要求が語ったこと」しか乗らない(原則6)。Phase 4 に入る前に要求横断で次を点検する。

1. **エンティティを列挙する**: ユーザーが操作・参照する対象オブジェクトを要求群から拾う(記事・コメント・タグ・添付・ユーザー・ロール・通知 等)。「ユーザーから見て名前のつく対象」であって、テーブルやデータモデルではない。
2. **各エンティティのライフサイクルを点検する**: そのエンティティについて「誰が・どのユーザー操作で 作成/管理 するか」「誰が 閲覧/利用 するか」が、いずれかの要求でカバーされているかを見る。閲覧側だけあって作成側がどの要求にも無ければ欠落候補。
3. **土台機能の前提を点検する**: ある要求が成立するために暗黙に必要な土台機能(例: 「CSV によるユーザー一括登録」が前提とするログイン認証)が、要求のどこにも無いかを見る。

挙げた欠落候補は Phase 4 の入力になる。成立に不可欠なもの(原則6の歯止めを通る)は機能として設計し、スコープ/ポリシー判断が要るものは確認ポイント・引き継ぎへ。重い論点なら Phase 3 のユーザー確認に合流させる。ここで点検するのは「機能設計に乗せるべき機能が揃っているか」というユーザー目線の話で、impact-analysis が見る「設計済み機能がコード上どこに当たるか」とは別レイヤー。前提機能をここで顕在化しないと、impact-analysis には閲覧機能の影響範囲だけが渡り、登録機能の存在自体が永久に分析対象から漏れる。

### Phase 2: 現状把握(必要に応じて)

既存画面・既存機能との接続が明示されている要求があれば、現状の UI/UX・機能仕様を把握する(完全新規で既存動線と接合しないなら不要)。把握対象は「ユーザーが見える振る舞い」に限定し(原則5)、結果は `現状把握` セクションに簡潔にまとめる。

### Phase 3: 評価軸の策定とユーザー確認

選定の物差しを確定する。誤ると全要求の選定が汚染されるため、案件固有軸はこの段階でユーザーと認識を合わせる(原則4)。

1. **評価軸を策定する**: 共通テンプレ軸(この案件での意味づけを1行ずつ)＋案件固有軸(あれば、各々に導出根拠を添える)。
2. **案件固有軸を1つ以上立てた場合のみ、確認を発火する**: `AskUserQuestion` で**案件固有軸(名前＋定義＋導出根拠)を主役に提示**しつつ、共通軸の意味づけも一覧で軽く添える(共通軸のズレも拾える)。「この理解で選定に進んでよいか/修正したい軸があるか」を問い、OK が出てから Phase 4 へ。
3. **案件固有軸を立てない(共通軸だけで足りる)場合は確認をスキップ**して Phase 4 へ。共通軸は普遍的で解釈のブレが小さく、毎回確認すると対話が重くなるため。
4. 確定した軸は `3. 評価軸` にそのまま反映する(導出根拠も残す)。

### Phase 4: 機能の洗い出しとドラフト作成

要求を1件ずつ機能化せず、2つのパスで進める(原則6)。

**パス1: 機能の洗い出し(広さ)** — 「これらの要求が満たされたサービスが成立するには、どんな機能が要るか」を起点に列挙する。要求仕様書がテーマ別なら**グループ単位**で、そうでなければ全要求まとめて。Phase 1.5 で挙げたライフサイクル欠落・前提機能をここで機能として拾い、閲覧機能と並んで登録機能が対等に挙がるようにする。各機能に**関連要求**(ID、複数可)を紐づけ、連番識別子(F1, F2, …)を振る。

**パス2: 各機能の詳細化(深さ)** — 各機能で次を通す。**単位が要求から機能に変わるだけで、1件あたりの別案探索は落とさない**:

1. **複数案を発想**(Phase 3 の評価軸を手がかりに対立軸が見える案を):
   - 関連要求に [決定] を含む機能 → ベースライン案 + それを脅かす別案を1〜2つ(原則1)
   - [方向性] のみに紐づく機能 → 真っ白から3案程度
   - Phase 1.5 由来で振る舞いがほぼ一意に定まる前提機能 → 別案探索は省き、成立に必要な最小限の振る舞いだけ書く(複数案を演じると足したこと自体が目立ちノイズになる)
2. **選定**: Phase 3 で確定した軸で比較し1案に絞る(ここで新たな軸を作らない)。ただし**関連要求に[要検討]があり合意形成を要する機能は、選択肢を出した上で選定を保留し確認ポイント/引き継ぎへ回す**(原則1)。
3. **却下案の整理**: 主要な対立軸を代表する案だけ残す(最大3つ目安。2案で十分なら2案で止め、3案目をひねり出さない)。
4. **確認ポイントの抽出**: ユーザー判断を仰ぎたい部分を書き出す。

ここまでをドラフトとして一度ファイルに書き出す。**この段階で(評価軸以外の)対話に入らず、まずドラフトを完成させる**。

ドラフト記述のルール(詳細は自己点検を参照):
- 操作フローは番号付きで2〜6ステップ程度。ユーザーが目で見て・手で操作することに限り、システム内部処理は書かない。
- **画面要素**(常に置かれる静的な配置。色・サイズ等の視覚指定はしない)と**状態のバリエーション**(ローディング・空・エラー・成功で同じ要素がどう変化するか)を書き分け、同じ情報を両方に書かない。
- 画面が複数登場する機能は**主要な接点(2〜3画面)に重点**を置き、他は接続点の言及に留める(全画面の機械的列挙はしない)。
- 実装フェーズへの送り(「具体方式は実装で詰める」等)は本文の括弧書きで散らさず `6. 後続フェーズへの引き継ぎ` に集約する。

### Phase 5: 論点深掘りの対話

ドラフトができたら、論点が大きい機能のみピックアップして対話する(Phase 3 の評価軸確認とは別。こちらは選定**後**に「結果が妥当か」を問う)。ピックアップ基準:

- **A.** 確認ポイントが書かれている機能(ユーザー判断が必要)
- **B.** 選定案と却下案の差が小さく、選定根拠がユーザーの価値観に依存しそうな機能
- **C.** 関連要求に [要検討] ラベルがあり、要求仕様書段階から判断が残っている機能
- **D.** Phase 1.5 由来の前提機能で、足すこと自体や範囲にユーザー判断が要るもの

ピックアップが0〜1件なら無理に増やさず、5件以上にもしない(対話が間延びする)。最大3件程度を目安に。

対話は、選定案と主要却下案・選定の論点(どの軸でどの案が勝ったか)を簡潔に提示し、`AskUserQuestion` で確認する(例: 「<機能名>: 選定案Xでよいか、別案Yに切り替えるか、混合案にするか」)。判断を受けて選定を確定し、他機能に波及する判断(ナビ全体の方針等)があれば関連機能も合わせて更新する。ピックアップしなかった機能はドラフトの選定をそのまま採用する(一括差し戻しは Phase 7 で受ける)。

### Phase 6: 横断的整合性とカバレッジの点検

複数機能にまたがる整合性をチェックし、必要なら `横断的な機能設計上の決定` に集約する(ナビ/動線の矛盾、同一画面要素を触る機能間の優先度、通知・状態表示パターンの揃い、既存機能とのデザイン整合)。不整合があればユーザーに報告し修正方針を相談する。

加えて、機能ベースで設計したことで生じる「要求の取りこぼし」と「機能の過剰」を双方向で検算する(原則6の機械的検算):

- **順方向(取りこぼし検出)**: 全要求が最低1つの機能の `関連要求` に現れるか。さらに各要求の意図が機能群で満たされているか — 特に Phase 1.5 で挙げたライフサイクル(その要求が触れるエンティティの作成/管理側)が機能に反映されているか。どの機能にも現れない要求、閲覧側しか機能化されていない要求は「薄まって漏れた」候補 → 機能を足すか確認ポイント/引き継ぎへ。
- **逆方向(過剰検出)**: すべての機能が最低1つの要求に辿れるか。どの要求にも紐づかない機能は、原則6の歯止め(消したら成立しないか)を通るか改めて確かめ、通らないなら落とす。
- スコープ/ポリシー判断を要する前提機能の欠落(認証方式など)が、確認ポイントか `6. 後続フェーズへの引き継ぎ` の「前提機能の欠落」に記録されているか。

### Phase 7: 出力とユーザー確認

完成した機能設計書を保存し、要点を提示して確認を求める: 機能の件数と選定案の見出し一覧(各機能の関連要求も)、Phase 1.5 で補った前提機能の明示、意外と捨てがたかった主要却下案を1〜2件、残っている確認ポイント・前提機能の欠落。修正指示が来たら該当箇所を更新し再確認する。

## 成果物のフォーマット

機能設計書は次のセクションで構成する。**セクション順序とフィールド名は維持する**(後続の影響分析がこの構造を機械的に走査して前提にする)。

```markdown
# 機能設計書: <機能名>

## 1. 概要

- **対象要求仕様書**: <要求仕様書のパス>
- **対象範囲**: <この機能設計書で扱う要求IDのリスト>
- **制約条件(上流から)**: <request-spec の各要求の「制約条件」由来の技術指定・既存基盤指定など。どの要求(R番号)由来かを併記。なければ「該当なし」>
- **対象外**: <要求仕様書にあるが本スキルで扱わない要求。その旨・理由に加え「差し戻し先」を必須で書く(例: R5 — 優先度低。次サイクルの request-spec で再評価 / 別 docs/plans/<別機能>/ で扱う)。なければ「該当なし」>
- **要求カバレッジ**: <全要求がいずれかの機能でカバーされているかの確認。機能↔要求の完全な対応は §4 各機能の `関連要求` を正とし、ここで繰り返さない>
- **1:1でない箇所**: <要求と機能が1:1にならない箇所だけを挙げる(1機能が複数要求にまたがる箇所、補った前提機能)。なければ「すべて1:1」>

## 2. 現状把握
<既存機能・既存UI/UXのうち本機能設計に関わる部分の要旨。なければ「該当なし」>

## 3. 評価軸
- **ユーザー価値**: <この案件でのこの軸の意味を1行> / **学習コスト**: ... / **標準・類似サービスとの揃え**: ... / **拡張性**: ... / **変更の不可逆性**: ...
- (案件固有軸があれば追加。定義に加えて「根拠: 要求仕様書のどこ/背景から」を添える)

## 4. 機能設計

### F1 <機能名>
- **関連要求**: R1, R2 (応える要求のID。複数可。前提機能の場合は「(前提機能) Rn を成立させるため」のように添える)
- **ゴール**: <この機能で何が達成されるかを1〜2行>

#### 選定案: <案の名前>
**ユーザー操作フロー**: 1. … 2. …
**画面要素** (静的な配置のみ。主要な接点 2〜3画面に重点): - <画面X>: <要素A>, <操作可能なもの>
**状態のバリエーション** (動的な見え方。該当するものだけ): - ローディング/空/エラー/成功: …
**採用理由**: - <どの評価軸でどの案より優位か>

#### 主要却下案
- **案A: <名前>** — <概要> / 却下理由: <どの評価軸で劣ったか>

#### 確認ポイント (あれば)
- <ユーザー判断が必要な未決点>

(機能の数だけ F1, F2, … と連番。前提機能で振る舞いがほぼ一意なものは選定案のみ浅く書き、主要却下案は省略してよい)

## 5. 横断的な機能設計上の決定
<複数機能にまたがる方針(通知パターンの統一など)。なければ「該当なし」>

## 6. 後続フェーズへの引き継ぎ
<次フェーズ(impact-analysis)で扱ってほしい論点や、機能設計の確定で新たに浮上した検討事項>

### 前提機能の欠落 (あれば)
<要求群が暗黙に前提するが、スコープ/ポリシー判断が必要で本スキルでは設計しなかった土台機能。なぜ保留したか(どの判断が要るか)を添える>
```

**全セクションを必ず置く**。該当内容がなければ見出し直下に「該当なし」と明記する(後続スキルはこの構造を前提に動くため、「セクションが無い」と「あって該当なし」は意味が違う)。`4. 機能設計` は機能(F1, F2, …)単位で組織し各機能に `関連要求` を必ず添える — impact-analysis はこの構造を舐めて全機能を拾い、`関連要求` から要求との対応を辿る。

## 引き渡し前の自己点検

出力前に各原則を守れたかを点検する(詳細は対応する原則/Phaseへ):

- **実装目線への踏み出し** — 記述からユーザーに見えない情報(ファイル名・テーブル名・API名)を消して振る舞いとして読めるか(原則2)
- **[決定] の素通し** — ベースライン案を脅かす別案を構想したか、構想して却下したか、構想すらしていないか(原則1)
- **[要検討] の畳み込み** — 合意形成を要する未決を勝手に1案へ畳まず、選定保留→確認ポイント/引き継ぎに回したか(原則1)
- **却下案の不足/過多** — 主要な対立軸を代表する案に絞れているか。弱い案を惰性で並べていないか(原則3)
- **評価軸の形骸化** — 採用/却下理由が、どの評価軸で勝負したか読み手に伝わるか(原則4)
- **案件固有軸の独断** — 固有軸を要求のどこから導いたか言語化できるか。立てたなら Phase 3 で確認したか(原則4)
- **操作フローの冗長** — ユーザーが見て操作することだけか、内部処理が混ざっていないか(原則2)
- **画面要素と状態の重複** — 静的な配置と動的な見え方を書き分け、同じ情報を重複させていないか。主要な接点に重点を置いたか
- **実装送りの散在** — 「実装で詰める」等の注釈を本文に散らさず `6.` に集約したか
- **前提機能の取りこぼし(under-reach)と妄想(over-reach)** — これは**対の失敗**。要求が触れる全エンティティの作成/閲覧両側を機能化したか(Phase 1.5・Phase 6 順方向)。逆に、足した機能はどれかの要求に辿れるか・消したら成立しないか(Phase 6 逆方向・原則6の歯止め)。迷ったら足さない側へ
- **関連要求の対応** — 全機能に `関連要求` を添え、双方向カバレッジを検算したか(Phase 6)

## 出力後にユーザーに確認すること

生成したら**論点が大きい点に絞って**確認する(全部を一度に聞かない):

- Phase 5 でピックアップしなかった機能の選定に違和感がないか
- Phase 1.5 由来で補った前提機能の足し方が妥当か・過不足はないか
- 主要却下案の選び方が妥当か(本来残すべき案が消えていないか)
- 評価軸が案件にマッチしているか(選定結果を見て改めて違和感がないか)
- 後続(impact-analysis)に渡したい論点・前提機能の欠落が `6.` に書かれているか
