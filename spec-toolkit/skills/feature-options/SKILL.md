# feature-options

要求仕様書(request-spec の成果物)を入力にとり、ユーザー目線で機能をどう実現するかの選択肢を洗い出し、評価して選定し、機能設計書としてまとめるスキル。

## このスキルが置かれている設計フロー

```
[1] 要求仕様書 (request-spec)
       ↓
[2] 機能選択肢の洗い出し・選定 (このスキル: feature-options)
       ↓
[3] 影響分析 (impact-analysis)
       ↓
[4] 実装設計 (implementation-design)
```

このスキルが解く問題は「ユーザーから見て機能がどう振る舞うか」を確定させること。後続フェーズの存在は、このスキルの「やらないこと」を強く規定する:

- **[3] 影響分析** がコードベース上の変更箇所・依存関係の事実を集める → このスキルでは特定ファイル・モジュールの指定・命名はしない
- **[4] 実装設計** が技術選定・データ構造・アーキテクチャ・フェーズ分割を行う → このスキルではライブラリ・テーブル設計・実装手順に踏み込まない

つまりこのスキルは「**要求から、ユーザー目線で機能の振る舞いだけを確定する**」のが仕事。「どこをどう実装するか」は意図的に棚上げにし、後続スキルが「より良い実装方法」を選ぶ余地を残す。

## 入力の前提

- **入力**: request-spec が生成した要求仕様書(`docs/plans/<機能名>/request-spec.md` 等)
- 要求仕様書には各要求に `[決定] | [方向性] | [要検討]` の具体度ラベルが付いている。**このスキルは全ての要求を対象とする**(後述の原則1)
- 要求仕様書が見当たらない、または要求一覧が欠けている場合は、まず request-spec を実施するようユーザーに案内する

## 中核となる原則

### 原則1: [決定] にも別案を必ず探る

ユーザー指示にあったように「具体的な変更点が指定されていても、より良い選択肢がないかを模索したい」状況が常にある。よってこのスキルは:

- **[決定]** ラベルの要求 → ステークホルダーの指定を「ベースライン案」として扱い、それを脅かす別案が成立するなら主要却下案として記録する。別案が見当たらなければ「別案検討: 該当なし」と明記する(検討した痕跡を残すこと自体に意味がある)
- **[方向性]** **[要検討]** ラベルの要求 → 真っ白から複数案を出し、選定する

[決定] を素通しすると、このスキルを差し込む意味の半分が失われる。ベースライン案の指定はあくまで「現時点での参照点」と捉え、別案探索の出発点として活用する。

### 原則2: ユーザー目線に留まり、実装目線に踏み出さない

このスキルが答えるべき問い:

- 何が見える / 何が押せる / 何が起こる (画面要素)
- ユーザーは何をどの順で操作するか (操作フロー)
- どんな状態がありえて、それぞれユーザーには何が見えるか (状態の見え方)
- 既存のどの動線・画面と接続するか (現状機能との接合点)

このスキルが答えてはいけない問い:

- どんなテーブル・APIで実現するか
- どのファイル・コンポーネントを作る/触るか
- どのライブラリを使うか
- どんな順序で実装するか

判定の助け: 書こうとしている記述から「ユーザーには見えない情報」(DB列名・API名・ファイルパス・実装言語)を取り除いて、それでも機能の振る舞いとして読めるか? 読めなければ実装目線に踏み出している。

例外: 要求仕様書に「Microsoft Entra IDを使う」のように制約として書かれている技術指定は、ユーザー視点の前提条件として参照してよい(独自に技術選定を新規追加してはいけない)。

### 原則3: 出力は「選定案＋主要却下案」に絞る

要求ごとに残すのは次の3点だけ:

1. **選定案**: ユーザー操作フロー + 画面要素 + 採用理由
2. **主要却下案** (最大3つ): どんな案で、なぜ採用しなかったか
3. **確認ポイント** (あれば): ユーザー判断が必要な未決点

検討の途中で出た雑多な案・短命なバリエーション・明らかに弱い案は **出力に残さない**。理由: 後続スキルの読み手にとって、ノイズが多いと「結局この機能は何になったのか」が読みにくくなる。検討プロセスではなく結論+主要分岐点を残す。

「却下案ゼロ」は基本的に怪しい。1案しか思い浮かばないなら、対立軸を意識して別案を発想する(後述の評価軸が手がかりになる)。最終的に却下案を絞り込んだ結果ゼロになる場合だけ「該当なし」と明記する。

### 原則4: 評価軸は「テンプレ＋案件固有」で軸の質を担保する

選択肢の比較は印象論ではなく、軸に基づいて行う。共通の物差しとして次のテンプレ軸を **常に意識する**:

- **ユーザー価値**: 目的(要求のWhy)をどれだけ満たすか
- **学習コスト**: ユーザーがその振る舞いを理解・習得しやすいか
- **標準/類似サービスとの揃え**: 既存の慣習・他サービスでの一般的な振る舞いに沿うか
- **拡張性**: 後で要求が増えたとき、その案は壊れにくいか
- **変更の不可逆性**: 一度提供したら後戻りが難しくならないか

加えて、案件特有に重要な軸があれば追加する(例: アクセシビリティ要件が強い案件なら「支援技術対応」、運用負荷を重視するなら「運用負担」)。

軸はあくまで「考えるための足場」。出力に評価マトリクスを必ず載せる必要はないが、選定案の採用理由・却下案の却下理由は **このうちのどの軸で勝ち負けがついたか** を読者が推察できる粒度で書く。

### 原則5: 既存実装の調査は「現状のUI/UX・機能仕様の把握」に限定する

調査が必要な場面:

- 新機能が既存機能と接続する箇所(ヘッダー、ナビゲーション、商品詳細画面等)で、現状のレイアウト・動線を知る必要があるとき
- 似た既存機能のUI/UXパターンを参考に揃えるべきか判断するとき
- 「現状はどう振る舞っているか」を変更案と対比する必要があるとき

調査でやらないこと:

- ファイル名・関数名・コンポーネント名を取得して機能設計に組み込む(impact-analysisの仕事)
- データ構造・API契約を調べて設計案に組み込む(implementation-designの仕事)
- 実装上の制約事項の洗い出し(impact-analysisの仕事)

調査の出力は機能設計書の前提条件・現状把握セクションにだけ反映し、選定案の本文では「画面の挙動」として記述する(例: ✗「ProductCard.tsx に handleFavorite を追加」/ ◯「商品カードの右上にお気に入りトグルを追加」)。

## 進め方 (ハイブリッド対話モード)

このスキルは「ドラフトを先に出して全体感を共有 → 論点が大きい要求だけ深掘り対話」というハイブリッド型で進める。要求が10件あっても全てを対話で詰めるのではなく、判断が分かれそうな箇所だけ立ち止まる。

### Phase 1: 入力の受領と俯瞰

1. 入力(要求仕様書のパス)を受け取る。指定が無ければユーザーに確認する
2. 要求仕様書を読み込み、要求一覧と各ラベル(`[決定] / [方向性] / [要検討]`)を把握する
3. 出力先パスを決定する: 要求仕様書と同じディレクトリの `feature-options.md`
   - 例: 入力が `docs/plans/favorite-products/request-spec.md` → 出力は `docs/plans/favorite-products/feature-options.md`
4. 既に `feature-options.md` が存在する場合はユーザーに上書きしてよいか確認する

### Phase 2: 現状把握(必要に応じて)

要求の中身を見て、現状のUI/UX・機能仕様を把握する価値がある要求があるかを判定する。判定基準:

- 既存画面・既存機能との接続が明示されている → 把握する価値あり
- 完全新規の独立機能で、既存動線との接合がない → 把握不要
- 「既存の通知機能を…」「商品詳細画面に…」のように既存名称が出てくる → 該当箇所を把握

把握する対象は「ユーザーが見える振る舞い」に限定する。コードの細部・データ構造には踏み込まない(原則5)。把握結果は機能設計書の `現状把握` セクションに簡潔にまとめる。

### Phase 3: 全要求のドラフト作成

要求仕様書の各要求について、頭の中で次のプロセスを通す:

1. **複数案を発想**: ユーザー価値・学習コスト・既存慣習・拡張性・不可逆性の各軸から、対立軸が見える案を3つ程度出す
   - [決定] ラベルの場合: ベースライン案(=指定された案) + その指定を脅かす別案を1〜2つ
   - [方向性] [要検討] の場合: 真っ白から3案程度
2. **選定**: テンプレ軸＋案件固有軸で比較し、選定案を1つに絞る
3. **却下案の整理**: 出した案のうち、選定案に対する主要な対立軸を代表する案だけ却下案として残す(最大3つ目安)
4. **確認ポイントの抽出**: ユーザー判断を仰ぎたい部分があれば書き出す

ここまでをドラフトとして一度ファイルに書き出す。**この段階で対話に入らず、まずドラフトを完成させる**。

ドラフト作成時の細かい注意:

- 操作フローは番号付きで2〜6ステップ程度に。1ステップが長すぎると本当の操作が見えなくなる
- 画面要素と状態のバリエーションは書き分ける:
  - **画面要素**は静的な配置(どの画面のどこに何が常に置かれているか・ユーザーが操作できるものは何か)を書く。視覚的なレイアウト指定(色・サイズ・余白)はしない
  - **状態のバリエーション**は動的な見え方(ローディング・空・エラー・成功などで、同じ画面要素がどう変化するか)を書く
  - 同じ情報を両方に書かない。状態で変わるものは「状態のバリエーション」側に寄せる
- **画面が複数登場する要求では、主要な接点(2〜3画面)に重点を置く**。それ以外の画面は「接続点があること」だけ言及し、要素の網羅列挙はしない。全画面を機械的に埋めると分量が膨らみ、本当に重要な接点が埋もれる
- 却下案は「主要な対立軸を代表する案」だけ残す。**2案で十分なら2案で止める。無理に3案目をひねり出さない**。3案目が「対立軸として弱い」「他案の劣化版」になるなら、原則3の趣旨(ノイズを減らす)に反する
- **実装フェーズへの送り(「具体方式は実装フェーズで詰める」等)は本文中の括弧書きで散らさず、`6. 後続フェーズへの引き継ぎ` セクションに集約する**。本文に注釈が頻出すると読みづらく、また「ユーザー目線で何が確定したか」がぼやける

### Phase 4: 論点深掘りの対話

ドラフトができたら、論点が大きい要求のみピックアップして対話する。ピックアップ基準:

- **A.** 確認ポイントが書かれている要求(ユーザー判断が必要)
- **B.** 選定案と却下案の差が小さく、選定の根拠がユーザーの価値観に依存しそうな要求
- **C.** [要検討] ラベルで、要求仕様書段階から判断が残っている要求

ピックアップ対象が無いか1件のみであれば、無理に複数件にしない。逆に5件以上にもしない(対話が間延びする)。最大3件程度を上限の目安にする。

対話の進め方:

1. ピックアップした要求について、選定案と主要却下案を簡潔に提示し、選定の論点(どの軸でどの案が勝ったか)を説明する
2. `AskUserQuestion` で確認する。形式の例:
   - 「<要求名>: 選定案Xでよいか、別案Yに切り替えるか、もしくは混合案にするか」
3. ユーザーの判断を受けて、該当要求の選定案を確定する。他の要求にも波及する判断(ナビゲーション全体の方針など)があれば、関連要求も合わせて更新する

ピックアップしなかった要求は、ドラフトの選定をそのまま採用する。一括レビューでの差し戻しは Phase 6 で受ける。

### Phase 5: 横断的整合性の整理

複数の要求にまたがる整合性をチェックし、必要に応じて `横断的な機能設計上の決定` セクションに集約する。チェック対象の例:

- 複数の要求でナビゲーション/動線に触れている → 全体として矛盾しないか
- 同じ画面要素を複数の要求が触る → 順序・優先度に一貫性があるか
- 通知・状態表示などのパターンが要求横断で揃っているか
- 既存機能とのデザイン/動作の整合がとれているか

不整合があれば、ユーザーに報告して修正方針を相談する。

### Phase 6: 出力とユーザー確認

完成した機能設計書をファイルに保存し、要点を提示してユーザーに確認を求める:

- 対象とした要求の件数と選定案の見出し一覧
- 主要な却下案で「これは意外と捨てがたかった」ものがあれば1〜2件強調
- 残っている確認ポイント

ユーザーから修正指示が来た場合は該当箇所を更新し、再度確認を求める。

## 成果物のフォーマット

機能設計書は次のセクションで構成する。**セクション順序とフィールド名は維持する**(後続の影響分析がこの構造を前提に動く)。

```markdown
# 機能設計書: <機能名>

## 1. 概要

- **対象要求仕様書**: <要求仕様書のパス>
- **対象範囲**: <この機能設計書で扱う要求IDのリスト>
- **対象外**: <要求仕様書にあるが、このスキルでは扱わない要求があればその旨と理由>

## 2. 現状把握

<既存機能・既存UI/UXのうち、本機能設計に関わる部分の要旨。なければ「該当なし」>

## 3. 評価軸

<本機能設計で重視する評価軸。共通軸+案件固有軸>

- **ユーザー価値**: <この機能設計でのこの軸の意味合いを1行>
- **学習コスト**: ...
- **標準/類似サービスとの揃え**: ...
- **拡張性**: ...
- **変更の不可逆性**: ...
- (案件固有軸があれば追加)

## 4. 機能設計

### 4.1 R1 <要求の名前> (具体度: [決定/方向性/要検討])

**ゴール**: <要求のWhat/Whyを1〜2行に圧縮>

#### 選定案: <案の名前>

**ユーザー操作フロー**:
1. ...
2. ...

**画面要素** (静的な配置のみ。主要な接点 2〜3画面に重点):
- <画面X>: <要素A>, <要素B>, <ユーザー操作可能なもの>
- <画面Y>: ...

**状態のバリエーション** (動的な見え方。該当するものだけ):
- ローディング中: ...
- 空: ...
- エラー: ...
- 成功: ...

**採用理由**:
- <どの評価軸でどの案より優位か>

#### 主要却下案

- **案A: <名前>** — <案の概要> / 却下理由: <どの評価軸で劣ったか>
- **案B: <名前>** — <案の概要> / 却下理由: ...

#### 確認ポイント (あれば)

- <ユーザー判断が必要な未決点>

(要求の数だけ繰り返す)

## 5. 横断的な機能設計上の決定

<複数要求にまたがる方針。なければ「該当なし」>

## 6. 後続フェーズへの引き継ぎ

<次フェーズ(impact-analysis)で扱ってほしい論点や、機能設計の確定により新たに浮上した検討事項>
```

セクションの省略可否:

- **省略しない。全セクションを必ず置く**。該当する内容がなければ見出しの直下に「該当なし」と明記する
- 理由: 後続スキル(impact-analysis)はこの構造を前提に動く。「セクションが存在しない」と「セクションがあって該当なし」は意味が違う

## やりがちな失敗とその回避

### 失敗1: 実装目線に踏み出す

症状: 機能設計書なのに「ProductCard.tsx に handleFavorite を追加」「favorites テーブルを作成」のような記述が混じる。

回避の問い: この記述からユーザーに見えない情報(ファイル名・テーブル名・API名)を消したとき、機能の振る舞いとして読めるか? 読めないなら実装目線に出ている。

### 失敗2: [決定] 要求を素通しする

症状: 要求仕様書で [決定] になっている要求について、ベースライン案だけ記述し別案探索をしていない。

回避の問い: ベースライン案を脅かしうる対立軸は何か? その軸で勝つ別案を1つでも構想したか? 構想して却下したか、それとも構想すらしていないか?

### 失敗3: 却下案が無くなる/ノイズが増える

症状: 「却下案: 該当なし」が大量にある、または却下案を5案以上書いて読みづらい。

回避の問い: 却下案を残す目的は「主要な対立軸を読み手に示す」こと。対立軸ごとに代表案1つに絞れているか? 弱い案を惰性で書いていないか?

### 失敗4: 操作フローが長すぎて何が起こるか追えない

症状: 「ユーザー操作フロー」が10ステップ以上あり、システム内部の処理まで書かれている。

回避の問い: そのステップはユーザーが目で見て・手で操作することか? それともシステム内部の処理か? 後者なら削るか、ユーザーから見える結果に書き換える。

### 失敗5: 評価軸が形骸化する

症状: 評価軸セクションに5項目並んでいるが、各案の採用理由・却下理由を読んでもどの軸で勝負がついたか分からない。

回避の問い: 採用理由・却下理由の中で、評価軸のうちどれに触れているか? 触れていないなら、軸を抽象的に置いているだけで実用していない。

### 失敗6: 「画面要素」と「状態のバリエーション」が重複する

症状: ローディング/空/エラー/成功などが「画面要素」セクションと「状態のバリエーション」セクションの両方に書かれ、同じ情報が重複している。あるいは登場する画面を全て網羅的に列挙し、本当に重要な接点が埋もれる。

回避の問い: 「画面要素」は **常に置かれている静的なもの** だけになっているか? **状態で変化するもの** は「状態のバリエーション」側だけに書いているか? 主要な接点(2〜3画面)に重点が置かれているか?

### 失敗7: 「実装フェーズへの送り」を本文中の括弧書きで散らす

症状: 選定案の本文に「(具体方式は実装フェーズで詰める)」「(後続で決定)」のような注釈が何度も挟まり、「結局このフェーズで何が確定したのか」が読み取りにくい。

回避の問い: その注釈は `6. 後続フェーズへの引き継ぎ` セクションに集約できないか? 本文は「ユーザー視点で何が確定したか」だけを淡々と書く方が、後続スキルの読み手にも親切。

## 出力後にユーザーに確認すること

機能設計書を生成したら、次の点をユーザーに確認する(全部を一度に聞くのではなく、論点が大きい点に絞る):

- Phase 4 でピックアップしなかった要求の選定に違和感がないか
- 主要却下案の選び方が妥当か(本来残すべき案が消えていないか)
- 評価軸の選び方が案件にマッチしているか
- 後続フェーズ(impact-analysis)に渡したい論点が `6. 後続フェーズへの引き継ぎ` に書かれているか
