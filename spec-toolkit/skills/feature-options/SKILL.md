# feature-options

要求仕様書(request-spec の成果物)を入力にとり、ユーザー目線で機能をどう実現するかの選択肢を洗い出し、評価して選定し、機能設計書としてまとめるスキル。

## このスキルが置かれている設計フロー

```
[1] 要求仕様書 (request-spec)
       ↓
[2] 機能選択肢の洗い出し・選定 (このスキル: feature-options)
       ↓
[3] 影響分析 (impact-analysis)
       ↓
[4] 実装設計 (implementation-design)
```

このスキルが解く問題は「ユーザーから見て機能がどう振る舞うか」を確定させること。後続フェーズの存在は、このスキルの「やらないこと」を強く規定する:

- **[3] 影響分析** がコードベース上の変更箇所・依存関係の事実を集める → このスキルでは特定ファイル・モジュールの指定・命名はしない
- **[4] 実装設計** が技術選定・データ構造・アーキテクチャ・フェーズ分割を行う → このスキルではライブラリ・テーブル設計・実装手順に踏み込まない

つまりこのスキルは「**要求から、ユーザー目線で機能の振る舞いだけを確定する**」のが仕事。「どこをどう実装するか」は意図的に棚上げにし、後続スキルが「より良い実装方法」を選ぶ余地を残す。

## 入力の前提

- **入力**: request-spec が生成した要求仕様書(`docs/plans/<機能名>/request-spec.md` 等)
- 要求仕様書には各要求に `[決定] | [方向性] | [要検討]` の具体度ラベルが付いている。**このスキルは全ての要求を対象とする**(後述の原則1)
- 要求仕様書が見当たらない、または要求一覧が欠けている場合は、まず request-spec を実施するようユーザーに案内する

## 中核となる原則

### 原則1: [決定] にも別案を必ず探る

ユーザー指示にあったように「具体的な変更点が指定されていても、より良い選択肢がないかを模索したい」状況が常にある。よってこのスキルは:

- **[決定]** ラベルの要求 → ステークホルダーの指定を「ベースライン案」として扱い、それを脅かす別案が成立するなら主要却下案として記録する。別案が見当たらなければ「別案検討: 該当なし」と明記する(検討した痕跡を残すこと自体に意味がある)
- **[方向性]** **[要検討]** ラベルの要求 → 真っ白から複数案を出し、選定する

[決定] を素通しすると、このスキルを差し込む意味の半分が失われる。ベースライン案の指定はあくまで「現時点での参照点」と捉え、別案探索の出発点として活用する。

### 原則2: ユーザー目線に留まり、実装目線に踏み出さない

このスキルが答えるべき問い:

- 何が見える / 何が押せる / 何が起こる (画面要素)
- ユーザーは何をどの順で操作するか (操作フロー)
- どんな状態がありえて、それぞれユーザーには何が見えるか (状態の見え方)
- 既存のどの動線・画面と接続するか (現状機能との接合点)

このスキルが答えてはいけない問い:

- どんなテーブル・APIで実現するか
- どのファイル・コンポーネントを作る/触るか
- どのライブラリを使うか
- どんな順序で実装するか

判定の助け: 書こうとしている記述から「ユーザーには見えない情報」(DB列名・API名・ファイルパス・実装言語)を取り除いて、それでも機能の振る舞いとして読めるか? 読めなければ実装目線に踏み出している。

例外: 要求仕様書に「Microsoft Entra IDを使う」のように制約として書かれている技術指定は、ユーザー視点の前提条件として参照してよい(独自に技術選定を新規追加してはいけない)。

### 原則3: 出力は「選定案＋主要却下案」に絞る

機能ごとに残すのは次の3点だけ:

1. **選定案**: ユーザー操作フロー + 画面要素 + 採用理由
2. **主要却下案** (最大3つ): どんな案で、なぜ採用しなかったか
3. **確認ポイント** (あれば): ユーザー判断が必要な未決点

検討の途中で出た雑多な案・短命なバリエーション・明らかに弱い案は **出力に残さない**。理由: 後続スキルの読み手にとって、ノイズが多いと「結局この機能は何になったのか」が読みにくくなる。検討プロセスではなく結論+主要分岐点を残す。

「却下案ゼロ」は基本的に怪しい。1案しか思い浮かばないなら、対立軸を意識して別案を発想する(後述の評価軸が手がかりになる)。最終的に却下案を絞り込んだ結果ゼロになる場合だけ「該当なし」と明記する。

### 原則4: 評価軸は「テンプレ＋案件固有」で軸の質を担保する

選択肢の比較は印象論ではなく、軸に基づいて行う。共通の物差しとして次のテンプレ軸を **常に意識する**:

- **ユーザー価値**: 目的(要求のWhy)をどれだけ満たすか
- **学習コスト**: ユーザーがその振る舞いを理解・習得しやすいか
- **標準/類似サービスとの揃え**: 既存の慣習・他サービスでの一般的な振る舞いに沿うか
- **拡張性**: 後で要求が増えたとき、その案は壊れにくいか
- **変更の不可逆性**: 一度提供したら後戻りが難しくならないか

加えて、案件特有に重要な軸があれば追加する(例: アクセシビリティ要件が強い案件なら「支援技術対応」、運用負荷を重視するなら「運用負担」)。**案件固有軸には必ず「導出根拠」を添える** — 要求仕様書のどの記述・背景・Why から、なぜこの案件でその軸が重要だと判断したか。根拠を明示することで、軸の解釈が要求の意図とズレていないかを後から検証できる。

案件固有軸は、立てたら選定に入る前にユーザーへ提示して認識を合わせる(後述の Phase 3 で実施)。理由: 誤った解釈の案件固有軸は1つの要求だけでなく **全要求の選定を汚染する**。ドラフトを作ってから軸の誤りに気づくと、全選定をやり直すことになり、ドラフト前に正すよりコストが大きい。導出根拠を添えてあれば、ユーザーは「その軸はそういう意味ではない」と早期に気づける。

軸はあくまで「考えるための足場」。出力に評価マトリクスを必ず載せる必要はないが、選定案の採用理由・却下案の却下理由は **このうちのどの軸で勝ち負けがついたか** を読者が推察できる粒度で書く。

### 原則5: 既存実装の調査は「現状のUI/UX・機能仕様の把握」に限定する

調査が必要な場面:

- 新機能が既存機能と接続する箇所(ヘッダー、ナビゲーション、商品詳細画面等)で、現状のレイアウト・動線を知る必要があるとき
- 似た既存機能のUI/UXパターンを参考に揃えるべきか判断するとき
- 「現状はどう振る舞っているか」を変更案と対比する必要があるとき

調査でやらないこと:

- ファイル名・関数名・コンポーネント名を取得して機能設計に組み込む(impact-analysisの仕事)
- データ構造・API契約を調べて設計案に組み込む(implementation-designの仕事)
- 実装上の制約事項の洗い出し(impact-analysisの仕事)

調査の出力は機能設計書の前提条件・現状把握セクションにだけ反映し、選定案の本文では「画面の挙動」として記述する(例: ✗「ProductCard.tsx に handleFavorite を追加」/ ◯「商品カードの右上にお気に入りトグルを追加」)。

### 原則6: 要求ではなく「機能」を組織単位にする

要求と機能は1:1ではない。1つの機能が複数の要求を満たすこともあれば(例: 1つの「コメント投稿」機能が、記事へのコメント要求とレビューへのコメント要求の両方を満たす)、1つの要求が複数の機能に分かれることもある。さらに、要求は機能ライフサイクルの一部しか語らないことが多い — 「閲覧したい」とは言っても「閲覧対象を誰がどう作るか」までは言わない。要求を1件ずつ機能化していくと、要求が語らなかった前提機能(閲覧する対象を登録する機能、一覧に項目を追加する機能、一括登録した利用者がログインする認証)がまるごと設計から抜け、全部実装しても使えないサービスになる。

そこでこのスキルは、機能設計書の `4. 機能設計` を **要求ではなく機能の単位で組織する**。各機能には「関連要求」を添えて、どの要求(複数可)に応えるものかを示す。要求を起点に機能を探すのではなく、「これらの要求が満たされたサービスが成立するには、どんな機能が要るか」を起点に機能を洗い出す(Phase 1.5・Phase 4)。

ただし「成立に必要な機能を補う」ことと「あれば便利な機能を妄想で足す」ことは違う。歯止めの問い: その機能を消したとき、関連要求が語った機能はユーザー操作として **成立するか**? 成立しない(操作対象が存在しない・前提状態に到達できない)なら必要な機能。成立する(あれば便利なだけ)なら足さない。迷ったら足さない側を選ぶ。これは request-spec の「自然な補完か過剰な追加か」を「動作するか」に翻訳した基準。スコープやポリシーの判断を要する前提(認証方式の選定など)は、勝手に1案に決めず、確認ポイントか `6. 後続フェーズへの引き継ぎ` に回して判断をユーザーに返す。

## 進め方 (ハイブリッド対話モード)

このスキルは「ドラフトを先に出して全体感を共有 → 論点が大きい機能だけ深掘り対話」というハイブリッド型で進める。機能が10件あっても全てを対話で詰めるのではなく、判断が分かれそうな箇所だけ立ち止まる。

立ち止まりは2種類ある: (1) **評価軸の確認**(案件固有軸を立てた場合のみ、選定の前に行う / Phase 3)と、(2) **論点深掘り**(選定の後、判断が分かれそうな機能についてのみ行う / Phase 5)。前者は「選定の物差しが正しいか」、後者は「物差しを当てた結果が妥当か」を確認するもので、目的とタイミングが異なる。

機能を要求から1件ずつ起こすと、要求が語らなかった前提機能が抜ける(原則6)。これを防ぐため、機能の洗い出し(Phase 4)の前に Phase 1.5 で要求横断にエンティティとライフサイクルを棚卸しし、洗い出しの後に Phase 6 で「全要求が機能でカバーされ、全機能が要求に辿れるか」を双方向に点検する。

### Phase 1: 入力の受領と俯瞰

1. 入力(要求仕様書のパス)を受け取る。指定が無ければユーザーに確認する
2. 要求仕様書を読み込み、要求一覧と各ラベル(`[決定] / [方向性] / [要検討]`)を把握する
3. 出力先パスを決定する: 要求仕様書と同じディレクトリの `feature-options.md`
   - 例: 入力が `docs/plans/favorite-products/request-spec.md` → 出力は `docs/plans/favorite-products/feature-options.md`
4. 既に `feature-options.md` が存在する場合はユーザーに上書きしてよいか確認する

### Phase 1.5: エンティティとライフサイクルの棚卸し

機能を要求から1件ずつ起こすと「要求が語ったこと」しか設計に乗らない(原則6)。これを防ぐため、機能の洗い出し(Phase 4)に入る前に、要求横断で次を点検しておく。

1. **エンティティを列挙する**: ユーザーが操作・参照する対象オブジェクトを要求群から拾う(例: 記事、コメント、タグ、添付ファイル、ユーザー、ロール、通知)。これは「ユーザーから見て名前のつく対象」であって、テーブルやデータモデルではない(実装目線に踏み出さない)。
2. **各エンティティのライフサイクルを点検する**: そのエンティティについて「誰が・どのユーザー操作で 作成/管理 するか」「誰が 閲覧/利用 するか」が、いずれかの要求でカバーされているかを見る。閲覧側だけあって作成側がどの要求にも無ければ、そのエンティティは欠落候補。
3. **土台機能の前提を点検する**: ある要求が成立するために暗黙に必要な土台機能(例: 「CSV によるユーザー一括登録」が前提とするログイン認証)が、要求のどこにも無いかを見る。

ここで挙げた欠落候補は Phase 4 の機能洗い出しの入力になる。成立に不可欠なもの(原則6の歯止めを通るもの)は機能として設計し、スコープ/ポリシー判断が要るものは確認ポイント・引き継ぎに回す。重い論点なら Phase 3 のユーザー確認に合流させる。

なお、ここで点検するのは「機能設計に乗せるべき機能が揃っているか」というユーザー目線の話で、後続の impact-analysis が見る「設計済みの機能がコード上どこに当たるか」とは別レイヤー。前提機能をこのフェーズで顕在化しておかないと、impact-analysis には閲覧機能の影響範囲だけが渡り、登録機能の存在自体が永久に分析対象から漏れる。だからこの点検は feature-options の責務に属する。

### Phase 2: 現状把握(必要に応じて)

要求の中身を見て、現状のUI/UX・機能仕様を把握する価値がある要求があるかを判定する。判定基準:

- 既存画面・既存機能との接続が明示されている → 把握する価値あり
- 完全新規の独立機能で、既存動線との接合がない → 把握不要
- 「既存の通知機能を…」「商品詳細画面に…」のように既存名称が出てくる → 該当箇所を把握

把握する対象は「ユーザーが見える振る舞い」に限定する。コードの細部・データ構造には踏み込まない(原則5)。把握結果は機能設計書の `現状把握` セクションに簡潔にまとめる。

### Phase 3: 評価軸の策定とユーザー確認

選定に入る前に、選定の物差しとなる評価軸を確定する。評価軸が誤っていると全要求の選定が汚染されるため、案件固有軸についてはこの段階でユーザーと認識を合わせる(原則4)。

1. **評価軸を策定する**: 現状把握(Phase 2)と要求一覧を踏まえ、次の2種類を用意する。
   - **共通テンプレ軸**(ユーザー価値 / 学習コスト / 標準・類似サービスとの揃え / 拡張性 / 変更の不可逆性): この案件での意味づけを1行ずつ与える。
   - **案件固有軸**: 要求の性質から特に重要な軸があれば追加する。**各案件固有軸には必ず導出根拠を添える**(要求仕様書のどの記述・背景・Why から、なぜその軸が重要と判断したか)。
2. **案件固有軸を1つ以上立てた場合のみ、ユーザー確認フェーズを発火する**:
   - `AskUserQuestion` で、**案件固有軸(名前＋定義＋導出根拠)を主役に提示**しつつ、共通軸の「この案件での意味づけ」も一覧で軽く添える(共通軸の意味づけのズレも拾えるように)。
   - 「この評価軸の理解で機能設計・選定に進んでよいか / 修正したい軸があるか」を問う。
   - 修正指示があれば軸を直して再提示する。OK が出てから Phase 4 へ進む。
3. **案件固有軸を立てない(共通テンプレ軸だけで足りる)場合は、確認をスキップして Phase 4 へ進む**。共通軸は普遍的で解釈のブレが小さく、毎回確認すると対話が重くなるため。
4. ここで確定した評価軸は、機能設計書の `3. 評価軸` セクションにそのまま反映する(案件固有軸の導出根拠も残す)。

### Phase 4: 機能の洗い出しとドラフト作成

ここで機能設計書の本体を作る。要求を1件ずつ機能化するのではなく、2つのパスで進める(原則6)。

#### パス1: 機能の洗い出し(広さ)

「これらの要求が満たされたサービスが成立するには、どんな機能が要るか」を起点に、必要な機能を列挙する。

- 要求仕様書がテーマ別にグループ化されている場合は **グループ単位** で洗い出す(関連の強い要求がまとまっているので、そのまとまりが成立する機能群を考えやすい)。グループ化されていない/小規模なら全要求をまとめて洗い出す。
- Phase 1.5 で挙げたエンティティのライフサイクル欠落・前提機能の欠落を、ここで機能として拾う。閲覧機能と並んでその対象を登録する機能が、一覧機能と並んでそこへ項目を追加する機能が、対等に挙がるようにする。
- 各機能に **関連要求**(応える要求の ID、複数可)を紐づける。1機能が複数要求にまたがってよいし、1要求が複数機能に分かれてもよい。
- 洗い出した機能には連番の識別子(F1, F2, …)を振る。

#### パス2: 各機能の詳細化(深さ)

洗い出した機能それぞれについて、頭の中で次のプロセスを通す。**単位が要求から機能に変わるだけで、1件あたりの掘り下げ(別案探索)は落とさない**:

1. **複数案を発想**: Phase 3 で確定した評価軸(共通軸＋案件固有軸)を手がかりに、対立軸が見える案を出す
   - 関連要求に [決定] ラベルが含まれる機能: ベースライン案(=指定された案) + その指定を脅かす別案を1〜2つ(原則1)
   - [方向性] [要検討] のみに紐づく機能: 真っ白から3案程度
   - Phase 1.5 由来の前提機能で、成立に必要だが振る舞いがほぼ一意に定まるもの: 別案探索は省き、成立に必要な最小限の振る舞いだけ書く(原則6。ここで複数案を演じると、足したこと自体が目立ちノイズになる)
2. **選定**: Phase 3 で確定した評価軸で比較し、選定案を1つに絞る(ここで評価軸を新たに作らない。確定済みの軸を使う)
3. **却下案の整理**: 出した案のうち、選定案に対する主要な対立軸を代表する案だけ却下案として残す(最大3つ目安)
4. **確認ポイントの抽出**: ユーザー判断を仰ぎたい部分があれば書き出す

ここまでをドラフトとして一度ファイルに書き出す。**この段階で(評価軸以外の)対話に入らず、まずドラフトを完成させる**。

ドラフト作成時の細かい注意:

- 操作フローは番号付きで2〜6ステップ程度に。1ステップが長すぎると本当の操作が見えなくなる
- 画面要素と状態のバリエーションは書き分ける:
  - **画面要素**は静的な配置(どの画面のどこに何が常に置かれているか・ユーザーが操作できるものは何か)を書く。視覚的なレイアウト指定(色・サイズ・余白)はしない
  - **状態のバリエーション**は動的な見え方(ローディング・空・エラー・成功などで、同じ画面要素がどう変化するか)を書く
  - 同じ情報を両方に書かない。状態で変わるものは「状態のバリエーション」側に寄せる
- **画面が複数登場する機能では、主要な接点(2〜3画面)に重点を置く**。それ以外の画面は「接続点があること」だけ言及し、要素の網羅列挙はしない。全画面を機械的に埋めると分量が膨らみ、本当に重要な接点が埋もれる
- 却下案は「主要な対立軸を代表する案」だけ残す。**2案で十分なら2案で止める。無理に3案目をひねり出さない**。3案目が「対立軸として弱い」「他案の劣化版」になるなら、原則3の趣旨(ノイズを減らす)に反する
- **実装フェーズへの送り(「具体方式は実装フェーズで詰める」等)は本文中の括弧書きで散らさず、`6. 後続フェーズへの引き継ぎ` セクションに集約する**。本文に注釈が頻出すると読みづらく、また「ユーザー目線で何が確定したか」がぼやける

### Phase 5: 論点深掘りの対話

ドラフトができたら、論点が大きい機能のみピックアップして対話する。これは Phase 3 の評価軸確認とは別物 — 評価軸確認が「選定の物差しが正しいか」を選定**前**に問うのに対し、ここでは「物差しを当てた結果(選定)が妥当か」を選定**後**に問う。ピックアップ基準:

- **A.** 確認ポイントが書かれている機能(ユーザー判断が必要)
- **B.** 選定案と却下案の差が小さく、選定の根拠がユーザーの価値観に依存しそうな機能
- **C.** 関連要求に [要検討] ラベルがあり、要求仕様書段階から判断が残っている機能
- **D.** Phase 1.5 由来の前提機能で、足すこと自体や範囲にユーザー判断が要るもの

ピックアップ対象が無いか1件のみであれば、無理に複数件にしない。逆に5件以上にもしない(対話が間延びする)。最大3件程度を上限の目安にする。

対話の進め方:

1. ピックアップした機能について、選定案と主要却下案を簡潔に提示し、選定の論点(どの軸でどの案が勝ったか)を説明する
2. `AskUserQuestion` で確認する。形式の例:
   - 「<機能名>: 選定案Xでよいか、別案Yに切り替えるか、もしくは混合案にするか」
3. ユーザーの判断を受けて、該当機能の選定案を確定する。他の機能にも波及する判断(ナビゲーション全体の方針など)があれば、関連する機能も合わせて更新する

ピックアップしなかった機能は、ドラフトの選定をそのまま採用する。一括レビューでの差し戻しは Phase 7 で受ける。

### Phase 6: 横断的整合性とカバレッジの点検

複数の機能にまたがる整合性をチェックし、必要に応じて `横断的な機能設計上の決定` セクションに集約する。チェック対象の例:

- 複数の機能でナビゲーション/動線に触れている → 全体として矛盾しないか
- 同じ画面要素を複数の機能が触る → 順序・優先度に一貫性があるか
- 通知・状態表示などのパターンが機能横断で揃っているか
- 既存機能とのデザイン/動作の整合がとれているか

不整合があれば、ユーザーに報告して修正方針を相談する。

加えて、機能ベースで設計したことで生じる「要求の取りこぼし」と「機能の過剰」を、双方向のカバレッジで点検する(原則6を機械的に検算する工程)。

- **順方向(取りこぼし検出)**: 要求仕様書の全要求が、最低1つの機能の `関連要求` に現れるか。さらに、各要求の意図が機能群で満たされているか — 特に Phase 1.5 で挙げたライフサイクル(その要求が触れるエンティティの作成/管理側)が機能に反映されているか。どの機能の関連要求にも現れない要求、または閲覧側しか機能化されていない要求は「薄まって漏れた」候補。機能を足すか、確認ポイント/引き継ぎに回す。
- **逆方向(過剰検出)**: すべての機能が最低1つの要求に辿れるか。どの要求にも紐づかない機能は、原則6の歯止め(消したら成立しないか)を通っているか改めて確かめる。通らないなら妄想機能として落とす。
- スコープ/ポリシー判断を要する前提機能の欠落(認証方式など)が、確認ポイントか `6. 後続フェーズへの引き継ぎ` の「前提機能の欠落」に記録されているか。

### Phase 7: 出力とユーザー確認

完成した機能設計書をファイルに保存し、要点を提示してユーザーに確認を求める:

- 洗い出した機能の件数と選定案の見出し一覧(各機能の関連要求も)
- Phase 1.5 で拾った前提機能・補った機能があれば、それを明示(要求に書かれていなかったが成立に必要として足したもの)
- 主要な却下案で「これは意外と捨てがたかった」ものがあれば1〜2件強調
- 残っている確認ポイント・前提機能の欠落

ユーザーから修正指示が来た場合は該当箇所を更新し、再度確認を求める。

## 成果物のフォーマット

機能設計書は次のセクションで構成する。**セクション順序とフィールド名は維持する**(後続の影響分析がこの構造を前提に動く)。

```markdown
# 機能設計書: <機能名>

## 1. 概要

- **対象要求仕様書**: <要求仕様書のパス>
- **対象範囲**: <この機能設計書で扱う要求IDのリスト>
- **対象外**: <要求仕様書にあるが、このスキルでは扱わない要求があればその旨と理由>
- **要求カバレッジ**: <全要求がいずれかの機能でカバーされているかの確認(例: R1〜R5 をすべてカバー)。機能↔要求の完全な対応は §4 各機能の `関連要求` を正とし、ここで繰り返さない>
- **1:1でない箇所**: <要求と機能が1:1にならない箇所だけを挙げる。1機能が複数要求にまたがる箇所、要求に書かれず補った前提機能(例: F2 項目の登録)。なければ「すべて1:1」>

## 2. 現状把握

<既存機能・既存UI/UXのうち、本機能設計に関わる部分の要旨。なければ「該当なし」>

## 3. 評価軸

<本機能設計で重視する評価軸。共通軸+案件固有軸>

- **ユーザー価値**: <この機能設計でのこの軸の意味合いを1行>
- **学習コスト**: ...
- **標準/類似サービスとの揃え**: ...
- **拡張性**: ...
- **変更の不可逆性**: ...
- (案件固有軸があれば追加。定義に加えて「根拠: 要求仕様書のどこ/背景から」を添える)

## 4. 機能設計

### F1 <機能名>

- **関連要求**: R1, R2 (応える要求のID。複数可。要求が語っていなかった前提機能の場合は「(前提機能) Rn を成立させるため」のように添える)
- **ゴール**: <この機能で何が達成されるかを1〜2行に圧縮>

#### 選定案: <案の名前>

**ユーザー操作フロー**:
1. ...
2. ...

**画面要素** (静的な配置のみ。主要な接点 2〜3画面に重点):
- <画面X>: <要素A>, <要素B>, <ユーザー操作可能なもの>
- <画面Y>: ...

**状態のバリエーション** (動的な見え方。該当するものだけ):
- ローディング中: ...
- 空: ...
- エラー: ...
- 成功: ...

**採用理由**:
- <どの評価軸でどの案より優位か>

#### 主要却下案

- **案A: <名前>** — <案の概要> / 却下理由: <どの評価軸で劣ったか>
- **案B: <名前>** — <案の概要> / 却下理由: ...

#### 確認ポイント (あれば)

- <ユーザー判断が必要な未決点>

(機能の数だけ繰り返す。F1, F2, … と連番。前提機能で振る舞いがほぼ一意なものは選定案のみを浅く書き、主要却下案は省略してよい)

## 5. 横断的な機能設計上の決定

<複数の機能にまたがる方針(通知パターンの統一など)。なければ「該当なし」>

## 6. 後続フェーズへの引き継ぎ

<次フェーズ(impact-analysis)で扱ってほしい論点や、機能設計の確定により新たに浮上した検討事項>

### 前提機能の欠落 (あれば)

<要求群が暗黙に前提しているが、スコープ/ポリシー判断が必要で本スキルでは設計しなかった土台機能。例: 「CSV一括登録した利用者がログインする認証機能」。なぜ設計を保留したか(どの判断が要るか)を1行添える>
```

セクションの省略可否:

- **省略しない。全セクションを必ず置く**。該当する内容がなければ見出しの直下に「該当なし」と明記する
- 理由: 後続スキル(impact-analysis)はこの構造を前提に動く。「セクションが存在しない」と「セクションがあって該当なし」は意味が違う
- `4. 機能設計` は機能(F1, F2, …)単位で組織し、各機能に `関連要求` を必ず添える。impact-analysis はこの構造を舐めて全機能を拾い、`関連要求` から要求との対応を辿る

## やりがちな失敗とその回避

### 失敗1: 実装目線に踏み出す

症状: 機能設計書なのに「ProductCard.tsx に handleFavorite を追加」「favorites テーブルを作成」のような記述が混じる。

回避の問い: この記述からユーザーに見えない情報(ファイル名・テーブル名・API名)を消したとき、機能の振る舞いとして読めるか? 読めないなら実装目線に出ている。

### 失敗2: [決定] 要求を素通しする

症状: 要求仕様書で [決定] になっている要求について、ベースライン案だけ記述し別案探索をしていない。

回避の問い: ベースライン案を脅かしうる対立軸は何か? その軸で勝つ別案を1つでも構想したか? 構想して却下したか、それとも構想すらしていないか?

### 失敗3: 却下案が無くなる/ノイズが増える

症状: 「却下案: 該当なし」が大量にある、または却下案を5案以上書いて読みづらい。

回避の問い: 却下案を残す目的は「主要な対立軸を読み手に示す」こと。対立軸ごとに代表案1つに絞れているか? 弱い案を惰性で書いていないか?

### 失敗4: 操作フローが長すぎて何が起こるか追えない

症状: 「ユーザー操作フロー」が10ステップ以上あり、システム内部の処理まで書かれている。

回避の問い: そのステップはユーザーが目で見て・手で操作することか? それともシステム内部の処理か? 後者なら削るか、ユーザーから見える結果に書き換える。

### 失敗5: 評価軸が形骸化する

症状: 評価軸セクションに5項目並んでいるが、各案の採用理由・却下理由を読んでもどの軸で勝負がついたか分からない。

回避の問い: 採用理由・却下理由の中で、評価軸のうちどれに触れているか? 触れていないなら、軸を抽象的に置いているだけで実用していない。

### 失敗6: 「画面要素」と「状態のバリエーション」が重複する

症状: ローディング/空/エラー/成功などが「画面要素」セクションと「状態のバリエーション」セクションの両方に書かれ、同じ情報が重複している。あるいは登場する画面を全て網羅的に列挙し、本当に重要な接点が埋もれる。

回避の問い: 「画面要素」は **常に置かれている静的なもの** だけになっているか? **状態で変化するもの** は「状態のバリエーション」側だけに書いているか? 主要な接点(2〜3画面)に重点が置かれているか?

### 失敗7: 「実装フェーズへの送り」を本文中の括弧書きで散らす

症状: 選定案の本文に「(具体方式は実装フェーズで詰める)」「(後続で決定)」のような注釈が何度も挟まり、「結局このフェーズで何が確定したのか」が読み取りにくい。

回避の問い: その注釈は `6. 後続フェーズへの引き継ぎ` セクションに集約できないか? 本文は「ユーザー視点で何が確定したか」だけを淡々と書く方が、後続スキルの読み手にも親切。

### 失敗8: 案件固有軸を独自解釈で立て、確認せず選定に使う

症状: 要求仕様書の意図とズレた解釈で案件固有軸を立て(例: 要求では触れていない観点を「重要そうだから」と軸にする)、ユーザー確認を経ずにその軸で全要求を評価・選定してしまう。誤りに気づくのが最終確認まで遅れ、選定全体が汚染される。

回避の問い: その案件固有軸は要求仕様書のどの記述・背景・Why から導出したか(導出根拠を言語化できるか)? 案件固有軸を立てたなら、選定に入る前(Phase 3)にユーザーへ提示して認識を合わせたか?

### 失敗9: 要求と1:1の機能しか設計せず、サービスとして成立しない

症状: 要求を1件ずつ機能化した結果、閲覧・消費・登録など要求が語った断片だけが設計され、それを成立させる前提機能が抜ける。「お気に入り一覧の閲覧」は設計されたがお気に入りに登録する機能が無い、「タグでの絞り込み」は設計されたがタグを付与する機能が無い、といった状態。要求一覧との照合では一見すべて埋まっているように見えるため気づきにくい。

回避の問い: 要求が触れているエンティティ(ユーザーが操作する対象)を要求横断で列挙したか(Phase 1.5)? 各エンティティについて「作成/管理」「閲覧/利用」の両側が機能でカバーされているか? Phase 6 の順方向カバレッジ(全要求の意図が機能群で満たされているか)を確かめたか?

### 失敗10: 前提機能を妄想で膨らませる/勝手に決める

症状: 前提機能の欠落を拾おうとするあまり、「あると便利」「いずれ要る」程度の機能まで足し、要求に無い機能が大量に増える。あるいはスコープ判断が要る前提(認証方式など)を勝手に1案に決めて設計してしまう。

回避の問い: その機能を消したとき、関連要求が語った機能はユーザー操作として本当に成立しないか(成立するなら足さない)? その前提機能の中身に複数の選択肢があり、どれを選ぶかでユーザー体験が変わるか(変わるなら設計せず確認ポイント/引き継ぎへ回す)? 逆方向カバレッジで、その機能はどれかの要求に辿れるか? 迷ったら足さない側を選んだか?

## 出力後にユーザーに確認すること

機能設計書を生成したら、次の点をユーザーに確認する(全部を一度に聞くのではなく、論点が大きい点に絞る):

- Phase 5 でピックアップしなかった機能の選定に違和感がないか
- Phase 1.5 由来で補った前提機能(要求に書かれていなかったもの)の足し方が妥当か。過不足はないか
- 主要却下案の選び方が妥当か(本来残すべき案が消えていないか)
- 評価軸が案件にマッチしているか(案件固有軸は Phase 3 で確認済みだが、選定結果を見て改めて違和感がないか)
- 後続フェーズ(impact-analysis)に渡したい論点・前提機能の欠落が `6. 後続フェーズへの引き継ぎ` に書かれているか
