# implementation-design

影響分析書(impact-analysis の成果物)の **設計バッチ単位** で、実装に入る前に必要な詳細設計を確定するスキル。

## このスキルが置かれている設計フロー

```
[1] 要求仕様書 (request-spec)
       ↓
[2] 機能設計書 (feature-options)
       ↓
[3] 影響分析書 (impact-analysis)
       ↓
[4] 実装設計書 (このスキル: implementation-design)
       ↓
   実装フェーズ (TDD)
```

このスキルが解く問題は **「設計バッチ単位で、実装に入れる粒度まで設計を確定する」** こと。前段(impact-analysis)が「何を・どの順で設計するか」を整理しているので、本スキルは **設計バッチに含まれるトピックの設計を1パスで完了させる** のが役割。

## 入力の前提

- **主入力**: impact-analysis が生成した影響分析書 (`docs/plans/<機能名>/impact-analysis.md`)
- **補助参照**: 機能設計書・要求仕様書 (同ディレクトリ)
- **対象範囲**: 影響分析書の `4.1 設計バッチ` に列挙されたバッチのうち、**1スキル実行につき1バッチ** だけを対象とする

影響分析書が見当たらない、または `4.1 設計バッチ` セクションが欠けている場合は、まず impact-analysis を実施するようユーザーに案内する。

## 中核となる設計

### 2段階フロー: 骨格 → 詳細

このスキルは設計を **骨格設計フェーズ** と **詳細設計+実装計画フェーズ** の2段階で進める。

- **骨格設計フェーズ**: 主要な意思決定・概念モデル・責務構造・トピック別方針を確定する。詳細(具体的なシグネチャ・列定義)は決めない
- **詳細設計+実装計画フェーズ**: 骨格を確定させた状態で、データ構造・APIインタフェース・主要動作フロー・エラー方針・TDDフェーズ計画を埋める

なぜ2段階か:

- 構造的な論点(主要意思決定・概念境界)は詳細設計より前に固める必要がある。詳細を書いた後に構造を変えると、詳細の全体を書き直すことになる
- 骨格段階でユーザーが介在することで、構造ごと作り直しの場合の手戻りを最小化できる
- 批評の入る場所も骨格に絞れる(批評が詳細に踏み込むと統合判断が破綻するため)

### 主設計者 + 批評役の構成

骨格設計は次の3エージェント協調で生成する:

- **greenfield-architect (主設計者)**: 既存実装や移行コストを考慮せず、要件を満たす最もシンプルな骨格を提案
- **brownfield-architect (批評役)**: greenfield骨格に対して、既存パターン整合・移行コスト・障害リスク・段階導入観点で批評
- **domain-first-architect (批評役)**: greenfield骨格に対して、概念境界・不変条件集中・用語一貫性・概念数の必要十分性観点で批評

批評役は **独立した代替設計案は出さない**。代替案を出すと本体スキルが「採用 vs 却下」の二者択一を迫られ、両者の良さを統合しにくい。批評として骨格への局所修正提案を出すことで、本体スキルが選択的に取り込める。

詳細設計+実装計画は greenfield-architect 単独で生成する。骨格段階で構造的論点は確定済みのため、詳細フェーズで批評を入れる必要がない。

## 中核となる原則

### 原則1: 1スキル実行 = 1設計バッチ

影響分析書に複数の設計バッチがある場合、ユーザーに対象バッチを選ばせる。複数バッチを並列に扱おうとすると、設計判断が浅くなる・成果物が肥大化する・ユーザー確認が混乱する、のいずれかが発生する。

バッチが1つしかない場合はユーザー選択をスキップして自動で対象にする。

### 原則2: 詳細レベルは「契約レベル」で止める

詳細設計セクション(3.x)に書くもの:

- データ構造 / DB スキーマ: 列名・型・制約・インデックス
- API / 関数インタフェース: シグネチャ・リクエスト/レスポンス形・主要エラー
- 主要動作フロー: 入力 → 処理 → 出力の5ステップ以内
- エラーハンドリング: 条件と対応方針

書かない:

- 実装本体のコード
- 内部アルゴリズムの擬似コード
- 呼び出し例

理由: 実装設計書は **実装フェーズで設計に立ち戻らずに済む契約レベル** を満たす情報のためにある。これを越えると (1) 文書量が肥大化して必要情報が探しにくくなる、(2) 読み手が設計レビューだけでなくコードレビューを要求される、(3) 実装の自由度が不当に縮む。

### 原則3: 批評の採否はユーザーに口頭で報告し、文書に残さない

批評役からの指摘とその採否(採用した / 採用しなかった / 部分採用)は、Phase 2 でユーザーに口頭で報告する。**実装設計書本文には残さない**。設計判断のトレーサビリティは大事だが、実装設計書は実装フェーズの読み物であり、検討プロセスを残すと信号が薄れる。

### 原則4: agent委譲を基本にし、ユーザー確認は各フェーズの末尾だけ

このスキルは agent への委譲を基本とし、ユーザーが介在するのは Phase 2 末尾と Phase 3 末尾の2回。各フェーズ内部での判断は agent に任せる。「全箇所で確認」「全選択肢を提示」は意図的にしない。前段の impact-analysis が論点を整理済みなので、設計判断の大半は agent に委ねられる。

## 進め方

### Phase 1: 入力受領と対象バッチの確定

1. 入力(影響分析書のパス)を受け取る。指定が無ければユーザーに確認する
2. 影響分析書を読み込み、`4.1 設計バッチ` を把握する
3. 対象バッチを確定する:
   - バッチが1つしかない → そのバッチを自動で対象にする
   - バッチが複数 → `AskUserQuestion` でユーザーに選ばせる
4. 対象バッチに含まれる設計トピック (`T<n>`) を `3. 設計トピック` から抽出する
5. 補助参照として機能設計書・要求仕様書を読み込む(同ディレクトリにあれば)
6. 出力先パスを決定する: `<dir>/implementation-design-<バッチスラッグ>.md`
   - 例: バッチ名「お気に入りデータ永続化」 → スラッグ `favorite-persistence` → ファイル `implementation-design-favorite-persistence.md`
   - スラッグはバッチ名から英数字・ハイフン中心に簡潔に作る (日本語をそのままファイル名に使わない)
7. 既にファイルが存在する場合はユーザーに上書きしてよいか確認する

### Phase 2: 骨格設計

#### 2.1 主設計の生成 (greenfield-architect)

`greenfield-architect` に骨格設計を依頼する。依頼内容:

- **フェーズ指示**: 「骨格設計フェーズ」と明示
- **対象設計バッチ**: バッチID・名前・含まれるトピックID
- **影響分析書**: 全文 (バッチ範囲を明示しつつ、他バッチの文脈も参照可能にする)
- **要求仕様書 / 機能設計書**: ドメイン語彙の参照源として渡す
- **期待する出力**: 骨格設計セクション (2.1〜2.4) のみ。詳細設計や実装計画は含めない

#### 2.2 批評の取得 (並列)

greenfield-architect の骨格が返ってきたら、`brownfield-architect` と `domain-first-architect` を **並列に** 起動する。

各エージェントへの依頼内容:

- **対象設計バッチ**: 同上
- **影響分析書**: 同上
- **要求仕様書 / 機能設計書**: 同上 (特に domain-first-architect には必須)
- **greenfield骨格**: 2.1 で得られた骨格セクション (2.1〜2.4)
- **期待する出力**: 批評項目リスト (重要度: 必須/推奨/参考、対象、観点、指摘、推奨調整)

並列実行ができない環境では順次でも可だが、独立して動かす(片方の出力をもう片方に渡さない)。

#### 2.3 統合: 批評を骨格に取り込む

メインエージェントが両者の批評を受け取り、骨格に対する修正を決定する。判定基準:

- **必須**: 原則として採用する。技術的に成立しない指摘は採用見送りでよいが、その場合は理由を整理する
- **推奨**: 採用すべきかをコストと効果で判断する。骨格の構造を歪めずに取り込めるなら採用
- **参考**: 文書には残さないが、検討した上で詳細フェーズの判断材料にする

採用した指摘は骨格セクション (2.1〜2.4) に反映する。具体的な反映方法:

- 主要意思決定の採用理由を補足する
- 概念モデルの不変条件を追加 / 修正
- 責務構造の責務境界を調整
- トピック別方針を更新

batch のサイズが大きく、批評を反映すると骨格全体を作り直す必要がある場合は、修正点を明示して greenfield-architect に骨格再生成を依頼する。

#### 2.4 ユーザー確認

メインエージェントが次の情報をユーザーに提示する:

- 確定した骨格設計 (2.1〜2.4)
- brownfield 批評の採否一覧 (採用したもの・採用しなかった理由)
- domain-first 批評の採否一覧 (採用したもの・採用しなかった理由)

確認文または `AskUserQuestion` で、次のいずれかをユーザーに求める:

- 骨格でOK → Phase 3 へ進む
- 修正指示あり → 指示を反映し、再度確認

骨格段階での修正は、本体スキルが指示を反映できる範囲なら本体で処理する。構造を作り直すような修正は greenfield-architect に再依頼する。

### Phase 3: 詳細設計 + 実装計画

#### 3.1 詳細設計と実装計画の生成 (greenfield-architect)

`greenfield-architect` に詳細設計と実装計画を依頼する。依頼内容:

- **フェーズ指示**: 「詳細設計+実装計画フェーズ」と明示
- **対象設計バッチ**: 同上
- **影響分析書**: 同上
- **確定骨格**: Phase 2 で確定した 2.1〜2.4
- **期待する出力**: 詳細設計セクション (3.1〜3.4) + 実装計画セクション (4) + 残課題セクション (5)

詳細レベルの境界 (原則2) を依頼に明記し、実装本体のコードや内部アルゴリズム擬似コードは書かないよう指示する。

#### 3.2 ファイル保存

骨格 (2.1〜2.4) と詳細 (3.1〜3.4) + 実装計画 (4) + 残課題 (5) を統合し、概要セクション (1) を付けて `implementation-design-<バッチスラッグ>.md` に保存する。

テンプレートは `assets/implementation-design-template.md` を参照する。

#### 3.3 ユーザー最終確認

メインエージェントが次の情報をユーザーに提示する:

- 成果物パス
- 主要な意思決定の要約 (3〜5行)
- 実装計画のフェーズ数と各フェーズの見出し

修正指示があれば該当箇所を更新する。修正がなければ完了。

## 成果物のフォーマット

実装設計書は次のセクションで構成する。**セクション順序とフィールド名は維持する**。

```markdown
# 実装設計書: <バッチ名>

## 1. 概要

- **対象設計バッチ**: <B<n>: バッチ名> (影響分析書 4.1)
- **含まれる設計トピック**: <T1, T3 等> (影響分析書 3)
- **参照ドキュメント**: <影響分析書 / 機能設計書 / 要求仕様書のパス>

## 2. 設計骨格

### 2.1 主要な意思決定
### 2.2 概念 / データモデル
### 2.3 モジュール / 責務構造
### 2.4 設計トピック別方針

## 3. 詳細設計

### 3.1 データ構造 / DB スキーマ
### 3.2 API / 関数インタフェース
### 3.3 主要な動作フロー
### 3.4 エラーハンドリング / エッジケース

## 4. 実装計画

### フェーズ 1: <フェーズ名>
### フェーズ 2: ...

## 5. 残課題・後続検討事項
```

セクションの省略可否:

- **省略しない。全セクションを必ず置く**。該当する内容がなければ見出しの直下に「該当なし」と明記する
- 理由: 実装フェーズや後続レビューがこの構造を前提に読む。「セクションが存在しない」と「セクションがあって該当なし」は意味が違う

## やりがちな失敗とその回避

### 失敗1: 1スキル実行で複数バッチを扱う

症状: 影響分析書に3バッチあるのを全部1つの実装設計書にまとめる。

回避の問い: そのバッチは本当に同時に設計すべきか? 影響分析書が複数バッチに分けたのは「別タイミングで設計してよい」という判断。1スキル実行で複数バッチを扱うと、文書が肥大化し、各バッチの設計判断が浅くなる。**バッチごとに別ファイルで実装設計書を作る**(スキルを複数回実行する)。

### 失敗2: 実装コードを設計書に書く

症状: 「3.2 API インタフェース」に関数本体の実装コードや、「3.3 主要動作フロー」に擬似コードが書かれている。

回避の問い: その記述は「契約」か「実装」か? 関数シグネチャは契約、関数本体は実装。実装は実装フェーズで書く。**実装設計書は契約レベルで止める**。

### 失敗3: 骨格段階で詳細に踏み込む

症状: 「2.2 概念モデル」に列定義、「2.4 トピック別方針」に関数シグネチャが書かれている。

回避の問い: 骨格段階の役割は「構造を確定する」こと。詳細(具体的な型・列・シグネチャ)は 3 で書く。骨格に詳細を入れると、Phase 3 で書く内容がなくなる、または 2 と 3 で同じ情報が重複する。

### 失敗4: 批評を全採用 / 全却下にする

症状: brownfield 批評の必須が3件あって全部採用、または推奨が5件あって全部不採用。

回避の問い: 採否は各指摘ごとに「採用すると骨格にどう反映されるか」「採用しないとどんなコストが残るか」で判断する。一括判断は批評を立てた意味を消す。

### 失敗5: 批評が代替設計に化けて気付かない

症状: brownfield 批評が「骨格全体を以下に置き換えるべき」と全面差し替えを提案している。本体スキルがそのまま採否を判断しようとしている。

回避の問い: その批評は「骨格への局所修正」の形か、「全面差し替え」の形か? 全面差し替えなら批評役の担当範囲外。「これは批評ではなく代替設計案。骨格を起点とした局所修正に絞ってほしい」と返して批評をやり直してもらう。

### 失敗6: ユーザー確認を Phase 2 末と Phase 3 末以外でも入れる

症状: 骨格生成の途中、批評取得の途中、詳細生成の途中で逐一ユーザーに確認している。

回避の問い: agent委譲が基本(原則4)。各フェーズの内部判断は agent に任せる。ユーザーが介在するのは Phase 2 末 (骨格確認) と Phase 3 末 (最終確認) の2回。これ以上増やすと前段の impact-analysis で論点整理した意味が薄れる。

### 失敗7: 批評の採否を実装設計書に書く

症状: 「## 5. レビュー記録」のようなセクションが生成され、批評の採否がそこに記録されている。

回避の問い: 実装設計書は実装フェーズの読み物。検討プロセスを残すと信号が薄れる(原則3)。批評の採否はユーザーに口頭で報告する場面のためだけのもの。

## 出力後にユーザーに確認すること

実装設計書を生成したら、次の点をユーザーに最終確認する:

- 設計骨格の主要意思決定が要求 / 機能設計の意図に沿っているか
- 詳細設計が契約レベルで止まっているか (実装コードや擬似コードが混入していないか)
- 実装計画の TDD フェーズ分割が現実的か (フェーズが大きすぎる / 小さすぎることはないか)
- 出力先パス `docs/plans/<機能名>/implementation-design-<バッチスラッグ>.md` で問題ないか

## テンプレート

`assets/implementation-design-template.md` に空テンプレートを置いている。実際に書き始めるときはこれをコピーして埋めていくのが速い。
