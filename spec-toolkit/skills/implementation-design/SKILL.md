# implementation-design

影響分析書(impact-analysis の成果物)の **設計バッチ単位** で、実装に入る前に必要な詳細設計を確定するスキル。

## このスキルが置かれている設計フロー

```
[1] 要求仕様書 → [2] 機能設計書 → [3] 影響分析書 → [4] 実装設計書(このスキル) → [5] 実装 (phase-implementation)
```

前段(impact-analysis)が「何を・どの順で設計するか」を整理済みなので、本スキルは **設計バッチに含まれるトピックの設計を1パスで完了させる** のが役割。これがパイプラインで唯一、バッチ数だけ複数回実行するフェーズ(1スキル実行=1バッチ)。

## 入口ガード

影響分析書が無い、または `4.1 設計バッチ` が欠けている場合は、**自分で影響分析を代行して埋めず**、まず impact-analysis を実施するようユーザーに案内して止まる。代行すると、前段が担う調査・トピック整理・バッチ化を飛ばした薄い設計になる。前段成果物が揃っていることが本スキルの前提。

## 入力の前提

- **主入力**: impact-analysis が生成した影響分析書(`docs/plans/<機能名>/impact-analysis.md`)
- **補助参照**: 機能設計書・要求仕様書(同ディレクトリ)
- **対象範囲**: 影響分析書の `4.1 設計バッチ` のうち、**1スキル実行につき1バッチ**だけを対象とする

## 中核となる設計

### 2段階フロー: 骨格 → 詳細

設計を2段階で進める。**骨格設計フェーズ**で主要意思決定・概念モデル・責務構造・トピック別方針を確定し(詳細なシグネチャ・列定義は決めない)、**詳細設計+実装計画フェーズ**で骨格を前提にデータ構造・APIインタフェース・動作フロー・エラー方針・実装計画(フェーズ分割)を埋める。

なぜ2段階か: 構造的論点(主要意思決定・概念境界)を詳細より前に固めないと、詳細を書いた後の構造変更で詳細全体を書き直すことになる。骨格段階でユーザーが介在することで構造ごと作り直しの手戻りを最小化し、批評の入る場所も骨格に絞れる(批評が詳細に踏み込むと統合判断が破綻する)。

### 主設計者 + 批評役の構成

骨格設計は3エージェント協調で生成する:

- **greenfield-architect (主設計者)**: 既存実装や移行コストを考慮せず、要件を満たす最もシンプルな骨格を提案
- **brownfield-architect (批評役)**: 既存パターン整合・移行コスト・障害リスク・段階導入の観点で批評
- **domain-first-architect (批評役)**: 概念境界・不変条件集中・用語一貫性・概念数の必要十分性の観点で批評

批評役は **独立した代替設計案を出さず、骨格への局所修正提案だけを返す**。代替案を出すと本体が「greenfield全体 vs 批評案全体」の二者択一を迫られ、両者の良さを統合できなくなる。局所修正なら本体が選択的に取り込める。詳細設計+実装計画は greenfield-architect 単独で生成する(骨格段階で構造的論点は確定済みのため、詳細フェーズで批評は不要)。

## 中核となる原則

進め方・フォーマット・自己点検はすべてこの5原則の適用。判断に迷ったらここへ戻る。

### 原則1: 1スキル実行 = 1設計バッチ

影響分析書に複数バッチがあれば、ユーザーに対象バッチを選ばせる(1つだけなら自動で対象にする)。複数バッチを並列に扱うと、設計判断が浅くなる・成果物が肥大化する・ユーザー確認が混乱する。

バッチ間整合のため、先行バッチで確定した実装設計書(同ディレクトリに既存)があれば読み込み、その確定事項(データモデル等)を前提にする。前提の変更が必要になった場合は `## 他文書の確定済み決定の変更` に従う。成果物の `1. 概要` には「全バッチの中で本書がどれか」を明記し、利用者が「あと何バッチ残っているか」を見失わないようにする。

### 原則2: 詳細レベルは「契約レベル」で止める

実装設計書は **実装フェーズで設計に立ち戻らずに済む契約レベル** の情報のためにある。これを越えると文書が肥大化し必要情報が探しにくくなり、読み手がコードレビューを要求され、実装の自由度が不当に縮む。境界はこの2列で判断する:

| 書く(契約) | 書かない(実装の中身) |
|---|---|
| 型・制約・インデックス | テーブル作成SQL本文 |
| シグネチャ・リクエスト/レスポンス形・主要エラー | 関数本体 |
| 主要動作フローの概略(5ステップ以内) | 全分岐の手続き・内部アルゴリズムの擬似コード・呼び出し例 |

これは骨格段階にも効く(逆向き): 骨格(2.x)に列定義やシグネチャを書かない。詳細は 3.x で書く。骨格に詳細を入れると Phase 3 で書く内容がなくなるか、2 と 3 で同じ情報が重複する。

### 原則3: 批評の採否は口頭で報告し、文書に残さない

批評役の指摘とその採否(採用/不採用/部分採用)は Phase 2 でユーザーに口頭報告し、**実装設計書本文には残さない**。実装設計書は実装フェーズの読み物で、検討プロセスを残すと信号が薄れる。`## レビュー記録` のようなセクションを作らない。

### 原則4: agent委譲を基本にし、ユーザー確認は各フェーズ末尾だけ

agent への委譲を基本とし、ユーザーが介在するのは **Phase 2 末尾(骨格確認)と Phase 3 末尾(最終確認)の2回だけ**。各フェーズ内部の判断は agent に任せる。骨格確認・詳細着手前という最も手戻りの少ないタイミングに確認を置くのが要点。逐一確認すると、前段の impact-analysis が論点整理した意味が薄れる。

### 原則5: 上流の未決事項を勝手に確定しない

影響分析書 `5. 後続フェーズへの引き継ぎ` の未確定論点、機能設計書の確認ポイント・引き継ぎ事項のうち、対象バッチに関係するものは影響度で扱いを分ける。**骨格の主要意思決定に影響する未決**は greenfield-architect が1案へ勝手に確定せず、Phase 2 末尾の骨格確認で「未決事項とその仮置き案」として明示提示し、ユーザーの判断を得る。**詳細の一部に閉じる未決**(骨格を変えずに後から差し替えられるもの)は設計を進め、`5. 残課題・後続検討事項` に未決のまま明記する。

ただし詳細に閉じる未決でも、**実装計画のいずれかのフェーズの完了条件をブロックするもの**は残課題に送らず、Phase 3 末尾の最終確認で確定させる。残課題に置いてよいのは、実装と並行して解消できる未決だけ。

未決が1案で埋まると採用理由が立ってしまい、「未決だったこと」自体が読み手から見えなくなる。上流(request-spec/feature-options)が守ってきた「未決を見える状態に保つ」規律を、この最終段で消さない。

## 進め方

### Phase 1: 入力受領と対象バッチの確定

1. 入力(影響分析書のパス)を受け取る。指定が無ければ確認する。**確定済みの実装設計書への改訂依頼**(レビュー指摘の反映等)の場合は、Phase 1〜3 を回さず `## 確定後の改訂` の手順に従う。
2. 影響分析書を読み、`4.1 設計バッチ` を把握する。
3. 対象バッチを確定する(1つなら自動、複数なら `AskUserQuestion` で選ばせる)。対象バッチに含まれる設計トピック(`T<n>`)を `3. 設計トピック` から抽出する。
4. 補助参照として機能設計書・要求仕様書を読む。**先行バッチの確定実装設計書があれば読み込む**(原則1: バッチ間整合)。
5. 対象バッチに関係する未確定論点を上流成果物から抽出しリスト化する(影響分析書 `5.` の未確定論点、機能設計書の確認ポイント・引き継ぎ事項)(原則5)。
6. 出力先を決定する: `<dir>/implementation-design-<バッチスラッグ>.md`(スラッグはバッチ名から英数字・ハイフンで簡潔に。日本語をファイル名に使わない)。既存ファイルがあれば上書き可否を確認する。

### Phase 2: 骨格設計

1. **主設計の生成 (greenfield-architect)**: 「骨格設計フェーズ」と明示し、対象設計バッチ(ID・名前・含まれるトピックID)、影響分析書(全文。バッチ範囲を明示しつつ他バッチの文脈も参照可)、要求仕様書/機能設計書(ドメイン語彙の参照源)を渡す。あわせて Phase 1 で抽出した対象バッチに関係する未決事項リストを渡し、設計判断で勝手に確定せず、骨格に影響するものは仮置きと明示し、詳細に閉じるものは残課題へ送るよう指示する(原則5)。期待する出力は骨格セクション(2.1〜2.4)のみ(詳細設計や実装計画は含めない)。
2. **批評の取得 (並列)**: greenfield骨格が返ったら `brownfield-architect` と `domain-first-architect` を**並列に**起動する。各依頼に対象バッチ・影響分析書・要求仕様書/機能設計書(特に domain-first には必須)・greenfield骨格(2.1〜2.4)を渡し、批評項目リスト(重要度: 必須/推奨/参考、対象、観点、指摘、推奨調整)を求める。並列不可なら順次でもよいが、片方の出力をもう片方に渡さない(独立性を保つ)。
3. **統合: 批評を骨格に取り込む**: 両者の批評を受け取り、骨格への修正を**指摘ごとに個別判断**する(一括採用/却下にしない)。必須は原則採用(技術的に成立しない場合のみ見送り、理由を整理)、推奨はコストと効果で判断(骨格構造を歪めず取り込めるなら採用)、参考は文書に残さず詳細フェーズの判断材料に。統合時は骨格を4観点(要件適合 / ドメインの自然さ / 既存資産整合 / 移行コスト・障害リスク)で通す。後3者は批評役の担当観点だが、批評が拾い損ねることもあるため本体が最終チェックを持ち、要件適合は批評役の担当外なので本体だけが見る。「既存資産整合」と「移行コスト」が相反したときの優先則: 既存実装が単一パターンで統一されている領域では、そのパターンに伴う標準的コスト(インフラ定義の追加等)を逸脱の理由にしない。逸脱案を採る場合は「新規コードが唯一の例外になる」事実を明示し、本体で確定せず手順4の骨格確認の論点としてユーザーに提示する。採用した指摘は骨格(2.1〜2.4)に反映する(主要意思決定の採用理由補足/不変条件の追加・修正/責務境界の調整/トピック別方針の更新)。批評を反映すると骨格全体を作り直す必要がある場合は、修正点を明示して greenfield-architect に再生成を依頼する。
   - 批評が「骨格全体を置き換えるべき」という**全面差し替え**の形になっていたら、それは批評役の担当範囲外。「局所修正に絞ってほしい」と返して批評をやり直してもらう。
4. **ユーザー確認**: 確定した骨格(2.1〜2.4)、brownfield/domain-first 批評の採否一覧(採用したもの・採用しなかった理由)、**骨格に影響する未決事項とその仮置き案**(あれば)を提示し、`AskUserQuestion` 等で「骨格でOK → Phase 3」か「修正指示」を求める。本体で反映できる範囲なら本体で、構造を作り直す修正は greenfield-architect に再依頼する。

### Phase 3: 詳細設計 + 実装計画

1. **生成 (greenfield-architect)**: 「詳細設計+実装計画フェーズ」と明示し、対象バッチ・影響分析書・確定骨格(2.1〜2.4)を渡す。期待する出力は詳細設計(3.1〜3.4)+実装計画(4)+残課題(5)。**契約レベルの境界(原則2)を依頼に明記**し、実装本体コードや擬似コードは書かないよう指示する。あわせて**網羅性の指示**を明記する: (a) 共有スキーマ/型を変更する場合、それを返す全経路(単一取得・一覧・mutation・公開・複製 等)を列挙して 3.2 に各経路の対応を書き、実装計画にも含めること。(b) 新規エンティティがある場合、3.1 のライフサイクル表(作成・更新・削除の全契機。削除は直接削除に加え DB スキーマのカスケード定義を祖先方向に遡った全経路)を埋めること。
2. **ファイル保存**: 骨格+詳細+実装計画+残課題を統合し、概要(1)を付けて `implementation-design-<バッチスラッグ>.md` に保存する(`assets/implementation-design-template.md` を参照)。
3. **ユーザー最終確認**: 成果物パス・主要意思決定の要約(3〜5行)・実装計画のフェーズ数と各フェーズ見出しを提示する。残課題(5)に実装計画のフェーズ完了条件をブロックする未決が残っていれば、この場で提示して確定を求める(原則5)。修正指示があれば該当箇所を更新する。

## 成果物のフォーマット

実装設計書は次のセクションで構成する。**セクション順序とフィールド名は維持する**。

```markdown
# 実装設計書: <バッチ名>

## 1. 概要
- **対象設計バッチ**: <B<n>: バッチ名> (影響分析書 4.1)
- **全バッチ中の位置**: <例: B1,B2,B3 のうち本書は B2。バッチ数だけ実装設計を繰り返す>
- **含まれる設計トピック**: <T1, T3 等> (影響分析書 3)
- **制約条件(上流から)**: <影響分析書/上流で制約として与えられた技術指定。どの要求(R)由来か。なければ「該当なし」>
- **参照ドキュメント**: <影響分析書 / 機能設計書 / 要求仕様書 / 先行バッチの実装設計書 のパス>

## 2. 設計骨格
### 2.1 主要な意思決定   ### 2.2 概念 / データモデル   ### 2.3 モジュール / 責務構造   ### 2.4 設計トピック別方針

## 3. 詳細設計
### 3.1 データ構造 / DB スキーマ   ### 3.2 API / 関数インタフェース   ### 3.3 主要な動作フロー   ### 3.4 エラーハンドリング / エッジケース
(3.1 には新規エンティティごとのライフサイクル表を含める。形式はテンプレート参照)

## 4. 実装計画
### フェーズ 1: <フェーズ名>   ### フェーズ 2: ...

## 5. 残課題・後続検討事項
```

**全セクションを必ず置く**。該当内容がなければ見出し直下に「該当なし」と明記する(実装フェーズ・後続レビューがこの構造を前提に読むため、「セクションが無い」と「あって該当なし」は意味が違う)。

## 引き渡し前の自己点検

出力前に各原則を守れたかを点検する(詳細は対応する原則/Phaseへ):

- **1実行=複数バッチ** — 1バッチだけを対象にしたか。複数バッチを1文書に詰めていないか(原則1)
- **実装コードの混入** — 3.2/3.3 に関数本体・擬似コード・呼び出し例が無いか。契約レベルで止まっているか(原則2の対比表)
- **骨格への詳細の漏れ** — 2.x に列定義・シグネチャが無いか(詳細は 3.x)(原則2)
- **2.4 の再掲肥大** — 設計トピック別方針が 2.1 の決定内容の再掲になっていないか。決定への参照(D<n>)と決定に現れない補足に留めたか
- **批評の一括採否** — 各指摘を「採ると骨格にどう反映されるか/採らないとどんなコストが残るか」で個別判断したか(Phase 2-3)
- **批評の代替設計化** — 批評が全面差し替えになっていないか。局所修正の形に戻したか(主設計者+批評役の構成)
- **4観点の吟味** — 理想設計を要件適合/ドメインの自然さ/既存資産整合/移行コスト・障害リスクの4観点で通したか。批評役が拾い損ねた観点を本体が補完したか(Phase 2-3)
- **批評採否の文書化** — `レビュー記録` のようなセクションを作っていないか。採否は口頭報告のみか(原則3)
- **確認の過剰** — ユーザー確認を Phase 2 末・Phase 3 末の2回に絞ったか(原則4)
- **実装フェーズの粒度** — 各フェーズについて「このフェーズが終わったら、何かを実行してテストが緑になり人が動作を確認できるか?」に Yes か。「型だけ定義」「ファイルだけ作る」のような中間状態をフェーズにしていないか
- **契約変更の波及全列挙** — 共有スキーマ/型を変更した場合、それを返す全経路(単一取得・一覧・mutation・公開・複製)を列挙し、各経路の対応を 3.2 と実装計画に明記したか(Phase 3-1)
- **削除連鎖の全列挙** — 削除連動を設計した場合、対象エンティティが消える全経路(直接削除 + DB スキーマのカスケード定義を祖先方向に遡った全経路)がライフサイクル表の削除行に並んでいるか(Phase 3-1)
- **ライフサイクル契機の要求遡及** — ライフサイクル表の各契機が要求(R)または上流決定に遡れるか。遡れない契機(YAGNI 候補)は骨格確認・最終確認のいずれかでユーザーに提示したか
- **バッチ間整合** — 先行バッチの確定事項(データモデル等)を前提にし、矛盾していないか(原則1)
- **他文書決定の無断変更** — 先行バッチ・上流成果物の確定済み決定を変更する場合、ユーザー確認の論点として提示し、承認後に変更元文書も改訂したか。先行契約が本バッチを制約する問題は、受容案と差し戻し案の両方を提示したか(他文書の確定済み決定の変更)
- **未決の無断確定** — 上流の未確定論点を勝手に1案へ畳んでいないか。骨格に影響する未決は骨格確認で提示したか。詳細に閉じる未決は `5.` に残したか。実装計画のフェーズ完了をブロックする未決を残課題に送っていないか(原則5)

## 出力後にユーザーに確認すること

生成したら次の点を最終確認する:

- 設計骨格の主要意思決定が要求/機能設計の意図に沿っているか
- 詳細設計が契約レベルで止まっているか(実装コード・擬似コードが混入していないか)
- 実装計画のフェーズ分割が現実的か(フェーズが大きすぎ/小さすぎないか)
- 出力先パスで問題ないか

## 確定後の改訂

確定済みの実装設計書に、レビュー起点等で決定の変更が入る場合の手順。実運用ではこの改訂が最も頻度の高い作業になる。

1. 旧決定の語彙(旧エンドポイント名・旧関数名・旧方式名)で成果物全体を grep し、全出現箇所を列挙する
2. 2.1→2.2→2.3→2.4→3.x→4→5 の順(決定→概念→責務→契約→フロー→計画→残課題)に編集する
3. 旧語彙の残存ゼロを grep で確認する(取り残しを見逃すと、実装フェーズが矛盾した設計書を読むことになる)
4. 改訂内容が先行バッチ・上流成果物の記述と矛盾する場合は `## 他文書の確定済み決定の変更` に従い、変更元も改訂する

編集では確定後の内容だけを残し、指摘の出所(「チームレビュー指摘」等)や旧決定からの変更経緯を本文に書かない(原則3 と同じ理由: 検討プロセスは成果物の信号を薄める)。

骨格構造が変わる規模の変更は、手編集せず greenfield-architect に該当セクションの再生成を依頼する。

## 他文書の確定済み決定の変更

設計中や確定後の改訂中に、先行バッチの実装設計書や上流成果物(機能設計書等)の確定済み決定を変更する必要が判明することがある。後段でしか見えない事情による変更は健全だが、次の2点を必ず守る。

1. **変更はユーザー確認の論点として提示する**: 「どの文書のどの決定を・なぜ変えるか」を、骨格に関わるものは Phase 2 末尾、詳細に閉じるものは Phase 3 末尾の確認で明示し、判断を得てから変更する。先行バッチの確定契約が本バッチの要求充足・UX を制約する問題を発見した場合も同様に、「制約を受容して本バッチ内で緩和する案」と「先行バッチへ差し戻して契約を改訂する案」の両方を論点として提示する(受容をエッジケース記述に埋めたまま確定しない)。
2. **承認された変更は変更元文書に反映する**: 先行バッチの実装設計書は `## 確定後の改訂` の手順で改訂し、機能設計書など上流成果物は該当箇所(選定案・横断的決定等)を更新する。自文書に「旧方針を上書きした」と宣言するだけで済ませない — 変更元に旧記述が残ると、その文書だけを読む実装フェーズ・後続バッチ・設計抽出(extract-design 等)が古い決定を正として読む。
