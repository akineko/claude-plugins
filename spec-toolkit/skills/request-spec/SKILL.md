# request-spec

ステークホルダー間で整理された要件・要望を、後続の設計フェーズが扱える「要求仕様書」に変換するスキル。

## このスキルが置かれている設計フロー

このスキルは、spec-toolkit の以下のドキュメントフローの最初のステップとして位置づく:

```
[1] 要求仕様書(このスキル) → [2] 機能選択肢の洗い出し・選定 → [3] 影響分析 → [4] 実装設計
```

後続フェーズの存在は、このスキルの「やらないこと」を決める重要な制約になる:

- **[2] 機能選択肢の洗い出し・選定** が「ユーザー視点でどう機能を実現するかの選択肢出し」を担う → このスキルでは UI/UX や機能の実現手段を決めない
- **[3] 影響分析** がコードベースの調査・変更箇所の洗い出しを担う → このスキルでは既存実装の調査・変更箇所の指定をしない
- **[4] 実装設計** がアーキテクチャ・データ構造・フェーズ分割を担う → このスキルでは技術選定や実装計画に踏み込まない

つまりこのスキルは「**整理された要求情報を、後続スキルが噛める形に整える**」だけが仕事。情報を増やす(具体化する)のではなく、構造化と最小限の補完に徹する。

## 入力の前提

このスキルが受け取る入力には次の特徴がある:

- **ある程度整理済み**: 関係者間で議論を経て、論点が一定収束している
- **粒度が一定でない**: 「ログイン機能にSSOを追加する。Microsoft Entra IDを使う」のように具体的なものと、「商品をお気に入り登録できるようにしたい、詳細は任せる/または提示してほしい」のように方向性だけのものが混在する
- **形式は不問**: 議事録、メモ書き、Slackの抜粋、口頭での要望の書き起こし、Issue文面など

この前提を踏まえて、入力に対しては次のように振る舞う:

- 具体的に書かれている要求は具体的なまま記録する。勝手に抽象化しない。
- 方向性のみの要求は方向性のまま記録する。勝手に具体化しない。
- 矛盾・抜け漏れ・前提の暗黙化があれば、要検討事項として明示する(勝手に解決しない)。

## 中核となる原則

要求仕様書スキルの品質は、次の4つの原則の徹底で決まる。

### 原則1: WhatとWhyに集中し、Howには踏み込まない

要求仕様書が答えるべき問い:

- **What**: 何を達成したいのか / 何ができるようになるのか
- **Why**: なぜそれが必要なのか / どんな課題を解決するのか
- **For whom**: 誰のための機能か

要求仕様書が答えてはいけない問い:

- **How**: どんなUIで / どんなアーキテクチャで / どのライブラリで / どのテーブルに
- **When (実装順)**: どのフェーズで作るか / どの順番で実装するか
- **Where (コード上)**: どのファイル・モジュールを変更するか

理由: How/When/Where は後続スキル([2][3][4])の担当領域。ここで決めてしまうと、後続スキルが「より良い選択肢」を提示する余地を奪う。特にユーザーが明示的に「他により良い選択肢がないかと模索したい」と望む場合があるため、要求仕様書段階での実装方針の固定化は害になる。

例外: ステークホルダーが明示的に「Microsoft Entra IDを使う」「既存の通知基盤に乗せる」のように実装上の制約を要求として指定している場合は、それは「制約条件」として記録する。Howに踏み込んだのではなく、Howの一部が制約として与えられている、という整理。

### 原則2: 要求ごとの「具体度」を明示する

各要求には次のいずれかのラベルを付ける:

- **[決定]**: 具体的な機能内容が確定している。後続スキルはこれを所与として扱う。
- **[方向性]**: やりたいことの方向は決まっているが具体は未定。後続スキル([2])がユーザー視点での選択肢を出す対象。
- **[要検討]**: 関係者間で議論が残っている、または相互に矛盾する要望が混在している。判断を要する。

ラベリングが大事な理由: 後続の「機能選択肢洗い出し」スキルは、**[方向性]** と **[要検討]** にラベルされた要求に対して選択肢を出す。**[決定]** にも「より良い選択肢がないか」を模索することはあるが、出発点として「すでに決まっているもの」と「まだ決まっていないもの」が区別されていないと、後続スキルは何を確定情報として扱えばよいか判断できない。

ラベリングは恣意的にならないよう、次の基準で判定する。判定の核は「**次に何が必要か**」であり、書き手や関係者の確信度ではない。

- **[決定]**: 機能内容が具体的に確定している。後続スキルはこれを所与として扱える。
  - 入力に「<機能名>を<具体的な手段>で実現する」と書かれている / 関係者間で具体仕様が合意済み
- **[方向性]**: 何を達成したいかは決まっているが具体は未定で、**後続スキル([2] 機能選択肢洗い出し)が選択肢を出して提案すれば前進できる**状態。
  - 入力に「<機能名>がほしい / 詳細は任せる / 案を出してほしい」など書かれている
  - 具体化のためにユーザー視点での実現方法を並べて見せる、というアプローチで進められる
- **[要検討]**: **関係者間の積極的な意思決定が必要**で、選択肢提示だけでは前進しない状態。
  - 入力に複数案が併記されていて未選定 / 関係者間で意見が対立している
  - 部門間の優先度調整、ポリシー判断、法務・コンプラ確認、スコープ調整など、合意形成プロセスを要する

`[方向性]` と `[要検討]` の判別ポイント: その項目について「**選択肢を並べて見せれば判断が前に進む**」のなら `[方向性]`、「選択肢を見せるだけでは不十分で、関係者の合意形成プロセスが必要」なら `[要検討]`。迷ったら `[要検討]` に倒す(後続フェーズで意思決定の負荷を顕在化させたほうが安全)。

### 原則3: 補完は「自然に導出可能な範囲」に限定する

入力からは明示されていなくても、次のレベルの情報は補完してよい:

- 入力全体から自明な前提条件(例: 「ログイン機能の改修」とあれば「既存ユーザーが影響を受ける」)
- スコープの境界線で「含まれない」ことが論理的に明らかなもの(例: 「PCブラウザのみ」と書かれていれば「モバイルアプリは対象外」)
- 用語の定義揺れの統一(同じものを指す異なる呼称の整理)

逆に、次のレベルの補完はしてはいけない:

- 「お気に入り機能」と聞いて「ボタンの色」「お気に入り上限数」のような実装詳細を勝手に決める
- 「通知機能」と聞いて「メール / プッシュ / アプリ内通知のどれか」を勝手に選ぶ
- 入力に書かれていないユースケースや関連機能を「あったほうがいい」と追加する

判定基準: 補完しようとしている情報を消したら要求仕様書として読めなくなるか? を自問する。読めなくなる = 自然な補完。読めるが情報が増えるだけ = 過剰な補完。

### 原則4: 不確実性を「問い」の形で残す

入力に含まれない・矛盾する・曖昧な情報は、勝手に解消せず「要検討事項」として残す。残し方には作法がある:

悪い例:
> ・お気に入りの上限数は要検討

良い例:
> ・お気に入りの上限数: 入力には記載なし。ユーザーごとに無制限とするか、UX/パフォーマンス観点で上限を設けるかは検討が必要(後続の機能選択肢洗い出しで扱う想定)。

問いの形にするときのコツ:

- **何が不明か**を書く(単に「要検討」だけでは情報量がゼロ)
- **なぜ重要か**を一言添える(検討の優先度判断に使われる)
- **誰がいつ扱うか**の示唆があれば付ける(後続スキルへの引き継ぎになる)

## 進め方

入力を受け取ったら、次の手順で進める。各ステップは独立して機能するので、入力の質に応じて省略・繰り返し可能。

### Step 1: 入力の俯瞰と一次分解

- 入力全体を読み、扱われているトピック(機能項目)を列挙する
- 各トピックを「機能要求」「非機能要求(性能・セキュリティ・運用等)」「制約条件」「背景情報」のいずれかに分類する
- このとき内容を要約しない。元の情報を失わない粒度で抽出する。
- あわせて、関連の強いトピック同士をテーマでクラスタリングする観点を持つ(例: 「コメント投稿」と「コメントへの返信」は同じコメントテーマ、「ロール権限」と「ユーザー登録」は同じユーザー・権限テーマ)。このクラスタは Step 5 の並び順とグループ見出しに使う。

### Step 2: 各要求への具体度ラベリング

- Step 1 で抽出した要求それぞれに **[決定] / [方向性] / [要検討]** ラベルを付ける
- ラベル判定に迷う場合は、より具体度が低い側に倒す(後続スキルで具体化される設計になっているため)
- 「決定だと思っていたが、よく読むと方向性だけだった」というケースは多い。**書き手の確信度ではなく、書かれている情報の具体度で判定する**

### Step 3: 自然な補完と用語統一

- 原則3 に従い、論理的に導出可能な前提・スコープ境界・暗黙の制約を補う
- 同じ概念に複数の呼称が使われている場合、最も明確なものに統一する(統一前後の対応は本文か用語集に残す)
- ここで「これは補完か、それとも過剰な追加か」の判断に迷ったら、補完しない側を選ぶ

### Step 4: 要検討事項の抽出

- 入力内の曖昧さ・矛盾・抜け漏れを洗い出す
- 原則4 に従い、「問い」の形で記述する
- どの後続スキルが扱う想定かが分かれば付記する

### Step 5: 要求仕様書の構造化出力

- 後述の「成果物のフォーマット」に従って要求仕様書を生成する
- **要求一覧の並び順**: Step 1 でクラスタリングしたテーマ単位で要求をまとめ、関連の強い要求を隣接させる。要求が多くテーマで束ねたほうが把握しやすい規模なら、`3. 要求一覧` の下にテーマ小見出しを置く(後述のフォーマット参照)。理由は2つ — (1)関連要求が離れて並ぶと「同じ対象についての要求」を読み手が拾い集める負担が生じる、(2)このテーマグループは後続の機能選択肢洗い出しで「どの範囲の機能をまとめて考えるか」の単位にもなる。要求が2〜3件と少なくテーマ分けの意味が薄い場合はグループ化せずフラットに並べる(過剰なグループ化はしない)
- **出力先パス**: ユーザーが指定していなければ `docs/plans/<機能名>/request-spec.md` に出力する
  - 後続スキル(機能選択肢洗い出し / 影響分析 / 実装設計)の成果物も `docs/plans/<機能名>/` 配下にまとまる前提のディレクトリ構造
  - `<機能名>` はケバブケースで簡潔に(例: `favorite-products`, `sso-entra-id`)
- **フォーマットは原則として後述の既定フォーマットを使う**(プロジェクト内に別の要求仕様書らしきファイルがあっても自動では合わせない)
  - 理由: 既定フォーマットは後続スキルが扱える構造(具体度ラベル / 要検討事項の3点セット 等)を前提に設計されている。プロジェクト内の既存ファイルが旧版スキルの成果物だったり、別目的のフォーマットだったりすると、後続フローで必要な情報が欠ける
  - ただし、プロジェクト内に既存の要求仕様書らしきファイル(`docs/plans/`, `docs/specs/`, `docs/requirements/` 配下など)を見つけた場合は、その存在をユーザーに伝える。ユーザーから明示的に「既存フォーマットに合わせて」と指示された場合のみ既定フォーマットを離れる

## 成果物のフォーマット

要求仕様書は次のセクションで構成する。**セクション順序とラベル形式は維持する**(後続スキルがこの構造を前提に動くため)。

```markdown
# 要求仕様書: <機能・改修の名称>

## 1. 背景と目的

<なぜこの変更が必要か / どんな課題を解決するか / 達成したい状態>
<関係者・主要なステークホルダーの記述があればここに>

## 2. 対象範囲

### 2.1 含むもの

<このスコープで扱う機能・改修項目を箇条書きで列挙>

### 2.2 含まないもの

<明示的に対象外とするもの。「今回はやらない」の合意事項>

### 2.3 前提条件

<入力から自然に導出される / 関係者間で合意済みの前提>

## 3. 要求一覧

関連の強い要求が隣り合うよう、テーマ単位でまとめて並べる。要求が多くテーマで束ねたほうが把握しやすい規模なら、テーマ小見出し(`###`)を置き、その下に各要求(`####`)を並べる。**要求IDはテーマをまたいでフラットな連番(3.1, 3.2, …)を維持する** — 後続スキルが `R3.1` のように参照するため、テーマ分けで番号を枝分かれさせない。要求が少数でテーマ分けの意味が薄ければ、見出しを置かず `### 3.1` から直接並べてよい。

各要求は次の形式で記述する。

### <テーマ名>

#### 3.1 <要求の名前>

- **具体度**: [決定] | [方向性] | [要検討]
- **What**: <何を達成したいか / 何ができるようになるか>
- **Why**: <なぜ必要か / どんな課題を解決するか>
- **For whom**: <誰のための機能か>
- **制約条件**(あれば): <ステークホルダーが指定した実装上の制約>
- **補足**(あれば): <入力に書かれていた具体的な情報のうち、上記に収まらないもの>

(同一テーマ内に関連要求を続け、テーマが変わったら次の `###` 見出しへ。要求の数だけ繰り返す)

## 4. 非機能要求

<性能・セキュリティ・可用性・運用などの要件。入力に明示があれば記録する。
**入力に明示がなければ「該当なし」と書く。観点(セキュリティの検討が必要そう、可用性目標を設けるべき 等)の推測列挙はしない**
— 観点の洗い出しは後続スキルの仕事で、要求仕様書段階で先取りすると過剰補完になる>

## 5. 要検討事項

各項目は次の形式で記述する。

- **論点**: <何が不明・未決定・矛盾しているか>
- **重要度の根拠**: <なぜこれを決める必要があるか>
- **想定する解決フェーズ**: <後続のどのスキル/フェーズで扱う想定か>

## 6. 関連情報

<元入力の所在(議事録ファイル名 / Issue URL / Slack スレッドへのリンク 等)と、外部の参考資料のみを記録する。
**本文(背景や要求一覧)と重複する要約は書かない** — 本文に既出の情報は本文を参照すれば足りる>
<用語の定義揺れを統一した場合はその対応表(揺れがなければ表ごと省略)>
```

セクションの省略可否:

- **省略しない。全セクションを必ず置く**。該当する内容がなければ見出しの直下に「該当なし」と明記する。
- 理由: 後続スキル(影響分析 / 実装設計 等)はこの構造を前提に動く。「セクションが存在しない」と「セクションがあって該当なし」は意味が違う。前者は書き忘れの可能性が残るが、後者は「検討した上で該当なし」という積極的判断として読める。

## やりがちな失敗とその回避

過去の運用で生じやすかった失敗パターンと、その回避のための問い:

### 失敗1: 後続フェーズが扱う情報を先取りしてしまう

症状: 要求仕様書なのに UI のワイヤーフレームや DB スキーマが書かれている。

回避の問い: この情報は **[2] 機能選択肢洗い出し** や **[3] 影響分析** や **[4] 実装設計** で扱う情報ではないか?

### 失敗2: 方向性だけの要求を勝手に具体化する

症状: 「お気に入り機能がほしい(詳細は任せる)」という入力に対して、勝手に上限数・ボタン位置・通知連動などの仕様を書いている。

回避の問い: この具体は入力に書かれていたか? それとも自分が補完したか? 補完したならそれは「自然な補完」か「過剰な追加」か?

### 失敗3: 要検討事項を抽象的に列挙して終わる

症状: 「上限数は要検討」「通知の方式は要検討」のように、論点だけが箇条書きされていて重要度や扱うフェーズの示唆がない。

回避の問い: この要検討事項を読んだ後続スキル/担当者は、何をすればよいかが分かるか? 重要度や扱うべきフェーズを推測できるか?

### 失敗4: 「決定」と「方向性」のラベリングを書き手の希望で行う

症状: ステークホルダーが「方向性レベルで合意した」だけのものを、書き手が「決定」と書いてしまう(または逆)。

回避の問い: ラベルは入力に書かれている **情報の具体度** で判定したか? 書き手や関係者の確信度で判定していないか?

### 失敗5: 矛盾を見つけても解消してしまう

症状: ステークホルダーAの「メール通知」とステークホルダーBの「アプリ内通知」が併記された入力に対し、片方を採用するか統合して「通知機能」と書いてしまう。

回避の問い: 入力に複数の選択肢や対立があった場合、それを **[要検討]** として残したか? 勝手に片方に倒していないか?

### 失敗6: 入力順のまま並べて関連要求が離散する

症状: 入力(議事録・メモ)に出てきた順で要求を並べた結果、同じ対象についての要求(例: 「コメント投稿」と「コメントへの返信」)が一覧の離れた位置に散らばり、読み手が関連を拾い集める負担を負う。

回避の問い: 関連の強い要求(同じエンティティ・同じ運用・依存関係のある要求)が隣り合っているか? テーマでクラスタリングして並べたか(Step 1・Step 5)? 要求が多いならテーマ小見出しで束ねたか?

## 出力後にユーザーに確認すること

要求仕様書を生成したら、次の点をユーザーに確認する(全部を一度に聞くのではなく、特に重要そうな点に絞る):

- **[方向性]/[要検討]** ラベルの判定が妥当か(具体度判定はこのスキルの肝で、後続フローに直接影響する)
- 補完した前提条件・スコープ境界が入力の意図と合っているか
- 要求一覧のテーマ分け・並び順が把握しやすいか(関連要求が離れていないか)

- プロジェクト内に既存の要求仕様書らしきファイルを検出した場合、その存在を伝えた上で「既定フォーマット」のままでよいか
