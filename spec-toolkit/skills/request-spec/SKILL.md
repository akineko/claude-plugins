# request-spec

ステークホルダー間で整理された要件・要望を、後続の設計フェーズが扱える「要求仕様書」に構造化するスキル。情報を増やす(具体化する)のではなく、What/Why/誰のため を失わずに整え、**何が確定で・何が未解決かを下流が判別できる状態**を作るのが本質。Howには踏み込まない。

## このスキルが置かれている設計フロー

spec-toolkit のドキュメントフローの最初のステップ。後続フェーズの存在が、このスキルの「やらないこと」を決める:

```
[1] 要求仕様書(このスキル) → [2] 機能選択肢の洗い出し・選定 → [3] 影響分析 → [4] 実装設計 → [5] 実装
```

- **[2] 機能選択肢** がユーザー視点での実現手段の選択肢出しを担う → ここでは UI/UX や機能の実現手段を決めない
- **[3] 影響分析** がコードベース調査・変更箇所の特定を担う → ここでは既存実装の調査・変更箇所の指定をしない
- **[4] 実装設計** がアーキテクチャ・データ構造・フェーズ分割を担う → ここでは技術選定や実装計画に踏み込まない

なぜ踏み込まないか: ここで実現手段を固定すると、後続スキルが「より良い選択肢」を提示する余地を奪うから。要求仕様書は「何を・なぜ・誰のために」までで止め、「どう実現するか」は空けておく。

## 入力の前提

- **ある程度整理済み**: 関係者間で議論を経て論点が一定収束している(が、まだ仕様化されていない)
- **粒度が不揃い**: 具体的に確定したもの(「SSOに Entra ID を使う」)と方向性だけのもの(「お気に入り機能がほしい、詳細は任せる」)が混在する
- **形式は不問**: 議事録・メモ・Slack 抜粋・口頭要望の書き起こし・Issue 文面など。複数情報源にまたがり、矛盾・重複・呼称揺れを含みうる

## 中核となる原則

要求仕様書の品質は次の4原則で決まる。進め方・フォーマット・自己点検はすべてこの4原則の適用なので、迷ったらここに戻る。

### 原則1: What/Why に集中し、How には踏み込まない

答えるべき問い — **What**(何を達成したいか) / **Why**(なぜ必要か) / **For whom**(誰のため)。
答えてはいけない問い — **How**(どんなUI/アーキテクチャ/ライブラリ/テーブルか) / **When**(実装順) / **Where**(変更するファイル)。

その場で効く一文判定: **書こうとしている一文は「実現できたか確認する条件」か、「どう実現するかの案」か。** 前者(要求)は残し、後者(How)は捨てる。

例外: ステークホルダーが「Microsoft Entra ID を使う」「既存の通知基盤に乗せる」と実装上の事項を所与として指定している場合は、**「制約条件」として記録**する。Howに踏み込んだのではなく、Howの一部が外から与えられた枠として渡されている、という整理。「外から与えられて動かせない枠」(制約として記録)か「枠の中でどう作るかの案」(How、扱わない)かで切り分ける。

### 原則2: 要求ごとの「具体度」を明示する

各要求に次のいずれかを付ける。下流はこの区別を頼りに「所与として扱うもの」と「これから詰めるもの」を切り分けるため、これがこのスキルの核。

- **[決定]**: 機能内容が具体的に確定。後続スキルは所与として扱える。
- **[方向性]**: やりたい方向はあるが具体は未定。後続スキル([2])が選択肢を出して提案すれば前進できる。
- **[要検討]**: 関係者間の合意形成が必要で、選択肢提示だけでは前進しない(意見対立・複数案併記・ポリシー/法務/スコープ判断など)。

判定の核は「**この記述だけで、下流は追加の意思決定なしに実装へ渡せるか**」であって、書き手や関係者の確信度・語調ではない。

- 渡せる(内容が一意に定まる) → **[決定]**
- 方向は分かるが、何かを決めないと進めない → **[方向性]**
- そもそも関係者で割れていて決まっていない → **[要検討]**

[方向性]と[要検討]の判別: 「選択肢を並べて見せれば判断が前に進む」なら[方向性]、「選択肢を見せるだけでは不十分で合意形成プロセスが要る」なら[要検討]。

迷ったら具体度の**低い側**(方向性・要検討寄り)へ倒す。理由は誤りのコストが非対称だから — 未確定を確定と誤ると下流で意思決定の必要性が顕在化せず手戻りを招くが、確定を方向性に倒しても下流は「念のため確認」するだけで済む。

### 原則3: 補完は「自然に導出可能な範囲」に限定する(捏造を防ぐ)

補完してよい — 入力全体から自明な前提(「ログイン改修」なら「既存ユーザーが影響を受ける」)、論理的に明らかなスコープ境界(「PCブラウザのみ」なら「モバイルは対象外」)、用語の呼称統一。

してはいけない補完は2系統:

1. **方向性だけの要望に、入力にない具体を確定として足す** — 上限数・UI・付随機能などを勝手に決めない。書かれていない細部は未解決点として残す。
2. **入力に明示のない非機能・付随ユースケースを推測で足す** — 「セキュリティも要るだろう」「ログも欲しいはず」を要求として書かない。**非機能は入力に明示があったものだけ**。

判定基準: 補完しようとする情報を消したら要求仕様書として読めなくなるか。読めなくなる=自然な補完、読めるが情報が増えるだけ=過剰な補完。

気づいた観点を捨てる必要はない。**ただし要求として断定せず「問い」(原則4)に落とす** —「〜の観点は入力に明示がない。後続で要検討か」と置く。観点の洗い出しは下流の責務だから、ここで先取りして確定させない。

### 原則4: 対立・不確実性は解消せず「見える状態」にする

あなたの仕事は対立を**解決すること**ではなく、対立が**見える状態**にすること。関係者間で矛盾・対立する要望(Aは「メール通知」/Bは「アプリ内通知」)を、片方に倒したり統合したりして見かけ上解消してはいけない。隠すと、本来必要な合意形成が下流や関係者から見えなくなる。

対立の可視化には2つの置き場を**両方**使う:

- **要求一覧のラベル**: 対立・未決を含む要求は、その要求**自体を[要検討]ラベル**にする(原則2)。対立する両論は補足に併記する。ここで粗いまま[方向性]でくくると、下流はラベルを見ただけでは対立に気づけない。**ひとつの要求の中に確定部分と対立・未決部分が混在する場合は要求を分割し**、確定部分は[決定]/[方向性]、対立・未決部分は[要検討]として、それぞれが下流にラベルで見えるようにする(例: 「通知チャネル拡充」を、合意済みのアプリ内通知=[方向性]と、部署間で割れているプッシュ通知=[要検討]に分ける)。
- **要検討事項(§5)**: 同じ論点の詳細(何が対立し、何を決める必要があるか)を「問い」の形で残す。

不確実・曖昧・未決の点は「問い」の形で残す。論点名だけ・「要検討」だけでは引き継ぎにならない。次の3点が分かる形にする:

- **何が不明か**(具体的に)
- **なぜ重要か**(決まらないと下流の何が止まるか)
- **どこで・誰が詰めるか**(後続のどのフェーズ/どのステークホルダー)

> 悪い例: 「・お気に入りの上限数は要検討」
> 良い例: 「・お気に入りの上限数: 入力に記載なし。無制限とするか UX/パフォーマンス観点で上限を設けるかの判断が要る(後続の機能選択肢洗い出しで扱う想定)」

## 進め方

入力を受け取ったら次の手順で進める。各ステップは上の原則の適用なので、判断に迷ったら原則へ戻る。

なお、このスキルはサブエージェントに分割せず単独で進める。複数情報源にまたがる矛盾・重複・呼称揺れの検出と要求の集約は、入力全体を1つの文脈に保持して初めて成立するため、情報源ごとに分けると逆効果になる。

1. **俯瞰と一次分解** — 入力全体を読み、トピックを「機能要求/非機能要求/制約条件/背景情報」に分類。要約せず元の情報を失わない粒度で抽出する。あわせて関連の強いトピックをテーマでクラスタリングする(例:「コメント投稿」と「コメントへの返信」は同じコメントテーマ)。このテーマは出力の並び順とグループ見出しに使い、後続の機能選択肢洗い出しでも「どの範囲をまとめて考えるか」の単位になる。
2. **具体度ラベリング**(原則2) — 各要求に [決定]/[方向性]/[要検討] を付ける。
3. **補完と用語統一**(原則3) — 論理的に導出可能な範囲だけ補い、呼称を統一する。
4. **要検討事項の抽出**(原則4) — 曖昧さ・矛盾・抜け漏れを「問い」の形にする。
5. **構造化出力** — 下記フォーマットで生成する。
   - **出力先**: ユーザー指定がなければ `docs/plans/<機能名>/request-spec.md`(`<機能名>` はケバブケース)。後続スキルの成果物も同じディレクトリ配下にまとまる前提。
   - **既定フォーマットを使う**。プロジェクト内に既存の要求仕様書らしきファイル(`docs/plans/`, `docs/specs/`, `docs/requirements/` 配下等)を見つけた場合は、その存在をユーザーに伝え、明示的に「既存フォーマットに合わせて」と指示された場合のみ既定を離れる。既定フォーマットは後続スキルが扱える構造を前提に設計されているため、旧版や別目的のフォーマットに自動で合わせると後続フローで必要情報が欠ける。

## 成果物のフォーマット

次のセクションで構成する。**セクション順序とフィールド形式は維持する**(後続スキルがこの構造を機械的に走査して前提にするため)。

```markdown
# 要求仕様書: <機能・改修の名称>

## 1. 背景と目的
<なぜ必要か / どんな課題を解決するか / 達成したい状態 / 主要なステークホルダー>

## 2. 対象範囲
### 2.1 含むもの
### 2.2 含まないもの   <明示的に対象外とする合意事項>
### 2.3 前提条件       <入力から自然に導出される / 合意済みの前提>

## 3. 要求一覧
```

関連の強い要求が隣り合うよう、テーマ単位でまとめて並べる。要求が多くテーマで束ねたほうが把握しやすければテーマ小見出し(`###`)を置きその下に各要求(`####`)を並べる。少数でテーマ分けの意味が薄ければ見出しなしで `### 3.1` から直接並べる。**要求IDはテーマをまたいでフラットな連番(3.1, 3.2, …)を維持する** — 後続スキルが `R3.1` のように参照するため、テーマ分けで番号を枝分かれさせない。

各要求の形式:

```markdown
#### 3.1 <要求の名前>
- **具体度**: [決定] | [方向性] | [要検討]
- **What**: <何を達成したいか>
- **Why**: <なぜ必要か>
- **For whom**: <誰のため>
- **制約条件**: <ステークホルダーが指定した実装上の制約。なければ「該当なし」>
- **補足**: <入力にあった具体情報のうち上記に収まらないもの。なければ「該当なし」>

## 4. 非機能要求
<性能・セキュリティ・可用性・運用など。入力に明示があれば記録。明示がなければ「該当なし」と書く(原則3: 観点の推測列挙はしない)>

## 5. 要検討事項
各項目を次の形式で(原則4):
- **論点**: <何が不明・未決・矛盾しているか>
- **重要度の根拠**: <なぜ決める必要があるか>
- **想定する解決フェーズ**: <後続のどのスキル/フェーズで扱うか>

## 6. 関連情報
<元入力の所在(議事録ファイル名 / Issue URL / Slack スレッド等)と外部参考資料のみ。本文と重複する要約は書かない。呼称を統一した場合はその対応表>
```

**全セクションを必ず置く**。該当する内容がなければ見出し直下に「該当なし」と明記する。理由: 後続スキルはこの構造を前提に動くため、「セクションが無い」(書き忘れの疑いが残る)と「あって該当なし」(検討した上での積極判断)は意味が違う。必須なのは見出しレベルのセクションであり、「あれば」「省略可」「該当する場合」と明記された下位項目・サブセクションは省略してよい。

## 引き渡し前の自己点検

各原則を守れたかを、出力前に次の問いで点検する(詳細は対応する原則を参照):

- **How混入** — 後続フェーズ([2][3][4])が扱う情報(UI/コード位置/アーキテクチャ/実装順)を先取りしていないか(原則1)
- **勝手な具体化** — 方向性だけの要望に入力にない具体を確定として足していないか。非機能・付随機能を推測で加えていないか(原則3)
- **語調での判定** — ラベルを情報の具体度で判定したか、書き手の確信度で判定していないか(原則2)
- **矛盾の解消** — 対立・複数案を片方に倒さず[要検討]として保持したか(原則4)
- **抽象的な要検討** — 要検討事項が「何が不明/なぜ重要/どこで詰めるか」を伝える形になっているか(原則4)
- **関連要求の離散** — 関連の強い要求をテーマで隣接させたか(進め方1)

## 出力後にユーザーに確認すること

生成したら次のうち**特に重要な点に絞って**確認する(全部を一度に聞かない):

- [方向性]/[要検討] ラベルの判定が妥当か(具体度判定はこのスキルの肝で後続フローに直結)
- 補完した前提・スコープ境界が入力の意図と合っているか
- 要求一覧のテーマ分け・並び順が把握しやすいか
- 要検討事項の論点に漏れがないか
- 出力先パスの `<機能名>` で問題ないか
- 既存の要求仕様書らしきファイルを検出した場合、既定フォーマットのままでよいか
