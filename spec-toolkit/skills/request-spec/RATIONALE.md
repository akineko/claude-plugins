# request-spec 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md の内容は再掲せず参照に留める。

## 目的と背景

ステークホルダー間で議論が一定収束したが、まだ形式化されていない要望群を、後続の設計フェーズが安心して取り込める「要求仕様書」に構造化する。情報を増やす（具体化する）のではなく、What/Why/誰のため を保ったまま整え、**「何が確定で・何が未解決か」を下流が判別できる状態**を作るのが本質。実現手段（How）には踏み込まず、下流が「より良い実現方法」を選ぶ余地を残す。パイプライン（request-spec → feature-options → impact-analysis → implementation-design）の最初段。

## 中核的な設計判断

### 具体度ラベル [決定]/[方向性]/[要検討]
- **決定**: 各要求に3値ラベルを付ける。判定の核は「この記述だけで、下流は追加の意思決定なしに実装へ渡せるか」。迷ったら具体度の低い側へ倒す。
- **却下した代替案**: 書き手の確信度・語調で判定する案。語調と実際の具体度はしばしばズレる。
- **防いでいる失敗**: 未確定を確定と誤認すると、下流で意思決定の必要性が顕在化せず手戻り・見落としを招く（誤りコストが非対称＝確定を方向性に倒す方が安全）。
- **出所**: 元設計の核。eval 3シナリオ（concrete-sso / direction-favorites / mixed-conflict）がこの区別を直接 assert。

### [方向性] と [要検討] の実務的判別
- **決定**: 「選択肢を並べて見せれば前進する」なら[方向性]、「合意形成プロセス（部門調整・ポリシー・法務）が要る」なら[要検討]。
- **出所/earned wisdom**: 下流 feature-options が[方向性]に対し選択肢を出すという挙動を知っているから引ける軸。下流の動作を把握していないと出てこない（ゼロベース再設計では新設計がこの軸を再現できず、現行の earned wisdom と確認された）。

### 固定スキーマ＋全セクション必須＋「該当なし」明記
- **決定**: 6セクション固定。該当内容がなくても見出しを残し「該当なし」と書く。
- **防いでいる失敗**: 後続スキルがこの構造を機械的に走査する前提。「セクション不在（書き忘れの疑い）」と「あって該当なし（検討済みの積極判断）」は意味が違う。
- **出所**: 元設計。2026-05 の再設計で新版が「レイアウト柔軟化」を提案したが、下流契約への構文依存ゆえ退行と判断し**維持**。

### 要求ID はテーマをまたぐフラット連番・枝分かれ禁止
- **防いでいる失敗**: 後続が `R3.1` のように参照するため、テーマ分けで番号を枝番にすると参照が壊れる。テーマでグループ化したい欲求と ID 安定性の衝突を実地で検出した結果。

### 既定フォーマット固定＋既存ファイル追従ガード
- **決定**: プロジェクト内に既存の要求仕様らしきファイルがあっても自動では合わせず、ユーザーが明示指示した場合のみ離れる。
- **防いでいる失敗**: 旧版スキルの成果物や別目的フォーマットに引きずられると、後続フローで必要な情報（具体度ラベル等）が欠ける。

### disable-model-invocation: true（明示起動専用）＋短い description
- **決定**: モデルによる自動起動を切り、スラッシュ/明示起動専用にする。description は1文で足りる。
- **却下した代替案**: 自動起動前提でトリガーフレーズ・除外境界を厚く書く長文 description。
- **理由**: パイプラインの明示的な段であり、前段成果物が前提のスキルを文脈マッチで誤起動させない。パイプライン全体の起動方針。

### 単独実行（サブエージェントに分割しない）
- **理由**: 複数情報源にまたがる矛盾・重複・呼称揺れの検出と要求の集約は、入力全体を1つの文脈に保持して初めて成立する。情報源ごとに分けると横断的な突き合わせが分断され逆効果。

### 元入力の保全（ファイル実体のない入力）【2026-07追加】
- **決定**: 入力がコマンド引数・対話テキスト等でファイル実体を持たない場合、`docs/plans/<機能名>/` 配下への保存を推奨としてユーザーに確認し、`6. 関連情報` からパス参照する。
- **防いでいる失敗**: 実運用で §6 の元入力が「コマンド引数として提示された記述」となり、会話が消えると要求の原典を辿れず、補完・ラベル判定の妥当性を検証する監査線が空文化していた。§6 の存在意義(原典への遡行)を担保する。
- **出所**: 2026-07-17 実運用成果物の横断レビュー。

### 未確定の詳細は §5 が唯一の置き場（補足は1行要約＋参照）【2026-07追加】
- **決定**: 原則4の2つの置き場（要求のラベル・補足 / §5 要検討事項）の役割分担を精緻化。補足は「何が未確定か」の1行要約＋「(5.n 参照)」に留め、選択肢の中身・重要度・解決フェーズの詳細は §5 だけに書く。
- **防いでいる失敗**: 実運用成果物で、要求の補足と §5 の論点記述がほぼ同文の二重記述になった。更新時に片方だけ直ると §5 と要求で言うことが食い違う。「下流がラベル・補足だけ見ても未確定に気づけるべき」という既存解釈（存在の可視化）は補足の1行要約で維持され、詳細の一元化と両立する。
- **出所**: 2026-07-19 実運用成果物の横断レビュー。implementation-design 原則6（不変条件は 2.2 が唯一の定義箇所）と同じ「1情報1箇所」の request-spec 版。

### §1 の「達成したい状態」「主要なステークホルダー」をラベル付き項目に【2026-07追加】
- **決定**: §1 背景と目的を「背景の文章＋末尾にラベル付き項目(達成したい状態 / 主要なステークホルダー)」の構成にした。
- **防いでいる失敗**: 一括プレースホルダの段落形式では、読み手が「ステークホルダーは誰か」を段落から探すことになる。実運用成果物が自発的にラベル付き段落にしており、その形式の公式化(implementation-design の決定 ID と同じ「実運用の自発形式の公式化」パターン)。背景の物語性は文章部分で維持する。
- **出所**: 2026-07-19 実運用成果物の横断レビュー。

### 記法規律（構造を潰した圧縮の禁止）【2026-07追加】
- **決定**: implementation-design で導入した記法規律（1項目1主張・段落内(1)(2)列挙の禁止・括弧内文の禁止・同格対象の見出し区切り）をテンプレート冒頭コメントと自己点検に展開。
- **防いでいる失敗**: 実運用成果物で、要求の補足に2つの独立した未確定事項が1段落に詰め込まれた。本スキルは本体が直接成果物を書くため（実装設計のようなエージェント定義側の規律が効かない）、テンプレートが記法の唯一の注入点。
- **注**: 記法ブロックは request-spec / feature-options / impact-analysis / quick-design の4テンプレートに同文で再掲している。スキルが実行時に他スキルのファイルを読まない独立性を優先した意図的な重複で、文言を変える場合は4テンプレート＋implementation-design 側を同期する。
- **出所**: 2026-07-19 実運用成果物の横断レビュー（implementation-design 記法規律の水平展開）。

## 解釈・仮定（要確認）

- **原則4「対立は可視化する」の置き場の解釈**: 当初「両論を[要検討]として並記」という表現が、ラベル化と要検討事項への切り出しの間で曖昧だった。eval（mixed-conflict）で対立が[要検討]ラベルから消える挙動を観測し、「対立は **要求自体を[要検討]ラベル**にし、混在時は要求を分割。詳細は要検討事項にも残す」と明確化した（2026-05）。⚠️ 「下流がラベルだけ見ても対立に気づけるべき」という解釈に基づく。2026-07 に「詳細は要検討事項**にも**残す」の二重記述を許す読みを廃し、補足=1行要約＋参照 / §5=詳細、の役割分担に精緻化（上記「未確定の詳細は §5 が唯一の置き場」参照）。
