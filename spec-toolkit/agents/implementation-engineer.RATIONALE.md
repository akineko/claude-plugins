# implementation-engineer 設計ノート

> 定義=implementation-engineer.md / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。
> phase-implementation スキルのオーケストレーションの一部。全体設計(実装/検証の分離・差し戻しループ・ハーネス範囲)は `../skills/phase-implementation/RATIONALE.md` 参照。

## 中核的な設計判断

### 【load-bearing】完了判定を担当外にする
- **決定**: 自分のテスト実行を「作業確認」と位置づけ、完了判定は completion-verifier の領分と明記。
- **防いでいる失敗**: 実装者の自己申告による幻覚的完了。これを消すと本体スキルの原則4(独立検証)が実装側から崩れる。

### 【load-bearing】TDD 規律をスキル本文でなくエージェント定義に置く
- **決定**: Red→Green→Refactor の規律・「テストが書けない契約は理解が曖昧」の判断基準をこの定義に集約。呼び出し側の依頼文には対象の特定情報だけを書かせる(SKILL.md Phase 2)。
- **理由**: 規律を依頼文で毎回転記すると、依頼の書き方次第で規律が薄れる。定義に置けば呼び出しパスに依らず一貫する。implementation-design(設計書側)がプロセス中立になったため、TDD の出所はここが唯一。

### 契約逸脱時の振る舞いを深刻度で2分する
- **決定**: 軽微な曖昧さ=解釈して進め報告 / 契約の矛盾=中断して差し戻し。分岐点は「契約(3.x)を変えずに実装内部の判断で吸収できるか」。
- **却下した代替案**: 全件エスカレーション(往復過多で原則4の確認最小化と矛盾)・全件自己解釈(黙った逸脱で設計書と実態が乖離)。
- **既存実装との衝突を中断側に明示(2026-07-02)**: 当初の文言は「契約同士の衝突」のみで、「契約と既存実装の衝突」(影響分析の見逃し起因)は読み込み任せだった。実装エージェントが「契約同士は矛盾していない」と解釈側に倒し既存側を歪めるリスクがあるため、ユーザー確認のうえ明示した。

### tools に編集系(Write, Edit)と Bash を持つ
- spec-toolkit の既存エージェントは全て読み取り専用だった。本エージェントは実装担当のため唯一編集を持つ。Agent(再委譲)は持たせない — 実装の再委譲はオーケストレーション構造を不透明にする。
