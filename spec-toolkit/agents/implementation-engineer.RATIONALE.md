# implementation-engineer 設計ノート

> 定義=implementation-engineer.md / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。
> phase-implementation / plan-implementation 両スキルのオーケストレーションの一部。全体設計(実装/検証の分離・差し戻しループ・ハーネス範囲)は `../skills/phase-implementation/RATIONALE.md`、連続実行・コミットに固有の決定は `../skills/plan-implementation/RATIONALE.md` 参照。

## 中核的な設計判断

### 【load-bearing】完了判定を担当外にする
- **決定**: 自分のテスト実行を「作業確認」と位置づけ、完了判定は completion-verifier の領分と明記。
- **防いでいる失敗**: 実装者の自己申告による幻覚的完了。これを消すと本体スキルの原則4(独立検証)が実装側から崩れる。

### 【load-bearing】TDD 規律をスキル本文でなくエージェント定義に置く
- **決定**: Red→Green→Refactor の規律・「テストが書けない契約は理解が曖昧」の判断基準をこの定義に集約。呼び出し側の依頼文には対象の特定情報だけを書かせる(SKILL.md Phase 2)。
- **理由**: 規律を依頼文で毎回転記すると、依頼の書き方次第で規律が薄れる。定義に置けば呼び出しパスに依らず一貫する。implementation-design(設計書側)がプロセス中立になったため、TDD の出所はここが唯一。

### 契約逸脱時の振る舞いを深刻度で2分する
- **決定**: 軽微な曖昧さ=解釈して進め報告 / 契約の矛盾=中断して差し戻し。分岐点は「契約(3.x)を変えずに実装内部の判断で吸収できるか」。
- **却下した代替案**: 全件エスカレーション(往復過多で原則4の確認最小化と矛盾)・全件自己解釈(黙った逸脱で設計書と実態が乖離)。
- **既存実装との衝突を中断側に明示(2026-07-02)**: 当初の文言は「契約同士の衝突」のみで、「契約と既存実装の衝突」(影響分析の見逃し起因)は読み込み任せだった。実装エージェントが「契約同士は矛盾していない」と解釈側に倒し既存側を歪めるリスクがあるため、ユーザー確認のうえ明示した。

### コードコメントの規律を定義に置く(密度は追従・設計書転記は禁止・フェーズ境界 TODO のみ例外)
- **決定**: コメントの密度・粒度を「既存コードへの追従」の列挙に加え、プロジェクト側のコメント規約(`.claude/rules/` 等)があれば優先。内容面は「設計書の判断ラベル・節番号・採用理由・フェーズ計画の転記禁止」「コードの言い換え禁止」を明示。フェーズ分割が生む誤解を招く中間状態のみ `TODO(フェーズN): <説明>` 形式のコメントを許可し、解消フェーズの実装時に検索して削除させる。
- **TODO 形式にした理由(ユーザー提案)**: 自由文の「フェーズNで解消」マーカーは検索キーが安定せず、後続フェーズの実装者が削除し損ねる。TODO なら grep・エディタハイライト・lint の既存エコシステムに乗り、「一時的な中間状態」という慣習的シグナルにもなる。フェーズ番号だけの TODO は設計書なしで解読不能になるため、説明の自由文を必須にしている。
- **防いでいる失敗**: 実運用(2026-07、バックエンドのフェーズ実装)で、生成コメントの過半が設計書の判断ラベルの転記・フェーズ参照・コードの言い換えとなり、コメントほぼ0行の既存コードから浮いた。原因は (a) コメント方針の不在、(b) 契約遵守と解釈報告の強い要求が「設計意図の保存=コメント転記」へ誘導、(c) 追従の列挙にコメントが無く追従対象と認識されない、の複合。完了検証は意図的に品質を見ない(スキル側 RATIONALE「ハーネスの範囲」)ため、生成時に防ぐしかない。「失敗5」を規則本文と重ねて置くのは、(b) の誘導に対する定義内の既存の型(規則＋補強の失敗エントリ)に合わせたもの。
- **出所**: 2026-07-22 実運用フィードバック。

### tools に編集系(Write, Edit)と Bash を持つ
