# completion-verifier 設計ノート

> 定義=completion-verifier.md / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。
> phase-implementation / plan-implementation 両スキルのオーケストレーションの一部。全体設計(実装/検証の分離・差し戻しループ・ハーネス範囲)は `../skills/phase-implementation/RATIONALE.md`、連続実行・コミットに固有の決定は `../skills/plan-implementation/RATIONALE.md` 参照。

## 中核的な設計判断

### 【load-bearing】編集ツールを持たない
- **決定**: tools は Read, Grep, Glob, Bash 系のみ。Write/Edit を意図的に外す。
- **防いでいる失敗**: 「見つけたら直す」で実装と検証の分離が崩れ、修正の正しさを検証する者がいなくなる。Bash があるため技術的には編集可能だが、定義本文の担当外と併せて二重に抑止する(Bash はテスト実行に必須で外せない)。

### 【load-bearing】テストを自分で実行する
- **決定**: 実装報告のテスト結果を信用せず、完了条件テストとリグレッションを自分のセッションで実行する。
- **防いでいる失敗**: 伝聞検証。実装者の実行結果の転記では、実行環境・実行範囲の差異や報告の誤りを検出できず、検証者の存在意義が消える。

### 検証は3点で固定し、逸脱は「所見」に隔離する
- **決定**: 完了条件テスト・リグレッション・契約整合の3点だけが合否に影響する。それ以外の気づきは所見として分離報告。
- **理由**: 品質・セキュリティレビューは実装後の別工程(スキル RATIONALE「ハーネスの範囲」参照)。所見チャネルを用意したのは、観点外の重大な気づきを完全に捨てさせると隠れた問題が消失するため — 合否に混ぜず、捨てもしない中間の出口。

### 不合格項目に「期待・実際・該当箇所」を必須化
- **決定**: 3点セットが揃わない指摘は不合格項目にできない(所見行き)。
- **防いでいる失敗**: 曖昧な差し戻しで implementation-engineer の修正が再び解釈任せになり、差し戻し上限(2回)を空転で消費する。
