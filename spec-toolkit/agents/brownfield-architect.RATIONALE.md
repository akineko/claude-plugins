# brownfield-architect 設計ノート

> 定義=`brownfield-architect.md` / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。
> implementation-design の3アーキテクト構成の批評役。全体の設計は `../skills/implementation-design/RATIONALE.md` 参照。

## 役割と位置づけ

greenfield 骨格が現実のコードベースに乗ったときのコスト・リスク・整合性を独立視点で点検する**批評役**（既存パターン整合・移行コスト・障害リスク・段階導入）。

## 中核的な設計判断（load-bearing）

### 独立した代替設計案を出さない／局所修正の提案に絞る
- **理由**: 別の完全な設計案を出すと、本体が「greenfield vs brownfield のどちらを選ぶか」の二者択一になり、両者の良さを統合できない。「批評＝置換可能な局所修正」に絞ることで本体が選択的に取り込める。
- **注意**: これがマルチエージェント統合が成立する核の一つ。「全体差し替え」に化けたら担当外。

### 指摘＋推奨調整はセット（規範的主張だけで終わらせない）
- **理由**: 「既存パターンに反する」だけでは本体が何を採るか決められない。骨格をどう調整すれば緩和されるかまで書く。

### 同型付随エンティティの配信前例を定型観点として定義に持つ【2026-07追加】
- **決定**: 骨格が新設エンティティを含む場合、同じ関係形（親に付随するエンティティ等）の既存実装が単一取得・一覧・mutation の各 API レスポンスでどう配信されているか（include の範囲）の前例確認を、担当範囲の定型観点として**エージェント定義側**に持たせた（呼び出し側の依頼テンプレではなく）。
- **防いでいる失敗**: 実運用（バックエンド設計バッチ）で新設エンティティの配信方式が3回の改訂を経て、既存の同型前例（親に付随する既存エンティティの全経路 include 配信）と同じ形に収束した。この前例はユーザーが指摘するまで批評に現れなかった（スキーマ規約の前例は調査したが配信の前例は観点になかった）。
- **却下した代替案**: implementation-design の Phase 2 批評依頼テンプレに載せる（本体が新設エンティティの有無を条件判定して渡す形）。本体の判定漏れがそのまま観点漏れになり、「観点になかったから調べなかった」という今回の失敗形が残るため却下。定義側なら brownfield 自身が毎回判定し、該当がなければ「該当なし」になるだけ。
- **出所**: 2026-07-15 実運用フィードバック提案6。

### tools に Bash 系を持つ（3アーキテクト中唯一）
- **理由**: 批評の価値は「現状コードを踏まえた点検」にあり、Read/Grep/Glob の読解に加え依存関係・テスト状況・ビルド構成の確認に Bash が有用。greenfield は要件理解の読解のみ、domain-first は要求文書の語彙参照のみで足りるため持たない。
- **出所**: 初期設計時の判断だが理由が未記録だったため、2026-07 レビューで遡及推定して記録。

## 今回の検証で確認したこと（2026-05）

実コードベースで、`client.ts`（get/post のみ→解除の DELETE 回避を推奨）・`db.ts`（単一キーのみ→複合キー冪等 upsert と明記を推奨）・server エントリ欠落（前提整備の先行を必須指摘）を**行番号付きの観察事実ベース**で批評し、**全て局所修正・代替設計の全面提示なし**を遵守した。能動コード観察という独立視点が単独スキルでは代替しにくいことの実証。
