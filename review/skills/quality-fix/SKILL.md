# コードレビュー修正ループ

quality-review が出す統合判断（対応区分つきの指摘）を起点に、「要対応」の修正と再レビューを自動で繰り返し、要対応が尽きた状態の作業ツリーを残すスキル。

役割分担は quality-review の二段構えに、修正の「手」を足した三層:

- **専門レビュアー**（`review:quality-review-correctness` / `-design` / `-performance`）は各レーンの所見に深刻さだけを付ける（quality-review と同一のエージェントをそのまま使う）。
- **あなた（メインエージェント）** は統合・対応区分の裁定・修正方針の決定・裁定の引き継ぎ・収束判定を担う。コードは直接編集しない。
- **修正者**（`review:quality-fix-implementer`）は確定済みの方針を最小差分で適用し検証する。裁定はしない。

このスキルは途中でユーザー確認を挟まずに作業ツリーを書き換え続ける（それがこのスキルを明示起動する意味）。止まるのは 収束・上限到達・停止条件（後述）のいずれかだけ。コミットはしない。

用語: **ラウンド** = 修正 → 再レビュー → 統合の1周。ラウンド0は初回レビュー（修正なし）。上限（既定3、`--max-rounds N` で変更）は修正ラウンド数で数える。

## 進め方

### 1. 起点を解決する（ラウンド0）

初回レビュー結果を次の分岐で用意する:

- **この会話に quality-review の報告があり、その報告以後レビュー対象のコードに変更がない**（会話履歴と `git status` / `git diff` で確認）→ その報告の指摘・対応区分・裁定をラウンド0として採用し、対象（git range 等）も報告から引き継ぐ。
- **それ以外**（対象が引数で指定された・報告がない・報告後にコードが変わった・判断に迷う）→ `../quality-review/SKILL.md` を読み、その手順1〜3（対象の解決・専門家への並列ディスパッチ・統合と客観判断）を実行してラウンド0を作る。手順4の単体報告は出さない（結果は次の開始宣言に畳む）。迷ったら自前レビューに倒す — 古い報告を信じて誤修正するより一周のコストの方が安い。

ラウンド0の要対応が0件なら、ループに入らず内訳（要相談・別対応・任意・見送り）を短く報告して終了する。

ループに入る前に1度だけ **開始宣言** を出す: 対象・修正する要対応の一覧（ID と一行所見）・上限ラウンド数。確認は求めず宣言して進む（ユーザーが誤起動に気づける最後の窓として）。

### 2. 修正方針を確定する

各要対応について、裁定時に読んだ周辺文脈と指摘の推奨を基に修正方針を確定する: 何を・どのファイルのどこを・どう変えるか、何は変えないか（修正の波及先＝追従が必要な呼び出し側も範囲に含めて特定する）。方針は修正者がそのまま実行できる具体度で書く — 修正者は会話の文脈を持たない。

この時点で「直し方がコード外の選択（規約・方針・業務判断）に依存する」と判明した指摘は要相談へ降格し、修正ログに記録する。方針が書けない指摘を修正者に丸投げしない。

### 3. 修正を委譲する

`review:quality-fix-implementer`（Agent ツール）に修正を委譲する。

- 割当: 同一ファイルに触れる指摘は1つの委譲にまとめる。ファイル集合が交差しない委譲だけを同一メッセージで並列起動する（並列編集の衝突防止）。
- 渡すもの: 指摘（ID・箇所・所見・根拠）／確定した修正方針／触ってよいファイル範囲／検証コマンド（プロジェクトのテスト・ビルド・リンタを特定して渡す。特定できなければ「関連する検証を自分で特定して実行」と指示）。中断条件はエージェント定義済みなので簡潔でよい。
- 中断報告が返ったら、あなたが再裁定する: 方針の誤りなら方針を直して再委譲／コード外の判断が必要なら要相談へ降格／指摘自体が成立しないと判明したら見送りへ変更。いずれも修正ログに記録する。

### 4. 再レビューする

修正の適用後、専門レビュアーを並列起動して再レビューさせる。起動要領・渡す情報・レーン増減の規律は quality-review の手順2と同じ。ただしループ固有の2点:

- 対象は「初回対象の差分＋ループ中の修正」。取得コマンドはあなたが組み立ててレビュアーに明示する:

| 初回対象 | 再レビューの取得 |
|---------|----------------|
| 未コミット変更全体（`git diff HEAD`） | そのまま `git diff HEAD`（修正も未コミット変更として自然に含まれる） |
| staged / unstaged 限定 | `git diff HEAD` に広げる（修正がどちらに落ちるかで対象が欠けるため、作業ツリー全体で見る） |
| ブランチ（`git diff <base>...HEAD`） | `git diff <base>`（作業ツリーとの比較に切り替え） |
| コミット・範囲・PR | 元の差分と `git diff`（作業ツリーの修正）の2本を明示し、両方を見せる |

- レビュアーに前ラウンドの指摘・裁定・「これが修正ループの何周目か」を **渡さない**。フレッシュな目で見させ、蒸し返しの抑制は次の手順の裁定引き継ぎで行う。「前回見送った点は指摘するな」と教えると、先入観で新規の実問題まで拾わなくなる。

### 5. 統合し、裁定を引き継ぐ

quality-review の手順3（重複統合・相違検出・対応区分の付与）を実行した上で、ループ固有の突合を **裁定台帳**（ループ内で保持する 論点 × 裁定 の記録）と行う:

- **裁定の引き継ぎ**: 過去ラウンドで見送り／任意／別対応／要相談と裁定した論点（同一箇所・同一趣旨）が再出現したら、同じ裁定を引き継ぐ。再裁定するのは、新しい所見がその裁定の根拠を崩す事実を含むときだけ（引き継ぎを外した理由を修正ログに記録）。これがないと、フレッシュなレビュアーが同じ指摘を挙げ続けてループが収束しない。
- **修正済みの再出現**: 前ラウンドで修正した論点が再指摘されたら、修正不十分として方針を変えて再修正する（1回まで）。2度目も消えなければ **収束不能** として要対応から外し、最終報告の残件に載せる（同種修正の無限反復を防ぐ）。
- **新規の要対応**: 次ラウンドの修正対象にする（修正が新しい問題を生むのは正常。そのための再レビュー）。

### 6. 収束を判定する

- 要対応が0（収束不能を除く）→ 収束。最終報告へ。
- 要対応が残り、完了した修正ラウンド数が上限未満 → 手順2へ戻る。
- 上限到達 → 停止。残った要対応と「なぜ収束しなかったか」を最終報告に明記する。

## 停止条件（ループを中断してユーザーへ返す）

自動ループの前提が崩れたら、収束を待たずに停止して報告する。黙って続けない:

- 修正者の中断が、方針の再裁定でも解けない設計レベルの問題を示した（直すべきものの定義自体が変わる）
- 修正起因でテストが壊れ、方針の範囲内で回復できない
- レビュー対象がループの外で変化した（ユーザーや別プロセスが並行してコードを変えた形跡）

停止時は、どこまで修正したか・作業ツリーの状態・選択肢（2〜3個＋推奨と理由）を添える。

## 報告フォーマット

最終報告は下記を会話内に出す（途中の各ラウンドはこのフォーマットを繰り返さず、1〜2行の経過報告に留める）。

```
# コードレビュー修正ループ: <対象の説明>

対象: <解決した範囲>（起点: 会話の quality-review 報告 / 自前レビュー）
経過: 修正ラウンド N/上限 M ・修正適用 X 件 ・<収束 / 上限到達 / 停止（理由）>
残件: 収束不能 N ・要相談 N ・別対応 N ・任意 N ・見送り N

総評: <2〜4行。何を直してどう収束したか・残った論点の所在。言及する指摘には ID を併記>

---

## 修正済み
### R<n>-#<m> <深刻さ絵文字> [視点] file:line — 一行所見
- 修正: <何をどう変えたか（修正者の報告の要約）>
- 検証: <実行した検証と結果 / 検証手段なし（理由）>

## 収束不能（修正を試みたが再指摘が消えなかった）
（試した方針・残る所見・推奨する次の一手を厚めに）

## 要相談
（ループ中に修正できなかったコード外判断の論点。何が決まれば直せるか・誰に確認するか）

## 別対応（範囲外）/ 任意 / 見送り
（最終ラウンドの裁定として quality-review の書き方の原則に従う。見送りは棄却根拠を厚めに）

## 修正ログ
（ラウンドごとに1行。裁定の変更・引き継ぎ解除・再修正もここに残す。
例: R1: R0-#1,R0-#4 を修正・R0-#2 を要相談へ降格 / R2: 新規 R1-#1 を修正・R0-#4 を方針変更で再修正 / R3: 再指摘なし・収束）
```

書き方の原則:

- **ID はラウンド接頭辞つき `R<n>-#<m>`**: 各ラウンドの新規指摘に `R<n>-#1` から採番し、初出ラウンドで固定する（ラウンドを跨いでも振り直さない）。quality-review の通し ID は1回の報告内でしか一意でないため、ループを跨ぐ参照には初出ラウンドを含める。会話の quality-review 報告をラウンド0として引き継いだ場合、その報告の `#m` は `R0-#m` とする（ユーザーが見た番号を保つ）。
- 深刻さと対応区分の意味論・「別PR」を本質判断の代わりにしない規律・情報配分（ユーザーが裁定を覆しうる指摘ほど厚く）・強調記号（`**`）を使わない、はすべて quality-review の書き方の原則に従う。
- 修正済みの各項目は、ユーザーが `git diff` で検証できる粒度（ファイルと変更の要旨）で書く。diff 全文は貼らない。
- 変更は作業ツリーに残して終わる。コミット・push はしない（ユーザーが差分を確認してから行う）。

## 対象外

- セキュリティ観点の指摘と修正（quality-review と同じ棲み分け。security-review / security-audit へ案内）
- レビュー結果だけが欲しい場合（→ quality-review）、外部レビューコメントへの対応判断（→ review-response）
- 修正のコミット・PR 作成（作業ツリーまでがこのスキルの責務）
