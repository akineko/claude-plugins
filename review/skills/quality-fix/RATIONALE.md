# quality-fix 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

quality-review の報告後、ユーザーが「#N を直して」→修正→再確認と手動で往復する手間をなくし、指摘の修正から再レビューまでを「直すべきものがなくなるまで」自動で収束させるスキル。ユーザーは quality-review のアウトプット（二軸判断・対応区分つき報告）に満足しており、その裁定の仕組みを信頼の土台として修正まで自動化したいという要望（2026-07-28）が起点。quality-review 本体は変更せず、別スキルとして追加した。

## 中核的な設計判断

### 【load-bearing】quality-review と分離した別スキルにする（本体に修正モードを足さない）
- **決定**: quality-review はレビューのみのまま残し、修正ループは quality-fix として分離。ループの再レビューも既存の3レビュアーエージェントをそのまま再利用する。
- **却下した代替案**: quality-review に `--fix` オプションを足す案。→ ユーザー確認なしで作業ツリーを書き換え続けるスキルは、レビュー専用スキルとは起動の覚悟が違う。別名で明示起動させることが安全装置になる。またユーザーは quality-review のアウトプットに満足しており、本体に手を入れるリスクを取る理由がない。
- **出所**: ユーザー要望（2026-07-28、「別途欲しい」と明示）。

### 起点は両対応（会話の直近レビュー結果を再利用、なければ自前実行）
- **決定**: 会話にこのセッションの quality-review 報告があり対象コードがその後変わっていなければラウンド0として採用、それ以外は quality-review の手順1〜3を自前実行してから始める。迷ったら自前レビューに倒す。
- **却下した代替案**: 常に自前レビュー（直前の結果があってもレビューを二重実行して無駄）／既存結果必須（「一発でレビュー〜修正収束まで」の使い方ができない）。
- **防いでいる失敗**: 古い報告（レビュー後にコードが変わった）を信じて誤修正する事故。安全側（自前レビュー）に倒す条項が対。
- **出所**: リードバック質疑でユーザー選択（2026-07-28、AskUserQuestion で両対応を採用）。

### 【load-bearing】自動修正するのは「要対応」のみ
- **決定**: 要対応だけを修正対象にする。要相談は自動裁定できないため最終報告へ集約、別対応・任意・見送りは報告のみ。
- **却下した代替案**: 任意も含めて全部直す案。→ quality-review の区分意味論で「要対応＝直すべき、かつこの差分の目的の内側」だけが無確認の自動修正を正当化できる。任意（好み）を自動で直すと、ユーザーが望まない変更を確認なしに積む。別対応（範囲外）を直すとこの差分の目的を超えて作業ツリーが膨らむ。
- **防いでいる失敗**: 「自動で走らせたら頼んでいない改変までされた」という信頼の毀損。
- **出所**: quality-review の区分定義（merit×scope）からの論理的帰結。合意の前提として宣言（2026-07-28）。

### 【load-bearing】修正はサブエージェント委譲、メインはコードを編集しない
- **決定**: メインは方針決定・委譲・統合・裁定に徹し、修正の適用は quality-fix-implementer が行う。同一ファイルに触れる指摘は1委譲にまとめ、ファイル集合が交差しない委譲だけ並列化。
- **却下した代替案**: メインが直接修正する案。→ レビュー3体→修正→再レビューを繰り返すループはメインのコンテキスト消費が激しく、実装詳細まで抱えると数ラウンドで枯渇しうる。quality-review の「メイン=判断、サブ=専門作業」の役割分担とも一貫させた。
- **出所**: リードバック質疑でユーザー選択（2026-07-28）。

### 【load-bearing】再レビューはフレッシュ実行＋統合側での裁定引き継ぎ
- **決定**: レビュアーには前ラウンドの指摘・裁定・ループの周回数を渡さず、毎回まっさらにレビューさせる。既裁定論点の再出現は、メインが裁定台帳と突合して裁定を引き継ぐ（新事実が根拠を崩すときだけ再裁定）。
- **却下した代替案**: レビュアーに「前回見送った指摘は挙げるな」と教える案。→ 先入観が入り、除外リストの周辺にある新規の実問題まで拾わなくなる（検出力の低下）。独立性はレビューの質の源泉なので、蒸し返しの抑制は検出側でなく統合側で行う。
- **防いでいる失敗**: (a) 見送り済み指摘が毎ラウンド要対応に再浮上してループが収束しない（引き継ぎがない場合）、(b) レビュアーの検出力低下（除外リストを渡した場合）。両方を同時に避けるための二層構造。

### 収束の三点セット（収束条件・上限・再修正1回）
- **決定**: 収束条件は「要対応0（収束不能を除く）」。修正ラウンド上限は既定3（`--max-rounds` で変更可）。修正済み論点が再指摘されたら方針を変えて再修正は1回まで、2度目は「収束不能」として要対応から外し残件報告する。
- **防いでいる失敗**: 指摘の振動（A を直すと B が出て B を直すと A が出る）や、同じ修正の無限反復でループが止まらない。収束不能を要対応に残すと上限まで空転するため、区分から外して残件に隔離する。
- **出所**: 上限の存在は合意の前提（2026-07-28）。既定値3と再修正1回は設計裁量（大半は1〜2周で収束する想定。実運用で調整前提）。

### quality-review の手順を参照実行する（内蔵しない）
- **決定**: 対象解決・ディスパッチ・統合の詳細は SKILL.md に転記せず、実行時に `../quality-review/SKILL.md` を読んで手順1〜3を実行させる。
- **却下した代替案**: 該当手順を quality-fix に複製する案。→ quality-review が更新されたとき二重管理になり、レビュー挙動が兄弟間で乖離する（1情報1箇所の原則）。同一プラグイン内のスキル連携は積極的に行う方針とも整合。
- **防いでいる失敗**: quality-review だけ改善されて quality-fix のレビュー品質が取り残される更新漏れ。

### ID はラウンド接頭辞つき `R<n>-#<m>`
- **決定**: 各ラウンドの新規指摘に `R<n>-#1` から採番し初出ラウンドで固定。引き継いだ quality-review 報告の `#m` は `R0-#m` に読み替える。
- **却下した代替案**: ループ全体の通し番号。→ どのラウンドで見つかった指摘かが ID から読めると修正ログとの突合が容易で、「R2 で新規に出た＝R1 の修正が生んだ可能性」という因果も追える。quality-review の `#m` は1回の報告内でしか一意でないため、そのままではループを跨ぐ参照に使えない。
- **出所**: 設計裁量（2026-07-28）。

### 開始宣言（確認ではなく宣言）
- **決定**: ループに入る前に対象・修正予定の要対応一覧・上限を1度だけ宣言する。承認は求めない。
- **却下した代替案**: 修正開始前にユーザー承認を挟む案。→ 「自動的に繰り返す」が依頼の核で、承認ゲートはそれを壊す。一方で無宣言で書き換え始めると誤起動（対象の取り違え）に気づく窓がない。宣言のみが両者のバランス。
- **出所**: 依頼文の「自動的に」（2026-07-28）＋誤起動リスクの緩和。

## 解釈・仮定（要確認）

- **「直すべきもの」の解釈**: ユーザーの「直すべきものを直して」を quality-review の対応区分「要対応」と解釈した。⚠️ 「任意も含めて直したい」運用が出てきたら、既定は要対応のまま引数（例: `--include 任意`）で広げる拡張を検討する。
- **上限の既定値3**: 仮置き。⚠️ 実運用で「3で足りない／多すぎる」が見えたら調整する。
- **直近レビュー採用の判定**: 「同一会話内＋報告以後に対象コードの変更なし」を採用条件とし、判定に迷ったら自前レビューに倒す。⚠️ 「変更なし」の厳密判定は難しいため安全側の倒し先だけ規定した。
- **コミットしない**: 修正は作業ツリーに残すところまで。⚠️ ラウンドごとにコミットして履歴を残したい運用もありうるが、ユーザーの差分確認前に履歴を作らない方を既定にした。
- **停止条件の「対象がループ外で変化」**: ユーザーが並行でコードを触るケースは検出できる範囲（修正者の整合確認・git status）でのみ拾う。⚠️ 完全な検出は保証しない。
