# Test Audit

広範囲（リポジトリ全体／特定モジュール）を対象に、「**壊れてもテストが気づいてくれない場所はどこか**」という軸で監査するオーケストレーションスキル。対象をコンポーネントに分割し、`test-gap-auditor` サブエージェントを並列に走らせ、結果をリスク順のテストギャップ台帳に統合する。スキル自身は直接コードを監査しない。テストも書かない（検出のみ）。

## このスキルの責務

| やること | やらないこと |
|---------|------------|
| 監査スコープの確定とテスト基盤の偵察 | 直接のギャップ判定・コード精読（サブエージェントが担当） |
| コンポーネント分割と監査計画の提示・合意 | テストコードの作成・修正 |
| カバレッジの実測（既設定で安全に走る場合のみ・中央で1回） | カバレッジ設定の新規導入（対象リポジトリを変更しない） |
| `test-gap-auditor` の並列起動 | テスト戦略・カバレッジ目標の策定 |
| 保護状況マトリクスとギャップ台帳の統合・リスク順位付け | バグ・脆弱性の指摘（quality-review / security-review の領分） |
| 全文台帳のファイル出力とチャット要約 | 暗黙起動 |

## 兄弟スキルとの関係

[[security-audit]] と同型の構造（コンポーネント分割 → 専門サブエージェント並列 → 統合レポート）だが、評価軸が異なる。

- **security-audit**: 公開フレームワークへの準拠状況。本スキル: **テストによる保護の有無**。
- **quality-review**: コード差分の品質（そのレビュー中にテスト不足も指摘しうるが、対象は変化した部分だけ）。本スキル: 差分ではなくリポジトリの現状のテスト保護状況。

「この PR にテストは足りてる？」なら quality-review、「このリポジトリでテストが薄くて危ないのはどこ？」「テストをどこから書き始めるべき？」なら本スキル。

## ワークフロー

| 段階 | 目的 | 依存 |
|------|------|------|
| 1 | 監査スコープの確定 | - |
| 2 | テスト基盤の偵察とコンポーネント分割 | 段階1 |
| 3 | カバレッジの実測（可能な場合のみ） | 段階2 |
| 4 | 監査計画の提示・合意 | 段階2 |
| 5 | test-gap-auditor の並列起動 | 段階4 |
| 6 | 結果の統合（マトリクス構築・ID 付与・リスク順位付け） | 段階5 全完了 |
| 7 | 全文台帳のファイル出力＋チャット要約 | 段階6 |

---

### 段階1: 監査スコープの確定

ユーザー指定を解釈する。指定がなければリポジトリルート全体を対象とする。

| 指定例 | 解釈 |
|-------|------|
| 指定なし | リポジトリ全体 |
| パス（`src/payments/` 等） | そのディレクトリ配下のコンポーネント |
| 「決済まわり」等の関心事 | 複数コンポーネントを跨ぐ関心事スライスとして扱う（段階4参照） |

リポジトリルートの絶対パスを確定して保持する。

### 段階2: テスト基盤の偵察とコンポーネント分割

スコープ内を偵察し、以下を把握する。広いリポジトリでは偵察を汎用の調査エージェント（general-purpose 等の読み取り系）に任せてよい（`test-gap-auditor` は監査専用なので偵察には使わない）。

**テスト基盤**（全作業項目に共通で渡す情報）:

- テストランナーと実行コマンド（`package.json` scripts / `pytest.ini` / `go.mod` 等から）
- テスト配置規約（co-located `*.test.ts` / `tests/` ディレクトリ / `__tests__/` 等）
- カバレッジ設定の有無（設定ファイル・スクリプトに既にあるか）
- モック・フィクスチャの慣習（あれば）

**コンポーネント分割**: 独立して監査しうる単位に分ける。monorepo は package／service 単位、単一レポは機能モジュール単位。各コンポーネントの役割を1行で把握する。テストコードしか無いディレクトリはコンポーネントにしない（ソースの側に紐づける）。

### 段階3: カバレッジの実測（可能な場合のみ）

以下を**すべて**満たす場合に限り、スキルが中央で **1 回だけ**カバレッジを実行し、per-file のサマリを各作業項目に添付する:

- カバレッジコマンドが対象リポジトリに**既に設定済み**（新規導入しない）
- 依存の追加インストールが不要
- 妥当な時間で完走する見込み（巨大スイートで数十分かかるなら見送る）

満たさない場合は実測なしの静的マッピングで続行する。これはデグレードであって失格ではない（実測はエージェントの当たりを速く正確にする補助情報にすぎない）。テストスイート自体が壊れていて走らない場合は、その事実を台帳冒頭の最重要事項として記録する（「テストが実行されていない」こと自体が最大のギャップ）。

**注意**: カバレッジ数値は「実行された」ことしか示さず「検証された」ことは示さない（assertion の無い形骸テストでも行カバレッジは稼げる）。数値は当たりを付ける材料に留め、保護の判定は必ずエージェントによるテスト内容の精読で行う。per-agent での再実行は重複して重いので禁止。

### 段階4: 監査計画の提示・合意

**作業項目 = 1 コンポーネント**。これが 1 サブエージェントの担当になる。

分割の指針:

- **既定はコンポーネント単位**。1 コンポーネントが大きすぎて 1 エージェントで網羅しきれない場合（目安: 主要ソース 30 ファイル超）、サブディレクトリや関心事でスライスして複数項目にする。
- **小さいコンポーネントの統合**: 主要ソースが 1〜3 ファイルの小さいコンポーネントは、関連の深いもの同士（同じドメインのモジュール群等）をまとめて 1 作業項目にしてよい（サブエージェント起動コストの削減。小規模リポジトリでコンポーネント数ぶん並列起動するのは過剰）。ただし金銭・認証などとくに被害の大きい領域は単独項目を維持する。統合しても保護状況マトリクスの行はコンポーネント単位を保つ（エージェント出力の箇所パスから振り分ける）。
- **関心事スライス（ユーザー指定時）**: 「決済まわり」のような指定では、複数コンポーネントの決済関連パスを 1 スコープにまとめて 1 項目にする。
- **低リスクの明示的除外**: 自明な型定義・生成コード・設定ファイルだけのディレクトリは項目化せず、計画で「対象外」と明示する（暗黙に落とさない）。

作業項目が出揃ったら、起動前に**監査計画を表で提示**し、合意を取る（多数のサブエージェントを起動する重い操作のため）。件数が多い場合は優先度（金銭・認証・データ整合性を扱うコンポーネントを先に等）や絞り込みを相談する。

```
## 監査計画（N コンポーネント / M 作業項目）
| # | コンポーネント | 役割 | 規模感 | 既存テスト |
|---|---|---|---|---|
| 1 | src/payments | 請求・返金 | 8 files | なし |
| 2 | src/cart | カート操作 | 4 files | cart.test.ts |
| 3 | src/auth | セッション管理 | 3 files | なし |

対象外: src/types（型定義のみ）
```

### 段階5: test-gap-auditor の並列起動

合意された作業項目について、**同一レスポンス内で** `review:test-gap-auditor` を並列起動する。作業項目が多い場合（目安 8 件超）は、優先度順にバッチ分割して順に流す（各バッチ内は並列）。

各サブエージェントへ送るプロンプトのテンプレート:

```
対象スコープ:
- コンポーネント: <名前>
- 対象パス:
  - <path1>
  - <path2>
- 役割: <1 行説明>

テスト基盤情報:
- テストランナー: <vitest 等 / 不明>
- テスト配置規約: <co-located *.test.ts 等>
- このスコープに対応しうる既存テスト: <パス群 / 見つかっていない>

カバレッジ実測: <per-file サマリ / 実測なし（理由: 未設定 等）>

重点ヒント: <このスコープで特に重要そうな領域 / なし>

リポジトリルート: <abs path>

手順は test-gap-auditor の定義に従う。出力フォーマットを厳守すること。
```

あるサブエージェントが失敗しても、残りの結果で監査を成立させ、失敗したスコープは段階7の「未確認・カバー外」に記録する。

### 段階6: 結果の統合

各 `test-gap-auditor` のマークダウン出力を読み、以下を構築する。

- **保護状況マトリクス**: コンポーネントごとに、識別された重要領域数と 保護済み/部分的/未保護/未確認 の内訳、ギャップ件数（C/H/M/L）を集計。
- **重複の整理**: 関心事スライスとコンポーネント項目が重なった場合など、同一箇所の同一ギャップは 1 件にまとめる（重大度は最大を採用）。
- **finding ID の付与**: 統合後の各ギャップに安定 ID `TA-<コンポーネント略号>-<連番>`（例 `TA-payments-01`）を振る。台帳・チャット要約で同じ ID を共有し、PR や議論での参照にも使える。
- **リスク順位付け**: 重大度順、同重大度内は「壊れたときの影響の広さ × 変更の入りやすさ（churn）」で並べる。台帳は**上から順にテストを書けば最も効率よくリスクが減る順**にする。

### 段階7: 全文台帳のファイル出力＋チャット要約

ギャップを集計して総合評価を決める。

| 評価 | 条件 |
|------|------|
| **Critical Exposure** | `critical` ギャップが 1 件以上 |
| **High Exposure** | `critical` は無いが `high` が 1 件以上 |
| **Medium Exposure** | `high` は無いが `medium` が 1 件以上 |
| **Low Exposure** | `low` のみ |
| **Well-Protected** | ギャップ 0 件 |

未確認の多さは評価を下げないが、台帳で明示し「確認しきれていない範囲」として残す（網羅できなかった事実を隠さない）。

出力は2系統に分ける。**全文はファイル、チャットは要約**（全文をチャットに流すと読めず、共有・見返しもできないため）。スキルはこれ以上の作業（テスト作成等）は行わない。

#### 7a. 全文台帳のファイル出力

全文を `docs/test-audit/<YYYY-MM-DD>-report.md` に書き出す（日付は `date` コマンドで取得、ディレクトリが無ければ作成、ユーザーが出力先を指定した場合はそれに従う。同日に複数回走らせる場合は連番を付けて上書きを避ける。例: `<日付>-2-report.md`）。以下が全文テンプレート:

````markdown
# Test Audit Report（テストギャップ台帳）
- **監査日**: 2026-07-04
- **対象リポジトリ**: <org/repo（`git remote` 由来。無ければプロジェクト名）。ローカル絶対パスは書かない>

## 総合評価
**High Exposure** — critical 0 / high 3（請求計算・返金エラーパス・セッション境界）

## 監査スコープとテスト基盤
- **対象**: リポジトリ全体（6 コンポーネント / 6 作業項目、対象外: src/types）
- **テストランナー**: vitest（`npm test`）
- **テスト配置規約**: co-located `*.test.ts`
- **カバレッジ実測**: なし（カバレッジ設定が未導入のため静的マッピングで監査）

## 保護状況マトリクス
| コンポーネント | 重要領域 | 保護済み | 部分的 | 未保護 | 未確認 | ギャップ (C/H/M/L) |
|---|---|---|---|---|---|---|
| src/payments | 5 | 0 | 0 | 5 | 0 | 0/2/1/0 |
| src/cart | 4 | 1 | 2 | 1 | 0 | 0/0/2/0 |
| src/utils | 3 | 3 | 0 | 0 | 0 | 0/0/0/0 |

## ギャップ台帳（リスク順）

### [HIGH] TA-payments-01 未テスト重要ロジック: 請求金額計算が無テスト
- **箇所**: src/payments/charge.ts:12-58
- **守られていないもの**: 通貨別の丸め（JPY 整数／USD セント）、割引と上限付きクーポンの適用順、税計算
- **壊れ方**: 丸め順序や割引適用順の変更が誰にも気づかれず通り、請求額がずれる（金銭影響・全注文に波及）
- **変更頻度**: 直近6ヶ月で 9 コミット（頻繁）
- **最寄りの既存テスト**: なし（payments 配下にテストファイルなし）
- **推奨テスト観点**: 通貨別丸めの境界（JPY 0.5 / USD 3桁目）、クーポン上限到達時の割引額、割引→税の適用順を固定する回帰テスト

### [MEDIUM] TA-cart-01 未検証境界条件: 数量バリデーションが未検証
- ...

## 既に守られている代表領域
（重複したテスト追加を避けるため、信頼してよい基盤を明示する。なければ「なし」）
- src/utils/format.ts — 境界値・異常系まで含む網羅的なテストあり（format.test.ts）

## 未確認・カバー外
- src/legacy — 監査エージェントが失敗し未監査。
- 変更頻度: git 履歴が参照できず全コンポーネントで省略。

## 実測データ
- カバレッジ実行: なし（未設定）／実行した場合はコマンドと全体数値・特記事項を記す
````

`未保護`/`未確認` が 0 のコンポーネントでもマトリクスの行は残す。ギャップ 0 件のコンポーネントは台帳で「ギャップなし」と明記する（暗黙省略しない）。各ギャップには段階6の `TA-...` ID を必ず付ける。

#### 7b. チャット要約

チャットには全文を貼らず、以下の要約だけを表示して全文ファイルのパスを示す。要約は **Critical/High に絞る**（件数が多いときの可読性のため）。Medium 以下・根拠・推奨テスト観点の詳細は全文ファイルに委ねる。

````markdown
# Test Audit 要約
- **総合評価**: High Exposure
- **台帳全文**: docs/test-audit/2026-07-04-report.md
- **対象**: リポジトリ全体（6 コンポーネント、テストランナー: vitest）

## 保護状況（ギャップ件数 C/H/M/L）
| コンポーネント | 重要領域 | 未保護 | ギャップ |
|---|---|---|---|
| src/payments | 5 | 5 | 0/2/1/0 |
| src/cart | 4 | 1 | 0/0/2/0 |
| src/utils | 3 | 0 | 0/0/0/0 |

## 重点ギャップ（Critical / High のみ）
- [HIGH] TA-payments-01 請求金額計算が無テスト — src/payments/charge.ts:12
- [HIGH] TA-payments-02 返金のエラーパスが未検証 — src/payments/refund.ts:20
- …（Medium/Low・推奨テスト観点は台帳全文参照）

テストの追加自体は本スキルの対象外です。台帳のリスク順に上から着手するのが効率的です。
````

## サブエージェントとの契約

### スキル → エージェント（入力）

段階5 のテンプレートで送る。テスト基盤情報とカバレッジ実測（あれば）は全項目に共通で渡し、エージェントに再探索させない。不明な項目は「不明」と書いて渡す。

### エージェント → スキル（出力）

`test-gap-auditor` の定義にある出力フォーマットで返る。スキルはこの構造（保護状況集計・ギャップ・保護済み領域・未確認）から機械的に集計してマトリクスと台帳を組む。

---

## 制約まとめ

- スキル自身は直接監査しない（オーケストレーション役）。テストコードも書かない（検出のみ）。
- 対象リポジトリを変更しない（カバレッジ設定の導入・依存追加もしない）。
- カバレッジ実測は既設定・追加依存なし・妥当な時間の場合に限り、中央で 1 回だけ。数値は補助情報で、保護の判定はテスト内容の精読による。
- 監査計画は起動前に提示して合意を取る（重い並列起動のため）。
- 作業項目が多い場合は優先度順にバッチ分割。各バッチ内は同一レスポンスで並列起動。
- `未確認` を `保護済み` で誤魔化さない。確認できなかった範囲は台帳に明示する。
- 全文台帳は `docs/test-audit/<日付>-report.md` に出力し、チャットには Critical/High に絞った要約のみ返す。
- 台帳にローカル絶対パスを書かない（対象リポジトリは org/repo 等の識別子で記す）。
- 各ギャップに安定 ID `TA-...` を付与する（台帳・要約で共有）。
- 暗黙起動なし（`disable-model-invocation: true`）。
