# review-walkthrough 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

AI コーディングの変更量が大きいと、生の diff では「量が多く読みきれない」「関連の強い単位がノイズで見分けづらい」ためレビューが困難（2026-08 ユーザー要望）。変更を意味単位に再編成し、AI の判断が入った場所に説明を付けた自己完結 HTML を生成して、人間レビューを速く・見落としなくする。作業合意は `docs/agreements/2026-08-07-review-walkthrough.md`、分析エージェント側の設計は `agents/walkthrough-unit-analyst.RATIONALE.md`。

## 中核的な設計判断

### 【load-bearing】資料生成と評価の分離
- **決定**: スキルは事実・経緯・判断材料の提示に徹し、良し悪しの評価・修正提案をしない。「確認ポイント」は問いの形に限定。
- **却下した代替案**: 重要ポイントに深刻度や推奨対応を付ける案 — quality-review と役割が重複し、資料の結論が人間の判断を先取り（アンカリング）してしまう。
- **防いでいる失敗**: 人間レビューの独立性の喪失。「AI が OK と言っているから流し読み」になったら、このスキルはレビューを支援するのではなく形骸化させる。
- **出所**: 設計議論（2026-08-07 リードバック、ユーザー承認）

### 【load-bearing】フレッシュセッションでの完全動作（情報源3層）
- **決定**: 必須層（diff・コードベース・git 履歴）だけで資料が成立する設計。設計書は「パスを渡されたら読む」任意入力、実装セッションの会話はボーナス。
- **却下した代替案**: (a) 実装中にレビューノートを随時書き出させるサイドカー方式 — プラグインなし実装・チャットのみ実装のケース（実利用の過半）をカバーできず、全実装フローへの介入が必要。(b) 特定の設計書フォーマットへの依存 — 設計書が無い利用状況が明示されている。
- **防いでいる失敗**: コンテキスト枯渇でスキルが実行不能になる問題そのもの。枯渇したら新セッションで実行すればよい、が答えになる。
- **出所**: ユーザー要望（2026-08、枯渇への悩みと「特定フォーマット非依存」の明示）

### 【load-bearing】「なぜ」の出所3値（conversation / doc / inferred）と捏造禁止
- **決定**: 説明の「なぜ」に出所チップを付け、会話・設計書に根拠が無いものは必ず推定（inferred）として表示。統合時の格上げも禁止。
- **防いでいる失敗**: もっともらしい理由の創作。フレッシュセッション実行では意図の直接証拠が無いため、この規律が無いと資料全体が「それらしい嘘」になる。推定と明示されていれば、レビュアーは確認ポイントを起点に検証できる。
- **出所**: 設計議論（2026-08-07）。「どのような意思決定をしたのか」を載せたいというユーザー構想と、フレッシュ動作要件の両立点。

### 【load-bearing】コード転記のスクリプト化と完全性の機械検査
- **決定**: diff の収集・構造化（map）と HTML への合成（render）は同梱の build.mjs が担い、モデルはコード本文を転記しない（ポイントの抜粋のみ分析エージェントがパッチから転記）。render は「全変更ファイルがユニットかノイズ棚に割り当てられていること」を検査し、違反は生成エラー。
- **却下した代替案**: HTML 全体をモデルに書かせる案 — 大規模差分でトークンとコンテキストが破綻し、コード引用のハルシネーションも混入する。
- **防いでいる失敗**: 巨大差分での破綻と、「資料に載っていない変更」の黙った取りこぼし（--allow-uncovered 時も「未分類」グループとして可視化される）。
- **出所**: 設計議論（2026-08-07）。「変更量が大きくて読めない」が原問題なので、スキル自身が大規模で破綻しては本末転倒。

### ハイライトは自作の正規表現ベース実装（Prism 同梱を却下）
- **決定**: template.html に約90行の自作ハイライター（言語別コメント様式＋キーワード集合の汎用トークナイザ）を同梱。外部リソース参照なし。
- **却下した代替案**: Prism.js の同梱（当初前提）— 200KB 超のミニファイド blob をこの Markdown 中心のリポジトリにコミットすることになり、ライト/ダーク2テーマ対応にもトークン配色 CSS の書き直しが必要。見た目は自作実装のモックでユーザー承認済み。
- **防いでいる失敗**: リポジトリの肥大とレビュー不能なベンダーコードの持ち込み。
- **出所**: 実装時判断（2026-08-07、前提更新 L1 として台帳記録・ユーザー報告済み）

### ユニット＝意味の単位、機械的変更はノイズ棚へ隔離
- **決定**: ファイル単位でなく「1つの要求を実現する呼び出し連鎖と共有契約」で束ね、読む順序を付ける。import 波及・lockfile 等は各ユニットから隔離し、末尾のノイズ棚に分類根拠付きで集約。
- **防いでいる失敗**: 「関連の強い単位で見ようとしてもノイズが多く見分けづらい」という原問題の再発。ノイズ棚に分類根拠を付けるのは、誤分類（実質変更の紛れ込み）をレビュアーが検出できるようにするため。
- **出所**: ユーザー構想（2026-08）＋設計議論

### 還流機能は「4値状態＋コメント」の統合 UI
- **決定**: 各ポイントに 未/OK/要修正/質問 の状態とコメント欄を付け、書き出しでは要修正・質問だけを Markdown 化（そのまま AI への修正依頼になる文面）。既読チェックと判定は分けない。
- **却下した代替案**: 既読チェックボックスとコメントの別管理 — 状態が二重になり進捗表示と矛盾しうる。
- **防いでいる失敗**: レビュー結果のチャットへの手書き転記と、その際の文脈（どのコードへの指摘か）の喪失。
- **出所**: 設計議論（2026-08-07 リードバック質問2、ユーザー承認）

### HTML の見た目はモック先行で確定
- **決定**: スキル実装前にサンプル差分の HTML モックを作りユーザーレビューで確定した。template.html はその承認版が正準で、構造変更時は現物で再確認する。
- **防いでいる失敗**: 言葉で合意した「つもり」の UI を実装後に作り直す手戻り。
- **出所**: 作業合意（2026-08-07）

## 解釈・仮定（要確認）

- **「特定フォーマットの設計書に依存しない」**: 「設計書を使うな」ではなく「あれば任意入力として読む（構造は仮定しない）」と解釈。⚠️設計書の自動探索（docs/ 配下を勝手に走査する等）はしない — 誤った文書を根拠にする方が害が大きいと判断。
- **「特定のブランチ」**: 既定ブランチ（origin/HEAD → main/master）との merge-base 起点の差分と解釈。⚠️比較先を変えたい場合は `A...B` 形式で渡す運用。
- **「1枚の HTML」**: オフラインで開ける完全自己完結（外部リソース参照なし）と解釈。レビュー状態は閲覧ブラウザの localStorage にのみ保存され、ファイル共有では状態は共有されない。⚠️状態も持ち運びたい要望が出たら書き出し Markdown で代替。
- **出力先 `docs/reviews/`**: ツール生成物は docs/ 配下というユーザー方針に整合させた。生成物はコミットしない前提（残すかはユーザー判断）。⚠️リポジトリによっては gitignore 追加を提案する余地がある。
- **巨大差分の縮退**: 上限で拒否せず「規模を伝えて絞り込み提案 or 粗い分割の宣言」と解釈。
