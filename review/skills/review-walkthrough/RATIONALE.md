# review-walkthrough 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

AI コーディングの変更量が大きいと、生の diff では「量が多く読みきれない」「関連の強い単位がノイズで見分けづらい」ためレビューが困難（2026-08 ユーザー要望）。変更を意味単位に再編成し、AI の判断が入った場所に説明を付けた自己完結 HTML を生成して、人間レビューを速く・見落としなくする。作業合意は `docs/agreements/2026-08-07-review-walkthrough.md`、分析エージェント側の設計は `agents/walkthrough-unit-analyst.RATIONALE.md`。

## 中核的な設計判断

### 【load-bearing】資料生成と評価の分離
- **決定**: スキルは事実・経緯・判断材料の提示に徹し、良し悪しの評価・修正提案をしない。「確認ポイント」は問いの形に限定。
- **却下した代替案**: 重要ポイントに深刻度や推奨対応を付ける案 — quality-review と役割が重複し、資料の結論が人間の判断を先取り（アンカリング）してしまう。
- **防いでいる失敗**: 人間レビューの独立性の喪失。「AI が OK と言っているから流し読み」になったら、このスキルはレビューを支援するのではなく形骸化させる。
- **出所**: 設計議論（2026-08-07 リードバック、ユーザー承認）

### 【load-bearing】フレッシュセッションでの完全動作（情報源3層）
- **決定**: 必須層（diff・コードベース・git 履歴）だけで資料が成立する設計。設計書は「パスを渡されたら読む」任意入力、実装セッションの会話はボーナス。
- **却下した代替案**: (a) 実装中にレビューノートを随時書き出させるサイドカー方式 — プラグインなし実装・チャットのみ実装のケース（実利用の過半）をカバーできず、全実装フローへの介入が必要。(b) 特定の設計書フォーマットへの依存 — 設計書が無い利用状況が明示されている。
- **防いでいる失敗**: コンテキスト枯渇でスキルが実行不能になる問題そのもの。枯渇したら新セッションで実行すればよい、が答えになる。
- **出所**: ユーザー要望（2026-08、枯渇への悩みと「特定フォーマット非依存」の明示）

### 【load-bearing】「なぜ」の出所3値（conversation / doc / inferred）と捏造禁止
- **決定**: 説明の「なぜ」に出所チップを付け、会話・設計書に根拠が無いものは必ず推定（inferred）として表示。統合時の格上げも禁止。
- **防いでいる失敗**: もっともらしい理由の創作。フレッシュセッション実行では意図の直接証拠が無いため、この規律が無いと資料全体が「それらしい嘘」になる。推定と明示されていれば、レビュアーは確認ポイントを起点に検証できる。
- **出所**: 設計議論（2026-08-07）。「どのような意思決定をしたのか」を載せたいというユーザー構想と、フレッシュ動作要件の両立点。

### 【load-bearing】コード転記のスクリプト化と完全性の機械検査
- **決定**: diff の収集・構造化（map）と HTML への合成（render）は同梱の build.mjs が担い、モデルはコード本文を転記しない（ポイントの抜粋のみ分析エージェントがパッチから転記）。render は「全変更ファイルがユニットかノイズ棚に割り当てられていること」を検査し、違反は生成エラー。
- **却下した代替案**: HTML 全体をモデルに書かせる案 — 大規模差分でトークンとコンテキストが破綻し、コード引用のハルシネーションも混入する。
- **防いでいる失敗**: 巨大差分での破綻と、「資料に載っていない変更」の黙った取りこぼし（--allow-uncovered 時も「未分類」グループとして可視化される）。
- **出所**: 設計議論（2026-08-07）。「変更量が大きくて読めない」が原問題なので、スキル自身が大規模で破綻しては本末転倒。

### 対象ミスの早期検出（コミット一覧・origin 優先基準・fetch 鮮度・条件付き確認ゲート）
- **決定**: (1) map はコミット範囲を持つ対象でコミット一覧を標準出力と map.json に出す。(2) ブランチ対象の diff 基準は `origin/<base>` があればそれを優先する。(3) origin/* を基準に使うときは FETCH_HEAD の経過時間（24h 超）で鮮度を警告する。(4) メインは疑わしいシグナル（他 PR の番号付きコミット・鮮度警告）があるときだけ、手順 2 に進む前にユーザーへ対象確認を挟む。
- **却下した代替案**: (a) スクリプトによる自動 `git fetch` — ネットワークアクセスと ref 更新の副作用をスクリプトが黙って持つべきではない。(b) 常設の対象確認ゲート — シグナルなしの通常フローに毎回1往復を足すのは過剰。(c) ローカル base と origin/base の rev-list 比較警告 — origin 優先化で基準がローカル base に依存しなくなり不要化。fetch 自体が古いケースを捕まえられない盲点もある（FETCH_HEAD の経過時間はそれを補う近似）。
- **防いでいる失敗**: 基準ブランチが古いままマージ済み PR の差分が混入し、資料完成後にユーザー指摘で発覚してやり直しになる手戻り。実運用（ブランチ対象のウォークスルー生成）で、基準の pull 忘れによりマージ済み PR 3件分・15ファイル相当が余計に混入し、並列分析の半分が無駄になった。map の出力がファイル一覧と統計のみでコミット一覧が無く、「他 PR の番号付きコミットが並ぶ＝基準側が古い」というサインを人間も AI も見られなかった。
- **出所**: 2026-08-10 実運用フィードバック

### ポイントの抜粋（diffs）は checks と整合させる
- **決定**: ポイントの抜粋を `diffs: [{file, diff}]`（1〜3 件、render が件数を機械検証）とし、メインは手順 5 で「diffs が checks の判断材料として足りるか」を検査する。不足時の対処は patches/ からの転記差し替え／ポイント分割／checks の絞り込み。選択基準と件数規律の正準は分析エージェント定義（経緯は `agents/walkthrough-unit-analyst.RATIONALE.md`）。
- **却下した代替案**: 文言修正（選択基準の変更）のみで単一 diff を維持 — 「起点か核心のどちらか1つ」というトレードオフが残り、複数ファイルに判断材料が分散する配管型を表現できない。ポイント分割で凌ぐと1つの意味単位が複数カードに割れ、読み手が往復する。
- **防いでいる失敗**: 提示した抜粋がそのポイントの checks のどれにも答えられない資料。実運用で、値を複数コンポーネント経由で受け渡して末端の計算に使う配管型の変更（判断材料が4ファイルに分散）に対し起点の1行だけが提示され、確認事項3件がいずれも資料内で検証不能だった。情報はユニットの全 diff には存在したが、そこから自力で探すことになり「生の diff を頭から読む以外の方法を提供する」目的が損なわれていた。
- **出所**: 2026-08-10 実運用フィードバック

### checks の適格性はエージェントとメインの二段で検査する
- **決定**: 手順 5 の整合検査の冒頭に「答えの決まった問い（代案が無い・明確に劣ると判明している確認）が checks に混ざっていないか」を追加し、混ざっていたら根拠を premises / why へ移して問いから外す。選定基準と why の内容型の正準は分析エージェント定義（経緯は `agents/walkthrough-unit-analyst.RATIONALE.md`）。
- **防いでいる失敗**: 分析エージェントの出力を素通しして、答えの決まった確認が資料に残り、レビュアーに不要な調査を発生させること。実運用（12 ポイント・29 確認事項）では件数規律（1〜3件）は守られており、欠けていたのは質のゲートだけだった。diffs↔checks 整合と同じく、規律は生成側（エージェント）と統合側（メイン）の二段に置く。
- **出所**: 2026-08-12 実運用フィードバック

### 【load-bearing】説明の階層は「答える問い」で分ける（重複の構造的排除）
- **決定**: 説明フィールドに階層ごとの排他的な役割を定義し、契約（data-contract.md「説明の階層」）・エージェント定義・手順5の検査の3箇所で強制する。全体像＝全体でしか言えないこと、ユニットの goal＝何のためか、background＝判断に必要な diff 外の仕組み、files[].role＝各ファイルの役割、ポイントの what/premises＝その箇所固有。あわせて役割が重複していたフィールドを廃止した（`tagline`＝name と同義、`flow`＝ファイルの並び順と role に吸収、`fileNotes`＝files[].note に吸収）。`order` は「ポイント間の依存があるときだけ」に限定。
- **却下した代替案**: (a) 各フィールドの文字数上限や書き方の注意を足す — 役割が未定義なままでは「短い重複」になるだけで、重複そのものは消えない。(b) 概要の要約を廃してカードだけにする — 全体の発端とユニット間の関係は、どのユニットを読んでも得られない情報なので残す価値がある。
- **防いでいる失敗**: 同じ対象を説明する自由記述フィールドが役割の定義なしに並ぶことで必然的に生じる重複。実運用の生成物では、全体像・概要カード・ユニット冒頭の3箇所が同一ユニットをほぼ同文で説明しており、読み手からは「文章量に対して得られる情報が少ない」と観測された。個々の文が悪いのではなく、どこに何を書くかが決まっていないことが原因なので、規律ではなく契約で解く。
- **出所**: 2026-08-10 実運用フィードバック（生成物レビュー、指摘①④）

### 【load-bearing】ファイル一覧・処理の流れ・全 diff を1つの構造に統合する
- **決定**: ユニットのファイルを「並び順＝読む順、各行に役割（記号名込み）・増減・そこに載るポイント番号」を持つ表にし、**各行を開くとそのファイルの diff だけが展開される**。ユニット末尾の一括「全 diff」折りたたみは廃止。ポイント側からは代表位置の隣のリンクで該当行へ飛べる（相互リンク）。
- **却下した代替案**: (a) 全 diff を削除して抜粋だけにする — HTML は小さくなるが、「変更ファイルが全てユニットかノイズ棚に割り当てられている」という完全性検査の結果をレビュアー自身が確かめる手段が資料から消える。(b) 一覧・流れ・全 diff を別々に置いたまま見出しだけ付ける — 同じファイル集合の3表現を読み手が突合する構造は残る。
- **防いでいる失敗**: (1) 説明の意図が伝わらないファイル一覧。実運用の生成物では、見出しのないパスの羅列とその下の散文の処理フローが並び、フローに出てくる関数名がどのファイルにあるか分からないため、結局全ファイルを開いて説明と見比べる必要があった。(2) 一括展開される全 diff。1ユニットで 650 行超が一度に開き、比較したい2箇所を往復するのにスクロールと記憶が要った。
- **出所**: 2026-08-10 実運用フィードバック（生成物レビュー、指摘②③）

### ユニットの「背景」とコード引用（説明特化スキルからの取り込み）
- **決定**: ユニットに任意の `background`（判断に必要な、diff の外にある仕組みの散文）と `codeRefs`（`{file, lines, caption}` を書くとスクリプトがワークツリーの現物から抽出して埋め込む引用）を置く。図（インライン SVG）は入れない。
- **却下した代替案**: (a) 文章の書き方の規律だけを取り込む — 機構の説明の置き場がユニット階層に無いという構造側の原因が残り、各ポイントの premises への分散は続く。(b) 図も許可する — 図はモデルが生成する成果物で誤図のリスクがあり、作図指針の移植で指示文書も膨らむ。背景と引用の効果を見てから判断する。(c) コード本文もモデルに書かせる — 転記のハルシネーションを増やす。行範囲だけを書かせてスクリプトが抽出する形なら、既存の「モデルはコードを転記しない」原則を崩さない。
- **防いでいる失敗**: 機構の説明が各ポイントの what と premises に散り、テキストと箇条書きに濃縮されて読みづらくなること。背景は新規の説明の追加ではなく**移設**なので、総量は増えず段階（全体像 → ユニットの仕組み → ポイント）だけが生まれる。コード引用は装飾ではなく、premises（外部挙動の言い切り）をレビュアーが検証する材料そのものになる。
- **解釈の注意**: 引用の対象は変更対象外のファイル（ライブラリ本体・変更していない既存コード）に限る想定で、変更対象ファイルを指定すると警告が出る（エラーにはしない — 変更ファイル内の未変更部分を引用する正当な場合があるため）。
- **出所**: 2026-08-10 実運用フィードバック（説明特化スキルの出力との比較。ユーザーが挙げた「段階的な説明」「背景となる技術の説明」「実際のコードの挿入」のうち、前2つを構造で、3つ目を抽出機構で満たす）

### ハイライトは自作の正規表現ベース実装（Prism 同梱を却下）
- **決定**: template.html に約90行の自作ハイライター（言語別コメント様式＋キーワード集合の汎用トークナイザ）を同梱。外部リソース参照なし。
- **却下した代替案**: Prism.js の同梱（当初前提）— 200KB 超のミニファイド blob をこの Markdown 中心のリポジトリにコミットすることになり、ライト/ダーク2テーマ対応にもトークン配色 CSS の書き直しが必要。見た目は自作実装のモックでユーザー承認済み。
- **防いでいる失敗**: リポジトリの肥大とレビュー不能なベンダーコードの持ち込み。
- **出所**: 実装時判断（2026-08-07、前提更新 L1 として台帳記録・ユーザー報告済み）

### ユニット＝意味の単位、機械的変更はノイズ棚へ隔離
- **決定**: ファイル単位でなく「1つの要求を実現する呼び出し連鎖と共有契約」で束ね、読む順序を付ける。import 波及・lockfile 等は各ユニットから隔離し、末尾のノイズ棚に分類根拠付きで集約。
- **防いでいる失敗**: 「関連の強い単位で見ようとしてもノイズが多く見分けづらい」という原問題の再発。ノイズ棚に分類根拠を付けるのは、誤分類（実質変更の紛れ込み）をレビュアーが検出できるようにするため。
- **出所**: ユーザー構想（2026-08）＋設計議論

### 還流機能は「4値状態＋コメント」の統合 UI
- **決定**: 各ポイントに 未/OK/要修正/質問 の状態とコメント欄を付け、書き出しでは要修正・質問だけを Markdown 化（そのまま AI への修正依頼になる文面）。既読チェックと判定は分けない。
- **却下した代替案**: 既読チェックボックスとコメントの別管理 — 状態が二重になり進捗表示と矛盾しうる。
- **防いでいる失敗**: レビュー結果のチャットへの手書き転記と、その際の文脈（どのコードへの指摘か）の喪失。
- **出所**: 設計議論（2026-08-07 リードバック質問2、ユーザー承認）

### HTML の見た目はモック先行で確定
- **決定**: スキル実装前にサンプル差分の HTML モックを作りユーザーレビューで確定した。template.html はその承認版が正準で、構造変更時は現物で再確認する。
- **防いでいる失敗**: 言葉で合意した「つもり」の UI を実装後に作り直す手戻り。
- **出所**: 作業合意（2026-08-07）

## 解釈・仮定（要確認）

- **「特定フォーマットの設計書に依存しない」**: 「設計書を使うな」ではなく「あれば任意入力として読む（構造は仮定しない）」と解釈。⚠️設計書の自動探索（docs/ 配下を勝手に走査する等）はしない — 誤った文書を根拠にする方が害が大きいと判断。
- **「特定のブランチ」**: 既定ブランチ（origin/HEAD → main/master）との merge-base 起点の差分と解釈。基準は `origin/<base>` があればそちらを優先（ローカル base の pull 忘れに結果が左右されないため。2026-08-10 変更）。⚠️比較先を変えたい場合（ローカル base を意図した位置に固定している等）は `A...B` 形式で渡す運用。
- **「1枚の HTML」**: オフラインで開ける完全自己完結（外部リソース参照なし）と解釈。レビュー状態は閲覧ブラウザの localStorage にのみ保存され、ファイル共有では状態は共有されない。⚠️状態も持ち運びたい要望が出たら書き出し Markdown で代替。
- **出力先 `docs/reviews/`**: ツール生成物は docs/ 配下というユーザー方針に整合させた。生成物はコミットしない前提（残すかはユーザー判断）。⚠️リポジトリによっては gitignore 追加を提案する余地がある。
- **巨大差分の縮退**: 上限で拒否せず「規模を伝えて絞り込み提案 or 粗い分割の宣言」と解釈。
- **`codeRefs` の抽出元**: 対象スナップショット（map 時点）ではなく**現在のワークツリー**から読む。引用するのが変更対象外の既存コード・ライブラリ本体である以上、対象との差が問題にならないと判断した。⚠️過去のコミットを対象にした資料で、引用元が後から変わっていた場合はズレる。実害が出たら map に「変更後リビジョン」を持たせて `git show` へ切り替える余地がある。
