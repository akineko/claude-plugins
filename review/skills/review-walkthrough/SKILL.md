# レビューウォークスルー資料の生成

AI が実装した変更量の大きい差分を、人間が「生の diff を頭から読む」以外の方法でレビューできるようにする。変更を**一緒に理解すべき意味の単位（ユニット）**に再編成し、**AI の判断・前提が入った場所（重要ポイント）**に説明を付けた、1枚の自己完結 HTML を生成する。

役割分担（このスキルの骨格）:

- **あなた（メイン）** = 判断と統合。対象の解決・ユニット分割・ポイントの取捨・全体像の執筆。
- **walkthrough-unit-analyst（サブエージェント）** = 読解と抽出。ユニット単位で diff と周辺コードを精読し、ポイント素材を構造化して返す。選出基準・記載項目の正準はエージェント定義にある。
- **scripts/build.mjs（スクリプト）** = コードの機械処理。diff の収集・構造化（map）と HTML への合成（render）。**コード本文をモデルが転記しない**ため、巨大差分でもコンテキストとトークンが破綻しない。分析をサブエージェントに逃がすので、残りコンテキストが少ないセッションでも実行できる。

このスキルは**評価しない**。良し悪しの指摘は quality-review / security-review、修正は quality-fix の領分。ここでは事実・経緯・判断材料を提示し、判断は人間に委ねる（資料に評価が混ざると人間レビューの独立性が壊れる）。

実行環境の前提: git リポジトリ内で実行する。`node`（>= 18）が必要（無ければその旨を伝えて中止する）。以下、`<skill>` はこのスキルのディレクトリ（起動時に通知されるベースディレクトリ）を指す。

## 手順 1: 対象の解決とマップ生成

依頼の自然言語を `--target` の指定に解決する。無指定の既定は**未コミットの変更全体**（コミット前レビューが最多のため）。

| 依頼の例 | 対象 | --target に渡す値 |
|---------|------|------------------|
| 無指定（既定） | 未コミット変更全体（staged + unstaged + untracked） | （省略） |
| 「これからコミットする分」 | ステージ済み | `staged` |
| 「unstaged だけ」 | 未ステージ + untracked | `unstaged` |
| 「このコミット」「abc123 を」 | 単一コミット | `<sha>` |
| 「A から B の範囲」 | コミット範囲 | `<A>..<B>` または `<A>...<B>` |
| 「このブランチの変更」 | 既定ブランチとの merge-base 起点の差分 | `<ブランチ名>` |
| 「PR #123 を」 | プルリクエスト | `gh pr checkout <番号>` でブランチを取得してからブランチ名で指定 |

```bash
node "<skill>/scripts/build.mjs" map --target "<spec>"
```

- 標準出力にファイル一覧と統計、**作業ディレクトリ**（map.json / patches/）のパスが出る。以降の全工程はこのスナップショットを共有する（途中で作業ツリーが変わっても結果が揺れない）。
- 差分が空ならユーザーに対象を確認して終了する。
- 規模の目安（60 ファイル超 または ±8,000 行超）を超える場合は、規模を伝えて重点パスへの絞り込みを提案するか、ユニット分割を粗くして進める旨を宣言する。黙って一部だけ扱わない。

## 手順 2: 情報源の整理（「なぜ」の出所）

説明の「なぜ」に使える情報源を3層で確認する。**必須層だけでも資料は成立する**（フレッシュセッションで完全動作。実装セッションのコンテキストが枯渇していたら、新しいセッションでこのスキルを実行すればよい）。

| 層 | 情報源 | すること |
|---|---|---|
| 必須 | diff・コードベース・git 履歴 | map が取得済み |
| 任意 | 設計ドキュメント | `--doc` 指定または会話で言及されたパスの存在を確認し、分析エージェントへ渡す（フォーマット不問・そのまま読ませる） |
| ボーナス | この会話の実装経緯 | このセッションで実装していた場合のみ下記のメモを作る |

会話に実装経緯がある場合、作業ディレクトリに `context-notes.md` を書き出す — 議論された決定・検討した代替案とその理由・仕様の解釈・ユーザーの明示要求を箇条書きで。**会話に無いことを書かない**。ここに創作が混ざると、資料の出所表示（会話/設計書/推定）全体が信用できなくなる。

## 手順 3: 意味の単位への分割

map.json（ファイル一覧・ハンクの関数名・mechanical マーク）と、必要に応じたパッチの流し読みで、変更を**ユニット**に分割する。

- ユニット = 1つの要求・機能を実現する呼び出し連鎖と共有契約の束。**ファイル単位ではない**（API→ロジック→永続化→テストを縦に束ねる。1ファイルの一部ずつが複数ユニットに登場してよい — その場合 fileNotes で注記）。
- 目安は 3〜8 ユニット。超えるなら機能領域で束ねる。
- ユニットの並び順 = 推奨の読み順。依存の上流（契約・データモデル）から下流（配線・テスト）へ。
- **ノイズの仮分類**: map の mechanical マーク（lockfile・生成物）に加え、import 波及・リネーム追随・フォーマットのみの変更・宣言だけの追随を各ユニットから隔離し、ノイズ棚へ回す。
- **全ファイルをユニットかノイズ棚のどちらかに割り当てる**。render が完全性を機械検査し、取りこぼしは生成エラーになる。

## 手順 4: ユニット分析の並列実行

ユニットごとに `review:walkthrough-unit-analyst` を**同一メッセージで並列起動**する。各エージェントへ渡すもの:

- リポジトリルートと作業ディレクトリのパス、担当ファイルのパッチファイル一覧（`patches/xxxx.patch`）
- ユニット仮説: 名前・目的の仮説・担当ファイル
- 情報源: `context-notes.md` のパス（あれば）・設計ドキュメントのパス（あれば）。**無い場合は「会話情報源なし。why の出所は doc / inferred のみ」と明示する**
- 出力はエージェント定義の JSON 契約どおりであること（定義に記載済みなので簡潔でよい）

回収した JSON がパース不能なら、内容を創作せず形式だけ自分で直す。形式以外が壊れていたら該当エージェントに差し戻す。

## 手順 5: 統合と裁定（あなたの中心作業）

1. **ポイントの取捨**: ユニットあたり 2〜5 件に絞る。超過時の優先順は 裁量判断・リスク集中・既存コードとの接続 ＞ 仕様の解釈・外部仕様への依存 ＞ 複雑性。資料全体で 25 件を超えるなら基準を上げて削る — 説明過多は「読みきれない」問題を説明で再生産する。
2. **採番**: 読む順に unit へ `u1..`、point へ `p1..` の id を振り、`no` は資料全体の通し番号にする。
3. **ノイズの最終裁定**: 各エージェントの noiseCandidates を突き合わせてグループ化し、各グループに分類根拠を1行書く（例:「差分が import 行のみ」）。**迷うものはユニット側に残す** — ノイズ棚への誤分類はレビューの穴になる。
4. **全体像の執筆**: meta.title と overview.summary（3〜6文 — 変更の狙い・ユニット構成・安全性や整合性の要になる箇所）を書く。
5. `<skill>/references/data-contract.md` を読み、契約に従って作業ディレクトリに `data.json` を書く。

## 手順 6: 組み立てと報告

```bash
node "<skill>/scripts/build.mjs" render \
  --data "<ws>/data.json" --map "<ws>/map.json" \
  --out "docs/reviews/<YYYY-MM-DD>-<slug>.html"
```

- slug は変更内容を表す ASCII ケバブケース。日付は `date` コマンドで確認する。
- 未割り当てエラーが出たら手順 3 に戻って割り当てを直す。`--allow-uncovered` は最後の手段（資料に「未分類の変更」グループとして明示され、使ったことを報告にも書く）。
- render の出力サマリ（ユニット数・ポイント数・警告）を確認してから報告する。

報告は次の形:

```
# レビュー資料を生成しました

対象: <label>（N ファイル ・ +adds −dels）
出力: docs/reviews/....html（ブラウザで開く: wslview <path> など）

ユニット（読む順）:
1. <名前> — ポイント N 件
...

重要ポイント: 計 N 件（裁量判断 N・リスク集中 N・…）
「なぜ」の出所: 会話 N ・設計書 N ・推定 N
ノイズ棚: N ファイル（グループ: …）

レビュー後は、HTML の「フィードバック書き出し」で得た Markdown をこの会話（または新しい会話）に貼ってもらえれば、修正依頼として対応します。
```

## 規律

- **評価・修正提案をしない**: 資料内の「確認ポイント」は必ず問いの形（「〜でよいか」「〜の要件はないか」）。「〜すべき」と書きたくなったら、それは quality-review の領分。
- **出所の正直さ**: 会話・設計書に根拠のない「なぜ」は必ず推定（inferred）として扱わせ、統合時も格上げしない。もっともらしい理由の創作がこの資料の最大の失敗形態。
- **載せない規律**: 自明・機械的な変更に説明を付けない。ポイント 0 件のユニット（説明と全 diff のみ）は正当な結果。
- **自己完結を壊さない**: 生成 HTML に外部リソース参照（CDN・画像 URL 等）を持ち込む変更をしない。
- このスキルは git 操作（add / commit）をしない。生成した資料を残すかはユーザーの判断（使い捨て前提なら削除してよい旨を伝える）。
