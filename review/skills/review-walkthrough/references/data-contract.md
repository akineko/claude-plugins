# data.json 契約 — render への入力形式

`scripts/build.mjs render` に渡す分析結果の形式。**メインエージェントが書くのは「モデル」列のフィールドだけ**。統計・ファイルごとの diff・背景の引用コード・生成日時はスクリプトが map と現物から充填する（コードの転記をモデルにさせないため。ポイントの `diffs` 抜粋だけは分析エージェントがパッチから転記する）。

## 説明の階層 — どの層に何を書くか

説明フィールドは4階層あり、**それぞれが答える問いは重ならない**。上位層に書いた事実を下位層で言い直さない（重複は分量だけ増えて情報が増えない）。

| 層 | フィールド | 答える問い | 書かないこと |
|---|---|---|---|
| 資料全体 | `overview.summary` | なぜこの変更全体が要ったか／全体としてどう解いたか／ユニットをどう分けどう関係するか／全体を貫く要注意点 | 個々のユニットの実装説明（ユニット層が持つ） |
| ユニット | `goal` | このユニットは何のためか | 全体の発端の再説明・実装手段の詳細 |
| ユニット | `background` | このユニットの判断に必要な、**diff の外にある仕組み** | 変更内容の要約（`files[].role` が持つ）・良し悪しの評価 |
| ユニット | `files[].role` | このファイルはこのユニットで何をしているか | 仕組みの説明（`background` が持つ） |
| ポイント | `what` / `premises` | この箇所で何をしていて、**この箇所固有**の前提は何か | `background` に書いた機構の再掲 |

ユニット名（`name`）は概要カードとユニット見出しの両方で使われるため、それ自体が説明になるように書く（1行の要約フィールドは持たない）。

## 全体構造

```json

    "title": "変更の一言タイトル（プレーンテキスト）",
    "target": "省略可: 対象の表示名（既定: map の label）",
    "note": "省略可: 読む前に知るべき対象側の注意（プレーンテキスト）。全体像の要約を書く場所ではない"
  },
  "overview": {
    "summary": "上表の役割で 3〜6 文（HTML 可）"
  },
  "units": [
    {
      "id": "u1",
      "name": "ユニット名。それ自体が変更の要約になる長さ（プレーンテキスト）",
      "goal": "このユニットは何のためか（HTML 可）",
      "background": "省略可: 判断に必要な仕組み 1〜3 段落（HTML 可。<p> で段落を分ける）",
      "codeRefs": [
        { "file": "既存コードのパス", "lines": "17-25", "caption": "この引用が何を示すか（プレーンテキスト）" }

          "checks": ["レビュアーへの問い（HTML 可）"],

            { "file": "src/foo.ts:42", "diff": "@@ -10,4 +10,8 @@ ...\n+追加行\n 文脈行（パッチからの転記）", "note": "省略可: 注記（プレーンテキスト）" }

  "noise": [
    {
      "name": "グループ名（プレーンテキスト）",
```

## 誰が何を書くか

| フィールド | 書き手 | 備考 |
|-----------|--------|------|
| meta.title / note, overview.summary | モデル（メイン） | 統合時に執筆 |
| meta.target / command / generated / stats | **スクリプト** | map から充填。モデルは書かない |
| units[].id, points[].id / no | モデル（メイン） | 読む順に u1../p1..、no は資料全体の通し番号 |
| units[] の記述・files[].role・points[] の中身 | モデル（分析エージェント → メインが取捨） | |
| units[].files[] の並び順 | モデル（分析エージェント） | 並び順がそのまま読む順として表示される |
| units[].files[] の diff・増減・status・載るポイント番号 | **スクリプト** | パッチから充填（2000 行/ファイルで切り詰め）。ポイント番号は `points[].file` と `points[].diffs[].file` から機械割り当て |
| units[].codeRefs[] の code・行番号 | **スクリプト** | ワークツリーの現物から抽出 |
| noise[].files の統計・小グループへの diff 添付 | **スクリプト** | 合計 120 行以下のグループに自動添付 |

## codeRefs（背景のコード引用）

`background` の主張——とくに外部ライブラリの挙動——の裏付けを、現物のコードで示すための任意フィールド。

- 引用するのは**変更対象ではないファイル**（ライブラリ本体・変更していない既存コード）。変更点はファイル行の diff が示すので、変更対象ファイルを指定すると警告が出る
- 1ユニットあたり最大 3 件、1件あたり 40 行まで。リポジトリ外のパスは指定できない
- `lines` は変更後（現在のワークツリー）の 1 始まり行番号で `"17-25"` または `"17"`。**指定前に現物を読んで行番号を確認する**
- `background` なしでは使えない

## 語彙（検証される）

- `kind`: `discretion`（裁量判断）/ `external`（外部仕様への依存）/ `interpretation`（仕様の解釈）/ `integration`（既存コードとの接続）/ `risk`（リスク集中）/ `complexity`（複雑性）
- `whySource`: `conversation`（会話に根拠）/ `doc`（設計書に根拠）/ `inferred`（コード・履歴からの推定）

表示名・配色は template.html が正準。語彙を増やす場合は template と build.mjs の両方を更新する。

## HTML とエスケープ

- **HTML 可**（エスケープされない）: summary / goal / background / order / files[].role / what / why / premises[] / checks[]。使うのは `<code>` `<b>`（background では加えて `<p>`）程度に留める
- **プレーンテキスト**（エスケープされる）: title / whatPlain / name（unit・noise）/ sub / reason / note 類 / file / files[].path / codeRefs[].caption

## 検証と完全性検査

render は必須フィールド・語彙・id/no の重複・`diffs` の件数（1〜3 件。選び方の正準は分析エージェント定義）・`codeRefs` の形式と行範囲を検証し、エラー時は生成しない。旧形式（`tagline` / `flow` / `fileNotes` / 文字列配列の `files` / 単数文字列の `diff`）は移行先を示すエラーになる。さらに **map の全ファイルが units[].files か noise[].files のどちらかに割り当てられていないとエラー**になる（取りこぼし防止）。`--allow-uncovered` を付けた場合のみ、未割り当てファイルを「未分類の変更（自動追加）」グループとして明示した上で生成する。
