## 目的と背景

[[test-audit]] 作成時（2026-07-04）に「テストコードのリファクタリング検出も行えるか」というユーザーの問いがあり、test-audit は意図的にスコープ外（保護の有無だけを判定）としていることを説明した上で、需要ありとして本スキルを作成。test-audit が「コードは守られているか」を見るのに対し、本スキルは「テストは信頼できる良いコードか」を見る対のスキル。監査オーケストレーションの構造（コンポーネント分割→専門エージェント並列→統合台帳）と、test-audit の eval で得た較正・粒度の知見をそのまま継承する。

## 中核的な設計判断

### 【load-bearing】test-audit と評価軸で分離する（保護 vs 品質）
- **決定**: 本スキルはテストコード自体の品質（信頼性・検証力・保守性・実行特性）だけを判定し、プロダクションコードの保護状況（カバレッジの穴・形骸テストによる無防備）には踏み込まない。エージェントにも「テストを書き足すべき→test-audit、このテストを直すべき→本スキル」という境目の目安を明記。
- **却下した代替案**: test-audit に品質観点を追加して 1 スキルに統合 → 1 エージェントが「コードの保護」と「テストの品質」を同時判定すると観点が混線する（review プラグイン全体の専任原則に反する）。台帳の意味も「テストを書く順」と「テストを直す順」で別物になり、混ぜると運用できない。
- **防いでいる失敗**: 保護ギャップと品質指摘が混ざった台帳になり、どちらの運用（書き足す/直す）にも使えなくなること。
- **出所**: ユーザー質問への回答で提示し合意（2026-07-04）。

### 【load-bearing】汎用 auditor 1 つ × 作業項目 = コンポーネントのテスト群（観点別に分割しない）
- **決定**: `test-quality-auditor` を 1 つだけ用意し、4 観点（信頼性・検証力・保守性・実行特性）は 1 エージェントが全部見る。
- **却下した代替案**: 観点別エージェント分割 → 4 観点の判定は同じ精読（テストとソースの突き合わせ）から派生するので分ける利得がなく、重複読み込みのコストだけ増える。test-audit と同じ理由。
- **出所**: [[test-audit]] RATIONALE の同判断を継承（2026-07-04）。

### 【load-bearing】テストだけでなく検証対象のソースも読ませる
- **決定**: エージェントの手順に「対応するソースを読み、注入可能な依存を確認する」を必須で入れ、「ソースは時刻注入可能なのにテストが実時刻を使う」型の不整合を重要指摘として扱う。
- **防いでいる失敗**: テストコードだけを読むと「どう直せるか」が言えず、改善方向が「モックを使いましょう」程度の一般論に落ちる。注入点の有無で改善方向の具体性が決定的に変わる。
- **出所**: 設計判断 2026-07-04。fixture の availability.test.ts（ソースは `now` 注入可・テストは実時刻）で検証する。

### 【load-bearing】テスト実行の実測は条件付き・中央 1 回・flaky の再実行実証はしない
- **決定**: 既設定・追加依存なし・妥当な時間なら 1 回だけ実行し、失敗テスト・時間分布を配る。flaky を再実行の繰り返しで実証しようとしない。非決定性は構造の精読で判定する。
- **却下した代替案**: N 回実行して flaky を実証 → 実行コストが監査の支配項になり、しかも N 回で再現しない flaky は普通にある（偽陰性）。構造判定（実時刻・順序依存・共有状態）の方が確実で安い。
- **出所**: 設計判断 2026-07-04。test-audit のカバレッジ実測（条件付き・中央1回・補助情報）と同じ原理。

### 疑いの濃い指摘への限定的な裏取り実行（統合後・数回まで・install 不可）
- **決定**: スイートが既に実行可能な場合、統合後・台帳確定前に、順序依存等の critical/high 指摘を該当ファイル単体・単一ケースの限定実行で裏取りしてよい。結果は指摘の「実害」の裏付けと「実測データ」に記録。裏取り不能でも指摘は弱めない。
- **却下した代替案**: 裏取りの全面禁止（初版）→ iteration-1 eval の baseline が「単独実行で FAIL・shuffle 全 seed FAIL」の実測で順序依存を証明し、実証ログの説得力が確認された。非改変（install 不可）と回数上限の制約内なら取り込む価値がある。
- **防いでいる失敗**: 台帳の critical 指摘が「構造上そう読める」止まりで、修正の説得力・優先度判断が弱くなること。逆方向には、裏取りの無制限化による実行コスト膨張と install による対象改変（baseline は npm install までやった — スキルでは許可しない）。
- **出所**: iteration-1 eval の baseline 観察 → ユーザー採用 2026-07-04。

### スイート横断の同一パターンは横断 1 件（TQ-x-）に統合
- **決定**: 「全コンポーネントでセットアップがコピペ」のような横断パターンは、コンポーネントごとに 1 件ずつ立てず、統合段階で横断 1 件にまとめて「同種の広がり」に列挙する。
- **防いでいる失敗**: 同じ指摘が N 回並ぶ台帳。修正も横断で一括（共有ヘルパー導入等）が自然なので、着手単位としても 1 件が正しい。
- **出所**: 設計判断 2026-07-04。

### test-audit iteration-1 の較正・粒度の知見を初版から織り込む
- **決定**: 「critical は稀・迷ったら下げる」「良質なファイルの残余問題は low 止まり」「1 指摘 = 1 ファイル × 1 種別」をエージェント定義に最初から明記。台帳=ファイル＋チャット=Critical/High 要約、安定 ID、絶対パス禁止、未確認の明示も同様に継承。
- **理由**: test-audit iteration-1 eval で実測した失敗（重大度インフレ・粒度過細・陰性コントロール誤検出）は監査系エージェントに共通の失敗モードで、ゼロから再発見させる理由がない。
- **出所**: [[test-audit]] RATIONALE・iteration-1/2 eval（2026-07-04）。

## 解釈・仮定（要確認）

- **「リファクタリングが必要なテスト」の解釈**: 保守性（重複・巨大テスト・命名）だけでなく、信頼性（flaky 構造・順序依存）・検証力（実装詳細結合・過剰モック）・実行特性（実待機・遅さ）まで含む「テストスイートの健全性監査」として広めに取った。⚠️ 純粋にコード構造のリファクタ候補だけが欲しい場合は広すぎる可能性。
- **重大度の意味論**: 「テストが嘘をつく度合い」を最上位に置いた（構造の汚さより誤シグナルを重く見る）。⚠️ 保守コスト重視の順位付けが好みなら要調整。
- **総合評価の名称**: テストへの信頼を表す Untrustworthy〜Healthy とした。⚠️ 呼称の好みは要確認。
- **出力先**: ユーザーの docs/ 規約に合わせ `docs/test-quality/` 配下。ユーザー指定で上書き可能。
