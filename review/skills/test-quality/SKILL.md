# Test Quality

広範囲（リポジトリ全体／特定モジュール）のテストスイートを対象に、「**このテストは信頼できるシグナルか・保守に耐えるコードか**」という軸で監査するオーケストレーションスキル。対象をコンポーネントに分割し、`test-quality-auditor` サブエージェントを並列に走らせ、結果をリスク順の指摘台帳に統合する。スキル自身は直接コードを監査しない。テストの修正も行わない（検出のみ）。

## このスキルの責務

| やること | やらないこと |
|---------|------------|
| 監査スコープの確定とテストスイートの偵察 | 直接の品質判定・コード精読（サブエージェントが担当） |
| コンポーネント分割と監査計画の提示・合意 | テストコードの修正・リファクタリング実施 |
| テスト実行の実測（既設定で安全に走る場合のみ・中央で1回） | テスト環境の新規構築・依存追加（対象リポジトリを変更しない） |
| `test-quality-auditor` の並列起動 | プロダクションコードの保護状況判定（test-audit の領分） |
| 品質状況の統合・リスク順位付け | バグ・脆弱性の指摘（quality-review / security-review の領分） |
| 全文台帳のファイル出力とチャット要約 | 暗黙起動 |

## 兄弟スキルとの関係

[[test-audit]] と対になるスキル。評価対象が異なる。

- **test-audit**: プロダクションコードは**テストで守られているか**（ギャップ検出。形骸テストも「保護が無い」という判定として扱う）。
- **本スキル**: テストコードは**信頼できる良いコードか**（flaky・脆さ・重複・検証力・速度）。
- **quality-review**: コード差分の品質（変化した部分だけ。テストも差分に含まれれば見る）。

「テストをどこから書き始めるべき？」なら test-audit、「テストはあるが信用できない・保守がつらい」「CI がたまに落ちる」「テストのリファクタ候補を洗い出したい」なら本スキル。監査中にプロダクションコードの保護ギャップに気づいた場合は指摘本体に混ぜず、test-audit の実行を案内する。

## ワークフロー

| 段階 | 目的 | 依存 |
|------|------|------|
| 1 | 監査スコープの確定 | - |
| 2 | テストスイートの偵察とコンポーネント分割 | 段階1 |
| 3 | テスト実行の実測（可能な場合のみ） | 段階2 |
| 4 | 監査計画の提示・合意 | 段階2 |
| 5 | test-quality-auditor の並列起動 | 段階4 |
| 6 | 結果の統合（ID 付与・リスク順位付け） | 段階5 全完了 |
| 7 | 全文台帳のファイル出力＋チャット要約 | 段階6 |

---

### 段階1: 監査スコープの確定

ユーザー指定を解釈する。指定がなければリポジトリ全体のテストコードを対象とする。

| 指定例 | 解釈 |
|-------|------|
| 指定なし | リポジトリ全体のテストスイート |
| パス（`src/payments/` 等） | そのディレクトリ配下（に対応するテスト群） |
| 「E2E だけ」「結合テストが遅い」等の関心事 | 該当するテストレイヤー・テスト群に絞る |

リポジトリルートの絶対パスを確定して保持する。

### 段階2: テストスイートの偵察とコンポーネント分割

スコープ内を偵察し、以下を把握する。広いリポジトリでは偵察を汎用の調査エージェント（general-purpose 等の読み取り系）に任せてよい（`test-quality-auditor` は監査専用なので偵察には使わない）。

**テストスイートの全体像**（全作業項目に共通で渡す情報）:

- テストランナーと実行コマンド、テスト配置規約（co-located / `tests/` / `__tests__/`）
- テストレイヤーの構成（unit / integration / E2E とその境目）
- 共有ヘルパー・fixture・ファクトリの慣習（あれば。監査の基準線になる）
- モックの慣習（何をモックするのが流儀か）

**コンポーネント分割**: テストコードのまとまり（対応するソースのコンポーネント単位が基本、E2E 等レイヤーで独立している場合はレイヤー単位）に分ける。テストファイルが 1〜3 個の小さいコンポーネントは関連するもの同士で 1 作業項目に統合してよい（起動コスト削減。マトリクス行はコンポーネント単位を保つ）。

### 段階3: テスト実行の実測（可能な場合のみ）

以下を**すべて**満たす場合に限り、スキルが中央で **1 回だけ**テストスイートを実行し、結果（失敗テスト・実行時間の分布・遅いテスト上位）を各作業項目に添付する:

- テストコマンドが対象リポジトリに**既に設定済み**で、依存の追加インストールが不要
- 妥当な時間で完走する見込み

満たさない場合は実測なしの静的監査で続行する（デグレードであって失格ではない）。実測できた場合の扱い:

- **既に失敗しているテスト**がコミットされていれば、それ自体を台帳の最重要事項として記録する（落ちたまま放置されたテストはスイート全体のシグナルを殺す）。
- 実行時間は「遅いテスト」の当たりを付ける材料にする。
- 1 回の実行で flaky は証明できない（非決定性の判定は構造の精読で行う）。再実行を繰り返して flaky を実証しようとしない（重い）。

**裏取り実行（統合後・任意）**: スイートが既に実行可能な場合に限り、順序依存・分離不全など疑いの濃い critical/high 指摘について、段階6の統合後・台帳確定前に**該当ファイル単体・単一ケースの限定実行**で裏を取ってよい（目安: 全体で数回まで。例: 単一ケース実行が全体実行と違う結果になることの確認）。実測で確認できた事実は該当指摘の「実害」の裏付けとして書き、実行内容を「実測データ」に記録する。ここでも install・設定変更はしない。裏取りできなかった指摘は構造上のリスクとして残してよい（実行できないことは指摘を弱めない）。

### 段階4: 監査計画の提示・合意

**作業項目 = 1 コンポーネントのテスト群**。作業項目が出揃ったら、起動前に**監査計画を表で提示**し、合意を取る（多数のサブエージェントを起動する重い操作のため）。件数が多い場合は優先度（CI を止めうる flaky 疑い・巨大なテスト群を先に等）や絞り込みを相談する。

```
## 監査計画（N コンポーネント / M 作業項目）
| # | コンポーネント | テストファイル数 | ケース数目安 | 実測情報 |
|---|---|---|---|---|
| 1 | src/booking | 2 | 15 | 失敗なし・最遅 1.2s |
| 2 | src/pricing + src/notify | 2 | 12 | - |

対象外: src/types（テストなし）
```

### 段階5: test-quality-auditor の並列起動

合意された作業項目について、**同一レスポンス内で** `review:test-quality-auditor` を並列起動する。作業項目が多い場合（目安 8 件超）は、優先度順にバッチ分割して順に流す（各バッチ内は並列）。

各サブエージェントへ送るプロンプトのテンプレート:

```
対象スコープ:
- コンポーネント: <名前>
- 対象テストファイル:
  - <path1>
  - <path2>
- 対応するソース: <パス群>

テストスイート情報:
- テストランナー: <vitest 等 / 不明>
- テストレイヤー: <unit 等>
- 共有ヘルパー・fixture の慣習: <あれば。「無し（各テスト自前）」も重要な情報>
- モックの慣習: <あれば / 不明>

テスト実行の実測: <失敗・時間分布 / 実測なし（理由）>

重点ヒント: <ユーザーが訴えた症状（CI がたまに落ちる等） / なし>

リポジトリルート: <abs path>

手順は test-quality-auditor の定義に従う。出力フォーマットを厳守すること。
```

あるサブエージェントが失敗しても、残りの結果で監査を成立させ、失敗したスコープは段階7の「未確認・カバー外」に記録する。

### 段階6: 結果の統合

各 `test-quality-auditor` のマークダウン出力を読み、以下を構築する。

- **品質状況マトリクス**: コンポーネントごとに、テストファイル数・ケース数と指摘件数（C/H/M/L）を集計。
- **重複の整理**: 同一箇所の同一問題は 1 件にまとめる（重大度は最大を採用）。スイート横断で同じパターンが繰り返されている場合（例: 全コンポーネントでセットアップがコピペ）、コンポーネントごとに分けず**横断 1 件**に統合して「同種の広がり」に列挙する。
- **finding ID の付与**: 統合後の各指摘に安定 ID `TQ-<コンポーネント略号>-<連番>`（例 `TQ-booking-01`、横断は `TQ-x-01`）を振る。
- **リスク順位付け**: 重大度順、同重大度内は「誤ったシグナルを出す頻度・保守を阻害する範囲」で並べる。台帳は**上から順に直せば最も効率よくテストへの信頼が回復する順**にする。

### 段階7: 全文台帳のファイル出力＋チャット要約

指摘を集計して総合評価を決める。

| 評価 | 条件 |
|------|------|
| **Untrustworthy** | `critical` 指摘が 1 件以上（テストが現に嘘をつきうる） |
| **Fragile** | `critical` は無いが `high` が 1 件以上 |
| **Needs Care** | `high` は無いが `medium` が 1 件以上 |
| **Minor Issues** | `low` のみ |
| **Healthy** | 指摘 0 件 |

出力は2系統に分ける。**全文はファイル、チャットは要約**。全文を `docs/test-quality/<YYYY-MM-DD>-report.md` に書き出す（日付は `date` コマンドで取得、ディレクトリが無ければ作成、ユーザーが出力先を指定した場合はそれに従う。同日複数回は連番で上書き回避）。台帳にローカル絶対パスを書かない（対象リポジトリは org/repo 等の識別子で記す）。

全文テンプレート:

````markdown
# Test Quality Report（テスト品質台帳）
- **監査日**: 2026-07-04
- **対象リポジトリ**: <org/repo または プロジェクト名>

## 総合評価
**Fragile** — critical 0 / high 2（順序依存・実時刻依存。CI の不安定さの主因候補）

## 監査スコープとテストスイート
- **対象**: リポジトリ全体（5 コンポーネント / 4 作業項目、対象外: src/types）
- **テストランナー**: vitest（`npm test`）／配置規約: co-located `*.test.ts`
- **テスト実行の実測**: なし（依存未インストールのため静的監査）

## 品質状況マトリクス
| コンポーネント | テストファイル | ケース数 | 指摘 (C/H/M/L) |
|---|---|---|---|
| src/booking | 2 | 15 | 0/2/0/0 |
| src/pricing | 1 | 8 | 0/0/1/0 |

## 指摘台帳（リスク順）

### [HIGH] TQ-booking-01 順序依存: 共有ストアを全テストが使い回しリセットが無い
- **箇所**: src/booking/booking-service.test.ts:5-8（全ケースに波及）
- **問題**: describe 外で生成した単一ストアを全ケースが共有し、後半のケースが前半の作成データに依存している
- **実害**: 実行順の変更・単体実行・並列化でテストが落ちる／前のテストの残骸で誤って通る（false green）
- **改善方向**: beforeEach でストアを生成し直すか、ケースごとに独立したインスタンスを使う
- **同種の広がり**: なし（他コンポーネントは独立インスタンス）

## 良い手本（維持すべきパターン）
（スイート内で基準にできる実例。なければ「なし」）
- src/refunds/refund-policy.test.ts — 時刻固定注入・it.each・挙動ベースの命名

## 未確認・カバー外
- flaky の実証: 静的監査のため構造上のリスク指摘に留まる（実測 1 回でも flaky は確定できない）
- src/legacy: 監査エージェントが失敗し未監査

## 実測データ
- テスト実行: なし（理由） / 実行した場合は失敗・時間分布・特記事項
````

チャット要約は Critical/High に絞り、台帳全文のパスを示す（Medium 以下・根拠・改善方向の詳細は全文に委ねる）。末尾に「テストの修正自体は本スキルの対象外」と付す。

## サブエージェントとの契約

### スキル → エージェント（入力）

段階5 のテンプレートで送る。テストスイート情報と実測（あれば）は全項目に共通で渡し、エージェントに再探索させない。不明な項目は「不明」と書いて渡す。

### エージェント → スキル（出力）

`test-quality-auditor` の定義にある出力フォーマットで返る。スキルはこの構造（品質状況集計・指摘・良い手本・未確認）から機械的に集計して台帳を組む。

---

## 制約まとめ

- スキル自身は直接監査しない（オーケストレーション役）。テストコードの修正もしない（検出のみ）。
- 対象リポジトリを変更しない（依存追加・設定導入もしない）。
- テスト実行の実測は既設定・追加依存なし・妥当な時間の場合に限り、中央で 1 回だけ。flaky の再実行実証はしない（疑いの濃い指摘への統合後の限定的な裏取り実行は数回まで可。install は不可）。
- 監査計画は起動前に提示して合意を取る（重い並列起動のため）。
- プロダクションコードの保護ギャップ・バグ・脆弱性は指摘本体に混ぜない（test-audit / quality-review / security-review を案内）。
- スイート横断の同一パターンは横断 1 件（`TQ-x-`）に統合する。
- 全文台帳は `docs/test-quality/<日付>-report.md` に出力し、チャットには Critical/High に絞った要約のみ返す。
- 台帳にローカル絶対パスを書かない。各指摘に安定 ID `TQ-...` を付与する。
- 暗黙起動なし（`disable-model-invocation: true`）。
