# review-response 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

外部から来たレビューコメント（人間チーム／別 AI セッション／PR のコメント）を受け取り、それが本当に対応すべき指摘かを独立検証し、対応方針と方向性を答えるスキル。コード修正は責務外。

想定する最多フロー: ①AI と設計相談しつつ実装 → ②完了後にチームレビューや新規 AI セッションで客観レビュー → ③実装セッションに戻りレビュー結果を本スキルへ渡す → ④設計・実装で得た情報と、不足分をドキュメント／コードから補って対応判断。ただし他者の PR を引き継ぐこともあり、実装セッション外でも単独で成立させる必要がある。

同プラグインの兄弟スキルとの関係:

- code-review は変更を自分でレビューして指摘を **生成** する（上流）。本スキルは外部から来た **既存コメントの対応判断**（下流）。両者は逆向きで、本スキルの入力は「自分が生成していない、信頼度未知の主張」である点が決定的に違う。
- audit-tracking は finding の対応状態を永続追跡する。本スキルは「レビュー→その場で対応依頼」の単一サイクルが想定で、永続追跡はしない（ID も使い捨て）。

なお dev-toolkit にも類似スキルがあるが、リポジトリ規約（プラグイン間参照の制限）によりユーザーの明示指示がない限り参照しない。本スキルは review プラグイン自身の規約＝ code-review の二軸思想だけを土台にゼロベースで設計した。

## 中核的な設計判断

### 【load-bearing】妥当性（客観）と対応方針（裁定）の二軸分離
- **決定**: 各コメントに、検証で導く妥当性（妥当／部分的に妥当／的外れ／前提誤り）と、文脈裁定で導く対応方針（対応推奨／方針を変えて対応／要相談／見送り）を独立に付ける。グルーピングの第一キーは対応方針。ヘッダの `[ ]` には客観軸の妥当性を出す。
- **却下した代替案**: code-review の対応区分（要対応／検討／任意／見送り）をそのまま流用する案。→ それだと「その指摘が本当に正しいのか」という検証結果が所見に溶けて埋もれる。本スキルの存在意義は外部コメントの妥当性検証なので、妥当性を一級の軸として前面に出す必要がある（ユーザーが二択で「妥当性×対応方針」を選択、2026-06-07）。
- **防いでいる失敗**: 「妥当だが別 PR で見送り」「部分的に妥当だから方針を変えて対応」「前提誤りなので見送り」といった、検証結果と対応が食い違う現実的な裁定が表現できなくなる。
- **出所**: ユーザー要望（2026-06-07、構想で「本当に対応が必要か」「修正案を鵜呑みにしない」を核に挙げた）＋出力形式の二択選択。

### 【load-bearing】コメントの主張も修正案も鵜呑みにしない（独立検証が中心）
- **決定**: コメントが修正方法まで書いていても従わず、実コード・周辺コード・呼び出し側／先・ドキュメントで裏取りしてから判断する。検証の結果より良い方向があれば「方針を変えて対応」にして推奨にその方向を書く。
- **防いでいる失敗**: レビューコメントは差分だけを見てつくことが多く、設計意図・呼び出し側の保証・既存規約・運用制約を踏まえていない。鵜呑みにすると的外れ／前提誤りの指摘に振り回され、誤った修正を生む。これはユーザーが構想で最も強調した点。
- **出所**: ユーザー要望（2026-06-07、「差分から得られる情報だけでつく場合も多い」「修正方法が書かれていても鵜呑みにしない」）。

### 【load-bearing】コード修正は責務外（方向性まで）
- **決定**: 推奨は「どの方向で直すか」を示すところまでで、編集は行わない。
- **防いでいる失敗**: 判断と修正を一体化すると、ユーザーが判断だけ見て取捨選択する余地が消える。ユーザーは結果を見てから「#2 と #4 を直して」と選んで依頼するワークフローを想定。
- **出所**: ユーザー要望（2026-06-07、「修正自体はスキルの責務外として良い」）。

### 【load-bearing】要相談 と 対応推奨 の境界
- **決定**: 「直すべきこと自体は確定で、どこで／どう直すか（検証層・許容値域・別 PR か）だけが未確定」なら対応推奨（未確定点は推奨欄に確認事項として添える）。要相談は「そもそも直すか否かがコード外の判断（法務・業務ポリシー・スコープ）に委ねられ、それが決まらないと正否すら確定しない」論点に限る。線引きは依頼の口調でなく中身で行う。
- **却下した代替案**: 「情報不足やトレードオフがあれば要相談」という曖昧な定義（初版）。→ 妥当な欠落（実害のある検証漏れ等）まで要相談に流れ、依頼の口調（「危険」vs「気になる」）で対応方針がぶれた。
- **防いでいる失敗**: eval iteration-1 で、同一の「負 quantity 検証なし」指摘が eval-0 では対応推奨・eval-1/eval-2 では要相談に揺れた。要相談がゴミ箱化すると「で、結局どうするのか」が曖昧になり、対応依頼につなげにくい。
- **出所**: eval iteration-1 の分析（2026-06-07）。with_skill が valid-but-placement-ambiguous な指摘を要相談に回す傾向を検出し、境界を明文化。

### 指摘にグローバル通し ID（`#1`〜）を振る
- **決定**: 報告に出る順（区分順＝対応推奨→方針変更→要相談→見送り）に上から `#1, #2, …` と採番する。
- **目的**: ユーザーが報告後に「#2 と #4 を直して」と指摘単位で次の対応を依頼できるようにする参照ハンドル。
- **スコープ（要注意）**: 1 回の報告内で一意な使い捨て ID。再実行で振り直される。audit-tracking の `SA-api-01` のようなレポート横断の永続追跡 ID とは別物（本スキルは単一サイクル想定）。
- **出所**: code-review の通し ID 方式を踏襲（同プラグイン内の一貫性）。

### PR は未解決コメントのみを対象
- **決定**: PR 対象時は `reviewThreads` の `isResolved:false` だけを評価し、解決済みは件数注記のみでスキップする。`isOutdated` は中身で判断。
- **却下した代替案**: 全コメントを取り解決済みも区別表示する案／インライン指摘のみに絞る案。→ ユーザーが「未解決コメントのみ」を選択（2026-06-07）。一度片付いた議論の蒸し返しを避け、開いている指摘に集中する。
- **防いでいる失敗**: 解決済みを再評価して二度手間・混乱を生む。
- **出所**: ユーザー選択（2026-06-07、PR コメント範囲の四択）。

### 返信ドラフトは作らない／出力はチャットのみ
- **決定**: レビュアーへの返信文は生成しない。判断結果はファイル保存せずチャットにインライン出力する。
- **却下した代替案**: 見送り・方針変更に返信案を添える／全件に添える案、`docs/` への保存案。→ ユーザーがいずれも最小案を選択（2026-06-07）。判断に集中させ、定義・振る舞いを単純に保つ（code-review がチャットのみに単純化したのと同じ思想）。
- **出所**: ユーザー選択（2026-06-07、返信ドラフト／出力先の各設問）。

### 情報量は対応方針でなく確信度・再考余地で配分する
- **決定**: 全指摘に最小セット（通し ID／妥当性／箇所／一行要約／主判断）を残し、ユーザーが裁定を覆しうる指摘（見送り・要相談・方針変更・確信の低いもの）ほど根拠を厚くする。見送りこそ棄却根拠を厚く。
- **防いでいる失敗**: 「下の区分ほど薄く」にすると、見送り・要相談という最も再判断したい所の検証材料が消える。
- **出所**: code-review の同原則を踏襲（外部コメント検証では棄却の透明性がさらに重要）。

## 解釈・仮定（要確認）

- **対象の特定**: 入力はコメントテキスト（既定）か PR 指定の二種。どの変更へのコメントか曖昧なら、実装セッション内なら直近の作業／未コミット変更を当て、無理なら尋ねる。⚠️ セッション外で貼られたテキストのみだと対象変更を取り違える恐れ。報告の「対象」「文脈」に何を見たか明記して緩和する想定。
- **セッション文脈の扱い**: 実装セッション内なら既知の設計意図を活用してよいが、記憶は誤りうるのでコード／ドキュメントで裏取りする前提。⚠️ どこまでセッション知識に頼り、どこから裏取り必須とするかの線引きは eval で要調整。
- **未解決判定の取得**: GitHub の resolved 状態は `reviewThreads` の GraphQL でしか取れないため `gh api graphql` を用いる。⚠️ スレッドに紐づかない会話コメント・レビュー総括には resolved 概念がないので「開いている指摘」として拾う方針だが、ノイズになるなら絞り込みを検討。
