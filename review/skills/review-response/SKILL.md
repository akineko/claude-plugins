# レビュー対応判断

外部から来たレビューコメントを受け取り、それが本当に対応すべき指摘かを独立に検証して、対応方針と方向性を答えるスキル。コードの修正そのものは行わない（方向性を示すところまで）。

このスキルの核心はここにある:

- レビューコメントは **差分だけを見てつくことが多く**、設計意図・呼び出し側・既存規約・運用制約といった文脈を踏まえていないことがある。コメントが修正方法まで書いていても、それが正しい方向とは限らない。
- だから各コメントを、差分・周辺コード・ドキュメント（と、あれば実装セッションで得た設計意図）で **裏取りしてから**、妥当性と対応方針を判断する。**コメントの主張も修正案も鵜呑みにしない** のがこのスキルの存在意義。

兄弟スキルとの棲み分け: quality-review は変更を自分でレビューして指摘を **生成** する。本スキルは外部（人間チーム／別 AI セッション／PR）から来た **既存コメントの対応判断** に特化する。脆弱性は security-review、フレームワーク準拠 finding の対応追跡は audit-tracking が担当。

## 二軸の判断

各コメントに、独立した二軸を付ける。これが報告の骨格になる。

妥当性（検証の結果、その指摘は客観的に正しいか）:

- 妥当 — 指摘どおりの問題が実在する
- 部分的に妥当 — 問題の核はあるが、範囲・程度・原因がコメントとずれている
- 的外れ — 検証するとコードはコメントの言う挙動をしない（コメント側の誤読）
- 前提誤り — コードはそう動くが、コメントが見ていない文脈（呼び出し側の保証・既存規約・別レイヤでの対処）により懸念が成り立たない

対応方針（で、どうするか。あなたの裁定）。**「本質的に直すべきか（merit）」を第一に決め**、「どこで直すか（この変更内か別PRか）」は直すべき指摘にだけ付く二次情報として扱う:

- 対応推奨 — 直すべきで、この変更（PR / コミット）の目的の内側。ここで、コメントの方向で直す。どう直すか（検証層・許容値域など）に未確定な選択が残っても、直すこと自体が確定していればここに入れ、選択は推奨欄に確認事項として添える
- 方針を変えて対応 — 直すべきだが、コメントの修正案とは別の方向で（鵜呑みにしない核がここ）
- 別対応（範囲外）— 直すべきだが、この変更の目的から外れる（別PR/後回し）。**なぜ範囲外かを必ず書く** — 例: 今回の変更が触っていない既存コードの問題／新規コードと既存の複数呼び出し箇所をまたぐ横断的改善。merit が「直すべき」で確定している点が任意・見送りと違う follow-up
- 要相談 — そもそも直すか否かがチームの規約・方針や法務・業務ポリシーの判断で決まり、それが定まらないとコード上の正否すら確定しない論点（例: 割引と税の適用順序が税法的に正しいか）。コードだけでは裁定できない。「別PRに回すか」というスコープだけの問題はここではなく別対応で扱う
- 任意 — コメントは妥当だが好み・nitpick の範囲で、直さなくても問題ではない。ここに「やるなら別PR」と書かない —「別PR」は直す価値が確定した指摘の置き場所で、好みを体よく送る言葉ではない
- 見送り — 直さない（的外れ／前提誤り、または妥当でも実害がない、など根拠付きで）

二軸は連動しない。妥当でも好みで任意、妥当でも範囲外で別対応、部分的に妥当だから方針を変えて対応、的外れ／前提誤りなので見送り、コード外の判断待ちで要相談 — こうした食い違いを表現できることが価値。妥当性は検証で導く客観評価、対応方針は文脈を踏まえたあなたの裁定で、別物として扱う。

「直さない」に見える区分（別対応・任意・見送り）は理由が違う: 別対応＝直すべきだが範囲外、任意＝好みで不要、見送り＝そもそも不要。読み手が最初に知りたい「本質的に直すべきか」を区分から一目で読めるよう、この違いを区分で表し、「別PR」の一言に本質判断を埋もれさせない。

要相談に流しすぎない。妥当な欠落（実害のある検証漏れなど）は、検証層・許容値域が未確定でも、直すべきこと自体が確定しているなら対応推奨（または範囲外なら別対応）にし、未確定の選択は推奨欄に確認事項として添える。要相談は「そもそも直すかどうか」がコード外の判断（規約・方針・法務・業務ポリシー）に委ねられ、それが決まらないと前に進めない論点に限る。「別PRに切るか」というスコープだけの判断は、直すべきと確定しているなら別対応であって要相談ではない。同じ指摘でも依頼の口調（「危険」か「気になる」か）で対応方針がぶれないよう、この線引きは口調でなく中身で判断する。

## 進め方

### 1. 入力を特定する

| 入力 | 対象 |
|------|------|
| コメントテキストが貼られている（既定） | そのテキスト。1 件でも複数でも。レビュアー名・どの変更へのコメントかが分かれば押さえる |
| PR 番号・URL（「PR #123」「このPRのコメント対応」） | その PR の **未解決** コメント（取得は段階 2） |

- どの変更に対するコメントか曖昧なときは確認する。実装セッション内で実行されているなら、直近の作業や未コミット変更が対象であることが多い（`git diff HEAD`・`git log` で見当を付ける）。
- 対象の変更が特定できないと検証ができないので、無理に進めず何を見れば良いかを尋ねる。

### 2. PR の未解決コメントを取得する（PR 対象時）

owner / repo / 番号を確定する（URL から抽出、または番号＋`gh repo view --json owner,name`）。未解決のインラインスレッドだけを取る:

```
gh api graphql -f query='
query($owner:String!,$repo:String!,$pr:Int!){
  repository(owner:$owner,name:$repo){ pullRequest(number:$pr){
    reviewThreads(first:100){ nodes{ isResolved isOutdated
      comments(first:20){ nodes{ author{login} body path line diffHunk } } } } } }
}' -F owner=<owner> -F repo=<repo> -F pr=<番号>
```

- `isResolved: true` のスレッドは **スキップ** し、件数だけ「解決済み N 件はスキップ」と注記する（一度片付いた議論を蒸し返さない）。`isOutdated` は行が古いだけで懸念が残りうるので中身で判断する（自明に無効化されているなら見送り）。
- レビュー本文の総括（`gh pr view <番号> --json reviews`）と、スレッドに紐づかない未解決の会話コメントも、開いている指摘として拾う。
- 検証の土台として背景と差分も取る: `gh pr view <番号>`（説明・意図）、`gh pr diff <番号>`（実際の変更）。深い文脈が要れば `gh pr checkout` でブランチを取得し全文を読む。

### 3. 各コメントを独立検証する

ここがこのスキルの中心。コメントの主張・修正案を **鵜呑みにせず**、実際に裏取りしてから妥当性と対応方針を決める。確認する文脈の例:

- 指摘箇所の実コードと **周辺コード・呼び出し側／先**（コメントの前提＝非 null・到達可能性・呼び出し順序などが本当に成り立つか）
- 既存の規約・パターン（指摘がそれと整合するか、それとも局所最適か）
- ドキュメント（`docs/`・README・設計書）に書かれた意図・制約
- この変更の目的に照らして本筋の指摘か、別 PR に回すべき範囲外か
- 実装セッションで既に得ている設計意図（あれば活用する。ただし記憶は誤りうるのでコード／ドキュメントで裏取りする。引き継ぎ・単独実行でも成立させるため、セッション文脈に依存しきらない）

検証結果から妥当性を決め、文脈を踏まえて対応方針を裁定する。コメントが「こう直せ」と書いていても、検証の結果より良い方向があれば「方針を変えて対応」とし、その方向を推奨に書く。問題が実在しなければ、指摘を捻り出さず根拠を添えて見送る。

### 4. 報告する

下記フォーマットで会話内に報告する（出力はチャットのみ。ファイルには保存しない）。

## 報告フォーマット

```
# レビュー対応判断: <対象の説明>

対象: <コメントの出所・件数（PR なら #番号・未解決 N 件／解決済み M 件はスキップ）>
文脈: <検証に使った差分・主要ファイル・参照したドキュメント>
結果: 対応推奨 N ・方針変更 N ・別対応 N ・要相談 N ・任意 N ・見送り N

総評: <2〜4 行。鵜呑みにできなかった指摘・要相談の所在・全体傾向。あなたの統合判断。言及する指摘には #ID を併記する>

---

## 対応推奨
### #N [妥当性] 出典 file:line — コメント一行要約
- コメント: <原文／要約。出所（レビュアー名・位置）>
- 妥当性: <4 区分のいずれか> — <一句で検証結果>
- 根拠: <裏取りした文脈。path:line・docs で何を確認したか>
- 推奨: <対応するならどの方向で直すか。コード修正そのものはしない>
- 主判断: 対応推奨 — <理由>

## 方針を変えて対応
（コメントの案を採らず別方向にする理由を厚く。推奨にその方向を書く）

## 別対応（範囲外）
（主判断に「直すべき」と確定した根拠＋なぜこの変更の範囲外か を必ず書く。この変更はブロックせず follow-up として残す）

## 要相談
（不足している情報・トレードオフ・確認したい論点を具体的に。何が決まれば前に進めるか・誰に確認するか。スコープだけの問題はここに置かない＝別対応へ）

## 任意
（薄くてよい。妥当だが好みの範囲。「やるなら別PR」と書かず「直さなくても問題ではない」と言い切る）

## 見送り
（棄却根拠を厚く。妥当性が「的外れ／前提誤り」ならどこで裏取りしたかを残し、ユーザーが「本当に見送ってよいか」を検証できるようにする）
```

書き方の原則:

- **指摘には通し ID（`#1` から）を振る**: 報告に出てくる順（区分順＝対応推奨→方針変更→別対応→要相談→任意→見送り、区分内は妥当性順）に上から通しで採番する。ユーザーが「#2 と #4 を直して」と **指摘単位で次の対応を依頼** するための参照ハンドル。1 回の報告内で一意で、再実行すると振り直される（レポート横断で永続する追跡 ID ではない）。
- **ヘッダの `[ ]` には妥当性を出す**: 対応方針はグルーピングで分かるので、ヘッダには客観軸である妥当性を見せる。深刻さ／対応区分の二軸を独立させる quality-review と同じ発想。
- **鵜呑みにしない原則を貫く**: コメントが具体的な修正案を含んでいても、検証の結果より良い方向があれば「方針を変えて対応」にして推奨にその方向を書く。妥当性が低い指摘は理由を添えて見送り／要相談に回す。コメントに引きずられて中身のない「対応推奨」を作らない。
- **「別PR」は場所の答えで、本質判断の代わりにしない**: 直すべき（merit）が確定した指摘を範囲外に置くときだけ別対応に入れ、なぜ範囲外かを書く。好み・方針の指摘を「やるなら別PR」とぼかさず、任意（直さなくてよい）か要相談（誰かが決める）に分ける。区分を見れば「本質的に直すべきか」が分かる状態を保つ（このスキルが解く中心課題）。
- **情報量は対応方針でなく確信度・再考余地で配分する**: 全指摘に最小セット（通し ID／妥当性／箇所／一行要約／主判断）を必ず残す。そのうえで、ユーザーが裁定を覆しうる指摘（見送り・要相談・方針変更・確信の低いもの）ほど根拠を厚くする。明白な対応推奨は主判断の一文に溶かして省略してよい。「下の区分ほど薄く」ではない — 見送りこそ棄却根拠が要る。
- **コードは修正しない**: 推奨は方向を示すところまで。実際に手を動かす対応は別途ユーザーが依頼する（このスキルの責務外）。
- **解決済みコメントは蒸し返さない**: PR の解決済みスレッドは件数注記のみ。検証しても問題が実在しなければ、無理に指摘を作らない。
- 強調記号（`**`）を本文の指摘に使わない。ラベルは素のまま（`妥当性:` `主判断:`）。

## 対象外

- **コード修正そのもの**: 方向性まで示すが、編集は行わない。
- **指摘の新規生成**: 差分を自分でレビューして指摘を起こすのは quality-review の責務。本スキルは外部コメントの対応判断に徹する。検証の途中で別の重大な問題に気づいたら、指摘本体に混ぜず一言添えるに留める。
- **脆弱性・フレームワーク準拠**: security-review（脆弱性レビュー）／ security-audit・audit-tracking（フレームワーク準拠と finding 追跡）が担当。レビューコメントがこれらに触れていても、対応判断は本スキルで行ってよいが、深い検証が要るなら該当スキルを案内する。
