# audit-tracking 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

[[security-audit]] が検出した finding に対し、修正・許容・不足仕様や AI 不可視設定の説明を行い、再チェックして状態を追跡したい、というユーザー要望（2026-05）。検出（ゼロベース）と対応管理（継続）を分けて扱うために独立スキルとした。

## 中核的な設計判断

### 【load-bearing】security-audit と別スキルにする
- **決定**: 対応管理を security-audit に統合せず独立スキルにする。
- **却下した代替案**: security-audit に対応管理を統合 → スキルが肥大化し「検出」と「対応」で起動意図が混ざる。security-audit のゼロベース純度（過去状態を読まず常に最新で検出）も損なう。
- **防いでいる失敗**: 単一責務の崩壊。呼び出し頻度の違い（監査=たまに全体／対応=finding を潰すたびに頻繁）にも合わない。security-review や手動 pentest の finding にも使い回せる汎用性も得る。
- **出所**: ユーザー設計議論 2026-05（ユーザー自身が別スキルを志向）。

### 【load-bearing】レポート（不変）と対応表（可変）を別ファイルにする
- **決定**: 監査レポートは改変せず、可変の対応状態は対応表に持つ。
- **防いでいる失敗**: 不変のスナップショット（いつ・どの版で何を検出したか）に可変状態を混ぜると、ゼロベース再監査のたびに状態が消えるか毎回マージが要る。Git のコミット（不変）と Issue（可変）の関係。
- **出所**: ユーザー設計議論 2026-05。

### 【load-bearing】1 レポート = 1 対応表（自動マージしない）
- **決定**: レポートと対応表を同じ日付スタンプで 1:1 に対にする。新レポートには新対応表を生成し、旧状態は自動引き継ぎしない。
- **却下した代替案**: 単一の生 `tracking.md` ＋ 新旧レポートの突合（マージ）ルール（0.3.0 の当初想定 v2）→ 検出は毎回ゼロベースでフレームワーク版や finding が変わるため、機械的マージは誤った引き継ぎを生みやすく、運用コスト・リスクに対し効果が低い。
- **防いでいる失敗**: 複雑な統合ルールの保守負債と、状態の誤った持ち越し。
- **出所**: ユーザー判断 2026-05-31（単純さを優先）。

### 【load-bearing】報告を鵜呑みにせず実コードで再チェック
- **決定**: 「修正した」報告でも該当コードを実読し、要件充足を確認できなければ `修正済み` にせず `再確認要` に留める。
- **防いでいる失敗**: 誤った「解決済み」。検証（2026-05-31）で「所有者照合を追加したという未反映の虚偽報告」を `orders.ts` 実読により `再確認要` へ正しく落とせることを実証。これが本スキルの存在価値の肝。
- **出所**: 設計時の明示要望 + 動作確認 eval。

### 安定 ID はレポートから引き継ぐ（無ければ採番）
- **決定**: レポートが finding に振った `SA-...` ID を引き継ぐ。ID の無い旧版レポートに限り本スキルがコンポーネント別連番で採番（フォールバック）。
- **却下した代替案**: 本スキルが常に採番→ レポートと対応表で ID が分かれ不整合。ID 採番の権威は検出側（security-audit）に置くのが自然。
- **出所**: ユーザー指摘 2026-05-31。

### 【load-bearing】対応表にローカル絶対パスを書かない
- **決定**: 対象リポジトリは `<org>/<repo>`（git remote 由来）かプロジェクト名で記す。
- **防いでいる失敗**: 実行者のローカル絶対パス混入で共有時に無意味・環境依存。
- **出所**: 実運用フィードバック 2026-05-31。

### 緩和済みと許容を区別する
- **決定**: `緩和済み`＝別の防御（WAF・インフラ等）で実害が抑えられている、`許容`＝防御は増えていないがリスクを受容、と分ける。
- **防いでいる失敗**: 「対処した気」になる曖昧な状態。残存リスクを 1 行残させることで情報を踏まえた判断にする。

## 解釈・仮定（要確認）

- **状態語彙**: 未対応/修正済み/緩和済み/許容/誤検出/再確認要 の 6 種。⚠️ 運用で過不足があれば調整。
- **コード修正はしない**: 修正はユーザー／別作業が行い、本スキルは結果を再チェックするだけ。⚠️ 「修正して」まで求められた場合の扱いは未定（現状はスコープ外）。
