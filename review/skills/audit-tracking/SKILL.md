# Audit Tracking

[[security-audit]] が検出した finding に対する**対応の記録・再チェック・状態管理**を行うスキル。監査レポート（スナップショット）とは別の「対応表」を生で管理し、ユーザーの対応報告（修正した／設定はこうなっている／許容する）を受けて該当箇所を再チェックし、状態を更新する。

検出（フレームワーク準拠の点検）はやり直さない。それは security-audit の責務で、本スキルは「検出済みの finding をどう片付けたか」を追跡する。

## このスキルの責務

| やること | やらないこと |
|---------|------------|
| レポートと対になる対応表の生成（無ければ）と finding ID の引き継ぎ（無ければ採番） | フレームワーク全体の再監査・新規ゼロベース検出（security-audit が担当） |
| ユーザーの対応報告を finding へ紐づけ、対応種別を判定 | コード修正そのもの（ユーザー／別作業が行い、本スキルは結果を再チェック） |
| 修正・説明報告の**単一 finding 再チェック** | レポート（スナップショット）の改変 |
| 状態の更新と対応表の書き出し | 全件をチャットに展開（差分サマリのみ表示） |
| チャットへの差分サマリ出力 | 新旧レポートの自動マージ（1 レポート = 1 対応表） |

## security-audit との関係

- security-audit は**ゼロベース検出**: 毎回最新フレームワークで点検し、`docs/security-audit/<日付>-report.md` に不変のスナップショットを出す。過去の対応状態は読まない。
- audit-tracking は**対応管理**: そのレポートと対になる対応表（`docs/security-audit/<日付>-tracking.md`）を生で維持する。
- 両者を分けるのは、不変のスナップショット（いつ・どの版で何を検出したか）と可変の状態（どう対応したか）を混ぜないため。Git のコミット（不変）と Issue（可変）の関係に近い。
- **レポートと対応表は 1:1**。1 つのレポートに 1 つの対応表が対応し、同じ日付スタンプで並置する。詳細は「レポートと対応表の対応（1:1）」。

finding を結ぶ安定 ID（`SA-<コンポーネント略号>-<連番>`、例 `SA-api-01`）は**レポートから引き継ぐ**。レポートに ID が無い場合（ID 付与前の旧版で出力したレポート等）のみ、本スキルがコンポーネント別連番で採番する（後方互換のフォールバック）。

## ワークフロー

| 段階 | 目的 | 依存 |
|------|------|------|
| 1 | 入力の特定（監査レポートと対応報告） | - |
| 2 | 対応表の用意（生成＝ID 引き継ぎ／無ければ採番 or 読込） | 段階1 |
| 3 | 報告の finding 紐づけと対応種別の判定 | 段階2 |
| 4 | 再チェック（種別ごと） | 段階3 |
| 5 | 状態更新と対応表の書き出し | 段階4 |
| 6 | チャットへの差分サマリ | 段階5 |

---

### 段階1: 入力の特定

- **監査レポート**: ユーザー指定があればそれ。なければ `docs/security-audit/` 内の最新 `*-report.md`（`date`／更新時刻で比較）を採用し、どれを使うかを 1 行で明示する。見つからなければ「先に security-audit を実行してください」と告げて終了。
- **対応報告**: ユーザーの発話／貼り付けテキスト。1 件でも複数でも可。ID 指定（`SA-api-01`）、箇所指定（`orders.ts:42`）、説明文のいずれでも受け付け、段階3 で finding に対応づける。
- **対応報告が無い場合（引数なし／レポート指定のみ）**: 照会モードとして扱う。状態は変更せず、対応表の現状から段階6の「残り状況」ロールアップだけを返す（対応表が無ければ段階2の生成だけ行い、全件未対応のロールアップを返す）。段階3〜5はスキップする。
- **対象リポジトリの識別子**: `git -C <root> remote get-url origin` から `<org>/<repo>`（例 `acme/shopflow`）を導出する。remote が無ければプロジェクト（ルートディレクトリ）名。**ローカル絶対パスは記録しない**（環境依存で共有時に無意味なため）。

### 段階2: 対応表の用意

対象レポートと対になる対応表を確認する。対応表の名前はレポート basename の `-report` を `-tracking` に置換したもの（例: `<日付>-report.md` → `<日付>-tracking.md`、同日連番付きなら `<日付>-2-report.md` → `<日付>-2-tracking.md`）。

- **無ければ生成**: レポートの全 finding を読み、後述のフォーマットで対応表を作る。
  - **ID**: レポートが各 finding に振った `SA-...` ID をそのまま引き継ぐ。レポートに ID が無い場合のみ、コンポーネント別に出現順で `SA-<コンポーネント略号>-<連番>` を採番する（例: api → `SA-api-01`）。略号はコンポーネント名から取る。
  - 全 finding を初期状態 `未対応` で seed し、ヘッダに対象リポジトリ識別子・元レポートのパス・監査日・フレームワーク版を記録する。
- **あれば読込**: 既存の状態と採番済み ID を保持したまま、今回の報告分だけ更新する。

### 段階3: 報告の紐づけと対応種別の判定

各報告を該当 finding（`SA-...` ID 優先、無ければ箇所＋概要で照合）に結びつけ、対応種別を判定する。

| 対応種別 | 内容 | 例 |
|---------|------|----|
| **修正** | コードを直した（ユーザーが実施済み） | 「所有者照合を追加した」 |
| **説明** | 不足していた仕様・AI から見えない設定・前提の補足 | 「前段に WAF がある」「この値は環境変数でデプロイ時に注入」 |
| **許容** | リスクを認識した上で許容する（理由付き） | 「内部ネットワーク限定なので許容」 |

判定できない報告は、どの finding のことか・どの種別かをユーザーに確認する（誤った状態更新を避ける）。

### 段階4: 再チェック

対象 finding **だけ**を確認する軽量再チェック。フレームワーク全体は再取得しない。finding の要件はレポートに記録済みなのでそれを基準にする。

- **修正**: 該当ファイルを `Read`/`Grep` で読み、レポートの要件を満たしたか検証する。
  - 満たした → `修正済み`。根拠（どこでどう満たしたか）を `path:line` で残す。
  - 不十分・別経路が残る → `再確認要`。何が足りないかを書く。
- **説明**: 補足情報を踏まえて再評価する。
  - そもそも問題でなかった（誤検出と判明） → `誤検出`。
  - コード外に緩和策（WAF・インフラ統制・運用・デプロイ時注入）がある → `緩和済み`。残存リスクを 1 行添える。
  - 説明では解消しない → `再確認要` か `未対応` のまま。理由を書く。
- **許容**: 根拠（理由・許容範囲・判断者がいれば）を記録し `許容`。再チェックは不要だが、残存リスクを 1 行残して「情報を踏まえた許容」にする。

報告を鵜呑みにせず、実コードを読んでから状態を決める。修正を確認できないのに `修正済み` にしない（誤った「解決済み」は最悪）。要件の詳細がレポートに無く判定に必要な場合のみ、レポート記載のフレームワーク版・出典 URL から**その要件だけ**を `WebFetch` で引く、または `review:framework-auditor` を当該 finding のスコープに絞って起動する（既定はしない。重いので最小限）。

### 段階5: 状態更新と対応表の書き出し

対象 finding の 状態／対応種別／対応内容・根拠／再チェック結果／更新日（`date` で取得）を更新し、`docs/security-audit/<日付>-tracking.md` を書き出す。ヘッダの「最終更新」も更新する。報告のなかった finding は触らない。

### 段階6: チャットへの差分サマリ

全件は表示せず、**今回更新した finding の差分**と**残り状況のロールアップ**だけを返す。

```
## 対応更新（3 件）
- SA-api-01 BOLA: 未対応 → 修正済み（orders.ts:42 で所有者照合を確認）
- SA-infra-02 機密平文: 未対応 → 緩和済み（デプロイ時に Secrets Manager 注入。残存: ローカル tfvars の管理）
- SA-api-02 未認証 API: 未対応 → 再確認要（1 本は認証追加、残り 2 本は未対応）

## 残り状況
- 未対応 N / 再確認要 1 / 修正済み 1 / 緩和済み 1 / 許容 0 / 誤検出 0（全 M 件）
- 未解決の Critical/High: SA-api-02(再確認要), SA-infra-01(未対応) ...
- 対応表: docs/security-audit/2026-05-31-tracking.md
```

## 対応表のフォーマット

`docs/security-audit/<日付>-tracking.md`。コンポーネント別にセクション分けし、各セクションの表に finding を並べる（セクション見出しがコンポーネントを表すので、表に「コンポーネント」列は持たない）。

````markdown
# Security Audit 対応管理表
- **対象リポジトリ**: acme/shopflow
- **元レポート**: docs/security-audit/2026-05-31-report.md（監査日 2026-05-31）
- **フレームワーク版**: OWASP API Security Top 10 (2023) / OWASP ASVS v5.0.0 / CIS AWS Foundations v3.0 (Prowler) / OWASP Docker Top 10
- **最終更新**: 2026-05-31

状態: 未対応 / 修正済み / 緩和済み / 許容 / 誤検出 / 再確認要

> ID はレポートの finding ID を引き継ぐ（レポートに無ければ本対応表で採番）。finding の箇所・攻撃経路・根拠の詳細は元レポートを参照する。

## api（API / バックエンド）

| ID | 要件(FW) | 概要 | 重大度 | 状態 | 対応種別 | 対応内容・根拠 | 再チェック結果 | 更新日 |
|----|---|---|---|---|---|---|---|---|
| SA-api-01 | API1:2023 | 公開エンドポイントのオブジェクトレベル認可欠落（BOLA） | CRITICAL | 修正済み | 修正 | 取得前に所有者照合を追加 | orders.ts:42 で照合を確認、他人 ID は 403 | 2026-05-31 |
| SA-api-02 | API5:2023 | 状態変更トリガ API が未認証 | HIGH | 未対応 | - | - | - | 2026-05-31 |

## infra（IaC / AWS）

> 複合 critical: SA-infra-01〜03 が外部 DB 到達経路を形成。優先是正。

| ID | 要件(FW) | 概要 | 重大度 | 状態 | 対応種別 | 対応内容・根拠 | 再チェック結果 | 更新日 |
|----|---|---|---|---|---|---|---|---|
| SA-infra-01 | CIS 2.3.3 | RDS がパブリックアクセス可能 | CRITICAL | 未対応 | - | - | - | 2026-05-31 |
````

- 各セクションの先頭に、複合リスクなどセクション固有の注記を `>` で任意に添えてよい。
- ヘッダの「対象リポジトリ」は `<org>/<repo>` か プロジェクト名のみ。ローカル絶対パスは書かない。

## 状態の定義

| 状態 | 意味 |
|------|------|
| **未対応** | 報告なし。初期状態。 |
| **修正済み** | コード修正を再チェックで確認し、要件を満たした。 |
| **緩和済み** | コード外の緩和策（WAF・インフラ・運用・デプロイ時注入など）が確認でき、残存リスクが許容範囲。finding 自体は実在する。 |
| **許容** | 未修正だが、リスクを認識した上で根拠付きで受容。 |
| **誤検出** | 補足情報により、そもそも問題でないと判明。 |
| **再確認要** | 対応の報告はあったが、再チェックで解決を確認できなかった。要追加対応。 |

`緩和済み` と `許容` を混同しない。緩和済み＝別の防御で実害が抑えられている、許容＝防御は増えていないがリスクを受け入れる。

## レポートと対応表の対応（1:1）

security-audit を再実行すると、その時点の最新フレームワークで新しいレポート `<新日付>-report.md` が出る。本スキルは **1 レポート = 1 対応表** とし、対応表は対象レポートの basename の `-report` を `-tracking` に置換した名前で対にする（日付・連番を共有する）。

- 新しいレポートには新しい対応表を生成する（全 finding を `未対応` で seed、ID はレポートから引き継ぎ／無ければ採番）。前回の対応表の状態は**自動では引き継がない**。
- 新旧レポートの自動マージ（突合）は行わない。検出は毎回ゼロベースでフレームワーク版や finding が変わりうるため、機械的なマージは誤った引き継ぎを生みやすく、運用コストに見合わないと判断した（複雑な統合ルールより 1:1 の単純さを優先）。
- 前回の対応を引き継ぎたい場合は、ユーザーが旧対応表を参照し、なお有効な状態を新対応表に転記する。指示があれば本スキルが転記を手伝うが、既定では行わない。

## 制約まとめ

- 検出はやり直さない（ゼロベース監査は security-audit）。本スキルは検出済み finding の対応追跡に徹する。
- コードは修正しない（修正は別途行い、本スキルは結果を再チェックする）。
- レポート（スナップショット）は改変しない。可変の状態は対応表（`<日付>-tracking.md`）に持つ。
- 対応表に**ローカル絶対パスを書かない**。対象リポジトリは `<org>/<repo>`／プロジェクト名で記す。
- finding の安定 ID はレポートから引き継ぐ（無ければ本スキルがコンポーネント別連番で採番）。紐づけは ID 優先、曖昧なら状態を更新せずユーザーに確認する。
- 再チェックは対象 finding だけの軽量確認。フレームワーク全体の再取得はしない（必要時のみ当該要件を最小フェッチ）。
- `修正済み` は再チェックの根拠を `path:line` で残す。確認できないなら `再確認要` に留める（誤った「解決済み」を作らない）。
- レポートと対応表は 1:1。新旧の自動マージはしない。
- チャットには差分サマリのみ。全件は対応表ファイルに委ねる。
