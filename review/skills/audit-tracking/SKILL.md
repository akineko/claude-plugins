# Audit Tracking

[[security-audit]] が検出した finding に対する**対応の記録・再チェック・状態管理**を行うスキル。監査レポート（スナップショット）とは別の「対応表」を生で管理し、ユーザーの対応報告（修正した／設定はこうなっている／許容する）を受けて該当箇所を再チェックし、状態を更新する。

検出（フレームワーク準拠の点検）はやり直さない。それは security-audit の責務で、本スキルは「検出済みの finding をどう片付けたか」を追跡する。

## このスキルの責務

| やること | やらないこと |
|---------|------------|
| 監査レポートからの対応表の生成（無ければ） | フレームワーク全体の再監査・新規ゼロベース検出（security-audit が担当） |
| ユーザーの対応報告を finding へ紐づけ、対応種別を判定 | コード修正そのもの（ユーザー／別作業が行い、本スキルは結果を再チェック） |
| 修正・説明報告の**単一 finding 再チェック** | レポート（スナップショット）の改変 |
| 状態の更新と対応表の書き出し | 全件をチャットに展開（差分サマリのみ表示） |
| チャットへの差分サマリ出力 | — |

## security-audit との関係

- security-audit は**ゼロベース検出**: 毎回最新フレームワークで点検し、`docs/security-audit/reports/<日付>.md` に不変のスナップショットを出す。過去の対応状態は読まない。
- audit-tracking は**継続的な対応管理**: スナップショットを入力に、複数回の監査・対応をまたいで動く対応表（`docs/security-audit/tracking.md`）を維持する。
- 両者を分けるのは、不変のスナップショット（いつ・どの版で何を検出したか）と可変の状態（どう対応したか）を混ぜないため。Git のコミット（不変）と Issue（可変）の関係に近い。

検出のキーは security-audit がレポートで各 finding に振る安定 ID `SA-<コンポーネント略号>-<連番>`（例 `SA-api-01`）。本スキルはこの ID で finding と対応状態を結ぶ。

## ワークフロー

| 段階 | 目的 | 依存 |
|------|------|------|
| 1 | 入力の特定（監査レポートと対応報告） | - |
| 2 | 対応表の用意（生成 or 読込） | 段階1 |
| 3 | 報告の finding 紐づけと対応種別の判定 | 段階2 |
| 4 | 再チェック（種別ごと） | 段階3 |
| 5 | 状態更新と対応表の書き出し | 段階4 |
| 6 | チャットへの差分サマリ | 段階5 |

---

### 段階1: 入力の特定

- **監査レポート**: ユーザー指定があればそれ。なければ `docs/security-audit/reports/` 内の最新（`date` で日付比較、または更新時刻）を採用し、どれを使うかを 1 行で明示する。レポートが見つからなければ「先に security-audit を実行してください」と告げて終了。
- **対応報告**: ユーザーの発話／貼り付けテキスト。1 件でも複数でも可。ID 指定（`SA-api-01`）、箇所指定（`orders.ts:8`）、説明文のいずれでも受け付け、段階3 で finding に対応づける。
- リポジトリルートの絶対パスを確定する。

### 段階2: 対応表の用意

`docs/security-audit/tracking.md` を確認する。

- **無ければ生成**: 採用したレポートの全 finding を読み、後述のフォーマットで対応表を作る。全 finding を初期状態 `未対応` で seed し、ヘッダにレポートのパス・監査日・フレームワーク版を記録する。
- **あれば読込**: 既存の状態を保持したまま、今回の報告分だけ更新する。レポートが前回より新しい場合の突合は「再監査時の突合」を参照（v1 では新規 finding の追記とヘッダ更新まで）。

### 段階3: 報告の紐づけと対応種別の判定

各報告を該当 finding（ID 優先、無ければ箇所＋内容で照合）に結びつけ、対応種別を判定する。

| 対応種別 | 内容 | 例 |
|---------|------|----|
| **修正** | コードを直した（ユーザーが実施済み） | 「所有者照合を追加した」 |
| **説明** | 不足していた仕様・AI から見えない設定・前提の補足 | 「前段に WAF がある」「この値は環境変数でデプロイ時に注入」 |
| **許容** | リスクを認識した上で許容する（理由付き） | 「内部ネットワーク限定なので許容」 |

判定できない報告は、どの finding のことか・どの種別かをユーザーに確認する（誤った状態更新を避ける）。

### 段階4: 再チェック

対象 finding **だけ**を確認する軽量再チェック。フレームワーク全体は再取得しない。finding の要件はレポートに記録済みなのでそれを基準にする。

- **修正**: 該当ファイルを `Read`/`Grep` で読み、レポートの要件を満たしたか検証する。
  - 満たした → `修正済み`。根拠（どこでどう満たしたか）を `path:line` で残す。
  - 不十分・別経路が残る → `再確認要`。何が足りないかを書く。
- **説明**: 補足情報を踏まえて再評価する。
  - そもそも問題でなかった（誤検出と判明） → `誤検出`。
  - コード外に緩和策（WAF・インフラ統制・運用・デプロイ時注入）がある → `緩和済み`。残存リスクを 1 行添える。
  - 説明では解消しない → `再確認要` か `未対応` のまま。理由を書く。
- **許容**: 根拠（理由・許容範囲・判断者がいれば）を記録し `許容`。再チェックは不要だが、残存リスクを 1 行残して「情報を踏まえた許容」にする。

要件の詳細がレポートに無く判定に必要な場合のみ、レポート記載のフレームワーク版・出典 URL から**その要件だけ**を `WebFetch` で引く、または `review:framework-auditor` を当該 finding のスコープに絞って起動する（既定はしない。重いので最小限）。

### 段階5: 状態更新と対応表の書き出し

対象行の 状態／対応種別／対応内容・根拠／再チェック結果／更新日（`date` で取得）を更新し、`docs/security-audit/tracking.md` を書き出す。ヘッダの「最終更新」も更新する。報告のなかった finding は触らない。

### 段階6: チャットへの差分サマリ

全件は表示せず、**今回更新した finding の差分**と**残り状況のロールアップ**だけを返す。

```
## 対応更新（3 件）
- SA-api-01 BOLA: 未対応 → 修正済み（orders.ts:8 に assertOwner 適用を確認）
- SA-api-04 ハードコード機密: 未対応 → 緩和済み（デプロイ時に環境変数注入、リポジトリには非含有。残存: ローカル .env の管理）
- SA-chat-01 過剰権限: 未対応 → 再確認要（run_shell は残存。query_db のみパラメータ化）

## 残り状況
- 未対応 2 / 再確認要 1 / 修正済み 1 / 緩和済み 1 / 許容 0 / 誤検出 0（全 5 件）
- 未解決の Critical/High: SA-chat-01(再確認要), SA-infra-02(未対応)
- 対応表: docs/security-audit/tracking.md
```

## 対応表のフォーマット

`docs/security-audit/tracking.md`:

````markdown
# Security Audit 対応管理表
- **対象リポジトリ**: <name / ルートパス>
- **元レポート**: docs/security-audit/reports/2026-05-30.md（監査日 2026-05-30）
- **フレームワーク版**: ASVS v5.0.0 / API Top10 2023 / MASVS v2.1.0 / LLM Top10 2025 / CIS AWS v3.0
- **最終更新**: 2026-06-02

状態: 未対応 / 修正済み / 緩和済み / 許容 / 誤検出 / 再確認要

| ID | コンポーネント | 要件(FW) | 重大度 | 状態 | 対応種別 | 対応内容・根拠 | 再チェック結果 | 更新日 |
|----|---|---|---|---|---|---|---|---|
| SA-api-01 | services/api | API1:2023 / ASVS 8.2.2 | CRITICAL | 修正済み | 修正 | 所有者照合ミドルウェアを追加 | orders.ts:8 で assertOwner 適用を確認、他人 ID で 403 | 2026-06-02 |
| SA-chat-01 | services/chat | LLM06:2025 | CRITICAL | 再確認要 | 修正 | query_db をパラメータ化 | run_shell が未対処で RCE 経路が残存 | 2026-06-02 |
| SA-infra-02 | infra | CIS 2.1.4 | CRITICAL | 未対応 | - | - | - | 2026-05-30 |
````

## 状態の定義

| 状態 | 意味 |
|------|------|
| **未対応** | 報告なし。初期状態。 |
| **修正済み** | コード修正を再チェックで確認し、要件を満たした。 |
| **緩和済み** | コード外の緩和策（WAF・インフラ・運用・デプロイ時注入など）が確認でき、残存リスクが許容範囲。finding 自体は実在する。 |
| **許容** | 未修正だが、リスクを認識した上で根拠付きで受容。 |
| **誤検出** | 補足情報により、そもそも問題でないと判明。 |
| **再確認要** | 対応の報告はあったが、再チェックで解決を確認できなかった。要追加対応。 |

`緩和済み` と `許容` を混同しない。緩和済み＝別の防御で実害が抑えられている、許容＝防御は増えていないがリスクを受け入れる。

## 再監査時の突合（将来 / v2）

security-audit を再実行すると新しいレポートが出る。本スキルは将来、新旧レポートを finding キー（コンポーネント＋要件＋箇所/概要）で突合し、(1) 残存 finding は状態を引き継ぐ、(2) 消えた finding は「再監査で未検出＝解決確認」に、(3) 新規 finding は `未対応` で追記、という照合を行う想定。v1 では「1 レポート＋対応報告 → 対応表の生成・更新」に絞り、新しいレポートを指定された場合はヘッダ更新と新規 finding の追記までを行う。

## 制約まとめ

- 検出はやり直さない（ゼロベース監査は security-audit）。本スキルは検出済み finding の対応追跡に徹する。
- コードは修正しない（修正は別途行い、本スキルは結果を再チェックする）。
- レポート（スナップショット）は改変しない。可変の状態は対応表（`docs/security-audit/tracking.md`）に持つ。
- finding の紐づけは ID（`SA-...`）優先。曖昧なら状態を更新せずユーザーに確認する。
- 再チェックは対象 finding だけの軽量確認。フレームワーク全体の再取得はしない（必要時のみ当該要件を最小フェッチ）。
- `修正済み` は再チェックの根拠を `path:line` で残す。確認できないなら `再確認要` に留める（誤った「解決済み」を作らない）。
- チャットには差分サマリのみ。全件は対応表ファイルに委ねる。
