# コードレビュー

変更を3つの専門レビュアーに並列で重点レビューさせ、メインエージェント（あなた）が統合して客観判断を下すスキル。

役割分担が肝なので最初に押さえる:

- **専門レビュアー（サブエージェント）** は各レーンに集中し、指摘に **深刻さ（客観的影響度 🔴🟡🟢）** だけを付ける。「実際に直すべきか」は判断しない。
- **あなた（メインエージェント）** は全指摘を集約し、周辺コード・プロジェクト背景を読んで **対応区分（要対応/別対応/要相談/任意/見送り）と主判断** を付ける。専門家が見る差分だけでは分からない文脈（呼び出し側・既存規約・運用上の制約・この差分の目的）で対応要否を裁定するのがあなたの中心的な仕事。

この二段構えにより、深刻さ（どれだけ重大か）と対応区分（実際どうするか）が独立して扱え、「重大だが今は見送ってよい」「些細だが今直すべき」といった現実的な判断を表現できる。

対応区分は **「本質的に直すべきか（merit）」を第一の問い** として決める。「どこで直すか（この差分内か別PRか）」は merit が「直すべき」の指摘にだけ付く二次情報で、merit の答えの代わりにはしない。「別PR」を本質判断の代わりに使うと、読み手は「実在する問題だが範囲外」なのか「好み程度で直さなくてよい」のかを区別できなくなる。区分を見ただけで「本質的に直すべきか」が読めるようにするのがこの分離の目的。

セキュリティ脆弱性（認証・認可・インジェクション・機密情報など）はこのスキルの対象外。依頼にセキュリティ観点が含まれる場合は、その部分は security-review（脆弱性レビュー）または security-audit（フレームワーク準拠監査）の担当だと案内する。

## 進め方

### 1. 対象を解決する

依頼の自然言語から、レビュー対象を具体的な差分に解決する。対象が明示されていなければ **未コミットの変更全体** を既定とする（最も多いコミット前レビューのため）。何を見たかは必ず報告ヘッダに明記し、対象の取り違えを防ぐ。

| 依頼の例 | 対象 | 取得 |
|---------|------|------|
| 「レビューして」（無指定・既定） | 未コミット変更全体（staged+unstaged＋新規） | `git diff HEAD` ＋ `git status` で新規ファイルを確認し内容を読む |
| 「これからコミットする分」「staged を見て」 | ステージ済み | `git diff --staged` |
| 「コミット前の変更」 | 作業ツリー全体 | `git diff HEAD`（＋新規ファイル） |
| 「このコミット」「abc123 を」 | 単一コミット | `git show <sha>` |
| 「A から B の範囲」 | コミット範囲 | `git diff <A>..<B>` |
| 「このブランチの変更」「PR にする前に」 | ブランチの差分 | `git diff <base>...HEAD`（base は既定ブランチ。`git symbolic-ref refs/remotes/origin/HEAD` や `gh repo view` で特定、不明なら main/master を試す） |
| 「PR #123」「このPR見て」 | プルリクエスト | `gh pr diff <番号>`。背景は `gh pr view <番号>`。深い文脈が要れば `gh pr checkout` でブランチを取得し全文を読む |
| 「src/api 以下に絞って」「○○サービスだけ」 | 上記＋パス限定 | 上のコマンドに `-- <pathspec>` を付ける |

- 対象が大きすぎる場合（数十ファイル超）は、その旨を伝え、重点を置くパス/サービスを確認するか、規模を明示した上で進める。黙って一部だけ見ない。
- 差分が空、または対象が解決できないときは、何を試したかを示して対象を確認する。

### 2. 専門家へ並列ディスパッチ

3つのサブエージェントを **同一メッセージ内で並列起動** する（Agent ツール、`subagent_type` に各エージェント名）。

- `review:quality-review-correctness` — 正確性
- `review:quality-review-design` — 設計・保守性
- `review:quality-review-performance` — パフォーマンス

各エージェントへ渡す情報:

- 解決済みの対象（git range／PR番号／pathspec と、差分を取得する具体コマンド）
- 変更ファイル一覧
- スコープの説明（monorepo のどのサービスか等、絞っているなら明記）
- 「自分のレーンに集中し、判定に必要なら周辺コードを読んでよい。深刻さだけ付け、対応区分は付けない」旨（各エージェント定義に記載済みなので簡潔でよい）

専門家を分けるのは、汎用レビューだと各視点が薄まるため。同じ箇所に複数視点の所見が出るのは想定内で、それは比較検討の材料になる（次ステップで扱う）。

### 3. 統合と客観判断

全エージェントの所見が出揃ったら、あなたが統合する。ここがこのスキルの中心。

1. **集約と整理**: 全指摘を集める。明らかな重複（同一箇所・同一論点）は1件にまとめる。各エージェント末尾の「他レーンで気づいた点」メモは、該当レーンの所見と突き合わせて拾う。
2. **相違の検出**: 同じ箇所に異なる視点から対立する所見が出ていたら（例: design は「分割すべき」、correctness は「分割すると整合性が壊れる」）、片方に潰さず両論を併記する材料として保持する（`⚖`）。
3. **客観判断（対応区分の付与）**: 各指摘について、差分だけでなく周辺コード・プロジェクト背景を確認し、対応区分と主判断を決める。確認する文脈の例:
   - 呼び出し側・呼び出し先が指摘の前提（非負・非null 等）を本当に満たすか
   - 周辺の既存コードがどの規約・パターンに従っているか（指摘がそれと整合するか）
   - 指摘箇所が到達可能か（デッドコード・無効化されたフラグ配下でないか）
   - この差分の目的に対して、その指摘が本筋か・別PRに回すべき範囲外か
   - 運用上の制約（既存の許容・別レイヤでの対処・後方互換）
   
   この確認の結果、深刻だが見送ってよい／些細だが今直すべき、といった深刻さと食い違う判断が出るのは正常。相違（`⚖`）はどちらを採るか／保留かを根拠とともに裁定する。
4. **深刻さの調整**: 専門家が付けた深刻さを基本に、エージェント間で基準がぶれていれば一貫性のため調整してよい。ただし下げる時は理由を持つ。

対応区分の定義（「本質的に直すべきか」で決め、「どこで直すか」は二次）:

- **要対応**: 直すべきで、かつこの差分（コミット/PR）の目的の内側。ここで直す。
- **別対応（範囲外）**: 直すべきだが、この差分の目的から外れる（別PR/後回し）。**なぜ範囲外かを必ず書く** — 例: 今回触っていない関連コードで見つけた既存バグ／新規コードと既存の複数呼び出し箇所をまたぐ横断的改善／無関係モジュール。merit が「直すべき」で確定している点が任意・見送りと決定的に違う。このPR自体はブロックしない follow-up。
- **要相談**: 直すか否かがチームの規約・方針や業務/法務の判断に依存し、それが決まらないとコード上の正否すら確定しない論点（例: 命名・レイヤ構成の規約が未確立で、どの形が正かをチームが決めるべき場合）。コードだけでは裁定できない。「別PRに切るか」というスコープだけの問題はここではなく別対応で扱う。
- **任意**: 好み・nitpick の範囲で、客観的に直す根拠は弱い。ここに「やるなら別PR」と書かない — 「別PR」は直す価値が確定した指摘の置き場所であって、好みの指摘を体よく送る言葉ではない。直さなくてよいなら理由を添えて「直さなくても問題ではない」と言い切る。
- **見送り**: 専門家は挙げたが、背景から対応不要と判断したもの（到達不能・既存許容・誤検出など）。棄却の透明性のため残す。

別対応・任意・見送りはどれも「このPRでは直さない」が理由が違う（範囲外だが要対応級／好みで不要／そもそも不要）。読み手が最初に知りたい「本質的に直すべきか」が区分から一目で分かるよう、この違いを区分で表す。相違（⚖）は区分を merit で裁定する — 決着がコード外判断に依存するなら要相談、片方の視点が勝つならその区分に置き、両論は併記する。

### 4. 報告する

下記フォーマットで会話内に報告する。

## 報告フォーマット

```
# コードレビュー: <対象の説明>

対象: <解決した範囲・ファイル数・増減行（絞っていればその旨）>
視点: 正確性・設計保守性・パフォーマンス（セキュリティ対象外 → 必要なら security-review）
結果: 要対応 N ・別対応 N ・要相談 N ・任意 N ・見送り N
総合: <Approve / Request Changes / Needs Discussion> — <一句で理由>

総評: <最も効く論点・全体傾向・相違の所在を2〜4行で。あなたの統合判断。言及する指摘には #ID を併記する>

---

## 要対応
### #N <深刻さ絵文字> [視点] file:line — 一行所見
- 所見: <何が問題か>
- 根拠/影響: <なぜ問題か。周辺コードで裏取りした文脈・波及先>
- 推奨: <どう直すか。手を動かしうる指摘にのみ>
- 主判断: 要対応 — <直すべき根拠と、この差分内で直す理由>

## 別対応（範囲外）
（主判断に「直すべき」と確定した根拠＋なぜこの差分の範囲外か を必ず書く。このPRはブロックせず follow-up として残す。相違は ⚖ を付け各視点を併記し、⚖ でも ID は1件1つ）

## 要相談
（直すか否かがコード外の判断に委ねられる論点。何が決まれば結論が出るか・誰に確認するかを書く。スコープだけの問題はここに置かない＝別対応へ）

## 任意
（薄くてよい。#ID・視点・箇所・一行所見 + 主判断のみ。「やるなら別PR」と書かず「直さなくても問題ではない」と言い切る）

## 見送り（専門家が指摘したが対応不要と判断）
（棄却根拠を厚めに。ユーザーが「本当に見送ってよいか」を検証できる材料を残す）
```

書き方の原則:

- **指摘には通しID（`#1` から）を振る**: 報告に出てくる順（＝区分順 要対応→別対応→要相談→任意→見送り、区分内は深刻さ順）に上から通しで採番する。これは後からユーザーが「#3 を対応して」と指摘単位で対応を依頼するための識別子。重複統合後の最終的な指摘集合に対して振り、相違（⚖）は複数視点にまたがっても1件＝1つのIDとする。総評で論点に言及する際は該当 #ID を併記し、結論から指摘本体へすぐ辿れるようにする。
- **二軸は独立**: 深刻さ（🔴 高/🟡 中/🟢 低、専門家由来の客観的影響度）と対応区分（あなたの裁定＝本質判断）は別物。グルーピングの第一キーは対応区分、区分内は深刻さ順。要対応に 🟢 が入ること、見送りに 🔴 が入ることは正常で、その食い違いこそ価値ある判断。
- **「別PR」は場所の答えで、本質判断の代わりにしない**: 直すべき（merit）が確定した指摘を範囲外に置くときだけ別対応に入れ、なぜ範囲外かを書く。好み・方針の指摘を「やるなら別PR」とぼかさない。区分を見れば「本質的に直すべきか」が分かる状態を保つ（このスキルが解く中心課題）。
- **総合は対応区分から導く**（深刻さではない）: 要対応が1件でもあれば Request Changes、要対応0でも要相談または未決着の相違（⚖）があれば Needs Discussion、いずれもなければ Approve。別対応（範囲外）だけが残る場合はこのPRは Approve でよく、follow-up として総評に出す。🔴 が残っていても区分が全て別対応/任意/見送りなら Approve になりうる — 二軸独立の帰結として正常。
- **全指摘に最小セットを必ず残す**: 通しID／視点タグ／箇所／一行所見／主判断（区分＋理由）。これだけ走査すれば、区分に関わらず一定の薄さで全件把握できる。把握コストを区分で増減させない。
- **情報量は対応区分でなく確信度・再考余地で配分する**: ユーザーが主判断を覆しうる指摘（見送り・相違・確信の低いもの）ほど根拠/影響を厚くする。明白な指摘は主判断の一文に溶かして省略してよい。「下の区分ほど薄く」ではない — 見送りこそ棄却根拠が要る。
- **強調記号（`**`）を使わない**。ラベルは素のまま（`所見:` `主判断:`）。
- 推奨（How to fix）は実際に手を動かしうる指摘にのみ付ける。見送りには付けない。
- 重大な問題が無ければ、専門家が「問題なし」とした旨と確認範囲を簡潔に報告する。指摘を捻り出さない。

## 対象外: セキュリティ

認証・認可・インジェクション・機密情報・暗号・依存脆弱性などは、質の異なる専門領域として別スキルが担当する。依頼にこれらが含まれる、またはレビュー中に重大なセキュリティ懸念に気づいた場合は、指摘本体に混ぜず、「セキュリティ観点は対象外。security-review（脆弱性レビュー）/ security-audit（フレームワーク準拠監査）での確認を推奨」と一言添える。
