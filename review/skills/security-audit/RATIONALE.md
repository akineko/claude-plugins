## 目的と背景

差分単位の [[security-review]] とは別に、リポジトリ全体・サービス単位を**公開フレームワークへの準拠**という軸で監査したい、というユーザー要望（2026-05）から生まれた。広範囲・多フレームワーク・多コンポーネントを、サブエージェントで分担して効率と専門性を両立させるのが狙い。検出のみを担い、対応管理は [[audit-tracking]] に分離している。

## 中核的な設計判断

### 【load-bearing】汎用 auditor 1 つ＋対応表で制御（フレームワークを焼き込まない）
- **決定**: `framework-auditor` を 1 つだけ用意し、起動時に〈スコープ＋単一フレームワーク＋参照元〉を渡す。種別→フレームワークの対応は `references/frameworks.md`。
- **却下した代替案**: フレームワークごとに専用サブエージェントを定義 → フレームワーク数だけ定義が増え保守が重く、内容を焼き込むとバージョン追従の狙いと矛盾。
- **防いでいる失敗**: フレームワーク追加・更新のたびに定義ファイルを増改築する負債。対応表 1 箇所の編集で済む。
- **出所**: ユーザー設計議論 2026-05。

### 【load-bearing】1 サブエージェント = 1 フレームワーク
- **決定**: 1 つの auditor には必ず 1 フレームワークだけ渡す。同一コンポーネントに複数当てるなら作業項目を分ける。
- **防いでいる失敗**: 1 エージェントが複数フレームワークを同時に扱うと観点が混線し、取りこぼす。iteration-1 eval で各 auditor が担当外（SQLi/secrets/SSRF）を「他フレームワーク気づき」メタに逃がし本文を専任領域に保てることを確認。
- **出所**: ユーザー懸念 + iteration-1 eval。

### 【load-bearing】フレームワーク本文は実行時フェッチ＋失敗時デグレード
- **決定**: 対応表は名称＋参照元 URL のみ。本文は auditor が実行時に取得。失敗時は学習知識で続行し「バージョン未確認」と明記（沈黙しない）。
- **防いでいる失敗**: 本文を埋め込むと本家のバージョンアップに追従できず陳腐化する。
- **出所**: ユーザー要望（バージョン追従）。iteration-1 eval で 5/5 フェッチ成功。

### 【load-bearing】取得困難なフレームワークは機械可読プロキシで代替
- **決定**: CIS Benchmarks 等（登録制・PDF で実行時フェッチ不可）は、Prowler の compliance JSON / kube-bench の cfg YAML を介して取得し「ツール解釈であり公式逐語ではない」と出典に明記。
- **防いでいる失敗**: `www.cisecurity.org` を直接叩く設計は破綻する。iteration-1 eval で Prowler `cis_3.0_aws.json` 経由が機能することを実証。
- **出所**: 事前調査 + eval。

### 要件ベース・フレームワークの重複回避（API は ASVS 主軸＋API Top10 を固有項目に絞る）
- **決定**: 同一スコープに要件ベース 2 つ（ASVS と API Security Top 10）を当てる時、API Top10 を API 固有項目（BOLA/BFLA/リソース消費等）に絞る。
- **出所**: iteration-1 で API 重複監査を観測 → iteration-2 で改善。
- **注**: iteration-2 実測ではトークン削減は小規模対象では出なかった（支配コストは対象読込＋フェッチ）。効果は役割分担の明確化と大規模 API でのコスト削減という質的・スケール上のもの。

### 【load-bearing】全文はファイル・チャットは要約（Critical/High のみ）
- **決定**: 全文を `docs/security-audit/<日付>-report.md` に出力、チャットは要約のみ。
- **防いでいる失敗**: 大規模リポジトリで全文をチャットに流すと読めず、後で見返せず共有もできない。
- **出所**: 実運用フィードバック 2026-05-31。

### 【load-bearing】レポートにローカル絶対パスを書かない
- **決定**: 対象リポジトリは `<org>/<repo>`（git remote 由来）かプロジェクト名で記す。
- **防いでいる失敗**: 実行者のローカル絶対パス（ユーザー名含む）が混入し、共有時に無意味・環境依存になる。
- **出所**: 実運用フィードバック 2026-05-31。

### 【load-bearing】finding ID はレポートで採番する（audit-tracking が引き継ぐ）
- **決定**: 統合後の各違反に `SA-<コンポーネント略号>-<連番>` を振る。レポート・チャット要約・対応表で同一 ID を共有。audit-tracking は引き継ぎ、ID の無い旧版レポートに限り自前採番でフォールバック。
- **却下した代替案**: ID 採番を audit-tracking に委譲→ レポート単体で finding を参照できず（PR・議論・チャット要約）、レポートと対応表で識別子が分かれて不整合。ID は状態でなく単なる finding のラベルなので、検出の権威記録であるレポートで付けるのが自然でゼロベース性も損なわない。
- **出所**: ユーザー指摘 2026-05-31。

### 未確認を独立区分とし「合致」で誤魔化さない
- **決定**: 静的監査で見えない範囲（実機確認・上位インフラ・デプロイ設定）は「未確認」に落とし、レポートに明示。
- **防いでいる失敗**: 確認できていないものを暗黙に「問題なし」と扱う誤った安心。iteration-1 eval で MASVS-RESILIENCE 等を正しく未確認に分類。

## 解釈・仮定（要確認）

- **ASVS 目標レベル**: 既定 L2 とした。⚠️ 組織標準が L1/L3 なら変える余地。
- **出力先**: ユーザーの「全プロジェクトで docs/ を用意する」規約に合わせ `docs/security-audit/` 配下。⚠️ docs レイアウトが違うプロジェクトでは出力先を上書き可能にしてある。
- **総合リスク評価**: 違反の最大重大度ベース（準拠率%でなく）。⚠️ 準拠率はフレームワーク内相対で、フレームワーク間比較には使わない。
