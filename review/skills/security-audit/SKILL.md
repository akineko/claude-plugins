# Security Audit

広範囲（リポジトリ全体／特定サービス）を対象に、**公開フレームワークへの準拠**という軸でセキュリティを監査するオーケストレーションスキル。対象をコンポーネントに分割し、各コンポーネントの種別に対応するフレームワークを `framework-auditor` サブエージェントに **1 つずつ** 割り当てて並列に走らせ、結果を統合する。スキル自身は直接コードを監査しない。

## このスキルの責務

| やること | やらないこと |
|---------|------------|
| 監査スコープの確定とコンポーネントの種別判定 | 直接の準拠判定・コード監査 |
| 対応表に基づくフレームワーク割り当て | フレームワーク要件本文の埋め込み（実行時フェッチに委ねる） |
| 〈コンポーネント×フレームワーク〉作業項目の生成と監査計画の提示 | 1 サブエージェントへの複数フレームワーク同時割り当て |
| `framework-auditor` の並列起動 | コード修正・パッチ生成 |
| カバレッジ・マトリクスと違反の統合・総合リスク評価 | 検出後の対応管理・再チェック（audit-tracking が担当） |
| 全文レポートのファイル出力とチャット要約 | 暗黙起動 |

## security-review との関係

[[security-review]] と棲み分ける。違いは以下のとおり:

- **対象**: security-review はコード差分・PR（変化）。本スキルはリポジトリ全体・サービス単位（広範囲の現状）。
- **分割軸**: security-review は攻撃面（injection/authz/secrets）の固定 3 エージェント。本スキルは〈コンポーネント×フレームワーク〉の動的な作業項目。
- **評価軸**: security-review は exploitability（悪用可能性）。本スキルは公開フレームワークへの準拠状況（合致/違反/非該当/未確認）。
- **フレームワークの持ち方**: security-review はエージェントの知識ベース。本スキルは名称＋参照元だけを対応表に持ち、実行時フェッチでバージョン追従する。

「この PR を見て」なら security-review、「ASVS でこのサービスを点検」「全体のセキュリティ準拠を評価」なら本スキル。

## ワークフロー

| 段階 | 目的 | 依存 |
|------|------|------|
| 1 | 監査スコープの確定 | - |
| 2 | コンポーネント偵察と種別判定 | 段階1 |
| 3 | フレームワーク割り当てと監査計画の提示・合意 | 段階2 |
| 4 | framework-auditor の並列起動 | 段階3 |
| 5 | 結果の統合（カバレッジ・マトリクス構築、重複整理） | 段階4 全完了 |
| 6 | 総合リスク評価／全文レポートのファイル出力＋チャット要約 | 段階5 |

---

### 段階1: 監査スコープの確定

ユーザー指定を解釈する。指定がなければリポジトリルート全体を対象とする。

| 指定例 | 解釈 |
|-------|------|
| 指定なし | リポジトリ全体 |
| パス（`services/payment/` 等） | そのディレクトリ配下のコンポーネント |
| 「認証まわりを横断で」等の関心事 | 後段でコンポーネントを跨いだ関心事スライスとして扱う（段階3参照） |
| フレームワーク名（「ASVS で」等） | そのフレームワークを優先割り当て。種別判定は通常どおり行う |

リポジトリルートの絶対パスを確定して保持する。

### 段階2: コンポーネント偵察と種別判定

スコープ内を偵察し、**コンポーネント**（独立して監査しうる単位）に分け、それぞれの種別を判定する。1 コンポーネントは複数種別に該当しうる。

判定の手がかり（深追いせず、構造とマーカーから推定する。広いリポジトリでは偵察自体をサブエージェントに任せてよい）:

| 種別 | マーカーの例 |
|------|------------|
| Web アプリ / バックエンドサービス | `package.json`/`go.mod`/`pom.xml`/`requirements.txt`、HTTP サーバ・ルーティング定義 |
| Web API | ルート定義に REST/GraphQL/gRPC、`openapi.yaml`、`schema.graphql` |
| モバイルアプリ | `*.swift`/`*.kt`、`Podfile`/`build.gradle`、`ios/`・`android/`、React Native/Flutter 構成 |
| LLM / 生成 AI 組込み | `openai`/`anthropic`/`langchain`/`llama_index` 等の依存、プロンプト構築・モデル呼び出し |
| 機械学習パイプライン | `*.ipynb`、学習スクリプト、モデル成果物、`torch`/`tensorflow`/`sklearn` |
| IaC / クラウド設定 | `*.tf`/`*.tfvars`、CloudFormation、`*.bicep`、Pulumi |
| コンテナ / Kubernetes | `Dockerfile`、`k8s/`・`*.yaml`（Deployment 等）、Helm チャート |
| CI/CD | `.github/workflows/`、`.gitlab-ci.yml`、`Jenkinsfile` |

monorepo では各 service ディレクトリ／各アプリが別コンポーネントになる。判定がつかないコードは「汎用」とし CWE Top 25 を当てる。

### 段階3: フレームワーク割り当てと監査計画の提示・合意

`references/frameworks.md` の対応表を読み、各コンポーネントの種別に **主軸** フレームワーク（必須・準拠判定用）と、必要なら **補助レンズ**（観点補強）を割り当てる。

**作業項目 = 〈コンポーネント × フレームワーク〉のペア**。これが 1 サブエージェントの担当になる。1 サブエージェントには必ず 1 フレームワークだけを渡す（複数を混ぜると観点が混線し漏れる）。

分割の指針:
- **既定はコンポーネント単位**。コンポーネントの該当種別ごとに主軸フレームワークを 1 つずつ作業項目化する。
- **巨大コンポーネントの細分化**: 1 コンポーネント＋1 フレームワークでも対象が広すぎて 1 エージェントが網羅しきれない場合、フレームワークの章（ASVS の認証章など）や関心事（認証/データ/外部連携）でスコープをさらに分けて複数項目にする。
- **関心事スライス（ユーザー指定時）**: 「認証を横断で」のような指定では、複数コンポーネントの認証関連パスを 1 スコープにまとめ、そこに認証系の章を持つフレームワーク（ASVS 認証章等）を当てる。
- **要件ベース・フレームワークの重複回避**: 同一スコープに要件ベースのフレームワークを 2 つ当てる場合（Web API の ASVS と API Security Top 10 など）は守備範囲が重なる。`frameworks.md` の「適用のコツ」に従い、片方を網羅主軸・もう片方を固有項目に絞って割り当てる（冗長な全件パスを避ける）。各サブエージェントへのプロンプトにこの絞り込み方針を明記する。

作業項目が出揃ったら、起動前に**監査計画を表で提示**し、合意を取る（多数のサブエージェントを起動する重い操作のため）。件数が多い場合は優先度（主軸 critical 種別を先に等）や絞り込みを相談する。

```
## 監査計画（N コンポーネント / M 作業項目）
| # | コンポーネント | 種別 | フレームワーク | 役割 |
|---|---|---|---|---|
| 1 | services/api | Web API | OWASP API Security Top 10 (2023) | 主軸 |
| 2 | services/api | Web API | OWASP ASVS v5.0.0 (認証/認可章) | 主軸 |
| 3 | apps/mobile | モバイル | OWASP MASVS v2.1.0 | 主軸 |
| 4 | infra/ | IaC(AWS) | CIS AWS Foundations (Prowler 経由) | 主軸 |
| 5 | services/chat | LLM 組込み | OWASP Top 10 for LLM Apps (2025) | 主軸 |
```

### 段階4: framework-auditor の並列起動

合意された作業項目について、**同一レスポンス内で** `review:framework-auditor` を並列起動する。作業項目が多い場合（目安 8 件超）は、優先度順にバッチ分割して順に流す（各バッチ内は並列）。

各サブエージェントへ送るプロンプトのテンプレート:

```
対象スコープ:
- コンポーネント: <名前>
- 対象パス:
  - <path1>
  - <path2>
- 役割: <1 行説明>

フレームワーク（このスコープでは下記 1 つだけを扱う）:
- 名称: <例: OWASP ASVS v5.0.0>
- discovery URL: <frameworks.md のディスカバリ URL>
- raw URL パターン: <frameworks.md の raw パターン>
- ピン留め: <タグ/ブランチ>
- 適用のコツ: <frameworks.md の該当行>
- 目標レベル: <ASVS の L2 等。なければ「既定」>

脅威モデル概要:
- 主な入力源: <... / 不明>
- 信頼境界: <... / 不明>
- 想定攻撃者: <... / 不明>

リポジトリルート: <abs path>

手順は framework-auditor の定義に従う。出力フォーマットを厳守すること。
```

フレームワーク要件の本文はテンプレートに埋め込まない。エージェントが URL から自分でフェッチする。あるサブエージェントが失敗しても、残りの結果で監査を成立させ、失敗は段階6の「未確認・カバー外」に記録する。

### 段階5: 結果の統合

各 `framework-auditor` のマークダウン出力を読み、以下を構築する。

- **カバレッジ・マトリクス**: 作業項目（コンポーネント×フレームワーク）ごとに 合致/違反/非該当/未確認 の件数を集計。準拠率を出す場合は**フレームワーク内の相対値**であり、要件数の異なるフレームワーク間で比較できない旨を注記する。
- **違反の集約**: 全違反を重大度付きで集める。
- **重複の整理**: 同一コンポーネントの同一箇所が複数フレームワークで違反として挙がった場合（例: ASVS 認証要件と API Top10 が同じ認証欠落を指摘）、1 件にまとめ、出典フレームワークを併記する。重大度は最大を採用。攻撃経路が異なるなら別件として残す。
- **finding ID の付与**: 統合後の各違反に安定 ID `SA-<コンポーネント略号>-<連番>`（例 `SA-api-01`）を振る。レポート・チャット要約・対応表で同じ ID を共有し、PR や議論での参照にも使える。audit-tracking はこの ID を引き継ぐ。

### 段階6: 総合リスク評価／全文レポートのファイル出力＋チャット要約

違反を集計して総合評価を決める。

| 評価 | 条件 |
|------|------|
| **Critical** | `critical` 違反が 1 件以上 |
| **High Risk** | `critical` は無いが `high` 違反が 1 件以上 |
| **Medium Risk** | `high` は無いが `medium` 違反が 1 件以上 |
| **Low Risk** | `low` 違反のみ |
| **Clear** | 違反 0 件 |

未確認の多さは評価を下げないが、レポートで明示し「確認しきれていない範囲」として残す（網羅できなかった事実を隠さない）。

出力は2系統に分ける。**全文はファイル、チャットは要約**（大規模監査でチャットに全文を流すと読めず、共有・見返しもできないため）。スキルはこれ以上の作業（コード修正等）は行わない。

#### 6a. 全文レポートのファイル出力

全文を `docs/security-audit/<YYYY-MM-DD>-report.md` に書き出す（日付は `date` コマンドで取得、ディレクトリが無ければ作成、ユーザーが出力先を指定した場合はそれに従う。同日に複数回走らせる場合は時刻や連番を付けて上書きを避ける）。レポートと対応表（audit-tracking）を 1:1 で対にするため、`reports/` のようなサブディレクトリは作らず、`docs/security-audit/` 直下に `<日付>-report.md` と `<日付>-tracking.md` を並置する。以下が全文テンプレート:

````markdown
# Security Audit Report
- **監査日**: 2026-05-30
- **対象リポジトリ**: <org/repo（`git remote` 由来。無ければプロジェクト名）。ローカル絶対パスは書かない>

## 総合リスク評価
**High Risk** — critical 0 / high 2（認可欠落・LLM 過剰権限）

## 監査スコープ
- **対象**: リポジトリ全体（5 コンポーネント / 5 作業項目）

  - services/api — Web API
  - apps/mobile — モバイル(iOS/Android)
  - infra/ — IaC(AWS)
  - services/chat — LLM 組込み

## カバレッジ・マトリクス
| コンポーネント | フレームワーク（バージョン） | 確認 | 合致 | 違反 | 非該当 | 未確認 | 準拠率 |
|---|---|---|---|---|---|---|---|
| services/api | API Security Top 10 (2023) | 10 | 7 | 2 | 1 | 0 | 70% |
| services/api | ASVS v5.0.0 (認証/認可) | 24 | 19 | 1 | 3 | 1 | 79% |
| apps/mobile | MASVS v2.1.0 | 24 | 18 | 1 | 4 | 1 | 75% |
| infra/ | CIS AWS Foundations (Prowler) | 32 | 28 | 1 | 3 | 0 | 88% |
````

`非該当`/`未確認` が 0 の作業項目でもマトリクスの列は残す。違反 0 件のコンポーネントは違反詳細で「違反なし」と明記する（暗黙省略しない）。各違反には段階5の `SA-...` ID を必ず付ける（audit-tracking が引き継ぐ参照キー）。

#### 6b. チャット要約

チャットには全文を貼らず、以下の要約だけを表示して全文ファイルのパスを示す。要約は **Critical/High に絞る**（件数が多いときの可読性のため）。Medium 以下・根拠・改善方向・未確認の詳細は全文ファイルに委ねる。

````markdown
# Security Audit 要約
- **総合リスク**: Critical
- **レポート全文**: docs/security-audit/2026-05-30-report.md
- **コンポーネント**: services/api(Web API), services/chat(LLM), apps/mobile(モバイル), infra(IaC/AWS)

## カバレッジ（違反件数 C/H/M/L ・未確認）
| コンポーネント | フレームワーク | 違反 | 未確認 |
|---|---|---|---|
| services/api | API Top10 + ASVS | 3/3/2/0 | 4 |
| services/chat | LLM Top10 | 1/3/1/0 | 1 |
| apps/mobile | MASVS | 1/4/1/0 | 3 |
| infra | CIS AWS | 3/3/1/1 | 2 |

## 重点検出（Critical / High のみ）
- [CRITICAL] SA-api-01 BOLA（認可欠落） — services/api/src/orders.ts:8
- [CRITICAL] SA-chat-01 過剰権限（任意シェル/SQL 実行） — services/chat/tools.py:6
- [HIGH] SA-infra-02 S3 public-read — infra/s3.tf:7
- …（Medium/Low・根拠・改善方向・未確認は全文ファイル参照）

検出後の対応（修正・許容・再チェック・状態管理）は audit-tracking スキルで行えます。
````

## サブエージェントとの契約

### スキル → エージェント（入力）

段階4 のテンプレートで送る。フレームワーク本文は埋め込まず、参照元 URL と適用のコツだけを渡す。脅威モデルは不明箇所を「不明」と書いて渡す。

### エージェント → スキル（出力）

`framework-auditor` の定義にある出力フォーマットで返る。スキルはこの構造（カバレッジ集計・違反・非該当・未確認）から機械的に集計してマトリクスを組む。

### フレームワークの専任

1 サブエージェント = 1 フレームワーク。複数を混ぜて渡さない。同一コンポーネントに複数フレームワークを当てる場合は作業項目（サブエージェント）を分ける。

---

## 制約まとめ

- スキル自身は直接監査しない（オーケストレーション役）。
- 1 サブエージェントに 1 フレームワークだけを割り当てる。
- フレームワーク本文は埋め込まず、対応表（`references/frameworks.md`）の名称＋参照元のみを持ち、実行時フェッチでバージョン追従する。
- 監査計画は起動前に提示して合意を取る（重い並列起動のため）。
- 作業項目が多い場合は優先度順にバッチ分割。各バッチ内は同一レスポンスで並列起動。
- `未確認` を `合致` で誤魔化さない。確認できなかった範囲はレポートに明示する。
- コード修正は行わない（検出のみ。修正・対応管理は audit-tracking が担当）。
- 全文レポートは `docs/security-audit/<日付>-report.md` に出力し（対応表と 1:1 で対にするため reports/ サブディレクトリは作らない）、チャットには Critical/High に絞った要約のみ返す。
- レポートにローカル絶対パスを書かない（対象リポジトリは org/repo 等の識別子で記す）。
- 各違反に安定 ID `SA-...` を付与する（レポート・要約・対応表で共有。audit-tracking が引き継ぐ）。
- 暗黙起動なし（`disable-model-invocation: true`）。
- 出力（フレームワーク出典）には実際に参照したバージョン／タグを必ず残す（再現性のため）。
