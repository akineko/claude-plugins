# security-review 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

差分（コミット前・staged・コミット・範囲・ブランチ・PR・パス絞り込み）を対象に、悪用可能性の軸でレビューする差分特化スキル。リポジトリ全体のフレームワーク準拠監査（security-audit）、差分のコード品質（quality-review）と棲み分ける。

旧版（injection/authz/secrets の固定3エージェント、exploitability 軸）が「微妙に使いづらい」とのことでゼロベース再設計。ユーザー指示により**他スキルの中身は参照せず**、要件とセキュリティドメインから設計した。ただし quality-review 再設計で有効だった「総合判定・深刻度の具体例・指摘の通しID・手動起動」という**原則**は、ユーザーが既に検証済みの知見として取り入れた（中身は流用せずセキュリティ用に再定義）。

## 中核的な設計判断

### 【load-bearing】二層分離：専門家=再現率 / メイン=適合率
- **決定**: 専門家サブエージェントは候補を広く拾うことに集中し、メインエージェントが周辺コード・文脈で誤検知を裁定して実リスクを評価する。専門家の生指摘の「転記」は禁止。
- **却下した代替案**: 専門家の結果をそのまま統合して並べるだけ（メインは整形のみ）。
- **防いでいる失敗**: 誤検知だらけで読まれないレポート／「危険に見えるが無害化済み」を実害として報告すること。ユーザーが最も求めた「客観的に対応すべきかの判断」がこの層に宿る。
- **出所**: ユーザー要望（2026-06）「メインには周辺コード・背景から客観的に対応要否を判断してほしい」。

### 【load-bearing】専門家は差分の外まで追跡する
- **決定**: 各専門家に「差分内だけでは悪用可能性は判定できない、source→sink・状態の流れを周辺コードまで追え」と明示。
- **防いでいる失敗**: 差分境界で思考を止め、sink だけ/source だけを見て悪用可能性を誤判定する（セキュリティ脆弱性は差分境界をまたぐのが常）。
- **出所**: セキュリティドメインの性質。ユーザーも「差分だけではない周辺コード」を重視。

### 4専門家構成（big3 ＋ logic-abuse）
- **決定**: injection / access-control / data-protection / logic-abuse の4本。依存・設定変更は独立エージェントにせず各専門家に分配。
- **却下した代替案**: ①3専門家（big3 のみ）= 業務ロジック悪用が手薄。②4専門家（4本目を deps-and-config）= 依存/設定は security-audit（repo 全体）と守備範囲が重なり、差分単位では各専門家への分配が自然。
- **防いでいる失敗**: 業務ロジック悪用（競合・リプレイ・符号/上限の抜け・濫用）の取りこぼし。これはクラスベースの専門家もコード品質レビューも最も見落とす固有の盲点。
- **出所**: ユーザー選択（2026-06）。専門家を分けて深掘りする方が効果的というユーザーの信念に沿う。

### 指摘の出力契約は SKILL.md の単一管理
- **決定**: 各指摘の出力形式は SKILL.md（フェーズ3）にのみ定義し、専門家エージェントは「タスク指示の契約に従え」と参照するだけにする。エージェント定義は専門性（taxonomy・方法論）に集中。
- **却下した代替案**: 各エージェント定義に出力形式を持たせる。
- **防いでいる失敗**: 4エージェント間で出力形式がドリフトし、メインの集約が壊れる（4x 同期ハザード）。
- **補足（2026-07-03）**: 契約がタスク指示から漏れた場合の全損を防ぐため、各エージェントに「最低限の項目（場所・脆弱性・悪用経路・影響・自己確信度）で自己完結して返す」フォールバックだけを持たせた。完全な形式は引き続き SKILL.md が正本。最低限項目は多少ドリフトしてもメインの集約が壊れないため、4x 同期ハザードの回避と両立する。

### 深刻度と確信度を別軸に分離
- **決定**: 深刻度＝悪用された場合の影響×到達可能性、確信度＝文脈上それが本当に実在し悪用可能か、を別々に付与。各に具体例/定義を添える。
- **防いでいる失敗**: 「どれだけ悪いか」と「本当に在るか」の混同。"今直すべきか" の判断には両軸が要る（高影響でも確信度 Low なら扱いが変わる）。
- **出所**: ユーザーの「客観判定」要望＋quality-review の「深刻度に具体例」知見。

### 【load-bearing】総合判定は差分起因の指摘だけから導く（既存の発見は follow-up に分離）
- **決定**: 出力契約に「由来（差分起因/既存）」を追加し、メインが diff・`git blame` で裁定して確定する。総合判定（マージ非推奨等）は差分起因のみから導き、既存の問題はレポートの独立セクション「既存の問題（差分外で発見・follow-up）」に分離する。既存でも Critical/High 級は「最重要」に併記して見落としを防ぐ。
- **解いた問題**: 専門家に差分の外まで追跡させる設計（load-bearing）の帰結として、この差分が導入していない既存の脆弱性も拾う。従来は由来を表す場所が無く、差分と無関係な既存の Critical でも「マージ非推奨」が発動し、この差分をブロックする誤判定になっていた。
- **防いでいる失敗**: 無関係な既存問題によるマージブロック／逆に「既存だから」と深刻な発見が埋もれること（最重要への併記で担保）。quality-review / review-response が 2026-06-08 の「merit と scope を畳まない」改訂で解いたのと同型の課題のセキュリティ版（あちらは直すべきか×どこで直すか、こちらはマージ可否×どこ由来か）。
- **出所**: プラグイン自己レビュー（2026-07-03）。

### 却下した指摘も理由付きで残す
- **決定**: 誤検知濃厚な候補を削除せず「却下」として実害が無い根拠と共に残す。
- **防いでいる失敗**: 同じ誤検知が次回以降に再提起される／ユーザーが「なぜこれは指摘されないのか」を再確認する手間。

### レポート出力はチャットに統一
- **決定**: 対象によらずチャットに全文出力する。ファイル出力・対象別の自動切替は持たない。
- **却下した代替案**: ①対象で自動切替（コミット前=チャット / 広い対象=ファイル＋要約、ファイルは `.security-review/` 配下）。一度はこれを採用したが、ユーザーが「スキルの振る舞い・定義をシンプルにしたい」とし却下。②常時ファイル。
- **防いでいる失敗**: 振る舞いの分岐・ファイルパス/gitignore 配慮・誤コミット懸念といった複雑さがスキル定義に載ること。ファイル出力が要る場面はユーザーが都度依頼する運用（この運用注記自体はノイズになるため SKILL.md には書かない）。
- **出所**: ユーザー要望（2026-06）。

### 【load-bearing】レポートの簡潔化は「表現の圧縮」であって情報削除ではない
- **決定**: 各指摘で、ユーザーが対応要否を最終判断するのに必要な情報（場所・脆弱性・悪用と影響＝リスクの大きさ・文脈での裁定＝本物か/対応要否・修正の向き）は全深刻度で残す。削るのは冗長な言い換え・長い攻撃手順の実演・指摘間で重複する説明・過剰なヘッジ。深刻度で密度を変える（Critical/High は厚め、Low/Info/却下は1段落だが判断根拠は残す）。悪用シナリオと影響は「悪用と影響」に統合。
- **却下した代替案**: ①フィールド一律フル記載（iteration-1 で1指摘7サブ項目・eval-0 が73行と冗長）。②深刻度の低い指摘をフィールドごと削る/1行に切り詰める案 → ユーザーが「簡潔化はしたいが最終判断に必要な情報は残したい」とし、情報削除ではなく表現圧縮に修正。
- **防いでいる失敗**: 重要指摘が周辺情報に埋もれて読まれない／逆に簡潔化のしすぎでユーザーが対応可否を判断できず異議も挟めなくなること。
- **出所**: ユーザー要望（2026-06）。iteration-1 の冗長性観察。

## 解釈・仮定（要確認）

- **指摘の通しID**: SEC-N とした。quality-review の `#N` と役割は同じ「1回の報告内で使い捨ての参照ハンドル」だが、体系はあえて揃えないことで確定（ユーザー確認済み 2026-07-03）。理由: security-review のレポートは深刻度順の独立文書として読まれ、`SEC-` プレフィックスは指摘がセキュリティ由来であることを文脈なしで伝える（audit 系の永続 ID `SA-` とも対になる）。技術的優劣は小さく、プラグイン横断の統一より単体レポートの参照性を優先した。
- **既定対象**: 「コミット前」を `git diff HEAD` ＋未追跡ファイルと解釈した。⚠️ staged のみを既定とする解釈もありうる（ユーザーは「コミット前のレビューが最頻」とのみ言及）。
- **security-audit の相互参照**: security-audit/SKILL.md の「分割軸」記述を旧設計（固定3エージェント injection/authz/secrets）から新設計（4攻撃面）へ更新済み（2026-06-03）。他の相互参照（評価軸=exploitability、フレームワーク=エージェント知識ベース等）は再設計後も正確なため据え置き。
