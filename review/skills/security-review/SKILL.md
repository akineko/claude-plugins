# Security Review

複数の攻撃面に特化したレビュアーを**並列**に走らせ、それぞれの指摘を統合し、悪用可能性を文脈と既存緩和策に照らして判定してマークダウンレポートにまとめるオーケストレーションスキル。スキル自身はコードを直接レビューしない。

## このスキルの責務

| やること | やらないこと |
|---------|------------|
| レビュー対象の特定と脅威モデル概要の構成 | 直接のコード脆弱性検出 |
| 3レビュアーの並列起動 | コード修正・パッチ生成 |
| 同一箇所の重複指摘の統合（攻撃面併記） | PR への自動コメント投稿 |
| 既存緩和策・到達可能性の照合による exploitability 判定 | 各レビュアーの元 severity の改変 |
| リスクレベルでの総合評価とレポート出力 | 暗黙起動 |

並列起動するのは「互いの結果に引きずられない独立判断」を確保するため。攻撃面ごとに視点が異なるので、直列で回すと後段の判定が前段に汚染される。同一レスポンス内で並列起動する。

## 暗黙起動しない理由

3つのサブエージェントを並列起動する重い処理を伴うため、`disable-model-invocation: true` を frontmatter に設定し、明示コマンド・明示依頼のみで起動する。

## code-review との関係

このスキルは [[code-review]] と骨組みを揃えてあるが、判定軸と統合方法はセキュリティ固有の事情で変えてある。違いは以下のとおり:

- **エージェント分割の軸**: 観点（正確性／設計／性能）ではなく**攻撃面**（injection／authz／secrets）
- **重複の扱い**: 同箇所が複数攻撃面で検出された場合は「攻撃面を併記」してマージ（code-review の視点併記と同じ精神）
- **矛盾の扱い**: 脆弱性は事実判定なので原則矛盾は起きない。矛盾セクションは設けない
- **トリアージの判定軸**: 「対応推奨 / 要検討 / 対応不要」ではなく **Exploitable / Conditional / Theoretical / False Positive**
- **総合評価**: PR 可否（Approve / Request Changes）ではなくリスクレベル（Critical / High Risk / Acceptable Risk / Clear）
- **メタ情報**: 「セキュリティ気づき」ではなく「他カテゴリ気づき」（運用・設計などセキュリティ外で目に入ったもの）

## ワークフロー

| 段階 | 目的 | 依存 |
|------|------|------|
| 1 | レビュー対象の特定と脅威モデル概要の構成 | - |
| 2 | 3レビュアーの並列起動 | 段階1 |
| 3 | 指摘の統合（重複マージ） | 段階2 全完了 |
| 4 | Exploitability 判定（既存緩和策・到達可能性の確認） | 段階3 |
| 5 | 総合リスク評価の判定 | 段階4 |
| 6 | 最終レポートの出力 | 段階5 |

---

### 段階1: レビュー対象の特定と脅威モデル概要の構成

#### ユーザー指定がある場合

| 指定例 | 解釈 |
|-------|------|
| `staged` / `--staged` | ステージング済み差分 |
| `unstaged` / `--unstaged` | 未ステージング差分 |
| `HEAD~3..HEAD`, `main..feature` | リビジョン範囲 → `git diff <range>` |
| `#123`, `PR 123`, `gh-pr:123` | GitHub PR → `gh pr diff 123` |
| パス（`src/foo/` など） | パス配下のファイル全体 |

#### 指定がない場合の自動検出

以下の順で確認し、**最初に差分が見つかったもの**を対象とする:

1. `git diff --staged --quiet` が非ゼロ終了 → ステージング差分
2. `git diff --quiet` が非ゼロ終了 → 未ステージング差分
3. 上記いずれも空 → 直近コミット `git diff HEAD~1 HEAD`

すべて空なら段階2には進まず、「レビュー対象が見つかりませんでした」と告げて終了。

#### コンテキストの確定

差分本文をスキルが読む必要はない。各レビュアーが自分で取得する。スキルは以下のメタ情報だけ確定して保持する:

- 対象種別 (`staged` | `unstaged` | `range` | `path` | `pr`)
- 差分取得コマンド（例: `git diff --staged`, `gh pr diff 123`）
- リポジトリルートの絶対パス
- 変更ファイル一覧（リポジトリルート相対のパス文字列）

変更ファイル一覧は以下で取得できる:

| 種別 | コマンド |
|------|---------|
| staged | `git diff --staged --name-only` |
| unstaged | `git diff --name-only` |
| range | `git diff --name-only <range>` |
| pr | `gh pr view <num> --json files --jq '.files[].path'` |
| path | `find <path> -type f` 等で列挙 |

#### 脅威モデル概要の収集

セキュリティレビューは「攻撃者がどこから来るか」が決まっていないと判定がぶれる。スキルは深追いせず、以下を**ヒントとして1〜3 行程度**で言語化する（必須ではない、不明な場合は「不明」と記録する）:

- 主な入力源（HTTP リクエスト / 認証済みユーザー操作 / 内部ジョブ / 設定ファイル 等）
- 信頼境界の位置（インターネット↔アプリ、アプリ↔DB、テナント↔テナント 等）
- 想定攻撃者（外部匿名／低権限ユーザー／内部運用者）

手がかりは以下から拾う（重い調査はしない）:

- リポジトリルートの `README` / `ARCHITECTURE.md` 等の冒頭
- 変更ファイルのパス（`src/api/`, `src/admin/`, `infra/` などから役割が推測できる）

確定できない場合は「不明」と書き、各レビュアーには `脅威モデル概要: 不明` として渡す。

---

### 段階2: 3レビュアーの並列起動

**同一レスポンス内で**3つの Task 呼び出しを並べる。逐次起動は禁止。

呼び出すサブエージェント:

| `subagent_type` | 担当攻撃面 |
|----------------|----------|
| `review:security-review-injection` | 信頼境界の汚染（SQLi, XSS, command/path/SSRF/deserialization/prompt injection 等） |
| `review:security-review-authz` | 認証・認可・セッション・権限境界（IDOR, 認可漏れ, 権限昇格, CSRF, セッション管理） |
| `review:security-review-secrets` | 機密情報・暗号・設定・依存関係（hardcoded secret, 弱い暗号, PII 漏洩, 危険な既定値, 過剰権限, 依存脆弱性） |

各レビュアーへのプロンプトは以下のテンプレートで送る（3エージェントで本体は同一、領域は各エージェント側の system に既出のため重複させない）:

```
レビュー対象:
- 種別: <staged | unstaged | range | path | pr>
- 差分取得コマンド: <command>
- リポジトリルート: <abs path>
- 変更ファイル:
  - <path1>
  - <path2>
  - ...

脅威モデル概要:
- 主な入力源: <例: 外部HTTP / 認証済みユーザー操作 / 内部ジョブ / 不明>
- 信頼境界: <例: インターネット↔API / 不明>
- 想定攻撃者: <例: 外部匿名 / 低権限ユーザー / 不明>

手順:
1. 差分取得コマンドを実行し、変更箇所を把握する。
2. 必要に応じて呼び出し元・型定義・テスト・既存緩和策を参照してよい。
3. あなたの担当攻撃面のみを評価する（他攻撃面は触れない）。
4. ただし、担当攻撃面の作業中に自然に発見した他カテゴリの問題はメタ情報として報告してよい。
5. 出力は SKILL.md 契約の構造に厳密に従う。
```

3エージェントが返ってきたら段階3へ。1つでも失敗した場合は、失敗理由を最終レポートの「補足」セクションに記載した上で残り2エージェントの結果でレビューを成立させる。

---

### 段階3: 指摘の統合

各レビュアーから返ってきたマークダウン出力を読み、指摘リストを抽出して内部表現に変換する。

#### マージのルール

- **同じファイル**かつ**近接行**（同一関数内、または ±10 行以内）かつ**同一の脆弱性事象**の指摘 → 1 つにマージ
- マージ時は各エージェントの `rationale` / `suggestion` を**併記**する
- 元の `severity` を**変更しない**。複数攻撃面で重大度が異なる場合は両方併記
- 似ているが攻撃経路が違う場合（例: 同じ sink への SQLi と PII リーク）はマージしない

#### 矛盾の扱い

セキュリティ指摘は事実判定（脆弱性が成立するか）なので、複数エージェントが「成立する」「成立しない」と分かれることは原則起きない。もし発生した場合は段階4で exploitability を確認するときに自然に解決するので、ここでは矛盾としては保持しない。

#### 内部表現（最終出力ではない）

```
{
  id: "S1",
  title: "...",
  location: "src/foo.ts:42-50",
  category_hint: "CWE-89 SQL Injection",
  views: [
    { reviewer: "injection", severity: "high",   rationale: "...", suggestion: "..." },
    { reviewer: "secrets",   severity: "medium", rationale: "...", suggestion: "..." }
  ]
}
```

`category_hint` はエージェントが付けた CWE / OWASP 識別子があれば残す（任意）。

### 段階4: Exploitability 判定（既存緩和策・到達可能性の確認）

レビュアーは差分中心に見るため、緩和策の存在や到達可能性で誤検出が混じりやすい。各統合指摘について、関連コードを Read/Grep で**実際に確認**してから判定する。

#### 必須確認項目

セキュリティ判定では以下を文脈に応じて確認する。**この確認なしに `False Positive` を付けない**（誤った安心は最悪）:

| 確認軸 | 例 |
|-------|----|
| 信頼境界 | 入力はどこから来るか（HTTP body / クエリパラメータ / ヘッダ / 内部呼び出し / 設定ファイル） |
| 既存の緩和策 | バリデーション関数、エスケープ、認可チェック、サニタイザ、暗号化が経路上に存在するか |
| 到達可能性 | 該当コードに信頼境界外から到達できるか（ルーティング / 認証ガード / 内部限定 API） |
| 影響範囲 | 成立した場合に何が漏れる／壊れるか（テナント越境 / 個人情報 / 認証情報 / 完全性） |

確認手段:

- 呼び出し元（Grep でシンボル検索）
- ミドルウェア・ガード（`auth`, `middleware`, `guard`, `decorator` 等の Grep）
- 設定ファイル（CORS, CSP, セキュリティヘッダ, IAM ポリシー）
- 既存のバリデーション・サニタイザ（`validate`, `sanitize`, `escape` 等）
- ルーティング定義（公開 / 認証必須 / 管理者専用）

#### 判定の 4 区分

| 判定 | 条件 |
|------|------|
| **Exploitable** | 攻撃経路が現実的に成立。前提条件が緩い（未認証で到達可能、外部入力が直接到達、緩和策なし）。 |
| **Conditional** | 攻撃成立に追加条件が必要だが、その条件は現実的（特定権限の取得後／特定設定下／別バグとの組み合わせ）。 |
| **Theoretical** | 攻撃面は存在するが、多層防御・到達不能性・実運用での緩和でほぼ exploit 困難。多層防御として対処は推奨。 |
| **False Positive** | 経路上の既存緩和策が機能している／信頼境界外から到達不能／入力が信頼済み等で、攻撃は成立しない。 |

#### 根拠の記録

判定には必ず根拠を残す。例:

> False Positive: `Grep` で `validateUserInput()` を src/middleware/validate.ts:20 に検出、対象ルートに適用済み。許可文字種が `[a-zA-Z0-9_-]` のため SQL メタ文字は到達しない。

> Conditional: 認証必須ルート配下のため未認証では到達不能。ただし低権限ユーザーが自身のテナントを越えてアクセスできる経路（テナント ID をパスから取得しているのみで認可チェックなし）が src/api/tenant.ts:55 に存在。

`False Positive` 判定は**必ず**「どの緩和策がどこで機能しているか」をパス付きで書く。書けないなら `Theoretical` に格下げする。

#### Severity の取り扱い

複数の攻撃面で検出された場合の severity は元のまま併記し、`Exploitable` のときは最大 severity を採用、`Conditional` のときは前提条件を考慮してエージェントの最大より 1 段下げてよい（推奨）。`Theoretical` 以下は段階5のカウントから除外する。

---

### 段階5: 総合リスク評価の判定

Exploitable と Conditional の指摘を集計して以下のいずれかに分類する。複数攻撃面で severity が異なる場合はその指摘の最大 severity（Conditional 段下げ後）を採用する。

| 評価 | 条件 |
|------|------|
| **Critical** | Exploitable に `critical` または `high` が 1 件以上 |
| **High Risk** | Critical 条件は満たさないが、Exploitable の `medium` が 2 件以上、または Conditional の `high` 以上が 1 件以上 |
| **Acceptable Risk** | Exploitable は `low` のみ／件数 1 件のみ、または Conditional の `medium` 以下のみ |
| **Clear** | Exploitable・Conditional いずれも 0 件 |

Theoretical / False Positive の件数は評価には影響しない（参考情報としてレポートに残す）。

---

### 段階6: 最終レポートの出力

以下のテンプレートでマークダウンを出力する。ユーザーに**そのまま表示**し、これ以上の作業（コード修正等）は行わない。

````markdown
# Security Review Report

## 総合評価
**High Risk** — Exploitable medium 2 件、Conditional high 1 件

## サマリー
- **対象**: ステージング済み差分 (3 files)
- **変更ファイル**:
  - src/api/user.ts
  - src/auth/session.ts
  - src/db/query.ts
- **指摘件数（判定後）**:
  - Exploitable: critical 0 / high 0 / medium 2 / low 0
  - Conditional: high 1 / medium 1 / low 0
  - Theoretical: 1
  - False Positive: 2
- **レビュアー**: injection / authz / secrets

## 脅威モデル概要
- **主な入力源**: 外部HTTP リクエスト（ユーザー認証あり / 一部公開エンドポイントあり）
- **信頼境界**: インターネット↔API、API↔DB、テナント間
- **想定攻撃者**: 外部匿名（公開エンドポイント経由）、低権限の認証済みユーザー（テナント越境）

## Exploitable

### [MEDIUM] テナント ID が認可チェックなしでパスから採用される
- **箇所**: src/api/tenant.ts:55-72
- **検出攻撃面**: authz (medium)
- **CWE/OWASP**: CWE-639 / OWASP A01:2021
- **authz レビュアー**:
  - 根拠: `req.params.tenantId` をそのまま `findTenant()` に渡しており、リクエスト元ユーザーがその tenant に属するかの検証がない。低権限ユーザーが他テナントのデータを参照できる。
  - 改善方向: ミドルウェアでリクエストユーザーの所属 tenant と照合し、不一致なら 403。
- **判定**: Exploitable
  - 確認: 認証必須ルート配下 (src/middleware/auth.ts:10) のため未認証では到達不能。ただし認証済みユーザーであれば任意の tenantId を指定可能。`Grep` で類似の認可チェックパターンを探したが、当該ルートのみ未適用。

### [MEDIUM] ...

## Conditional

### [HIGH] DEBUG ログにアクセストークンが出力される
- **箇所**: src/auth/session.ts:120
- **検出攻撃面**: secrets (high)
- **CWE/OWASP**: CWE-532
- **secrets レビュアー**:
  - 根拠: `logger.debug('session created', { token })` で生のトークン文字列をログに渡している。ログが集約基盤に流れている場合、運用者が認証情報を取得可能。
  - 改善方向: トークンはハッシュ・先頭数文字のみ・専用マスカーで処理する。
- **判定**: Conditional
  - 確認: 本番では `LOG_LEVEL=info` で DEBUG 抑止 (config/prod.yml:8)、ただし障害時に運用者が手動で DEBUG を有効化する運用 (runbook 記載) のため、その期間は漏洩する。

## Theoretical

### [LOW] 古い暗号スイートの許容
- **箇所**: infra/nginx.conf:42
- **検出攻撃面**: secrets (low)
- **CWE/OWASP**: CWE-327
- **secrets レビュアー**: TLS 1.2 で CBC 系スイートを許容。
- **判定**: Theoretical
  - 確認: フロントの CDN で TLS ターミネーションされているため、本オリジンへの直接接続はプライベートネットワーク経由のみ。多層防御として更新は推奨。

## False Positive

### [HIGH] SQL クエリへの直接連結
- **箇所**: src/db/query.ts:88
- **検出攻撃面**: injection (high)
- **injection レビュアー**: テンプレートリテラルで SQL を組み立てており SQLi 可能。
- **判定**: False Positive
  - 確認: 当該関数は内部スケジューラのみから呼ばれる (Grep で呼び出し元 src/job/cleanup.ts:30 のみ)。引数は enum 型の固定値で、ユーザー入力は到達しない。型と呼び出し元の制約により外部からの汚染経路なし。

## 他カテゴリ気づき（レビュアーのメタ情報より）
- injection レビュアー: なし
- authz レビュアー: ルートハンドラの責務肥大化（設計領域）— src/api/user.ts:200-340
- secrets レビュアー: なし

## 補足
（レビュアーが触れたが指摘に至らなかった気づき、レビューが及ばなかった範囲、レビュアー失敗の事実など）
````

`Theoretical` / `False Positive` がゼロの場合もセクション見出しは残し「該当なし」と書く（暗黙省略しない）。`他カテゴリ気づき` が 3 レビュアーともなしなら「なし」とだけ書いてセクションを残す。

## サブエージェントとの契約

### スキル → エージェント（入力）

段階2のテンプレートで送る。差分の中身は埋め込まない。エージェントが自分で `Bash` で取得する。脅威モデル概要は不明箇所があれば「不明」と書いて渡す（エージェント側で過剰に推測させない）。

### エージェント → スキル（出力フォーマット）

3 エージェントとも以下の構造で返す（攻撃面名のみ差し替え）。スキルはこの構造を前提に統合する。

````markdown
# <攻撃面名>レビュー結果

## 指摘一覧

### 指摘 1
- **severity**: critical | high | medium | low
- **箇所**: <path>:<line>(-<line>)
- **カテゴリ**: <攻撃面内のサブカテゴリ>
- **CWE/OWASP**: <CWE 番号や OWASP カテゴリ。わからなければ省略>
- **概要**: <1 行サマリー>
- **攻撃経路**: <どこから入った汚染／どのユーザーが起点／どの権限が必要か>
- **想定影響**: <データ漏洩 / 完全性破壊 / 権限昇格 / DoS 等>
- **根拠**: <なぜ問題か。経路上の sink まで含めて>
- **改善方向**: <具体的なコードではなく方向性>

### 指摘 2
- ...

## メタ情報
- **レビュー視点**: <攻撃面名>
````

統合の安定性のため、エージェントには上記フォーマットの**厳守**を求める。スキルはここから機械的に指摘を抽出する。

### 攻撃面の厳密な分離

| エージェント | 担当攻撃面 |
|------------|----------|
| security-review-injection | 信頼境界の汚染攻撃（SQLi, XSS, command/path/SSRF/deserialization/prompt injection 等） |
| security-review-authz | 認証・認可・セッション・権限境界 |
| security-review-secrets | 機密情報・暗号・設定・依存関係 |

担当外の指摘は出さない。境界に近い問題は各レビュアーが**自攻撃面の言葉でのみ**語る。他カテゴリの気づきは指摘リストではなくメタ情報セクションに記録する。

---

## 制約まとめ

- レビュアーは必ず並列起動（同一レスポンス内に 3 つの Task コール）
- スキル自身は直接レビューしない（オーケストレーション役）
- コード修正は行わない（レポートのみ）
- 各レビュアーの元の severity を統合時に変更しない（Conditional 格下げは判定時のみ）
- 矛盾セクションは設けない（脆弱性は事実判定）
- `False Positive` 判定は緩和策のパスを必ず明記。書けないなら `Theoretical` に格下げ
- 自動検出順序は staged → unstaged → `HEAD~1 HEAD`
- 暗黙起動なし（`disable-model-invocation: true`）
