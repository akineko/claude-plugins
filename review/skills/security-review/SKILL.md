# Security Review

コード差分を対象に、**悪用可能性（exploitability）**の軸でセキュリティをレビューするオーケストレーションスキル。攻撃面ごとの専門サブエージェントを並列に走らせて候補を広く拾い、**メインエージェント（あなた）が周辺コードとプロジェクト文脈で誤検知を裁定し、実際のリスクと「今直すべきか」を客観判定**する。

## 設計の核：再現率と適合率の分離

このスキルの価値は二層分離にある。崩さないこと。

- **専門家サブエージェント = 再現率（recall）担当**: 各攻撃面を深く掘り、差分の外（source→sink）まで追って候補を広く拾う。撃ち漏らしを減らす。
- **メインエージェント = 適合率（precision）担当**: 候補を周辺コード・プロジェクト背景・既存の防御策と突き合わせ、誤検知を殺し、実リスクを評価する。ノイズを減らす。

専門家の生指摘をそのまま並べるだけの「転記」は禁止。メインの裁定こそがこのスキルの成果物。

## 責務の境界

| やること | やらないこと |
|---------|------------|
| 対象差分の解決（コミット前 / staged / コミット / 範囲 / ブランチ / PR / パス絞り込み） | リポジトリ全体の網羅監査（security-audit が担当） |
| 攻撃面別専門家の並列起動 | コード品質・設計・性能のレビュー（code-review が担当） |
| 専門家結果の統合・重複排除・見解相違の裁定 | 公開フレームワークへの準拠判定（security-audit が担当） |
| 周辺コード・文脈に基づく誤検知の除外と実リスク評価 | コード修正・パッチ適用（指摘と修正案の提示まで） |
| 総合判定とレポート出力 | 暗黙起動（手動 `/security-review` のみ） |

兄弟スキル：差分のコード品質は **code-review**、リポジトリ全体のフレームワーク準拠監査は **security-audit**、検出後の対応管理は **audit-tracking**。

## フェーズ 1：対象の解決

引数を次の決定表で具体的な diff と変更ファイル一覧に解決する。`git`/`gh` を実行して確定させる。

| 指定 | 解決方法 |
|------|---------|
| **なし（既定 = コミット前）** | `git diff HEAD`（staged + unstaged のトラッキング済み変更）。さらに `git status --porcelain` で**未追跡ファイル**を拾い対象に含める |
| `staged` | `git diff --staged` |
| `unstaged` | `git diff` |
| コミット（`<sha>`） | `git show <sha>`（= `git diff <sha>^..<sha>`） |
| 範囲（`<a>..<b>` / `<a>...<b>`） | `git diff <a>..<b>`。3点指定はそのまま尊重 |
| ブランチ（`<branch>` または「現在のブランチ」） | base を検出（`main`/`master`/`develop` の存在する方）し `git diff $(git merge-base <base> HEAD)..HEAD` |
| PR（`PR番号` / PR URL） | `gh pr diff <番号>` で差分、`gh pr view <番号>` で説明・文脈を取得 |
| パス絞り込み（末尾 `-- <path>`） | 上記コマンドに `-- <path>` を付与（monorepo のサービス/ディレクトリ単位） |

- base ブランチや PR 解決に失敗したら、推測で進めず**ユーザーに確認**する。
- 解決した対象（コマンド・変更ファイル数・主な変更領域）を**1行でユーザーに提示**してからレビューに入る（スコープの取り違えを早期に潰す）。
- 差分が空なら、その旨を伝えて終了する。

## フェーズ 2：文脈の事前把握（軽量）

裁定の土台として、変更領域の**信頼モデル**を素早く掴む。差分の前後をなぞる程度でよい（深掘りはフェーズ4で対象を絞って行う）。

- このコードは何か（公開 API / 内部ツール / バッチ / フロント）、誰が呼ぶか（未認証 / 認証済み / 管理者 / 内部のみ）
- 認証・認可の仕掛けはどこにあるか（ミドルウェア / ゲートウェイ / フレームワーク機構）
- 入力の入口と信頼境界はどこか
- テスト/フィクスチャ/サンプルコードか、本番経路か

掴んだ文脈は、次フェーズで専門家に渡す**コンテキストメモ**にまとめる（数行）。

## フェーズ 3：専門家サブエージェントの並列起動

Task ツールで以下の4専門家を**1メッセージ内で並列に**起動する（`subagent_type` に各エージェント名）。

- `security-review-injection` — 信頼できない入力 → 危険シンク
- `security-review-access-control` — 認証・認可・セッション・テナント分離
- `security-review-data-protection` — 秘密情報・暗号・機微データ
- `security-review-logic-abuse` — 業務ロジック悪用・競合・リプレイ・濫用

> 差分の規模・性質に応じて専門家を増減してよい（例: 設定/インフラ中心の差分で logic-abuse が空振りしそうなら外す、依存追加が主なら data-protection に依存 CVE 確認を明示依頼する）。減らした場合は最終レポートのスコープに明記する。

各専門家への**タスクプロンプト**には次を必ず含める：

1. **対象差分**: フェーズ1で解決した diff（小さければ全文、大きければ「この git コマンドで取得せよ」＋変更ファイル一覧）
2. **コンテキストメモ**: フェーズ2で掴んだ信頼モデル
3. **指摘の出力契約**（下記）

### 指摘の出力契約（単一の出所）

各専門家には、見つけた指摘を次の形式で**1件ずつ自己完結**して返すよう指示する（メインが集約・裁定するため）：

```
- 攻撃面: <injection / access-control / data-protection / logic-abuse>
- タイトル: <一行で何が問題か>
- 場所: <file:line（複数なら主たる箇所＋関連箇所）>
- 脆弱性: <何が・なぜ悪用可能か。クラスと機構>
- 悪用シナリオ: <攻撃者視点の具体的な手順・入力例>
- データフロー/前提: <source→sink や状態の流れ。差分の外に依存する箇所を明示>
- 影響: <悪用された場合に危険に晒される資産・範囲>
- 修正案: <方向性。複数あれば併記>
- 自己確信度: <high/medium/low ＋ 確認しきれなかった仮定（メインが検証する手がかり）>
```

加えて各専門家は **「確認した範囲」**（見た箇所・対象外と判断した箇所）を末尾に簡潔に報告する。指摘ゼロでも範囲報告は返す。

## フェーズ 4：統合と裁定（このスキルの本体）

専門家の生結果を**そのまま並べない**。次の手順で精錬する。

1. **クラスタリングと重複排除**: 同一箇所・同一根本原因の指摘をまとめる。
2. **見解相違の検出**: 同じ箇所に複数の専門家が異なる深刻度・異なる解釈を付けた場合、**両論を保持**して裁定対象にする（潰さない）。
3. **文脈照合による検証**: 各候補について、自己確信度で示された未確認の仮定を**実コードで検証**する——
   - source は本当に攻撃者制御か、経路は到達可能か（公開エンドポイントか、上流ガードがあるか）
   - 既存の防御（パラメータ化・エスケープ・ミドルウェア認可・トランザクション・マスキング）が実際に効いているか
   - テスト/サンプル/デッドコードなど、実運用に影響しない箇所ではないか
   必要なら該当ファイルを読み込み、`git blame`/周辺実装で裏を取る。**確信が高く影響が大きい指摘ほど検証を厚く**する。
4. **深刻度・確信度・推奨の付与**: 下記基準で各指摘に **深刻度 / 確信度 / 推奨対応** を付ける。誤検知濃厚なものは消さず「却下」として理由付きで残す（同じ誤検知を再提起させないため）。

### 深刻度（悪用された場合の影響 × 到達可能性）

| 深刻度 | 目安と例 |
|--------|---------|
| **Critical** | 未認証で悪用でき全体侵害・大量漏洩・RCE に至る。例: 公開エンドポイントの未認証 SQLi で全ユーザー情報取得、本番資格情報のハードコード |
| **High** | 限定的な前提（任意の認証ユーザー等）で重大な影響。例: 任意ログインユーザーが他者の注文を読める IDOR、管理画面の格納型 XSS、決済の二重処理 |
| **Medium** | 特定条件下で悪用可、または緩和策が一部存在し中程度の影響。例: 被害者の誘導が要る反射型 XSS、レート制限欠如による低速ブルートフォース |
| **Low** | 悪用が困難または影響が小さい。例: スタックトレースの情報露出、弱いパスワードポリシー |
| **Info** | 現状悪用不可だが多層防御として価値あり。例: フレームワークが既に緩和しているがヘッダ未設定 |

### 確信度（文脈上、本当に悪用可能で到達可能か）

- **High**: 実コードに対し具体的な悪用経路を確認できた
- **Medium**: 妥当だが未検証の仮定に依存（source の攻撃者制御性や上流ガードを確認しきれない等）
- **Low**: パターン一致のみ。人間の確認が要る／誤検知の可能性

### 推奨対応

- **今直す** / **近く直す** / **許容＋記録**（リスク受容が妥当な根拠を添える）/ **却下（誤検知濃厚）**（なぜ実害が無いかを添える）

## フェーズ 5：総合判定とレポート

### 総合判定（先頭に置く）

- 🔴 **マージ非推奨** — Critical/High を確信度高く確認
- 🟡 **条件付き** — Medium 中心。修正推奨だがブロッカーではない
- 🟢 **悪用可能な問題なし** — 確認範囲で実害ある指摘なし（何を確認したかを必ず添える。「問題なし」だけにしない）

レポートはチャットに全文出力する。

### レポート構成

```
# Security Review — <対象>

## 総合判定
<🔴/🟡/🟢 ＋ 一文の理由>
深刻度別件数: Critical N / High N / Medium N / Low N / Info N（却下 N）

## 最重要
<上位1〜3件を一言ずつ。ここだけ読めば要点が分かる>

## 指摘
### SEC-1: <タイトル> 〔深刻度 / 確信度 / 推奨対応〕
- 攻撃面 / 場所:
- 脆弱性: <クラスと機構。1〜2文>
- 悪用と影響: <どう悪用され、何が危険に晒されるか。リスクの大きさが伝わる範囲で。1〜2文>
- 文脈での裁定: <周辺コード・背景を踏まえ、本物か／対応要否／なぜこの深刻度・確信度か。差分の外に依存する点>
- 修正案: <方向性>
- 専門家間の見解: <相違があった場合のみ。両論と裁定理由>
（SEC-2, SEC-3, ... 深刻度→確信度の順で並べる）

## 却下した候補
<誤検知濃厚として却下した指摘を1件1段落で。場所＋なぜ実害が無いか（同じ指摘の再提起を防ぐ）>

## 確認スコープ
- 対象: <diff コマンド / ファイル数>
- 走らせた専門家: <一覧。減らした場合は理由>
- 対象外: <差分外の領域。例: リポジトリ全体の設定は未確認 → security-audit を案内>
```

### 簡潔さと判断材料の両立

簡潔さは**表現の圧縮**であって情報の削除ではない。ユーザーが「対応するか否か」を最終判断できる材料は、どの深刻度でも残す。

- **全深刻度で残す（削らない）**: 場所・脆弱性（何が問題か）・悪用と影響（リスクの大きさ）・文脈での裁定（本物か／対応要否）・修正の向き。確信度が Low でも「なぜ確信が持てないか」を残し、ユーザーが自分で判断・異議を挟めるようにする。
- **削る（表現の冗長さ）**: 言い換えの重複、逐次的で長い攻撃手順の実演、複数の指摘で繰り返す同じ説明（一度書いて以後は「SEC-N 参照」）、過剰なヘッジ。各項目は1〜2文を目安にする。
- **深刻度で密度を変える**: Critical/High は悪用と影響をやや厚く（判断の重みが大きいため）。Low/Info と却下は1段落に圧縮するが、場所・判断根拠・対応の向きは必ず含める。
- 指摘には **SEC-1 から通し番号**を振る（後で「SEC-3 を直して」と参照できる）。
- 各指摘は単体で読めるようにする。差分の外に依存する判断は依存箇所を必ず書く（差分だけ見ても再検証できないため）。
- 嘘をつかない。確信度 Low は Low と書き、確認できなかった領域は「対象外」に正直に書く。
