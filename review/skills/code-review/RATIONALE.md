# code-review 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

変更（コミット前/コミット/範囲/ブランチ/PR、monorepo の特定パス）を、視点の異なる専門サブエージェントに重点レビューさせ、メインエージェントが統合・客観判断するスキル。最多のユースケースはコミット前レビュー、次いで他者の PR レビュー。

旧 code-review（correctness/design/performance の3エージェント構成）が存在したが、ユーザー指示により **旧実装を一切参照せず要件からゼロベースで再設計**した（git 履歴の旧版との比較は別途行える）。レーン名が旧版と一致するのは、非セキュリティのコードレビューで自然に立つ軸が同じだったため。

同プラグインに security-review（脆弱性）/ security-audit（フレームワーク準拠）があり、セキュリティはそちらの領域。本スキルは明示的に対象外とする。

## 中核的な設計判断

### 【load-bearing】深刻さ（専門家）と対応区分（主エージェント）の分離
- **決定**: 専門家は指摘に深刻さ（🔴🟡🟢＝客観的影響度）だけを付け、対応区分（要対応/検討/任意/見送り）と主判断はメインエージェントが付ける。
- **却下した代替案**: 専門家が対応要否まで判断する案。→ 専門家は差分中心しか見ておらず、呼び出し側・規約・運用制約・差分の目的といった文脈を持たないため、対応判断が的外れになる。
- **防いでいる失敗**: 「重大だが見送ってよい（到達不能・別レイヤ対処）」「些細だが今直すべき（新規公開APIの命名）」が表現できなくなる。二軸が潰れると現実的な裁定ができない。
- **出所**: ユーザー要望（2026-06、「メインに統合と客観判断をさせたい」）＋フォーマット議論で二軸独立を明確化。

### 【load-bearing】グルーピングの第一キーは対応区分（深刻さではない）
- **決定**: 報告は 要対応→検討→任意→見送り でまとめ、区分内を深刻さ順にする。
- **防いでいる失敗**: 深刻さでまとめると「で、何を直すのか」が散らばり triage しにくい。開発者が最初に知りたいのは対応スタンス。
- **出所**: フォーマット議論でユーザーが確認（2026-06）。

### 1行「総合」をヘッダに置く（対応区分から導く）
- **決定**: ヘッダに Approve / Request Changes / Needs Discussion の1行を置き、深刻さでなく対応区分から機械的に導く（要対応≥1→Request Changes、要対応0かつ相違/委ねた検討→Needs Discussion、他→Approve）。
- **ラベルを英語にする理由**: 日本語のヘッダ（対象/視点/結果/総評）の中で英語ラベルは視認性が上がり、最重要の結論が埋もれない。あえての言語不統一（ユーザー判断、2026-06）。
- **二軸との整合**: 対応区分から導くため「🔴 が残るが Approve」は正常。
- **却下した代替案**: 深刻さ（High の有無）から導く。→ 二軸独立の中核思想（重大だが見送り＝承認可）と矛盾する。
- **出所**: dev-toolkit 旧 code-review の総合評価（Approve/Request Changes/Needs Discussion）を二軸思想に合わせて取り込み（2026-06）。

### 【load-bearing】情報量は対応区分でなく「確信度・再考余地」で配分する
- **決定**: 全指摘に最小セット（視点/箇所/一行所見/主判断）を必ず残し、根拠/影響はユーザーが主判断を覆しうる指摘（見送り・相違・確信の低いもの）ほど厚くする。見送りは棄却根拠を厚めに。
- **却下した代替案**: 「要対応→見送りの順に情報量を減らす」案。→ ユーザーが明示的に否定。見送り・相違こそユーザーが「本当に？」と再判断する所で、情報を削ると主判断を検証できない。情報量と対応区分は連動しない。
- **防いでいる失敗**: 把握コストが区分で増減してブレる／棄却した指摘の検証材料が消える。
- **出所**: フォーマット議論（2026-06、ユーザーが「情報量と判断は必ずしも一致しない」と指摘）。

### 指摘にグローバル通しID（`#1`〜）を振る
- **決定**: 報告に出る順（区分順＝要対応→検討→任意→見送り、区分内は深刻さ順）に、重複統合後の最終指摘集合へ上から `#1, #2, …` と通しで採番する。総評で言及する論点にも #ID を併記する。
- **目的**: ユーザーが報告を受けた後「#3 を対応して」と**指摘単位で対応依頼**できるようにする。従来は指摘を文章で言い表すしかなく参照が曖昧だった（ユーザー要望、2026-06）。
- **却下した代替案**:
  - 視点プレフィックス（C1/D1/P1）。→ 視点は既存の `[視点]` タグで分かりID側に持たせると冗長。かつ相違（⚖）は1指摘が複数視点にまたがるためプレフィックスを一意に決められず、併記ルール（C2⚖D1 等）が要る。ユーザーは「連番」を明示要望したこともあり不採用。
  - 対応区分プレフィックス。→ 区分はメインの裁定で動きうるためIDに焼き込むと不安定。
- **相違（⚖）の扱い**: 複数視点にまたがっても1件＝1つのID。グローバル連番なので特別ルール不要（これがプレフィックス案を退けた決め手）。
- **スコープ（要注意）**: このIDは**1回の報告内で一意な参照ハンドル**であり、再レビューすると番号は振り直される。security-audit/audit-tracking の `SA-api-01` のような**レポート横断で永続する追跡ID**とは別物。本スキルの想定は「レビュー→その場で対応依頼」の単一サイクルで、永続追跡は範囲外（必要になれば別途 tracking 系の仕組みに委ねる）。
- **出所**: ユーザー要望（2026-06）＋方式選択で「グローバル連番」を採用。

### 見送り区分を残す
- **決定**: 専門家が挙げたが対応不要と判断した指摘を「見送り」として棄却根拠つきで残す。
- **防いでいる失敗**: 主エージェントが何を棄却したかが見えず、「客観的に対応要否を判断して教えて」というユーザー要望の核（棄却の透明性）が失われる。
- **出所**: ユーザー要望＋フォーマット議論で「残す」を確認。

### 3レーン（正確性・設計保守性・パフォーマンス）に限定
- **決定**: テスト網羅性など第4の軸は入れず3軸。
- **却下した代替案**: テスト網羅性を独立軸に追加。→ 任意として提案したがユーザーは3軸を選択（軸を増やすと並列コストと統合コストが上がる）。
- **出所**: ユーザー選択（2026-06）。

### 専門家は各レーンに集中・自然な重複だけ相違として扱う
- **決定**: わざと範囲を重複させて意見を競わせるのではなく、各レーンは絞り、自然に同じ箇所へ別視点の所見が出たときだけ相違（⚖）として両論併記・裁定する。各エージェントは他レーンで気づいた点を末尾メモに回す。
- **防いでいる失敗**: 汎用レビューや過度な重複で各視点が薄まる（ユーザーが専門特化を望んだ理由そのもの）。
- **出所**: ユーザー要望（2026-06）。

### セキュリティ対象外
- **決定**: 認証・認可・インジェクション・機密情報等は扱わず、security-review / security-audit を案内する。重大な懸念に気づいたら指摘本体に混ぜず一言添えるに留める。
- **出所**: ユーザー明示（「セキュリティは別スキルの専門分野」）。

### 出力先は状況で切替（既定インライン・PR/ブランチ/依頼でファイル保存）
- **決定**: 既定はインライン、対象が PR/ブランチ または依頼時に `docs/code-review/<日付>-<範囲>.md` へ保存。
- **防いでいる失敗**: 毎回ファイル化すると最多のコミット前レビューが重くなる。逆に PR レビューは記録・共有が欲しい。
- **出所**: ユーザー選択（2026-06）。docs/ 配下はプロジェクト規約に準拠。

### 専門家は読み取り専用
- **決定**: 3エージェントの tools に Write/Edit を含めない（Read/Grep/Glob/Bash 系のみ）。
- **防いでいる失敗**: レビュアーがコードを改変する事故。レビューは観察に徹する。

## 解釈・仮定（要確認）

- **対象未指定時の既定**: ユーザーが対象を言わなければ「未コミット変更全体（staged+unstaged＋新規ファイル）」と解釈し `git diff HEAD` ＋新規確認で取得。⚠️ 「これからコミットする分（staged のみ）」を意図する場合がありうるため、ヘッダに「何を見たか」を必ず明記して取り違えを緩和している。
- **専門家が読む範囲**: 差分中心だが、判定に必要なら周辺コードを読みに行かせる。最終的なプロジェクト背景の裁定はメインが担う。⚠️ 専門家にどこまで周辺を読ませると質とコストが釣り合うかは eval で要調整。
- **ブランチ base 検出**: `git symbolic-ref refs/remotes/origin/HEAD` → `gh repo view` → main/master の順で推定。⚠️ develop 等をトランクとする運用では誤検出の可能性。
- **深刻さ絵文字＋区分テキストの二軸表記**: 冗長でなく独立軸の可視化として有用、とユーザー確認済み（2026-06）。
