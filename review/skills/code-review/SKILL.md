# Code Review

複数の専門レビュアーを**並列**に走らせ、それぞれの指摘を統合・トリアージしてマークダウンレポートにまとめるオーケストレーションスキル。スキル自身はコードを直接レビューしない。

## このスキルの責務

| やること | やらないこと |
|---------|------------|
| レビュー対象の特定とコンテキスト構成 | 直接のコードレビュー |
| 3レビュアーの並列起動 | コード修正・パッチ生成 |
| 指摘の統合（重複マージ・矛盾保持） | PR への自動コメント投稿 |
| 関連コードを踏まえたトリアージ | 各レビュアーの元 severity の改変 |
| 総合評価とレポート出力 | 暗黙起動 |

並列起動するのは「互いの結果に引きずられない独立判断」を確保するため。直列でレビュアーを回すと、後続の判断が前の指摘に汚染されるので必ず同一レスポンス内で並列起動する。

## 暗黙起動しない理由

3つのサブエージェントを並列起動する重い処理を伴うため、`disable-model-invocation: true` を frontmatter に設定し、明示コマンド・明示依頼のみで起動する。

## ワークフロー

| 段階 | 目的 | 依存 |
|------|------|------|
| 1 | レビュー対象の特定とコンテキスト構成 | - |
| 2 | 3レビュアーの並列起動 | 段階1 |
| 3 | 指摘の統合 | 段階2 全完了 |
| 4 | トリアージ（関連コードの照合） | 段階3 |
| 5 | 総合評価の判定 | 段階4 |
| 6 | 最終レポートの出力 | 段階5 |

---

### 段階1: レビュー対象の特定とコンテキスト構成

#### ユーザー指定がある場合

| 指定例 | 解釈 |
|-------|------|
| `staged` / `--staged` | ステージング済み差分 |
| `unstaged` / `--unstaged` | 未ステージング差分 |
| `HEAD~3..HEAD`, `main..feature` | リビジョン範囲 → `git diff <range>` |
| `#123`, `PR 123`, `gh-pr:123` | GitHub PR → `gh pr diff 123` |
| パス（`src/foo/` など） | パス配下のファイル全体 |

#### 指定がない場合の自動検出

以下の順で確認し、**最初に差分が見つかったもの**を対象とする:

1. `git diff --staged --quiet` が非ゼロ終了 → ステージング差分
2. `git diff --quiet` が非ゼロ終了 → 未ステージング差分
3. 上記いずれも空 → 直近コミット `git diff HEAD~1 HEAD`

すべて空なら段階2には進まず、「レビュー対象が見つかりませんでした」と告げて終了。

#### コンテキストの確定

差分本文をスキルが読む必要はない。各レビュアーが自分で取得するので、スキルは以下のメタ情報だけ確定して保持する:

- 対象種別 (`staged` | `unstaged` | `range` | `path` | `pr`)
- 差分取得コマンド (例: `git diff --staged`, `gh pr diff 123`)
- リポジトリルートの絶対パス
- 変更ファイル一覧（リポジトリルート相対のパス文字列）

変更ファイル一覧は以下で取得できる:

| 種別 | コマンド |
|------|---------|
| staged | `git diff --staged --name-only` |
| unstaged | `git diff --name-only` |
| range | `git diff --name-only <range>` |
| pr | `gh pr view <num> --json files --jq '.files[].path'` |
| path | `find <path> -type f` 等で列挙 |

---

### 段階2: 3レビュアーの並列起動

**同一レスポンス内で**3つの Task 呼び出しを並べる。逐次起動は禁止。

呼び出すサブエージェント:

| `subagent_type` | 担当 |
|----------------|------|
| `review:code-review-correctness` | 正確性（ロジック・境界・例外・型安全性） |
| `review:code-review-design` | 設計（責務分離・命名・構造・変更容易性） |
| `review:code-review-performance` | 性能（性能・スケーラビリティ・リソース・障害解析性） |

各レビュアーへのプロンプトは以下のテンプレートで送る（3エージェントで本体は同一、領域は各エージェント側の system に既出のため重複させない）:

```
レビュー対象:
- 種別: <staged | unstaged | range | path | pr>
- 差分取得コマンド: <command>
- リポジトリルート: <abs path>
- 変更ファイル:
  - <path1>
  - <path2>
  - ...

手順:
1. 差分取得コマンドを実行し、変更箇所を把握する。
2. 必要に応じて呼び出し元・型定義・テストを参照してよい。
3. あなたの専門領域のみを評価する（他領域は触れない）。
4. ただし、専門領域の作業中に自然に発見したセキュリティ上の問題はメタ情報として報告してよい。
5. 出力は SKILL.md 契約の構造に厳密に従う。
```

3エージェントが返ってきたら段階3へ。1つでも失敗した場合は、失敗理由を最終レポートの「補足」セクションに記載した上で残り2エージェントの結果でレビューを成立させる。

---

### 段階3: 指摘の統合

各レビュアーから返ってきたマークダウン出力を読み、指摘リストを抽出して内部表現に変換する。

#### マージのルール

- **同じファイル**かつ**近接行**（同一関数内、または ±10 行以内）かつ**同一テーマ**の指摘 → 1 つにマージ
- マージ時は各視点の `rationale` / `suggestion` を**併記**する
- 元の `severity` を**変更しない**。複数視点で重大度が異なる場合は両方併記
- 似ているが論点が違う場合（例: 命名 vs 型）はマージしない

#### 矛盾の検出

- 同一箇所に対して「やるべき」vs「やるべきでない」など方向が逆の指摘 → `contradiction: true` を立てる
- 矛盾するレビュアーが片方しかいない場合（他は無言）は矛盾扱いしない

#### 内部表現（最終出力ではない）

```
{
  id: "M1",
  title: "...",
  location: "src/foo.ts:42-50",
  views: [
    { reviewer: "correctness", severity: "high",   rationale: "...", suggestion: "..." },
    { reviewer: "design",      severity: "medium", rationale: "...", suggestion: "..." }
  ],
  contradiction: false
}
```

スキルが TodoList を使っている場合、統合後の指摘 ID をトリアージタスクの単位として扱うとよい。

---

### 段階4: トリアージ（関連コードの照合）

レビュアーは差分中心に見るため、文脈不足で誤認する指摘が混じりうる。各統合指摘について、関連コードを Read/Grep で**実際に確認**してから判定する。

#### 確認対象（指摘の性質に応じて取捨）

- 呼び出し元（Grep でシンボル検索）
- 既存ユーティリティ・ヘルパー
- 型定義
- テストファイル
- 周辺の同種実装

#### 判定の 3 区分

| 判定 | 条件 |
|------|------|
| **対応推奨** | 関連コードを確認しても問題が存在し、修正すべき |
| **要検討** | 指摘は妥当だが、既存コードとの整合性／トレードオフがあり一律に判断できない |
| **対応不要** | 既に別箇所で対処済み／早すぎる最適化／コンテキスト不足による誤認／規約・スタイルの個人差 |

#### 矛盾指摘の扱い

矛盾指摘は両論をそのまま保持した上で、トリアージ段階でオーケストレーターとして「どちらに寄せるか」の**推奨判断**を付記する。**最終判断はユーザーに委ねる**。両方を「要検討」扱いにし、推奨判断とその根拠をレポートに書く。

#### 根拠の記録

判定には必ず根拠を残す。例:

> 対応不要: `Grep` で `foo()` の呼び出しを検索 → src/bar.ts:10 のみで利用、そこで nil チェック済み。

トリアージで「対応不要」となった指摘は段階5の総合評価カウントから除外する。

---

### 段階5: 総合評価の判定

トリアージ後の指摘（対応不要を除く）を集計して以下のいずれかに分類する。「複数視点で severity が異なる場合」はその指摘の最大 severity を採用する。

| 評価 | 条件 |
|------|------|
| **Approve** | high と medium がいずれも 0 件（low のみ、または指摘なし） |
| **Request Changes** | high が 1 件以上 |
| **Needs Discussion** | 上記いずれでもなく、矛盾指摘がある／要検討の medium 以上がある |

---

### 段階6: 最終レポートの出力

以下のテンプレートでマークダウンを出力する。ユーザーに**そのまま表示**し、これ以上の作業（コード修正等）は行わない。

````markdown
# Code Review Report

## 総合評価
**Request Changes** — high 1 件、対応推奨の medium 2 件

## サマリー
- **対象**: ステージング済み差分 (3 files)
- **変更ファイル**:
  - src/foo.ts
  - src/bar.ts
  - tests/foo.test.ts
- **指摘件数（トリアージ後）**:
  - 対応推奨: high 1 / medium 2 / low 0
  - 要検討: medium 1 / low 1
  - 対応不要: 2
- **レビュアー**: 正確性 / 設計 / 性能

## 対応推奨

### [HIGH] 配列インデックスの境界チェック漏れ
- **箇所**: src/foo.ts:42-50
- **検出視点**: 正確性 (high), 設計 (medium)
- **正確性レビュアー**:
  - 根拠: `arr[i+1]` が `i == arr.length - 1` のとき undefined。後続の `.map` で TypeError。
  - 改善方向: ループ条件を `i < arr.length - 1` に変更、または末尾要素を別処理に分岐。
- **設計レビュアー**:
  - 根拠: ループ本体が境界処理と通常処理を混在させている。
  - 改善方向: 末尾要素の扱いを別関数に分離。
- **トリアージ**: 対応推奨
  - 確認: `Grep` で `foo()` の呼び出しを src/usecase.ts:88 に検出、空配列を渡すコードパスあり。テスト未カバー。

### [MEDIUM] ...

## 要検討

### [MEDIUM] N+1 クエリの可能性
- **箇所**: src/repo/user.ts:30
- **検出視点**: 性能 (medium)
- **性能レビュアー**:
  - 根拠: ループ内で個別取得。100 件想定なら 100 クエリ。
  - 改善方向: バッチ取得 or JOIN。
- **トリアージ**: 要検討
  - 確認: 呼び出し元 src/api/userList.ts は最大 10 件で利用。現時点の運用負荷は軽微。
  - 推奨判断: 件数上限の保証が必要。上限が緩む可能性があれば対応推奨に格上げ。

## 対応不要

### [LOW] 命名規則の揺れ
- **箇所**: src/foo.ts:12
- **検出視点**: 設計 (low)
- **設計レビュアー**: `getUserById` と `fetchUser` が混在。
- **トリアージ**: 対応不要
  - 確認: リポジトリ全体で両方の命名が併存。プロジェクト規約は未定義。スタイル統一は別タスクで扱うべき。

## 矛盾する指摘

### キャッシュ導入の是非 (src/cache.ts:55)
- **性能レビュアー**: リクエスト毎に再計算しているのでキャッシュすべき (medium)
- **設計レビュアー**: 現時点でキャッシュは時期尚早 (low)
- **トリアージ**: 要検討
  - 推奨判断: ホットパスでないため設計側に寄せたい。ただし呼び出し頻度が上がる予定があれば再考。

## セキュリティ気づき（レビュアーのメタ情報より）
- 正確性レビュアー: なし
- 設計レビュアー: 環境変数経由の secret が DEBUG ログに出力される可能性あり (src/log.ts:18)
- 性能レビュアー: なし

## 補足
（レビュアーが触れたが指摘に至らなかった気づき、レビューが及ばなかった範囲、レビュアー失敗の事実など）
````

矛盾する指摘がなければ「矛盾する指摘: なし」と書く。セキュリティ気づきが 3 レビュアーともなしなら「なし」とだけ書いてセクションを残す（暗黙省略しない）。

## サブエージェントとの契約

### スキル → エージェント（入力）

段階2のテンプレートで送る。差分の中身は埋め込まない。エージェントが自分で `Bash` で取得する。

### エージェント → スキル（出力フォーマット）

3 エージェントとも以下の構造で返す（領域名のみ差し替え）。スキルはこの構造を前提に統合する。

````markdown
# <領域名>レビュー結果

## 指摘一覧

### 指摘 1
- **severity**: high | medium | low
- **箇所**: <path>:<line>(-<line>)
- **カテゴリ**: <領域内のサブカテゴリ>
- **概要**: <1 行サマリー>
- **根拠**: <なぜ問題か>
- **改善方向**: <具体的なコードではなく方向性>

### 指摘 2
- ...

## メタ情報
- **レビュー視点**: <領域名>
- **確認した範囲**: <差分のみ / 呼び出し元 X 件まで / テスト Y まで など>
- **セキュリティ気づき**: なし | <内容>
````

指摘が 0 件の場合:

```
## 指摘一覧
指摘なし。
```

統合の安定性のため、エージェントには上記フォーマットの**厳守**を求める。スキルはここから機械的に指摘を抽出する。

### 領域の厳密な分離

| エージェント | 担当領域 |
|------------|---------|
| code-review-correctness | ロジック破綻、境界条件、例外系、型安全性 |
| code-review-design | 責務分離、命名、構造、変更容易性 |
| code-review-performance | パフォーマンス、スケーラビリティ、リソース効率、障害解析性 |

担当外の指摘は出さない。境界に近い問題は各レビュアーが**自領域の言葉でのみ**語る。セキュリティ気づきは指摘リストではなくメタ情報セクションに記録する。

---

## 制約まとめ

- レビュアーは必ず並列起動（同一レスポンス内に 3 つの Task コール）
- スキル自身は直接レビューしない（オーケストレーション役）
- コード修正は行わない（レポートのみ）
- 各レビュアーの元の severity を統合時に変更しない
- 矛盾指摘は両論保持、トリアージで推奨判断を付記、最終判断はユーザー
- 自動検出順序は staged → unstaged → `HEAD~1 HEAD`
- 暗黙起動なし（`disable-model-invocation: true`）
