# security-review-data-protection 設計ノート

> 定義=security-review-data-protection.md / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。全体設計は [[security-review]] の RATIONALE を参照。

## 役割と位置づけ

security-review スキルの並列専門家の1つ。秘密情報・暗号・機微データの保護に特化（再現率担当）。

## 中核的な設計判断

### 【load-bearing】追加された秘密情報は履歴に残ることを指摘に含める
- **決定**: 差分で追加された秘密情報は、後で消しても git 履歴に残る点を明示させる（ローテーション要否の最終裁定はメイン）。
- **防いでいる失敗**: 「次のコミットで消すから大丈夫」という誤った安心。漏洩した資格情報は無効化が必要という運用判断に繋げる。

### 機微データの露出は呼び出し先まで読んで確定する
- **決定**: レスポンス DTO・共通ロガー等、機微データの行き先を周辺コードで追跡させる。
- **防いでいる失敗**: 差分の追加行だけでは「共通ロガーが丸ごと出力する」「DTO に内部フィールドが混ざる」露出を見逃す。

### 依存・サプライチェーンの確認を本エージェントに分配
- **決定**: 差分で追加・更新された依存の既知脆弱性（CVE）・不審パッケージ（typosquatting）・install スクリプト等の確認を担当クラスに含める。既知脆弱性の確認は監査コマンド（`npm audit` 等）が使えればそれを、無ければ学習知識で行い、確認しきれない場合は自己確信度と仮定に明記する（本エージェントは WebFetch/WebSearch を持たないため、外部 CVE データベースの参照はできない前提）。
- **出所**: security-review の RATIONALE「4専門家構成」で deps-and-config の第5エージェント案を却下し「各専門家に分配」と決定済みだったが、分配先の定義に反映されておらず宙に浮いていた（SKILL.md には「依存追加が主なら data-protection に明示依頼」とだけあった）。2026-07-03 のプラグイン自己レビューで発覚し、定義側に明文化。
- **防いでいる失敗**: 差分での依存追加という頻出の攻撃面が、どの専門家の担当クラスにも無く素通りすること。

### ダミー/公開可能値の除外責任を持たせる
- **決定**: 「秘密情報に見えるがダミー/公開可能」を誤検知として除外する責任を本エージェントに置く。
- **防いでいる失敗**: テスト用ダミーキーを大量に Critical 報告してノイズ化すること。最終裁定はメインだが、一次の選別で確信度を正しく付ける。
