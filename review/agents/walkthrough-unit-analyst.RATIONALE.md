# walkthrough-unit-analyst 設計ノート

> 定義=walkthrough-unit-analyst.md / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。

## 役割と位置づけ

review-walkthrough スキルの分析レーン。ユニット（変更の意味単位）ごとに並列起動され、レビュー資料の素材（ポイント・ユニット記述・ノイズ候補）を構造化 JSON で返す。オーケストレーション全体の設計判断は `../skills/review-walkthrough/RATIONALE.md` を参照。

## 中核的な設計判断

### 【load-bearing】重要ポイントの選出基準（6種の kind）はこの定義が正準
- **決定**: 選出基準の表・各ポイントの記載項目はエージェント定義に置き、SKILL.md には再掲しない（メインは絞り込みの優先順のみ持つ）。
- **防いでいる失敗**: 基準の二重管理による更新漏れ（1情報1箇所）。実行時に基準を必要とするのは分析を行うこのエージェントだけ。
- **出所**: リポジトリ規約（CLAUDE.md のドキュメント方針）

### 【load-bearing】ポイントは 2〜5 件、無理に作らない
- **決定**: 上限を定義に焼き込み、該当が無ければ 0〜1 件でよいと明記。
- **防いでいる失敗**: 説明過多による「読みきれない」問題の再生産と、基準に満たない変更への水増し指摘。件数を埋めようとする圧はサブエージェントに構造的にかかる（何か返さねばという圧）ため、「無理に作らない」を明文化しないと防げない。
- **出所**: 設計議論（2026-08-07）

### 【load-bearing】diffs は「転記」であって「生成」ではない
- **決定**: ポイントの抜粋（diffs）はパッチファイルからそのまま写す（要約・改変・行の創作を禁止）。
- **防いでいる失敗**: コード引用のハルシネーション。資料のコードが実物と違ったら、レビュアーの判断ごと壊れる。全ファイルの diff は render スクリプトが機械転記するため、モデル転記はこの抜粋だけに限定されている。
- **出所**: 設計議論（2026-08-07）

### 【load-bearing】diffs の選択基準は「checks の判断材料になる行」＋返却前の整合自己検査
- **決定**: 抜粋の選択基準を「ポイントを最もよく示す行」ではなく「checks の判断材料になる行（読むとレビュアーの判断が変わる行）」とし、起点より判断の核心（計算・分岐・ガード）を優先する。返却前に checks×diffs の整合を自己検査する。原則 1 件で、checks が1箇所では答えられない配管型のみ 2〜3 件（上限はスクリプトも検証）。
- **却下した代替案**: 「最もよく示す」のまま単一 diff — *変更内容の説明*としては自然だが*レビュアーの判断が変わる箇所*とは別軸で、配管型では値を渡し始めた起点の1行が選ばれやすい。複数化だけで基準を直さない案も、どの箇所を選ぶかの軸が無いままでは同じ失敗を件数分繰り返す。
- **防いでいる失敗**: checks のどれにも答えられない抜粋。実運用で、値を複数コンポーネント経由で受け渡して末端の計算に使う配管型の変更（判断材料が4ファイルに分散）に対し、起点の1行だけが提示され、確認事項3件すべてが提示 diff では検証できなかった。エージェントは情報自体を把握していた（what に位置付きで言及）が、単一 diff の契約に提示する枠が無く、選択基準も判断価値を指していなかった。
- **出所**: 2026-08-10 実運用フィードバック

### 【load-bearing】checks は「答えが開いている問い」に限り、答えを分ける材料を併記する
- **決定**: checks の選定基準を「現状を否定する側の答えを自分で言えるか」とし、言えない・明確に劣るなら問いにせず根拠を premises / why へ言い切りで移す。載せる問いには対立する選択肢と代償を記録・コードから言える範囲で併記する。振り分けの原理は「実装時に決着した選択は why が持ち、決着していない・裁定が要る選択だけが checks に載る」で、why の内容型と対をなす。答えがレビュアー側にしか無い問い（ドメイン要件・運用条件の有無）は開いた問いとして扱う。深掘り調査は義務化しない — 開いているか分からない問いは載せてよい（それは正当に検証責任の発生場所）。
- **却下した代替案**: (a) 判定法「Yes と答えられたとき何も変わらないなら載せない」— 正当な既存形式「〜の要件はないか」（No で何も変わらないのが正常）まで落としてしまう。(b) `alternatives` フィールドの新設（空配列で「代案なし」を構造的に明示する案）— 選定基準の導入後は「載っている＝開いている」が資料の不変条件になり、調査不要の合図は「載っていない」こと自体が担う。空配列は「検討した結果ない」と「検討していない」を区別できず結局文章が要る。常設フィールドは全ポイントに代案調査の固定費と作文リスクを乗せ、render 側（契約・検証・テンプレート）の変更も伴う。効果を見てなお構造化が要るなら後から追加できる（旧形式をエラーで移行案内する仕組みが既にある）。
- **防いでいる失敗**: 答えの決まった確認への不要な調査。実運用（フロントエンド描画系の変更、12 ポイント・29 確認事項）で、代替案が実在しない・明確に劣る確認が複数載り、レビュアーが「載っているからには代案があるのでは」と調査を始め、レビュー後に代替案の有無を問う往復が 5 件発生した（回答に外部ライブラリのソース確認や実測が必要だった）。checks の規定が形式（問いの形・件数）のみで、問いの形に変換できるものが全部通る構造だったことが原因（エージェントは答えが決まっていることを把握済みだった — 調査不足ではなく基準の不在）。
- **出所**: 2026-08-12 実運用フィードバック

### 【load-bearing】why は設計判断の形（目的 → 選択肢 → 選んだ理由）で書く
- **決定**: why の内容型を「何のためか → 検討された選択肢 → これを選んだ理由（何を優先し、何を代償にしたか）」と規定。裁定の事実（「ユーザーが決めた」等）は出所であって理由ではなく、裁定が何を優先した結果かまで記録から読み取れる範囲で書く。選択肢の検討が記録に無ければ「記録に無い」と明示し、分析時に思い付いた代案を「検討された」ように書かない。
- **却下した代替案**: 出所分類のみの現状維持 — 捏造禁止の圧力が強い一方で内容の型が無いと、会話の文の転記（「誰がそう言ったか」）で要件を満たせてしまい、書き手は安全側（裁定の事実で止める）に振れて選択肢の比較が落ちる。
- **防いでいる失敗**: 伝聞止まりの why。実運用で whySource が conversation / doc のポイントの大半が「誰がそう言ったか」で終わり、何と比べて何を優先した判断かが読めなかった。AI 実装は選択肢の検討過程が成果物に残らない（人間なら PR 説明や議論に残る）ため、「何と比べてこれを選んだか」はこの資料が最も提供すべき情報で、出所の正しさだけでは足りない。
- **出所**: 2026-08-12 実運用フィードバック

### 【load-bearing】whySource の判定規則と捏造禁止
- **決定**: 会話メモに根拠→conversation、設計書に記述（位置を明記）→doc、それ以外は必ず inferred で「推定の根拠」を添える。
- **防いでいる失敗**: もっともらしい理由の創作。フレッシュセッション実行（会話情報源なし）が正規の利用形態なので、出所の嘘は資料全体の信頼を壊す。
- **出所**: ユーザー要望（2026-08、意思決定の説明を載せたい）と枯渇対応の両立

### 【load-bearing】ユニット層とポイント層の書き分け（background / files[].role / premises）
- **決定**: ユニット記述に `background`（判断に必要な、diff の外にある仕組み）を置き、`files` を `{path, role, note?}` の順序付き配列にする。premises は「そのポイント固有」に限定し、ユニット全体が乗る機構は background へ集約させる。返却前の自己検査に「同じ事実を両層に書いていないか」「role だけを上から読んでユニットの動きを辿れるか」を追加。
- **却下した代替案**: (a) `flow`（散文の処理フロー）を残して files に role を足す — 同じ順序情報が2箇所に出て重複が再発する。散文は記号名を出しても所在を示せないので、順序付きの役割表が上位互換。(b) 背景の要否をエージェントに任せず必須にする — 文言変更のような機構の無いユニットで水増しが起きる（件数を埋めようとする圧はサブエージェントに構造的にかかる）。任意とし「該当が無ければ省略する」を明記した。
- **防いでいる失敗**: (1) 機構の説明の分散。実運用の生成物では、ユニット共通の外部挙動（描画ライブラリの仕様）が1ポイントの premises に 6 件並び、他ポイントにも同種の前提が重複していた。置き場が無かったことが原因で、エージェントの判断ミスではない。(2) 意図の伝わらないファイル一覧。パスの羅列と散文のフローが分離していたため、説明に出る関数名の所在が分からなかった。
- **出所**: 2026-08-10 実運用フィードバック（生成物レビュー）

### コード引用は行範囲だけを返す（本文はスクリプトが抽出）
- **決定**: `codeRefs` として `{file, lines, caption}` だけを返し、コード本文は書かない。指定前に現物を Read して行番号を確認する義務を課す。
- **防いでいる失敗**: 引用コードのハルシネーション。「モデルはコードを転記しない」という全体設計（例外はポイント抜粋の転記のみ）を、背景の引用を足しても崩さないための形。行番号の誤りはスクリプトが範囲外・行数超過として弾く。
- **出所**: 2026-08-10 実運用フィードバック

### 評価の禁止（checks は問いの形）
- **決定**: 良し悪しの判定・修正提案を書かず、レビュアーへの問いに変換する。テスト欠落の気づきも「追加を求めるか」の形。
- **防いでいる失敗**: quality-review との役割重複と、資料によるレビュアーのアンカリング。
- **出所**: スキル側 RATIONALE「資料生成と評価の分離」の分担

### 読み取り専用・担当ユニット限定
- **決定**: Bash は git の閲覧系に限定し作業ツリーを変更しない。他ユニットの分析には踏み込まず、気づきは unitNote に載せてメインに裁定させる。
- **防いでいる失敗**: 並列実行時の競合と、ユニット間で重複・矛盾する分析。

## 解釈・仮定（要確認）

- **ユニット仮説の扱い**: メインの分割はあくまで仮説であり、エージェントは name の改善・分割への異議（unitNote）までは出せるが、ファイルの再割り当て自体はしないと解釈。⚠️分割の誤りが多発するようなら、再割り当て提案の往復を設計に足す余地がある。
