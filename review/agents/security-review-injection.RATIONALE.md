# security-review-injection 設計ノート

> 定義=security-review-injection.md / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。全体設計（二層分離・出力契約・専門家構成の選定理由）は [[security-review]] の RATIONALE を参照。

## 役割と位置づけ

security-review スキルの並列専門家の1つ。「信頼できない入力 → 危険シンク」のテイントフローに特化（再現率担当）。最終的な誤検知裁定はメインエージェントが行うため、本エージェントは**広く拾いつつ、自分で確認できた範囲の悪用可能性は検証する**という非対称な責務を持つ。

## 中核的な設計判断

### 【load-bearing】1エージェントで広いインジェクション系を束ねる
- **決定**: SQLi/コマンド/XSS/SSRF/パストラバーサル/デシリアライズ/SSTI/プロンプトインジェクション等を1専門家に集約。
- **却下した代替案**: クラスごとにエージェント分割。
- **防いでいる失敗**: これらは「source→sink のテイント」という同一の思考様式で見るのが効率的で、分割すると思考が重複しコストだけ増える。クラス横断の見落とし（例: 入力が XSS にも SSRF にもなる）も1エージェントの方が拾える。

### 削除された無害化も sink と同格に見る
- **決定**: 追加シンクだけでなく「差分で削除されたバリデーション/エスケープ」を最重要候補として明示。
- **防いでいる失敗**: 「守りが外れた変化」は追加コードが無いので diff の追加行ばかり見ると見落とす。

## 解釈・仮定（要確認）

- **境界事例の扱い**: SSRF で内部 API の認可を抜く等、access-control と重なる事象は「気づいた範囲で触れてよいが深追いしない」とした。⚠️ 重複裁定はメインに委ねる前提。担当を厳格に分けすぎると境界の脆弱性が落ちるため、あえて緩い越境を許容している。
