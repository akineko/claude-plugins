# security-review-access-control 設計ノート

> 定義=security-review-access-control.md / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。全体設計は [[security-review]] の RATIONALE を参照。

## 役割と位置づけ

security-review スキルの並列専門家の1つ。認証・認可・セッション・テナント分離に特化（再現率担当）。

## 中核的な設計判断

### 【load-bearing】ハンドラ単体で保護を判断せず、実際のミドルウェア/ルーティングを読む
- **決定**: 「呼び出し元の権限と対象の所有関係を、実際のルーティング/ミドルウェア構成を読んで確定させる」と明示。
- **防いでいる失敗**: 認可は上位の層（ミドルウェア・ゲートウェイ・デコレータ）で効いていることが多く、ハンドラの追加行だけ見ると「認可漏れ」と誤検知する／逆に経路依存の抜けを「保護済み」と見逃す。差分の外を読むことが必須なクラス。

### 認可の「存在」ではなく「正しさ」を見る
- **決定**: 認可が在っても、所有者検証になっているか・フェイルオープンでないか・クライアント申告値を信用していないかを検証対象にする。
- **防いでいる失敗**: ログイン確認だけで所有者検証を欠く IDOR を「認可あり」と誤って安全判定すること。

## 解釈・仮定（要確認）

- **マスアサインメントの分担**: 権限項目（role/isAdmin 等）の上書きは access-control、業務不変条件の破壊は logic-abuse、と分担した。⚠️ 重なる指摘の最終裁定はメインに委ねる。
