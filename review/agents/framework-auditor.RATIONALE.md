# framework-auditor 設計ノート

> 定義=`framework-auditor.md` / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。実行時は非読込。

## 役割と位置づけ

[[security-audit]] スキルのオーケストレーション部品。〈1 スコープ × 1 フレームワーク〉を担当する汎用監査エージェント。全体設計（なぜ汎用 1 つなのか・なぜ実行時フェッチなのか等）は security-audit の RATIONALE.md を参照。ここはエージェント固有の load-bearing な決定に絞る。

## 中核的な設計判断

### 【load-bearing】1 フレームワークに専念、担当外はメタ情報へ逃がす
- **決定**: 渡された 1 フレームワークの要件だけで判定する。担当外で気づいた問題は「他フレームワーク気づき」メタにのみ書き、指摘本体に混ぜない。
- **防いでいる失敗**: 複数観点の混線と、別フレームワーク担当との二重計上。iteration-1 eval で API Top10 担当が SQLi/secrets を本文に出さずメタへ逃がし、ASVS 担当が本文で拾う分担が成立。
- **出所**: security-audit の「1 エージェント=1 フレームワーク」方針 + eval。

### 【load-bearing】実行時フェッチ＋失敗時デグレード（沈黙しない）
- **決定**: discovery URL で現構成を把握 → 関連章を raw 取得。失敗時は学習知識で続行し、出典に「バージョン未確認（フェッチ失敗）」と必ず明記。
- **防いでいる失敗**: フェッチ失敗を黙って学習知識で埋め、古い・不正確な基準で監査してしまうこと。バージョン追従の前提（本文を埋め込まない）を成立させる要。

### 【load-bearing】4 区分を取り違えない（合致/違反/非該当/未確認）
- **決定**: 「悪用できそうだが確証なし」は違反（重大度で表現）、「確認材料が足りない」は未確認。`合致` で誤魔化さない。
- **防いでいる失敗**: 確認できていないものを暗黙に安全扱いする誤った安心。security-audit が未確認をレポートに明示できるのはこの区分が前提。

### 章/カテゴリ単位で関連判定し、全要件を機械的に舐めない
- **決定**: まず章・カテゴリで関連/非該当を切り、関連分のみ要件 ID まで掘る。無関係カテゴリはカテゴリ単位で非該当にまとめる。
- **防いでいる失敗**: ASVS 数百要件を全件走査して破綻・冗長化すること。これは手抜きではなく、限られた確認を関連箇所に集中させ網羅の体裁で取りこぼすのを防ぐため。

### 出力フォーマット厳守
- **決定**: カバレッジ集計・違反・非該当・未確認の構造を厳守。
- **理由**: security-audit がこの構造から機械的に集計してマトリクスを組むため。崩すと統合が壊れる。

## 解釈・仮定（要確認）

- **付与ツール**: `WebFetch`/`WebSearch` を持たせている。⚠️ フレームワーク取得に必須のため（他の review 系エージェントは静的解析のみで不要）。
- **再チェックでの再起動**: audit-tracking が単一 finding の再検証で本エージェントをスコープを絞って呼ぶ余地を残しているが、既定では呼ばない（重い）。
