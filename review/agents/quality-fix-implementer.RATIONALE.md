# quality-fix-implementer 設計ノート

> 定義=quality-fix-implementer.md / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。

## 役割と位置づけ

quality-fix スキルのオーケストレーションの一部。裁定済み指摘への修正適用専任の実装者。全体設計（ループ構造・裁定の引き継ぎ・収束条件）は quality-fix スキルの RATIONALE.md を参照。

## 中核的な設計判断

### 【load-bearing】裁定権を持たない「手」に徹する（中断はしても方針変更はしない）
- **決定**: 方針と実コードが矛盾しても、現場で方針を変えたり指摘を「対応不要」と断じたりせず、証拠つきで中断報告する。再裁定はメインの専権。
- **却下した代替案**: 実装者に裁量を持たせて現場解決させる案。→ 対応区分の裁定は周辺コード・プロジェクト背景を統合したメインの仕事（quality-review の二段構えの延長）。会話文脈を持たない実装者が現場判断すると、裁定の一貫性（裁定台帳との整合）が壊れ、ループの収束管理ができなくなる。
- **防いでいる失敗**: 実装者が「これは直さなくてよさそう」と勝手にスキップ、または方針と違う直し方をして、メインの収束判定と実態がずれる。

### 【load-bearing】修正前に方針と現状の整合確認を義務化
- **決定**: 手を動かす前に、指摘箇所と方針の前提（周辺コード）を読み、方針が現状と整合するかを確認する。
- **防いでいる失敗**: ループの後半ラウンドでは前のラウンドの修正でコードが動いており、レビュー時点の行番号・前提が古くなっていることがある。古い方針の盲目的適用は新しいバグを作る（修正ループ固有のリスク）。

### 同一ファイル群を1グループとして受け取る前提
- **決定**: 割当の単位は「同一ファイルに触れる指摘のグループ」。グルーピングはスキル側（メイン）が行い、実装者は自分の範囲外に書き込まない。
- **防いでいる失敗**: 並列起動された実装者同士が同じファイルを編集して衝突する。範囲逸脱の禁止と中断条件（範囲外の変更が必要になったら中断）はこの並列安全性の担保と対。

### 変更経緯コメントの禁止
- **決定**: 「レビュー指摘対応」「〜を修正」のような経緯コメントをコードに書かせない。経緯は報告で伝える。
- **出所**: 実運用フィードバック（2026-07、実装エージェントが差分説明コメントを残す問題への規律導入）と同じ思想。レビュー指摘の修正は特に「何を直したかをコードに書きたくなる」誘惑が強い場面のため明文化。

### 検証手段がない場合の明示報告
- **決定**: テスト・ビルド等の検証手段が見つからないときは「検証手段なし（理由）」と報告させ、黙って「検証済み」扱いにさせない。
- **防いでいる失敗**: メインが「全修正が検証済み」と誤認したまま再レビューに進み、最終報告の検証欄が実態より強く見える。

## 解釈・仮定（要確認）

- **Write を持たせる**: 修正方針にテスト追加・新規ファイル作成が含まれうるため Edit だけでなく Write も付与した。⚠️ 範囲逸脱の禁止で新規ファイルの乱造は抑止する想定だが、運用で問題が出れば方針側で「新規作成は方針に明記された場合のみ」と縛る。
