# security-review-logic-abuse 設計ノート

> 定義=security-review-logic-abuse.md / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。全体設計（なぜ4本目にこの専門家を選んだか）は [[security-review]] の RATIONALE を参照。

## 役割と位置づけ

security-review スキルの並列専門家の1つ。業務ロジックの悪用（意図された機能の濫用）に特化（再現率担当）。クラスベースの専門家（injection/access-control/data-protection）が拾えない「正しく動くコードの抜け道」を担当する、本スキル独自の盲点埋め。

## 中核的な設計判断

### 【load-bearing】「正常系を裏返す」方法論で探す
- **決定**: 既知の脆弱性クラスを当てはめるのではなく、想定フローを把握した上で「負/極大/ゼロ/境界の値」「順序入れ替え」「並列・再送」「途中離脱」を当てはめさせる。
- **防いでいる失敗**: パターンマッチ思考では業務ロジック悪用は見つからない。この方法論を消すとエージェントが「クラスベース専門家の劣化版」になり存在意義を失う。

### 【load-bearing】「攻撃者が利益を得るか」で code-review と切り分ける
- **決定**: 単なる実装ミス・バグは対象外（code-review 担当）。攻撃者がそれを使って金銭・無償リソース・サービス妨害を得られる場合のみセキュリティ指摘とする。
- **防いでいる失敗**: 通常のロジックバグを大量にセキュリティ指摘として報告し、code-review と二重化・ノイズ化すること。

## 解釈・仮定（要確認）

- **マスアサインメントの分担**: 業務不変条件の破壊は本エージェント、権限項目の上書きは access-control、と分担した。⚠️ 重なる指摘の最終裁定はメインに委ねる。
