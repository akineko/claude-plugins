# refactor-apply 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

scout / unify の成果物を「順番に修正したい」というユーザー要望（2026-07）に応える実行系スキル。scout 試作（2026-06）では apply モードは「リスク最大・堅牢な安全ハーネスが要る」として却下され将来拡張とされていた — 本スキルはその安全ハーネス（再検証・挙動保存契約・項目単位コミット・確認ゲート）を独立スキルとして実装し、scout の「コード非改変」load-bearing 判断を保ったまま適用を成立させたもの。

## 中核的な設計判断

### 【load-bearing】1項目 = 1 implementer = 1コミット
- **決定**: 項目ごとに implementer を起動し、メインはコードを読まない・書かない。
- **却下した代替案**: メインが直接実装する。→ 発端の悩み「メインが調査するとコンテキストが枯渇する」の実装版。数件でセッションが尽き、「順番に修正」が成立しない。
- **防いでいる失敗**: 長いバックログの消化中のコンテキスト崩壊、失敗項目の残骸が次の項目に混入する汚染、revert 単位の喪失。

### 【load-bearing】既定は1件ごとの確認ゲート、連続は引数オプトイン
- **決定**: 既定モードは項目ごとに報告提示→ユーザー確認→コミット。「連続」指定時のみ確認を省く（それでも中止・要判断では止まる）。
- **出所**: ユーザー選択（2026-07: 推奨案を承認）。リファクタリングは1件ごとが独立した意思決定であり、静かに10件進んで全部やり直しになるのが最悪ケース。
- **補強（2026-07-07）**: 連続モードのコミットが「任意ステップではなくモードの定義そのもの」であること、およびリスクの向き（未コミットで積み残す方が revert 単位を壊す危険側）を SKILL.md に明記した。**背景**: sonnet で continuous-mode eval を実行したところ、実装は正しく進めた一方で項目ごとの `git commit` を自律実行せず、全変更を作業ツリーに残して「コミットするか」とユーザーに尋ねて終了した（連続モードの契約違反）。モデルの一般的な「commit は要確認」傾向が連続モードの明示指示を上書きした形。コミット系統の指示自体は無傷だったため、指示の強調でモデルの慎重さの矛先を正す方針を採った。**検証済み**: 補強後に同一 fixture で continuous-mode eval を再走したところ、sonnet が項目ごとに独立コミット（1項目1コミット・メッセージに計画#ID・計画ファイル非コミット）を自律実行するようになり 6/6 に改善（補強前は 4/6）。指示の強調でモデルの挙動を矯正できることを確認したため、モデル前提への割り切り（フォールバック案）は不要と判断した。

### 【load-bearing】挙動保存が既定、例外は計画の明記だけ
- **決定**: implementer の契約を「挙動変更: あり」の明記内容以外は挙動保存とする。「ついで修正」はコミットに含めない。
- **防いでいる失敗**: リファクタリングを装った無断の仕様変更。scout のレーン規律（バグ・脆弱性はリファクタ候補にしない）の実行系での対応物で、これが崩れると「refactor: 」コミットが信用できなくなる。

### 【load-bearing】計画ファイルはコミットしない（ローカル管理ファイル）
- **決定**: バックログ/移行計画はリファクタリング状況のローカル管理ファイルであり、git 履歴に載せない。項目のコミットに含めず、状態更新のためのコミットも作らない。
- **却下した代替案**: 状態更新を `docs:` コミットとして記録（iteration-1 eval のランが自発的に発明した形。ハッシュ記録と1項目1コミットを両立する合理的な案ではあった）。→ ユーザーの運用前提が「管理ファイルはコミットしない」であり、履歴も項目あたり2コミットに倍増する。
- **防いでいる失敗**: ツールの管理ファイルがユーザーのリポジトリ履歴に混入すること。明文化しないと実行ごとにコミットする/しないがブレる（eval で実証済み）。
- **出所**: ユーザー指示（2026-07: 状況管理ファイルはコミットしない想定）。

### スキャン時コミットによる鮮度チェック（implementer 再検証の前段）
- **決定**: 計画ヘッダの「スキャン時コミット」を基準に、メインが項目着手前に `git diff --stat` で対象パスの変更有無を機械的に確認する。前提消滅が明らかなら implementer を起動せず見送りを提案し、変更ありなら implementer に重点確認箇所として伝える。
- **却下した代替案**: implementer の再検証だけに任せる（従来形）。→ 対象ファイル削除のような明白な stale にもエージェント起動コストがかかり、再検証の焦点も絞れない。
- **防いでいる失敗**: 古い候補への無駄な implementer 起動、スキャン後の変更の見落とし。`--stat` はファイル名と行数だけでコードを読まないため「メインはコードに触れない」原則と両立する。旧形式（ヘッダに sha なし）の計画では省略し、従来どおり implementer の再検証に任せる（implementer の再検証自体は廃止しない）。
- **出所**: refactor-radar の鮮度チェック機構の移植（ユーザー指示による統合, 2026-07-07）。

### 状態更新は `状態:` 行のみ・計画ファイルが唯一の真実
- **決定**: 計画ファイルの項目本文には触れず状態行だけ更新する。進捗の別台帳を作らない。
- **防いでいる失敗**: 成果物（scout/unify の判断記録）の改変による監査性喪失。台帳が二重になると必ず片方が古くなる。セッションを跨ぐ再開が「ファイルを読むだけ」で成立するのはこの一元化のおかげ。
- **補足**: 状態語彙（未着手/完了/見送り/要再検討）は scout / unify / apply の3スキル共有契約。変更時は3つの SKILL.md を同時に更新する。

### テスト未整備時は特性テスト先行を推奨（強制はしない）
- **決定**: implementer は小さく機械的な変更なら特性テストを足して進み、大きければ「テスト整備が先」と中止する。メインは選択肢（テスト項目化/リスク承知/見送り）を提示する。
- **防いでいる失敗**: 「テストが無いから何もできない」の全停止と、「テストが無いまま突き進む」の無保証適用の両極。⚠️ 大小の線引きは implementer の判断に委ねた（機械的な閾値を置くと形骸化するため）。

## 解釈・仮定（要確認）

- **コミットメッセージ形式**: リポジトリの他プラグインを参照せず、Conventional Commits の `refactor:` ＋計画ファイル名#ID の素朴な形式にした。⚠️ プロジェクト側に規約があればそちらを優先する運用を想定。
- **差し戻し**: 既定モードでユーザーが修正指示を出した場合、同じ implementer に追加指示する（新規起動しない）解釈にした。⚠️ エージェントの継続が効かない環境では再起動＋文脈再説明になる。
