# リファクタリング適用

refactor-scout のバックログ / refactor-unify の移行計画を **1件ずつ消化する実行系** スキル。1項目 = 1 implementer エージェント = 1コミット。あなた（メイン＝オーケストレータ）は項目の選択・ユーザー確認・コミット・状態更新だけを持ち、**コードは読まない・書かない**。実装はすべてサブエージェントに委ねる — こうすることで、何十件消化してもあなたのコンテキストが伸びず、長いバックログを複数セッションに渡って安定して消化できる。

最初に役割分担を押さえる:

- **refactor-implementer（サブエージェント）** は項目1件を受け取り、候補の再検証 → 挙動保存の実装 → テスト等での検証 → 構造化報告まで自己完結で行う。コミットはしない。
- **あなた** は計画ファイルの解釈、消化順序の決定、報告のユーザーへの提示、コミット、計画ファイルの状態更新を行う。

このスキルがやらないこと（兄弟スキルとの棲み分け）:

- **新しい候補を探さない**。消化中に気づいた別の問題は implementer の所見として報告に載り、あなたはそれをユーザーに伝えるだけ（必要なら refactor-scout の再実行を案内）。
- **設計検討要の項目を実装しない**。「設計検討: 要」や統合系（refactor-unify で扱う）の印が付いた項目はスキップし、先に設計を固める先（unify / 設計相談）を案内する。設計が未確定のまま実装に入るのが、リファクタリングで最も高くつく失敗。
- **計画に明記のない挙動変更をしない**。「挙動変更: あり」と書かれた項目のその内容だけが例外。

## 進め方

### 1. 計画ファイルと前提を確認する

- **計画ファイルの特定**: 引数で指定されたファイル、なければ `docs/refactoring/` 配下の計画ファイルを挙げて確認する。
- **作業ツリーの確認**: `git status` で汚れていれば、そのまま進めてよいか確認する（無関係な変更が項目のコミットに混ざると revert 単位が壊れる）。ただし docs/refactoring/ 配下の計画ファイルが未追跡なのは正常（計画ファイルはコミットしない運用のため）で、汚れとは見なさない。
- **検証手段の把握**: テストコマンド・型チェック・lint の起動方法を package.json / CI 設定 / README 等から把握する。見つからなければユーザーに確認する（implementer に渡すため。項目ごとに探し直させない）。

### 2. 消化する項目と順序を決める

- 計画ファイルの `消化順序` ヘッダに従う: `記載順（依存あり）` なら上から順に（unify の移行計画は前の項目が後の項目の前提）。`任意` なら P1 から順を既定とし、#ID 指定があればそれを使う。
- 「N件」指定があればその件数で止める。指定がなければ、既定モードでは1件ずつ確認しながら進み、ユーザーが止めるまで続ける。
- 状態が `完了` `見送り` の項目は飛ばす。`要再検討` は事情が書かれているので、解消していそうならユーザーに再開を確認する。

### 3. 項目を実行する

まず鮮度チェックを行う。計画ファイルのヘッダの「スキャン時コミット」を基準に、`git diff --stat <スキャン時コミット>..HEAD -- <項目の対象パス>` で対象の変更有無を確認する（--stat のみ。コードは読まない）:

- 対象ファイルの削除など前提の消滅が明らか → implementer を起動せず、理由を添えて「見送り」を提案する。
- 差分あり → スキャン時以降に変更があった旨と変更ファイル一覧を implementer に伝え、再検証を重点化させる。
- 差分なし → そのまま進む。ヘッダに「スキャン時コミット」が無い旧形式の計画ではこのチェックを省き、implementer の再検証に任せる。

`refactor-toolkit:refactor-implementer` を起動し、次を渡す:

- 項目の本文全体（自己完結の記述。#ID・箇所・候補・方向性・完了条件・挙動変更の明記）
- 鮮度チェックの結果（スキャン時以降の対象変更の有無・変更ファイル一覧）
- 検証手段（テストコマンド等）
- リポジトリのルートと対象プロジェクトの注意点（あれば）

報告（結果 / 変更ファイル / 検証結果 / 所見）を受け取る。あなた自身で diff を読み直さない — 検証結果と報告で判断し、詳細確認はユーザーに `git diff` を案内する。

### 4. 確認・コミット・状態更新

- **既定モード**: 報告を要約してユーザーに提示し、確認を待つ。OK ならコミットし、状態を更新して次の項目へ。修正指示があれば implementer に差し戻す（同じエージェントに追加指示）。
- **連続モード**（「連続」指定時）: 確認を挟まず コミット → 状態更新 → 次へ。implementer が「中止」「要判断」を返したときだけ止まってユーザーに諮る。**各項目のコミットは連続モードの任意ステップではなく定義そのもの**であり、可否をユーザーに尋ねず必ず実行する（コミット可否を尋ねて止まるのは既定モードの挙動で、連続モードでこれをやるとモードの意味が消える）。リスクの向きに注意: コミットはローカルで容易に戻せる（`git revert`/`reset`）が、**コミットせず複数項目の変更を作業ツリーに積み残す方が、1項目1コミットの revert 単位を壊す危険な結果**になる。実装済みの変更を未コミットのまま次の項目やまとめ報告に進めない。
- **コミット**: 1項目1コミット。メッセージは `refactor: <一行要約> (<計画ファイル名>#ID)`。挙動変更ありの項目は実態に合わせて `fix:` 等を使う。コミットに含めるのは実装の変更だけで、**計画ファイルは含めない**。
- **状態更新**: 計画ファイルの該当項目の `状態:` 行だけを書き換える: `完了（<コミットハッシュ>）` / `見送り（<理由>）` / `要再検討（<理由>）`。それ以外の本文は変更しない（計画は scout / unify の成果物で、書き換えると監査性が失われる）。計画ファイルはリファクタリング状況のローカル管理ファイルであり **コミットしない**（git 履歴に載せず、状態更新のためのコミットも作らない）。

### 5. 中止・無効化の扱い

- implementer は中止時に作業ツリーを着手前に戻して返る契約。報告の理由を `要再検討（<理由>）` として状態に記録する。
- 再検証で「候補が既に解消している／前提が変わった」と返った場合は `見送り（コード変更で解消済み）` 等にする。スキャン時点と今のコードは違いうるので、これは正常な結果。
- テスト未整備で挙動保存を証明できない場合は無理に進めず、選択肢を提示する: 特性テストを先に足す（それ自体を項目化）/ リスク承知で進める / 見送り。推奨は特性テスト先行（挙動保存はこのスキルの信頼の根幹）。

### 6. 終了時の報告

セッションの消化結果を要約する: 完了 N 件（コミット一覧）・見送り N 件・要再検討 N 件、残項目数と次に着手すべき項目。計画ファイルが最新状態に更新されていることを確認する。

## 原則

- **1項目1コミットを崩さない**。複数項目をまとめると revert 単位・レビュー単位が失われる。逆に1項目の途中でコミットを割る判断は implementer の報告に従ってよい（大きな移行の安全な中間点）。
- **状態は計画ファイルが唯一の真実**。別の管理台帳・メモを作らない。セッションを跨いだ再開は計画ファイルを読むだけで成立する。
- **メインはコードに触れない**。読みたくなったら implementer への指示が不足しているサイン。指示を足して再委譲する。
- **挙動保存の例外は計画の明記だけ**。implementer が「ついでに直したい」を報告してきても、コミットに含めさせない（別項目・別レーンへ）。
