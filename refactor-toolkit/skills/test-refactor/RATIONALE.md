# test-refactor 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

テストコードのリファクタリング（検証力を弱めずに保守性・可読性・信頼性・速度を改善）を、診断→計画→承認→適用の一連で行う。review プラグインの test-quality（テスト品質監査）が別スキル思想の派生であるため、「ゼロベースで設計したらどういう構成になるか」を探る目的で、既存プラグインを参照せず新規プラグイン test-toolkit に設計した（2026-07、ユーザー要望）。

## 中核的な設計判断

### 【load-bearing】変換の3類型 × 検証プロトコル
- **決定**: 変換を保存的/削減的/強化的に分類し、類型ごとに安全の証明方法（green check / マッピング+mutation check / red check）を変える。taxonomy.md を唯一の定義とする。
- **防いでいる失敗**: 「変更後も green = 安全」という誤謬。テストのリファクタリングを守るテストは存在せず、絶対に落ちないテストも green のまま。この構造が無いと削減的変換が無証明で通る。
- **出所**: 設計議論（2026-07）

### 【load-bearing】弱め方向の変更は禁止・強め方向は許容
- **決定**: 検証力を弱める変換は証明必須。強化（L1/L2/L3）は red check 付きで積極的に行う。
- **却下した代替案**: 強化をスコープ外にする（テストギャップ監査の領分に譲る）案 → 実用上ユーザーが期待するのは両方向の健全化のため採用しない。
- **出所**: ユーザー決定（2026-07）

### 2段階検出（モジュール別インベントリ → 横断突合）
- **決定**: surveyor が検証インベントリをファイル出力し、cross-analyzer がそれを突合する。
- **却下した代替案**: (a) 全テストを1コンテキストで読む — スケールしない。(b) 分類別の専門スカウトを並列起動 — 同じテスト↔プロダクション対を分類の数だけ再読するコストが掛かるうえ、主要な検出対象（レイヤー間重複・セットアップコピペ）がファイル横断でしか見つからない構造に合わない。
- **防いでいる失敗**: レイヤー間重複・同値重複の取りこぼし（単一ファイル調査では原理的に発見不能）。

### 【load-bearing】テスト実行の生ログをメインコンテキストに載せない
- **決定**: テスト実行は baseline-runner / implementer 内に閉じ、メインは構造化サマリのみ受け取る。大きな中間生成物（インベントリ）はファイル渡し。
- **防いでいる失敗**: verbose なレポーター・大量のスタックトレースによるメインコンテキストの圧迫と、後続フェーズ（計画・報告）の判断品質低下。
- **出所**: ユーザー指摘（2026-07）。baseline-runner の返すファイル別実行時間が、速度系候補の優先度付けと Phase 6 の前後比較の基盤を兼ねる（委譲の副産物）。

### デフォルトスコープ = リポジトリ全体
- **決定**: パス引数省略時はリポジトリ全体。--diff は明示オプション。150 テストファイル超で続行確認する規模ガードを併設。
- **却下した代替案**: デフォルト --diff → 小規模プロジェクトが多く、都度「全体」を指定する手間を避けたいというユーザー要望で全体に変更（規模ガードが大規模側の事故を受け止める）。
- **出所**: ユーザー決定（2026-07）

### 期待値が間違っているテストは報告のみ
- **決定**: プロダクションのバグを固定しているテストは修正せず「報告のみ事項」へ。
- **防いでいる失敗**: リファクタリング（挙動保存）とバグ修正（挙動変更）の混線。テスト修正で挙動仕様が黙って変わる事故。

### 単一スキル + 承認チェックポイント
- **決定**: scan / apply を別スキルに分けず、Phase 4 の承認と計画ファイルの永続化（--plan-only / --apply）で運用を分節する。
- **却下した代替案**: 2スキル分割 — 診断と修正は利用単位としてセットであり、計画ファイルが分割の利点（後日再開・選択適用）を吸収する。

### mutation check は「静的に証明しきれない場合に必須」
- **決定**: 削減的変換のうちカバレッジマッピングをコードを読んで確認できるものはマッピングで足り、確認しきれないものだけ mutation check を必須にする。
- **却下した代替案**: 全削減的項目に mutation check — テスト実行コストが掛かりすぎ、適用フェーズが実用にならない。

### 【load-bearing】一時変更の復元に git checkout / restore を使わない
- **決定**: mutation / red check の復元は「事前コピー保存 → 書き戻し → git diff 確認」で行う（taxonomy.md に手順を明記）。
- **防いでいる失敗**: 対象ファイルにあったユーザーの未コミット変更ごと巻き戻す破壊事故。

### 適用の逐次実行
- **決定**: implementer はファイルグループ単位で逐次起動。
- **却下した代替案**: worktree 分離による並列適用 — 編集衝突・テスト実行の資源競合・マージの複雑さに対し、所要時間の大半が検証のテスト実行である以上、並列化の利得が小さい。

### 【load-bearing】カバレッジマッピングのスコープ内限定
- **決定**: 削減の根拠（代替カバレッジ）にできるのはスコープ内のテストのみ。スコープ外にしか根拠が無い削減候補は「要ユーザー判断」で計画に残す。cross-analyzer / implementer / taxonomy の三重で明記。
- **防いでいる失敗**: eval scoped-monorepo（iteration-1）で実証された事故 — cross-analyzer への「裏取りで両側を読め」という指示（誤検出防止に必要）が、読んだスコープ外テストをそのまま削減根拠に転用する挙動を誘発した。スコープ外は検証インベントリ・ベースラインの対象外で品質も存続も保証がない。
- **出所**: eval scoped-monorepo iteration-1（2026-07）

### 【load-bearing】変換によるスメルの新規持ち込み禁止
- **決定**: 変換の手段として taxonomy スメルを導入しない。特に「期待値をプロダクション関数の呼び出しで計算する」書き換えを明示禁止（期待値はリテラル固定）。
- **防いでいる失敗**: 同 eval で C1 縮退の際、期待値を検証対象の formatYen() 自身で計算する書き換えが発生（テストが実装の鏡になり全リグレッションを素通しする、L8 の悪化形）。
- **出所**: eval scoped-monorepo iteration-1（2026-07）

### L5/L6 の判別基準
- **決定**: 複数振る舞いの混在は L6（分割）、テスト名と無関係な実装詳細の固定は L5（緩和）。複合ケースは分割時も各フィールドに契約判定を通す。
- **防いでいる失敗**: eval full-pipeline（iteration-1）で全フィールド一括 toEqual を L6 と分類し、分割によってバージョン文字列（実装詳細）の検証を「意図的なテスト」に昇格・温存した。安全側の失敗（検証力は維持）だが過剰詳細が残る。
- **出所**: eval full-pipeline-single-package iteration-1（2026-07）

### 強化的変換にも契約判定を通す
- **決定**: 強化で固定する対象は契約判定を通し、実装詳細フィールドは固定しない（taxonomy「強化的」の項）。
- **防いでいる失敗**: iteration-2 で L5 を正しく緩和した同じ実行が、L1 強化の際に generatedBy（バージョン文字列）を別テストで固定し直した — 脆い固定が場所を変えて残存する「モグラ叩き」。緩和ルールだけでは強化経由の再持ち込みを防げない。
- **出所**: eval full-pipeline-single-package iteration-2（2026-07）

### DAMP 保持の操作手順化（明示上書き or 名前付き定数）
- **決定**: 結果を左右する値を含む抽出は「テスト側で明示上書き」か「名前付き定数の参照」で由来を追える形に限定し、どちらも取れなければ要ユーザー判断（taxonomy 判断ガイド）。
- **防いでいる失敗**: 原則論（「結果を左右する値はテストに残す」）だけでは実行間で判断がブレた — iteration-1 は同一項目を要ユーザー判断で保留、iteration-2 は値ごとファクトリへ隠して適用（テストから 1300 の由来が追えなくなった）。操作手順まで落として判断を安定させる。
- **出所**: eval full-pipeline-single-package iteration-1/2 の判断差異（2026-07）

### 作業ディレクトリの実行ごと一意化
- **決定**: 中間生成物ディレクトリは mktemp -d 等で実行専用に新規作成（SKILL.md Phase 1）。
- **防いでいる失敗**: iteration-2 で別実行の残留インベントリが横断分析の入力に混入した（cross-analyzer が自力除外して実害は無かったが、汚染は削減誤指摘の温床になる）。
- **出所**: eval scoped-monorepo iteration-2 の運用メモ（2026-07）

## 解釈・仮定（要確認）

- **規模ガード閾値**: 「意図しない全体スキャンを防ぐ」→ 150 テストファイル超で確認、と解釈。⚠️ 閾値は仮置きで、運用・eval で調整する前提。
- **「リポジトリ全体」**: git 管理下のテストファイル全部（node_modules 等の依存物は対象外）と解釈。
- **--diff の基準**: デフォルトブランチとの差分＋未コミット変更と解釈。⚠️「main との差分のみ」等の別解釈もありうる。
- **計画ファイルの置き場**: ツール生成物を docs/ 配下に置くユーザー方針に従い `docs/test-refactor/` とし、docs/ が無いプロジェクトでは作成する解釈。⚠️ 対象プロジェクト側の規約と衝突する場合の扱いは未確認。
- **cross-analyzer は1体**: インベントリは要約で小さいため、規模ガード内（〜150ファイル）なら1コンテキストで突合可能と仮定。⚠️ 破綻する規模ではパッケージ別分割＋パッケージ間パスの2段構成に改訂する。
- **surveyor 1体あたり最大10ファイル**: 仮置き。⚠️ eval で調整する前提。
