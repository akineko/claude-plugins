# refactor-unify 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

「汎用化できそうだが良い設計が思い浮かばず／時間の都合で、コピー後修正で作ったロジック」を安全に統合するための分析・設計スキル（ユーザー要望 2026-07: refactor-toolkit の3用途のうちの1つ）。

refactor-scout と分けた理由: 分析の形（範囲スキャン vs 横並び比較）と成果物（独立項目のバックログ vs 依存順序つき移行計画）が本質的に違い、1スキルにモード分岐で持たせると両方の指示が濁る。scout のバックログの「統合系・設計検討要」候補を受け取る下流でもある。

## 中核的な設計判断

### 【load-bearing】統合設計はサブエージェントに委譲せず、ユーザー対話で確定する
- **決定**: 比較分析（コンテキストを食う読み比べ）だけを divergence-mapper に委譲し、設計判断はメインがユーザーとの対話で行う。
- **却下した代替案**: 設計案の生成までエージェントに任せる。→ このスキルの発端は「良い設計が思い浮かばなかった」であり、寄せ先・表現方法・置き場所は要件知識を持つユーザーにしか決められない。コンテキスト経済より判断品質を優先する唯一の工程。
- **防いでいる失敗**: もっともらしい統合案が対話なしに確定し、要件差を潰した抽象が生まれること。

### 【load-bearing】挙動変更の明示契約（refactor-apply との接続）
- **決定**: 事故的差分の是正など挙動が変わる移行項目には「挙動変更: あり — <内容>」を必ず明記させる。
- **防いでいる失敗**: refactor-apply の implementer は挙動保存が既定契約のため、明記が無いと「挙動が変わるので中止」と正しく拒否する（＝計画が消化できない）。逆に契約が緩いと、事故的差分の是正を装った無断の仕様変更が通る。明示は両方向の事故を防ぐ。
- **出所**: apply との契約設計（2026-07）。

### 【load-bearing】「統合しない」を正当な結論として明文化
- **決定**: 意図的差分が多く統合案が複雑化するなら、部分統合・現状維持を理由付きで成果物にする。
- **防いでいる失敗**: over-DRY（引数・フラグだらけの共通関数）。複製の保守税より抽象の複雑税が高くつくケースを、スキルが「統合ありき」で押し切ること。

### 移行計画は 1サイト=1項目 の段階分割
- **却下した代替案**: 全サイト一括置換の1項目。→ 失敗時の切り戻し単位が失われ、apply の「1項目=1コミット」と噛み合わない。
- **防いでいる失敗**: 途中失敗で全サイト中途半端な状態になること。各項目完了時点でテストが通る状態を保つ。

### 計画ファイルの状態語彙は scout/apply と共有契約
- **決定**: `未着手/完了/見送り/要再検討` の4値と自己完結項目の形式を scout のバックログと揃える。
- **防いでいる失敗**: apply が入力形式ごとに分岐する複雑化。**この語彙・形式を変えるときは refactor-scout / refactor-unify / refactor-apply の3つの SKILL.md を同時に更新する**（分散定義は各スキルが実行時に他スキルを読めないための意図的な重複）。

## 解釈・仮定（要確認）

- **サイト特定の手段**: 代表実装からの複製探しは grep（関数名・特徴的ロジック）で足りると解釈した。⚠️ 名前も形も違う意味的な複製の発見は scout（locality レンズ＋シャード手がかり）の仕事とし、こちらには持たせていない。
- **バグ疑いの扱い**: 事故的差分の是正は「ユーザーが寄せ先を決めた挙動変更」として計画に載せる（レーン内）が、複製と無関係な純粋なバグはレーン外の申し送りと解釈した。⚠️ 境界が曖昧なケースは対話で確認する運用。
