# 類似実装の統合設計

「汎用化できそうだが良い設計が思い浮かばなかった」「時間の都合でコピー後に修正して作った」実装群を、安全に1つの設計へ集約するための **比較分析と移行計画づくり** のスキル。コードは修正しない。成果物は、確定した統合設計と、refactor-apply が1件ずつ消化できる段階的な移行計画。

最初に役割分担を押さえる:

- **divergence-mapper（サブエージェント）** が全サイトを読み比べ、共通骨格・サイト間差分（意図的/事故的/不明の分類付き）・各サイトの文脈制約を構造化して返す。設計判断はしない。
- **あなた（メイン＝オーケストレータ）** はサイトの特定、差分マトリクスを材料にした **ユーザーとの設計対話**、確定した設計の移行計画化を担う。コードの読み比べ（コンテキストを大量に食う作業）はサブエージェントに任せ、あなたは判断と対話に徹する。

統合設計を機械的に決めないことがこのスキルの肝。どの挙動に寄せるか・差分をどう表現するかは正解が一意に決まらない設計判断であり、ユーザーが決め手を持っている（だからこそ元々「良い設計が思い浮かばず」コピーされた）。

このスキルがやらないこと（兄弟スキルとの棲み分け）:

- **広域スキャンで候補を探さない**。範囲を舐めて重複を発見するのは refactor-scout の仕事。こちらは「この実装群を統合したい」が起点（scout のバックログの統合系候補から来ることも多い）。
- **コードを書き換えない**。移行計画の実装は refactor-apply。ここで手を動かすと、設計の合意より先にコードが進んでしまう。
- **挙動差の正誤を勝手に裁定しない**。事故的差分（片方だけバグ修正が入った等）はどちらが正か決めないと統合できないが、それは対話の論点として提示し、ユーザーに決めさせて計画に記録する。

## 進め方

### 1. サイトを特定する

統合対象の実装群（サイト）を確定する。引数や会話でパス群が示されていればそれを使う。代表実装1つだけ示された場合は、関数名・特徴的なロジック・エラーメッセージ等を grep して複製候補を集める。scout のバックログ項目が起点なら、そこに列挙された箇所を使う。

集めたら **最終的なサイト一覧を必ずユーザーに確認する**。取り込み漏れがあると、統合設計がそのサイトの要件を知らずに固まり、後で移行できずに破綻する。逆に「実は別物」を混ぜると設計が無駄に複雑になる。

### 2. 差分マトリクスを取得する

`refactor-toolkit:refactor-divergence-mapper` を起動し、サイト一覧（パス＋シンボル）と把握している文脈（各サイトの用途・関連ドキュメント）を渡す。比較は全サイトを同時に見る必要があるため、サイト数が多くても1エージェントで行う（分割すると「AとBだけにある差分」が見えなくなる）。

返ってくるもの: 共通骨格 / 番号付きの差分一覧（意図的・事故的・不明の分類と根拠）/ 各サイトの文脈制約（呼び出し元・型・テスト有無）/ バグ疑いの申し送り。

### 3. 設計対話で統合設計を固める（中心工程）

差分マトリクスを要約して提示し、論点を1つずつ確定する。選択肢を出すときは推奨とその理由を添え、好みの問題なら「好みで選んでよい」と明示する。

1. **統合可否の判断**: まず「統合すべきか」を問う。意図的差分が多く、統合すると引数やフラグだらけの複雑な抽象になるなら、**「統合しない（一部だけ統合する／共通部分だけ切り出す）」も正当な結論**。無理な DRY 化は複製より高くつく。この判断も理由付きで成果物に残す。
2. **事故的差分の寄せ先**: 差分ごとに、どのサイトの挙動に揃えるかをユーザーに決めさせる。**挙動が変わるサイトが生じる場合は、その旨を明示的に確認して計画に記録する**（refactor-apply の挙動保存契約の例外になるため、曖昧にできない）。
3. **意図的差分の表現方法**: 引数・strategy・設定・フックなど、要件差をどう表現するか。差分の数と性質に応じて 2〜3 案を比較提示する。
4. **共通実装の置き場所と命名**: プロジェクトの支配的な構成（shared/・utils/・ドメインパッケージ等）に合わせる。
5. **移行順序**: テストが厚い・呼び出しが単純なサイトから始め、リスクの高いサイトを後にする。順序の根拠も計画に書く。

### 4. 移行計画を出力する

確定した設計と移行手順を Markdown ファイルに保存し、会話内には要約を出す。保存先はプロジェクトの `docs/` 配下（例 `docs/refactoring/unify-<対象スラッグ>.md`）。無ければ保存先を提案して確認する。

各項目は refactor-apply が単独で読んで着手できる自己完結の記述にする（apply はこの会話を参照できない）。典型構成: ①共通実装の作成＋テスト → ②サイトごとの移行（低リスク順に1サイト=1項目）→ ③旧実装の削除。

## 出力フォーマット

### 移行計画ファイル

```
# 統合移行計画: <対象の説明>

対象サイト: <N箇所。path:line の一覧>
スキャン時コミット: <分析時点の HEAD sha。refactor-apply が鮮度チェックの基準に使う>
消化順序: 記載順（依存あり）
統合設計: <確定した設計の要約: 共通実装の置き場所・シグネチャ・意図的差分の表現方法>
決定記録: <対話で確定した判断と理由。事故的差分の寄せ先、統合しなかった部分とその理由を含む>

---

## #1 共通実装の作成
- 内容: <何を作るか。骨格・シグネチャ・意図的差分の表現>
- 対象: <新規ファイルパス>
- 完了条件: <新テストが通る等>
- 挙動変更: なし
- 状態: 未着手

## #2 <サイト名> の移行
- 内容: <このサイトを共通実装に差し替える手順の要点>
- 対象: <path>
- 完了条件: <既存テスト green 等>
- 挙動変更: なし / あり — <何がどう変わるか。事故的差分の是正なら旧挙動と新挙動を明記>
- 状態: 未着手

（以降サイトごとに1項目、最後に旧実装の削除）
```

状態は `未着手 / 完了（コミット）/ 見送り（理由）/ 要再検討（理由）` の4値。状態の語彙（refactor-apply が消化時に更新する）と「スキャン時コミット」ヘッダは refactor-apply との共有契約なので、変えたり省いたりしない。

### 会話内の要約

保存したファイルのパス、統合設計の骨子、挙動変更を伴う項目の一覧（あれば強調）を示し、消化は refactor-apply を案内する。

## 原則

- **サイト一覧の合意なしに設計を始めない**。漏れたサイトは移行できず、混ざった別物は設計を歪める。
- **事故的差分の寄せ先はユーザーが決める**。挙動の正誤はコードだけからは判定できない（片方が「バグ修正済み」なのか「仕様が違う」のかは要件の知識）。決定と理由は計画の決定記録に残す。
- **挙動変更は項目に明記する**。移行は原則挙動保存であり、例外（事故的差分の是正）を計画に明記しないと、refactor-apply の実装者が「挙動が変わるので中止」と正しく拒否してしまう。
- **統合しない勇気を持つ**。統合案が複雑になりすぎるなら、その事実こそが「これらは別物」というシグナル。部分統合・現状維持も理由付きで立派な成果物。
- **移行は段階に切る**。一括置換は失敗時の切り戻し単位が失われる。1サイト=1項目とし、各項目の完了時点でテストが通る状態を保つ。
