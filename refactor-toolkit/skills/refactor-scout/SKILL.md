# リファクタリング候補スカウト

指定した範囲（モジュール / 機能 / PR・作業ブランチ / リポジトリ全体）を能動的にスキャンし、既存コードに潜むリファクタリング候補を洗い出して、**ROI（保守性への効果 ÷ コスト・リスク）で順位付けした改善バックログ**を出力するスキル。コードは修正しない。発見と優先順位付けが役割で、バックログの実装は refactor-apply、類似実装群の統合設計は refactor-unify（いずれも本プラグインの兄弟スキル）に委ねる。

最初に役割分担を押さえる:

- **検出スペシャリスト（サブエージェント）** は3つのレンズ（アーキテクチャ / 局所スメル / ドリフト）に分かれ、各候補に **影響度（保守性への客観的なダメージ 🔴🟡🟢）だけ** を付ける。優先度や着手順は判断しない。
- **あなた（メイン＝オーケストレータ）** は全候補を統合し、変更頻度・影響範囲・テスト有無などの **ROI シグナルを集めて優先度（P1/P2/P3）を裁定** し、順序付きのバックログにする。スキャン範囲の解決、設計意図との突き合わせ、ROI 判定、バックログ化があなたの中心的な仕事。

影響度（どれだけ保守を蝕むか）と優先度（実際どの順で着手すべきか）を分けるのが肝。これにより「影響大だが今触るとリスクが高いので後回し」「影響中だが変更頻発・低コストなので最優先」といった現実的な判断を表現できる。

このスキルがやらないこと（兄弟スキルとの棲み分け）:

- **差分のマージ判定ではない**。コミット/PR が導入した問題をゲートするのは quality-review の領域。こちらは未変更コードを含む既存設計全体の棚卸し。PR・ブランチを対象に受け取る場合も、差分はスコープ解決の種にすぎず、評価するのは変更が触れた領域の既存構造（差分行のゲートはしない）。
- **コードを書き換えない**。候補の適用は refactor-apply がバックログを1件ずつ消化する別工程。影響の大きい構造的候補には「設計検討が必要」と印を付け、類似実装の統合系なら refactor-unify を差し向ける。
- **挙動バグ・脆弱性は扱わない**。リファクタリング候補は構造・保守性（スメル・設計・ドリフト）に限る。ロジックの誤り（→ correctness レビュー）やセキュリティ脆弱性（→ security-review）は、気づいても候補として順位付けせず、レポート末尾に一言申し送るに留める。これらを混ぜるとバックログが「直すべき欠陥」と「設計改善」を取り違え、レーンがぼやける。

## 進め方

### 1. スキャン範囲と文脈を固める

対象は4つの形で受け取る。対象が示されていなければ、どれを見るかを確認する（黙って全体を舐めない／黙って一部だけ見ない）。何をスキャンしたかは必ず報告に明記する。

- **モジュール/ディレクトリのパス**（既定・高シグナル低コスト）。
- **機能**（「認証まわり」「今実装し終えた CSV エクスポート」等）。パスが直接示されないので、git 履歴（直近のコミットが触ったファイル群）・エントリポイントからの参照・キーワード grep で関連ファイル集合に解決し、**スキャン前にその集合をユーザーに確認する**（解決を誤ると以降の全工程が別の場所を見ることになる）。機能の実装完了直後に設計を見直すのが典型ユース。
- **PR / 作業ブランチ**（PR 番号・URL、または「このブランチの変更」）。`gh pr diff <番号> --name-only`（ブランチは `git diff --name-only $(git merge-base <ベースブランチ> HEAD) HEAD` と `git status --short`）で変更ファイルを取得する。変更ファイルは種にすぎないので、各ファイルの呼び出し元・対になるテスト・同一モジュールの隣接ファイルを **1ホップまで** 加えて関連ファイル集合に解決する（それ以上は広げない）。機能と同様、**スキャン前にその集合をユーザーに確認する**。実装を終えた PR/ブランチの設計見直しが典型ユースで、差分のマージゲートではない。
- **リポジトリ全体**: 明示されたときだけ行う。

範囲を決めたら、検出の前に文脈を集める（これがスペシャリストの精度を左右する）:

- **設計意図の所在**: `docs/`・ADR（`docs/adr/` 等）・`ARCHITECTURE.md`・`README` に書かれた、意図された構造・レイヤ・命名・依存方針。後で「文書化された決定に沿う候補」を落とすために使う。
- **支配的なパターン**: 対象周辺で実際に多数派になっている書き方・構成（規約が文書化されていなくても、コードから読み取れる「この場の流儀」）。
- **スタックとツール**: 言語、依存解析の手段、テストの所在とランナー。プロジェクトに linter / 依存解析ツールがあれば後段で活用する。

### 2. 検出スペシャリストへディスパッチ（スコープ規模で起動方法を変える）

スコープの規模で起動方法を選ぶ。どの規模でも **3レンズすべてを必ず通す**。

- **数ファイル程度の小さいスコープ**: サブエージェントを起動せず、3レンズのブリーフ（各エージェント定義）を自分で順に適用してよい。1エージェントで十分見通せる範囲では、並列起動のオーバーヘッド（数分・追加トークン）が検出の質に見合わないため。
- **大きいモジュール（1エージェントで読み切れる規模、目安〜100ファイル）**: 3つのサブエージェントを **同一メッセージ内で並列起動** する（Agent ツール、`subagent_type` に各エージェント名）。広い範囲を1エージェントで読むと各観点が薄まり、とくにファイル横断のアーキ問題を局所スメルに埋もれさせて見落とすため、専任させる。
- **1エージェントで読み切れない規模（モノレポの1サービス全体・リポジトリ全体など、目安100ファイル超）**: レンズごとに扱いを変える。architecture は依存の把握（grep 中心）が仕事で全体を1つの視野で見る必要があるため **分割せず全域を1エージェント** に任せる。locality / drift はコードの中身を読む必要があるため **モジュール/ディレクトリ単位のシャードに分割し、シャード×レンズで並列起動** する。locality には範囲がシャードであることを伝える（シャードの外に対がありそうな汎用処理の手がかりを返させ、統合時に照合するため）。

シャード×レンズの並列起動に入る前に、規模ガードを通す: 起動エージェント数の見積り（シャード数 × 2 ＋ architecture 1体）と対象規模を提示し、続行かスコープ縮小かを確認する（推奨と理由を添える）。想定外の大量起動はコスト・時間に直結するため、黙って起動しない。

並列起動する場合のエージェント:

- `refactor-toolkit:refactor-scan-architecture` — ファイル横断の構造問題（結合・凝集・循環依存・レイヤ違反・神モジュール・責務の置き場所）。**このスキルの主役レンズ**。
- `refactor-toolkit:refactor-scan-locality` — ユニット内の機械的スメル（重複・長すぎる関数・深いネスト・複雑な条件分岐・デッドコード・基本型への執着）。
- `refactor-toolkit:refactor-scan-drift` — 文書化された設計意図および支配的パターンからの乖離（アーキテクチャの劣化・規約違反・意図と実装のズレ）。

各エージェントへ渡す情報:

- 解決済みのスキャン範囲（パス一覧）とファイル inventory
- 手順1で集めた設計意図ドキュメントと支配的パターンの要約
- 言語・スタックと、使えるツール（linter / 依存解析）の有無
- 「自分のレンズに集中し、各候補に影響度（🔴🟡🟢）だけを付ける。優先度・着手順は付けない」旨（各エージェント定義に記載済みなので簡潔でよい）

レンズを分けるのは、汎用スキャンだと各観点が薄まるため。とくにアーキテクチャ問題は複数ファイルを跨ぐので、専従させないと局所スメルに埋もれて見落とす。

### 3. ROI で統合・順位付け（中心工程）

全候補が出揃ったら、あなたが統合する。ここがこのスキルの価値の源泉。

1. **集約・重複統合・レーン外の除外**: 同一箇所・同一論点は1件にまとめる。アーキ候補と局所候補が同じコードを別角度で指していることがある（例「神モジュール」と「その中の長関数」）。包含関係があれば上位（構造）に束ねる。スペシャリストが挙げた**挙動バグ・脆弱性はここで候補から外し**、レポート末尾の申し送りに回す（レーン外）。シャード分割した場合は、locality が返した「汎用処理の手がかり」を全域 grep で照合し、シャードを跨いだ重複を取りこぼしていないか確かめる（シャード内しか見えない locality の死角を埋める）。
2. **設計意図との突き合わせ**: 候補が ADR 等の **意図的な決定に反していないか** を確認する。「一見スメルだが、文書化された判断の結果」なら候補から落とす（理由を残す）。文書化された設計を壊す提案をしないことが、能動スキャンの信頼性を支える。
3. **ROI シグナルの収集**: 各候補について次を見て、優先度の材料にする。
   - **影響度（payoff）**: スペシャリストの深刻さ × 将来の変更をどれだけ阻害するか。多くの変更の前提を縛る構造問題ほど高い。
   - **影響範囲（reach）**: 依存元・呼び出し箇所の広さ。広いほど効果が大きい（同時にコストも増える）。
   - **変更頻度（churn）**: `git log --oneline -- <path>` 等で、その箇所が頻繁に変わるか。高頻度 × 高複雑度は保守税を繰り返し払っており ROI が高い。git 履歴が無ければこのシグナルは省く。
   - **コスト（effort）**: 局所的な抽出/改名で済むか、横断的な再構成かの概算。
   - **リスク（risk）**: 退行リスク。テストで守られているか、クリティカルパスか。テストが無く影響範囲が広いほどリスクは高い。
4. **優先度（P1/P2/P3）の裁定**: 影響度を、コスト・リスクと変更頻度で割り引いて決める。
   - **P1（まず着手）**: 影響度が高く、コスト中以下・リスク制御可能。または変更頻度が高く保守税が大きい。最も費用対効果が高い。
   - **P2（計画して着手）**: 影響度は高いがコスト大／リスク高（先にテストを足す等の前提が要る）、または影響度中・低コスト。
   - **P3（余裕があれば）**: 局所的で影響の小さい改善。

   影響度と優先度が食い違うのは正常（影響大でも P3、影響中でも P1 はありうる）。その食い違いの理由（高リスク・高頻度など）こそ書く価値がある。
5. **設計検討への引き継ぎ印**: コスト大の構造的候補は、適用前に再設計の意思決定を要する。バックログ上で「設計検討が必要」と印を付け、このスキルはそこまでは踏み込まない（候補の提示で止める）。うち **複数の類似実装を1つに集約する統合系**（コピー改変で分岐したロジック等）は、比較分析と対話で統合設計を固める refactor-unify の領分なので、バックログにその旨を書く。

### 4. バックログを出力する

優先度順の改善バックログを **Markdown ファイルに保存** し、会話内には要約を出す。バックログは時間をかけて消化する持続的な成果物なので、ファイルとして残す。

- 保存先: プロジェクトに `docs/` があればその配下（例 `docs/refactoring/<対象スラッグ>.md`）。無ければ保存先を提案して確認する。
- 既存のバックログが同じ対象を扱っていれば先に読み、**完了・見送り済みの項目を新候補として再掲しない**（同一候補は旧 #ID と状態を引き継ぐ）。上書きか別ファイルかは確認する。
- バックログは refactor-apply が1件ずつ消化する前提の成果物。各項目は、**後で単独で読んでも着手できる自己完結の記述**にする（apply はバックログとコードだけを見て動き、このスキャン時の会話は参照できない）。

## 出力フォーマット

### バックログファイル

```
# リファクタリング・バックログ: <対象の説明>

対象: <スキャンした範囲・ファイル数（絞っていればその旨）>
スキャン時コミット: <スキャン時点の HEAD sha。refactor-apply が鮮度チェックの基準に使う>
レンズ: アーキテクチャ・局所スメル・ドリフト
件数: P1 N ・P2 N ・P3 N （設計検討要 N ・棄却 N）
消化順序: 任意（P1 から順を推奨）
総評: <最も効く構造的論点・全体傾向を2〜4行。言及する候補には #ID を併記>

---

## P1（まず着手）
### #N <🔴🟡🟢> [レンズ] path:line（複数なら主たる箇所＋「ほか N 箇所」）— 一行要約
- 候補: <何が問題か。アーキ候補なら跨ぐファイル/モジュールを具体に>
- 効果/根拠: <直すと何が楽になるか。放置コスト。周辺の支配的パターンとの差>
- ROI: 影響度=高 / コスト=中 / リスク=低 / 変更頻度=高 — <優先度の理由を一句>
- 方向性: <どう直すか。方向が明確な時のみ。具体実装までは書かない>
- 設計検討: 要/不要 <要なら、なぜ単独で適用できないか。統合系なら「refactor-unify で扱う」と書く>
- 状態: 未着手

## P2（計画して着手）
（同形式。リスク・コストで P1 から落ちた理由を ROI 行に明記）

## P3（余裕があれば）
（薄くてよい。#ID・レンズ・箇所・一行要約 + ROI の一句のみ）

## 設計検討が必要（構造的・大）
（再設計の意思決定を要する候補。問題の所在と、なぜこのスキルの範囲外（適用前に設計が要る）かを書く。P1/P2 と重複してよく、その場合は該当 #ID を再掲し印を付ける）

## 棄却（スペシャリストは挙げたが候補から外した）
（文書化された意図に沿う／到達不能・デッドでない既存許容 など、外した理由。透明性のため残す）
```

状態は `未着手 / 完了（コミット）/ 見送り（理由）/ 要再検討（理由）` の4値。状態の語彙（refactor-apply が消化時に更新する）と「スキャン時コミット」ヘッダは refactor-apply との共有契約なので、変えたり省いたりしない。

### 会話内の要約

保存したファイルのパスと、P1 を中心に「まず効く 3〜5 件」を箇条書きで示す。全件はファイルを参照させる。次の一歩として、バックログの消化は refactor-apply、統合系の設計検討は refactor-unify を案内する。

## 原則

- **影響度（スペシャリスト由来）と優先度（あなたの裁定）は独立軸**。グルーピングの第一キーは優先度、優先度内は影響度順。影響大が P3 に、影響中が P1 に入るのは正常で、その食い違いの理由こそ価値。
- **ROI を必ず明示する**。各候補に影響度/コスト/リスク（/変更頻度）の一言を付ける。これが「なぜこの順か」の説明であり、バックログを単なるスメル一覧と分ける核心。
- **変更頻度は増幅器であって起点ではない**。churn は既存のスメル・設計問題の優先度を押し上げるシグナルにすぎない。スメルも設計問題も無い「高頻度だが綺麗なファイル」は候補にしない。churn 単体で候補や優先度を作らない。
- **文書化された意図を壊す提案をしない**。ADR 等に反する「改善」は棄却に回し理由を残す。これを怠ると能動スキャンは信頼を失う。
- **コードは修正しない／再設計まで踏み込まない**。大きい構造的候補は「設計検討要」で止める。発見と順位付けがこのスキルの仕事。
- **候補を捻り出さない**。重大な候補が無ければ、スキャン範囲と照合した支配的パターンを添えて「優先度の高い候補は見つからなかった」と言い切る。
- **情報量は確信度・再考余地で配分する**。棄却やリスク評価が際どいものほど根拠を厚く。明白な P3 は一句で済ませる。
