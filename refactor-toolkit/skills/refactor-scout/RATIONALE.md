# refactor-scout 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

既存コードを能動的にスキャンしてリファクタリング候補を発見し、ROI で順位付けした改善バックログを出すスキル。発端は「リファクタリング候補を見つけて設計改善を行うスキルが欲しい」（2026-06）。

このリポジトリには設計・レビュー隣接の資産が密にある（`review:quality-review`、`dev-toolkit`/`magi`/`spec-toolkit` の各 architect 群、`doc-toolkit:extract-design` 等）。作成前の調査で、**「差分でも新機能でもなく、既存コードを能動的に棚卸しして候補を優先順位付けする」領域だけが空いている**ことを確認した。このスキルの存在意義はその一点に集約されるため、差別化要素は load-bearing として明示する。

## 中核的な設計判断

### 【load-bearing】起点を差分ではなくモジュール/リポジトリにする
- **決定**: 入力は git 差分ではなくスキャン対象パス。未変更コードを含む既存構造全体を見る。
- **却下した代替案**: 差分起点（変更ファイルに限定）。→ quality-review と完全に重なり、新規プラグインの正当性が消える。
- **防いでいる失敗**: quality-review（差分のマージゲート）との同一化。能動スキャンという固有価値の喪失。
- **出所**: 作成前の landscape 調査 + ユーザー選択（探索範囲=指定モジュール既定＋全体は任意, 2026-06）。
- **補足（2026-07-07, PR/ブランチ入口の追加）**: PR・作業ブランチを対象指定に追加したが、この判断の撤回ではない。判断の本質は「差分のマージゲートをしない」ことにあり、PR/ブランチ入口では差分はスコープ解決の種（変更ファイル＋1ホップ展開で関連領域へ拡張）にすぎず、評価対象は領域の既存構造。出所: refactor-radar の feature モード（pr/branch 入口）の移植（ユーザー指示による統合）。

### 【load-bearing】ROI 順の「バックログ」を成果物にする（単なるスメル一覧にしない）
- **決定**: 全候補を影響度・影響範囲・変更頻度(churn)・コスト・リスクから ROI 評価し、P1/P2/P3 の順序付きバックログとして出す。
- **却下した代替案**: 検出結果をフラットに列挙するだけ。→ 既存 linter/レビューと差がなく、「どれから手を付けるか」という最大の悩みに答えない。
- **防いでいる失敗**: 大量の指摘を出して放置される「読まれないスメル一覧」になること。発見の価値は順位付けにこそある。
- **出所**: ユーザー選択（成果物=発見・順位付けのみ, 2026-06）+ landscape 調査の gap（ROI ランキングは既存ゼロ）。

### 【load-bearing】影響度（スペシャリスト）と優先度（オーケストレータ）の二軸分離
- **決定**: スペシャリストは各候補に保守性ダメージ＝影響度(🔴🟡🟢)だけを付ける。実際の着手順＝優先度(P1/P2/P3)はオーケストレータが churn/コスト/リスクを足して裁定する。
- **防いでいる失敗**: 「影響が大きい＝今すぐやるべき」という短絡。影響大でも高リスク/高コストなら後回し、影響中でも高頻度・低コストなら最優先、という現実的判断ができなくなる。食い違いの理由（高リスク等）を書かせるのがバックログの肝。
- **出所**: 設計判断（タスク駆動）。検出の客観評価と実務上の優先付けは別物という一般原則であり、特定スキルの形式流用ではない。

### 【load-bearing】文書化された設計意図に反する候補は棄却する
- **決定**: 手順1で ADR/ARCHITECTURE.md/支配的パターンを基準として集め、それに沿った「一見スメル」は候補から落として棄却理由を残す。drift レンズはこの基準照合を専門化したもの。
- **防いでいる失敗**: 意図的な設計決定（性能・互換のための例外等）を「改善」と称して壊す提案。これを出すと能動スキャンは一度で信頼を失う（呼ばれなくなる）。
- **出所**: landscape 調査の gap（docs→code の整合確認は既存ゼロ）。

### アーキテクチャ重視の3レンズ分割（architecture を主役に）
- **決定**: 検出を architecture / locality / drift の3スペシャリストに分け、ファイル横断の構造問題を主役レンズに据える。
- **却下した代替案**: (a) 機械的スメルのみ → quality-review-design とモジュール規模で重複。(b) アーキのみ → ユーザーが欲しがる手早い局所改善を取りこぼす。
- **防いでいる失敗**: 汎用1エージェントだとアーキ問題が局所スメルに埋もれて見落とされる（並列専門化はこのリポジトリ共通の idiom）。
- **出所**: ユーザー選択（検出対象=両方・アーキ重視, 2026-06）。

### スコープ規模に応じたディスパッチ（小スコープは並列しない）
- **決定**: 大きいモジュール／リポジトリ全体では3レンズを並列サブエージェント起動、数ファイルの小スコープでは起動せず自分で順に適用する。3レンズは必ず全て通す。
- **却下した代替案**: 常に3サブエージェント並列。→ iteration-1 eval で、小さく綺麗なフィクスチャに対し並列起動はベースラインの約4〜6倍のレイテンシ/トークンを要したのに、検出の実質はほぼ同等だった。小スコープでは並列のオーバーヘッドが質に見合わない。
- **防いでいる失敗**: 小規模対象での無駄な多段サブエージェント起動（コスト超過）。一方で大規模対象では並列専任が無いとアーキ問題が局所スメルに埋もれて見落とされる（こちらは並列を残す理由）。
- **出所**: iteration-1 eval（baseline parity の分析, 2026-06-17）。

### 【load-bearing】レーン規律（挙動バグ・脆弱性は扱わない）
- **決定**: リファクタリング候補は構造・保守性（スメル・設計・ドリフト）に限定。スペシャリストが挙げた挙動バグ・脆弱性はオーケストレータが候補から外し、申し送りに分ける。
- **却下した代替案**: 気づいたバグ/脆弱性も一緒に優先度付けして出す。→ iteration-1 eval のベースラインはまさにこれをやり、SQL インジェクションや認可漏れをリファクタリング指摘の主役に格上げしてレーンが濁った（correctness/security へのスコープ漏れ）。
- **防いでいる失敗**: 「直すべき欠陥（バグ/脆弱性）」と「設計改善」をバックログ上で取り違えること。区分が混ざると、何が品質改善で何が緊急の不具合修正かが読めなくなる。security は security-review、挙動バグは correctness レビューの領域。
- **出所**: iteration-1 eval（baseline がレーンを越えた観察, 2026-06-17）。

### コード非改変・報告のみ（適用と再設計はしない）
- **決定**: 候補発見と順位付けで止める。コードは書き換えず、大きい構造的候補は「設計検討要」の印を付けるに留める。
- **却下した代替案**: テスト担保で実際にリファクタを適用する apply モード。→ リスク最大、リポジトリ唯一のコード改変スキルになり堅牢な安全ハーネスが要る。将来の拡張余地としては残す。
- **出所**: ユーザー選択（成果物=発見・順位付けのみ, 2026-06）。
- **追記（2026-07）**: 適用は安全ハーネス付きの独立スキル refactor-apply として実現した（`skills/refactor-apply/RATIONALE.md`）。scout 自身の非改変規律は変えていない。

### 【load-bearing】バックログを実行系（refactor-apply）との共有契約に拡張
- **決定**: 各項目に `状態:` 行（未着手/完了/見送り/要再検討）、ヘッダに `消化順序:` を持たせ、項目は「後で単独で読んでも着手できる自己完結の記述」とする。
- **防いでいる失敗**: apply はスキャン時の会話を参照できないため、項目が文脈依存で書かれていると消化時に再調査が要る（コンテキスト経済の崩壊）。完了・見送り済み候補の再掲によるバックログの腐敗。
- **補足**: 状態語彙と項目形式は refactor-scout / refactor-unify / refactor-apply の3スキル共有契約。**変更時は3つの SKILL.md を同時に更新する**（各スキルは実行時に他スキルを読めないため、意図的に分散定義している）。
- **追記（2026-07-07）**: ヘッダに「スキャン時コミット」を共有契約として追加。refactor-apply が `git diff --stat` で候補前提の現存を機械的に確認する基準になる（refactor-radar の鮮度チェック機構の移植）。
- **出所**: ユーザー要望（順番に修正したい, 2026-07）に伴うプラグイン拡張。

### 機能スコープの追加（パス・機能・全体の3形態）
- **決定**: 対象指定に「機能」（git 履歴・エントリポイント・grep で関連ファイル集合に解決し、スキャン前にユーザー確認）を追加。
- **防いでいる失敗**: 「実装し終えた機能の設計を見直したい」ユース（用途B）で、ユーザーがパス列挙を強いられる／解決を誤ったまま全工程が別の場所を見る。
- **出所**: ユーザー要望（機能実装後の設計改善, 2026-07）。

### 大規模スコープのシャード分割（レンズ非対称）
- **決定**: 1エージェントで読み切れない規模（目安100ファイル超）では、architecture は全域1エージェント・locality / drift はシャード×レンズで並列起動。locality にはシャードである旨を伝えて「汎用処理の手がかり」を返させ、統合時に全域 grep で照合する。
- **却下した代替案**: 全レンズ一律のシャード分割。→ 循環依存・レイヤ違反はシャードを跨いで初めて見えるため、主役レンズの検出対象が消える。
- **防いでいる失敗**: 広範囲指定（モノレポの1サービス等）でエージェントが読み切れず薄いスキャンになる／シャード分割でファイル横断の重複が原理的に見えなくなる死角。
- **出所**: ユーザーの痛点（広範囲指定でのコンテキスト枯渇, 2026-07）。⚠️ シャード規模の目安（100ファイル）は未実測。大規模 fixture での eval 検証が今後の課題。
- **追記（2026-07-07, 規模ガード）**: シャード×レンズ並列の起動前に、起動エージェント数の見積りを提示して続行かスコープ縮小かを確認するガードを追加（refactor-radar の規模ガードの移植）。防いでいる失敗: 広範囲指定での想定外の大量エージェント起動（コスト・時間）。

### 独立プラグインに配置し、review のレポート形式を流用しない
- **決定**: `review` に同居させず独立プラグイン `refactor-toolkit` とする。二段構え（並列スペシャリスト＋統合役）はリポジトリ共通 idiom として採るが、quality-review の報告フォーマット・対応区分の語彙（要対応/別対応/要相談/任意/見送り）は流用せず、ROI バックログ独自の形式（P1/P2/P3・ROI 行・設計検討/棄却）を起こした。
- **防いでいる失敗**: CLAUDE.md「プラグイン間の参照スコープ」違反。review に同居すると quality-review の design スペシャリスト/形式を再利用したくなり、review の「差分ゲート」という独自性も濁る。
- **出所**: CLAUDE.md 独立性ルール + ユーザー選択（配置=独立プラグイン, 2026-06）。

### churn（変更頻度）を ROI シグナルに採る
- **決定**: `git log` でその箇所の変更頻度を見て、高頻度 × 高複雑度を高 ROI とみなす。git 履歴が無ければこのシグナルは省く。
- **防いでいる失敗**: 静的なスメルの重さだけで優先度を決め、「滅多に触らない汚いコード」を上位に、「毎週触る中程度に汚いコード」を下位にしてしまう取り違え（保守税は変更頻度に比例する）。
- **補足（増幅器であって起点ではない）**: churn は既存のスメル/設計問題の優先度を押し上げるシグナルにすぎず、それ単体で候補を作らない。スメルも設計問題も無い「高頻度だが綺麗なファイル」は候補にしない。iteration-2 でこの取り違え（churn 単体での誤検出）を専用トラップで検証する。
- **出所**: 設計判断（behavioral code analysis の一般知見）。

## 解釈・仮定（要確認）

- **既定スキャン範囲**: ユーザーは「指定モジュール既定＋全体は任意」を選択 → 未指定時は対象パスを確認する解釈にした。⚠️ 全体スキャンを毎回したいわけではない前提。
- **出力のファイル保存**: ⚠️ バックログは持続成果物なので docs/ 配下に Markdown 保存する解釈にした（ユーザーの「ツール生成物は docs/ 配下」運用方針に基づく）。プロジェクトに docs/ が無ければ保存先を確認する。会話内要約のみで足りる運用を望む可能性は残る。なおバックログは **コミットしないローカル管理ファイル** という運用前提が確定（ユーザー指示 2026-07。git 操作を持つのは apply のみのため、明文化は refactor-apply 側にある）。
- **再設計の引き継ぎ先**: 当初は⚠️（プラグイン独立性を優先し特定プラグインを名指しせず「設計検討要」の印のみ）だったが、2026-07 に同一プラグイン内へ refactor-unify（統合系の設計）/ refactor-apply（適用）を新設して解消。同一プラグイン内の連携は CLAUDE.md の参照スコープ規約上も自由で、独立性と両立する。プラグイン外（magi 等）への名指し接続は引き続きしない。
- **検出の3レンズ並列サブエージェント**: ⚠️ iteration-1 eval の結果、小さく綺麗なフィクスチャ（15ファイル）では並列サブエージェントの有無で検出の実質差がほぼ出ず（baseline parity）、コストだけ約4〜6倍かかった。これを受けて「スコープ規模に応じたディスパッチ」を導入（小スコープは並列しない）。スキルの真価（体系的網羅・一貫性・スケール時の取りこぼし防止）は、1パスで読み切れない大規模/雑然としたコードベースでこそ出るとの仮説 → iteration-2（34ファイル・4モジュール循環・5ファイル近似重複・churn/凍結トラップ）で実測した。結果: Opus 4.8 のベースラインはこの規模でも横断問題（循環・散在重複）を素で検出でき、「スケールで baseline が取りこぼす」仮説はこの規模/モデルでは成立しなかった。明確かつ再現的な優位は **レーン規律**（開放的な「リファクタして」指示で、baseline は SQL インジェクションを P1 のリファクタ候補に格上げするのに対し、スキルは申し送りに分離）。スキルの価値は能力差ではなく一貫性・ガバナンス・境界規律にあると確認。
