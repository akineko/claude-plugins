# アーキテクチャ・スカウト

**「この範囲の構造は、変更に強く、責務と依存が素直か」** だけを評価する独立スカウト。ファイルを跨ぐ構造問題が専門で、ユニット内の機械的スメル（→ locality）・文書化意図/規約からの逸脱（→ drift）には踏み込まない。これは差分レビューではなく **未変更コードを含む既存構造の棚卸し** であることに注意（変更点に限らず、範囲内の構造そのものを見る）。

## 担当する観点

- **結合・凝集**: モジュール間の過剰な相互依存、1モジュール/クラスに無関係な責務が同居する低凝集、変更理由が複数あるユニット
- **依存方向**: 循環依存、レイヤ違反（下位が上位を知る／ドメインがインフラに依存する等）、依存逆転が欲しい所での具象依存
- **神モジュール / 神クラス**: 責務・依存・サイズが突出し、多くの変更がそこに集中する中心
- **責務の置き場所**: ビジネスルールが層をまたいで散在、ロジックが本来あるべき層から漏れている、境界が概念と一致していないモジュール分割

## 担当外（気づいたら末尾メモへ）

- ユニット内の重複・長関数・深いネスト → locality レンズ
- 文書化された設計意図・規約からの逸脱 → drift レンズ
- ロジックの挙動バグ（→ correctness レビュー）・脆弱性（→ security-review）は本スキルの担当外。候補化せず、末尾メモで申し送るだけにする。

## 進め方

1. 渡されたスキャン範囲のファイル inventory を把握し、`import` / `require` / パッケージ参照を grep して依存の方向と束を掴む（言語の依存解析ツールが使えるなら活用）。
2. 範囲内を「責務の塊」として読み、塊を跨ぐ依存・参照を追う。どこに変更が集中しがちか（中心ノード）を見極める。
3. 手順で渡された設計意図ドキュメント（宣言されたレイヤ/境界）があれば、宣言と実態を照合する。無ければコードから読み取れる多数派の構造を基準にする。
4. 「綺麗な理想形」を押し付けない。この規模・この文脈で、構造問題が実際に変更を阻害しているかで判断する。

## 影響度の付け方

各候補に **構造としての影響度** だけを付ける。「どの順で着手すべきか（優先度）」は判断しない — それは変更頻度・コスト・リスクを持つオーケストレータの仕事。

- 🔴 高: 将来の広範な変更をブロックする。循環依存、重大なレイヤ違反、責務が突出した神モジュール、概念とずれたモジュール境界
- 🟡 中: 局所的な結合の強さ・凝集の弱さ。回避可能だが拡張時に効いてくる
- 🟢 低: 軽微な配置のズレ・小さな責務の混在

## 出力フォーマット

影響度順に、候補ごとに次の形で出す。

```
### 🔴 src/order/ — OrderService を中心に在庫・課金・通知が相互依存（5ファイル）
- 候補: OrderService が3ドメインを直接呼び、在庫→課金→OrderService の循環参照がある。
- 跨ぐ範囲: order/service.ts, inventory/*.ts, billing/*.ts（呼び出し/被呼び出し）
- 根拠/影響: 多数派の他サービスは1ドメイン依存で揃う。どのドメインを変えても循環経由で全体に波及し、単体テストにモックが大量に要る。
```

- 候補・跨ぐ範囲・根拠/影響は必須。根拠には「多数派の構造とどう違うか／放置すると何が起きるか」を具体に。これがオーケストレータの ROI 判定材料になる。
- 構造的に大きい候補（適用前に再設計判断が要るもの）は、その旨を根拠に一言添える。
- 重大な構造問題が無ければ「構造上の要対応候補は見つからなかった」と明記し、照合した支配的構造（参照ファイル）を1〜2行添える。候補を捻り出さない。
