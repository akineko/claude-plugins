# refactor-implementer 設計ノート

> 定義=refactor-implementer.md / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。

## 役割と位置づけ

refactor-apply の実装工程を担う。全体設計（1項目=1エージェント=1コミット、メインはコードに触れない）は `skills/refactor-apply/RATIONALE.md` 参照。

## 中核的な設計判断

### 【load-bearing】コミットしない（境界はオーケストレータ）
- **防いでいる失敗**: エージェントがコミットすると、ユーザー確認前に履歴が進む（既定モードの確認ゲートが無意味になる）。また修正指示での差し戻し時に履歴の巻き戻しが要る。

### 【load-bearing】中止時のロールバック契約
- **決定**: 中止・失敗時は作業ツリーを着手前に戻してから報告する。
- **防いでいる失敗**: 連続モードで前の項目の残骸の上に次の項目が実装される汚染。「中途半端な適用が一番高くつく」の実装形。

### 着手前のテスト実行（green 確認）
- **防いでいる失敗**: 既存の赤テストを自分の破壊と誤認して直そうとする暴走、および自分の破壊を「元から赤かった」と誤報告する事故。

### ツール無制限（tools 行なし）
- **決定**: スキャン系と異なり tools を制限しない（Write/Edit/Bash が本務）。
- **出所**: プラグイン内で唯一のコード改変エージェントであることは意図的な集中（refactor-scout の「コード非改変」load-bearing 判断を、改変責務のこのエージェント1点に隔離して両立させた）。

### 鮮度チェック結果の受け入れ（再検証の起点化）
- **決定**: オーケストレータが渡す鮮度チェックの結果（スキャン時以降の対象変更の有無）を再検証の起点にする。再検証そのものは廃止しない（渡されない旧形式の計画でも自立して動けるように）。
- **出所**: refactor-radar の鮮度チェック機構の移植（2026-07-07。機構全体の設計判断は `skills/refactor-apply/RATIONALE.md` 参照）。
