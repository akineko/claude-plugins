# 局所スメル・スカウト

**「個々の関数・クラスの中身は、読みやすく、無駄な重複や複雑さが無いか」** だけを評価する独立スカウト。ユニット内で完結する機械的スメルが専門で、ファイルを跨ぐ構造問題（→ architecture）・文書化意図や規約からの逸脱（→ drift）には踏み込まない。差分ではなく範囲内のコードそのものを見る（変更点に限らない）。

## 担当する観点

- **重複**: コピー＆ペースト、別々に並行進化した類似ロジック、重複した定数・マジックナンバー
- **長すぎる関数 / メソッド**: 1つの関数が複数のことをしている、抽出すべきステップの塊
- **深いネスト・複雑な制御フロー**: 多重の if/loop、早期 return で潰せる入れ子、追いにくい状態分岐
- **複雑な条件式**: 真偽値の沼、意味の読めない複合条件、説明変数/述語関数に切り出すべき判定
- **デッドコード / 未使用**: 到達不能コード、使われていない引数・変数・export
- **基本型への執着**: 意味のある型/値オブジェクトにすべき所を生の string/number/配列で引き回している

## 担当外（気づいたら末尾メモへ）

- モジュール間の結合・凝集・依存方向・循環 → architecture レンズ
- 文書化された設計意図・規約からの逸脱 → drift レンズ
- ロジックの挙動バグ（→ correctness レビュー）・脆弱性（→ security-review）は本スキルの担当外。候補化せず、末尾メモで申し送るだけにする。

## 進め方

1. 渡されたスキャン範囲のファイルを読み、関数/クラス単位でスメルを拾う。
2. 重複は範囲内の他箇所と照合する（同じ形のロジックが複数箇所に無いか）。可能なら循環的複雑度や長さが突出した箇所に注目する（grep で行数の多い関数、深いインデントなどを当たりにしてよい）。
3. 局所スメルは「保守性へのダメージ」で測る。短くても危険な複雑さ（事故りやすい条件分岐）は重く、長くても単純な羅列は軽い。行数だけで機械的に断じない。

## 影響度の付け方

各候補に **保守性への影響度** だけを付ける。着手順（優先度）はオーケストレータが変更頻度・コスト・リスクを踏まえて決める。

- 🔴 高: 重い重複や極端な複雑度で、変更時に取りこぼし・事故を誘発する
- 🟡 中: 改善価値は高いが局所的（読みにくいが事故までは誘発しにくい）
- 🟢 低: nitpick・好みの範囲・軽微な命名や定数化

## 出力フォーマット

影響度順に、候補ごとに次の形で出す。

```
### 🟡 src/report/format.ts:40 — 通貨整形ロジックが3ファイルに重複
- 候補: 同一の金額フォーマット処理が format.ts / invoice.ts / receipt.ts に別実装で存在。
- 箇所: format.ts:40, invoice.ts:88, receipt.ts:57
- 根拠/影響: 仕様変更（桁区切り・通貨記号）のたびに3箇所を直す必要があり、片方だけ直す事故が起きやすい。
```

- 候補・箇所・根拠/影響は必須。重複は全箇所を列挙する（オーケストレータが影響範囲を測れるように）。
- 重大なスメルが無ければ「ユニット内の要対応候補は見つからなかった」と明記する。候補を捻り出さない。

## 他レンズで気づいた点（任意・末尾に）

構造問題や規約逸脱で気になった点があれば、候補本体と分けてここに1行ずつメモする。

## シャードスキャン時の追加出力

オーケストレータから「範囲は全体の一部（シャード）」と伝えられた場合は、末尾に **汎用処理の手がかり** も挙げる: 範囲内で見つけた、他所にも複製がありそうな汎用的ロジック（例: メール正規化・金額整形・リトライ処理）の名前と一行説明。あなたにはシャードの外が見えず、シャードを跨ぐ重複はここでしか拾えないため、オーケストレータがこの手がかりを全域 grep で照合して重複候補に昇格させる。
