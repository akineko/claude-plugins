# test-refactor

テストコードを「診断 → 横断分析 → 計画 → 承認 → 適用 → 報告」のパイプラインでリファクタリングする。

## 前提となる洞察

プロダクションコードのリファクタリングはテストが守ってくれるが、テストのリファクタリングを守ってくれるテストは存在しない。「変更後もテストが green」は安全の証明にならない — 絶対に落ちないテストも green のままだからだ。このスキルの中核は、変換の種類ごとに安全の証明方法を変える検証プロトコル（`references/taxonomy.md`）にある。検出や変換の巧拙よりこのプロトコルの遵守を優先する。

## 不変条件（全フェーズで維持）

1. **検証力を弱めない**: テストやアサーションを削る・緩める変換は、taxonomy.md の定める証明（カバレッジマッピング、必要なら mutation check）を伴わない限り実施しない。カバレッジマッピングの根拠にできるのは**スコープ内のテストのみ**（正準ルールは taxonomy.md）。
2. **検証力の強化は許容**: 弱いアサーションの強化や flaky 解消は積極的に行う（red check で裏付ける）。
3. **プロダクションコードを恒久変更しない**: mutation check / red check のための一時変更は、検証後に必ず元の内容へ復元する。
4. **期待値が間違っているテストは直さない**: プロダクションのバグを固定しているテストを見つけたら、修正せず「報告のみ事項」に回す。それはバグ発見でありリファクタリングではない（挙動が変わる）。
5. **テスト実行の生ログをメインコンテキストに載せない**: テスト実行はすべてサブエージェント内で行い、構造化サマリだけを受け取る。大きな中間生成物（検証インベントリ等）もファイル渡しにする。verbose なレポーターや大量のスタックトレースがコンテキストを圧迫し、後続フェーズの判断品質を落とすため。

## 変換の3類型（正準定義は references/taxonomy.md）

| 類型 | 内容 | 検証プロトコル |
|------|------|--------------|
| 保存的 | 検証内容を変えない（命名・分割・抽出・定数化・高速化） | green check |
| 削減的 | テスト/アサーションを削る・緩める | カバレッジマッピング（＋証明しきれない場合は mutation check） |
| 強化的 | 検証力を上げる（アサーション強化・flaky 解消） | red check |

## 引数の解釈

- **パス（複数可）**: 対象をそのディレクトリ/ファイル配下のテストに限定する。モノレポでサービス単位に絞るときに使う。
- **省略時**: リポジトリ全体（git 管理下のテストファイルすべて。node_modules 等の依存物は対象外）。
- **`--diff`**: ブランチ差分（デフォルトブランチとの差分＋未コミット変更）に含まれるテストファイルを対象にする。横断分析には比較相手が必要なため、差分テストと同じプロダクションコードを検証する既存テストもインベントリ化の対象に含める。
- **`--plan-only`**: Phase 3 の計画作成で終了する（適用しない）。
- **`--apply <計画ファイル>`**: 既存の計画ファイルを読み、未適用の承認済み項目から Phase 5 を再開する。Phase 0 は省略しない — 計画作成時から状況が変わっている可能性があるため。

## パイプライン

### Phase 0: 前提確認

1. 現在日時を `date` コマンドで確認する（計画ファイル名に使う）。
2. **スコープ解決**: ワークスペース定義（package.json の workspaces / pnpm-workspace.yaml / turbo.json / nx.json / go.work 等）を確認し、スコープに含まれるパッケージとテスト実行方法の当たりを付ける。単一パッケージ構成ならリポジトリ全体が1パッケージ。
3. **テストファイル列挙**: スコープ内のテストファイルを列挙する（`*.test.*` / `*.spec.*` / `test_*.py` / `*_test.go` / `tests/` ディレクトリ等、プロジェクトの規約に従う）。
4. **規模ガード**: テストファイル数を確認する。**150 を超える場合は続行せず**、パッケージ別の内訳を示してスコープを絞るか続行するかをユーザーに確認する（意図しない全体スキャンで大量のエージェント起動とテスト実行が走るのを防ぐ）。
5. **ベースライン実行**: パッケージごとに `test-refactor-baseline-runner` を並列起動する。渡すもの: パッケージパス、対象テストファイル一覧。受け取るもの: テストコマンド / green・red ファイル / ファイル別実行時間 / 未コミット変更 / 警告。
6. red のテストファイルは対象から除外し、報告のみ事項に載せる（全体中止にしない — 一部が壊れていても残りはリファクタリングできる）。対象テストファイルに未コミット変更があればそれも報告に含める（ユーザーの作業と差分が混ざるため）。

### Phase 1: モジュール別調査

1. 中間生成物用の作業ディレクトリを `mktemp -d` で**実行ごとに一意に**作る（セッションのスクラッチディレクトリ配下を使う場合も必ず実行専用の新規サブディレクトリを切る）。過去の実行の残留インベントリが混入すると横断分析が汚染されるため。
2. テストファイルをディレクトリ単位でグループ化する（1グループ最大10ファイル目安。巨大なファイルは少なめに）。
3. グループごとに `test-refactor-surveyor` を並列起動する。渡すもの:
   - 担当テストファイル一覧と、検証対象（プロダクションコード）の探し方のヒント
   - この SKILL.md と同じディレクトリにある `references/taxonomy.md` の絶対パス
   - 検証インベントリの出力先ディレクトリ（作業ディレクトリ配下）
4. 受け取るもの: 局所指摘（L系）のリスト（インライン）とインベントリファイルのパス。インベントリの中身はメインでは読まない。

### Phase 2: 横断分析

`test-refactor-cross-analyzer` を1体起動する。渡すもの: インベントリディレクトリのパス、taxonomy.md の絶対パス、スコープの説明（対象パッケージ・スコープ境界）。受け取るもの: 横断指摘（C系）のリストと未評価範囲の注記。

スコープが限定されている場合、スコープ外との重複（例: 対象パッケージのテストと、それを利用する別パッケージのテストの重複）は評価されていない。この事実は Phase 6 の報告に必ず明記する（見ていないものを「無かった」と誤読させない）。また、スコープ外のテストは削減の根拠（代替カバレッジ）にできない — 相手側がスコープ外にある重複の指摘は「要ユーザー判断」として計画に残す。

### Phase 3: 計画

1. 局所指摘と横断指摘を統合し、同一箇所・同一分類の重複を排除して ID（TR-001 形式）を振る。
2. `references/taxonomy.md` の判断ガイドに照らして各指摘の確信度を確認する。confidence が low のもの、削減的変換で判断が割れうるものには「要ユーザー判断」フラグを付ける。
3. 優先度バンド（taxonomy.md 参照。バンド1=信頼の回復、2=コスト削減、3=快適性）の順に並べる。
4. 計画ファイルを `docs/test-refactor/plan-<YYYYMMDD-HHmm>.md` に保存する（`docs/` が無ければ作成）。形式は後述。

### Phase 4: 承認チェックポイント

計画の要約（バンド別・分類別の件数、代表的な項目、要ユーザー判断の項目）を提示し、適用範囲をユーザーに確認する: 全件 / バンド指定 / 個別選択 / 中断（計画のみ保存）。「要ユーザー判断」フラグの付いた項目は、明示的に承認されない限り適用しない。`--plan-only` の場合はここまでで終了し、計画ファイルのパスと `--apply` での再開方法を案内する。

### Phase 5: 適用

1. 承認された項目を、触るテストファイル単位でグループ化する（複数ファイルに跨る項目は関係ファイルをすべて含むグループにし、同じファイルに触るグループ同士は結合する）。
2. グループごとに `test-refactor-implementer` を**逐次**起動する（並列にしない — テストファイル編集の衝突とテスト実行の資源競合を避ける。所要時間の大半は検証のテスト実行なので並列化の利得も小さい）。渡すもの: グループ内の承認済み項目（計画ファイルの該当部分）、taxonomy.md の絶対パス、該当パッケージのテストコマンド、ベースラインのファイル別実行時間。
3. 受け取るもの: 項目別の結果（applied / skipped / failed、検証エビデンス、備考）。
4. グループ完了ごとに計画ファイルの項目ステータスを更新する（`--apply` での再開を正確にするため）。

### Phase 6: 報告

以下の構成で報告する:

- **概要**: 適用 / スキップ / 失敗の件数、バンド別内訳
- **変更一覧**: 項目ごとに「何を → どう変えたか」と検証エビデンス（実施した check と結果）
- **削減の対応表**: 削除・緩和した検証それぞれについて「どのテストが同じ振る舞いを守り続けるか」
- **速度改善**: 該当項目の前後の実測時間
- **報告のみ事項**: 期待値バグ疑い、red で除外したファイル、未コミット変更の警告、スコープ外未評価の注記
- **計画ファイルのパス**: 未適用項目が残る場合は `--apply` での再開方法

## 計画ファイル形式

```markdown
# test-refactor 計画 <YYYY-MM-DD HH:mm>

## 実行コンテキスト
- スコープ: <パス / リポジトリ全体 / --diff>
- パッケージとテストコマンド: <一覧>
- ベースライン: <テストファイル数、red 除外、総実行時間>

## 項目

### TR-001 [バンド1] [L1 hollow-assertion] <一言サマリ>
- 場所: <ファイル:行>
- 根拠: <検出の根拠>
- 変換: <提案する変換>（類型: 強化的 / 検証: red check）
- 確信度: high / 要ユーザー判断: なし
- 状態: 未適用 | 承認済み | applied | skipped | failed
```

## 判断に迷ったら

適用しない。削減的変換は「証明できなければやらない」が原則で、見送った項目は計画に残るためユーザーが後から判断できる。件数を稼ぐ必要はない。
