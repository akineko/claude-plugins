# テストリファクタリング分類カタログ

test-refactor スキルの全エージェント（surveyor / cross-analyzer / implementer）とメインエージェントが共有する唯一の定義。指摘の category は本ファイルの ID を用いる。

## 1. 変換の3類型と検証プロトコル

テストのリファクタリングには「守ってくれるテスト」が存在しないため、変換の性質ごとに安全の証明方法を変える。

どの類型にも共通する制約:

- **スメルを持ち込まない**: 変換によって本カタログのスメルを新たに導入しない。特に、期待値を検証対象のプロダクション関数の呼び出しで計算する書き換えは、いかなる変換の手段としても禁止（L8 の悪化形 — テストが実装の鏡になり、どんなリグレッションにも fail しなくなる）。期待値は必ずリテラルで固定する。
- **カバレッジマッピングの根拠はスコープ内に限る**（詳細は「削減的」の項）。

### 保存的（preserving）— 検証内容を変えない

対象: 命名改善、1テスト1振る舞いへの分割、セットアップ抽出、マジック値の定数化、期待値計算の直線化、ケース数を変えないパラメタライズ、準備手段の高速化。

**green check**: 変更したテストファイルを実行し、全テストが pass することを確認する。

### 削減的（reducing）— テスト/アサーションを削る・緩める

対象: 重複テストの削除、同値テストの統合、過剰詳細アサーションの緩和、テストレベルの移動。

**カバレッジマッピング**: 削る・緩める検証それぞれについて「どのテスト（ファイル:テスト名）が同じ振る舞いを守り続けるか」を明記する。マッピング先が同じ振る舞いを検証していることをコードを読んで確認できるなら、これで証明として足りる。

**マッピング先にできるのは今回のスコープ内のテストだけ**。スコープ外のテストは、たとえ裏取りで実在と内容を確認できても削減の根拠にならない — スコープ外は検証インベントリ・ベースライン実行の対象外で、この実行はその品質も存続も保証していないため。スコープ外にしか根拠が無い削減候補は適用せず、「要ユーザー判断」フラグ付きで計画に残し、報告の未評価注記に含める。

**mutation check**（マッピングを静的に確認しきれない場合は必須）: 削る検証が守っていた振る舞いに対応するプロダクションコードへ代表的な欠陥を一時注入し（条件反転・戻り値の固定・境界のずらし等、最小の変異）、スコープ内の残存テストを実行していずれかが fail することを確認してから復元する。

### 強化的（strengthening）— 検証力を上げる

対象: 弱いアサーションの強化、トートロジー解消、flaky 要因除去。

強化で固定する対象は**契約判定（判断ガイド）を通す**。空洞アサーションを「全フィールドの厳密一致」で置き換えるのは強化ではなく L5 の持ち込みになる — テスト名が掲げる振る舞いと無関係な実装詳細（バージョン文字列・生成メタデータ等）は固定しない。

**red check**: 強化後のアサーションが守る振る舞いをプロダクション側で一時的に壊し、対象テストが fail することを確認して復元し、pass に戻ることも確認する。壊し方が定まらない場合は期待値を一時的に変えて fail を確認する簡易版でも可（証明としては弱いので、結果報告にその旨を書く）。

flaky 修正の検証: 対象テストを3回以上連続実行し（フレームワークが対応していればランダム順・並列オプションも使い）、安定して pass することを確認する。

### 一時変更の復元手順（mutation / red check 共通）

1. 変更前に対象ファイルの内容をコピー保存する（作業ディレクトリへ）。
2. 検証後、保存した内容を書き戻して復元する。**`git checkout` / `git restore` で復元しない** — ユーザーの未コミット変更ごと消す事故を防ぐため。
3. 復元後に `git diff -- <対象ファイル>` で意図しない差分が残っていないことを確認する。

## 2. 局所分類（L系）

単一のテストファイルとその検証対象だけで判定できる分類。surveyor が検出する。

### L1 hollow-assertion — 空洞化したテスト

- 兆候: アサーションが無い（実行して例外が出ないことしか確認していない）/ `toBeTruthy`・not-null・件数のみ等の緩すぎる検証 / 中身を誰も検討していない巨大スナップショット
- 変換: 守るべき振る舞いを特定して意味のあるアサーションへ強化。スナップショットは意味のあるフィールドの明示的検証へ
- 類型: 強化的 / バンド1

### L2 tautology — トートロジー

- 兆候: モックに設定した値をそのまま検証している / ライブラリ・フレームワーク自体の動作を検証している / プロダクションコードをどう壊しても fail し得ない構造
- 変換: 自分のコードの振る舞い検証へ書き換え（強化的）。書き換える対象がそもそも無ければ削除（削減的）
- 類型: 強化的 or 削減的 / バンド1

### L3 flaky-pattern — 不安定要因

- 兆候: 実時刻・タイムゾーン依存 / シード無し乱数 / `sleep` 等の固定時間待ち / テスト間で共有される可変状態 / 実行順序依存 / 外部ネットワーク依存
- 変換: fake timers・時刻注入、シード固定、条件待ちへの置換、状態の分離
- 類型: 強化的 / バンド1

### L4 dead-test — 死んだテスト

- 兆候: skip/xit の放置（理由コメントも期限も無い）/ コメントアウトされたテスト / 削除済み機能のテスト
- 変換: 削除。復活の見込みが読み取れるものは削除せず「報告のみ事項」に回す
- 類型: 削減的（実質的な検証力はすでにゼロ）/ バンド2

### L5 over-specification — 過剰詳細

- 兆候: プロトコルが仕様でないモックの呼び出し回数・引数の網羅的検証 / 意味を持たない DOM 構造の細部（クラス名・タグ階層）への依存 / 一部フィールドしか意味がないのに全体スナップショット / 内部状態への直接アサーション
- 変換: 公開契約（判断ガイド参照）への検証に緩和
- L6 との判別: 1テストが複数の独立した「振る舞い」を検証していれば L6（分割）。テスト名が掲げる振る舞いと無関係な実装詳細（バージョン文字列・生成メタデータ・全フィールド一括固定等）まで検証していれば L5（緩和）。両方に該当する複合ケースでは、分割する際も各フィールドに契約判定を通す — 実装詳細の検証を分割によって「意図的なテスト」に昇格・温存しない
- 類型: 削減的 / バンド2

### L6 eager-test — 1テスト複数振る舞い

- 兆候: 独立した複数の振る舞いを1テストで検証しており、fail したときどれが壊れたか名前から分からない
- 変換: 1テスト1振る舞いに分割
- 類型: 保存的 / バンド3

### L7 obscure-name — 名前が振る舞いを語らない

- 兆候: `test1`・`works`・対象関数名だけ等、fail したとき名前だけで何が壊れたか分からない
- 変換: 「<条件>のとき<期待される振る舞い>」が読み取れる名前へ（プロジェクトの既存の命名スタイルに合わせる）
- 類型: 保存的 / バンド3

### L8 test-logic — テスト内ロジック

- 兆候: テスト内の if/for/try-catch / 期待値をプロダクションと同じロジックの再実装で計算している（実装が間違っていれば期待値も同じように間違う）
- 変換: 直線化、期待値のリテラル固定（同型ケースの列挙になるならパラメタライズも可）
- 類型: 保存的 / バンド3

### L9 magic-values — 意味の見えないテストデータ

- 兆候: 入力と期待値の関係が読み取れない裸のリテラル / 結果に無関係なデータがテストの本質を埋もれさせている
- 変換: 意図の分かる命名・定数化、無関係データのヘルパー既定値への退避（判断ガイドの DAMP/DRY 参照）
- 類型: 保存的 / バンド3

### L10 heavy-setup — 過剰に重い準備

- 兆候: UI 操作経由の状態構築 / 不要な実 I/O / 一部のテストしか使わないのに全テストが払う重い beforeEach / 実タイマー
- 変換: 直接的な状態構築への置換、必要なテストだけが払う準備への移動、fake timers
- 注意: 実依存のテストダブル化（実 DB → インメモリ等）は統合の保証を失うため「要ユーザー判断」を付ける
- 類型: 保存的（ダブル化を含む場合は削減的として扱う）/ バンド3

## 3. 横断分類（C系）

複数ファイルの検証インベントリの突合で見つかる分類。cross-analyzer が検出する。**インベントリは要約で情報が落ちているため、疑いを持ったら必ず両側のソースを読んで裏取りしてから指摘する。**

### C1 layer-duplication — レイヤー間重複

- 兆候: 定義側（関数/コンポーネント自体）のテストと利用側のテストが同じ詳細を検証している
- 変換: 詳細検証を定義側に寄せ、利用側は結合点（正しく繋がっていること）の検証に縮退。定義側にカバレッジが無い場合は削減ではなく「詳細検証の移動」を提案する
- スコープ注意: 裏取りで読んだ相手側のテストがスコープ外にある場合、この重複は「検出・報告のみ」— 削減の根拠にできない（カバレッジマッピングのスコープ内限定ルール）。「要ユーザー判断」フラグを付けて計画に残す
- 類型: 削減的 / バンド2

### C2 setup-duplication — セットアップのコピペ

- 兆候: 複数ファイルに同型の準備コードがあり、差分は一部の値だけ
- 変換: ヘルパー・ファクトリ・ビルダーへの抽出。DAMP/DRY の線引き（判断ガイド）を守る
- 類型: 保存的 / バンド2

### C3 equivalence-duplication — 同値クラス重複

- 兆候: 値が違うだけで同じ同値クラス・同じ振る舞いを検証するテストが複数ある
- 変換: パラメタライズへの統合または削除。境界値は別クラスなので統合しない（判断ガイド）
- 類型: 削減的 / バンド2

### C4 pyramid-violation — テストレベル違反

- 兆候: ユニットテストで検証できる分岐・ロジックを E2E・結合テストで網羅している（遅さの主要因になりやすい）
- 変換: 詳細をユニットレベルへ移し、上位レベルは代表経路の検証に縮退
- 類型: 削減的（移動を伴う）/ バンド3

## 4. 判断ガイド

### 同値クラス判定（C3・L8 の統合判断で必須）

統合・削除の前に、プロダクション側の契約から入力空間の分割を導出する。別クラスの典型: 境界値（最小/最大/±1・空・null・型やサイズの境界）、正常系とエラー系、分岐の各枝。導出できない・確信が持てない場合は統合せず confidence: low で計画に残す。

### 契約判定（L5・C1 の緩和判断で必須）

公開契約 = ドキュメント・型シグネチャ・呼び出し側が実際に依存しているもの。緩めてよいのは実装詳細への依存だけ。ただし相互作用自体が仕様の場合（例: 課金 API をちょうど1回呼ぶこと）はモック検証が契約そのものなので緩めない。判断に迷う要素が1つでもあれば「要ユーザー判断」を付ける。

### DAMP/DRY の線引き（C2・L9 の抽出判断で必須）

テストの結果を左右する値はテスト内に見えるまま残し、結果に無関係な準備だけをヘルパーに隠す。ヘルパーは「無害な既定値＋テストごとの明示上書き」形式（ファクトリ/ビルダー）にし、既定値に検証上の意味を持たせない。抽出後は、テスト本体だけを読んで「何が結果を決めるか」が分かる状態になっているかを確認する。

結果を左右する値を含む準備を抽出する場合の操作手順: (a) 該当値はテスト側から明示的に上書きして渡す、または (b) 名前付き定数として export しテストがその定数をアサーションと併せて参照する、のいずれかで**値の由来をテストから追える形**にする。どちらも取れない（値ごとヘルパーに隠すしかない）抽出は適用せず「要ユーザー判断」で計画に残す。

## 5. 優先度バンド

| バンド | テーマ | 分類 | 理由 |
|-------|--------|------|------|
| 1 | 信頼の回復 | L1, L2, L3 | 偽りの安心（守っていないのに green）と CI 不信は存在自体が害 |
| 2 | コスト削減 | L4, L5, C1, C2, C3 | 変更のたびに保守コストとして課金され続ける |
| 3 | 快適性 | L6, L7, L8, L9, L10, C4 | 改善価値はあるが、後回しにしても害が広がらない |

## 6. 成果物スキーマ

### 検証インベントリ（surveyor がテストファイルごとに1つ、JSON でファイル出力）

```json
{
  "testFile": "packages/billing/src/invoice.test.ts",
  "level": "unit | integration | e2e",
  "targets": ["packages/billing/src/invoice.ts"],
  "setupFingerprint": ["顧客ファクトリ（既定値）", "Stripe クライアントをモック"],
  "behaviors": [
    {
      "name": "テスト名そのまま",
      "line": 42,
      "verifies": "何の振る舞いを検証しているか（対象・条件・期待を含む正規化した一文）",
      "inputClass": "入力の同値クラスの特徴（境界値ならその旨）",
      "assertionStyle": "output | state | interaction | snapshot"
    }
  ]
}
```

`verifies` は突合の要なので、テスト名の写しではなく実装を読んで正規化した記述にする（例: 「請求額が上限超過のとき InvoiceError を投げる」）。横断分析の精度はこの欄の品質で決まる。

### 指摘（surveyor / cross-analyzer がインライン返却）

```json
{
  "category": "L5",
  "files": ["対象ファイル（複数可）"],
  "lines": "該当行の範囲",
  "evidence": "検出の根拠（観察した事実。推測を書かない）",
  "proposal": "提案する変換の具体的説明",
  "type": "preserving | reducing | strengthening",
  "verification": "green | red | mapping | mapping+mutation",
  "confidence": "high | medium | low",
  "notes": "リスク・要ユーザー判断の理由（該当時のみ）"
}
```

### 適用結果（implementer がインライン返却）

```json
{
  "id": "TR-001",
  "status": "applied | skipped | failed",
  "verification": "実施した check と結果（例: red check — 割引率の条件を反転して fail を確認、復元後 pass）",
  "timing": "速度系項目のみ: 前後の実測時間",
  "notes": "skipped/failed の理由、作業中に発見した報告のみ事項"
}
```
