# インフラ・デプロイ設計書を作成する

新規 Web サービス立ち上げ時に、プロジェクト概要書・アーキテクチャ設計書・セキュリティ設計書を入力としてインフラ・デプロイ設計書を対話的に作成する。後続のテスト戦略書、リポジトリ・開発環境設計書、ADR の入力となる。

## 想定する開発

- 小中規模の自社 PoC / 受託開発
- 一般公開せず、契約会社や受託元などの限定公開が主流
- プロジェクト概要書（`docs/project-overview.md`）、アーキテクチャ設計書（`docs/architecture.md`）、セキュリティ設計書（`docs/security.md`）が先に存在する想定

## 重要な制約

- **方針レベルの設計に留める**: 具体的な Terraform コードや IaC マニフェストは対象外。実装時に決定
- **環境構成は dev + prod の 2 環境を基本**: staging が契約要件等で必要な場合のみ追加
- **IaC は必須としない**: PaaS の GUI 設定で十分なケースが多い。ただし採用しない場合でも **設定値のドキュメント化を必須** とする（再現性担保）
- **監視は最小構成を基本**: ヘルスチェック + エラー通知 + PaaS 標準のログ閲覧で十分。複雑な分散トレーシング・APM は PoC には過剰
- **災害復旧（DR）は本格運用フェーズの課題**: 本書ではバックアップ方針のみを扱い、RPO/RTO の定義や復旧手順は対象外。明示的な要件があれば例外的に記載
- **保留を許容する**: 確定できない情報は「保留」として記録。理由・確認事項も残す
- **増分更新**: 各子セクション確定時点でファイルを更新する
- **ADR候補の収集**: ホスティング基盤・IaC ツールの選定など重要な決定は ADR 候補として付録に記録

## 使用方法

```
/infrastructure-design [ホスティングや環境構成で決まっている内容]
```

引数がない場合は入力ドキュメントから進める。

## 作成フロー

### 1. 入力ドキュメントの取得

1. **プロジェクト概要書の検出**: `docs/project-overview.md` の存在を確認
   - 見つかれば読み込み、特に「2.1 アクセス経路」「3.3 前提・制約条件（予算・納期・リージョン）」「5. 非機能要件（可用性・性能）」を抽出
   - 見つからない場合: 他の想定パスも確認。それでもなければ `/project-overview` の先行実行を推奨

2. **アーキテクチャ設計書の検出**: `docs/architecture.md` の存在を確認
   - 見つかれば読み込み、特に「2.1 フロントエンド」「2.2 バックエンド」「2.3 データストア」「2.5 外部サービス」「4. 外部連携」を抽出
   - 見つからない場合: `/architecture-design` の先行実行を推奨。デプロイ単位・ランタイムが未確定では本書のホスティング判断ができない

3. **セキュリティ設計書の検出**: `docs/security.md` の存在を確認
   - 見つかれば読み込み、特に「3.x ネットワーク制約」「5.1 シークレット管理」「7. ロギング・監査の要件」を抽出
   - 見つからない場合: `/security-design` の先行実行を推奨。シークレット保管先・監査ログ保管要件が未確定だと本書の対応箇所が不完全になる

4. **引数があれば** 追加コンテキストとして取り込む

### 2. 既存ファイルの検出と再開判定

デフォルトの保存先（`docs/infrastructure.md`）および他の想定場所に既存のインフラ・デプロイ設計書がないか確認する。

- **既存あり**: 記載状況（確定済み / 保留 / 未着手）を一覧化して提示し、以下から選んでもらう:
  - **続きから再開**: 未着手セクションと保留セクションを順に進める
  - **特定セクションを修正**: セクション番号を指定して該当箇所を再作成
  - **最初からやり直し**: 既存ファイルをバックアップ（`.bak`）した上で新規作成

記載状況の判定基準:
- **確定済み**: 実際の内容が書かれている
- **保留**: 「付録: 保留事項」に該当セクションが記載されている
- **未着手**: テンプレートのプレースホルダー（`[...]`）のまま

- **既存なし**: 新規作成モードで次のステップへ

### 3. 保存場所の決定

以下を提示し確認:

- 推奨: `docs/infrastructure.md`
- 他候補の例: `docs/design/infrastructure.md`、`docs/infra.md`（短縮形）、リポジトリルート直下

確認後、ディレクトリが無ければ作成し、`assets/template.md` をコピーして雛形を配置する。

### 4. 子セクション単位での作成

以下の順で対話的に埋める。**1 セクション確定ごとにファイルを更新する**。

順序は「上流の決定が下流の選択肢を狭める」流れに従う。環境数 → ホスティング → ネットワーク → CI/CD → IaC → 監視 → バックアップ → シークレット管理、の順で確定する。

1. `1.1 環境一覧`
2. `1.2 各環境の用途・差分`
3. `2.1 アプリケーション層`
4. `2.2 データストア層`
5. `2.3 その他のサービス`
6. `3.1 公開範囲`
7. `3.2 内部通信`
8. `4.1 パイプライン構成`
9. `4.2 リリース戦略`
10. `4.3 ロールバック方針`
11. `5.1 IaC 対象範囲`
12. `5.2 ツール`
13. `6.1 監視・アラート`
14. `6.2 ログ集約`
15. `7. バックアップ方針`
16. `8.1 シークレットの保管先`
17. `8.2 ローテーション方針`

#### 各セクションの処理手順

1. **入力ドキュメントからの抽出**: 概要書・アーキテクチャ書・セキュリティ書のうち、このセクションの判断材料となる項目を引用して提示する
   - 例: 2.1 アプリケーション層 → アーキテクチャ書「2.1 フロントエンド」「2.2 バックエンド」（ランタイムとデプロイ単位）
   - 例: 3.1 公開範囲 → 概要書「アクセス経路」、セキュリティ書「ネットワーク制約」
   - 例: 6.2 ログ集約 → セキュリティ書「7.2 ログ保管要件」（保管期間・改ざん防止要件）
   - 例: 8.1 シークレットの保管先 → セキュリティ書「5.1 シークレット管理」（保管方針）
2. **内容案の作成と提示**:
   - 情報が十分にある → 案を作成して提示。ホスティング系では必ず「他候補と落選理由」も併記
   - 情報が不足 → 案・例・観点・確認候補を提示して質問する
3. **3 つの選択肢を常に提示**:
   - **採用**: 案をそのまま / 一部修正で確定
   - **追加情報で再作成**: 提示した質問に回答してもらい、案を作り直す
   - **保留**: このセクションは未確定として記録し、次のセクションへ進む
4. **ファイル更新**:
   - 採用 → 本文の該当セクションを更新
   - 保留 → 本文はプレースホルダーのままにし、「付録: 保留事項」に項目を追記
5. **ADR候補の判定**: 以下のいずれかを満たす決定は「付録: ADR候補」に追記:
   - ホスティング基盤の選定（Vercel vs Cloud Run vs ECS 等）
   - データストアのホスティング方式（マネージド vs セルフホスト）
   - IaC ツールの選定（Terraform / CDK / 不採用 等）
   - リリース戦略（trunk-based / Git Flow 等）
6. 次のセクションへ進む

#### 曖昧な回答へのプッシュバック

下流の設計書で判断材料となる項目は、具体化されていないと手戻りが発生する。以下の粒度の回答があれば、具体化を促してから確定させる:

| セクション | 粒度が粗い回答の例 | 具体化を促す観点 |
|---|---|---|
| 1.1 環境一覧 | 「dev と prod くらい」 | 検証用 staging が必要か（受託で本番リリース前検証が要件のケース）。プレビュー環境（PR ごと）はどうするか |
| 2.1 アプリケーション層 | 「Vercel で」 | プラン（Hobby / Pro）、リージョン、Edge Runtime の使用範囲。ランタイム制約はアーキテクチャ書と整合するか |
| 2.2 データストア層 | 「マネージド DB」 | 具体サービス（Supabase / RDS / Cloud SQL 等）、リージョン、バックアップ機能の有無 |
| 3.1 公開範囲 | 「社内のみ」 | VPN / IP 制限 / Basic 認証 / Cloudflare Access のどれか。誰が管理するか |
| 4.1 パイプライン構成 | 「GitHub Actions で」 | 走らせるジョブ（Lint / 型チェック / Test / Build / Deploy）、並列度、PR 時と main push 時の差 |
| 5.1 IaC 対象範囲 | 「IaC で管理」 | 何を IaC 対象にするか（インフラ全体 / 主要のみ / 不採用）。GUI 設定の場合の設定値ドキュメント化方針 |
| 6.1 監視・アラート | 「監視する」 | 何のメトリクスをアラートにするか（エラー率 / レイテンシ / 外形監視）。通知先（Slack / Email） |
| 7. バックアップ | 「DB バックアップ」 | 取得頻度、保持期間、リストア手順の検証要否 |
| 8.1 シークレット保管先 | 「環境変数」 | どこに保管するか（Vercel Env / GitHub Secrets / AWS Secrets Manager 等）。誰がアクセス可能か |

プッシュバックしても情報が出ない場合は、保留として記録する。

#### セクションごとの出力形式ガイド

| セクション | 推奨形式 | 補足 |
|---|---|---|
| 1.1 環境一覧 | 表（環境名 / 用途 / URL or ホスト） | dev + prod を基本 |
| 1.2 各環境の差分 | 箇条書き | データ、外部連携の差し替え（Sandbox API 等） |
| 2.1 アプリケーション層 | 採用 / 選定理由 / 他候補 の3行構成 | 4〜5行程度。詳細は ADR へ |
| 2.2 データストア層 | 採用 / 選定理由 / 他候補 の3行構成 | アーキテクチャ書「2.3」と整合 |
| 2.3 その他のサービス | 箇条書き | オブジェクトストレージ、キュー、検索基盤等。用途を1文で |
| 3.1 公開範囲 | 1〜3 文 | 採用方式と理由 |
| 3.2 内部通信 | 1〜3 文 or 「該当なし」 | VPC 構成が必要なときのみ |
| 4.1 パイプライン構成 | 箇条書き or 簡易図 | ジョブ一覧、走るタイミング |
| 4.2 リリース戦略 | 1〜3 文 | trunk-based / Git Flow / 環境連動の方式 |
| 4.3 ロールバック方針 | 1〜2 文 | 即時切り戻しの方式（PaaS のリビジョン機能依拠 等） |
| 5.1 IaC 対象範囲 | 1〜3 文 | IaC の有無と対象範囲。不採用なら「設定値ドキュメント化」を明記 |
| 5.2 ツール | 1 文 | 採用ツール、または「PaaS GUI + 設定値ドキュメント」 |
| 6.1 監視・アラート | 箇条書き | 監視項目 / 閾値 / 通知先 |
| 6.2 ログ集約 | 箇条書き | 集約先、保管期間（セキュリティ書要件と整合）、検索手段 |
| 7. バックアップ方針 | 箇条書き | データ種別 / 取得頻度 / 保持期間 |
| 8.1 シークレット保管先 | 箇条書き | サービス、アクセス権限 |
| 8.2 ローテーション方針 | 1〜2 文 or 「不要」 | 必要なら頻度と手順 |

### 5. 完了時の整合性チェック

全セクション完了時に以下を確認し、不整合があれば提示してユーザーに判断を委ねる:

- **アーキテクチャ書のランタイム ↔ 2.1 アプリケーション層**: 採用ホスティングが当該ランタイムをサポートしているか
- **アーキテクチャ書のデータストア ↔ 2.2 データストア層**: ホスティング方式と DB 種別が整合しているか
- **概要書のアクセス経路 ↔ 3.1 公開範囲**: 限定公開の方式が概要書の前提と一致しているか
- **概要書の制約条件（リージョン）↔ 2.x ホスティング**: 採用サービスのリージョンが要件に合致しているか
- **セキュリティ書 7.2 ログ保管要件 ↔ 6.2 ログ集約**: 保管期間・改ざん防止要件が満たせる構成になっているか
- **セキュリティ書 5.1 シークレット管理方針 ↔ 8.1 保管先**: 保管方針と具体的な保管先が整合しているか
- **概要書の非機能要件（可用性・性能）↔ 2.x, 6.x**: 可用性 SLA や性能要件に対し、選定サービスと監視がスケールしているか
- **保留事項の残り**: 残っている保留事項を一覧で提示し、再検討するかを確認

### 6. 完了

以下を案内する:

- ファイルパス
- 「付録: ADR候補」の一覧（後続の ADR スキルへの入力になる）
- 次のステップ（テスト戦略書、リポジトリ・開発環境設計書）。本書を入力として進められる旨を伝える
  - 特にテスト戦略書側で参照する E2E 実行環境（dev / prod）、リポジトリ・開発環境設計書側で参照する CI/CD 設定情報を一覧で提示
- 保留事項が残っている場合は、それを下流ドキュメント作成前に解消すべきか並行して解消するかを併せて提示

## 保留事項の記録フォーマット

本文のセクションはプレースホルダーのままにし、「付録: 保留事項」に以下の形式で追記する:

```markdown
### [セクション番号] 項目名

- **未確定内容**: 何が決まっていないか
- **必要な情報 / 確認事項**: 確認すべきこと、調査が必要な点
- **補足**: ここまでに集まった情報・前提・候補案
```

## ADR候補の記録フォーマット

「付録: ADR候補」に以下の形式で追記する:

```markdown
- [ ] [インフラ判断のタイトル] — 理由: [変更コスト / 議論の余地 / 影響範囲 等]
```

完了時にこの一覧を提示する。後続の ADR 作成スキルがこのリストを入力として詳細化する。

## 使用例

### 例 1: 概要書・アーキテクチャ書・セキュリティ書ありの状態で起動

ユーザー: `/infrastructure-design`

実行:
1. 3 つの上流ドキュメントを検出して読み込み
2. 既存のインフラ設計書なしを確認
3. `docs/infrastructure.md` への保存を確認
4. 1.1 環境一覧から順に対話的に埋める
5. 確定ごとに ADR 候補を判定して付録に追記

### 例 2: 引数付きで起動

ユーザー: `/infrastructure-design Vercel + Supabase で行きたい。dev と prod の 2 環境`

実行:
1. 上流ドキュメントを読み込み
2. 引数を 1.1 環境一覧・2.1 アプリケーション層・2.2 データストア層の初期案として取り込み
3. 各セクションで引数の方向性を案として提示し、上流ドキュメントとの整合性を検証しながら確定

### 例 3: 再開

ユーザー: `/infrastructure-design` (既存のインフラ設計書あり)

実行:
1. 既存ファイルを検出し、状態（確定済み / 保留 / 未着手）を一覧化
2. 「続きから再開 / 特定セクションを修正 / 最初からやり直し」を選択してもらう
3. 選択に応じて進める

## トラブルシューティング

### 上流ドキュメントが存在しない

原因: アーキテクチャ・セキュリティ設計が未着手のままインフラ設計を始めようとしている
解決策: `/architecture-design` および `/security-design` の先行実行を推奨する。特にアーキテクチャ書のデプロイ単位・ランタイム、セキュリティ書のログ要件・シークレット保管方針が未確定では、本書の対応箇所が宙に浮く。続行を希望する場合は、これらの項目を口頭で確認した上で進める

### 過剰なインフラ構成を提案している傾向が見える

原因: 大規模本格運用を前提としたベストプラクティスを引っ張ってきている
解決策: 限定公開・PoC・小中規模を再確認する。「マネージドサービス標準機能で済む範囲」を基本にし、Kubernetes・本格的なオブザーバビリティ・マルチリージョンなどは要件として明示されていない限り採用しない。コストと複雑性は運用負債の源泉になる

### IaC 採用の必要性で悩む

原因: モダン開発として「IaC は当然」という前提が先行している
解決策: PoC・受託の小中規模では PaaS の GUI 設定 + 設定値ドキュメント化で十分なケースが多い。**「設定値の再現性が確保できるか」** を判断軸にする。再現できれば IaC は不要、再現が難しい複雑な構成なら IaC を採用、という順序で考える

### 整合性チェックで多数の不整合が見つかった場合

原因: 上流ドキュメントの決定とインフラ選定が乖離していた、または途中で要件が追加されて初期決定が陳腐化
解決策: 不整合を提示し、どちらを修正するかユーザーに判断を委ねる。アーキテクチャ書側の修正が必要な場合は `/architecture-design`、セキュリティ書側なら `/security-design` の再実行を推奨
