# ディレクトリ構成設計書を作成する

新規 Web サービス立ち上げ時に、アーキテクチャ設計書・リポジトリ・開発環境設計書・テスト戦略書を入力としてパッケージ単位のディレクトリ構成設計書を対話的に作成する。AI による実装フェーズで参照される、ファイル配置の前提資料となる。

## 想定する開発

- 小中規模の自社 PoC / 受託開発
- 一般公開せず、契約会社や受託元などの限定公開が主流
- アーキテクチャ設計書（`docs/architecture.md`）、リポジトリ・開発環境設計書（`docs/repository-environment.md`）が先に存在する想定
- テスト戦略書（`docs/test-strategy.md`）は望ましいが、未作成でも進められる

## 重要な制約

- **パッケージ単位で扱う**: モノレポの場合はパッケージごとに本スキルを実行し、それぞれ独立したファイルを生成する。シングルリポジトリなら 1 回で完結
- **構成スタイルはフレームワーク・パッケージ種別で判断**: feature-based / layer-based / フレームワーク慣習 のいずれかをプロジェクト性質で選ぶ。デフォルトを固定しない
- **テストファイルはコロケーションが基本**: ソースと同じディレクトリに `*.test.ts` を置く。E2E は別配置（`e2e/`, `tests/e2e/` 等）
- **パスエイリアスはデフォルトで導入**: `@/`, `~/` 等。深い相対パス（`../../../`）の発生を防ぐ
- **保留を許容する**: 確定できない情報は「保留」として記録。理由・確認事項も残す
- **増分更新**: 各子セクション確定時点でファイルを更新する
- **ADR候補の収集**: 構成スタイル選定など重要な決定は ADR 候補として付録に記録

## 使用方法

```
/directory-structure [対象パッケージ名や採用したい構成スタイル]
```

引数がない場合は入力ドキュメントから対象パッケージを抽出して確認する。

## 作成フロー

### 1. 入力ドキュメントの取得

1. **アーキテクチャ設計書の検出**: `docs/architecture.md` の存在を確認
   - 見つかれば読み込み、特に「2. 技術スタック」「3.2 レイヤリング・モジュール境界」を抽出
   - 見つからない場合: `/architecture-design` の先行実行を推奨。フレームワーク・パッケージ種別が未確定だと構成方針が決まらない

2. **リポジトリ・開発環境設計書の検出**: `docs/repository-environment.md` の存在を確認
   - 見つかれば読み込み、特に「1.1 構成方針」「1.2 モノレポのトップレベル構成」「3.3 型チェッカ」を抽出
   - モノレポなら対象パッケージ一覧を抽出
   - 見つからない場合: `/repository-environment` の先行実行を推奨

   注: パスエイリアス自体（`@/` のマッピング等）は本書（5.1 パスエイリアス）で初めて定義することが多い。リポジトリ書側に記述がなくても問題ないが、tsconfig の paths 設定方針が記載されている場合はそれと整合させる。

3. **テスト戦略書の検出**: `docs/test-strategy.md` の存在を確認
   - 見つかれば読み込み、特に「2. テストレベル」「5. テストデータとモック」を抽出
   - 見つからない場合: 警告のみ。本書側ではテストファイル配置が「コロケーション（推奨）」のデフォルトに倒れる旨を伝える

4. **引数があれば** 対象パッケージ指定や構成スタイル希望として取り込む

### 2. 対象パッケージの確認

1. **モノレポか判定**: リポジトリ・開発環境設計書の「1.1 構成方針」を確認
2. **対象パッケージの特定**:
   - **シングルリポジトリ**: 唯一のパッケージを対象とする
   - **モノレポ**: 引数で指定があればそれ。なければパッケージ一覧（apps/web, apps/api, packages/shared 等）を提示し、どれを対象にするか確認
3. **対象パッケージの種別確認**:
   - FE app（Next.js / React + Vite / Vue 等）
   - BE app（Hono / Express / FastAPI / Go API 等）
   - 共通ライブラリ（型定義 / ユーティリティ / UIコンポーネント等）
   - CLI ツール
   - その他
4. **採用フレームワーク・主要ライブラリの確認**: アーキテクチャ書から該当パッケージの技術スタックを抽出

これらは後続セクションの選択肢を大きく狭めるため、ここで明確化しておく。

### 3. 既存ファイルの検出と再開判定

対象パッケージに対するディレクトリ構成設計書がないか確認する。

- 推奨保存先: `docs/directory-structure.md`（シングル）、`docs/directory/<package>.md`（モノレポ）
- 他の想定場所: パッケージディレクトリ直下の `DIRECTORY.md`、`docs/<package>-directory.md`

- **既存あり**: 記載状況（確定済み / 保留 / 未着手）を一覧化して提示し、以下から選んでもらう:
  - **続きから再開**: 未着手セクションと保留セクションを順に進める
  - **特定セクションを修正**: セクション番号を指定して該当箇所を再作成
  - **最初からやり直し**: 既存ファイルをバックアップ（`.bak`）した上で新規作成

記載状況の判定基準:
- **確定済み**: 実際の内容が書かれている
- **保留**: 「付録: 保留事項」に該当セクションが記載されている
- **未着手**: テンプレートのプレースホルダー（`[...]`）のまま

- **既存なし**: 新規作成モードで次のステップへ

### 4. 保存場所の決定

以下を提示し確認:

- シングルリポジトリ: `docs/directory-structure.md`
- モノレポ: `docs/directory/<package>.md`（例: `docs/directory/web.md`, `docs/directory/api.md`）
- 他候補: パッケージディレクトリ直下の `DIRECTORY.md`、`docs/<package>-directory.md`

確認後、ディレクトリが無ければ作成し、`assets/template.md` をコピーして雛形を配置する。テンプレートの「対象パッケージ」「採用フレームワーク」は冒頭で記入する。

### 5. 子セクション単位での作成

以下の順で対話的に埋める。**1 セクション確定ごとにファイルを更新する**。

順序は「全体構造 → 詳細規約」の流れ。構成スタイル → トップレベル構成 → サブディレクトリ → 命名規約 → テスト配置 → インポート規約、の順で確定する。

1. `1.1 対象パッケージ`
2. `1.2 採用フレームワーク・パッケージ種別`
3. `2.1 構成スタイル`
4. `2.2 トップレベル構成`
5. `2.3 サブディレクトリ規約`
6. `3.1 ファイル名の形式`
7. `3.2 拡張子の使い分け`
8. `4. テストファイルの配置`
9. `5.1 パスエイリアス`
10. `5.2 相対パス vs 絶対パスの使い分け`

#### 各セクションの処理手順

1. **入力ドキュメントからの抽出**: アーキテクチャ書・リポジトリ書・テスト戦略書のうち、このセクションの判断材料となる項目を引用して提示する
   - 例: 2.1 構成スタイル → アーキテクチャ書「フレームワーク」「3.2 レイヤリング・モジュール境界」、パッケージ種別
   - 例: 2.2 トップレベル構成 → フレームワーク慣習（Next.js なら `app/`, Vite + React なら `src/` 等）
   - 例: 4. テスト配置 → テスト戦略書「2. テストレベル」「2.3 E2Eテスト」（E2E の有無で配置先が変わる）
   - 例: 5.1 パスエイリアス → リポジトリ書「3.3 型チェッカ」（tsconfig の paths 設定との連動）
2. **内容案の作成と提示**:
   - フレームワーク慣習が明確 → 慣習に沿った案を提示し、修正点を確認
   - パッケージ種別から方針が読める → 案を作成して提示
   - 情報が不足 → 案・例・観点・確認候補を提示して質問する
3. **3 つの選択肢を常に提示**:
   - **採用**: 案をそのまま / 一部修正で確定
   - **追加情報で再作成**: 提示した質問に回答してもらい、案を作り直す
   - **保留**: このセクションは未確定として記録し、次のセクションへ進む
4. **ファイル更新**:
   - 採用 → 本文の該当セクションを更新
   - 保留 → 本文はプレースホルダーのままにし、「付録: 保留事項」に項目を追記
5. **ADR候補の判定**: 以下のいずれかを満たす決定は「付録: ADR候補」に追記:
   - 構成スタイル（feature-based / layer-based / フレームワーク慣習）の選定
   - テストファイルの配置方針（コロケーション以外を採用する場合）
   - パスエイリアスの設計（複数エイリアスの定義、特殊な命名）
   - フレームワーク慣習からの大きな逸脱
6. 次のセクションへ進む

#### パッケージ種別・フレームワーク別の構成推奨

各セクションで、パッケージ種別とフレームワークから読み取れる慣習に基づいて推奨を提示する。デフォルトを固定せず、文脈で選ぶ。

| パッケージ種別 / フレームワーク | 構成スタイル傾向 | トップレベル構成例 | テスト配置 |
|---|---|---|---|
| Next.js (App Router) | フレームワーク慣習 + feature-based | `app/`, `components/`, `lib/`, `features/`（任意）| コロケーション、E2E は `e2e/` |
| Next.js (Pages Router) | フレームワーク慣習 + feature-based | `pages/`, `components/`, `lib/`, `features/` | コロケーション、E2E は `e2e/` |
| React + Vite (SPA) | feature-based | `src/features/`, `src/components/`, `src/lib/`, `src/routes/`（ルーティング採用時）| コロケーション、E2E は `e2e/` |
| Vue (Nuxt) | フレームワーク慣習 | `pages/`, `components/`, `composables/`, `server/` | コロケーション |
| Hono / Express (TS) | layer-based | `src/routes/`, `src/services/`, `src/repositories/`, `src/lib/` | コロケーション or `src/__tests__/` |
| FastAPI (Python) | layer-based | `app/api/`, `app/services/`, `app/models/`, `app/core/` | `tests/` トップレベル（pytest 慣習）|
| Go API | layer-based + Go 慣習 | `cmd/`, `internal/`, `pkg/` | `_test.go` を同一ディレクトリ（Go 標準）|
| 共通ライブラリ (TS) | 機能別エクスポート | `src/<feature>/`, `src/index.ts` | コロケーション |
| CLI ツール (TS) | コマンド別 | `src/commands/`, `src/lib/`, `src/index.ts` | コロケーション |

これは推奨の出発点であり、プロジェクト個別の事情で上書きされうる。

#### 曖昧な回答へのプッシュバック

下流の実装フェーズで判断材料となる項目は、具体化されていないと AI が実装時に毎回確認する必要が出る。以下の粒度の回答があれば、具体化を促してから確定させる:

| セクション | 粒度が粗い回答の例 | 具体化を促す観点 |
|---|---|---|
| 2.1 構成スタイル | 「feature-based」 | 「feature」の単位（業務機能 / 画面 / ドメイン）、共通要素の置き場所 |
| 2.2 トップレベル構成 | 「普通の構成で」 | フレームワーク慣習に沿うか / カスタマイズするか、`features/` の有無 |
| 2.3 サブディレクトリ規約 | 「適当に切る」 | feature 内部の標準構成（components / hooks / api / types 等）、共通化の閾値 |
| 3.1 ファイル名の形式 | 「フレームワーク標準で」 | TS/TSX の使い分け、コンポーネント/フック/ユーティリティの命名 |
| 4. テスト配置 | 「コロケーションで」 | E2E の配置、テストヘルパーの置き場所、テストデータ（fixtures）の配置 |
| 5.1 パスエイリアス | 「`@/` で」 | 起点（src 直下 / プロジェクトルート）、複数エイリアス定義の有無 |

プッシュバックしても情報が出ない場合は、保留として記録する。

#### セクションごとの出力形式ガイド

| セクション | 推奨形式 | 補足 |
|---|---|---|
| 1.1 対象パッケージ | 1 行 | パッケージパス（例: `apps/web`） |
| 1.2 採用フレームワーク・種別 | 1〜2 行 | 例: Next.js 14 (App Router), FE app |
| 2.1 構成スタイル | 採用 / 選定理由 / 他候補 の3行構成 | 「feature 単位」の定義も含める |
| 2.2 トップレベル構成 | ツリー図 + 各ディレクトリの 1 行説明 | `src/` 直下のみで十分 |
| 2.3 サブディレクトリ規約 | feature/モジュール内部の標準構成（ツリー or 箇条書き）| 共通化の閾値も明記 |
| 3.1 ファイル名の形式 | 表形式（種別 × 命名規約）| コンポーネント / フック / ユーティリティ / 型定義 |
| 3.2 拡張子の使い分け | 表形式（拡張子 × 用途）| .ts / .tsx / .test.ts / .stories.tsx 等 |
| 4. テスト配置 | 1〜3 文 + 配置例 | ユニット / インテグレーション / E2E の配置を明示 |
| 5.1 パスエイリアス | 表形式（エイリアス × 解決先 × 用途）| tsconfig との対応も明記 |
| 5.2 相対 vs 絶対 | 1〜2 文 | どこで相対、どこで絶対を使うか |

### 6. 完了時の整合性チェック

全セクション完了時に以下を確認し、不整合があれば提示してユーザーに判断を委ねる:

- **アーキテクチャ書のフレームワーク ↔ 2.2 トップレベル構成**: フレームワーク慣習と矛盾していないか（Next.js App Router で `pages/` を作っていないか等）
- **リポジトリ書 3.3 型チェッカ ↔ 5.1 パスエイリアス**: tsconfig の paths 設定方針と整合するか
- **テスト戦略書 2. テストレベル ↔ 4. テスト配置**: E2E の採否とテスト配置が一致しているか（E2E 不採用なのに `e2e/` を作っていないか）
- **テスト戦略書 5. モック方針 ↔ 2.3 サブディレクトリ規約**: Repository パターン採用なら `repositories/` の配置があるか
- **モノレポ採用 ↔ 5.1 パスエイリアス**: モノレポ内パッケージ参照のエイリアス設計が考慮されているか
- **保留事項の残り**: 残っている保留事項を一覧で提示し、再検討するかを確認

### 7. 完了

以下を案内する:

- ファイルパス
- 「付録: ADR候補」の一覧（後続の ADR スキルへの入力になる）
- モノレポで他にもパッケージがある場合、次のパッケージに対して本スキルを再実行する旨を案内
- 保留事項が残っている場合は、それを実装フェーズ前に解消すべきか並行して解消するかを併せて提示

## 保留事項の記録フォーマット

本文のセクションはプレースホルダーのままにし、「付録: 保留事項」に以下の形式で追記する:

```markdown
### [セクション番号] 項目名

- **未確定内容**: 何が決まっていないか
- **必要な情報 / 確認事項**: 確認すべきこと、調査が必要な点
- **補足**: ここまでに集まった情報・前提・候補案
```

## ADR候補の記録フォーマット

「付録: ADR候補」に以下の形式で追記する:

```markdown
- [ ] [ディレクトリ構成判断のタイトル] — 理由: [変更コスト / 議論の余地 / 影響範囲 等]
```

完了時にこの一覧を提示する。後続の ADR 作成スキルがこのリストを入力として詳細化する。

## 使用例

### 例 1: シングルリポジトリで起動

ユーザー: `/directory-structure`

実行:
1. 上流ドキュメントを検出して読み込み
2. シングルリポジトリと判定、唯一のパッケージを対象に確定
3. 既存ファイルなしを確認
4. `docs/directory-structure.md` への保存を確認
5. 1.1 から順に対話的に埋める

### 例 2: モノレポで対象パッケージ指定

ユーザー: `/directory-structure apps/web`

実行:
1. 上流ドキュメントを読み込み（モノレポと判定）
2. 引数で指定された `apps/web` を対象に確定
3. アーキテクチャ書から `apps/web` の技術スタックを抽出
4. `docs/directory/web.md` への保存を確認
5. 1.1 から順に対話的に埋める

### 例 3: 構成スタイル指定で起動

ユーザー: `/directory-structure feature-based で`

実行:
1. 上流ドキュメントを読み込み
2. 対象パッケージを確認
3. 引数を 2.1 構成スタイルの初期案として取り込み、フレームワーク慣習との整合を検証しながら確定

### 例 4: 再開

ユーザー: `/directory-structure` (既存のディレクトリ構成設計書あり)

実行:
1. 既存ファイルを検出し、状態（確定済み / 保留 / 未着手）を一覧化
2. 「続きから再開 / 特定セクションを修正 / 最初からやり直し」を選択してもらう
3. 選択に応じて進める

## トラブルシューティング

### 上流ドキュメントが存在しない

原因: アーキテクチャ・リポジトリ設計が未着手のまま本書を始めようとしている
解決策: `/architecture-design` および `/repository-environment` の先行実行を推奨する。フレームワークが未確定だと構成スタイルが決まらず、リポジトリ構成（モノレポか）が未確定だと保存先・対象パッケージが決まらない

### モノレポで対象パッケージが特定できない

原因: リポジトリ・開発環境設計書のパッケージ一覧が抽象的
解決策: ユーザーに対象パッケージを直接確認する。引数で `apps/web` のように指定してもらうのが確実。複数パッケージを一度に処理しようとせず、1 パッケージずつ実行する

### 過剰に詳細な構成を提案している傾向が見える

原因: 大規模プロジェクトの「あるべき構成」を引っ張ってきている
解決策: 限定公開・PoC・小中規模を再確認する。`features/` の中をさらに `domain/` `application/` `infrastructure/` と DDD 風に細分化するのは多くのケースで過剰。**最低限は: トップレベル（src/ 配下の主要ディレクトリ）+ feature/モジュール内部の標準構成**。それ以上はチームの慣習や既存資産がない限り採用しない

### 構成スタイルで feature-based vs layer-based に迷う

原因: どちらにも理屈があり、判断軸が決まらない
解決策: 判断軸を以下に絞る:
- **画面・機能単位での開発が中心** → feature-based（FE app の多く）
- **同じレイヤーを横断的に変更することが多い**（API のエンドポイント追加で複数のサービス・リポジトリを編集等）→ layer-based（BE app の多く）
- **フレームワークが慣習を強く持つ**（Next.js の `app/`, Nuxt の `pages/`）→ フレームワーク慣習に沿う
- **共通ライブラリ** → 機能別エクスポート（feature-based の軽量版）

### テスト配置でコロケーション以外を希望される

原因: 既存資産で `__tests__/` や `tests/` トップレベル配置の慣習がある
解決策: 既存慣習を尊重して採用する。ただし以下を確認:
- E2E は別配置（`e2e/` か `tests/e2e/`）にする方が整理しやすい
- `__tests__/` を採用する場合、サブディレクトリで階層を保つか平置きするか
- pytest（Python）や Go では言語標準の慣習（`tests/` トップレベル / `_test.go` 同居）に従うのが自然

### パスエイリアスで複雑な設計になっている

原因: 「`@features/`」「`@lib/`」「`@components/`」など複数エイリアスを設計しようとしている
解決策: 単一の `@/` で `src/` 起点とするのが最もシンプルで広く使われる。複数エイリアスは保守コストが上がる割にメリットが薄い。モノレポでパッケージ間参照（`@workspace/shared` 等）が必要な場合のみ複数化を検討
