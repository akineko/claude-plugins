# ADR を作成・運用する

新規 Web サービス立ち上げ時に、各設計書から主要な技術判断を ADR (Architecture Decision Record) として切り出し、運用中の新規判断も継続的に追加する。

## 想定する開発

- 小中規模の自社 PoC / 受託開発
- 一般公開せず、契約会社や受託元などの限定公開が主流
- 各設計書（アーキテクチャ / セキュリティ / インフラ / リポジトリ・開発環境 / ディレクトリ構成 / テスト戦略）が先に存在する想定
- 各設計書の「付録: ADR候補」が初期 ADR の入力源

## 重要な制約

- **軽量版テンプレートを使う**: Michael Nygard の Context / Decision / Alternatives / Consequences を採用。MADR や拡張形式は対象外
- **書きすぎない**: ADR を書く対象は「変更コスト高 / 選定理由が問われる / 他のメンバー・AI が疑問に思う」を満たす決定のみ。自明な選択や実装詳細は対象外。初期セットアップでは **5〜10 件** を目安とする
- **保管場所と命名を統一する**: `docs/adr/` 配下に `NNNN-kebab-case-title.md` 形式で配置。番号は連番、削除はせず Superseded / Deprecated で表現
- **ステータスを最小化する**: Proposed / Accepted / Superseded by NNNN / Deprecated の 4 状態のみ。Draft や Rejected 等は採用しない
- **ファイル削除を禁止する**: 過去の判断は資料価値があるため、不要になったら Deprecated で表現する
- **増分更新**: 個別 ADR は 1 ファイルずつ確定して書き出す。途中保留も許容

## 使用方法

```
/adr [タイトルや概要]
```

- **引数なし** → モード判定ロジックに従って自動判別、必要に応じてユーザーに確認
- **引数あり** → 新規 ADR 追加モードでタイトルや概要として取り込む

## モード判定

起動時に以下の手順でモードを決定する:

1. `docs/adr/README.md` の存在確認
2. `docs/adr/[0-9]*.md` の個別 ADR ファイルを検索

| 状態 | 引数なし時のデフォルト | 引数あり時 |
|---|---|---|
| ガイドなし・ADR なし | **モード A: 初期セットアップ** | モード B（先にガイド作成） |
| ガイドあり・ADR なし | ユーザー確認（A 続き / B / C） | モード B |
| ガイドあり・ADR あり | ユーザー確認（B / C） | モード B |

ユーザーが明示的にモードを指定した場合（例: 「初期セットアップから」「既存を編集したい」）はそれに従う。

## モード A: 初期セットアップ

各設計書の「付録: ADR候補」から主要決定を切り出して ADR ファイル群を生成する。

### A-1. 運用ガイドの作成

1. 保存場所を確認（推奨: `docs/adr/README.md`）
2. ディレクトリがなければ作成
3. `assets/readme-template.md` をコピーして `README.md` を生成
4. プロジェクト名・固有情報があればプレースホルダーを置換

### A-2. 上流設計書の検出

以下のパスを順に確認し、見つかったものから「付録: ADR候補」セクションを抽出する:

- `docs/architecture.md`
- `docs/security.md`
- `docs/infrastructure.md`
- `docs/repository-environment.md`
- `docs/directory-structure.md` または `docs/directory/*.md`（パッケージ別の場合）
- `docs/test-strategy.md`

各設計書について:
- 「付録: ADR候補」セクションが存在 → リストを抽出
- セクションが空 or 形式が異なる → 警告のみ。ユーザーに口頭で挙げてもらう
- 設計書自体がない → 警告のみ。先行作成（`/architecture-design` 等）を推奨するが、続行を希望すれば進める

設計書が一切見つからない場合は、設計書の先行作成を強く推奨し、続行する場合はモード B への切り替えを提案する。

### A-3. ADR 候補の集約と選定

1. 全設計書から抽出した候補を一覧化して提示（後述「重複統合の判断軸」に従って統合）
2. ユーザーと相談して採否を決定:
   - **採用**: ADR 化する
   - **保留**: 後で判断（README の「保留中の候補」に記録）
   - **対象外**: ADR 化しない（書きすぎ防止。後述「典型的な対象外候補」を参照）
3. 採用は **5〜10 件** を目安。大きく超える場合は「重要度の低いものを対象外で良いか」を再確認

#### 重複統合の判断軸

同じ技術選定が複数の設計書から候補として挙がることがある。以下を判断軸として統合可否を決める:

- **同一決定（統合する）**: 同じ技術・同じ選択を、異なる設計書が異なる視点で記述している
  - 例: 「Azure AD SSO の採用」がアーキテクチャ書（認証基盤として）とセキュリティ書（認証方式として）の両方に登場 → 1 つの ADR に統合
  - 例: 「CloudWatch Logs を監査ログ集約基盤に採用」がセキュリティ書とインフラ書の両方に登場 → 1 つの ADR に統合
- **別軸の決定（統合しない）**: 同じドメインだが異なる側面の決定
  - 例: 「ホスティング基盤として ECS Fargate を採用」と「IaC ツールとして CDK を採用」 → どちらも AWS 関連だが別 ADR
  - 例: 「データストアとして RDS PostgreSQL を採用」と「DB 暗号化を RDS 透過暗号化に統一」 → 別 ADR

統合する場合、Context には両方の設計書からの引用を含めるとよい。

#### 典型的な対象外候補

以下は ADR 化を見送るべき候補の例。書きすぎ防止のためフィルタリングする:

- **実装規約レベル**: 「TypeScript の strict 設定の細部」「Conventional Commits の type 一覧」「pre-commit に何を含めるか」など、規約として運用されるが将来覆ることが少ないもの
- **フレームワーク慣習からの逸脱がない決定**: 「Next.js App Router の `app/` 配置」など、慣習通りで疑問の余地が少ないもの
- **後から容易に変えられる決定**: 「ESLint のルール追加」「テストヘルパー関数の配置」など、影響範囲が局所的でリファクタしやすいもの
- **テスト戦略・ディレクトリ構成書由来の規約寄り項目**: 多くは実装規約レベルになる傾向があるため、ADR 化は慎重に判断する

判断に迷う場合は「この決定を 1 年後に振り返る価値があるか」「他のメンバー / AI が `なぜこうしたのか` と疑問を持つ可能性があるか」を考える。

### A-4. 個別 ADR の作成

採用された候補それぞれについて、以下を行う。**1 件確定するごとにファイルを書き出す**（増分更新）。

1. **番号の決定**: 既存 ADR の最大番号 + 1（連番、ゼロ埋め 4 桁）
2. **タイトルの確定**: 短く明確に（例: 「Next.js を採用する」）
3. **ファイル名**: `NNNN-kebab-case-title.md`
   - 日本語タイトルは英訳した上で kebab-case 化（例: 「Next.js を採用する」 → `0001-use-nextjs.md`）
   - ユーザーに最終的なファイル名を確認
4. **本文の埋め込み** (`assets/adr-template.md` を起点):
   - **Context**: 設計書から関連する前提・制約を抽出して案を提示
   - **Decision**: 設計書の決定内容を簡潔に
   - **Alternatives**: 設計書の「他候補と落選理由」を抽出
   - **Consequences**: プラス/マイナス両方の影響。情報がなければユーザーに確認
5. **ステータス**: 設計書で確定済みの決定なので **Accepted** がデフォルト
6. **Date**: `date +%Y-%m-%d` で取得した今日の日付
7. **ユーザー確認後にファイル作成**

### A-5. 完了時の整合性チェック

- 作成した ADR の一覧（番号・タイトル・元の設計書）を README の「ADR 一覧」に追記する
- 保留中の候補があれば README の「保留中の候補」に記録
- 採用候補と元の設計書の対応が取れているかを最終確認

### A-6. 完了

- 作成した ADR ファイル一覧を提示
- 運用フェーズでの追加方法（`/adr [タイトル]`）を案内
- 保留中の候補がある場合、いつ再判断するかをユーザーに促す

## モード B: 新規 ADR 追加

運用中の新規技術判断を 1 件の ADR として作成する。

### B-1. 前提確認

- `docs/adr/README.md` がない場合は、運用ガイドの先行作成を提案。同意があれば A-1 を実行してから本モードに戻る
- 同意がなければ警告したうえで個別 ADR の作成のみ進める

### B-2. タイトルの確定

- 引数があれば、それを初期案として採用。短く明確かを確認
- なければユーザーに確認
- 良い例: 「DB のキャッシュ層に Redis を導入する」「認可ロジックを CASL から自前実装に置き換える」
- 悪い例: 「Redis」「認可の改善」（曖昧すぎる）

### B-3. 番号とファイル名の決定

1. `docs/adr/` 配下の既存 ADR を走査して最大番号を取得し、+1 を新番号とする
2. ファイル名: `NNNN-kebab-case-title.md`
3. ユーザーにファイル名を確認

### B-4. 本文の対話的な作成

以下を順に対話で埋める。**保留可**:

1. **Context**: なぜこの判断が必要になったか、前提・制約は何か
2. **Decision**: 何を選ぶか
3. **Alternatives**: 他に検討した選択肢と落選理由
4. **Consequences**: この決定の結果として生じる影響（プラス/マイナス両方）

各項目の処理:
- 情報が十分 → 案を提示してユーザー確認
- 不足 → 質問して具体化を促す
- どうしても決まらない → Proposed ステータスでファイル化し、後日 Accepted に更新

### B-5. ステータスの確定

- **Accepted**（デフォルト）: チームで合意済みの決定
- **Proposed**: まだ提案段階で議論中

新規作成時に Superseded / Deprecated は選ばない（既存 ADR の改訂で使用）。

### B-6. ファイル作成と完了

`docs/adr/NNNN-kebab-case-title.md` として書き出す。`README.md` の「ADR 一覧」を更新（任意）。

## モード C: 既存 ADR 編集

特定の ADR のステータス変更（Superseded / Deprecated）や内容修正を行う。

### C-1. 対象 ADR の選択

`docs/adr/` 配下の ADR 一覧（番号・タイトル・現在のステータス）を提示し、対象を選択してもらう。

### C-2. 操作の選択

- **Superseded 化**: 後継 ADR の番号を指定してステータスを `Superseded by NNNN` に
- **Deprecated 化**: 後継なしで非推奨化
- **内容修正**: Context / Decision / Alternatives / Consequences の該当箇所を書き換え
- **ステータスのみ変更**: 例: Proposed → Accepted

### C-3. Superseded 化の手順

1. 後継 ADR が既に存在 → そのまま `Superseded by NNNN` に更新
2. 後継 ADR が未作成 → 先にモード B で新規作成。新 ADR の Context に「Supersedes NNNN」を明記してから戻る
3. 旧 ADR のステータスを更新

### C-4. Deprecated 化の手順

1. ステータスを `Deprecated` に更新
2. Consequences の末尾に「Deprecated 理由」を追記

### C-5. ファイル更新

- 該当ファイルを書き換える
- **ファイル名は変更しない**（番号と URL の安定性を保つ）
- **ファイルを削除しない**（過去の判断の資料価値を保つ）
- `README.md` の ADR 一覧を更新（任意）

## ADR 候補抽出のヒント

各設計書の「付録: ADR候補」セクションがある場合は、それを優先的に取り込む。形式が異なる場合や候補が空の場合に備えて、典型的な候補は以下:

| 設計書 | 典型的な ADR 候補 |
|---|---|
| アーキテクチャ | フロント/バックフレームワーク、データストア、認証基盤、外部サービス、通信方式 |
| セキュリティ | 認証方式、データ暗号化方式、シークレット管理基盤 |
| インフラ | ホスティング、IaC ツール、リリース戦略 |
| リポジトリ・開発環境 | モノレポ判断、パッケージマネージャ、Linter/Formatter、ビルドツール |
| ディレクトリ構成 | 構成スタイル、フレームワーク慣習からの逸脱、特殊なエイリアス設計 |
| テスト戦略 | テストランナー、E2E ツール、モック戦略 |

これらは目安であり、実際は各設計書側で記録された候補リストを優先する。

## 命名規約

- **ファイル名**: `NNNN-kebab-case-title.md`
  - NNNN: 4 桁の連番（0001, 0002, ...）
  - title: タイトルを kebab-case 化（小文字 + ハイフン）。日本語は英訳した上で kebab-case 化
  - 例: 「Next.js を採用する」 → `0001-use-nextjs.md`
  - 例: 「DB のキャッシュ層に Redis を導入する」 → `0007-add-redis-cache-layer.md`
- **連番のルール**: 一度割り当てた番号は再利用しない。Superseded / Deprecated でも番号は残す
- **ファイル削除の禁止**: 不要になった ADR は Deprecated で表現する

## 使用例

### 例 1: 初期セットアップ（設計書揃った状態で起動）

ユーザー: `/adr`

実行:
1. `docs/adr/README.md` および ADR ファイルが存在しないことを確認 → モード A
2. 6 つの上流設計書を検出して「付録: ADR候補」を抽出
3. 候補一覧を提示し、ユーザーと相談して 5〜10 件を採用
4. 各候補について Context / Decision / Alternatives / Consequences を埋めて 1 件ずつファイル化
5. 完了時に ADR 一覧と保留中の候補を提示

### 例 2: 単発追加

ユーザー: `/adr DB のキャッシュ層に Redis を導入する`

実行:
1. `docs/adr/` の最大番号 + 1 を取得（例: 既存 8 件 → 0009）
2. ファイル名を `0009-add-redis-cache-layer.md` として確認
3. Context / Decision / Alternatives / Consequences を対話的に埋める
4. ステータス（Accepted / Proposed）を確認
5. ファイル作成して完了

### 例 3: 既存 ADR を Superseded 化

ユーザー: `/adr` （引数なし、既存 ADR あり）

実行:
1. モード判定 → 既存 ADR ありのため、新規追加 / 既存編集 / 再セットアップを確認
2. ユーザー: 「0003 を Superseded 化したい」
3. モード C を選択
4. 後継 ADR の有無を確認
   - なければ先にモード B で新 ADR を作成（例: 0010）
   - 後継ありなら NNNN を取得
5. 0003 のステータスを `Superseded by 0010` に更新
6. 必要に応じて 0010 の Context に「Supersedes 0003」を追記

## トラブルシューティング

### 設計書が存在しない / 「付録: ADR候補」セクションがない

原因: 上流の設計書がない、またはセクション形式が異なる
解決策: 設計書の作成（`/architecture-design` 等）を先に推奨。既に設計済みだが ADR 候補セクションがない場合は、ユーザーに口頭で「変更コスト高な決定を 5〜10 件挙げてもらう」形でモード A を進める

### ADR 候補が多すぎる（10 件を大きく超える）

原因: 設計書の「ADR 候補」が網羅的すぎる、または自明な決定まで含まれている
解決策: 「変更コスト高 / 選定理由が問われる」を満たさないものを対象外にする。ADR は「将来見返したい決定」のみが対象

### 既存 ADR と重複する判断が出てきた

原因: 似た判断を別文脈で再度行っている
解決策: 既存 ADR を確認し、内容が等価なら新規作成せず Consequences 等を追記。新しい状況下で前の決定を覆す場合は Supersede を使う

### Consequences に書く影響が思いつかない

原因: 決定を抽象的に捉えすぎている
解決策: 3 観点で具体化を促す:
- 開発速度への影響（プラス/マイナス）
- 運用コストへの影響
- 将来の変更容易性への影響

### Superseded 後の運用が不明

原因: 古い ADR を消したくなる
解決策: **削除しない**。`Superseded by NNNN` を残すことで、過去の判断と現在の判断の差分が読み取れるようになる。古い ADR は資料としての価値を保つ

### 番号に欠番ができた / 番号衝突

原因: 並列作成、リネーム、誤削除
解決策: 欠番は埋めない（連番の意味を「作成順」と割り切る）。衝突した場合は片方を最大番号 + 1 に振り直し、内容修正だけ行う（ファイル名変更ではなく新規作成として処理し、旧ファイルを削除しない）

### Proposed のまま放置されている ADR がある

原因: 議論が中断したまま忘れられた
解決策: 定期的に Proposed の ADR を棚卸しし、Accepted / Rejected 相当（Deprecated 化）の判断を促す。Rejected の場合は Deprecated ステータス + Consequences に「採用見送り」と理由を記載
