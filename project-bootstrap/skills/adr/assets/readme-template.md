# ADR (Architecture Decision Record)

このディレクトリは本プロジェクトの重要な技術判断を ADR として記録する場所である。

## 目的

重要な技術判断の「なぜ」を残し、将来の変更・引き継ぎ時に判断材料となるようにする。コードや設計書からは読み取れない、選択時の文脈・代替案・トレードオフを保存する。

## ADR を書く対象

以下のいずれかを満たす決定:

- 一度決めると変更コストが高い
- 複数の妥当な選択肢があり、選定理由が問われる
- 他のメンバー / AI が疑問に思う可能性が高い

例: フレームワーク、認証基盤、DB、モノレポ判断、状態管理、E2E ツール

対象外: 自明な選択（HTTPS 必須、TypeScript 採用 等）、実装の細部、後から容易に変えられる選択

## 命名規約

- ファイル: `NNNN-kebab-case-title.md`
  - NNNN: 4 桁の連番（0001, 0002, ...）
  - title: 短く明確に。日本語タイトルは英訳して kebab-case 化
- 一度割り当てた番号は再利用しない
- ファイルの削除は禁止（Deprecated で表現）

## ステータス遷移

```
Proposed ──→ Accepted ──→ Superseded by NNNN
                  └─────→ Deprecated
```

- **Proposed**: 提案段階・議論中
- **Accepted**: 合意済みの決定
- **Superseded by NNNN**: 後続の ADR で置き換えられた
- **Deprecated**: もはや採用されない（後継なし）

## ADR テンプレート

````markdown
# NNNN. タイトル

- **Status**: Accepted
- **Date**: YYYY-MM-DD

## Context

何を判断する必要があったか。前提・制約。

## Decision

何を選んだか。

## Alternatives

検討した他の選択肢と落選理由。

## Consequences

この決定によって生じる影響（プラス/マイナス両方）。
````

## 運用フロー

### 初期セットアップ

主要な設計書（`docs/architecture.md` 等）の「付録: ADR候補」を集約し、5〜10 件の重要決定を ADR 化する。`/adr` コマンドで自動化される。

### 運用中の追加

新たな技術判断が発生したら、`/adr [タイトル]` で 1 件ずつ追加する。

### 既存 ADR の改訂

既存 ADR を覆す決定が必要になった場合は、新しい ADR を作成し、古い ADR の Status を `Superseded by NNNN` に変更する。古い ADR は削除しない。
