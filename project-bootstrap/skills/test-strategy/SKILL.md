# テスト戦略書を作成する

新規 Web サービス立ち上げ時に、プロジェクト概要書・アーキテクチャ設計書・セキュリティ設計書・インフラ設計書を入力としてテスト戦略書を対話的に作成する。後続の機能設計・実装フェーズと ADR の入力となる。

## 想定する開発

- 小中規模の自社 PoC / 受託開発
- 一般公開せず、契約会社や受託元などの限定公開が主流
- プロジェクト概要書（`docs/project-overview.md`）、アーキテクチャ設計書（`docs/architecture.md`）、セキュリティ設計書（`docs/security.md`）、インフラ設計書（`docs/infrastructure.md`）が先に存在する想定
- TDD を前提とした実装が主流。テストはリグレッション検出 + AI による変更時のセーフティネットとして機能させる

## 重要な制約

- **数値目標を設けないことを基本とする**: カバレッジは「クリティカルパス必須」「認可ロジック必須」など、テストすべき領域の言語化を優先。数値目標は受託要件で明示された場合のみ設定
- **E2E は採用任意**: クリティカルパスのみの採用が基本。プロジェクト性質によっては不採用も選択肢として残す
- **モック方針は2系統を許容**: 「レイヤー別（データアクセス・認可は実DB、ビジネスロジックはモック可）」を基本としつつ、Repository パターン + DI による全モックも選択肢として提示
- **書きすぎないテスト**: PoC・小中規模では「すべてに対するテスト」は逆効果。クリティカルパス・認可・複雑なビジネスロジックを優先
- **保留を許容する**: 確定できない情報は「保留」として記録。理由・確認事項も残す
- **増分更新**: 各子セクション確定時点でファイルを更新する
- **ADR候補の収集**: 主要なテストツール選定（テストランナー / E2Eツール）など重要な決定は ADR 候補として付録に記録

## 使用方法

```
/test-strategy [テスト方針やツールで決まっている内容]
```

引数がない場合は入力ドキュメントから進める。

## 作成フロー

### 1. 入力ドキュメントの取得

1. **プロジェクト概要書の検出**: `docs/project-overview.md` の存在を確認
   - 見つかれば読み込み、特に「2.2 主要ユースケース」「4. 機能要件」「5. 非機能要件」を抽出
   - 見つからない場合: 他の想定パスも確認。それでもなければ `/project-overview` の先行実行を推奨。クリティカルパスが定まらないと E2E スコープが決まらない

2. **アーキテクチャ設計書の検出**: `docs/architecture.md` の存在を確認
   - 見つかれば読み込み、特に「1. システム概要」「3. 主要な構造方針」「4. 外部連携」を抽出
   - 見つからない場合: `/architecture-design` の先行実行を推奨。技術スタック・通信方式が未確定だとテストランナー・E2Eツールが決まらない

3. **セキュリティ設計書の検出**: `docs/security.md` の存在を確認
   - 見つかれば読み込み、特に「3. 認可」「6. アプリケーションセキュリティ」を抽出
   - 見つからない場合: 警告のみ。本書側では認可ロジックの必須テスト領域に影響する旨を伝える

4. **インフラ設計書の検出**: `docs/infrastructure.md` の存在を確認
   - 見つかれば読み込み、特に「1. 環境構成」「4. CI/CD」を抽出
   - 見つからない場合: 警告のみ。本書側では E2E の実行環境と CI 連携に影響する旨を伝える

5. **引数があれば** 追加コンテキストとして取り込む

### 2. 既存ファイルの検出と再開判定

デフォルトの保存先（`docs/test-strategy.md`）および他の想定場所に既存のテスト戦略書がないか確認する。

- **既存あり**: 記載状況（確定済み / 保留 / 未着手）を一覧化して提示し、以下から選んでもらう:
  - **続きから再開**: 未着手セクションと保留セクションを順に進める
  - **特定セクションを修正**: セクション番号を指定して該当箇所を再作成
  - **最初からやり直し**: 既存ファイルをバックアップ（`.bak`）した上で新規作成

記載状況の判定基準:
- **確定済み**: 実際の内容が書かれている
- **保留**: 「付録: 保留事項」に該当セクションが記載されている
- **未着手**: テンプレートのプレースホルダー（`[...]`）のまま

- **既存なし**: 新規作成モードで次のステップへ

### 3. 保存場所の決定

以下を提示し確認:

- 推奨: `docs/test-strategy.md`
- 他候補の例: `docs/testing.md`、`docs/qa.md`、リポジトリルート直下

確認後、ディレクトリが無ければ作成し、`assets/template.md` をコピーして雛形を配置する。

### 4. 子セクション単位での作成

以下の順で対話的に埋める。**1 セクション確定ごとにファイルを更新する**。

順序は「方針 → レベルごとのスコープ → ツール → カバレッジ・モック → CI → 維持」の流れに従う。

1. `1.1 テストの目的`
2. `1.2 全体方針`
3. `2.1 ユニットテスト`
4. `2.2 インテグレーションテスト`
5. `2.3 E2E テスト` (採否を含めて確認)
6. `3.1 テストランナー・アサーション・モック`
7. `3.2 E2E ツール` (E2E 採用時のみ)
8. `4.1 計測対象と目標値`
9. `4.2 必ずテストすべき領域`
10. `4.3 テスト不要・除外領域`
11. `5.1 テストデータの管理`
12. `5.2 外部依存のモック方針`
13. `6.1 実行タイミング`
14. `6.2 品質ゲート`
15. `7.1 flaky test への対応方針`

#### 各セクションの処理手順

1. **入力ドキュメントからの抽出**: 上流ドキュメントから、このセクションの判断材料となる項目を引用して提示する
   - 例: 1.1 目的 → 概要書「5. 非機能要件（信頼性関連）」、TDD 採用方針
   - 例: 2.3 E2E → 概要書「2.2 主要ユースケース」のうちクリティカルなものを特定
   - 例: 3.1 テストランナー → アーキテクチャ書「2.1/2.2 フロントエンド・バックエンド」のフレームワーク
   - 例: 4.2 必須領域 → セキュリティ書「3. 認可」、概要書「2.2 主要ユースケース」
   - 例: 5.2 モック方針 → アーキテクチャ書「3.2 レイヤリング」「4. 外部連携」
   - 例: 6.1 実行タイミング → インフラ書「4.1 パイプライン構成」
2. **内容案の作成と提示**:
   - 情報が十分にある → 案を作成して提示。ツール系では必ず「他候補と落選理由」も併記
   - 情報が不足 → 案・例・観点・確認候補を提示して質問する
3. **3 つの選択肢を常に提示**:
   - **採用**: 案をそのまま / 一部修正で確定
   - **追加情報で再作成**: 提示した質問に回答してもらい、案を作り直す
   - **保留**: このセクションは未確定として記録し、次のセクションへ進む
4. **ファイル更新**:
   - 採用 → 本文の該当セクションを更新
   - 保留 → 本文はプレースホルダーのままにし、「付録: 保留事項」に項目を追記
5. **ADR候補の判定**: 以下のいずれかを満たす決定は「付録: ADR候補」に追記:
   - テストランナーの選定（Vitest / Jest / Playwright Test 等の主要選定）
   - E2E ツールの選定（Playwright / Cypress / Puppeteer 等）
   - モック方針の方向性（実DB併用 vs Repository+DI 全モック）
   - カバレッジ目標値の設定（数値目標を採用した場合）
   - 認可ロジックのテスト戦略（実DB必須 / DI でモック可能 等）
6. 次のセクションへ進む

#### 2.3 E2E テストの特殊な処理

2.3 は他セクションと異なり、**採否の判断**（E2E を採用するか）と、採用時の**詳細埋め**（対象シナリオ・実行環境）の 2 段構えになる。混乱を避けるため以下の順で進める:

1. まず採否を確認（「E2E を採用しますか？」）
2. **採用する場合**: 対象シナリオ・実行環境について「採用 / 追加情報で再作成 / 保留」の通常フローで埋める。3.2 E2E ツールも続けて埋める
3. **採用しない場合**: 「不採用」の理由を 1〜2 行で記録し、3.2 はスキップ（「該当なし」と記載）

採否そのものを保留にすることも可能（後日決定）。その場合は 2.3 全体を保留扱いとし、3.2 もスキップ。

#### 言語・フレームワークに応じた推奨提示

ツール選定セクション（特に 3.x）では、**アーキテクチャ書の技術スタックに合わせた推奨** を提示する。デフォルトを固定せず、文脈で選ぶ。

| 文脈 | テストランナーの傾向 | E2E ツールの傾向 | モック / DB の傾向 |
|---|---|---|---|
| TypeScript / Vite | Vitest（Vite との親和性）| Playwright | MSW（API モック）/ Testcontainers |
| TypeScript / Next.js | Vitest / Jest（FW標準） | Playwright | MSW / Prisma の DB 接続切替 |
| TypeScript / Hono / Node API | Vitest / node:test | Playwright API テスト | Testcontainers / SQLite メモリ |
| Python / FastAPI | pytest | Playwright（必要時） | pytest-mock / Testcontainers |
| Go | testing 標準 + testify | Playwright（必要時） | gomock / Testcontainers |
| Rust | cargo test | （UI 不在なら不要） | mockall |

これは推奨の出発点であり、プロジェクト個別の事情（既存資産・チーム慣習・契約要件）で上書きされうる。

#### 曖昧な回答へのプッシュバック

下流（実装フェーズ）で判断材料となる項目は、具体化されていないと手戻りが発生する。以下の粒度の回答があれば、具体化を促してから確定させる:

| セクション | 粒度が粗い回答の例 | 具体化を促す観点 |
|---|---|---|
| 1.1 目的 | 「品質を上げるため」 | 何を最も重視するか（リグレッション検出 / TDD駆動 / AI変更のセーフティ / 契約要件 等） |
| 2.1 ユニット | 「主要ロジック」 | 対象範囲（ピュアな関数 / クラスのメソッド / フック等の挙動）、テスト粒度 |
| 2.3 E2E | 「主要シナリオ」 | 採否、採用するなら 2〜5 本のクリティカルパスをユースケース名で特定 |
| 3.1 テストランナー | 「Vitest / Jest」 | 設定の出発点（FW標準 / 独自）、カバレッジ計測ツール（c8 / istanbul 等）の同梱 |
| 3.2 E2E ツール | 「Playwright」 | ブラウザ範囲（Chromium のみ等）、実行環境（CI / ローカル / プレビュー環境） |
| 4.1 カバレッジ | 「80%」 | 計測対象（行 / 分岐）、対象モジュール、しきい値の運用（CI ブロック / 警告） |
| 4.2 必須領域 | 「ビジネスロジック」 | 具体的な機能・モジュール名、認可・データ整合性の取り扱い |
| 5.2 モック方針 | 「適宜モック」 | レイヤーごとの判断基準、DB をどう扱うか（実DB / インメモリ / DI で差替）、外部 API のスタブ方法 |
| 6.1 実行タイミング | 「CI で」 | PR / main push / 定期、E2E をどこで走らせるか、所要時間の許容範囲 |
| 6.2 品質ゲート | 「テスト失敗でブロック」 | カバレッジ未達の扱い、flaky test の暫定許容、強制マージ運用 |

プッシュバックしても情報が出ない場合は、保留として記録する。

#### セクションごとの出力形式ガイド

| セクション | 推奨形式 | 補足 |
|---|---|---|
| 1.1 テストの目的 | 1〜3 行 + 重視する目的の優先順位 | リグレッション検出 / TDD / AI セーフティ / 契約要件 等 |
| 1.2 全体方針 | 1〜3 行 | テストピラミッドのバランスや「書かないテスト」の方針 |
| 2.1 ユニットテスト | 対象 / 粒度 / 規模感 | ピュア関数中心か、結合テスト寄りか |
| 2.2 インテグレーションテスト | 対象 / 範囲 / DB の扱い | 認可ロジックの扱いを明記 |
| 2.3 E2E テスト | 採否 / 対象シナリオ / 実行環境 | 不採用なら理由を1〜2 行で。採用なら 2〜5 本のシナリオ名 |
| 3.1 テストランナー他 | 採用 / 選定理由 / 他候補 | 4〜5 行 |
| 3.2 E2E ツール | 採用 / 選定理由 / 他候補 | E2E 採用時のみ。不採用時は「該当なし」 |
| 4.1 計測対象と目標値 | 1〜3 行 | 「数値目標は設けない（必須領域で代替）」と明記してよい |
| 4.2 必須領域 | 箇条書き | クリティカルパス、認可ロジック、複雑なビジネスロジック等 |
| 4.3 除外領域 | 箇条書き | 自動生成コード、フレームワーク提供部、UI のスタイル等 |
| 5.1 テストデータ | 1〜3 行 | fixtures / ファクトリ / シード戦略 |
| 5.2 モック方針 | レイヤーごとの方針表 / 1 段落 | レイヤー別 vs Repository+DI 全モックを明示 |
| 6.1 実行タイミング | 箇条書き | PR / push / nightly などの分担 |
| 6.2 品質ゲート | 1〜3 行 | テスト失敗・カバレッジ未達の扱い |
| 7.1 flaky 対応 | 1〜3 行 | 検出・隔離・再現方針 |

### 5. 完了時の整合性チェック

全セクション完了時に以下を確認し、不整合があれば提示してユーザーに判断を委ねる:

- **概要書の主要ユースケース ↔ 2.3 E2E 対象 / 4.2 必須領域**: クリティカルパスがテストでカバーされる流れになっているか
- **アーキテクチャ書のフレームワーク ↔ 3.1 テストランナー**: フレームワーク標準と矛盾していないか（例: Next.js で Vitest を選ぶ場合の設定負荷など）
- **アーキテクチャ書の通信方式 ↔ 2.2 インテグレーション範囲**: API テストのレベル（HTTP 経由 / 関数直叩き）が決まっているか
- **アーキテクチャ書のレイヤリング ↔ 5.2 モック方針**: レイヤー別モックの場合、レイヤー境界が定まっているか
- **セキュリティ書 3. 認可 ↔ 4.2 必須領域 / 5.2 モック方針**: 認可ロジックが必須領域に含まれ、テスト時の DB 扱いが整合しているか
- **インフラ書 1. 環境構成 ↔ 2.3 E2E 実行環境**: E2E をどの環境（dev / staging / preview）で走らせるかが整合しているか
- **インフラ書 4.1 パイプライン ↔ 6.1 実行タイミング**: CI で実行する内容に齟齬がないか
- **保留事項の残り**: 残っている保留事項を一覧で提示し、再検討するかを確認

### 6. 完了

以下を案内する:

- ファイルパス
- 「付録: ADR候補」の一覧（後続の ADR スキルへの入力になる）
- 次のステップ（機能設計・実装フェーズ）。本書を入力として進められる旨を伝える
  - 特に実装時のテストファイル配置はディレクトリ構成設計書（`docs/directory-structure.md` または `docs/directory/<package>.md`）の「テストファイル配置」と整合させること
- 保留事項が残っている場合は、それを実装開始前に解消すべきか並行して解消するかを併せて提示

## 保留事項の記録フォーマット

本文のセクションはプレースホルダーのままにし、「付録: 保留事項」に以下の形式で追記する:

```markdown
### [セクション番号] 項目名

- **未確定内容**: 何が決まっていないか
- **必要な情報 / 確認事項**: 確認すべきこと、調査が必要な点
- **補足**: ここまでに集まった情報・前提・候補案
```

## ADR候補の記録フォーマット

「付録: ADR候補」に以下の形式で追記する:

```markdown
- [ ] [テスト戦略判断のタイトル] — 理由: [変更コスト / 議論の余地 / 影響範囲 等]
```

完了時にこの一覧を提示する。後続の ADR 作成スキルがこのリストを入力として詳細化する。

## 使用例

### 例 1: 上流ドキュメント揃った状態で起動

ユーザー: `/test-strategy`

実行:
1. 4 つの上流ドキュメントを検出して読み込み
2. 既存のテスト戦略書なしを確認
3. `docs/test-strategy.md` への保存を確認
4. 1.1 テストの目的から順に対話的に埋める
5. 確定ごとに ADR 候補を判定して付録に追記

### 例 2: 引数付きで起動

ユーザー: `/test-strategy Vitest と Playwright で、E2E はクリティカルパス3本のみ`

実行:
1. 上流ドキュメントを読み込み
2. 引数を 2.3 E2E・3.1 テストランナー・3.2 E2E ツールの初期案として取り込み
3. 各セクションで引数の方向性を案として提示し、上流ドキュメントとの整合性を検証しながら確定

### 例 3: 再開

ユーザー: `/test-strategy` (既存のテスト戦略書あり)

実行:
1. 既存ファイルを検出し、状態（確定済み / 保留 / 未着手）を一覧化
2. 「続きから再開 / 特定セクションを修正 / 最初からやり直し」を選択してもらう
3. 選択に応じて進める

## トラブルシューティング

### 上流ドキュメントが存在しない

原因: 概要書・アーキテクチャ設計が未着手のまま本書を始めようとしている
解決策: 最低でも `/project-overview` と `/architecture-design` の先行実行を推奨する。概要書のクリティカルパスが定まらないと E2E スコープが決まらず、アーキテクチャ書の技術スタックが定まらないとテストツール選定が浮く。続行を希望する場合は、これらの項目を口頭で確認した上で進める

### E2E の採否で悩む

原因: 「E2E はあるべき」という前提と「PoC では不要」の間で判断軸が決まらない
解決策: 判断軸を以下に絞る:
- **クリティカルパスが 1〜3 本に明確に定まっている** → E2E 採用（その本数だけ）
- **限定公開・短期運用・UI が薄い** → E2E 不採用も合理的
- **長期運用予定 / 多機能 / リグレッション検出が重要** → E2E 採用
書きすぎると保守負担になるため、採用するなら本数を絞る

### カバレッジ目標値で悩む

原因: 「カバレッジ何%が適切か」に固執している
解決策: PoC・小中規模では **数値目標を設けず、必須領域の言語化** に集中する。受託で「カバレッジ 80% 以上」が契約要件として明示されている場合のみ数値目標を設定する。それ以外は「クリティカルパス必須」「認可ロジック必須」「複雑なビジネスロジック必須」と言語化したほうが効果的

### モック方針で悩む

原因: 「実DBと向き合う重さ」と「全モックの脆さ」のトレードオフで判断軸が決まらない
解決策: 判断軸を以下に絞る:
- **DB スキーマの変更頻度が高い / マイグレーションを含めて検証したい** → レイヤー別（データアクセス・認可は実DB）
- **Repository パターンを採用していて DI が整理されている / テストの実行速度を最優先** → Repository + DI 全モック
- **どちらも採用しづらい中間** → レイヤー別を基本に、認可ロジックのみ実DB で他はモック可能、というハイブリッド
判断後は 5.2 でレイヤーごとのモック方針表を作って明示する

### 過剰なテストセットを提案している傾向が見える

原因: 「あるべきテスト構成」を引っ張ってきている（unit / integration / contract / e2e / performance / a11y / visual regression のフルセット等）
解決策: 限定公開・PoC・小中規模を再確認する。**必須は: ユニット + 認可・クリティカルパスのインテグレーション**。それ以外は要件として明示されない限り採用しない。Visual regression や Performance テストは運用フェーズで必要になったら追加

### 整合性チェックで多数の不整合が見つかった場合

原因: 上流ドキュメントの決定とテスト戦略が乖離していた、または途中で要件が追加されて初期決定が陳腐化
解決策: 不整合を提示し、どちらを修正するかユーザーに判断を委ねる。アーキテクチャ書側の修正が必要な場合は `/architecture-design`、セキュリティ書側なら `/security-design`、インフラ書側なら `/infrastructure-design` の再実行を推奨
