# プロジェクト概要書を作成する

新規 Web サービスの立ち上げ時に、技術選定・アーキテクチャ設計・セキュリティ設計・インフラ設計・テスト戦略などの下流ドキュメントへの入力となる概要書を、対話的に作成する。

## 想定する開発

- 小中規模の自社 PoC / 受託開発
- 一般公開せず、契約会社や受託元などの限定公開が主流
- 機能設計に入る前の準備段階ドキュメント群の 1 つとして利用される

## 重要な制約

- **技術選定や設計判断は行わない**: このフェーズは情報を揃えることが目的。技術選定は下流ドキュメントで行う
- **曖昧さへの対処**: 技術判断に直結する項目（ロール、アクセス経路、データ機密度、制約等）で粒度が粗い回答があれば、具体化を促す。それでも出ない場合は保留として記録する
- **保留を許容する**: 確定できない情報は「保留」として記録。同時に、確認方法や前提の情報も残す
- **増分更新**: 各子セクション確定時点でファイルを更新する。会話が中断されても作業が失われないように

## 使用方法

```
/project-overview [プロジェクトの概要や決まっている内容]
```

引数がない場合は入力を求める。

## 作成フロー

### 1. 初期コンテキストの取得

1. 引数があればそれを初期入力として使う
2. 引数がなければ以下の順で確認:
   - 既存の企画書・要件書・議事録などがあるか？（あればパスを聞いて読み込む）
   - なければプロジェクトの概要を 1〜2 段落で説明するよう求める

### 2. 既存ファイルの検出と再開判定

デフォルトの保存先（`docs/project-overview.md`）および他の想定場所に既存の概要書がないか確認する。

- **既存あり**: 記載状況（確定済み / 保留 / 未着手）を一覧化して提示し、以下から選んでもらう:
  - **続きから再開**: 未着手セクションと保留セクションを順に進める
  - **特定セクションを修正**: セクション番号を指定して該当箇所を再作成
  - **最初からやり直し**: 既存ファイルをバックアップ（`.bak`）した上で新規作成

記載状況の判定基準:
- **確定済み**: 実際の内容が書かれている
- **保留**: 「付録: 保留事項」に該当セクションが記載されている
- **未着手**: テンプレートのプレースホルダー（`[...]`）のまま

- **既存なし**: 新規作成モードで次のステップへ。

### 3. 保存場所の決定

以下を提示し確認:

- 推奨: `docs/project-overview.md`
- 他候補の例: `docs/requirements/project-overview.md`、リポジトリルート直下

確認後、ディレクトリが無ければ作成し、`assets/template.md` をコピーして雛形を配置する。

### 4. 子セクション単位での作成

以下の順で対話的に埋める。**1 セクション確定ごとにファイルを更新する**（途中で中断されても作業が残るため）。

1. `1.1 目的`
2. `1.2 成功基準`
3. `2.1 想定利用者（ロール・アクセス経路・扱うデータ）`
4. `2.2 主要ユースケース`
5. `3.1 対応範囲`
6. `3.2 対象外（明示）`
7. `3.3 前提・制約条件`
8. `4.1 機能一覧`
9. `4.2 優先度（MVP / v1 / 将来）`
10. `5. 非機能要件`

#### 各セクションの処理手順

1. **情報の抽出**: 初期コンテキスト・既存ファイル・これまでの対話から、このセクションに該当する情報を抽出する
2. **内容案の作成と提示**:
   - 情報が十分にある → 案を作成して提示
   - 情報が不足 → 案・例・考え方・PM への確認候補を提示して質問する
3. **3 つの選択肢を常に提示**:
   - **採用**: 案をそのまま / 一部修正で確定
   - **追加情報で再作成**: 提示した質問に回答してもらい、案を作り直す
   - **保留**: このセクションは未確定として記録し、次のセクションへ進む
4. **ファイル更新**:
   - 採用 → 本文の該当セクションを更新
   - 保留 → 本文はプレースホルダーのままにし、「付録: 保留事項」に項目を追記
5. 次のセクションへ進む

#### 曖昧な回答へのプッシュバック

技術選定・セキュリティ設計・インフラ設計で判断材料となる項目は、具体化されていないと下流で手戻りが発生する。以下の粒度の回答があれば、具体化を促してから確定させる:

| セクション | 粒度が粗い回答の例 | 具体化を促す観点 |
|---|---|---|
| 1.1 目的 | 「業務効率化」「生産性向上」 | 具体的にどの業務のどの部分か？何が改善されるのか？ |
| 2.1 ロール | 「社内ユーザー」「一般ユーザー」 | 具体的な部署・役職・人数感。外部委託者は含むか |
| 2.1 アクセス経路 | 未指定 | 社内網 / VPN / 招待制公開URL / SSO (Azure AD, Google Workspace 等) / 認証なし |
| 2.1 扱うデータ | 未指定 | 個人情報 / 機密情報 / 業務データ / 公開情報。機密度のレベル |
| 3.3 制約条件 | 「特になし」 | 納期・予算・既存システム連携・必須技術・法令・契約条件は本当にないか |
| 5. 非機能要件 | 「高い可用性」「十分な性能」 | 具体的な目標値や水準（同時接続数、応答時間、稼働率など） |

プッシュバックしても情報が出ない場合は、保留として記録する（この場合も「具体化に必要な観点」を保留事項の補足として残す）。

#### セクションごとの出力形式ガイド

| セクション | 推奨形式 | 補足 |
|---|---|---|
| 1.1 目的 | 1〜3 文の散文 | テンプレ: 「[誰] が [何] できるようにすることで [課題] を解決する」 |
| 1.2 成功基準 | 箇条書き | 定性で可、定量があれば尚良い |
| 2.1 想定利用者 | ロールごとのサブセクション | 各ロールに「概要」「アクセス経路」「扱う主要データと機密度」を記載 |
| 2.2 主要ユースケース | 箇条書き | 「[ロール] が [何] をする」の形式。クリティカルパスと頻度の高い操作のみ、3〜10 個を目安 |
| 3.1 対応範囲 | 箇条書き | |
| 3.2 対象外 | 箇条書き | 期待されがちだが対象外のものを明示（例: モバイルアプリ版、多言語化、管理者機能） |
| 3.3 前提・制約条件 | 箇条書き | 期間・予算・既存システム連携・必須技術・法令・契約条件など |
| 4.1 機能一覧 | 箇条書き | 機能名＋1 文程度の説明 |
| 4.2 優先度 | MVP / v1 / 将来 にグループ化 | 4.1 の機能名を参照する形で記載 |
| 5. 非機能要件 | 観点ごとの見出し + 箇条書き | 性能・可用性・セキュリティ・保守性・拡張性 |

### 5. 完了時の整合性チェック

全セクション完了時に以下を確認し、不整合があれば提示してユーザーに判断を委ねる:

- **ロール ↔ 機能**: 2.1 のロールが 4.1 の機能のアクターとして登場しているか
- **ユースケース ↔ 機能**: 2.2 のユースケースが 4.1 の機能でカバーされているか
- **制約 ↔ 非機能要件**: 3.3 の制約と 5 の非機能要件に矛盾はないか
- **対象外 ↔ 機能**: 3.2 対象外と 4.1 機能に矛盾はないか
- **保留事項の残り**: 残っている保留事項を一覧で提示し、再検討するかを確認

### 6. 完了

ファイルパスを案内し、次のステップ（技術選定・アーキテクチャ設計・セキュリティ設計・インフラ設計・テスト戦略など）への引き継ぎを促す。保留事項が残っている場合は、それが下流ドキュメント作成前に解消すべきか、並行して解消するかも併せて提示する。

## 保留事項の記録フォーマット

本文のセクションはプレースホルダーのままにし、「付録: 保留事項」に以下の形式で追記する:

```markdown
### [セクション番号] 項目名

- **未確定内容**: 何が決まっていないか
- **必要な情報 / 確認事項**: PM や関係者に聞くべきこと、調査が必要な点
- **補足**: ここまでに集まった情報・前提・候補案
```

保留事項は再開時や下流ドキュメント作成時に「未解決の論点リスト」として機能する。情報が薄くても記録を残すこと（検討の出発点として価値がある）。

## 使用例

### 例 1: 引数付きで起動

ユーザー: `/project-overview 社内の経費精算ワークフローシステム。申請者と承認者ロール。既存人事システム連携あり`

実行:
1. 引数を初期コンテキストとして取得
2. 既存ファイルなしを確認
3. `docs/project-overview.md` への保存を確認
4. 1.1 から順に対話的に埋める

### 例 2: 引数なしで起動

ユーザー: `/project-overview`

実行:
1. 既存の企画書・要件書の有無を確認
2. あれば読み込み、なければ概要を説明するよう求める
3. 保存場所を確認し、テンプレートを配置
4. 各セクションを対話的に埋める

### 例 3: 再開

ユーザー: `/project-overview` (既存の概要書あり)

実行:
1. 既存ファイルを検出し、状態（確定済み / 保留 / 未着手）を一覧化
2. 「続きから再開 / 特定セクションを修正 / 最初からやり直し」を選択してもらう
3. 選択に応じて進める

## トラブルシューティング

### 情報がほとんどない状態での起動

原因: プロジェクト初期で PM からの情報も未整備
解決策: 各セクションで積極的に保留を活用する。完成する概要書は不完全でも、「PM や関係者に確認すべき事項の一覧」として価値を持つ。確認事項を揃えた上で一度 PM とすり合わせるよう促す

### 技術的な詳細を書きたがる場合

原因: 開発者視点で技術選定を先取りしてしまう
解決策: 技術選定は下流で行うことを伝え、3.3 前提・制約条件 には「使用必須と指定された技術」のみ記載するよう誘導する。その他の技術案はこのドキュメントとは別にメモしてもらう

### 整合性チェックで多数の不整合が見つかった場合

原因: セクション間の情報の乖離、または後半で理解が深まり初期情報が陳腐化している
解決策: 不整合を提示し、どちら側を修正するかユーザーに判断を委ねる。大幅な修正が必要な場合は、該当セクションを再作成することを提案する
