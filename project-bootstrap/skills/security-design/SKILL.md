# セキュリティ設計書を作成する

新規 Web サービス立ち上げ時に、プロジェクト概要書とアーキテクチャ設計書を入力としてセキュリティ設計書を対話的に作成する。後続のインフラ・デプロイ設計書、テスト戦略書、ADR の入力となる。

## 想定する開発

- 小中規模の自社 PoC / 受託開発
- 一般公開せず、契約会社や受託元などの限定公開が主流
- プロジェクト概要書（`docs/project-overview.md` 等）とアーキテクチャ設計書（`docs/architecture.md` 等）が先に存在する想定

## 重要な制約

- **方針レベルの設計に留める**: 具体実装（CSPヘッダの値、Cookie属性の指定等）は対象外。実装時に決定
- **ログ実装の詳細はインフラ書側**: 本書では監査要件のみを定義する。ログ集約基盤・保管期間の具体構成はインフラ・デプロイ設計書側で扱う
- **詳細な脅威モデリングは行わない**: 限定公開・小中規模を前提に、簡易な脅威リストで進める。STRIDE 等のフレームワーク準拠が契約要件にある場合のみ拡張する
- **保留を許容する**: 確定できない情報は「保留」として記録。理由・確認事項も残す
- **増分更新**: 各子セクション確定時点でファイルを更新する。会話が中断されても作業が失われないように
- **ADR候補の収集**: 認証基盤・暗号化方式など重要な選定はADR候補として付録に記録

## 使用方法

```
/security-design [セキュリティ要件や決まっている内容]
```

引数がない場合は入力ドキュメントから進める。

## 作成フロー

### 1. 入力ドキュメントの取得

1. **プロジェクト概要書の検出**: `docs/project-overview.md` の存在を確認
   - 見つかれば読み込み、特に「2.1 想定利用者（ロール・アクセス経路・扱うデータ）」「3.3 前提・制約条件」「5. 非機能要件のセキュリティ項目」を抽出
   - 見つからない場合: 他の想定パスも確認。それでもなければ `/project-overview` の先行実行を推奨

2. **アーキテクチャ設計書の検出**: `docs/architecture.md` の存在を確認
   - 見つかれば読み込み、特に「2.3 データストア」「2.4 認証基盤」「2.5 外部サービス」「4. 外部連携」を抽出
   - 見つからない場合: `/architecture-design` の先行実行を推奨。アーキテクチャ未確定では認証基盤・データ保護の整合判断ができない

3. **引数があれば** 追加コンテキストとして取り込む

### 2. 既存ファイルの検出と再開判定

デフォルトの保存先（`docs/security.md`）および他の想定場所に既存のセキュリティ設計書がないか確認する。

- **既存あり**: 記載状況（確定済み / 保留 / 未着手）を一覧化して提示し、以下から選んでもらう:
  - **続きから再開**: 未着手セクションと保留セクションを順に進める
  - **特定セクションを修正**: セクション番号を指定して該当箇所を再作成
  - **最初からやり直し**: 既存ファイルをバックアップ（`.bak`）した上で新規作成

記載状況の判定基準:
- **確定済み**: 実際の内容が書かれている
- **保留**: 「付録: 保留事項」に該当セクションが記載されている
- **未着手**: テンプレートのプレースホルダー（`[...]`）のまま

- **既存なし**: 新規作成モードで次のステップへ

### 3. 保存場所の決定

以下を提示し確認:

- 推奨: `docs/security.md`
- 他候補の例: `docs/design/security.md`、リポジトリルート直下

確認後、ディレクトリが無ければ作成し、`assets/template.md` をコピーして雛形を配置する。

### 4. 子セクション単位での作成

以下の順で対話的に埋める。**1 セクション確定ごとにファイルを更新する**。

順序は「前提を固めてから個別領域へ」「認証→認可の自然な流れ」に従う。

1. `1.1 セキュリティ要件`
2. `1.2 想定する主要な脅威`
3. `2.1 認証方式`
4. `2.2 セッション管理`
5. `2.3 多要素認証の要否`
6. `3.1 ロール定義`
7. `3.2 権限マトリクス`
8. `3.3 認可判定の実装方針`
9. `4.1 通信路の暗号化`
10. `4.2 保管時の暗号化`
11. `4.3 PII・機密データの取り扱い`
12. `4.4 データ保持期間と削除方針`
13. `5.1 シークレット管理`
14. `5.2 認証情報の保管`
15. `6.1 OWASP Top 10 対応方針`
16. `6.2 依存関係の脆弱性管理`
17. `6.3 CSP / CORS / Cookie 設定方針`
18. `7.1 監査対象操作`
19. `7.2 ログ保管要件`

#### 各セクションの処理手順

1. **入力ドキュメントからの抽出**: 概要書・アーキテクチャ設計書のうち、このセクションの判断材料となる項目を引用して提示する
   - 例: 2.1 認証方式 を作るときは概要書の「アクセス経路」とアーキテクチャ書の「認証基盤」を引用
   - 例: 4.2 保管時の暗号化 を作るときは概要書の「扱うデータ機密度」とアーキテクチャ書の「データストア」を引用
2. **内容案の作成と提示**:
   - 情報が十分にある → 案を作成して提示
   - 情報が不足 → 案・例・観点・確認候補を提示して質問する
3. **3 つの選択肢を常に提示**:
   - **採用**: 案をそのまま / 一部修正で確定
   - **追加情報で再作成**: 提示した質問に回答してもらい、案を作り直す
   - **保留**: このセクションは未確定として記録し、次のセクションへ進む
4. **ファイル更新**:
   - 採用 → 本文の該当セクションを更新
   - 保留 → 本文はプレースホルダーのままにし、「付録: 保留事項」に項目を追記
5. **ADR候補の判定**: 以下のいずれかを満たす決定は「付録: ADR候補」に追記:
   - 認証方式・認可方式の選定（自前 vs SaaS、SSO 統合方式 等）
   - 暗号化方式の選定（カラム単位暗号化 vs DB 透過暗号化 等）
   - シークレット管理基盤の選定
6. 次のセクションへ進む

#### 曖昧な回答へのプッシュバック

下流の設計書で判断材料となる項目は、具体化されていないと手戻りが発生する。以下の粒度の回答があれば、具体化を促してから確定させる:

| セクション | 粒度が粗い回答の例 | 具体化を促す観点 |
|---|---|---|
| 1.1 セキュリティ要件 | 「特に指定なし」 | 契約・法令由来の要件は本当にないか（保管リージョン、監査ログ、ISMS 等） |
| 1.2 主要な脅威 | 「不正アクセス全般」 | 限定公開を踏まえて、具体的に何が起きると困るか（権限昇格 / データ漏洩 / なりすまし 等） |
| 2.1 認証方式 | 「ログイン機能あり」 | SSO / メール+パスワード / マジックリンク / IP制限 のいずれか。IdP（Azure AD / Google Workspace 等）は何か |
| 3.1 ロール定義 | 「管理者と一般ユーザー」 | 権限差は具体的に何か。読み取り / 書き込み / 設定変更 / 他ユーザー管理 |
| 4.2 保管時の暗号化 | 「暗号化する」 | DB 全体の透過暗号化か、特定カラムの個別暗号化か。鍵管理はどこか |
| 5.1 シークレット管理 | 「環境変数で管理」 | どこに保管するか（Vercel Env / GitHub Secrets / AWS Secrets Manager 等）。.env のコミット防止策は |
| 7.1 監査対象操作 | 「重要な操作」 | 認証イベント / 権限変更 / 機密データの操作 のうちどれを記録するか |

プッシュバックしても情報が出ない場合は、保留として記録する。

#### セクションごとの出力形式ガイド

| セクション | 推奨形式 | 補足 |
|---|---|---|
| 1.1 セキュリティ要件 | 箇条書き | 契約・法令・ISMS 等、外部由来の要件を列挙 |
| 1.2 主要な脅威 | 箇条書き（5〜10 個） | 各脅威に「対策方針 1 行」を併記 |
| 2.1 認証方式 | 1〜3 文 | アーキテクチャ書の認証基盤と整合させる |
| 2.2 セッション管理 | 箇条書き | 有効期限、無効化、リフレッシュ方針 |
| 2.3 多要素認証 | 1〜2 文 | 要否と方式（要なら） |
| 3.1 ロール定義 | ロールごとのサブセクション | 概要書のロールを引き継いで詳細化 |
| 3.2 権限マトリクス | 表（ロール × リソース × アクション） | 主要なリソース 5〜10 個に絞る |
| 3.3 認可判定の実装方針 | 1〜3 文 | どのレイヤーでチェックするか（ミドルウェア / リソース層 / DB ポリシー） |
| 4.1〜4.2 暗号化 | 1〜2 文ずつ | TLS 強制、保管時暗号化の方式 |
| 4.3 PII 取り扱い | 箇条書き | 収集データ、利用目的、共有先の方針 |
| 4.4 保持期間 | 表（データ種別 × 保持期間 × 削除方針） | |
| 5.1〜5.2 機密情報管理 | 箇条書き | 保管先、ローテーション、ハッシュアルゴリズム |
| 6.1 OWASP 対応 | 箇条書き（観点ごと） | 詳細実装は省略、対応する旨の方針のみ |
| 6.2 依存脆弱性 | 1〜2 文 | Dependabot / Renovate 等の自動化方針 |
| 6.3 CSP/CORS/Cookie | 1〜3 文 | 方針のみ。具体値は実装時 |
| 7.1 監査対象操作 | 箇条書き | 認証イベント、権限変更、機密データ操作 等 |
| 7.2 ログ保管要件 | 箇条書き | 保管期間・改ざん防止要件のみ。実装はインフラ書 |

### 5. 完了時の整合性チェック

全セクション完了時に以下を確認し、不整合があれば提示してユーザーに判断を委ねる:

- **概要書のデータ機密度 ↔ データ保護**: 機密度の高いデータに対し 4 章の保護策が十分か
- **概要書のアクセス経路 ↔ 認証方式**: アクセス経路（VPN / SSO / 公開 URL）と 2.1 認証方式が整合しているか
- **アーキテクチャ書の認証基盤 ↔ 2.1 認証方式**: 採用認証基盤の機能で実現できる方式になっているか
- **アーキテクチャ書のデータストア ↔ 4.2 保管時暗号化**: 採用 DB の機能で実現できる暗号化方式になっているか
- **アーキテクチャ書の外部連携 ↔ 5.1 シークレット管理**: 連携先の認証情報がシークレット管理対象に含まれているか
- **概要書の非機能要件（セキュリティ）↔ 全体**: 概要書の要件すべてが本書でカバーされているか
- **保留事項の残り**: 残っている保留事項を一覧で提示し、再検討するかを確認

### 6. 完了

以下を案内する:

- ファイルパス
- 「付録: ADR候補」の一覧（後続のADRスキルへの入力になる）
- 次のステップ（インフラ・デプロイ設計書、テスト戦略書）。本書を入力として進められる旨を伝える
  - 特にインフラ書側で実装すべき項目（ログ保管基盤、シークレット保管先、ネットワーク制約）を一覧で提示
- 保留事項が残っている場合は、それを下流ドキュメント作成前に解消すべきか並行して解消するかを併せて提示

## 保留事項の記録フォーマット

本文のセクションはプレースホルダーのままにし、「付録: 保留事項」に以下の形式で追記する:

```markdown
### [セクション番号] 項目名

- **未確定内容**: 何が決まっていないか
- **必要な情報 / 確認事項**: 確認すべきこと、調査が必要な点
- **補足**: ここまでに集まった情報・前提・候補案
```

## ADR候補の記録フォーマット

「付録: ADR候補」に以下の形式で追記する:

```markdown
- [ ] [セキュリティ判断のタイトル] — 理由: [変更コスト / 議論の余地 / 影響範囲 等]
```

完了時にこの一覧を提示する。後続のADR作成スキルがこのリストを入力として詳細化する。

## 使用例

### 例 1: 概要書・アーキテクチャ書ありの状態で起動

ユーザー: `/security-design`

実行:
1. `docs/project-overview.md` と `docs/architecture.md` を検出して読み込み
2. 既存のセキュリティ設計書なしを確認
3. `docs/security.md` への保存を確認
4. 1.1 セキュリティ要件から順に対話的に埋める
5. 確定ごとにADR候補を判定して付録に追記

### 例 2: 引数付きで起動

ユーザー: `/security-design Azure AD でのSSOが必須。監査ログは1年保管`

実行:
1. 入力ドキュメントを読み込み
2. 引数を 1.1 セキュリティ要件・2.1 認証方式の制約として取り込み
3. 各セクションを対話的に埋める

### 例 3: 再開

ユーザー: `/security-design` (既存のセキュリティ設計書あり)

実行:
1. 既存ファイルを検出し、状態（確定済み / 保留 / 未着手）を一覧化
2. 「続きから再開 / 特定セクションを修正 / 最初からやり直し」を選択してもらう
3. 選択に応じて進める

## トラブルシューティング

### 概要書・アーキテクチャ書が存在しない

原因: 上流ドキュメントを作成せずにセキュリティ設計から始めようとしている
解決策: `/project-overview` および `/architecture-design` の先行実行を推奨する。特にアーキテクチャ書の認証基盤・データストアが未確定では本書の判断ができない。続行を希望する場合は、これらの項目を口頭で確認した上で進める

### セキュリティ要件が「特に指定なし」と言われた場合

原因: PM やクライアントから明示的な要件が提示されていない
解決策: 受託・限定公開で「ない」ケースは少ない。以下を確認するよう促す:
- 契約書・SLA に記載のセキュリティ条項
- 取り扱う個人情報の有無（あれば個人情報保護法）
- 業界・取引先固有のコンプライアンス要件（ISMS、PマークSOC2 等）
- 過去類似プロジェクトで指定された要件

### 過剰な対策を提案している傾向が見える

原因: 一般公開サービスを前提としたベストプラクティスを引っ張ってくる
解決策: 限定公開・PoC であることを再確認する。総当たり攻撃対策・DDoS 対策など外部由来の脅威は、ネットワーク制限（VPN/IP 制限）で大部分が緩和されることを思い出す。コストに見合う対策に絞る

### 整合性チェックで多数の不整合が見つかった場合

原因: アーキテクチャ書の決定とセキュリティ要件が乖離していた、または後半で要件が追加されて初期決定が陳腐化
解決策: 不整合を提示し、どちらを修正するかユーザーに判断を委ねる。アーキテクチャ書側に修正が必要な場合は、`/architecture-design` の再実行を推奨
