# リポジトリ・開発環境設計書を作成する

新規 Web サービス立ち上げ時に、プロジェクト概要書・アーキテクチャ設計書・セキュリティ設計書・インフラ設計書を入力としてリポジトリ・開発環境設計書を対話的に作成する。後続のディレクトリ構成設計書、テスト戦略書、ADR の入力となる。

## 想定する開発

- 小中規模の自社 PoC / 受託開発
- 一般公開せず、契約会社や受託元などの限定公開が主流
- プロジェクト概要書（`docs/project-overview.md`）、アーキテクチャ設計書（`docs/architecture.md`）、セキュリティ設計書（`docs/security.md`）、インフラ設計書（`docs/infra.md`）が先に存在する想定

## 重要な制約

- **プロジェクト全体の静的な土台のみを扱う**: パッケージ内部のディレクトリ構成・命名規約は対象外（後続の `directory-structure` スキルで扱う）
- **リポジトリ構成はプロジェクト性質で判断**: 「複数アプリ or 共通パッケージあり」がモノレポ採用の閾値。デフォルトは決め打ちしない
- **Linter / Formatter は言語・フレームワークに応じた推奨を提示**: Biome / ESLint+Prettier / フレームワーク標準のいずれかを文脈で選ぶ。デフォルトを固定しない
- **ブランチ戦略はインフラ設計書と分担**: 概要のみ本書に記載し、CI/CD と連動する詳細はインフラ設計書側で扱う
- **ローカル `.env` 運用のみを扱う**: 本番のシークレット保管先はインフラ設計書、保管方針はセキュリティ設計書側
- **保留を許容する**: 確定できない情報は「保留」として記録。理由・確認事項も残す
- **増分更新**: 各子セクション確定時点でファイルを更新する
- **ADR候補の収集**: モノレポ判断・主要ツール選定など重要な決定は ADR 候補として付録に記録

## 使用方法

```
/repository-environment [リポジトリ構成やツールで決まっている内容]
```

引数がない場合は入力ドキュメントから進める。

## 作成フロー

### 1. 入力ドキュメントの取得

1. **プロジェクト概要書の検出**: `docs/project-overview.md` の存在を確認
   - 見つかれば読み込み、特に「3.3 前提・制約条件」を抽出（言語縛り、既存資産との互換性、納期等）
   - 見つからない場合: 他の想定パスも確認。それでもなければ `/project-overview` の先行実行を推奨

2. **アーキテクチャ設計書の検出**: `docs/architecture.md` の存在を確認
   - 見つかれば読み込み、特に「2. 技術スタック（FE/BE/DB）」「3.2 レイヤリング・モジュール境界」を抽出
   - 見つからない場合: `/architecture-design` の先行実行を推奨。技術スタックが未確定だとツールチェインが決まらない

3. **セキュリティ設計書の検出**: `docs/security.md` の存在を確認
   - 見つかれば読み込み、特に「5.1 シークレット管理」「6. アプリケーションセキュリティ」を抽出
   - 見つからない場合: 警告のみ。本書側ではローカル `.env` と pre-commit のシークレット検出方針に影響する旨を伝える

4. **インフラ設計書の検出**: `docs/infra.md` の存在を確認
   - 見つかれば読み込み、特に「4.1 パイプライン構成」「4.2 リリース戦略」「8.1 シークレット保管先」を抽出
   - 見つからない場合: 警告のみ。本書側ではブランチ戦略の概要記述に影響する旨を伝える

5. **引数があれば** 追加コンテキストとして取り込む

### 2. 既存ファイルの検出と再開判定

デフォルトの保存先（`docs/repository-environment.md`）および他の想定場所に既存のリポジトリ・開発環境設計書がないか確認する。

- **既存あり**: 記載状況（確定済み / 保留 / 未着手）を一覧化して提示し、以下から選んでもらう:
  - **続きから再開**: 未着手セクションと保留セクションを順に進める
  - **特定セクションを修正**: セクション番号を指定して該当箇所を再作成
  - **最初からやり直し**: 既存ファイルをバックアップ（`.bak`）した上で新規作成

記載状況の判定基準:
- **確定済み**: 実際の内容が書かれている
- **保留**: 「付録: 保留事項」に該当セクションが記載されている
- **未着手**: テンプレートのプレースホルダー（`[...]`）のまま

- **既存なし**: 新規作成モードで次のステップへ

### 3. 保存場所の決定

以下を提示し確認:

- 推奨: `docs/repository-environment.md`
- 他候補の例: `docs/dev-environment.md`、`docs/repo-setup.md`、リポジトリルート直下

確認後、ディレクトリが無ければ作成し、`assets/template.md` をコピーして雛形を配置する。

### 4. 子セクション単位での作成

以下の順で対話的に埋める。**1 セクション確定ごとにファイルを更新する**。

順序は「上流の決定が下流の選択肢を狭める」流れに従う。リポジトリ構成 → ツールチェイン → 品質ツール → Git運用 → Hooks → エディタ → ローカル環境変数、の順で確定する。

1. `1.1 構成方針`
2. `1.2 モノレポのトップレベル構成` (モノレポ採用時のみ)
3. `2.1 ランタイム・バージョン管理`
4. `2.2 パッケージマネージャ`
5. `2.3 ビルドツール`
6. `2.4 タスクランナー`
7. `3.1 Linter`
8. `3.2 Formatter`
9. `3.3 型チェッカ`
10. `3.4 共通設定の管理方針` (モノレポ採用時のみ重要)
11. `4.1 ブランチ戦略の概要`
12. `4.2 コミットメッセージ規約`
13. `4.3 .gitignore 方針`
14. `5.1 採用ツール` (Git Hooks)
15. `5.2 pre-commit で実行する内容`
16. `5.3 commit-msg で実行する内容`
17. `6.1 .editorconfig`
18. `6.2 推奨拡張機能`
19. `6.3 開発コンテナ`
20. `7.1 .env 運用方針`
21. `7.2 .env.example の管理`

#### 各セクションの処理手順

1. **入力ドキュメントからの抽出**: 概要書・アーキテクチャ書・セキュリティ書・インフラ書のうち、このセクションの判断材料となる項目を引用して提示する
   - 例: 1.1 構成方針 → アーキテクチャ書「全体構成（FE/BE/共通ライブラリの数）」、概要書「制約条件」
   - 例: 2.1 ランタイム → アーキテクチャ書「2.1 フロントエンド」「2.2 バックエンド」のランタイム
   - 例: 3.x コード品質ツール → アーキテクチャ書の言語・フレームワーク
   - 例: 4.1 ブランチ戦略 → インフラ書「4.2 リリース戦略」（trunk-based / Git Flow 等との整合）
   - 例: 5.2 pre-commit → セキュリティ書「5.1 シークレット管理」「6. アプリケーションセキュリティ」（シークレット検出の必要性）
   - 例: 7.1 `.env` 運用 → インフラ書「8.1 シークレット保管先」（ローカルと本番の保管先の対応関係）
2. **内容案の作成と提示**:
   - 情報が十分にある → 案を作成して提示。ツール系では必ず「他候補と落選理由」も併記
   - 情報が不足 → 案・例・観点・確認候補を提示して質問する
3. **3 つの選択肢を常に提示**:
   - **採用**: 案をそのまま / 一部修正で確定
   - **追加情報で再作成**: 提示した質問に回答してもらい、案を作り直す
   - **保留**: このセクションは未確定として記録し、次のセクションへ進む
4. **ファイル更新**:
   - 採用 → 本文の該当セクションを更新
   - 保留 → 本文はプレースホルダーのままにし、「付録: 保留事項」に項目を追記
5. **ADR候補の判定**: 以下のいずれかを満たす決定は「付録: ADR候補」に追記:
   - リポジトリ構成（モノレポ vs シングル / マルチリポ）
   - パッケージマネージャの選定（pnpm vs npm vs bun 等）
   - ビルドツール / タスクランナーの選定（Turborepo / Nx 等の構造的影響が大きいもの）
   - Linter / Formatter の選定（Biome 一本化 vs ESLint+Prettier 等、影響が広いもの）
   - 型チェッカの設定方針（TypeScript の strict 設定など、コード全体に影響するもの）
6. 次のセクションへ進む

#### 言語・フレームワークに応じた推奨提示

ツール選定セクション（特に 2.x, 3.x, 5.x）では、**アーキテクチャ書の技術スタックに合わせた推奨** を提示する。デフォルトを固定せず、文脈で選ぶ。

| 文脈 | パッケージマネージャの傾向 | Linter/Formatter の傾向 | Hooks ツールの傾向 |
|---|---|---|---|
| TypeScript / Next.js / React | pnpm（モノレポ）/ npm（シングル）| Biome（新規・速度優先）/ ESLint+Prettier（既存資産・FW標準）| lefthook / simple-git-hooks |
| TypeScript / Hono / Node API | pnpm / npm | Biome / ESLint+Prettier | lefthook |
| Python / FastAPI | uv / Poetry | Ruff（lint+format 一本）| pre-commit (Python) |
| Go | （標準）| gofmt + golangci-lint | lefthook / pre-commit |
| Rust | cargo（標準）| rustfmt + clippy | lefthook |

これは推奨の出発点であり、プロジェクト個別の事情（既存資産・チーム慣習・契約要件）で上書きされうる。

#### 曖昧な回答へのプッシュバック

下流の設計書で判断材料となる項目は、具体化されていないと手戻りが発生する。以下の粒度の回答があれば、具体化を促してから確定させる:

| セクション | 粒度が粗い回答の例 | 具体化を促す観点 |
|---|---|---|
| 1.1 構成方針 | 「モノレポで」 | アプリ/パッケージの想定数、共通ライブラリの想定、ツール（Turborepo / Nx / pnpm workspaces 等） |
| 1.1 構成方針 | 「普通のシングル」 | 将来のモバイル / CLI / 共通ライブラリ追加予定の有無 |
| 2.1 ランタイム | 「Node.js」 | バージョン（LTS の特定 minor）、固定方法（Volta / mise / .nvmrc） |
| 2.2 パッケージマネージャ | 「npm でいい」 | ロックファイル運用、モノレポでの workspace 機能要否 |
| 2.3 ビルドツール | 「フレームワーク標準で」 | 具体ツール名、カスタム設定の予定 |
| 3.1 Linter | 「ESLint」 | 設定の出発点（recommended / airbnb / プロジェクト独自）、自動修正運用 |
| 3.3 型チェッカ | 「TypeScript」 | strict / strictNullChecks / noUncheckedIndexedAccess 等の具体設定 |
| 4.1 ブランチ戦略 | 「GitHub Flow」 | 環境連動（main → prod / dev → staging）、リリース時のタグ運用 |
| 4.2 コミット規約 | 「Conventional Commits」 | type 一覧、scope の使い方、検証する範囲（本人 / CI） |
| 5.2 pre-commit | 「Lint かける」 | 対象ファイル（変更分のみ / 全体）、実行コマンド、シークレット検出の有無 |
| 7.1 `.env` 運用 | 「.env で管理」 | コミットしない方針の徹底（.gitignore 確認）、複数環境（.env.local, .env.development）の使い分け |

プッシュバックしても情報が出ない場合は、保留として記録する。

#### セクションごとの出力形式ガイド

| セクション | 推奨形式 | 補足 |
|---|---|---|
| 1.1 構成方針 | 採用 / 選定理由 / 他候補 の3行構成 | モノレポなら採用ツールも記載 |
| 1.2 モノレポのトップレベル構成 | ツリー図 + 1〜3 行の方針 | `apps/` `packages/` 等の切り分け方針。詳細はディレクトリ構成設計書 |
| 2.1 ランタイム | 採用 / バージョン / 固定方法 | 例: Node.js 20 LTS, Volta で固定 |
| 2.2 パッケージマネージャ | 採用 / 選定理由 / 他候補 | 4〜5 行 |
| 2.3 ビルドツール | 採用 / 選定理由 | 1〜3 行。フレームワーク標準なら明記 |
| 2.4 タスクランナー | 採用 / 選定理由 | npm scripts 直で十分なケース多数 |
| 3.1 Linter | 採用 / 設定出発点 / 自動修正方針 | Biome なら 3.2 と統合可 |
| 3.2 Formatter | 採用 / 設定出発点 / 適用範囲 | Biome 採用時は「3.1と一本化」と記載 |
| 3.3 型チェッカ | 採用 / strict 設定 / 検証タイミング | 言語が型なしなら「該当なし」 |
| 3.4 共通設定の管理方針 | 1〜3 文 | モノレポでの設定共有（共通 config パッケージ等）。シングルなら「該当なし」 |
| 4.1 ブランチ戦略の概要 | 1〜3 文 | インフラ書のリリース戦略との関係を明記 |
| 4.2 コミットメッセージ規約 | 採用規約 / type一覧 / 検証 | Conventional Commits なら type と scope を例示 |
| 4.3 .gitignore 方針 | 箇条書き | 必ず除外する種別（.env、ビルド成果物、ローカル設定） |
| 5.1 採用ツール (Git Hooks) | 採用 / 選定理由 | Husky / lefthook / simple-git-hooks 等 |
| 5.2 pre-commit | 箇条書き | 実行ジョブと対象ファイル |
| 5.3 commit-msg | 1〜2 文 or 「該当なし」 | 規約検証など |
| 6.1 .editorconfig | 1〜2 文 + 主要設定 | 採否と主要項目（インデント、改行コード等） |
| 6.2 推奨拡張機能 | 箇条書き | `.vscode/extensions.json` の主要項目 |
| 6.3 開発コンテナ | 1〜2 文 or 「該当なし」 | devcontainer 採否と理由 |
| 7.1 .env 運用方針 | 箇条書き | ファイル名、コミット禁止、複数環境の使い分け |
| 7.2 .env.example の管理 | 1〜2 文 | キー一覧の同期方針 |

### 5. 完了時の整合性チェック

全セクション完了時に以下を確認し、不整合があれば提示してユーザーに判断を委ねる:

- **アーキテクチャ書のランタイム ↔ 2.1 ランタイム**: バージョン整合性（FE/BE で異なる場合は両方に対応できる管理ツールを選定しているか）
- **アーキテクチャ書のフレームワーク ↔ 2.3 ビルドツール / 3.x 品質ツール**: フレームワーク標準と矛盾していないか
- **インフラ書のリリース戦略 ↔ 4.1 ブランチ戦略**: 例えば trunk-based を採用しているのに Git Flow を選んでいないか
- **インフラ書の CI 構成 ↔ 5.2 pre-commit**: pre-commit で実行する項目が CI と重複しすぎていないか / 過不足はないか
- **インフラ書の 8.1 シークレット保管先 ↔ 7.1 .env 運用**: ローカルでの保管方法と本番の保管先が連続的に運用できるか
- **セキュリティ書 5.1 シークレット管理 ↔ 5.2 pre-commit**: シークレット検出（detect-secrets / gitleaks 等）が pre-commit に組み込まれているか
- **モノレポ採用 ↔ 2.4 タスクランナー / 3.4 共通設定**: モノレポを採用したならタスクランナーと共通設定の管理方針が具体化されているか
- **保留事項の残り**: 残っている保留事項を一覧で提示し、再検討するかを確認

### 6. 完了

以下を案内する:

- ファイルパス
- 「付録: ADR候補」の一覧（後続の ADR スキルへの入力になる）
- 次のステップ（ディレクトリ構成設計書、テスト戦略書）。本書を入力として進められる旨を伝える
  - 特にディレクトリ構成設計書側で参照するパッケージ一覧（モノレポなら apps/packages の構成）、テスト戦略書側で参照するタスクランナー / 型チェッカ設定を一覧で提示
- 保留事項が残っている場合は、それを下流ドキュメント作成前に解消すべきか並行して解消するかを併せて提示

## 保留事項の記録フォーマット

本文のセクションはプレースホルダーのままにし、「付録: 保留事項」に以下の形式で追記する:

```markdown
### [セクション番号] 項目名

- **未確定内容**: 何が決まっていないか
- **必要な情報 / 確認事項**: 確認すべきこと、調査が必要な点
- **補足**: ここまでに集まった情報・前提・候補案
```

## ADR候補の記録フォーマット

「付録: ADR候補」に以下の形式で追記する:

```markdown
- [ ] [リポジトリ・開発環境判断のタイトル] — 理由: [変更コスト / 議論の余地 / 影響範囲 等]
```

完了時にこの一覧を提示する。後続の ADR 作成スキルがこのリストを入力として詳細化する。

## 使用例

### 例 1: 上流ドキュメント揃った状態で起動

ユーザー: `/repository-environment`

実行:
1. 4 つの上流ドキュメントを検出して読み込み
2. 既存のリポジトリ・開発環境設計書なしを確認
3. `docs/repository-environment.md` への保存を確認
4. 1.1 構成方針から順に対話的に埋める
5. 確定ごとに ADR 候補を判定して付録に追記

### 例 2: 引数付きで起動

ユーザー: `/repository-environment pnpm モノレポで Turborepo、Biome を使いたい`

実行:
1. 上流ドキュメントを読み込み
2. 引数を 1.1 構成方針・2.2 パッケージマネージャ・2.4 タスクランナー・3.1/3.2 の初期案として取り込み
3. 各セクションで引数の方向性を案として提示し、上流ドキュメントとの整合性を検証しながら確定

### 例 3: 再開

ユーザー: `/repository-environment` (既存のリポジトリ・開発環境設計書あり)

実行:
1. 既存ファイルを検出し、状態（確定済み / 保留 / 未着手）を一覧化
2. 「続きから再開 / 特定セクションを修正 / 最初からやり直し」を選択してもらう
3. 選択に応じて進める

## トラブルシューティング

### 上流ドキュメントが存在しない

原因: アーキテクチャ・インフラ設計が未着手のまま本書を始めようとしている
解決策: `/architecture-design` および `/infra-design` の先行実行を推奨する。アーキテクチャ書の技術スタックが未確定だとツールチェイン選定が決まらない。インフラ書のリリース戦略が未確定だとブランチ戦略が浮いてしまう。続行を希望する場合は、これらの項目を口頭で確認した上で進める

### 過剰なツールセットを提案している傾向が見える

原因: モダン開発として「あるべき構成」を引っ張ってきている
解決策: 限定公開・PoC・小中規模を再確認する。Husky + lint-staged + commitlint + Renovate + ... のフルセットは保守負担になる。**必須は: パッケージマネージャ + Linter/Formatter + 最低限の Git Hooks（pre-commit でのフォーマット検証）**。それ以外は要件として明示されない限り採用しない

### モノレポ採用の必要性で悩む

原因: 「モノレポは将来のためにあるべき」という前提が先行している
解決策: モノレポ採用の閾値を **「複数アプリ or 共通パッケージあり」** に統一する。FE と BE が別リポジトリで運用される受託案件は意外と多い。判断材料: 同じチームが両方を頻繁に同時編集するか、共通の型定義・ユーティリティを共有したいか。Yes ならモノレポ、No ならシングル/マルチリポ

### Linter / Formatter で迷う

原因: Biome の新しさと ESLint+Prettier の実績で判断軸が決まらない
解決策: 判断軸を以下に絞る:
- **既存資産との互換性が必要** → ESLint+Prettier
- **フレームワーク標準が ESLint** → ESLint+Prettier（無理に剥がさない）
- **新規プロジェクト・速度重視・依存を減らしたい** → Biome
- **言語が TypeScript 以外** → 言語のエコシステム標準（Ruff / golangci-lint / rustfmt+clippy）

### 整合性チェックで多数の不整合が見つかった場合

原因: 上流ドキュメントの決定とツールチェインが乖離していた、または途中で要件が追加されて初期決定が陳腐化
解決策: 不整合を提示し、どちらを修正するかユーザーに判断を委ねる。アーキテクチャ書側の修正が必要な場合は `/architecture-design`、インフラ書側なら `/infra-design` の再実行を推奨
