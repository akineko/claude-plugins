# システムアーキテクチャ設計書を作成する

新規 Web サービス立ち上げ時に、プロジェクト概要書を入力としてアーキテクチャ設計書を対話的に作成する。後続のセキュリティ設計書、インフラ・デプロイ設計書、リポジトリ・開発環境設計書、テスト戦略書、ADR の起点となる。

## 想定する開発

- 小中規模の自社 PoC / 受託開発
- 一般公開せず、契約会社や受託元などの限定公開が主流
- プロジェクト概要書（`docs/project-overview.md` 等）が先に存在する想定

## 重要な制約

- **概念レベルの設計に留める**: ファイル単位のディレクトリ構成や実装詳細は対象外（リポジトリ・開発環境設計書、ディレクトリ構成設計書、機能設計の領域）
- **詳細な脅威分析・インフラ構成は対象外**: それぞれセキュリティ設計書・インフラ設計書で扱う。本書では「アーキテクチャ上の方針」までを記述
- **保留を許容する**: 確定できない情報は「保留」として記録。理由・確認事項も残す
- **増分更新**: 各子セクション確定時点でファイルを更新する。会話が中断されても作業が失われないように
- **ADR候補の収集**: 技術選定時に「変更コストが高い」「他候補との比較で議論の余地がある」決定はADR候補として付録に記録

## 使用方法

```
/architecture-design [アーキテクチャの方向性や決まっている内容]
```

引数がない場合は入力を求める。

## 作成フロー

### 1. 入力ドキュメントの取得

1. **プロジェクト概要書の検出**: `docs/project-overview.md` の存在を確認
   - 見つかれば読み込み、内容を初期コンテキストとする
   - 見つからない場合: 他の想定パス（`docs/requirements/project-overview.md` 等）も確認。それでもなければユーザーにパスを聞く
   - 概要書がまったく存在しない場合: 概要書なしでアーキテクチャ設計を進めるリスクを伝え、`/project-overview` の先行実行を推奨。それでも続行を希望する場合のみ進める

2. **引数があれば** 追加コンテキストとして取り込む

### 2. 既存ファイルの検出と再開判定

デフォルトの保存先（`docs/architecture.md`）および他の想定場所に既存のアーキテクチャ設計書がないか確認する。

- **既存あり**: 記載状況（確定済み / 保留 / 未着手）を一覧化して提示し、以下から選んでもらう:
  - **続きから再開**: 未着手セクションと保留セクションを順に進める
  - **特定セクションを修正**: セクション番号を指定して該当箇所を再作成
  - **最初からやり直し**: 既存ファイルをバックアップ（`.bak`）した上で新規作成

記載状況の判定基準:
- **確定済み**: 実際の内容が書かれている
- **保留**: 「付録: 保留事項」に該当セクションが記載されている
- **未着手**: テンプレートのプレースホルダー（`[...]`）のまま

- **既存なし**: 新規作成モードで次のステップへ

### 3. 保存場所の決定

以下を提示し確認:

- 推奨: `docs/architecture.md`
- 他候補の例: `docs/design/architecture.md`、リポジトリルート直下

確認後、ディレクトリが無ければ作成し、`assets/template.md` をコピーして雛形を配置する。

### 4. 子セクション単位での作成

以下の順で対話的に埋める。**1 セクション確定ごとにファイルを更新する**。

順序は「上流の決定が下流の選択肢を狭める」流れに従う。アーキテクチャスタイルが決まると技術スタックの選択肢が絞れるため、1.2 を 1.1 より先に確定する。

1. `1.2 アーキテクチャスタイル`
2. `1.1 全体構成図`
3. `2.1 フロントエンド`
4. `2.2 バックエンド`
5. `2.3 データストア`
6. `2.4 認証基盤`
7. `2.5 外部サービス`
8. `3.1 通信方式`
9. `3.2 レイヤリング・モジュール境界`
10. `3.3 状態管理方針`
11. `3.4 非同期・バックグラウンド処理`
12. `4.1 連携先一覧`
13. `4.2 連携方式`
14. `5. 非機能要件への対応`

#### 各セクションの処理手順

1. **概要書からの入力抽出**: プロジェクト概要書のうち、このセクションの判断材料となる項目を抽出して提示する（例: 2.4 認証基盤を作るときは「2.1 ロール・アクセス経路」を引用）
2. **内容案の作成と提示**:
   - 情報が十分にある → 案を作成して提示。技術スタック系セクションでは必ず「他候補と落選理由」も併記
   - 情報が不足 → 案・例・観点・確認候補を提示して質問する
3. **3 つの選択肢を常に提示**:
   - **採用**: 案をそのまま / 一部修正で確定
   - **追加情報で再作成**: 提示した質問に回答してもらい、案を作り直す
   - **保留**: このセクションは未確定として記録し、次のセクションへ進む
4. **ファイル更新**:
   - 採用 → 本文の該当セクションを更新
   - 保留 → 本文はプレースホルダーのままにし、「付録: 保留事項」に項目を追記
5. **ADR候補の判定**: 技術スタック系（2.x）と構造方針（3.1）で確定した決定について、以下のいずれかを満たすなら「付録: ADR候補」に追記:
   - 一度決めると変更コストが高い
   - 他候補との比較で議論の余地がある
   - 後続メンバー / AIが疑問に思う可能性が高い
6. 次のセクションへ進む

#### 曖昧な回答へのプッシュバック

下流の設計書で判断材料となる項目は、具体化されていないと手戻りが発生する。以下の粒度の回答があれば、具体化を促してから確定させる:

| セクション | 粒度が粗い回答の例 | 具体化を促す観点 |
|---|---|---|
| 1.2 アーキテクチャスタイル | 「Webアプリ」 | SPA+API / SSR / サーバレス / モバイル+API のどれか。デプロイ単位はいくつか |
| 2.x 技術スタック | 「適切なものを選ぶ」 | 候補3つ程度を提示し、プロジェクト特性と合致するものを選ぶ |
| 2.4 認証基盤 | 「認証あり」 | 認証方式（SSO / パスワード / マジックリンク）、IdP（Azure AD / Google Workspace 等）の有無 |
| 3.1 通信方式 | 未指定 | REST / GraphQL / tRPC / RPC のいずれか。理由も |
| 4.2 連携方式 | 「API連携」 | 同期 / 非同期、認証方式、エラー時の方針 |
| 5. 非機能要件 | 「概要書通り」 | 概要書の各非機能要件にアーキテクチャ上どう対処するかを 1 文ずつ |

プッシュバックしても情報が出ない場合は、保留として記録する。

#### セクションごとの出力形式ガイド

| セクション | 推奨形式 | 補足 |
|---|---|---|
| 1.1 全体構成図 | ASCII図 or Mermaid | 概念図レベル。複数サービス構成のときコンポーネント図に昇格 |
| 1.2 アーキテクチャスタイル | 1〜3 文 | 採用スタイル＋選定理由 |
| 2.1〜2.4 技術スタック | 採用 / 選定理由 / 他候補 の3行構成 | 4〜5行程度を目安。詳細はADRへ |
| 2.5 外部サービス | サービスごとの箇条書き | 用途を1文で |
| 3.1〜3.4 構造方針 | 1〜3 文の散文 | 不要な項目（3.4 等）は「該当なし」で可 |
| 4.1 連携先一覧 | 表（連携先 / 用途 / 連携方向） | |
| 4.2 連携方式 | 散文または表 | 複雑なフローのみ簡易シーケンス追記 |
| 5. 非機能要件 | 観点ごとの見出し + 1 文 | 概要書の項目に対応する形で記述 |

### 5. 完了時の整合性チェック

全セクション完了時に以下を確認し、不整合があれば提示してユーザーに判断を委ねる:

- **概要書の制約 ↔ 技術スタック**: 概要書の制約条件（必須技術、既存システム連携、納期等）と技術選定に矛盾はないか
- **データ機密度 ↔ データストア / 外部サービス**: 機密データを扱うのに外部サービスへ送信する設計になっていないか
- **アクセス経路 ↔ 認証基盤**: 概要書のアクセス経路（VPN / SSO 等）と認証基盤の選定が整合しているか
- **アーキテクチャスタイル ↔ 技術スタック**: スタイルと採用FW・データストアが整合しているか（例: サーバレス選定なのに長時間バッチ前提の構成 等）
- **非機能要件 ↔ 5章**: 概要書の非機能要件すべてに 5 章で対応しているか
- **保留事項の残り**: 残っている保留事項を一覧で提示し、再検討するかを確認

### 6. 完了

以下を案内する:

- ファイルパス
- 「付録: ADR候補」の一覧（後続のADRスキルへの入力になる）
- 次のステップ（セキュリティ設計書、インフラ・デプロイ設計書、リポジトリ・開発環境設計書、テスト戦略書）。本書を入力として進められる旨を伝える
- 保留事項が残っている場合は、それを下流ドキュメント作成前に解消すべきか並行して解消するかを併せて提示

## 保留事項の記録フォーマット

本文のセクションはプレースホルダーのままにし、「付録: 保留事項」に以下の形式で追記する:

```markdown
### [セクション番号] 項目名

- **未確定内容**: 何が決まっていないか
- **必要な情報 / 確認事項**: 確認すべきこと、調査が必要な点
- **補足**: ここまでに集まった情報・前提・候補案
```

## ADR候補の記録フォーマット

「付録: ADR候補」に以下の形式で追記する:

```markdown
- [ ] [技術判断のタイトル] — 理由: [変更コスト / 議論の余地 / 影響範囲 等]
```

完了時にこの一覧を提示する。後続のADR作成スキルがこのリストを入力として詳細化する。

## 使用例

### 例 1: 概要書ありの状態で起動

ユーザー: `/architecture-design`

実行:
1. `docs/project-overview.md` を検出して読み込み
2. 既存のアーキテクチャ設計書なしを確認
3. `docs/architecture.md` への保存を確認
4. 1.2 アーキテクチャスタイルから順に対話的に埋める
5. 確定ごとにADR候補を判定して付録に追記

### 例 2: 引数付きで起動

ユーザー: `/architecture-design Next.js + Supabase で行きたい。フロントは社内Azure ADでSSO`

実行:
1. 概要書を読み込み
2. 引数を初期スタック案として取り込み
3. 各セクションで引数の方向性を案として提示し、概要書との整合性を検証しながら確定

### 例 3: 再開

ユーザー: `/architecture-design` (既存のアーキテクチャ設計書あり)

実行:
1. 既存ファイルを検出し、状態（確定済み / 保留 / 未着手）を一覧化
2. 「続きから再開 / 特定セクションを修正 / 最初からやり直し」を選択してもらう
3. 選択に応じて進める

## トラブルシューティング

### 概要書が存在しない

原因: プロジェクト概要書を作成せずにアーキテクチャ設計から始めようとしている
解決策: `/project-overview` の先行実行を推奨する。最低限の入力（目的・利用者・データ機密度・制約条件・非機能要件）が揃わないと、本書の判断材料が不足する。続行を希望する場合は、これらの項目を口頭で確認した上で進める

### ユーザーが特定の技術を強く推している

原因: 開発者の慣れ・好み、既存資産との連続性
解決策: その技術を採用すること自体は問題ない。ただし「他候補と落選理由」を埋めるため、なぜ他候補ではなくその技術かを言語化してもらう。これがADRの価値そのものになる

### 整合性チェックで多数の不整合が見つかった場合

原因: セクション間の情報の乖離、または後半で理解が深まり初期決定が陳腐化
解決策: 不整合を提示し、どちらを修正するかユーザーに判断を委ねる。技術スタックの大幅な変更が必要な場合は、概要書側に修正が必要かも併せて確認する

### 「とりあえず最新技術で」と言われた場合

原因: 技術選定の判断軸が定まっていない
解決策: 概要書の制約条件（納期・予算・既存資産・運用体制）を再確認し、それに合致するかを判断軸にする。最新技術は学習コスト・エコシステム成熟度の観点で受託開発・PoCには不向きなことも多い旨を伝える
