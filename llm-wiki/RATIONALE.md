# llm-wiki 設計ノート（プラグイン全体）

> 各スキルの SKILL.md=「何をするか（指示）」/ 本ファイル=プラグイン横断の「なぜこの形か（意図・解釈・却下案・守る失敗）」。スキル固有の判断は各 `skills/<name>/RATIONALE.md` に置く。実行時は非読込。更新時に改訂する。

## 目的と背景

- Andrej Karpathy の "LLM Wiki"（生ソース / Wiki / スキーマの三層構造と ingest / query / lint ワークフロー）を出発点に、記事が未定義とした部分を独自に定義してスキル化したのが v0.1。
- 2026-07、Google 策定の [Open Knowledge Format (OKF)](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md) v0.1 を受けて「OKF をベースに、独自カスタマイズは可能な限り OKF に吸収する」方針をユーザーが決定。実運用開始前だったため、互換性の配慮なしに v0.2.0 で全面刷新した。
- 現在の位置づけ: **Karpathy = 思想**（三層構造・ワークフロー）、**OKF = 物理フォーマット**、**スキーマ CLAUDE.md = OKF が委ねる部分のプロデューサー規約**。

## 中核的な設計判断

### 【load-bearing】OKF 準拠の3分類ルール
- **決定**: (1) OKF が定義する事項（ページ形式・予約ファイル・リンク・log 体裁）は OKF に従い独自定義しない。(2) OKF が自由に委ねる事項（配置・命名・ワークフロー）はスキーマがプロデューサー規約として定める。(3) どちらにも根拠のない独自要素は持たない。スキーマ冒頭の「OKF 準拠宣言」がこの区分を Wiki 利用者（LLM）に伝える。
- **防いでいる失敗**: 独自拡張が増えて OKF コンシューマから読めない Wiki になること。逆に、OKF が規定しない部分まで「仕様だから」と硬直化すること。
- **出所**: ユーザー要望（2026-07-23）「独自カスタマイズ部分は可能な限り OKF に吸収」

### リンク記法は標準 Markdown 相対リンク（wikilink 全廃）
- **決定**: `[title](./page.md)`。OKF 推奨のバンドルルート絶対リンク（`/page.md`）ではなく相対リンクを使う。
- **却下した代替案**: Obsidian wikilink `[[...]]`（旧仕様）— OKF コンシューマが解決できない最大の非互換だった。なお Karpathy の原文も Markdown リンクで、wikilink は旧 llm-wiki 側の独自化。／絶対リンク — Wiki をプロジェクトリポジトリのサブディレクトリに置くと GitHub 上でリンクが壊れる。フラット配置では相対と絶対に実質差がなく、レンダリング互換で相対が勝つ。
- **防いでいる失敗**: GitHub / Obsidian でリンクが辿れない Wiki。
- **出所**: 設計議論（2026-07-23）。サブディレクトリ化する際は絶対リンクへの移行を再検討する（スキーマに明記済み）

### 【load-bearing】フラット配置 + タイププレフィックス命名（案A）
- **決定**: `source-` / `concept-` 等のプレフィックスで型を示すフラット配置。プレフィックスは「フラット配置における OKF のタイプ別サブディレクトリの等価物」。
- **却下した代替案**: OKF イディオムのタイプ別ディレクトリ（`sources/` 等 + 各 `index.md`）— 相対リンクが `../` 混じりで煩雑になり、index.md の管理点も増える。個人〜小規模 Wiki には過剰。
- **防いでいる失敗**: 立ち上げ期の構造過剰。ただし成長時の移行パス（wiki-schema でサブディレクトリ化を計画）はスキーマに明記してあり、これを消すと大規模化した Wiki の逃げ道がなくなる。
- **出所**: ユーザー決定（2026-07-24）「案Aで進めて将来必要になればディレクトリ分割」

### frontmatter は OKF §4.1 のフィールドのみ（独自フィールド禁止）
- **決定**: `type`（必須・記述的な Title Case の統制語彙）/ `title` / `description` / `resource` / `tags` / `timestamp`。旧 `created`・`aliases` は削除、`source_url` → `resource`、`updated` → `timestamp` に吸収。
- **却下した代替案**: `created` 維持 — 作成日は git 履歴で代替できるため削除。`aliases` 維持 — Obsidian 由来の独自要素で、検索は description と本文で足りる想定。必要になったら wiki-schema で再導入する（OKF は追加キーを許容するので準拠は壊れない）。
- **出所**: ユーザー要望（2026-07-23）「実運用前なので frontmatter の不要なタグは削除して良い」

### 【load-bearing】description と index.md の一元化
- **決定**: index.md エントリの説明文は frontmatter `description` の転記。description が正で index は導出物。乖離は wiki-lint が検出する。
- **防いでいる失敗**: 旧仕様では index の1行サマリが独立管理で、ページ更新時に乖離し放題だった。OKF §6「エントリはリンク先 concept の description を含める SHOULD」が一元化の根拠。
- **出所**: OKF SPEC §6 + 設計議論（2026-07-23）

### 本文にタイトル H1 を書かない / セクション見出しは H1
- **決定**: タイトルは frontmatter `title` に一元化し、本文はセクション H1（`# 主張` `# 関連` `# Citations`）で構成する。外部出典は OKF 慣例の `# Citations`（番号付き）。
- **却下した代替案**: 旧仕様の「H1 タイトル + H2 セクション」— OKF の例示（§4.3/4.4。慣例見出しは H1、本文にタイトル行なし）との乖離と、title と H1 の二重管理を避けるため廃止。
- **出所**: OKF SPEC §4.2–4.4 の精読（2026-07-24）。仕様の必須要件ではなくイディオムへの追従

### log.md は OKF §7 形式（Karpathy 形式を捨てた唯一の箇所）
- **決定**: `# Directory Update Log` + `## YYYY-MM-DD` 日付見出し・新しい日付が上・`* **カテゴリ**: 散文`。カテゴリ語彙 Init / Ingest / Query / Lint / Schema / Note は旧 action 語彙の翻訳（OKF ではカテゴリ太字は慣例であって要求ではないため、独自語彙でも準拠は保たれる）。
- **却下した代替案**: Karpathy 直伝の `## [日付] action | title` 形式（旧仕様）— OKF の予約ファイル構造（§9 適合条件が §7 準拠を要求）と衝突するため、思想の出所より仕様準拠を優先した。
- **出所**: ユーザー方針（2026-07-23）「OKF をベースに」

### 未解決リンク＝エラーではなく仕分けリスト
- **決定**: OKF §5.3 はリンク切れを「まだ書かれていない知識の表明」として有効とする。wiki-lint はエラー扱いせず typo / 作成候補に仕分けて報告する。ただし「リンクを通すためだけの空ページ作成」は本 Wiki の品質規約として引き続き禁止（OKF より厳しいがプロデューサー規約として有効）。
- **防いでいる失敗**: lint が未執筆リンクを機械的に断罪して、知識の TODO マーカーとしての価値を潰すこと。
- **出所**: OKF SPEC §5.3 の精読（2026-07-24）

### 運用ドキュメントも OKF 準拠、ただし index 非掲載
- **決定**: スキーマ（CLAUDE.md）・lint レポート・マイグレーション計画にも frontmatter（`type: Wiki Schema` / `Lint Report` / `Migration Plan`）を付け、バンドル全体を OKF-valid に保つ。ただし index.md は知識ページ専用のカタログとし、これらは載せない。
- **却下した代替案**: 運用ファイルをバンドル外に置く — Wiki の自己完結性（1 ディレクトリで完結・git clone で配布可能）が壊れる。
- **防いでいる失敗**: OKF §9 適合違反（非予約 `.md` の frontmatter 欠落）と、index が運用ファイルで汚れて progressive disclosure が濁ること。
- **出所**: OKF SPEC §9 の精読（2026-07-24）

## 解釈・仮定（要確認）

- **「吸収」の範囲**: ユーザーの「可能な限り OKF に吸収」を「必須要件だけでなくイディオム（タイトル H1 なし・H1 セクション・`# Citations`）まで追従する。ただし OKF が明示的に自由へ委ねる領域（配置・命名）は選択の問題として扱う」と解釈した。⚠️ イディオム追従（特に本文の H1 規約）が Obsidian での閲覧性等で不便なら、OKF 適合を壊さずに戻せる部分。
- **timestamp の粒度**: OKF の例が datetime（`...T14:30:00Z`）なので `date -u +%Y-%m-%dT%H:%M:%SZ` を規定した。⚠️ 日付だけで十分なら ISO 8601 の日付形式（`YYYY-MM-DD`）に緩めても準拠は保たれる。
- **プラグイン version**: スキーマ全面刷新（破壊的）だが 0.x 系のため 0.1.0 → 0.2.0 の minor で表現した。
