# Wiki スキーマのカスタマイズ

既存 Wiki の運用を続けながら、新しい用途・ページタイプ・規則をスキーマに反映する。**既存ページへの影響を伴う変更はマイグレーション計画とセットで提案**することで、Wiki が壊れない状態で進化させる。

## 基本原則

- **追加変更は安全、命名変更は慎重**: 新しいページタイプを追加するだけなら既存ページに影響しない。命名規則の変更・既存タイプのリネームは破壊的なのでマイグレーション計画を必ず作る
- **スキーマは育てる物**: 「最初からすべて決める」のではなく、運用で必要になったら追加する。先回りして書きすぎない
- **記録に残す**: スキーマ変更は `log.md` に `schema` action で必ず記録する。**いつ何を変えたか**を辿れるようにする
- **既存規約と矛盾させない**: 新しい規則を足すとき、既存セクションと衝突しないか確認する。衝突するなら旧規則を更新する

## ワークフロー

```
入力（Wiki ルート or 空）
  │
  ├─ Phase 1: Wiki ルートの確定とスキーマ読み込み
  ├─ Phase 2: 変更内容の聞き取り
  ├─ Phase 3: 既存スキーマと既存ページへの影響評価
  ├─ Phase 4: スキーマ変更案の提示と合意
  ├─ Phase 5: スキーマ更新（必要ならマイグレーション計画）
  └─ Phase 6: log.md への記録
```

## Phase 1: Wiki ルートの確定とスキーマ読み込み

### 1.1 ルート探索

`$ARGUMENTS` を以下の優先順位で解決する:

1. 引数で指定されたパス
2. `./wiki/` （ファイル `CLAUDE.md` または `AGENTS.md` があれば採用）
3. `./` （同上）

どれにも見つからなければ「Wiki が見つからない。`/llm-wiki:wiki-init` で初期化してから使ってください」と伝えて中止。

### 1.2 既存スキーマの読み込み

`<wiki-root>/CLAUDE.md`（または `AGENTS.md`）を読み、以下を把握:

- 現在の用途記述（冒頭の "目的" セクション）
- 既存のページタイププレフィックス一覧
- フロントマター規約
- 既存の "拡張" セクションに何が追記されているか

### 1.3 既存ページの軽量スキャン

`ls <wiki-root>/*.md` でページ名を列挙し、以下をメモする:

- 使われているプレフィックスとそれぞれのページ数
- スキーマに記載されていない命名（例外）が存在するか

これは Phase 3 で影響評価に使う。

## Phase 2: 変更内容の聞き取り

`AskUserQuestion` で「何を変えたいか」を確認する。

```
スキーマのどこを変えたいですか？（複数選択可）
1. 用途を追加する（例: 競合分析の用途を追加）
2. ページタイプを追加する（例: decision-* を追加）
3. ページタイプを削除・リネームする（破壊的）
4. フロントマターのフィールドを増減する
5. ワークフロー（ingest/query/lint）の手順を調整する
6. 自由記述
```

選択された項目について **具体例** を引き出す。例:

- 「`decision-*` を追加したい」 → どんな内容を書くか、既存の `topic-*` とどう区別するか
- 「`tags` を必須にしたい」 → 既存ページにも追加するか、今後だけにするか

## Phase 3: 既存スキーマと既存ページへの影響評価

各変更案について、以下のマトリクスで影響を分類する:

| 変更内容 | 既存ページへの影響 | 必要な対応 |
|---|---|---|
| 新しいページタイプを追加 | なし | スキーマの命名規約表にエントリ追加 |
| 新しいフロントマター項目を任意で追加 | なし | スキーマに記載するだけ |
| 新しいフロントマター項目を **必須** で追加 | あり（既存ページに項目が無い） | マイグレーション計画必須 |
| ページタイプのリネーム（例: `topic-` → `theme-`） | あり（既存ファイル名・wikilink すべて） | マイグレーション計画必須 |
| ワークフローの手順変更 | なし（運用方針の変更のみ） | スキーマ更新と log 記録 |
| 既存ルールと矛盾する追加 | あり（旧ルール従いの記述が陳腐化） | 旧ルールを修正、または `wiki-lint` で検出する旨を追記 |

破壊的変更の場合、ユーザーに以下を提示して合意を取る:

```
この変更は既存の {N} ページに影響します:
- 影響ページ: {サンプル 5 件}
- 必要な作業: {ファイル名変更 / wikilink 修正 / フロントマター追記 等}

進め方の選択肢:
1. スキーマだけ更新し、移行は後で wiki-lint に任せる（緩やか）
2. スキーマ更新と同時にこのスキルでマイグレーションも実行する（一気通貫）
3. 一旦中止して別の方法を考える
```

## Phase 4: スキーマ変更案の提示と合意

具体的な diff を **before/after の形** で提示する。Phase 3 で複数の変更がある場合はまとめて提示する。

```
## 命名規約への追加

### Before
| プレフィックス | 用途 | 例 |
| `source-` | 生ソースの要約 | source-foo.md |
| `concept-` | 概念 | concept-bar.md |

### After
| プレフィックス | 用途 | 例 |
| `source-` | 生ソースの要約 | source-foo.md |
| `concept-` | 概念 | concept-bar.md |
| `decision-` | 意思決定記録（ADR 風）| decision-2026-04-30-storage.md |

### 影響
- 新しいページタイプを追加するのみ。既存ページへの影響なし
```

ユーザーに「この変更で進めてよいか」を確認する。修正指示があれば反映して再提示する。

## Phase 5: スキーマ更新（必要ならマイグレーション計画）

### 5.1 スキーマ更新

合意された変更を `<wiki-root>/CLAUDE.md` に反映する。Edit ツールで該当セクションを更新する（ファイルを丸ごと書き直さない）。

更新時の注意:

- 既存の "目的" セクションのユーザー固有の記述を保護する
- 既存の "拡張" セクションを保護する
- セクション順序を不必要に変えない

### 5.1.1 整合性チェックリスト

スキーマの変更は CLAUDE.md の **複数箇所** を同時に更新する必要があることが多い。漏れを防ぐため、変更タイプごとに以下のチェックリストを必ず確認する:

**ページタイプを追加する場合**

- [ ] 命名規約表に新しいプレフィックス行を追加
- [ ] フロントマター `type` の許容値リストに追加
- [ ] index.md のカテゴリ見出しを追加（必要なら追加方針を SKILL に書く必要は無いが、実際の index.md を Edit する作業は別途指示）
- [ ] 用途の説明を追加（命名規約表の右列）

**ページタイプを削除する場合**

- [ ] 命名規約表から行を削除
- [ ] フロントマター `type` の許容値リストから削除
- [ ] index.md からカテゴリ見出しを削除（既存ページがあれば移行先を別途検討）
- [ ] 該当ページが既に存在するか確認し、あればマイグレーション計画必須

**ページタイプをリネームする場合（破壊的）**

- [ ] 命名規約表のプレフィックスを変更
- [ ] フロントマター `type` 値を変更
- [ ] index.md のカテゴリ見出しを変更
- [ ] 既存ファイルのリネーム計画を migration ファイルに記載

**フロントマター項目を必須化する場合（破壊的）**

- [ ] フロントマター規約セクションの該当項目を「任意」→「必須」へ
- [ ] 既存ページに項目が無いものをリストアップする手順を migration ファイルに記載

更新が複数箇所にまたがるとき、どの箇所を更新したかを Phase 6 の log エントリに具体的に書く。

### 5.2 マイグレーション計画（破壊的変更の場合のみ）

破壊的変更を伴う場合、以下を含む計画を `<wiki-root>/migration-{YYYY-MM-DD}-{slug}.md` に書き出す（`{slug}` は変更内容を 2〜4 語の kebab-case で表す。例: `migration-2026-04-30-rename-topic.md`）。同日に複数のマイグレーションを立ち上げても上書きしない構造にする。

```markdown
# Migration: {変更の概要}

## 動機
{なぜ変えるか}

## 対象ファイル
- {ファイル1}
- {ファイル2}
- ...

## 必要な変換
1. ファイル名: `topic-*.md` → `theme-*.md`
2. wikilink: `[[topic-foo]]` → `[[theme-foo]]`（全ファイル）
3. フロントマター: `type: topic` → `type: theme`
4. index.md の見出し更新

## 自動化可能な手順
{git mv とテキスト置換で済む部分の手順案}

## 手作業が必要な箇所
{個別判断が要る部分}
```

ユーザーが「実行して」と言うまでマイグレーションは実行しない。スキーマ変更とは独立した意思決定。

## Phase 6: log.md への記録

`<wiki-root>/log.md` に追記する:

```markdown
## [{今日の日付}] schema | {変更の総括}

- 追加: {追加した項目}
- 変更: {変更した項目}
- 削除: {削除した項目}
- 影響: {既存ページへの影響の有無}
- マイグレーション: {不要 / migration-YYYY-MM-DD-{slug}.md に計画}
- 更新箇所: {命名規約表 / フロントマター type 列挙 / index.md カテゴリ など、CLAUDE.md 内のどこを更新したか}
```

日付は `date +%Y-%m-%d` で取得する。

最後にユーザーに以下を伝える:

- スキーマファイルの更新箇所
- マイグレーション計画ファイル（あれば）のパス
- 次にやるべきこと（マイグレーション実行 / 新タイプでの ingest 等）

## 禁止事項

- 既存スキーマファイルを丸ごと書き直す（差分が追えなくなる）
- ユーザー合意なしの破壊的変更
- マイグレーションを伴う変更を計画なしに即実行する
- 既存の "目的" や "拡張" セクションのユーザー固有記述を勝手に書き換える
