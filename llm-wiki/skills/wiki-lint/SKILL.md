# Wiki 健全性チェック（lint）

Wiki 全体を走査し、運用していると徐々にたまる **不健全さ** を検出する。検出するだけで自動修正はしない。**人間と LLM のレビューを介して直す**ことで、Wiki の品質を保つ。

## 基本原則

- **検出はする、修正はしない**: 自動修正は誤った介入のリスクが高い。lint は気づきを生むだけで、修正は `wiki-ingest` / `wiki-schema` / 手作業で行う
- **網羅性より優先順位**: 軽微な指摘で埋め尽くすより、影響の大きい矛盾・stale を上位に出す
- **再現可能なチェック**: 出力は `log.md` に記録され、次回の lint で「前回からの差分」を比べられる形にする
- **静的チェックと意味的チェックを分ける**: 壊れた wikilink のような静的なものはまとめて出す。矛盾検出のような意味的なものは丁寧に証拠を添える

## ワークフロー

```
入力（Wiki ルート or 空）
  │
  ├─ Phase 1: Wiki ルートとスキーマの確定
  ├─ Phase 2: ページ一覧の取得とメタ情報抽出
  ├─ Phase 3: 静的チェック（リンク・index・命名規約）
  ├─ Phase 4: 意味的チェック（矛盾・stale・孤立・欠落）
  ├─ Phase 5: レポート生成
  └─ Phase 6: log.md への記録
```

## Phase 1: Wiki ルートとスキーマの確定

`$ARGUMENTS` から Wiki ルートを決定。なければ `./wiki/` → `./` の順で `CLAUDE.md` または `AGENTS.md` を探索する。

スキーマを読み、以下を Phase 3 のチェック基準として把握する:

- ページタイプのプレフィックス
- フロントマター必須項目
- index.md のカテゴリ構成

### 1.x 早期リターン（空 Wiki）

`<wiki-root>/*.md` のうち `CLAUDE.md` / `AGENTS.md` / `index.md` / `log.md` 以外のページが **0 件** なら、「Wiki にまだコンテンツが無いため lint は不要」とユーザーに伝えて即終了する。レポートも log エントリも作らない。

## Phase 2: ページ一覧の取得とメタ情報抽出

```bash
# Wiki ルート直下の .md ファイル一覧
ls <wiki-root>/*.md
```

各ページについて、以下を取得（必要に応じて Read / Grep を使う）:

- ファイル名とプレフィックス
- フロントマター（title, type, created, updated, source_url 等）
- 本文中の `[[wikilink]]` の集合（grep で抽出）
- 本文の長さ（極端に短いページの検出用）

`index.md` と `log.md` も読み込む。これらはチェック対象でもあり、参照点でもある。

## Phase 3: 静的チェック

### 3.1 壊れた wikilink

すべてのページから `[[xxx]]` を抽出し、対応する `xxx.md` が存在するかを確認する。

```
broken_link:
- [[concept-foo]] が source-bar.md から参照されているが、ファイル concept-foo.md が存在しない
```

#### 3.1.1 メタ表現の除外

スキーマファイル（`CLAUDE.md` / `AGENTS.md`）と `log.md` には、規約説明用の **メタ wikilink** が含まれる。これらは実体ページへの参照ではないので、壊れたリンクとして検出してはならない。

除外対象:

- **コードフェンス内のリンク**: `` ```...``` `` や行頭インデント 4 以上の擬似コードブロック内
- **`CLAUDE.md` / `AGENTS.md` 全体**: 規約・命名規則を説明するため `[[concept-self-attention]]` のような **例示的** リンクを含む
- **`log.md` 全体**: 過去のエントリには既に削除済みのページへの参照が残ることがある（履歴として保持）
- **明らかなプレースホルダ表現**: `[[ページのファイル名（拡張子なし）]]` `[[未作成のページ]]` `[[xxx]]` `[[ページ名]]` `[[wiki-link]]` のように、ファイル名でない説明文が `[[]]` で囲まれているもの
- **ワイルドカード表現**: `[[source-*]]` `[[concept-*.md]]` のような `*` を含むパターン

判定基準: ファイル名として実在しうる kebab-case の文字列（英数字・ハイフン・アンダースコア）以外を含むリンクは除外する。

### 3.2 index.md と実ファイルの乖離

- index.md にエントリがあるが実ファイルが無い → **stale な目次**
- 実ファイルがあるが index.md にエントリが無い → **未登録ページ**

### 3.3 命名規約違反

スキーマで定義されたプレフィックスに従わないファイル名を検出する。

```
naming_violation:
- foo.md がプレフィックスを持たない（スキーマに無い形式）
- author-baz.md がスキーマに無い `author-` を使っている（`person-` が正?）
```

### 3.4 フロントマター違反

スキーマで定義された必須項目が欠けているページを検出する。

- `title` が無い
- `type` が無い、または値がスキーマのタイプ一覧に無い
- `source` 型なのに `source_url` が無い
- `updated` が `created` より過去になっている

### 3.5 内容が極端に薄いページ

本文が 100 文字未満（フロントマター除く）のページを「実体のない空ページ」として警告する。

## Phase 4: 意味的チェック

ここは LLM の判断が必要。**Wiki が小さければ全ページを精読**、大きければ以下のサンプリング戦略を使う:

- 直近 30 日に `updated` または `created` されたページ全件
- ランダムサンプル 20 ページ
- 同じ tag を共有するページのクラスタ単位

### 4.1 既知の矛盾の取り込み（4.2 矛盾検出の前段）

矛盾検出を始める前に `log.md` を遡り、`query` action と `ingest` action のエントリで「矛盾検出: ...」と記録されたものを **既知リスト** として抽出する。検出された矛盾はレポートで以下に分けて出す:

- **既知の未解決**: log 記録済みでまだ解消されていないもの
- **新規発見**: 今回 lint で初めて検出したもの

これにより、過去に見つかっている矛盾を再報告して優先度判定を狂わせることを防ぐ。

### 4.2 矛盾の検出

同じ事実・主張について複数のページで異なる記述がある場合を検出する。

検出のヒント:

- 同じ概念ページ（concept-/topic-）の本文で、異なる出典 `[[source-*]]` から異なる結論が示されている
- ある source ページの主張と、別の source ページの主張が定量的に食い違う
- person ページの所属・経歴で、出典別に異なる情報がある

レポート例:

```
contradiction:
- 主題: Transformer の発表年
- 食い違い:
  - [[source-foo]] では 2017 年と記述
  - [[source-bar]] では 2018 年と記述
- 推定原因: 投稿日と発表日の混同の可能性
- 推奨アクション: source 原文を確認し、どちらか正しい方を採用、もう一方を修正
- 既知/新規: 既知の未解決（log 2026-04-15 のエントリで記録済み）
```

### 4.2 stale な記述

新しい source で更新されているはずなのに、古い概念ページが古いままの状態を検出する。

- 古い `[[source-A]]` を引用している `[[concept-X]]` がある
- 同じ主題を扱う新しい `[[source-B]]` が存在し、A の主張と異なっている
- しかし `[[concept-X]]` は B を引用していない

### 4.3 孤立ページ

どのページからも `[[link]]` されていないページ。`index.md` からのリンクは「カタログとしての存在」なのでカウントするかどうか選択:

- **完全孤立**: index.md からも他ページからもリンクされていない（ほぼバグ）
- **index 限定**: index.md にだけ存在し、他ページから参照されていない（記述が他ページに統合されていない可能性）

### 4.4 欠落している重要概念

複数の source / topic ページから言及されているが、専用 `concept-*` ページが無い用語を検出する。

検出方法:

- 既存 source ページに頻出するキーワード・固有名詞・専門用語を抽出（言語に応じて: 英語は大文字始まりのトークン、日本語はカタカナ語・繰り返し出現する複合名詞・専門用語などを LLM の判断で抽出）
- それらに対応する `concept-*.md` または `person-*.md` が存在するかチェック
- 3 ページ以上から言及があるのに専用ページが無いものをリストアップ

### 4.5 ソース取り込みの偏り

ある topic ページが特定の 1 つの source にのみ依存している場合、視点が偏っている可能性を指摘する。「裏取りソースを ingest すると robust になる」と提案する。

> このチェックは Wiki が成熟した段階で意味を持つ。`source-*` ページが **5 件未満** の立ち上げ期は実施しない（ほぼ全 topic が偏った状態で当然のため）。

## Phase 5: レポート生成

`<wiki-root>/lint-report-{YYYY-MM-DD}.md` に結果を書き出す。日付は必ず `date +%Y-%m-%d` で取得する（決め打ちしない）。

### 5.1 検出 0 件カテゴリの省略

サマリ表は全カテゴリの件数を必ず記載するが、**件数 0 のカテゴリの詳細セクションは省略**する。読み手が読むのは「該当があった項目」だけなので、空の見出しを並べない。

すべてのカテゴリが 0 件の場合は、超短縮版を採用する:

```markdown
# Wiki Lint Report — {YYYY-MM-DD}

検出された問題はありません（全 9 カテゴリ 0 件）。Wiki は健全です。

前回 lint との差分: {あれば、なければ "前回も健全"}
```

前回 lint と同じ内容の検出結果が続いている場合は、レポート末尾に「前回からの変化なし」と明記する（読み手が「進捗なし」を即座に把握できる）。

### 5.2 標準フォーマット

検出ありの場合:

```markdown
# Wiki Lint Report — {YYYY-MM-DD}

## サマリ

| カテゴリ | 件数 |
|---|---|
| 矛盾 | 2 |
| stale 記述 | 5 |
| 孤立ページ | 3 |
| 欠落概念 | 4 |
| 壊れたリンク | 1 |
| index.md 乖離 | 2 |
| 命名規約違反 | 0 |
| フロントマター違反 | 1 |
| 薄いページ | 2 |

## 高優先（矛盾・stale）

### contradiction-1: Transformer の発表年
- {詳細}
- 既知/新規: {新規 or 既知の未解決}
- {推奨アクション}

### stale-1: concept-self-attention の引用が古い
- {詳細}

## 中優先（孤立・欠落）
（該当があれば記載）

## 低優先（静的・フォーマット）
（該当があれば記載）

## 推奨される次のアクション

1. 高優先項目から順に着手:
   - contradiction-1 は source 原文の確認が必要
   - stale-1 は `wiki-ingest` で再取り込みすると自動修正される可能性
2. 欠落概念は新ソース ingest のヒント:
   - "{欠落概念名}" を扱う良いソースが見つかれば取り込みを推奨
3. 静的違反は手作業 / `wiki-schema` でルール調整
```

レポート提示時、ユーザーに「優先度の高いものから対処したいか」を確認する。**自動修正には進まない**。

## Phase 6: log.md への記録

日付は必ず `date +%Y-%m-%d` で取得する（決め打ちしない）。

`<wiki-root>/log.md` に追記:

```markdown
## [{今日の日付}] lint | 健全性チェック実施

- レポート: lint-report-{YYYY-MM-DD}.md
- サマリ: 矛盾 N / stale M / 孤立 K / 欠落 J / 静的違反 L
- 前回 lint との差分: {あれば。前回 log を参照}
```

前回の lint からの **差分** を出すには、log.md 内の `lint` action のエントリを遡って前回のサマリを読み、件数を比較する。

## レポート以外の出力

ユーザーへの直接の応答では、以下を簡潔に伝える:

- 高優先項目（矛盾・stale）の件数と代表例 1〜2 件
- レポートファイルのパス
- 「修正に進むか、別途対応するか」を確認

## 禁止事項

- 自動修正の実行（壊れたリンクを勝手に消す、矛盾を勝手に片方に寄せる、孤立ページを勝手に削除する等）
- レポートでの根拠なしの断定（必ず該当ページ名・該当行を示す）
- 大量の低優先指摘でレポートを埋め尽くす（高優先を埋もれさせない）
- 前回 lint との差分を取らずに毎回ゼロから出す（累積している問題が見えなくなる）
