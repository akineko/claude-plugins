# Wiki への取り込み（ingest）

生ソースを Wiki 内のサマリページに変換し、関連ページを cross-reference で更新して、知識を「累積する形」で蓄積する。

## 基本原則

- **スキーマが正**: スキーマ（`<wiki-root>/CLAUDE.md`）に書かれた命名規則・フロントマター規約・ページタイプに従う。スキーマに無いタイプを勝手に作らない
- **要約ではなく、Wiki ページを書く**: 1 記事を 1 ファイルに丸ごとコピーするのではなく、**Wiki の他のページとつながる形** で再構成する。引用は要点のみ
- **横の更新が本体（成熟期）**: Wiki が育つと、ソースから新しいページを 1 つ作るのは入口に過ぎず、**既存の関連ページ 5〜15 個を更新**することが ingest の本質になる。これがあるから「Wiki が累積する」
- **立ち上げ期は骨格作り**: ただし Wiki 内のページが少ない初期は横の更新が物理的にできない。代わりに `concept-*` / `person-*` の新規作成を多めにして **骨格を作るフェーズ** と位置づける（Phase 5.1 のフォールバック参照）
- **人間との擦り合わせ**: 自動で全部やらず、要点を提示してユーザーから強調点・観点を引き出す（バッチモードでは省略可）

## ワークフロー

```
入力（URL/パス/テキスト）
  │
  ├─ Phase 1: Wiki ルートとスキーマの確定
  ├─ Phase 2: ソースの取得と精読
  ├─ Phase 3: 要点の擦り合わせ（人間の関与）
  ├─ Phase 4: source-*.md の作成
  ├─ Phase 5: 関連ページの探索と更新
  ├─ Phase 6: 新規 concept-/person-/topic- ページの作成
  ├─ Phase 7: index.md の更新
  └─ Phase 8: log.md への記録
```

## Phase 1: Wiki ルートとスキーマの確定

### 1.1 ルート探索

引数で Wiki ルートが指定されていればそれを使う。なければ `./wiki/` → `./` の順に `CLAUDE.md` または `AGENTS.md` を探す。見つからなければ「Wiki が見つからない。`/llm-wiki:wiki-init` で初期化を」と伝えて中止。

### 1.2 スキーマ読込

`<wiki-root>/CLAUDE.md` を読み、以下を必ず把握する:

- ページタイプのプレフィックス一覧
- フロントマター規約
- `index.md` 更新時のカテゴリ見出し
- ingest ワークフローのカスタマイズがあるか

### 1.3 既存ページの軽量カタログ化

`<wiki-root>/index.md` を読む。これが Phase 5 で「どの既存ページに cross-reference を足すか」を判断する起点になる。

## Phase 2: ソースの取得と精読

入力に応じて取得方法を分ける:

| 入力 | 取得方法 |
|---|---|
| URL（HTTP/HTTPS） | `WebFetch` で本文を取得 |
| ローカルファイルパス（.md / .txt / .pdf） | `Read` で読み込む（PDF は pages 指定可） |
| 直接テキスト | そのまま使用 |
| YouTube / 動画 URL | トランスクリプトの取得手段を持たないので、ユーザーに転写テキストの貼り付けを依頼する |

複数ソースの一括取り込みを依頼された場合は、**1 つずつ Phase 2〜8 を回す**（並列処理しない。横の更新で衝突するため）。

## Phase 3: 要点の擦り合わせ（人間の関与）

ソース読了後、以下を **箇条書きで** 提示する:

```
ソースの要点を整理しました。Wiki に書く前に強調したい観点を教えてください。

主要な主張:
- {主張1}
- {主張2}
- {主張3}

新しい概念・用語:
- {概念1}: {1 行説明}
- {概念2}: {1 行説明}

登場する人物・組織:
- {人物1}（{役割}）

このソースから派生して、関連しそうな既存ページの候補:
- `{既存ページ}.md` — 更新内容案: {1 行}

何を強調しますか？ あるいはこのまま進めてよいですか？
```

ユーザーが「このまま進めて」「OK」と返したらそのまま進む。修正指示があれば反映する。

**バッチモード**: ユーザーが事前に「複数まとめて、確認なしで進めて」と指示している場合、この phase はスキップして Phase 4 に進む。

## Phase 4: `source-*.md` の作成

ファイル名は `source-{slug}.md`。`{slug}` は kebab-case で、URL や題名から機械的に生成する。

雛形:

```markdown
---
type: Source
title: {ソース題名}
description: {このソースを 1 文で要約。index.md にそのまま転記される}
resource: {URL。ローカルファイル・直接テキストの場合はフィールドごと省略}
tags: [{自然に拾えるタグ。無ければフィールドごと省略}]
timestamp: {現在日時（ISO 8601）}
---

# 主張

{Phase 3 で擦り合わせた主要な主張を箇条書き → ページの背骨}

# 重要な引用

> {原文の引用 1（短く）}

> {原文の引用 2}

# 解釈・含意

{ソースが示唆する含意。事実と解釈を明確に分ける}

# 関連

* [{関連ページ1の title}](./{関連ページ1}.md) - {どう関連するか}
* [{関連ページ2の title}](./{関連ページ2}.md) - {同上}

# Citations

[1] [{ソース題名}]({URL or ローカルパス}) — {著者名 / 媒体名 / 公開日}
```

注意:

- フロントマターはスキーマに合わせる。`timestamp` は `date -u +%Y-%m-%dT%H:%M:%SZ` で取得する
- **本文にタイトルの H1 を書かない**（タイトルは frontmatter の `title` に一元化。スキーマの「本文の体裁」参照）
- `description` は index.md のエントリに転記される 1 文。「このページは何を扱っているか」を書く
- `tags` はスキーマ上「任意」なので、題名・本文から自然に拾えるタグが無ければ **フィールドごと省略する**（無理に推測したタグは検索性を悪化させる）
- 「主張」セクションは Wiki の他のページから参照されることを想定し、**1 文ずつが独立して引用しやすい形**にする
- 「重要な引用」は元の言葉を残す価値がある場合のみ（標準的な内容ならスキップ）。**ソースが既に要約記事で原典でない場合は引用 0 件でよい**。原典の主張は「主張」セクションに集約する
- 全文転載は避ける。あくまでサマリ

## Phase 5: 関連ページの探索と更新

### 5.1 候補の特定

以下を順に行う:

1. `index.md` をスキャンし、ソースの主題・概念・人物に近いページ名を 10〜20 個ピックアップ
2. それらのページを `Read` し、本当に関連しているか確認
3. 関連が確認できたものを **5〜15 個** に絞る（少なすぎると累積しない、多すぎるとノイズになる）

### 5.1.1 立ち上げ期のフォールバック

Wiki 内のページ（`source-*` `concept-*` `person-*` `topic-*` など）が **20 個未満** のときは、5〜15 個ルールを満たせなくて構わない。**0 件でもよい**。

代わりに以下を優先する:

- Phase 6 で新規 `concept-*` / `person-*` を多めに作り、骨格を作る
- 関連が確認できた数件のみ更新する
- 「立ち上げ期」と「成熟期」の運用差は SKILL の前提であり、満たせないルールに無理に合わせない

### 5.2 更新パターン

各既存ページに対して、以下のいずれかの形で cross-reference を追加する:

| パターン | 例 | 補足 |
|---|---|---|
| 新しい主張・データの追加 | 「[2026 年の研究](./source-foo.md) では X が示された」 | 既存記述に追加 |
| 既存記述への補強リンク | 既存の文に [新ソース](./source-foo.md) を脚注的に追加 | 矛盾しない裏取り |
| 既存記述への反証リンク | 「ただし [別の調査](./source-foo.md) は別の見解を示す」 | 矛盾の場合は 5.3 へ |
| 「# 関連」セクションへのリンク追加 | 末尾の関連ページリストに追加 | 直接の主張変更が無いとき |

更新した既存ページは frontmatter の `timestamp` も更新する。「# 関連」セクションのリンクが 10 件を超え始めたら、**種別ごと（source / concept / person）に小見出し（H2）で束ねる**と読みやすい。

### 5.3 矛盾と補強の使い分け

新ソースの主張と既存ページの記述の関係を、以下のいずれかに分類する:

| 関係 | 判定基準 | 扱い |
|---|---|---|
| **補強** | 同じ主張を別の出典が裏付ける / 既存記述に新しいデータが追加できる | 既存ページの本文に統合してよい。出典として `(./source-new.md)` へのリンクを添える |
| **拡張** | 既存記述と矛盾しないが、新しい角度を提供する | 既存ページの該当セクションに 1 段落追加。並置不要 |
| **矛盾** | 同じ事実について異なる結論を主張している | 既存記述を **消さず並置** する |

矛盾の場合の並置例:

```markdown
- 旧来は X とされていた（[旧ソース](./source-old.md)）
- 一方 2026 年に Y という反証が示された（[新ソース](./source-new.md)）
```

矛盾の発見は Wiki の価値の中核。これを `log.md` に必ず記録する（Phase 8）。補強・拡張は記録不要。

## Phase 6: 新規 concept-/person-/topic- ページの作成

Phase 3 で挙がった新概念・人物について、**専用ページが無ければ作成**する。

> **`topic-` の責務境界**: `topic-` ページは原則 query 時の書き戻しで作る（`/llm-wiki:wiki-query` の Phase 5 参照）。ingest 中に `topic-` を作るのは「ソース 1 件で完結する横断テーマ」がはっきり立ち上がった場合に限る。**迷ったら作らない**（後から query で発生させる方が自然）。

最小フォーマット:

```markdown
---
type: Concept | Person | Topic
title: {正式名称}
description: {このページを 1 文で要約。index.md にそのまま転記される}
timestamp: {現在日時（ISO 8601）}
---

{1〜3 段落で定義・概要}

# 関連

* [{関連ページの title}](./{関連ページ}.md) - {どう関連するか}
* [{ソースの title}](./source-{slug}.md) - {出典}
```

> 注: 「とりあえず空ページを作る」のは禁止。1〜3 段落の実体を必ず書く。中身が薄くなる場合は、source ページ内のセクションに留めて、専用ページは作らない。

## Phase 7: index.md の更新

新規作成したすべてのページ（source-/concept-/person-/topic-）を `index.md` の該当カテゴリに追加する:

```markdown
* [{title}](./source-{slug}.md) - {frontmatter の description をそのまま転記}
```

カテゴリ見出し（H1）がスキーマで決まっているので、勝手に新カテゴリを作らない。既存ページの `description` を変更した場合は index.md の該当エントリも同じ文に揃える。

## Phase 8: log.md への記録

今日の日付見出しの下に追記する（見出しが無ければ H1 直後に新設。**新しい日付が上**）:

```markdown
## {今日の日付}

* **Ingest**: [{ソース題名}](./source-{slug}.md) を取り込み。作成: {新規ページのリスト}。更新: {既存ページ数} 件
  - 矛盾検出: {あれば内容。なければこの行ごと省略}
```

日付は必ず `date +%Y-%m-%d` で取得する。

## 完了報告

最後にユーザーに以下を提示:

- 作成・更新したファイルのリスト（パス付き）
- 検出した矛盾があればその内容
- 次のアクション提案（例: 「この概念について `wiki-query` で深掘りできます」「`wiki-lint` で全体の健全性を確認できます」）

## 禁止事項

- スキーマに無いページタイプを使う / 命名規則を破る
- ソースの全文転載
- 中身の無い空 concept/person ページの量産
- ユーザー確認なしの複数ソース一括処理（明示的にバッチモードを依頼された場合のみ可）
- 既存ページの記述を矛盾と決めつけて削除する（並置するのが原則）
