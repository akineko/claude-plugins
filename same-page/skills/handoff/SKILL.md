# handoff — セッション間の引き継ぎ

セッションが変わると会話の記憶は消える。次のセッション（未来の自分と AI）が「どこまで終わり、何を決め、次に何をするか」を推測ではなく記録から復元できるようにする。handoff の読み手は次のセッションの AI である — 人間向けの要約ではなく、再開に必要な情報を書く。

## 手順 1: 対象の特定

- 引数の合意ファイル、なければこの会話が扱ってきた active な合意ファイル。
- 合意ファイルがない（軽量作業だった）場合:
  - 作業が完了している → 引き継ぎは不要。その旨を伝えて終わる。
  - 続きが残っている → 合意ファイルを新規作成してから（readback の手順 5 と同じ要領、テンプレートは `../../templates/agreement.md`）現在地を書く。

## 手順 2: 会話の棚卸し

この会話を遡り、記録から漏れているものを拾う:

1. **未記載の決定** — ユーザーと確定したのに決定台帳にない選択・方針転換 → 台帳に追記（確認: ✔）
2. **未記載の裁量判断** — 説明が要る判断で台帳にないもの → 台帳に追記（確認は実際に報告済みかで判断）
3. **前提の変化** — 会話中に崩れた・追加された前提 → 「前提」を更新

## 手順 3: 現在地の更新

合意ファイルの「現在地」を全面的に書き直す（追記ではなく置き換え。古い現在地は誤誘導になる）:

- **進捗**: 完了条件ごとの状態。作業中のものは「どこまでできていて何が残っているか」を1行で
- **次の一手**: 再開時に最初にやる具体的アクション（「続きをやる」ではなく「X のテストを書くところから。対象は `path/to/file`」の粒度）
- **開いている問題**: ユーザーの回答待ち・未解決の論点・保留した話題
- **注意（ハマりどころ）**: この会話で学んだ罠・落とし穴・非自明な事情のうち、次のセッションが同じ回り道をしそうなもの（なければ「なし」）

`updated` を更新する（日付は `date` で確認）。

## 手順 4: 締めの報告

ユーザーに向けて短く報告する:

- 台帳に追記した決定（あれば）
- 現在地の要点（進捗1行＋次の一手1行）
- 再開方法の案内: 「次のセッションで続きを依頼すれば、フックが合意ファイルを通知し、そこから再開します」

## 規律

- 現在地は「次のセッションの AI が最初の5分で行動を始められるか」で自己検査する。ファイルパス・コマンド・条件番号など、再開の起点は具体名で書く。
- 会話の要約を書かない。再開に効く情報だけを書く（経緯の物語は台帳と確定事項が既に持っている）。
- 完了した作業の handoff はしない（それは signoff で閉じる）。中途半端に両方やらず、完了なら signoff を提案する。
