# readback 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。プラグイン横断の意図は `same-page/RATIONALE.md` を参照。

## 目的と背景

認識ズレの最上流（依頼→解釈の変換点）を潰す、プラグインの中核スキル。ここでズレると下流のすべて（実装・検証）が「間違った目標への正確な前進」になるため、フローの最初に置いた。

## 中核的な設計判断

### 【load-bearing】深さ3段階と「迷ったら軽い方」
- **決定**: 軽量／標準／重量の3段階を影響範囲・解釈の分散・手戻りコストで判定し、判定に迷ったら軽い方に倒す。軽量は質問ゼロ・ファイルなしで即着手。
- **却下した代替案**: 全依頼で合意ファイル作成 — 小さな依頼での儀式化がスキル自体を嫌われさせ、無効化（ユーザーがプラグインを外す・指示で迂回する）を招くため却下。
- **防いでいる失敗**: 過剰確認。認識合わせの最大の敵は認識合わせのコスト自身であり、「止まらない軽量モード」があるからこそ全依頼での自動起動が許容される。この判断と description の自動起動設計は相互依存している。

### 【load-bearing】質問は1ラウンド・最大3問
- **決定**: 質問数を構造的に制限し、超過しそうなら依頼の分割を提案する。
- **防いでいる失敗**: 質問の洪水（トリアージの放棄）。質問が多いほど1問あたりの回答の質が下がり、ユーザーは「進めてくれ」と雑に答えるようになる — 認識合わせの形をした認識放棄。

### 【load-bearing】second-reader にメインの解釈を渡さない
- **決定**: 重量モードで起動する second-reader には依頼文の逐語とリポジトリパスだけを渡す。
- **防いでいる失敗**: アンカリング。メインの解釈を見た解釈者は独立サンプルでなくなり、「一致したから分散小」という推論の根拠が壊れる。相違点だけが価値を持つ仕組みなので、独立性はこのスキルの測定装置の校正に相当する。

### 言い換えに「含意の明文化」を必須化
- **決定**: リードバックの言い換えには、依頼が明示していない含意・帰結を最低1つ含める。
- **却下した代替案**: 自由形式の要約 — オウム返しに退化しやすく、オウム返しはユーザーに「伝わった」という誤安心を与えるだけで何も検証しないため却下。
- **防いでいる失敗**: 検出力ゼロのリードバック。含意（「つまり既存の自動リトライは廃止になります」）はユーザーの想定と衝突したときだけ反応が返る、能動的なズレ検出器。

### 2軸トリアージ（被害×分散）の2×2
- **決定**: 曖昧点を「質問する／宣言して進む／黙って選んで記録／黙って選ぶ」の4象限に振り分ける。
- **防いでいる失敗**: 「全部聞く」と「全部推測する」の二極。特に「被害大×分散小＝宣言して進む」の象限が、確認回数を増やさずに事後検証可能性を確保する要。

### 【load-bearing】起動経路の二重化（フック注入＋発動重視 description）
- **決定**: SessionStart フックで毎セッション「開発依頼を受けたらコードを書く前に readback を起動する」を注入し（`hooks/session-start-context.sh`）、description も「依頼文の型（実装して・直して等）の列挙＋命令形＋依頼が小さいことは省略の理由にならない」に改訂した。
- **却下した代替案**: (a) description の強化のみ — 実装依頼はモデル自身の中核能力なので道具（スキル一覧）を探す動機が生まれず、ワードをいくら強くしても「一覧を見ずに直接コードを書き始める」問題は解けない。(b) UserPromptSubmit での毎プロンプト注入 — 確実性は最高だがコンテキスト消費が過剰なため却下。
- **防いでいる失敗**: プロセス系スキル（道具ではなく手順を課すスキル）の不発。実運用で「通常の開発依頼では起動しない」ことが確認された。
- **出所**: 実運用フィードバック（2026-07-26）。

## 解釈・仮定（要確認）

- **深さ判定の閾値**: 「1〜2ファイル」「数十分」等の具体値は初期仮説として置いた。⚠️実運用でズレたら表の値だけ調整する（構造は保つ）。
- **標準でもファイル作成**: 標準以上は合意ファイルを作ると解釈した（セッション跨ぎと signoff の基準固定の価値が、ファイル1つのコストを上回ると判断）。⚠️「標準はインラインで十分」という運用感覚ならここが調整点。
- **自動起動の設計**: プラグインを入れる＝常時薄い認識合わせを望んでいる、と解釈している。⚠️逆に起動が過剰になった場合は、フックの注入文言を弱める → description を絞る → disable-model-invocation、の順に調整する（起動経路の二重化を参照）。
