# readback — 依頼の復唱と合意の固定

依頼を受け取ったら、着手する前に「自分がどう解釈したか」を検証可能な形でユーザーに返し、ズレを作業前に潰す。ただし確認そのものにコストがあるため、深さは依頼のリスクに比例させ、小さな依頼では止まらない。

## 手順 0: 深さの判定

依頼を読み、3観点で軽量／標準／重量を判定する。**最も重い観点に合わせる**。迷ったら軽い方（過剰確認はこのスキルの失敗形態）。ユーザーが深さを明示したら（`--heavy`、「ちゃんと合意を作って」等）無条件に従う。

| 観点 | 軽量 | 標準 | 重量 |
|------|------|------|------|
| 影響範囲 | 1〜2ファイルの局所変更 | 1モジュール内に収まる | モジュール横断・公開API・データ変更・不可逆操作を含む |
| 解釈の分散 | 合理的な解釈が実質1つ | 2〜3点を確認すれば確定する | 目的や方式のレベルで解釈が割れうる |
| ズレ時の手戻り | 数分で作り直せる | 数十分 | 設計からやり直し、または取り返しがつかない |

深さごとの動作:

- **軽量**: 解釈宣言（1〜3行）を出してそのまま着手。合意ファイルなし。質問は原則ゼロ（被害大×分散大の1点があるときのみ例外的に1問）。
- **標準**: 手順 1〜5 を実施。質問は1ラウンド最大3問。合意ファイルを作成。
- **重量**: 標準に加えて second-reader エージェントを投入し、解釈の分散を実測する。

**継続判定**: `docs/agreements/` に `status: active` の合意ファイルがある場合（SessionStart フックが通知する）、まず依頼がその続きかを判定する。続きなら新規合意を作らず、既存ファイルの「現在地」を読んで文脈を復元し、必要なら合意を更新する。

## 手順 1: 文脈の最小収集

依頼に登場する対象（ファイル・機能・エラー・用語）を特定できる最小限だけコードベースを読む。深い調査は fulfill の領分であり、ここで時間を使うとリードバックが遅れて認識合わせ自体が嫌われる。

**重量のみ**: 文脈収集と並行して second-reader を起動する。渡すのは「ユーザーの依頼文の逐語」と「対象リポジトリのパス」だけ。**自分の解釈・仮説は一切渡さない**（渡すと独立性が壊れ、分散の実測にならない）。

## 手順 2: 解釈の構築

6つの次元で自分の解釈を書き出す（この時点ではユーザーに見せない作業メモ）:

1. **目的**（なぜ）— 明示されているか、推定か。推定なら（推定）を付ける
2. **成果物**（何を）— 期待される変更の形
3. **スコープの縁** — 隣接する周辺（テスト・ドキュメント・同種の類似箇所・ついでのリファクタ）を含むか否か
4. **品質基準** — 使い捨てか本番品質か。互換性維持か破壊的変更可か
5. **方式の自由度** — ユーザーに想定方式がありそうか、任されているか
6. **完了条件** — 何をもって完了か（検証可能な形に翻訳する）

## 手順 3: 曖昧点のトリアージ

解釈の各次元について曖昧点を洗い出し、2軸で振り分ける。**重量では second-reader の解釈と自分の解釈を突き合わせ、相違した点を「分散大」の実測値として扱う**（一致した点は分散小の根拠になる）。

| | 解釈の分散: 大 | 解釈の分散: 小 |
|---|---|---|
| **ズレ被害: 大** | 質問する | 宣言して進む（リードバックに前提として明記） |
| **ズレ被害: 小** | 黙って合理的に選び、決定台帳に記録 | 黙って選ぶ |

- 質問は**1ラウンド・最大3問**。4問以上必要だと感じたら、依頼が大きすぎるか前提の対話が不足しているサインなので、質問を絞る代わりにその旨を正直に伝えて依頼の分割を提案する。
- コードベースの規約・既存スタイルから答えが読み取れることは聞かない（読んで従う）。

## 手順 4: リードバックの提示

以下の構成でユーザーに提示する:

1. **言い換え**（1〜3行）— 依頼文の繰り返しではなく自分の言葉で。**依頼が明示していない含意・帰結を最低1つ明文化する**（例: 「この変更で既存の自動リトライは廃止になります」）。含意の明文化こそがズレの検出器で、オウム返しは何も検出しない。
2. **やらないこと** — スコープの縁で「含めない」と判断した周辺作業を理由付きで（ズレの大半は縁で起きる）。
3. **前提** — 確認せずに進む宣言型の仮定（被害大×分散小）。
4. **完了条件** — 検証可能な形で。
5. **質問** — あれば AskUserQuestion で（使えない環境では箇条書き）。各質問は必ず「選択肢＋推奨＋推奨の理由」の形にし、オープンクエスチョンにしない。推奨理由はユーザーが AI の理解度を検査する材料でもある。

**悪いリードバック / 良いリードバック**:

| 悪い | 何が悪いか | 良い |
|------|-----------|------|
| 「ログイン機能を修正します」 | オウム返し。理解を証明しない | 「セッション切れ時に無言で失敗する再ログインを、エラー表示＋再認証ダイアログに変えると理解しました。既存の自動リトライは廃止になります」 |
| 「どのように実装しますか？」 | 設計の丸投げ | 「セッション延長APIを叩く案と再認証を求める案があり、後者を推奨します（延長は監査ログに残らないため）。どちらにしますか？」 |
| 質問を8個並べる | トリアージの放棄 | 被害大×分散大の3問に絞り、残りは前提として宣言する |
| 「変数名はcamelCaseでいいですか？」 | コードベースを読めば分かる | 聞かずに既存規約に従う |

## 手順 5: 合意の固定

- **軽量**: 「この理解で進めます: …」と宣言し、そのまま Skill ツールで fulfill を起動して実装に入る。ファイルは作らない。
- **標準・重量**: 質問への回答を反映し、`docs/agreements/YYYY-MM-DD-<slug>.md` を作成する。
  - 日付は `date` コマンドで確認する。
  - フォーマットはプラグインの `templates/agreement.md`（この SKILL.md から `../../templates/agreement.md`、または `${CLAUDE_PLUGIN_ROOT}/templates/agreement.md`）が正準。テンプレートの指示（コメント削除・空セクションは「なし」）に従う。
  - 質問で確定した内容は「確定事項」へ、宣言した仮定は「前提」へ、質問せず選んだ小さな判断は「決定台帳」へ（種別: 裁量）。
  - 作成後、ファイルパスと合意の要点（やること／やらないこと／完了条件）を短く報告し、Skill ツールで fulfill を起動して実装に進む（ユーザーが確認してからと言った場合のみ待つ）。

## 規律

- 軽量と判定したら止まらない。質問ゼロを恐れない。
- 依頼にない親切（ついで修正・ついでリファクタ）を合意に加えない。気づいた改善点は「やらないこと」に理由付きで置くか、作業後に提案として分離する。
- second-reader に自分の解釈を渡さない。
- ユーザーが「いいからやって」と言ったら軽量に切り替えて即座に進む。このスキルはゲートではなく補助。
- 完了条件に書けないこと（検証方法を示せないこと）を合意に入れない。書けないなら、それはまだ合意できていない。
