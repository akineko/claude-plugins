# signoff — 証拠つき完了検証

「できました」は主張であって証拠ではない。合意した完了条件を独立の目で検証し、実装中に黙って決めたことを開示して、ユーザーが安心して「完了」と言える状態を作る。

## 手順 1: 検証基準の確定

- 合意ファイルがあれば「完了条件」をそのまま基準にする。
- インライン合意のみの場合、会話から完了条件を再構成し、**検証を始める前に**「この条件で検証します: …」と宣言する（基準の後出しを防ぐ）。
- 完了条件が検証不能な書き方だった場合、検証可能な形に翻訳して宣言する（翻訳が解釈を含むなら、その旨を明示）。

## 手順 2: 独立検証（evidence-auditor）

evidence-auditor エージェントを起動する。渡すもの:

- 合意ファイルのパス（またはインライン合意の全文: 完了条件・やること・やらないこと）
- 変更の範囲を特定する情報（対象ブランチ・比較先など。エージェントが `git diff` で自力特定できるなら省略可）

**渡さないもの: 実装の経緯・実装中の言い分・「たぶん大丈夫」の類の自己評価**。実装文脈を渡すと監査が自己弁護に汚染される。

evidence-auditor は完了条件ごとの判定（達成／部分達成／未達／検証不能）と証拠、スコープ照合の結果を返す。

**例外**: 変更が微小（1〜2ファイル・完了条件が1つ）でエージェント起動が過剰な場合は、メインが同じ手順で検証してよい。ただしその場合も必ず**実行による証拠**（テスト・再現手順の実施）を取り、コードを読んだだけの「達成のはず」で判定しない。

## 手順 3: 裁量判断の開示

決定台帳（またはインライン合意時の判断メモ）から「確認」列が空欄のものを抽出する。各判断を1行＋選択理由で提示する。これはユーザーが「それは違う」と言える最後の安価な機会。開示した判断は台帳の確認列に ✔ を入れる。

## 手順 4: 完了報告

以下の構成で報告する:

1. **判定サマリ** — 完了条件 N 件中: 達成 x / 部分 y / 未達 z / 検証不能 w
2. **条件ごとの判定と証拠** — 達成: 何をどう実行して確認したか（コマンドと結果の要点）。未達・部分: 何が欠けているか。検証不能: なぜ検証できないか、代替の確認手段
3. **合意外の変更** — 変更ファイルのうち合意の「やること」に対応しないもの（ついで修正の検出）。あれば、残すか戻すかを確認
4. **裁量判断の開示**（手順 3 の内容）
5. **残課題・提案** — スコープ外として見送ったもの、作業中に気づいた改善候補（合意に混ぜず、ここで分離して提案）

## 手順 5: 合意ファイルの更新

- 全条件達成し、合意外変更と裁量判断にユーザーの異議がなければ: frontmatter の `status: done`、`updated` を更新（日付は `date` で確認）。
- 未達が残りユーザーが続行を選んだ場合: `active` のまま、決定台帳に判定結果の要点を1行記録し、fulfill に戻る。
- ユーザーが「ここまでで良い」と打ち切った場合: 未達条件を台帳に記録（種別: 合意変更、確認: ✔）した上で `done` にする。

## 規律

- 判定を甘くして完了に倒さない。部分達成は部分達成と言う（未達の報告は失敗ではなく、このスキルの成果物）。
- 証拠のない「達成」を書かない。実行できるものは実行する。
- 合意外の変更を黙って通さない（良かれと思った変更ほど開示する）。
- 完了報告の長さは変更の大きさに比例させる。1条件の小さな作業なら5行で足りる。儀式化しない。
