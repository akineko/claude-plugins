## 目的と背景

会話内の漸進的な乖離（決めたつもり／聞いたつもり／終わったつもり）を、作業の節目で安価に照合する。readback（入口）と signoff（出口）の間を埋める、フロー途中の再同期点。

## 中核的な設計判断

### 【load-bearing】表示のみ・ファイルを更新しない
- **決定**: checkpoint は読み取り専用とし、永続化はすべて handoff に委ねた。
- **却下した代替案**: checkpoint でも台帳を更新する — 「途中で何度も呼べる」性質と両立せず（呼ぶたびに書き込みが走ると呼ぶことにコストが生まれ、気軽な再同期という役割が死ぬ）、handoff との責務境界も濁るため却下。
- **防いでいる失敗**: 呼ぶことへのためらい。何度呼ばれても安全（冪等）だからこそ、ユーザーは「ちょっと確認」を気軽にできる。

### 【load-bearing】「なし」の明記（未報告判断・合意とのズレ）
- **決定**: 該当がなくても項目を省略せず「なし」と書く。
- **防いでいる失敗**: 「書いてない」の二義性。省略された項目は「確認したが無かった」のか「確認していない」のか読み手に区別できず、再同期レポートの信頼性そのものを毀損する。「なし」は確認済みの宣言。

### git 現物での裏取り
- **決定**: 進捗・変更状況は記憶ではなく `git status` / `git diff --stat` で確認してから書く。
- **防いでいる失敗**: 会話が長いときほど起きる「やったつもり報告」。再同期レポート自体がズレていたら本末転倒で、このスキルだけは自分の記憶を信用してはいけない。

### 1画面（約25行）の上限
- **決定**: レポート全体に長さ上限を置き、詳細より照合可能性を優先した。
- **防いでいる失敗**: 読まれない再同期。長いレポートはユーザーが流し読みし、ズレの発見器として機能しなくなる。上限は「ユーザーが全行を読む」ことを設計上の前提にするための制約。

## 解釈・仮定（要確認）

- **自動起動の許可**: 「今どうなってる？」等への応答として構造化レポートが出るのは価値と判断し、自動起動を許した。⚠️単発の質問（「テスト通った？」）への誤起動が目立つなら、description をさらに絞るか disable-model-invocation に切り替える。
- **修正の反映先**: レポートへのユーザーの指摘は「合意ファイルがあれば台帳に記録」とした（表示のみの原則の唯一の例外はユーザー指摘の記録）。⚠️これも handoff に寄せる運用（checkpoint では一切書かない）もあり得る。
