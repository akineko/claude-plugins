# same-page プラグイン全体 設計ノート

> README=「何であるか」/ 各 SKILL.md=「何をするか」/ 本ファイル=「なぜこの構成か（プラグイン横断の意図・解釈・却下案）」。実行時は非読込。スキル個別の判断は各スキルの RATIONALE.md へ。

## 目的と背景

ユーザー依頼（2026-07-17）:「一切の妥協なくユーザーと認識のズレなく効率的に開発を行えるスキルやエージェントが揃ったプラグイン」を、既存プラグインを参考にせずゼロベースで設計・実装する。

出発点に置いた問題定義: 認識のズレは「暗黙の解釈が検証されないまま作業に変換される瞬間」に生まれ、発見が遅れるほど手戻りが指数的に高くつく。既存の開発支援が「作る・検査する」を扱うのに対し、本プラグインは「ユーザーの頭の中と AI の頭の中を同期させ続ける」ことだけを一貫した責務とする。

## 中核的な設計判断

### 【load-bearing】ズレの発生点分解によるスキル構成（3+2）
- **決定**: ズレの発生点を「依頼→解釈」（readback）「実装中の裁量」（fulfill）「完了の主張」（signoff）の3点に分解して1点1スキルを置き、時間軸の乖離に対して会話内（checkpoint）とセッション間（handoff）の2スキルを横断で置いた。
- **却下した代替案**: 単一の巨大スキル（フロー全体を1スキルで） — 途中参加（signoff だけ使う等）ができず、description が濁って自動起動精度も落ちるため却下。
- **防いでいる失敗**: スキル間の責務重複と、「どのスキルを呼べばいいか分からない」状態。各スキルの description 末尾に兄弟スキルとの棲み分けを明記する形で固定した。

### 【load-bearing】リスク比例の原則を全スキルに貫通させる
- **決定**: 確認・検証・記録のすべてを「ズレたときの被害 × 解釈の分散」でトリアージし、小さい依頼では止まらない（readback の軽量モード、signoff の例外条項、fulfill の L0 記録基準「説明が要る判断だけ」）。
- **防いでいる失敗**: 認識合わせのコストが認識合わせ自体を嫌われさせ、プラグインが外される・無視される事態。「全部確認する」は認識合わせではなく責任転嫁、という立場を README の原則3に明文化した。
- **出所**: 設計議論。「効率的に」という依頼文の解釈（下記⚠️参照）。

### 【load-bearing】独立性の原則 — 検証者に結論・経緯を渡さない
- **決定**: second-reader にはメインの解釈を、evidence-auditor には実装の経緯を渡さない。両エージェント定義に「紛れ込んでも無視する」防御まで書いた（二重防御）。
- **防いでいる失敗**: アンカリング（独立解釈が独立でなくなり、分散の実測が壊れる）と自己弁護汚染（実装者の言い分が監査に混入し、判定が甘くなる）。
- **出所**: 設計議論。自己採点は構造的に甘くなるという一般知見。

### 契約メタファーの命名（readback / fulfill / signoff）
- **決定**: 復唱→履行→完了承認という合意のライフサイクルで命名を統一した。
- **却下した代替案**: intake / work / verify 等の汎用語 — 他プラグインとの識別性が低く、スキル名から役割の連関が読めないため却下。
- **防いでいる失敗**: 名前からフローが想起できないことによる誤用（README のフロー図と命名が相互補強する）。

### 合意ファイルの設計 — docs/agreements/ 配置・決定台帳の内蔵
- **決定**: 対象プロジェクトの `docs/agreements/YYYY-MM-DD-<slug>.md` に置き、frontmatter `status` でライフサイクル管理。決定台帳・現在地を合意ファイルに内蔵し、別ファイルに分けない。フォーマットの正準は `templates/agreement.md` の1箇所のみ。
- **却下した代替案**: (a) 台帳・現在地の別ファイル化 — 参照が分散し更新漏れを招くため却下。(b) インデックスファイルでの一覧管理 — frontmatter の glob で足り、インデックスは更新漏れの元なので却下。
- **出所**: ユーザーの「docs/ 配下にツール生成物を置く」方針（メモリ）と「1情報1箇所」方針（グローバル CLAUDE.md）。

### 【load-bearing】SessionStart フックによる起動リマインダーと作業中合意の自動通知
- **決定**: セッション開始時に (1) 常時: 「開発依頼を受けたらコードを書く前に readback を起動する」リマインダー（2〜3行）、(2) `status: active` な合意ファイルがあればその一覧と復元指示、を注入するフックを置いた。
- **却下した代替案**: 合意通知のみで通常は沈黙（初版の設計）— 実運用（2026-07-26）で readback が通常の開発依頼に不発となり、description 単独の自動起動は信頼できないと判明したため、常時リマインダーを追加した（詳細は readback の RATIONALE「起動経路の二重化」）。
- **防いでいる失敗**: セッション跨ぎのズレ（合意通知の層）と、プロセス系スキルの不発（常時リマインダーの層）。セッション跨ぎのズレは「ユーザーも AI も前回の詳細を忘れている」状態で起きるため、どちらかが思い出す前提の設計は構造的に破綻する。自動検出だけが機能する。
- **出所**: 設計議論＋実運用フィードバック（2026-07-26）。出力は `hookSpecificOutput.additionalContext` の JSON 形式（公式ドキュメントと公式プラグイン実例で確認した、コンテキスト注入の確実な形式。プレーン stdout はバージョンにより挙動が揺れる）。JSON エスケープは可搬性のため外部コマンドに依存せず bash 置換で行う。

### 実装能力は最小限に留める（fulfill を設計パイプラインにしない）
- **決定**: fulfill は「合意→タスク分解→TDD実装→逸脱プロトコル」だけを持ち、多段の設計文書生成や精緻なフェーズ管理は持たない。
- **却下した代替案**: 設計〜実装のフルパイプライン内蔵 — 本プラグインの責務（認識同期）から外れ、大規模設計が必要な案件はその旨を正直に言う方が誠実なため却下。
- **防いでいる失敗**: プラグインの責務肥大と、既存の設計系ツールとの役割衝突。

## 解釈・仮定（要確認）

- **「効率的に」の解釈**: ユーザーは「効率的に開発」と言った → 「応答や実装の速度」ではなく「確認のトリアージによる中断の最小化＋手戻りの削減＋ユーザーの検証コスト（読む量・答える量）の最小化」と解釈して全スキルに反映した。⚠️速度側の最適化（並列化の徹底等）を期待していた場合はズレている。
- **「揃った」の解釈**: フロー全体（着手前〜完了後〜セッション間）を途切れなくカバーする最小セット＝5スキル+3エージェントと解釈した。⚠️より多機能（レビュー専門スキル等）を期待していた場合は不足。
- **eval 未作成**: 本体の設計・実装を先行し、skill-creator での eval 整備は次ステップとした。⚠️「実装」に eval まで含む意図だった場合は未完。
- **既存プラグインの不参照**: 指示通り、既存プラグインの SKILL.md・エージェント定義は一切読まずに設計した。リポジトリのインフラ（marketplace.json・RATIONALE テンプレート・plugin.json スキーマ）のみ参照した。
