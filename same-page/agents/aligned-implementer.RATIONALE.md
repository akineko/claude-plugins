# aligned-implementer 設計ノート

> 定義=aligned-implementer.md / 本ファイル=保守者向けの決定の出所・load-bearing な制約。定義の再掲はしない。オーケストレーション全体は fulfill の RATIONALE.md を参照。

## 役割と位置づけ

fulfill の実装実働部隊。メイン文脈を実装詳細で圧迫しないためのコンテキスト分離と、独立タスクの並列実行のために存在する。「合意への忠実さ」をエージェント単体でも保てるよう、逸脱プロトコルを内蔵する。

## 中核的な設計判断

### 【load-bearing】逸脱プロトコル表の再掲（正準は fulfill/SKILL.md）
- **決定**: fulfill/SKILL.md と同内容のプロトコル表を定義に持つ。
- **却下した代替案**: 呼び出し時にプロトコルをプロンプトで渡す — 呼び出し側の書き漏れで最重要の統制が欠落しうるため、定義に焼き込んだ。
- **防いでいる失敗**: エージェント単独実行時のプロトコル欠落。**更新時は fulfill/SKILL.md と必ず同時に直す**（二重管理は自己完結性の対価。fulfill の RATIONALE にも同じ注意を記載済み）。

### 【load-bearing】合意ファイルを編集しない
- **決定**: 決定台帳への記録はオーケストレータの仕事とし、エージェントは判断リストを構造化して返すだけにした。
- **防いでいる失敗**: 並列起動された複数の実装者が同一の合意ファイルに追記して競合・上書き消失すること。

### コミットしない
- **決定**: 作業ツリーへの変更までを責務とした。
- **防いでいる失敗**: signoff の検証（合意外変更の検出を含む）前に履歴が確定してしまうこと。コミットはユーザーの領分。

### ツール無制限（tools フィールドなし）
- **決定**: 実装には Read/Write/Edit/Bash の全系統が必要なため制限しない。統制はツールではなくプロトコル（L2 停止・非コミット・合意ファイル非編集）で行う。

### 「迷ったら L2」を定義側にも記載
- **決定**: 停止側に倒すバイアスを実装者自身に持たせた。
- **防いでいる失敗**: サブエージェントは「完了して戻りたい」圧力を持ちやすく、グレーな発見を裁量（L0/L1）に丸めて進みがち。判定の既定値を停止側に置くことで相殺する。

## 解釈・仮定（要確認）

- **L2 停止時の作業ツリー**: 変更を戻すか残すかはエージェントに委ね、報告で状態を明示させる形にした。⚠️「必ず着手前に戻す」規律の方が安全だが、部分的な進捗が選択肢の判断材料になる場合も多いため、明示報告を条件に残置を許した。
