# distill-knowledge

このスキルは「経験 → 転用可能な知見」への蒸留を行う。素材（生の事象・コード・議論）から、**他の文脈に持ち出せる構造**だけを取り出して Markdown に固定する。

ナレッジベースに残す価値があるかどうかの判定もスキル側の責任。集めた情報をそのまま整形するだけのタスクではない。

## 起動から完了までの流れ

1. 何を蒸留したいか（対象）と情報源を特定する
2. 知見の種類を判別し、対応する references を読み込む
3. 素材を集める（会話履歴の読み返し / ファイル読込 / リポジトリ調査）
4. 蒸留する（後述の「蒸留の四原則」を適用）
5. 転用可能性を判定する（微妙なものはユーザーに確認）
6. 出力ファイルを作成する

## ステップ1: 対象と情報源の特定

ユーザーの依頼から、以下を整理する。曖昧な場合は推定し、推定に自信がない場合のみ確認する（自明なら確認しない）。

- **何の知見か**: 一文で要約できるか試みる。例: 「N+1 問題を特定するためのデバッグ手順」「マルチテナント DB 設計でテナント分離方式を選ぶ判断軸」
- **情報源**: 以下のいずれか（複数可）
  - 直近の会話履歴（このセッションでのやりとり）
  - ユーザーが明示したファイル群（添付・パス指定）
  - リポジトリのコード/ドキュメント（ユーザーが「このリポジトリの○○について」と指示）

情報源の指定が曖昧で、かつ会話履歴に明確な対象が含まれていない場合のみ確認する。会話の流れから何を蒸留すべきか読み取れるなら、確認なしで進める。

## ステップ2: 種類の判別と references の読み込み

蒸留対象がどの種類に属するかを判別し、対応する references を読む。複数種類にまたがる場合は複数読む。

| 種類 | 該当する典型例 | references |
|------|----------------|------------|
| トラブルシューティング系 | バグ・インシデント・つまずき・想定外の挙動・調査の遠回り | `references/troubleshooting.md` |
| 設計判断系 | アーキテクチャ選定・技術選定・データモデル設計・API 設計 | `references/design-decision.md` |
| ツール/ライブラリ Tips 系 | CLI 使いこなし・ライブラリの落とし穴・開発環境構築 | `references/tooling-tips.md` |
| パフォーマンス系 | 計測手法・ボトルネック解消・スケール対応 | `references/performance.md` |
| プロセス/運用系 | レビュー運用・リリース手順・チーム連携・ワークフロー改善 | `references/process.md` |

どれにも当てはまらない場合、最も近い種類の references を参考にしつつ、後述の「蒸留の四原則」だけで構成しても良い。無理に分類しない。

## ステップ3: 素材集め

情報源に応じて以下を実施する。

- **会話履歴**: 関連するやりとりを脳内で再構成。発端・試行錯誤・行き詰まり・転換点・結論を洗い出す
- **ファイル**: 指定ファイルを Read。複数なら全部読む
- **リポジトリ調査**: Glob / Grep / Read を使い、対象に関連するコード・コミット履歴・既存ドキュメントを集める。コミット履歴は判断の背景を含むことが多いので `git log` を活用する

素材が薄い（再現可能な知見にするには情報不足）と感じたら、書き始める前にユーザーに何を補足したいか伝える。

## ステップ4: 蒸留 ― 蒸留の四原則

集めた素材をそのまま書き写すのではなく、以下の四原則を通して「知見の核」を取り出す。

### 原則1: 条件と結論を分離する

知見は「ある条件下で、ある結論が成り立つ」という形に整理できる時にだけ転用される。

- 悪い形: 「Redis のキー設計は `<tenant>:<entity>:<id>` にすると良い」
- 良い形: 「マルチテナントでキャッシュを共有する Redis 構成では、テナント ID をキーの最上位プレフィックスに置くことで、テナント単位の一括削除と誤マッチ防止を同時に満たせる」

「ある条件下で」が抜けた知見は、他文脈に持ち出した時に誤適用される。

### 原則2: 観測した現象と本質的な構造を区別する

表面的な事象（エラーメッセージ・特定の症状・特定の API の挙動）と、その背後の構造（並行性問題・契約の不一致・状態管理の欠陥）は別物として書く。

- 表面だけ書くと: 同じエラーが出た時にしか役に立たない
- 構造を書くと: 別の表層にも同じ知見が適用できる

両方書くのが理想（表面を見て構造に辿り着けるよう）。

### 原則3: 「やったこと」より「なぜそれを選ばなかったか」を残す

採用した手段の説明だけでは、読者は「なぜそれが他より良いのか」を判断できない。

- 検討した代替案
- 各代替案を採用しなかった理由（具体的に何が問題だったか）
- 採用案を選んだ評価軸

これらを残すことで、読者は自分の文脈に当てはめて再判断できる。

### 原則4: 陳腐化しやすい情報は明示的に分離する

以下のものは時間とともに陳腐化する。残すなら「いつ時点の情報か」を明記し、知見の本体とは分離する。

- 具体的なバージョン番号
- 特定のライブラリの API シグネチャ
- 当時のチーム規模・組織状況
- 具体的なツール名（代替手段が出やすい領域では特に）
- パフォーマンス計測値（環境依存）

本体には「○○系のライブラリでは」「サイズの大きい組織では」のように抽象化した形で書き、付録的に「2026年5月時点では FooLib v3 を使用」のように補足する。

## ステップ5: 転用可能性の判定

書き上げる前（または書きながら）に、以下を点検する。

| チェック項目 | 通らなかった場合の対処 |
|-------------|----------------------|
| プロジェクト固有の名詞（社内サービス名・特定の業務ドメイン）を抜いても価値が残るか | 残らないなら蒸留対象として不適。ユーザーに「これはプロジェクト固有色が強いです」と伝え、それでも残すか確認 |
| 他人が読んで自分の文脈に翻訳できるか | できないなら抽象度が低い。原則1・2を再適用 |
| 単発の事象ではなくパターン化できるか | できないなら「気付きメモ」レベル。ナレッジ化するなら、より大きな構造の一例として扱える書き方に変える |
| 条件を満たさない場合に「適用しない」と判断できるか | できないなら適用範囲が不明瞭。条件記述を強化 |

**微妙な判定が必要なケース**:
- プロジェクト固有要素が多いが核には転用価値がある → ユーザーに「この部分は抽象化して残し、固有部分は削ります」と方針を伝えてから進める
- 知見の境界（どこまでが今回の話でどこからが一般論か）が曖昧 → ユーザーに境界を確認
- 複数の知見が混在しており、分割すべきか統合すべきか不明 → ユーザーに確認

問題なく転用可能と判断できる場合は確認せず進める。

## ステップ6: ファイル出力

スキルを実行しているリポジトリのルートに直接出力する。

### 単一の知見の場合

リポジトリルートに `<topic-slug>.md` を作成する。

- ファイル名は内容を表す kebab-case（例: `redis-multitenant-keying.md`, `n-plus-one-debugging.md`）
- ファイル先頭に H1 タイトル、続けて本文

### 複数の知見をまとめて出力する場合

リポジトリルートに `<topic-slug>/` ディレクトリを作り、その中に複数の `.md` を配置する。

- ディレクトリ名は包括的なテーマを表す kebab-case
- ディレクトリ直下に `README.md` を置き、各ファイルへのリンクと一行説明を載せる
- 個別ファイルは内容を表す kebab-case

### 既存ファイルとの衝突

同名ファイルが既に存在する場合は上書きせず、ユーザーに通知して以下のいずれかを選ばせる:
- 別名で新規作成
- 既存ファイルに追記（追記位置と方針を確認）
- 上書き

### Markdown の体裁

- H1 は必ず1つ。タイトルは「何の知見か」が一目でわかる名詞句
- 冒頭に「この知見は何か」「いつ役に立つか」を 2〜4 行で要約
- 本文構造は references の種類別テンプレートに従う
- コードブロックは言語タグを必ず付ける
- 抽象的な原則を書いたら、その直後に最低1つの具体例を添える（具体例なしの抽象は読者が理解できない）

## 完了報告

出力したファイルのパスをユーザーに伝える。複数ファイルなら全パスを列挙する。手動で移動させると聞いているので、移動の提案やナレッジベースへのコミット提案はしない。

## このスキルを起動すべきでない場合

以下は対象外。混同しないこと。

- **個別プロジェクトの設計書を作りたい**: 転用を目的としない、そのプロジェクト専用の設計記録。別のドキュメント化タスクで対応すべき
- **コードのコメントを増やしたい**: コード内の文書化はこのスキルの対象外
- **議事録・進捗報告を作りたい**: 蒸留ではなく記録。対象外
- **対象が薄すぎる/事象が単発で構造が見えない**: 無理に蒸留しない。ユーザーにその旨を伝える
