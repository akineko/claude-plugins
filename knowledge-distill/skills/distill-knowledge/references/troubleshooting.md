# トラブルシューティング系の蒸留ガイド

バグ・インシデント・つまずき・想定外の挙動・調査の遠回り、といった経験を扱う。

## このカテゴリ特有の落とし穴

このカテゴリの素材は「特定の事象との戦いの記録」になりやすい。素材をそのまま書くと、同じエラーメッセージに遭遇した人にしか役に立たない記録ができてしまう。

これを避けるには、調査の過程で「自分が何を仮説として持ち、何によって裏切られ、どこで本質に辿り着いたか」を意識的に再構成する必要がある。修正コミットだけ見て書いてはいけない。

## 含めるべき要素

以下の構造で書く。順序は固定だが、該当する素材がない要素は省略可。

### 症状の抽象化（必須）
- 観測された表層的な現象を**条件付き**で書く: 「○○な状況下で、××が起きる」
- 特定のエラーメッセージは具体例として残しつつ、それを抽象化した一段上の記述も並べる
- 例: 「(具体) `NoSuchMethodError: getInstant()` が起動時に出る → (抽象) クラスパス上に同名クラスの古いバージョンが優先されている時に、新しい API を呼ぼうとして起きる」

### 誤った仮説とその反証（重要）
ここがこのカテゴリの肝。「最初こう思ったが違った」を明示的に書く。

- 最初に立てた仮説（何故そう思ったか含めて）
- それが反証された理由（何を見て間違いに気づいたか）

これを書くことで、同じ罠にハマる読者を救う。「正解だけ」では同じ仮説を立てて遠回りする。

### 真因の構造
- 表面ではなく構造として書く（蒸留の原則2）
- なぜこの構造が起きるのかの説明（仕組み・前提・トレードオフ）

### 検知方法
- どうやってこの問題を見つけるか（事後発見の手がかり）
- どうやって事前に防ぐか（テスト・型・lint・運用ルール）

両方の観点を書く。事前防止だけ書くと、既に起きた人を救えない。

### 解決のアプローチ
- 採用した解決方法（抽象化して書く。コード断片は最小限）
- 別の解決方法と、なぜそれを採らなかったか（蒸留の原則3）

### 再発防止に効く構造（あれば）
- このクラスの問題を根本的に減らす設計・運用の変更案
- 「直し方」より「起きにくくする構造」を上位に置く

## このカテゴリで陳腐化しやすい情報

- ライブラリ/フレームワークの特定バージョンに固有の挙動
- スタックトレースの行番号
- 当時のインフラ構成

本体には抽象形で書き、付録に「○年○月時点で確認した具体的環境」として記録する。

## 書く前のセルフチェック

- 「自分のプロジェクトで」を主語にしていないか（一般化されているか）
- 同じエラーメッセージ以外の状況でも、この知見が役立つ場面を最低1つ思いつくか
- 「やった対処」だけになっていないか（仮説と構造が書かれているか）
