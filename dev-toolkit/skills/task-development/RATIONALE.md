## 目的と背景

設計書を作るほどではない小規模タスクを、要件の直接記述だけから TDD で完了させる。td-task-designer が要件を実装計画に整理し、FE/BE の developer エージェントが並列実装、test-runner と requirements-reviewer が検証する自己完結の実行系。

元は「実装設計書のフェーズ実装（パターンA）」と「設計書なしの小規模タスク（パターンB）」の2モード構成だったが、2026-07 の棚卸しで dev-toolkit の設計パイプライン（request-spec〜multi-perspective-design）を削除したのに伴い、設計書ベースの役割を手放して旧パターンB専用に再定義した。

## 中核的な設計判断

### 【load-bearing】共有ファイルを編集しうるタスクは同一並列グループに入れない
- **決定**: 依存関係がなくても、共有の型定義・API契約・設定ファイル・マイグレーションを編集しうるタスク同士は別グループに分離する。
- **防いでいる失敗**: 並列実行するエージェント同士が同一ファイルを編集して競合・上書きが起きる。依存関係の分析だけではこの競合を検出できない。
- **出所**: 初期設計（2モード時代のパターンAから継承）。

### 【load-bearing】同一グループのエージェントは1レスポンスで全て同時起動
- **決定**: グループ内エージェントの逐次起動を禁止事項として明記。
- **防いでいる失敗**: 並列化が骨抜きになり、グループ分けの意味が失われる（明記しないとモデルは安全側に倒して逐次起動しがち）。
- **出所**: 初期設計から継承。

### テスト失敗時の自動修正ループは最大3回で打ち切り
- **決定**: 修正→再テストはユーザー確認なしで自動で回すが、3回で解消しなければ経緯を報告して判断を仰ぐ。
- **防いでいる失敗**: 毎回のユーザー確認による停滞と、無限修正ループによる暴走の両方。
- **出所**: 初期設計から継承。

### 実装開始前に計画のユーザー承認を挟む
- **決定**: td-task-designer の計画を提示し、承認を得てから並列実行に入る。
- **防いでいる失敗**: 要件の解釈ズレのまま複数エージェントが並列実装し、手戻りが増幅される。設計書レビューを省くスキルなので、ここが唯一の方向修正ポイント。
- **出所**: 初期設計から継承。

### スキル本体はコードを書かない（委譲専任）
- **決定**: 実装は必ず developer エージェントに委譲し、本体はオーケストレーションに徹する。
- **防いでいる失敗**: 本体が実装を抱え込むと並列化・役割分担（TDD 実装／テスト実行／要件レビューの分離）が崩れる。
- **出所**: 初期設計から継承。
