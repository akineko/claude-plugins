# 移植可能な規約・方針の抽出

既存プロジェクトのコードベースとドキュメントから、設計方針・ディレクトリ構成・コーディング規約などを「他プロジェクトでも使える形」で抽出し、1 つのマークダウンドキュメントにまとめる。

## このスキルの位置づけ

| | architecture-doc | **extract-conventions** |
|---|---|---|
| 目的 | そのプロジェクトの設計意図を残す | 他プロジェクトに移植可能な形で抽出する |
| 固有名 | 残してよい（むしろ残すべき） | プレースホルダ化する |
| 焦点 | 全体構造・設計判断の「なぜ」 | 横展開できる方針・パターン・ルール |
| 読者 | このプロジェクトに関わる人 | 別プロジェクトで採用を検討する人 |

両者は補完関係にある。設計意図の記録なら `architecture-doc`、移植目的の抽出ならこちらを使う。

## 基本原則

- **コードを正、ドキュメントを参考に**: ドキュメントは意図を、コードは実態を表す。乖離があれば実態を優先しつつ、その乖離自体も記録する
- **推測で埋めない**: 「なぜ」が読み取れない場合、無理に推測せず「明示的な記録は確認できなかった」と書く。捏造は移植先で誤った判断を招く
- **固有名は必ずプレースホルダ化**: ドメイン用語・社名・プロジェクト名・特定の機能名は `<feature>` `<entity>` `<service>` などに置換する
- **適用条件を明示**: 「どんな規模・スタックで成立するか」を書かないと、移植先で形骸化する
- **読者は同じ技術スタックの別プロジェクト**: 言語・フレームワーク前提は説明しない。プロジェクト固有の文脈のみ汎用化対象

## ワークフロー概要

```
入力（対象トピック）
  │
  ├─ Phase 1: 対象の特定とスコープ確定
  │     └─ 引数を解釈し、曖昧なら確認。複数対象の許容判定
  │
  ├─ Phase 2: 出力先の決定
  │     └─ docs/conventions/<topic>.md を基本に、既存ルールがあれば従う
  │
  ├─ Phase 3: 情報の抽出
  │     └─ コード → ドキュメント → コミット履歴 の順に確認、矛盾は記録
  │
  ├─ Phase 4: 汎用化
  │     └─ 固有名のプレースホルダ化、適用条件の整理
  │
  ├─ Phase 5: ドキュメント生成
  │     └─ assets/template.md を雛形に出力
  │
  ├─ Phase 6: 自己検証
  │     └─ 固有名残存チェック、初見可読性チェック
  │
  └─ Phase 7: ユーザー確認・修正
```

## Phase 1: 対象の特定とスコープ確定

### 1.1 入力の解釈

`$ARGUMENTS` を以下のように分類する:

| 入力例 | 判定 |
|---|---|
| 「フロントエンドのディレクトリ構成」 | 明確な単一トピック → そのまま採用 |
| 「エラーハンドリングとログの方針」 | 関連する複数トピック → まとめて 1 ドキュメントとして扱う |
| 「設計方針」「コーディング規約」 | 範囲が広すぎる → 1.2 で具体化を促す |
| （引数なし） | AskUserQuestion で対象を尋ねる |

### 1.2 曖昧な対象の具体化

範囲が広すぎる、または対象領域が判断できない場合は AskUserQuestion で確認する。

確認時は、コードベースを軽く眺めた上で「このプロジェクトに存在する具体的なトピック候補」を提示する。例:

```
対象が広いため絞り込みたいです。以下のどれを抽出しますか？

1. フロントエンドのディレクトリ構成と機能単位の分割ルール
2. API クライアント層のエラーハンドリング方針
3. ログ出力の方針（出力先・レベル・フォーマット）
4. テストの種別ごとの責務分担と配置
```

### 1.3 関連トピックの統合判定

複数トピックを 1 ドキュメントにまとめるかは以下で判断する:

- **まとめる**: 一方の方針が他方の前提になっている、または同じ層に属する（例: ログとエラーハンドリング、FE 構成と画面単位の状態管理）
- **分ける**: 抽出元のレイヤが大きく異なる、または読者が独立して採用しうる（例: FE 構成と DB スキーマ）

判断に迷う場合は AskUserQuestion で確認する。

## Phase 2: 出力先の決定

このスキルが生成するのは「他プロジェクトに移植するための汎用化されたドキュメント」であり、抽出元プロジェクトでそのプロジェクト固有のドキュメントとして運用する性格のものではない。そのため、抽出元プロジェクトの既存ドキュメント配置ルール（例: `docs/libs/`、`docs/architecture/` など、特定ライブラリ・領域のガイドが集約された場所）に揃えてはいけない。揃えると「このプロジェクト用のガイド」と誤読され、移植目的の位置づけが失われる。

以下の優先順位で配置先を決定する:

1. **ユーザーがファイル名・配置先を指定している場合**: その指定をそのまま使う
2. **指定がない場合**: 推奨パス `docs/conventions/<topic>.md` を使う
   - `<topic>` は対象に応じた kebab-case（例: `frontend-directory-structure.md`、`error-handling.md`、`msw-handler-structure.md`）
   - 複数トピックをまとめる場合は両者を表す名詞句（例: `error-handling-and-logging.md`）
3. **決定したパスをユーザーに提示して確認する**

抽出元プロジェクトに `docs/conventions/` 相当の「移植可能な規約を集めたディレクトリ」が既に存在する場合に限り、そこに揃えてよい。プロジェクト固有のガイド集約ディレクトリ（`docs/libs/` など）は対象外。

## Phase 3: 情報の抽出

### 3.1 抽出元の優先順位

以下の順で確認する。**コードが正、ドキュメントは意図の補強、コミット履歴は経緯の補強**として扱う。

1. **コード**: 実態。ディレクトリ構成、命名、依存方向、コーディングパターンを直接観察する
2. **ドキュメント**: 意図の補強。`README`・`CLAUDE.md`・`docs/`・`ADR`・`CONTRIBUTING` 等
3. **コミット履歴・PR 履歴**: 経緯の補強。「なぜそうしたか」がコミットメッセージに残ることがある

### 3.2 矛盾の検出と扱い

ドキュメントとコードに乖離がある場合は次のいずれかとして扱う:

- **ドキュメントが古い**: コード実態を採用。乖離を「具体的な構成・ルール」セクションに脚注として残す
- **コードが部分的に逸脱**: 大半のコードが従う方針を採用。逸脱箇所は「アンチパターン例」として活用できる
- **判断不能**: ユーザーに確認する

### 3.3 codebase-investigator の活用

抽出対象が複数レイヤーにまたがる、またはコードベース調査が大きい場合は `codebase-investigator` エージェントに調査を委ねる。

調査プロンプトでは以下を指示する:

```
以下のトピックに関する規約・方針を抽出するための調査を行え。
出力は他プロジェクトでの採用検討に使う想定なので、固有名（社名・プロダクト名・特定機能名）には印を付けて報告せよ。

## トピック
<対象トピック>

## 調査の観点

1. **実態（コード）**: ディレクトリ構成、命名規則、レイヤ分割、依存方向、コーディングパターン
2. **意図（ドキュメント）**: README・CLAUDE.md・docs/ で言及されている方針・ルール
3. **乖離**: ドキュメントとコードで食い違う点
4. **適用条件の手がかり**: なぜこの方針か、どの規模・性質で成立しているか（コードや履歴から推測できる範囲で）
5. **採用していない選択肢**: 「検討したが不採用」と読み取れる記述や、コミット履歴上の方針転換

## 出力形式

- 事実とそこから読み取れる解釈を分けて報告せよ
- 「明示的な根拠なし」の場合はそう書け。推測で埋めない
```

## Phase 4: 汎用化

### 4.1 固有名のプレースホルダ化

抽出した内容から以下を機械的に置換する:

| 種類 | 置換先 |
|---|---|
| 機能名・ドメイン名（例: `Invoice`, `OrderHistory`） | `<feature>` または `<entity>` |
| サービス名・社内システム名 | `<service>` |
| プロダクト名・社名 | `<product>` `<organization>` |
| 特定 API のエンドポイント名 | `<resource>` |
| 特定の DB テーブル名 | `<entity>` |

ただし、**スタック由来の用語は残す**（同じ技術スタック前提のため）:
- フレームワーク名（React, Vue, NestJS, Prisma 等）
- 標準的なディレクトリ名（`components`, `hooks`, `pages`, `services` 等）
- 言語固有の概念（`interface`, `enum`, `trait` 等）

### 4.2 適用条件の整理

以下の観点を「流用時の注意点・適用条件」セクションに記述する:

- **規模**: 何画面・何エンドポイント程度のプロジェクトを想定しているか
- **チーム規模**: 単独 / 数名 / 数十名で機能するか
- **前提技術**: フレームワーク・主要ライブラリの前提
- **アンチパターン**: 移植時に陥りがちな誤適用パターン

明示的な根拠が無い項目は、コードベースから推測できる範囲（コードベースの行数・モジュール数・テスト戦略の網羅度など）で書く。推測である旨を明示すること。

## Phase 5: ドキュメント生成

`assets/template.md` をコピーし、以下のルールで埋める。

### 5.1 セクションごとの記述方針

| セクション | 書き方 |
|---|---|
| 概要 | 1〜2 文。対象の範囲を明示。「扱わないこと」も 1 行で |
| 採用している方針・パターン | 箇条書き。各項目は太字タイトル + 1 行要約 |
| 設計判断の理由・背景 | 各方針について「なぜ」を散文で。根拠（コード/ドキュメント/履歴）を添える |
| 採用していない選択肢 | コードや履歴から読み取れた範囲のみ記述。読み取れない場合はセクションごと削除 |
| 具体的な構成・ルール | ディレクトリツリー・命名規則・コーディングパターンを具体的に。固有名はプレースホルダ化 |
| サンプルコード | 任意。汎用化したコード片を提示。型名・関数名もプレースホルダ化 |
| 流用時の注意点・適用条件 | 規模・前提・アンチパターンを箇条書き |
| 関連情報 | 関連ドキュメントや外部資料へのリンク |

### 5.2 不要なセクションの扱い

抽出元から該当する情報が得られないセクションは以下のいずれかを選ぶ:

- **セクションごと削除**: 「サンプルコード」など、無くても読者が困らないものはこちら
- **一文だけ残す**: 「採用していない選択肢」「関連情報」など、読者が「探したが見つからなかった」と知りたい可能性があるものはこちら。例: 「明示的に『採用しなかった』と記録された選択肢はコード・ドキュメント上では確認できなかった。」

空セクション（見出しだけ残して中身が無い）は読者の混乱を招くので避ける。特に「採用していない選択肢」「サンプルコード」「関連情報」は任意で扱ってよい。

### 5.3 コード片の扱い

サンプルコードを載せる場合は以下を満たすこと:

- 固有の型名・関数名はプレースホルダ化されている
- そのまま貼っても動く程度に完結している（依存関係の前提は明記）
- 5〜30 行程度。長すぎる場合は要点のみ抽出する

## Phase 6: 自己検証

ドキュメント生成後、以下を必ずチェックする。1 つでも該当すれば修正する。

### 6.1 固有名残存チェック

- [ ] 機能名・ドメイン名がそのまま残っていないか（grep で確認）
- [ ] 社名・プロダクト名が含まれていないか
- [ ] 特定の URL・エンドポイント・テーブル名が残っていないか

抽出元のリポジトリ名・ディレクトリ名から候補語を機械的に拾い、本文中に残っていないか確認する。

### 6.2 初見可読性チェック

- [ ] 「このプロジェクトでは」のような自己言及表現が残っていないか
- [ ] 「最近変更された」「新しく追加した」のような時間依存の記述がないか
- [ ] 抽出元プロジェクトを知らない読者が、用語の説明なしで読めるか

### 6.3 推測混入チェック

- [ ] 「おそらく」「だと思われる」など曖昧な根拠で書かれた断定がないか
- [ ] 「なぜ」の説明が、コードや記録から読み取れる範囲を超えていないか

推測で書いた箇所は「明示的な根拠は確認できなかった」と書き直すか、削除する。

## Phase 7: ユーザー確認・修正

### 7.1 ドキュメントの提示

生成したドキュメントの概要を簡潔に提示する:

- 対象トピックと出力先パス
- カバーした方針の見出しを箇条書き
- 推測や保留として残した項目があればその一覧
- 自己検証で気になった点があれば申告

提示後、AskUserQuestion で確認:

```
規約抽出ドキュメントを作成しました: <パス>

内容を確認して、修正したい箇所があれば指摘してください。
特に以下を見ていただきたいです:
- プロジェクト固有の用語が残っていないか
- 設計判断の「なぜ」が誤っていないか
- 適用条件の前提に違和感がないか

問題なければ「OK」と回答してください。
```

### 7.2 フィードバック対応

| ユーザーの回答 | アクション |
|---|---|
| 「OK」等 | 完了 |
| 修正指示あり | 指示に基づいて修正し、再度 7.1 に戻る |
| 追加調査が必要 | Phase 3 から該当箇所を再調査する |

修正時も Phase 6 の自己検証を再度実施する。

## 使用例

### 例 1: 単一トピックを引数で指定

ユーザー: `/extract-conventions フロントエンドのディレクトリ構成`

実行:
1. 対象は明確 → そのまま採用
2. 出力先 `docs/conventions/frontend-directory-structure.md` を提示
3. コードベースを調査し、ディレクトリ構成と命名規則を抽出
4. 機能名をプレースホルダ化してテンプレートに流し込む
5. 自己検証 → ユーザーに確認

### 例 2: 関連する複数トピック

ユーザー: `/extract-conventions エラーハンドリングとログの方針`

実行:
1. 関連トピックなので 1 ドキュメントにまとめる旨を提示
2. 出力先 `docs/conventions/error-handling-and-logging.md` を提示
3. エラーハンドリング層とログ出力層の両方を調査
4. 共通する設計思想（例: 例外境界、構造化ログ）も抽出
5. 自己検証 → ユーザーに確認

### 例 3: 範囲が広すぎる入力

ユーザー: `/extract-conventions 設計方針`

実行:
1. 範囲が広いので AskUserQuestion で具体化
2. コードベースから候補を提示（FE 構成 / BE 構成 / エラーハンドリング / テスト方針 など）
3. 選択された対象で Phase 1.1 から再開

## トラブルシューティング

### 抽出元に方針らしきものが見当たらない

原因: コードベース全体に一貫したパターンがなく、ファイルごとに書き方が違う

解決策: ユーザーに「明示的な規約として定着していない可能性がある」と伝え、どう扱うか確認する。選択肢:
- 最も多い書き方を「事実上のパターン」として記述する（その旨明示）
- 抽出を中止し、方針が無いという事実を報告する

### ドキュメントとコードが大きく乖離している

原因: ドキュメントが古い、または建前と実態が違う

解決策: コード実態を主とし、ドキュメントとの差分を「具体的な構成・ルール」セクションに記録する。差分自体が「移植先で陥りがちな失敗」のヒントになることが多いので、「流用時の注意点」にも反映する。

### 「なぜ」が読み取れない

原因: 設計判断の意図がコード・コミット・ドキュメントのどこにも残っていない

解決策: 推測で埋めず、「明示的な根拠は確認できなかった」と明記する。読者は別プロジェクトで採用判断する立場なので、根拠の有無は重要な情報。
