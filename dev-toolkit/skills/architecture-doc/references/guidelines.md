# アーキテクチャドキュメント ガイドライン

## 目的

アーキテクチャドキュメントは、コードを読むだけでは理解しにくい**全体構造**と**拡張時のルール**を伝えるために書く。
コードの転記ではなく、構造の見取り図と運用上のガイドを残すことが目的。

---

## ドキュメント種別

対象に応じて 2 種別を使い分ける。

### 種別 A: 設計意図中心型

- 対象: アプリ全体 / 機能設計 / パッケージのレイヤ構成
- 主軸: 全体構造と概観
- 含めるもの: レイヤー / 責務 / 依存方向 / データフロー / 命名・配置の原則

### 種別 B: 拡張ガイド付き型

- 対象: 監査ログ / ディレクトリ構成 / エラー種別 / マイグレーション規約 / 多言語キー
- 主軸: 既存の構造 + 新規追加時の手順
- 含めるもの: 既存種別の概観 / 配置・命名・必須項目 / 追加手順 / レビュー観点

判別の目安: 「種別の集合があり、今後も新規追加が続く」なら B。そうでなければ A。

---

## 記載すべき内容

- **全体構造と関係性**: 複数ファイル・レイヤーにまたがる構造の概観
- **拡張時のルール**（種別 B のみ）: 新規追加時の配置・命名・必須項目・手順
- **制約・前提条件**: 設計の背景にある技術的制約やビジネス要件

### 設計判断の扱い

専用セクションは作らず、以下のいずれかで扱う。

- **小さな判断**: 概観/全体構造の説明文に「〜にしている。理由: 〜」の形で織り込む
- **大きな判断**: `adr-doc` スキルで独立 ADR として記録する。本ドキュメントからは「関連 ADR」サブセクションでリンクする

「設計判断っぽい説明」が独立した節として並び始めたら、構造的に蓄積が始まっているサイン。概観への織り込み・ADR 化のいずれかで分散させる。

---

## 記載すべきでない内容

- **ディレクトリツリーやファイル一覧の全列挙**: `tree` や `ls` で得られる情報と同等
  - 種別 B の拡張ガイドで「代表的なツリー」を示すのは可
- **コンポーネント名・Props・型定義の転記**: コードを読めばわかる事実の列挙
- **hook のシグネチャや実装コードの全文**: 変更のたびに更新が必要になる
- **個別の API エンドポイントやクエリキーの詳細**: 該当層のコードで十分
- **独立した「設計判断」セクション**: 上記の通り、別の置き場に分散させる

---

## 粒度の基準

### 適切な粒度

- ファイル名・関数名への言及は「代表例」としての参照に留め、網羅的な列挙はしない
- 設計パターンの説明は**概念と責務**を中心に書き、コード片は最小限にする
- **アーキテクチャの方針変更時のみ更新が必要**な抽象度で書く

### 粒度が細かすぎるサイン

以下に該当する場合、コード変更のたびに更新が必要な内容になっている。抽象度を上げるか、記載を削除する。

- コンポーネントや hook の追加・リネームのたびに更新が必要
- Zod スキーマや hook の引数シグネチャなど、型定義の転記がある
- データフローの説明が個別の API 呼び出しやキャッシュキーのレベルまで踏み込んでいる

---

## メンテナンス

### 更新タイミング

- **アーキテクチャの方針が変わったとき**（新パターン導入、責務分離の変更など）
- **拡張ガイドのルールが変わったとき**（種別 B、命名規則の変更など）
- **設計判断の前提が変わったとき**（技術的制約の解消、要件変更など）

以下の場合は更新不要：

- ファイルの追加・リネーム・移動
- hook やコンポーネントのインターフェース変更
- リファクタリング（設計方針が変わらない場合）

### ADR との連動

新しい大きな設計判断が発生した場合は `adr-doc` で ADR を作成し、本ドキュメントの「関連 ADR」セクションにリンクを追加する。本ドキュメント側に判断の本文を書き写さない（SSoT を ADR 側に寄せる）。
