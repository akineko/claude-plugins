# アーキテクチャドキュメントの作成

既存のコードベースや完成した設計を調査し、設計の全体像と運用ガイドラインを伝えるアーキテクチャドキュメントを作成する。

## 基本原則

このスキルが作るドキュメントは「コードの転記」ではなく「コードからは読み取りにくい全体像と運用ガイドの記録」。
コードを読めばわかる事実（ファイル一覧、型定義、API 仕様）は書かず、構造の見取り図と拡張時のルールを残す。

ドキュメントの粒度は「アーキテクチャの方針変更時のみ更新が必要」な抽象度を目指す。コンポーネントの追加やリネームで更新が必要になるなら、それは細かすぎる。

### 設計判断の扱い

**「## 設計判断」専用セクションは作らない**。理由：
- セクションを置くと判断が積み上がり、結果として「設計判断を全部読まないと全容が掴めない」状態になる
- 小さな判断は概観の説明文に「〜にしている。理由: 〜」の形で自然に織り込む
- 独立した節として残したい大きな判断は **`adr-doc` スキル** で ADR 化する

詳細なガイドラインは `references/guidelines.md` にある。判断に迷ったら参照すること。

## 関連スキルとの使い分け

| | architecture-doc | adr-doc | extract-conventions |
|---|---|---|---|
| 目的 | プロジェクト固有の全体像・拡張ガイドの記録 | 1 件の設計判断を独立 ADR として記録 | 他プロジェクトに移植可能な形で抽出 |
| 出力単位 | 1 領域 1 ファイル | 1 判断 1 ファイル | 1 トピック 1 ファイル |
| 固有名 | 残す | 残す | プレースホルダ化する |

## ワークフロー概要

```
入力（対象パス or テキスト）
  │
  ├─ Phase 1: 初期化（入力判定・種別判定・スコープ確認・出力先決定）
  │
  ├─ Phase 2: コードベース調査（codebase-investigator）
  │
  ├─ Phase 3: ドキュメント生成（種別に応じたテンプレート）
  │
  ├─ Phase 4: ユーザー確認・修正
  │
  成果物: 配置先に決定した .md ファイル
```

## Phase 1: 初期化

### 1.1 入力の判定

`$ARGUMENTS` の内容から入力種別を判定する:

| 入力 | 判定方法 | アクション |
|------|---------|-----------|
| ディレクトリパス | 存在するディレクトリ | そのディレクトリを調査対象とする |
| ファイルパス | 存在するファイル（.md 等） | 設計書・仕様書として読み込み、関連コードを調査対象とする |
| テキスト | パスでない文字列 | テキストからドキュメント化対象を推定する |
| 空 | — | AskUserQuestion で入力を求める |

### 1.2 ドキュメント種別の判定

対象から次の 2 種別を判定する。

| 種別 | 主軸 | 対象例 |
|---|---|---|
| A. 設計意図中心型 | 全体構造と概観 | アプリ全体 / 機能設計 / パッケージのレイヤ構成 |
| B. 拡張ガイド付き型 | 全体構造 + 新規追加時の手順 | 監査ログ / ディレクトリ構成 / エラー種別 / マイグレーション規約 / 多言語キー |

判定基準：
- 対象に「種別の集合（ログ種別、エラー種別、キーの集合など）が並ぶ構造」があり、新規追加が今後も継続的に発生する → **B**
- 対象が「単一のシステム構造（機能・アプリ全体・パッケージ）」で、拡張ガイドの需要が薄い → **A**
- 曖昧な場合は AskUserQuestion で確認する

### 1.3 スコープと出力先の決定

スコープを 4 段で扱い、デフォルト配置先を決める。

| スコープ | 例 | デフォルト配置先 |
|---|---|---|
| プロジェクト全体 | モノレポルート | `ARCHITECTURE.md` または `docs/architecture.md` |
| パッケージ単位 | `apps/web/` 等 | `{package}/docs/architecture.md` |
| 機能単位 | 1 つの複雑な機能 | `docs/features/{feature}/architecture.md` |

決定の優先順位:

1. **プロジェクトのルールを確認**: CLAUDE.md、README、既存のドキュメント構造（`docs/` や `ARCHITECTURE.md` の有無）を軽く調べる
   - 明示的なルールがあれば従う
   - 既存の `ARCHITECTURE.md` や `docs/architecture/` があれば、その配置に揃える
2. ルールも前例もなければ上記デフォルトを使う
3. パスをユーザーに提示して確認する

### 1.4 ドキュメント化のスコープ確認

対象が広い場合（リポジトリ全体、複数サービスにまたがる等）、AskUserQuestion でスコープを絞る:

```
ドキュメント化の対象が広範囲です。以下のどの範囲を対象としますか？
1. {候補1} — {簡潔な説明}
2. {候補2} — {簡潔な説明}
3. 全体の概観

番号で指定してください。
```

単純な CRUD 画面など設計判断のない領域は、ドキュメントを作成する意義が薄い。その場合はユーザーにその旨を伝え、本当に必要か確認する。

## Phase 2: コードベース調査

`codebase-investigator` に調査を依頼する。種別に応じて観点を切り替える。

### 2.1 共通観点

- **全体構造と責務分離**: レイヤー構成、モジュール構成と各レイヤー間の依存方向
- **データフロー**: 主要なデータの流れ（概念レベル）
- **制約と前提**: 技術的制約、外部サービスの制約、パフォーマンス・セキュリティ要件
- **構造の背後にある意図**: コード・コミット・ドキュメントから読み取れる範囲で

### 2.2 種別 A 向けの追加観点

- **パターンの選択**: 使用しているデザインパターンと適用箇所、一貫したパターンと例外
- **境界の設計意図**: レイヤー間で何が許され何が禁止されているか

### 2.3 種別 B 向けの追加観点

- **既存の種別/配置の集合**: 例えばログ種別、エラー種別、ディレクトリ配置パターンの一覧
- **拡張時に守られているルール**: 命名、必須項目、配置先、依存方向、登録手順
- **レビュー観点**: PR レビューで指摘されてきた典型的な逸脱

### 2.4 ファイル入力（設計書）の場合の追加観点

- 設計書に記載された設計判断が実際のコードでどう実現されているか
- 設計書と実装の乖離があれば、その事実

### 2.5 調査の実行

対象範囲に応じて単一または並列で調査する。

```
Agent(
  subagent_type="codebase-investigator",
  prompt=下記の調査プロンプト
)
```

調査プロンプトには上記観点を含め、「個々のファイル名・関数名・型定義の網羅的な列挙は不要。構造の代表例として必要最小限の具体名に言及するに留める」と明記する。

## Phase 3: ドキュメント生成

### 3.1 テンプレート（種別 A: 設計意図中心型）

```markdown
# {対象の名称}

## 概要

{この領域が何をするか、1-2 文}

## アーキテクチャ概観

{レイヤー構成 / 責務分離 / 依存方向 / 主要なデータフロー / 命名・配置の原則}
{設計判断の Why は説明文に織り込む。例:}
{- 「クエリキーは entities 層に置いている。shared 層は『ドメイン非依存』の制約があるため」}
{- 「pages がデータ取得を担い、widgets は props 駆動。取得状態の分岐を 1 箇所に集約するため」}

{Mermaid 図が有効な場合は使用する}

## 制約と前提条件

{設計の背景にある技術的制約やビジネス要件、運用上の前提}

## 関連ドキュメント

### 関連 ADR
- [ADR-NNN: タイトル]({path})

### その他
- {関連する設計書やドキュメントへのリンク}
```

### 3.2 テンプレート（種別 B: 拡張ガイド付き型）

```markdown
# {対象の名称}

## 概要

{この領域が何をするか、1-2 文}

## 全体構造

{既存の種別・配置の集合の概観}
{設計判断の Why は説明文に織り込む。例:}
{- 「監査ログは write-only。改ざん検知のため後段でハッシュチェーンを取る」}
{- 「ディレクトリは FSD レイヤーに揃える。app → pages → widgets → features → entities → shared の依存方向を保つため」}

## 拡張ガイド

新規に {種別 / ファイル / エンドポイント / ...} を追加する際の手順とルール。

- **配置先**: {どこに置くか}
- **命名規則**: {命名のルール、kebab-case / PascalCase の使い分け}
- **必須項目**: {含めるべきフィールド、ファイル、export}
- **手順**: {1. 〜 2. 〜 3. 〜}
- **レビュー観点**: {PR レビューで確認すべきこと}

## 制約と前提条件

{拡張時に固定とみなしてよい技術的制約・運用上の前提}

## 関連ドキュメント

### 関連 ADR
- {既存 ADR があればリンク}

### その他
- {関連する設計書やドキュメントへのリンク}
```

「関連 ADR」「その他」はリンクが無ければサブ見出しごと省略してよい。

### 3.3 記述ルール

- **コードを読めばわかる事実を書かない**: ファイル名・関数名は代表例として最小限に言及する。網羅的なリストは作らない
- **小さな設計判断は説明文に織り込む**: 「〜にしている。理由: 〜」の形で、概観/全体構造の中に短く書く
- **大きな設計判断は ADR に外出しする**: 独立した節として書きたくなったら `adr-doc` スキルを使う
- **コード片は最小限**: パターンの説明は概念と責務で行う
- **概念図を活用する**: Mermaid 記法で構造やフローを視覚化する

### 3.4 設計判断の独立節を作らないルール（重要）

`## 設計判断` という見出しを禁止するだけでは不十分。以下の**カモフラージュパターン**も同じく禁止する。

#### 禁止パターン

1. **`Why / How to apply` 型の対構造を持つ独立節**
   - 「### {判断のタイトル}」配下に `**Why:**` `**How to apply:**` を並べる構造そのものを作らない
   - フォーマットがあると LLM もユーザーも埋めたくなり、判断が積み上がる構造的バイアスを生む

2. **「◯◯の方針」「◯◯の判断」のような領域別 H2 グループ**
   - `## レイヤー分離の方針` `## ピン表示の実装方針` のような H2 で領域別に判断を寄せ集めるのは、結局「設計判断セクションを領域別に分割しただけ」
   - 領域別のサブセクションを切るなら `## アーキテクチャ概観` 配下に `### レイヤー構成` `### 状態管理` のように内包する

3. **`### {判断}` 形式の独立節が 3 つ以上並ぶ構成**
   - 概観配下や全体構造配下に判断節が 3 つ以上並んだら、ADR への外出しを強く検討する

#### Bad / Good

**Bad（独立節として並べる）**
```markdown
### Overlay ルートは pointer-events: none、可視アイコンのみ auto

**Why:** これを忘れると overlay が canvas 全体を覆い、操作を塞ぐ。
**How to apply:** 最外殻 div に必ず pointer-events-none を指定する。
```

**Good A（概観の説明文に織り込む）**
```markdown
## アーキテクチャ概観

...overlay の最外殻 div は `pointer-events-none` を必須にしている（canvas
のドラッグ操作を塞がないため）。個別アイコンは subscribeFrame 内で可視時のみ
`auto` に切り替える。
```

**Good B（大きな判断は ADR にする）**
```markdown
## アーキテクチャ概観

...USDA パーサはホワイトリスト方式で実装している（詳細は [ADR-005](...)）。

## 関連ドキュメント

### 関連 ADR
- [ADR-005: USDA パーサはホワイトリスト方式](decisions/005-usda-whitelist-parser.md)
```

### 3.5 粒度チェック

ドキュメント生成後、以下を自己チェックする。1 つでも該当すれば修正する:

- [ ] コンポーネントやファイルの追加・リネームで更新が必要になる記述がないか
- [ ] 型定義やインターフェースの転記がないか
- [ ] 個別の API エンドポイントやキャッシュキーに言及していないか
- [ ] ディレクトリツリーの全列挙がないか（種別 B の代表ツリーは可）
- [ ] **`Why / How to apply` 型の対構造を持つ節があるか** → 説明文に織り込むか ADR 化する
- [ ] **`### {判断のタイトル}` 形式の独立節が 3 つ以上並んでいるか** → ADR 化を強く推奨
- [ ] **`## ◯◯の方針` `## ◯◯の判断` のような領域別判断グループの H2 があるか** → 概観配下のサブセクションに移すか ADR 化する

## Phase 4: ユーザー確認・修正

### 4.1 ドキュメントの提示

生成したドキュメントの概要を簡潔に提示する:

- 種別（A or B）と全体の構成（見出し一覧）
- 概観で言及した主要な要素
- 種別 B の場合は拡張ガイドのカバー範囲

提示後、AskUserQuestion で確認:

```
アーキテクチャドキュメントを作成しました: {成果物パス}

内容を確認して、修正したい箇所があれば指摘してください。
問題なければ「OK」と回答してください。
```

### 4.2 フィードバック対応

| ユーザーの回答 | アクション |
|---|---|
| 「OK」等 | Phase 5 へ |
| 修正指示あり | 指示に基づいて修正し、再度 4.1 に戻る |
| 追加調査が必要 | Phase 2 の追加調査を実行してから修正 |
| 「この判断は ADR として残したい」 | `adr-doc` スキルの利用を案内する |

修正時も粒度チェック（3.4）を再実施する。

## Phase 5: 完了

1. 成果物のファイルパスを案内する
2. ドキュメントの概要を 3-5 行で提示する
3. メンテナンスの指針を案内する: 「アーキテクチャの方針が変わったときに更新してください。ファイルの追加・リネーム程度では更新不要です」
4. 独立 ADR にしたい設計判断が残っていれば、`adr-doc` スキルでの追加記録を案内する
