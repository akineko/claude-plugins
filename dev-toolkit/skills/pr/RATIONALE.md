# pr 設計ノート

> SKILL.md=「何をするか（指示）」/ 本ファイル=「なぜこの形か（意図・解釈・却下案・守る失敗）」。実行時は非読込。更新時に改訂する。SKILL.md は再掲せず参照に留める。

## 目的と背景

push 済みのカレントブランチから GitHub の PR を作成する作業を自動化する。`commit`（コミット作成）の下流に位置し、コミット履歴と差分から PR のタイトル・本文を生成する。push 自体はユーザーの責務（どのコミットまで上げるか・force push の要否などはユーザー判断）とし、スキルは push しない方針。

## 中核的な設計判断

### 【load-bearing】push はスキルが行わず、未push なら作成を中止してユーザーに依頼
- **決定**: Step 1 で push 状態を検証し、未push・未push コミットありなら PR を作成せず push を依頼して終了。`git push` は禁止事項。
- **却下した代替案**: スキルが自動 push してから PR 作成 → どこまで・どのリモートへ push するかはユーザー判断（force push やブランチ保護の絡み）であり、勝手な push は外向きで取り返しがつきにくい。
- **防いでいる失敗**: 未push 状態での `gh pr create`（リモートに head が無く失敗 or 古い状態で PR 作成）、意図しない push。
- **出所**: ユーザー要望（2026-06）。

### 【load-bearing】base の既定は GitHub のデフォルトブランチ（main 固定ではない）
- **決定**: base 省略時は `gh repo view --json defaultBranchRef` で取得した名前を使う。ユーザー明示時はそれを優先。
- **却下した代替案**: main をハードコード → デフォルトブランチが master/develop 等に変更されているリポジトリで誤った base になる。
- **防いでいる失敗**: 存在しない/誤った base への PR 作成。
- **出所**: ユーザー要望（2026-06、「main だが設定が変わっていれば設定値」）。

### context: fork（確認なしで即作成）
- **決定**: `commit` と同じく `context: fork`。PR 内容の作成前確認は行わず、合意フォーマットで即作成。
- **却下した代替案**: draft を提示して承認後に作成 → ユーザーが「commit と同じ思想（確認なし即作成）」を選択（2026-06）。fork は自己完結処理で本流コンテキストを汚さない利点があり、結果（PR URL）を返すだけのこのスキルに適合。
- **防いでいる失敗**: fork でも「前提条件未達による中止＋依頼」は report-and-terminate として成立する（commit が「ステージング無し→終了」を fork 内で行うのと同じ）。内容確認の省略と前提条件チェックは別物として禁止事項に明記。
- **出所**: ユーザー選択（2026-06）。

### 【load-bearing】本文は why（背景・理由）を変更点より前に置き、原則必ず書く
- **決定**: 既定フォーマットの順序を 概要 → 背景・理由 → 主な変更点 → 確認方法 とする。さらに背景・理由は trivial な変更（typo/format/単純な文言）以外では**省略不可**とし、「実装が単純/自明だから省略」を明示的に禁じる。
- **却下した代替案**: (a) 概要 → 主な変更点 → 背景（標準的な並び）→ ユーザーが「背景・理由を主な変更点の上に」と明示（2026-06）。(b) 「意図が自明なら背景・理由も省略可」という緩い省略許容（iteration-1 の初版）→ 後述の eval で全 PR から背景・理由が脱落したため棄却。
- **防いでいる失敗**: iteration-1 eval で実証 — PR を作った with_skill 3件すべてが背景・理由を省略し、ユーザーが最優先した why-first が機能しなかった。原因は「自明なら省略可」を LLM が「実装が単純＝省略」と広く解釈したこと。why は実装の単純さと無関係、と明記して再発を防ぐ。
- **出所**: ユーザー要望（2026-06）＋ iteration-1 eval（eval-1/3/4 で背景・理由が脱落）→ ユーザー選択「原則必ず含める」（2026-06）。

### PR タイトルの scope はコミットの scope を踏襲
- **決定**: ブランチのコミット群が共通 scope を持つなら、単一リポでも PR タイトルにその scope を残す。scope が無い場合のみ `commit` の monorepo 限定ルールに従う。
- **却下した代替案**: `commit` と完全同一（monorepo のみ scope）→ iteration-1 eval-1 で `feat(profile):` のコミット群から PR タイトルが `feat:` に scope を落とした。コミットが既に確立した分類情報を PR で捨てるのは情報損失。
- **防いでいる失敗**: コミットが持つ scope の脱落（eval-1 で実証）。
- **出所**: iteration-1 eval（eval-1）→ ユーザー選択「コミットの scope を踏襲」（2026-06）。

### 既存 PR テンプレートを既定フォーマットより優先
- **決定**: `.github/PULL_REQUEST_TEMPLATE.md` 等が存在する場合、そのテンプレート構造を骨子にし、既定フォーマットは使わない。
- **防いでいる失敗**: リポジトリ規約（テンプレート）を無視した本文生成。汎用スキルとして他リポジトリで使ったときに浮く。
- **出所**: 設計判断（汎用性確保）。

### 既存 open PR があれば重複作成しない
- **決定**: Step 3 で `gh pr list --head` を確認し、あれば URL 案内のみで終了。
- **防いでいる失敗**: 同一ブランチに対する重複 PR 作成。
- **出所**: 境界チェック（gh は重複作成自体は弾くがエラーになる前に検知して案内する方が親切）。

### Conventional Commits の type 表は commit スキルを参照（再掲しない）
- **決定**: タイトルの type/scope の詳細規約は同プラグインの `commit` スキルに委譲し、pr 側は要点のみ記載。
- **却下した代替案**: type 表を pr 側にも複製 → 更新漏れの温床。同一プラグイン内の参照は CLAUDE.md で許容されている。
- **出所**: リポジトリ規約（1 情報 1 箇所）。

## 解釈・仮定（要確認）

- **本文の言語**: 明示要望が無かったため「リポジトリの既存コミット/PR の言語に合わせる、判別不能なら日本語」と解釈。⚠️ 常に日本語固定にしたい場合は要調整。
- **確認方法セクション**: ⚠️ チェックボックス（`- [ ]`）ではなく素の箇条書きにした。自動生成された項目にチェックボックスを付けると「未確認の TODO」に見えるため。テンプレート側にチェックボックスがあればそれに従う。
- **remote の仮定**: upstream 未設定時は `origin` を仮定。⚠️ 複数リモート/fork 運用では誤る可能性があるが、未push なら結局 push 依頼で止まるので実害は限定的。
