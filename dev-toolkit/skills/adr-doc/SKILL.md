# ADR の作成

個別の設計判断を Architecture Decision Record として 1 ファイル 1 件で記録する。

## 基本原則

- **1 ADR = 1 判断**: 複数の独立した判断を 1 ファイルにまとめない
- **判断時点の事実のみを書く**: 後で覆った場合は新しい ADR で Supersede する。元の ADR は履歴として残す
- **代替案は実際に検討されたものだけ書く**: 推測で埋めない。読み取れない場合は「明示的な記録は確認できなかった」と明記
- **固有名は残す**: プロジェクト固有の用語・ファイル名・モジュール名は具体的に書いてよい（移植目的ではないため）

## 関連スキルとの使い分け

| | adr-doc | architecture-doc |
|---|---|---|
| 単位 | 1 判断 1 ファイル | 1 領域 1 ファイル |
| 主軸 | 1 つの決定の背景・選択肢・結果 | 全体構造と拡張ガイド |
| 性格 | 時点記録（決定の経緯） | 現状記録（いまどうなっているか） |
| 更新 | 基本不変。新判断は新 ADR | 構造変更時に更新 |

`architecture-doc` 内に独立した「設計判断」セクションが並んでいる場合、それらを個別 ADR に切り出すのにこのスキルを使う。

## ワークフロー概要

```
入力（判断のタイトル / 説明 / 関連コード）
  │
  ├─ Phase 1: 配置先と番号の決定
  │
  ├─ Phase 2: コンテキスト調査（必要なら codebase-investigator）
  │
  ├─ Phase 3: ADR ドラフト生成
  │
  ├─ Phase 4: ユーザー確認・修正
  │
  ├─ Phase 5: 関連 architecture.md への追記提案
  │
  成果物: {decisions_dir}/NNN-{topic}.md
```

## Phase 1: 配置先と番号の決定

### 1.1 配置先の判定

優先順位:

1. **既存の ADR ディレクトリを探す**: 以下を順に確認する
   - `docs/decisions/`
   - `docs/adr/`
   - `decisions/`
   - `adr/`
   - パッケージ・機能スコープなら `{scope}/docs/decisions/` 等も確認
2. **ユーザーが配置先を指定している場合**: その指定をそのまま使う
3. **見つからない場合**: スコープに応じてデフォルトを提案する

| スコープ | デフォルト配置先 |
|---|---|
| プロジェクト全体 | `docs/decisions/` |
| パッケージ単位 | `{package}/docs/decisions/` |
| 機能単位 | `docs/features/{feature}/decisions/` |
| モジュール単位 | 親プロジェクトの `decisions/` に集約するか、`{module}/decisions/` に置くかを確認 |

決定したパスをユーザーに提示して確認する。

### 1.2 番号採番

配置先の既存 ADR を走査し、ファイル名の先頭にある番号の最大値 + 1 で採番する。3 桁ゼロパディング（例: `001`, `002`）。

採番時の注意:
- 番号は不連続になっても採番のままにする（ADR を削除しない原則のため、通常は連続する）
- 既存番号と衝突しないことを確認する

### 1.3 ファイル名

`NNN-{kebab-case-topic}.md` 形式。トピックは判断のタイトルから短く生成する。

例:
- `001-error-handling.md`
- `002-auth-method.md`
- `003-frontend-state-management.md`

長すぎるトピック名は要点だけ抜き出す（`007-use-tanstack-query-for-server-state.md` ではなく `007-server-state-tanstack-query.md` のように）。

## Phase 2: コンテキスト調査

判断の前提となるコード・既存 ADR・設計ドキュメントを調査する。範囲が広い場合は `codebase-investigator` に委ねる。

### 2.1 調査観点

- **背景**: なぜこの判断が必要になったか（コード上の制約、要件、トレードオフ）
- **採用したアプローチ**: 具体的な決定内容
- **代替案**: 検討された他の選択肢（コミット履歴・PR・ドキュメントから読み取れる範囲）
- **結果**: 採用後の影響（ポジティブ / ネガティブ / 中立）
- **関連 ADR**: 本判断が前提とする / 上書きする ADR

### 2.2 既存 ADR との関係

新規 ADR が既存 ADR を覆す場合は、対象 ADR の Status を `Superseded by ADR-NNN` に更新するかをユーザーに確認する（更新は Phase 5 の追記提案と同じく承認制）。

### 2.3 「読み取れない」場合の扱い

- ユーザーから直接情報を提供してもらう（AskUserQuestion）
- それでも不明な点は「明示的な記録は確認できなかった」と本文に明記する
- 推測で埋めない（後日参照する人を誤誘導するため）

## Phase 3: ADR ドラフト生成

### 3.1 テンプレート

```markdown
# ADR-NNN: {判断のタイトル}

- **Status**: Accepted
- **Date**: YYYY-MM-DD
- **Deciders**: {省略可。役割名で書くこともある（例: フロントエンドチーム）}

## Context

{判断が必要になった背景・制約・要件を簡潔に。3-10 行が目安}

## Decision

{採用した決定内容。断定形で書く。具体的なライブラリ名・ファイル名・設定値を含めてよい}

## Consequences

### Positive
- {結果として得られたもの}

### Negative
- {引き換えに失ったもの・新たな制約}

### Neutral
- {ポジティブでもネガティブでもない影響、運用上の留意点}

## Alternatives Considered

### {代替案 1 のタイトル}
{内容と却下理由}

### {代替案 2 のタイトル}
{内容と却下理由}

## References

- {関連 ADR / Issue / PR / コード / 外部資料へのリンク}
```

### 3.2 Status の値

- **Proposed**: 提案中、未決定
- **Accepted**: 採用済み（デフォルト）
- **Deprecated**: 非推奨化されたが置換 ADR は無い
- **Superseded by ADR-NNN**: ADR-NNN によって置き換えられた

新規作成時は基本 `Accepted`。提案として残す場合のみ `Proposed`。

### 3.3 各セクションの書き方

- **Context**: 判断時点の状況のみを書く。「現在は」「最近は」のような時点語は避ける（後日読むと混乱する）
- **Decision**: 「〜にする」「〜を採用する」の断定形。トレードオフの説明は Consequences に分ける
- **Consequences**: 採用したことで何が起こるかを Positive / Negative / Neutral で分類する。Neutral は省略可
- **Alternatives Considered**: 実際に検討された案だけ。仮想的な対比のために書かない。情報が得られない場合はセクションごと省略してよい
- **References**: ADR への内部リンクは相対パスで書く

### 3.4 1 つの ADR の長さ

目安として 1 ファイル 1-2 画面分（50-150 行）。これを大きく超える場合は、複数の判断を 1 ファイルに詰め込んでいる可能性が高い。分割を検討する。

## Phase 4: ユーザー確認・修正

### 4.1 ドラフトの提示

生成した ADR の要旨を簡潔に提示する:

- ファイルパスと採番した番号
- Context の 1 行要約
- Decision の 1 行要約
- 代替案として記載した項目（あれば）

提示後、AskUserQuestion で確認:

```
ADR を作成しました: {成果物パス}

内容を確認して、修正したい箇所があれば指摘してください。
特に Context（判断の背景）と Alternatives（代替案）が事実と合っているかをご確認ください。
問題なければ「OK」と回答してください。
```

### 4.2 フィードバック対応

| ユーザーの回答 | アクション |
|---|---|
| 「OK」等 | Phase 5 へ |
| 修正指示あり | 指示に基づいて修正し、再度 4.1 に戻る |
| 「この判断は ADR にしないでよかった」 | ファイルを削除し、`architecture-doc` の説明文への織り込みを提案する |

## Phase 5: 関連 architecture.md への追記提案

ADR が確定したら、近傍のアーキテクチャドキュメントへの「関連 ADR」リンク追記をユーザーに確認する。

### 5.1 追記候補の探索

ADR 配置先の親ディレクトリから順に上に辿り、以下のファイルを探す:

- `architecture.md`
- `ARCHITECTURE.md`
- `docs/architecture.md`

複数見つかった場合は最も近いものを優先する。

### 5.2 追記の確認と実行

```
近くに {path} があります。このファイルの「関連 ADR」セクションに本 ADR へのリンクを追加しますか？
```

承認されれば、対象ファイルの「関連 ADR」サブセクション（無ければ「関連ドキュメント」セクション配下に新設）に以下を追記する:

```markdown
- [ADR-NNN: {判断のタイトル}]({相対パス})
```

「関連 ADR」サブセクションが存在しない既存ファイルへの追記時は、配置位置を提案してユーザーに確認する。

### 5.3 Supersede の処理

Phase 2.2 で既存 ADR を覆す判断と確認できた場合、対象 ADR の Status を `Superseded by ADR-NNN` に更新するかをここで再度確認する。承認されれば対象 ADR を編集する。

## トラブルシューティング

### 既存 ADR の番号体系が独特

例えば `0001-` のような 4 桁ゼロパディングや、`adr-001-` のような接頭辞付きの場合は、既存の形式に揃える。新規 ADR だけ異なる形式にしない。

### Context に書くべき情報が判断不能

ユーザーから直接情報を引き出す。それでも不明な箇所は「明示的な記録は確認できなかった」と書く。推測で埋めない。

### 1 つの判断にまとめるか分けるか迷う

以下のいずれかに該当するなら分ける:
- 異なる時期に独立に決まる可能性がある
- 一方が後日 Supersede される可能性が高い
- 読者が片方だけ参照する場面がある
